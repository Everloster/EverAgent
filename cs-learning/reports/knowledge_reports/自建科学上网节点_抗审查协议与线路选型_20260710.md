# 自建科学上网节点：从抗审查协议到线路选型的系统工程

> 用一台 VPS 自建"翻墙/科学上网"节点，本质是一场与审查系统的军备竞赛。
> 本报告把散落在实操里的经验，升级成一份系统的原理 + 选型工程学。
> 创建日期：2026-07-10

---

## 0. 定位：本报告与既有报告的分界

本领域已有一篇 [`Tailscale_WireGuard_VPN_原理深度解析.md`](./Tailscale_WireGuard_VPN_原理深度解析.md)，讲的是**"访问我自己的私有设备"**这条路线——WireGuard 加密隧道、Tailscale 零信任组网、NAT 穿透、DERP 中继，威胁模型是"公网/公司网络的窃听者"。

本报告讲**另一条完全不同的路线**：用 VPS 自建**抗审查的出海代理节点**，威胁模型是**国家级审查系统（GFW）的主动探测与深度包检测（DPI）**。两者虽都叫"VPN"，但目标、威胁模型、协议栈截然不同：

| 维度 | 私有组网（既有报告） | 抗审查出海（本报告） |
|------|---------------------|---------------------|
| 目标 | 安全访问自己的设备 | 突破审查访问开放互联网 |
| 对手 | 被动窃听者 | 主动探测的审查系统 |
| 关键指标 | 连通性、延迟、易用 | **不可检测性（indistinguishability）** |
| 代表协议 | WireGuard / Tailscale | VLESS+Reality / Hysteria2 / SS-2022 |
| 为何 WireGuard 不行 | —— | 握手指纹固定，秒级被封（见 §2） |

> **本报告的实操落地**以一台**东京 AWS Lightsail 自建节点**（Xray-core + VLESS+Reality + Vision）为真实部署案例，文中会多处以它为例对照。（该节点的完整配置档案属个人基础设施，不在本公开仓。）

## 1. 问题的本质：审查系统在检测什么

要理解为什么协议演化成今天这样，先要理解对手。GFW（Great Firewall）不是一个"防火墙"，而是一套**分布式的流量分类与阻断系统**，有两条正交的能力线：

1. **被动 DPI（Deep Packet Inspection）**：在流量经过时观测，靠包结构、时序、熵值、TLS 指纹、SNI 等特征分类。[Web] `https://kaiyanfan.github.io/blog/2026/gfw07/`
2. **主动探测（Active Probing）**：被动分析怀疑某连接后，GFW **主动发起自己的连接**去试探该服务器，看它像不像代理。[Web] 同上

关键认知：**DPI 不需要解密你的流量**。它只需要识别"承载流量的协议长什么形状"。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide`

- WireGuard 的握手发起包**永远是精确的 148 字节**（1 字节类型 + 3 字节保留零 + 4 字节 sender index + 32 字节临时公钥），结构从不变化。俄罗斯 TSPU 能在**第一个包**就近 100% 准确识别 WireGuard。[Web] 同上
- OpenVPN 有可识别的控制通道帧格式和时序，GFW 已可靠封锁多年。[Web] 同上

所以"加密载荷"从来不是关键——**握手和行为的形状**才是。这就是所有抗审查协议演化的主线。

## 2. 主动探测：审查系统如何"反问"你的服务器

这是自建节点最容易翻车、也最反直觉的一环。它决定了"为什么我的 Shadowsocks 用着用着就被封了"。

### 2.1 触发与时序

被动 DPI 把某连接标记为"可疑"后，记录服务器 IP + 端口，然后从 GFW 控制的机器发起探测。基于 2019 年的一次测量研究（IMC'20 论文）：[Web] `https://kaiyanfan.github.io/blog/2026/gfw07/`

- 研究者收到 **超过 5 万次探测**，来自 **12000+ 个独立 IP**
- 探测源 IP 主要属于两个自治系统：**AS4837（CHINA169）** 和 **AS4134（CHINANET）**——巧的是，你自建节点在国内的裸连出口往往也走这两个 AS
- 约 **90% 的探测**源端口在 32768–65535（Linux 默认临时端口范围）
- 时序：首个探测可在可疑流量出现后 **1 秒内**到达；**50% 以上在 1 分钟内**，多数在 20 分钟内；后续探测多在 1 小时内，个别晚至 10 小时

### 2.2 Shadowsocks 是怎么被"问"出来的

Shadowsocks 全加密、看起来像随机字节，GFW 无法构造合法包，于是用**反复试探 + 观察 TCP 层行为**：[Web] 同上

- **ATYP 爆破攻击（2015 年发现）**：利用流密码无完整性校验的弱点。Shadowsocks 首包的 ATYP 字段只有 3 个合法值（`0x01` IPv4 / `0x03` 域名 / `0x04` IPv6），且偏移固定。攻击者遍历该字节位置的 256 种密文值——若恰好**只有 3 次**服务器没有立即关闭连接，几乎实锤是 Shadowsocks。
- **随机字节攻击**：发随机字节，观察服务器反应。不同实现会表现出特征行为：`Timeout`（包太短、等更多字节）、`TCP RST`（解密后 ATYP 非法）、`FIN/ACK`。例如 OutlineVPN v1.0.6：50 字节随机探测回 FIN/ACK，更长的回 RST——**这种长度阈值差异本身就是指纹**。
- **FIN vs RST 的根因**是 Linux 内核 TCP 关闭行为：`close()` 前若已 `recv()` 读空缓冲区 → FIN/ACK；有未读数据 → RST。**一个纯粹的实现细节，就成了指纹向量**。
- **重放攻击（Replay）**：GFW 捕获你连接的首包，原样重放到服务器。Shadowsocks 无状态，会当成合法请求并回应——即便 GFW 解不开响应，"服务器有意义地回应了"本身就是证据。还会做首字节/第 16 字节（ATYP）的变异重放。

### 2.3 抗探测的三条铁律

现代协议要抵抗主动探测，必须同时满足：[Web] 同上

1. **用认证加密（AEAD）**——纯流密码反复导致致命漏洞（ATYP 爆破的根源）。
2. **对非法请求的响应必须一致**——要么一律超时（研究证明大量正常服务器也这样，不可指纹化），要么一律 RST（但要小心处理不完整包）。
3. **实现重放保护**——现代做法是**时间戳校验**：首包含客户端时间戳，服务器比对时钟，差值超阈值（如 30 秒）就拒绝。这样服务器只需缓存 30 秒内的 salt，而非永久存储。

> **对照实测案例**：该案例用 VLESS+Reality，从架构上就没有"自己的假响应"可被探测（见 §3.3），这正是它比 Shadowsocks 更抗封的根本原因。

## 3. 协议栈演化：从"加密载荷"到"我就是真的 HTTPS"

按抵抗审查的思路，代理协议经历了四代演化：

### 3.1 演化谱系

| 代际 | 代表 | 核心思路 | 为何被攻破 |
|------|------|---------|-----------|
| 一代·加密载荷 | Shadowsocks（早期）| 把内容加密成随机字节 | 高熵 + 无握手，主动探测（§2.2）+ 熵分析 |
| 二代·模仿 TLS | VMess+WS+TLS、Trojan | 做一次真 TLS 握手，伪装成 HTTPS 网站 | 用**自签证书**，与 Certificate Transparency 日志中真实证书不符；主动探测时假网页/响应头露馅 [Web] `https://fexyn.com/blog/vless-reality-protocol-guide` |
| 三代·成为 TLS | **VLESS+Reality** | 不模仿，**直接借用真实网站的真 TLS 握手和真证书** | 尚无有效被动检测（见下）|
| 并行·QUIC 系 | **Hysteria2 / TUIC** | 走 UDP/QUIC，主打弱网性能 | QUIC 指纹仍是检测信号（见 §4）|

### 3.2 为什么 Trojan 在 2025 年集体失守

Trojan 曾被认为"不可检测"，因为它做真 TLS 握手 + 对未认证探测者返回一个真实的网页。但它的致命伤：**用自签证书**。Certificate Transparency（CT）日志让"假的 Microsoft 证书"与真的一眼可辨；且主动探测时，Trojan 服务器返回的占位页 HTTP 响应头与它声称运行的真实软件有微妙差异。2025 年 8 月主动探测大规模化后，Trojan 部署被批量识别。[Web] `https://habr.com/en/articles/963022/`、`https://fexyn.com/blog/vless-reality-protocol-guide`

### 3.3 Reality 的核心诡计：没有"假"可供检测

Reality 是 Xray-core 于 2023 年初 v1.8.0 引入的特性。它的思路是**结构性的欺骗**——三样东西全是真的：[Web] `https://fexyn.com/blog/vless-reality-protocol-guide`

1. **真 TLS 1.3 握手**：客户端用 [uTLS](https://github.com/refraction-networking/utls) 生成与 Chrome/Firefox/Safari **字节级一致**的 ClientHello，SNI 填一个真实高流量网站（如 `www.microsoft.com`、`www.apple.com`）。
2. **真证书**：服务器**并发地**去连接真实的 `www.microsoft.com`，把它返回的真证书链转发给客户端。客户端像浏览器一样验证——CT 日志里查得到，签发者是公共 CA。
3. **真目标**：认证信息藏在 TLS 1.3 加密的 key-share 扩展里（`shortId` + X25519 公钥），被动观测者读不到。

关键分流：[Web] 同上
- **认证客户端**（5a）：TLS 会话建立后，作为 VLESS 帧的传输通道，VPN 数据在"看起来是到 Microsoft 的 HTTPS"里流动。
- **未认证探测者**（5b）：服务器**透明地把它代理到真的 `www.microsoft.com`**，探测者拿到真 Microsoft 的内容、响应头、TLS 记录——**一切都是真的**。

结论：主动探测者面对 Reality **没有任何"假"可以对比**。唯一能区分的是 key-share 扩展里那段加密的 `shortId`，而审查者读不到。要封 Reality，只能封掉伪装目标本身（Microsoft/Cloudflare/Apple）——而这些站 GFW 不敢封。[Web] 同上

### 3.4 Vision flow：消除 TLS-in-TLS 指纹

一个微妙但关键的点：当你在 TLS 隧道里访问 HTTPS 网站，会产生**"TLS 套 TLS"（TLS-in-TLS）**的嵌套模式——即使全加密，包大小和时序分析仍能看出来。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide`

XTLS Vision flow（`xtls-rprx-vision`）检测到内层已是 TLS 保护的载荷时，以最小额外包装直接透传，避免冗余加密。一篇 2024 年 USENIX 论文确认：**VLESS+Vision 流量在包大小和时序分析下，与直连伪装目标的 HTTPS 统计上不可区分**。[Web] 同上

> **对照实测案例**：配置里的 `flow: xtls-rprx-vision` 就是这个。这不是可有可无的选项——没有 Vision，TLS-in-TLS 仍是可用的检测信号。

### 3.5 SNI / 伪装目标（dest）的选择策略

Reality 的成败很大程度取决于 `dest`/SNI 选得对不对：[Web] `https://ask.csdn.net/questions/8853912`

- 选**全球广泛访问、有多 CDN 节点**的主流站（apple.com、microsoft.com）。
- **避免国内可达但境外不可达**的域名（易被黑白名单比对）。
- **证书链要小**——一个实测踩过的坑：用 `microsoft.com` 会因证书链过大导致 uTLS 握手失败（`handshake did not complete`），换 `www.apple.com` 才稳。
- 伪装目标必须是**你不控制**的真站。若指向自己的域名，审查者会发现"大量住宅用户连到某 VPS 上的域名"这一异常模式。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide`

## 4. QUIC 路线：Hysteria2 与"弱网之王"的代价

Reality 走 TCP，抗审查最强但受制于 TCP 的队头阻塞。另一条路线是走 UDP/QUIC 的 **Hysteria2 / TUIC**，主打**弱网性能**。

### 4.1 Brutal 拥塞控制：反其道而行

传统拥塞控制（BBR、Cubic、Reno）把**丢包**当作网络拥塞信号，一丢包就降速。Hysteria 的自研算法 **Brutal** 反过来：[Web] `https://habr.com/en/articles/1008554/`、`https://juejin.cn/post/7606793134375600191`

- 采用**固定发送速率模型**：你告诉它带宽（如 50 Mbps），它就锁定这个速率硬发，**忽略丢包信号**，只用 RTT 上升作为唯一的减速触发。
- 效果：在 **5% 丢包**环境下，Hysteria 仍能保持 **70% 以上吞吐**，而 TCP（Cubic）可能只剩 **10%**。[Web] `https://juejin.cn/post/7606793134375600191`
- 在移动/高丢包网络上，相比走 BBR 的 Reality 有 **2–3× 吞吐**。[Web] `https://lunaire.app/en/blog/hysteria-2-vs-vless-reality`

一篇 USENIX **FOCI'25 论文**（*Is Custom Congestion Control a Bad Idea for Circumvention Tools?*）证实：Cubic（无论 TCP 还是 QUIC）作为基于丢包的算法，在 5% 丢包率下性能会下降**几个数量级**，而 Hysteria/Brutal 的定速模型能有效利用链路容量。[Web] `https://ayushmishra.net/pdfs/foci25-customcc.pdf`（经 WebSearch 摘要，PDF 全文抓取失败 [待验证：具体图表数字]）

### 4.2 代价一：不公平与"损人利己"

Brutal 忽略丢包硬发，意味着它**会挤占同链路上其他 TCP 流的带宽**——对邻居不公平。FOCI'25 论文正是围绕这种"定速 CCA 对正常流量是否掠夺"展开的批判性研究。[Web] 同上 [推测] 对于家庭共享带宽场景，长期跑 Brutal 满速可能影响家人其他设备的体验。

### 4.3 代价二：QUIC 指纹仍是检测信号

Hysteria2 伪装成 HTTP/3，但它走 UDP/QUIC，而 **QUIC 的指纹本身就是一个检测信号**。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide` 2026 年 4 月 GFW 升级后加入了 **QUIC SNI 检查**。[Web] 同上 且 GFW 技术评述有专章（gfw13）讲 Hysteria 的检测。[Web] `https://kaiyanfan.github.io/blog/2026/gfw13/`（未深读 [待验证]）

### 4.4 选型结论：Reality vs Hysteria2

| 场景 | 首选 | 理由 |
|------|------|------|
| 稳定有线/家庭宽带 + 强审查 | **VLESS+Reality+Vision** | 抗审查最强，稳定网下速度足够 |
| 高丢包移动网 / 跨境弱网 | **Hysteria2** | Brutal 在丢包下 2–3× 吞吐 |
| 无审查网络（纯加速） | WireGuard | 最快最简，但一旦有 DPI 就废 |

> 很多人的实践是**两者都部署**：Reality 做主力/保底，Hysteria2 做弱网备用，客户端里一键切。

## 5. 线路与 VPS 选型：性能瓶颈的真相

这是自建党最大的认知误区来源。**协议决定"能不能连"，线路决定"快不快"**，两者正交。

### 5.1 核心事实：瓶颈通常不在 VPS，而在跨境线路

以该东京自建节点的实测为例：
- VPS 本身 → Cloudflare：**605 Mbps**（东京 AWS，本地测出 75 MB/s）
- 客户端（国内）→ 经 VPS → Cloudflare：晚高峰仅 **~2 Mbps**
- 直连 Cloudflare（裸连，同样走公网出海）：也是 **~2 Mbps**

结论：直连和自建 VPS 的下载速度几乎一样 → **瓶颈不在 VPS、不在协议，而在"客户端所在地运营商的国际出口"**（电信 163 晚高峰拥塞）。本机 BBR 等调优已到顶，无法突破运营商那一段。

### 5.2 回国/出海线路分档（决定晚高峰体验）

中国跨境线路分档明显，这是**商业机场比自建裸连快的根本原因**：[Web] `https://www.163.com/dy/article/KNBPPRMG05318KHZ.html`、`https://m.sohu.com/a/1028393312_122551421/`

| 线路 | AS / 特征 | 华南→香港延迟 | 晚高峰稳定性 | 谁在用 |
|------|----------|--------------|-------------|--------|
| **CN2 GIA**（顶级）| AS4809，全程 59.43.* 节点 | 15–25ms | 几乎无拥堵，丢包 <0.1–0.5% | 优质商业机场、贵价 VPS |
| CN2 GT | AS4809 但优先级低 | 稍高 | 高峰有波动 | 中端 |
| BGP 多线 | 多运营商融合 | 50–80ms | 一般 | 普通建站 |
| 普通公网 / 163 | AS4134 / AS4837 | 高、晚高峰拥塞 | 差 | **裸连 + 自建 AWS 直连** |
| IEPL / IPLC | 国际专线，不过公网墙 | 最稳 | 最优（但极贵）| 高端机场 |

关键：**AWS Lightsail / 大多数云厂商的默认出口走的是普通公网（163）**，天生不优化回国路由。商业机场贵，贵在它买了 CN2 GIA / IEPL 专线，避开了拥塞的公网出海段。

### 5.3 自建想改善晚高峰，只有两条真路

1. **换落地机为回国优化线路**（单机搞定，推荐）：把机器换成本身就针对中国访问优化的，如**腾讯云香港轻量**（地理近、腾讯网络到大陆好）、**搬瓦工 CN2 GIA-E**（专门回国优化）。同样自建，**换线路比换配置有用得多**。
2. **加国内中转**（复杂，不推荐个人）：国内中转小鸡 → 落地机，中转段走优化线路。等于自己搭半个机场，成本 + 运维 + 大陆 VPS 需备案/易被查，性价比低。

> **务实结论**：为让自建在晚高峰也快而加中转/换贵线路，经济上往往不如直接用一个商业机场兜底。低峰用自建（省钱、自控、大带宽），晚高峰刚需切商业机场。

### 5.4 成本与止血

自建的隐藏成本是**流量费**。一个真实教训：某台旧 EC2 因跑 BT/DHT 大流量欠费 $37 被停机。自建党务必：设置账单告警、**绝不在节点上跑 BT/DHT 等大流量任务**、选带充足流量包的套餐（如 Lightsail $7 档含 2TB/月出站）。

## 6. 客户端与订阅分流生态

有了节点，还要解决"多设备统一管理 + 智能分流"。

### 6.1 客户端与内核

- **内核**：`mihomo`（Clash.Meta 后继，支持 VLESS+Reality/Hysteria2/全协议）、`sing-box`（新一代，协议全、配置现代化）、`Xray-core`（服务端主力）。
- **GUI 客户端**：Clash Verge Rev（跨平台，mihomo 内核）、v2rayN（Windows）、sing-box 官方 App（iOS/Android）。
- **该案例的选择**：服务端 Xray-core v26；客户端 Clash Verge Rev（mihomo v1.19.x）。

### 6.2 订阅链接：多设备同步的关键

自建党的高级玩法是**把配置托管成一个 URL**（订阅链接），多设备"订阅"即可，改规则只需在服务端换一次文件，所有设备刷新即更新。常见做法：用 nginx 在非标端口托管、只响应 `/[hex]/[hex].yaml` 精确路径防扫描、订阅链接等同密码。

> **反面案例**：商业机场 MonoCloud 会**故意关闭订阅链接功能**（防转卖/锁客户端），本地配置也加密存储、自研内核不落地 Clash 配置——三重锁死，无法干净地导出到通用客户端。这正是自建的一个隐性优势：**配置完全自己掌控**。

### 6.3 分流规则：别自己造轮子

分流（国内直连、国外走代理、AI 服务专用、广告拦截）用**开源规则集**（`rule-providers`），与主流机场同源，不必手写。典型组合：
- 国内外/广告：`Loyalsoldier/clash-rules@release`（jsdelivr CDN）
- AI 专用：`blackmatrix7/ios_rule_script` 的 OpenAI/Claude/Gemini 规则集
- 个人自定义规则放 `rules:` 段最前（优先级最高）

geosite/geoip 数据库提供了域名/IP 的分类基础，规则集在其上做分组路由。

## 7. 端到端组装：一台节点的完整决策链

把前面所有维度串成一条自建决策链：

```
1. 目标环境有审查吗?
   ├─ 无  → WireGuard（最快最简）
   └─ 有  → 继续
2. 网络稳定吗?
   ├─ 稳定有线  → VLESS+Reality+Vision（TCP，抗审查最强）
   └─ 高丢包移动 → Hysteria2（QUIC+Brutal，弱网 2-3×）
3. 伪装目标(dest)怎么选?
   → 全球主流站、多CDN、证书链小、你不控制（apple/microsoft/cloudflare）
4. 落地机线路?
   ├─ 省钱自控   → AWS/普通云（公网出海，晚高峰认怂）
   └─ 要晚高峰快 → 腾讯云香港轻量 / 搬瓦工 CN2 GIA
5. 抗探测三铁律都满足? （AEAD / 一致响应 / 重放保护）
   → 现代 Reality/Hysteria2 默认满足；老版 SS 要升级到 SS-2022
6. 多设备管理?
   → nginx 托管订阅链接（防扫描路径）+ 开源 rule-providers 分流
7. 止血?
   → 账单告警 + 绝不跑 BT/DHT + 关闭 access log（隐私）
```

## 8. 未解问题与前沿

### 8.1 IP 信誉——Reality 唯一的软肋
Reality 从协议层几乎不可检测，但审查者转向 **IP 信誉分析**：注意到"某 IP 既收住宅用户连接、又代理到 Microsoft"这种异常模式。俄罗斯 TSPU 已用此封了部分 VPS IP 段，早期社区报告显示对正确部署的 Reality 检测率仍 <5%。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide` [待验证：中国 GFW 对应数字] 这解释了为什么"独享 IP、干净 IP、住宅 IP"越来越值钱。

### 8.2 军备竞赛没有终点
GFW 技术评述系列的收尾观点：**探测方法一旦被研究和公开，很快就会过时**——协议能针对性打补丁，GFW 再升级。[Web] `https://kaiyanfan.github.io/blog/2026/gfw07/` 2026 年 4 月 GFW 的升级（物理拔除数千中继、加熵分析、QUIC SNI 检查、DoH 识别）就是最新一轮。[Web] `https://fexyn.com/blog/vless-reality-protocol-guide` [待验证：该次升级的独立信源]

### 8.3 自建 vs 商业机场的长期分工 [推测]
自建的优势是**配置自控、无订阅锁、隐私（日志自己管）、大带宽**；劣势是**线路是短板**（除非买贵线路）、需自己运维、IP 需自己养。商业机场反之。长期看，**两者共存**可能是刚需用户的常态——自建保底 + 机场兜晚高峰。

## 9. 结论

1. **抗审查的核心是"不可区分性"，不是"加密强度"**。协议演化四代，终点是 Reality 的"我就是真的 HTTPS"——没有假可供检测。
2. **主动探测是自建最易翻车处**：老 Shadowsocks 因无认证/响应不一致/无重放保护被批量识别；现代协议靠 AEAD + 一致响应 + 时间戳重放保护抵抗。
3. **协议决定能不能连，线路决定快不快**，两者正交。自建的性能瓶颈通常在跨境公网出口，不在 VPS 或协议；BBR 等本机调优有天花板。
4. **务实工程学**：Reality+Vision 做主力，Hysteria2 做弱网备用，开源规则集做分流，nginx 托管订阅做多设备同步，账单告警 + 不跑大流量做止血。想要晚高峰快只能换回国优化线路或用商业机场兜底。

## 思考与追问

1. **IP 信誉战会走向何方？** 如果审查者最终能靠"住宅用户 → 代理到大站"的行为模式高效封 IP，那 Reality 的协议优势会被 IP 层抵消。届时"住宅 IP 代理 / CDN 前置 / 域名前置（domain fronting）"会不会重新成为主线？CDN 厂商（Cloudflare）的态度是关键变量——值得追一篇"域名前置与 CDN 中转"的专题。

2. **Brutal 这类"损人利己"的定速拥塞控制，是否会被审查系统反过来当作检测特征？** FOCI'25 论文关注的是公平性，但"忽略丢包硬发"的流量模式本身是否统计上异常、可被 DPI 用作 Hysteria 指纹？这与 §4.3 的 QUIC 指纹是两个不同的检测面，值得深挖 gfw13（Hysteria 专章）验证。

3. **自建到底值不值？** 如果把"运维时间成本 + 线路短板 + IP 维护"折算进去，对一个普通用户，自建相比一个 CN2 GIA 商业机场的真实性价比是多少？这需要一个量化模型：把"每月省的钱 / 每月花的运维时间 / 晚高峰可用性差值"三者放在一起算。或许结论是"自建的价值主要在学习和自控，不在省钱"。
