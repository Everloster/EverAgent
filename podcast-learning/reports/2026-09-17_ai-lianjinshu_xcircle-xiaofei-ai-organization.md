# 管理工作减少之后，谁负责、怎样分钱

这期不是一套已经验证的组织改造配方，而是一场没有完全达成共识的讨论。小飞带来鹿客、XMind 等转型案例，认为 AI 可以承担更多信息汇总与协作，让团队围绕业务结果重新组合；徐文浩不断追问，错误由谁负责，复杂业务能否由少数人闭环，以及效率提高之后有没有更多收入。任鑫则把两边的说法放到具体情境里检验。

最值得留下的判断是：**减少汇报和交接，不等于取消责任、专业分工与资源取舍。** 只有这些关系也说清楚了，“AI 原生组织”才不只是新的组织图。

本文根据完整访谈整理，并对照节目引用的 Dorsey、Botha 原文。公司变化和数字按嘉宾的经验归因，未取得内部经营、绩效或工时数据，不把标题转写成所有管理岗位都将消失的预测。

## 三个人究竟在争什么

[节目](https://www.ximalaya.com/sound/1015908823)介绍小飞为 XCircle 创始人，长期参与新的组织形式实践，现帮助企业做 AI 原生组织转型。XCircle 同时提供相关 Agent 产品，因此案例来自咨询和产品实践，不能等同于独立评估。

开头约 04:36 起，任鑫先问：过去已有小队、合弄制、人单合一等尝试，为什么没有普遍成为成功的组织范式？小飞承认，看到的规模化成功案例仍然有限，随后提出 AI 可能改变的三件事：信息如何流动、专业工作链条能否缩短，以及利益如何分配。

徐文浩的疑问在约 19:17 后贯穿全场。他认可协作摩擦可以减少，但认为真实业务仍需要有人判断和负责。讨论最容易混淆的，是一方在描述希望出现的两三年后的形态，另一方在追问今天如何落地。约 45:56，小飞对此作了明确区分，并将当前实践形容为仍在探索中的混乱。

## 原文没有取消负责人和教练

节目引用的是 Jack Dorsey 与 Roelof Botha 于 **2026-03-31** 发布的 [From Hierarchy to Intelligence](https://block.xyz/inside/from-hierarchy-to-intelligence)。文章把层级的一部分作用解释为信息汇总与传递，并提出由持续更新的公司、客户信息模型承担更多协调。

这里的“公司世界模型”不是已经证明能够预测所有组织行为的神经网络。作者首先指向可记录的决定、讨论、代码、计划、问题和进展；客户模型则从交易等信号出发，进一步的因果和预测能力仍在演进设想中。

原文保留了三类人的角色：

| 角色 | 仍由人承担的工作 |
|---|---|
| Individual Contributor | 建设和运行具体能力、模型、系统及界面，需要专业技能 |
| DRI，直接责任人 | 对跨团队问题和客户结果负责，协调相应资源 |
| Player-coach | 自己参与工作，同时培养他人、传递技艺 |

作者还将新情况、伦理和高风险判断留给人，并明确说转型处于早期、部分尝试可能先失败。因此，这篇原文是一种组织设计主张，不是管理活动已全部消失的实验证明。

把信息路由交给 AI，仍需要判断哪些信息是真实的、谁可以访问、遇到冲突听谁的，以及谁有权采取行动。共享上下文可以减少重复解释，但不会自动解决这些问题。

## 一个 Agent 有 owner，为什么仍没有回答完“谁负责”

约 22:20—31:40，小飞提出每个 Agent 都应有 owner，像需要有人带教的实习生。徐文浩继续追问：如果我做了一个 Agent，别人拿去投广告或发布代码，出错算开发者的，还是使用者的？

这个追问揭示了“owner”一词里的多种职责。下面是本文按访谈问题拆开的**示意分工**，不是某家公司已实施的制度：

| 责任 | 要明确的事情 |
|---|---|
| Agent 维护 | 适用范围、版本、已知限制和故障修复由谁维护 |
| 业务选择 | 为什么用它处理这件事，结果对客户是否合适，由谁判断 |
| 执行权限 | 谁允许发布、采购、投放或消耗预算，额度与条件是什么 |
| 异常处理 | 谁停止操作、回退、通知受影响的人，并组织后续修复 |

这些职责可以由同一个人承担，但不能因为名字都叫 owner 就省略。工具开发者能保证某些接口行为，未必能替所有使用场景判断业务后果；使用者做了决策，也不必然了解所有内部实现缺陷。

徐文浩担心，如果所有使用损失都推给工具提供者，对方可能只愿提供只读查询，协作又回到原来的职能边界。小飞则强调，多因一果的错误原来就存在，轻微问题可以共同修复，严重问题仍需具体处理。两人并没有就一套责任规则达成共识。

本文的理解是，明确责任的目的首先应是让决策、恢复和改进能够发生，而不是预先决定谁承担全部经济损失。把接口约束、使用条件和决策记录留下，比出事后只找一个名义上的 Agent owner 更有帮助。

## 分钱与背锅，都是在问贡献怎样归因

任鑫将两者联系起来：出错时要知道谁负责，成功时也要判断收益属于 Agent 的开发者还是使用者。加入共享 Agent 后，贡献不一定能简单归到单个人。

小飞举了一个实践方向：中后台由输出管理要求转为提供 Agent 服务，前台产生业务收益后，按一定比例支持中后台。任鑫则谈到另一个公司先奖励制作、使用 Agent 的人，暂不精细分配全部功劳。这些是案例和尝试，不是统一的激励标准。

需要区分投入和结果。Agent 数量、token 消耗、生成了多少文档或代码，反映了部分活动；它们不直接说明创造了多少净价值。共享基础设施可能让多个团队受益，短期可见的前台收入也可能依赖长期维护。如果只奖励容易计数的产出，低可见度的质量、支持和风险处理工作可能被忽略。

约 80:32，小飞进一步介绍用 AI 汇总工作结果、提出奖金分配建议，并由管理者补充遗漏信息。它可以帮助整理资料、暴露理由，却不能使公平标准自动成立。谁定义“贡献”，哪些信息缺失，团队能否解释和复核，仍由组织决定。管理者觉得建议更全面，与建议经过独立公平性验证，是不同层面的证据。

节目中“AI 杠杆”“一人加 AI 产生数倍生产力”的展示，没有披露完整换算方法，本文不把它换算成可替代的人数或薪资。模型成本属于投入，经过验收的业务结果、质量与总成本才更接近需要评价的产出。

## 团队变小，不意味着业务链自然闭合

约 47:05—64:23，小飞强调围绕结果组成小队，减少旧汇报线对资源和优先级的拉扯，并建议逐步压缩到两到四人。小队不只是临时从几个部门各借一个人：如果大家的评价与资源仍握在原来的职能负责人手里，新的项目负责人未必真正有权推动工作。

这个观点解释了为什么改一张组织图可能没有效果。但任鑫、徐文浩也指出，做一把新智能锁，还涉及供应链、制造、销售与验证；好产品和最终收入之间可能隔很久。换成圈子、role 或 DRI 的名称，不能使物理依赖和专业要求消失。

小飞随后承认，专业分工并非完全消失，复杂业务也不能立即符合愿景。较短的链路可以更彻底地由个人或小队承担，长链路则先减少交接、缩短周期。这一补充比“任何产品都只需两个人”更接近整场讨论。

一个**自拟瓶颈算例**可以说明为什么单点提效不足。假设流程必须依次经过方案准备与验收：准备每天能做 20 项，验收每天只能处理 10 项。AI 将准备提高到每天 40 项，整个流程的完成能力仍受后一步限制。如果继续按更快速度投入，积压还会增加。

这不是某家公司的测量结果，只是在说明应该观察哪里：从需求出现到可用结果交付，等待发生在哪里，返工多少，质量有没有改变。代码生成更快、会议更少，可以是中间收益，却不能直接等同于收入翻倍。

## HR 的案例，是重新分配职能，不是所有人事工作消失

约 64:23—73:49，小飞介绍鹿客把原有 HR 职能重新组合，将人和 AI 资源一起考虑。来源使用 Human AI Resource Office 的英文展开，缩写在简介和转写中有 HARO/HERO 等写法；本文以“人和 AI 资源团队”称呼，避免假定已核实正式命名。

按嘉宾描述，工资、社保等基础事务仍须可靠完成；更贴近业务的一侧，会先检查新需求能否通过 Agent、流程调整或角色重组解决，再决定是否招人。相关负责人被描述为既懂技术、战略，又能进入业务现场；复杂 Agent 由专门人员建设，较小工具也可由一线自己搭建。

这里变化的是资源配置方式，而非仅把 HR 改个名字。招聘也没有因为“AI 优先”就完全消失。要作出好的配置决定，需要知道任务边界、可用工具能力和现实约束，而不能只把某个流程自动化比例当作结论。

人才部分同样不能只保留前半段的年龄比较。小飞后来明确补充，有丰富领域经验、又能用好 AI 的资深人员也在发挥作用。“纯做汇报的人需要转向业务”是嘉宾对其案例的观察，不是年龄或岗位名称决定个人价值的证明。

## 案例数字应该怎样读

| 节目中的说法 | 证据范围与容易混淆之处 |
|---|---|
| 建议小队为 2—4 人 | 是设计方向；嘉宾也说部分团队仍在调整，不是所有客户都已达到 |
| XMind 转型约半年后，二十来位原 manager 无人报告管理时间超过三成 | 是交流中的时间自述，不是独立工时审计，更不是全部员工或管理者减少七成 |
| 某公司给 Agent 制作者涨薪 30% | 任鑫讲述的个别激励尝试，未给出长期成本与绩效效果 |
| 某些公司人员成本下降、部分业务好转 | 缺少同口径的前后数据和对照，不能隔离 AI、组织调整与人员变动的各自影响 |
| “AI 生产力”折算为数倍人力 | 未公开指标、基线与质量校验，不能直接理解为数倍收入或确定的裁员空间 |
| 一家公司集体弃用飞书 | 匿名公司的工具选择与体验，不能推导某协作产品不支持 Agent，或所有公司都应更换 |

尤其是 XMind 的时间自述，小飞自己给出的解释是：管理仍然存在，但不再一定是一份全职的信息协调工作。这个说法也与 Block 的 player-coach 角色更接近，而不是“再无管理职责”。

## 公司为什么仍可能有价值

约 37:45—45:56，徐文浩提出另一个问题：如果一个人靠 AI 就能端到端完成全部业务，为什么还留在公司？模型 API 并不是只有公司才能购买。

小飞认为，个人加平台的合作可能增加，组织可以更开放；徐文浩则强调人的注意力有限，竞争中仍会需要伙伴与分工。两者的判断并不完全相同，小飞也明确表示自己期待的形态未必成为主流。

从这场讨论可进一步推导：公司需要说明它提供了哪些个人不易独自取得或维护的条件，例如客户关系、品牌信任、专业支持、供应链或共同承担不确定性的能力。大家都能买到模型，并不意味着这些条件也自动相同；反过来，若组织只是增加审批和转述，它的价值确实更容易被质疑。

“可以单干”因此不等于“单干总是更有利”，一人公司与平台合作也不天然成功。这里讨论的是新的可选组织方式，不是对听众离职、创业或裁员的建议。

## 比先拆部门更具体的起点

节目约 87:32 给出的三步，反而比宏大的组织命名更容易检验：先画出价值链，明确客户需要什么；再用 Agent 减少自己反复处理的工作，释放时间；随后找到整条链真正的制约点，优先改善那里。

本文建议，在这个起点上再留下可复查的基线：原来交付一项结果要多久，等待和返工在哪里，质量怎样验收，由谁作最终决定。改变后用相同口径再看。如果只是把耗时从制作挪到审核，或把责任转给另一个团队，系统并没有必然变好。

小飞最后谈到的服务重点也带有选择性：较小、较新的团队，或业务本身 AI 原生的公司更受关注；口述中使用了“或”，随后又补充大公司的独立业务小团队可以尝试。不能把“150 人以内、成立三年以内、业务 AI 原生”加工成严格且必须同时满足的规则，也不能说嘉宾断言所有老公司都无法转型。

这期留下的是几组需要继续跟踪的问题：谁真正得到决策权，谁承担维护和恢复，效率是否转成更好的交付，组织又如何承认不同形式的贡献。没有共识本身不是缺点；将这些问题提前暴露出来，比只宣布减少层级更接近实际变革。
