# 微软 CoreAI 访谈：模型会写查询、能交付表格，为什么企业 AI 仍然需要大量产品工作

这期英文访谈围绕一个经常被模型演示掩盖的问题：原型已经能工作，为什么进入真实业务以后仍然交不了差？微软 CoreAI 产品副总裁 Marco Casalaina 的回答，落在上下文、权限、评价标准与实际采用上。[1]

最有用的结论是：**模型能力扩大了能做什么，产品工作则决定它在具体组织中怎样被正确、安全地使用。**

## 1. 模型不是完整产品，定制也不只有训练权重一种含义

**节目约 01:13—06:00。**

Marco 首先强调，模型需要进入 Harness、工具与交互系统，才能产生实际工作结果。通用模型更强，并不意味着专门任务和定制需求消失。

访谈以本地转写和文档版面处理为例：具体人名、跨页表格、翻译后的版面等要求，会影响什么结果才真正可用。

这些例子不应被读成“必须自己训练模型”。实际定制可能涉及提示、词汇、数据处理、工具、模型选择或后训练。应该先找出任务失败在哪里，再选择改动哪一层，而不是把所有产品问题都称为模型不足。

节目中关于微软产品能力与处理规模的介绍属于嘉宾自述，本文没有进行产品测试或性能复现。

## 2. Agent 有自己的名字，不等于有独立的安全边界

**节目约 06:00—12:56。**

Marco 区分了给助手起一个名字，与让它在独立安全上下文中执行。其描述的企业 Agent 可以拥有独立通信和文件空间，再按需要授予访问权限，而不是直接借用一个高权限用户的全部操作能力。

这个设计的目标是最小权限、可识别的执行主体与可管理的责任关系。但需要避免进一步简化成“独立身份必然比委托访问更安全”。

以本次查阅的 Microsoft Graph 官方文档为例：[2]

- 委托访问同时受到用户自身权限与应用获授 scope 的约束。
- 应用身份访问不依赖登录用户，某些 application permission 的范围反而很广。
- 是否使用哪种模式，应由实际需求和最小权限原则决定。

因此，风险来自过宽授权与边界不清，而不是某一个身份模式的名字。一个独立 Agent 若被授予过大的范围，仍然可能越权；一个经过严格限定的用户委托，也不等于自动继承所有权限。

企业需要明确的至少包括：Agent 为谁工作、能访问哪些资源、哪些动作需确认、如何撤销，以及怎样区分人与 Agent 的操作记录。

## 3. 宝马案例：SQL 写得出来，不代表模型知道字段是什么意思

**节目约 17:32—23:51。**

Marco 介绍了 BMW MDR 测试车辆数据的案例。按其说法，车辆带有大量传感器，过去只有少数熟悉数据的人能有效查询；团队花了约半年跨部门整理数据字典，才让更多工程师能用自然语言提问。

这里的工作不是单纯把数据搬进模型，而是解释：传感器测什么、数值有什么含义、相关业务术语怎样映射到它，以及用户会如何提问。

这个案例可以拆成四个层次：

1. **格式可读**：文件或数据库能够被访问。
2. **查询合法**：生成的 SQL 等语句能执行。
3. **业务语义正确**：选到了与制动、天气等问题真正对应的数据。
4. **结果可解释**：用户知道数据范围和结论限制。

前两项成功，不能自动证明后两项成功。模型能生成查询，也不能凭空知道只有企业内部专家掌握的定义。

“约半年”和“数千传感器”是嘉宾对项目的描述，不代表所有企业都需要同样周期，也不是模型训练耗时。本文没有取得宝马原始项目数据，不能量化数据字典单独带来的效果。

## 4. 交回一张完整价格表，并不等于定价正确

**节目约 23:51—28:47。**

访谈中的公寓定价例子说明了通用指标的盲区：Agent 收到房源表，返回填满价格的表。若只看任务完成，似乎已经成功；但某类户型的价格可能明显不合理。

这不意味着任务完成度、相关性或来源一致性毫无价值，而是它们不能替代业务标准。回答基于检索资料，也不证明资料本身正确，或模型选择了正确的比较对象。

对于定价任务，具体标准可能要求考虑面积、卧室与卫生间数量、可比房源和其他明确条件。真正的改进，是把“看起来做完了”转成可检查的要求。

同样，“模型声称考虑了某因素”也不应直接算作通过。能否观察它用了什么资料、是否遗漏关键条件，以及输出是否进入合理范围，都需要业务定义与证据。

## 5. Rubric 要从设计时写，并在真实错误中修订

**节目约 28:47—36:09。**

Marco 建议，在设计 Agent 时就写清评价标准，而不是上线后再临时决定什么算成功。访谈提到将要求拆成细项、赋予重要性，并事先讨论可接受的错误类型和阈值。

其中更重要的是反馈内容：用户不只说“错了”，还要说明为什么错。原因可能带来一项新规则，也可能修订旧规则的适用条件。

这个过程至少需要三种工作：

- 业务专家解释规则及例外。
- 评测维护者把它转成可重复检查的材料。
- 开发者改进 Agent，并验证旧问题是否真的改善、其他问题是否回归。

但分权重并不能代替硬边界。若某项要求是不得泄露他人信息，就不应因为其他项目得分很高而被平均掉。**不可违反的授权约束应有独立控制；允许优化的质量维度才适合讨论加权取舍。** 这是本文的工程分析，不是对某个 Foundry 实现的审计结论。

还要注意，模型与 rubric 同时改变，会让前后分数难以比较。应保留版本和固定回归样本，避免只把标准改得更宽松就称为产品进步。

## 6. 试点期不是发布前的形式手续

**节目约 12:56—17:32、38:02 之后。**

访谈把“得到使用者的接受”与“技术上已经部署”分开讨论。员工、客户和社区可能对 AI 的介入有不同顾虑。强行把功能推到面前，不等于它已经解决真实问题。

较长的试点期，可以让真实用户提出原型阶段没有想到的要求和错误，再把这些信息带回标准与系统。但“更长”不是一个统一月数，应该对应风险、使用频率与需要观察的情况。

试点也不能只是收集满意度。对业务系统，更有意义的问题包括：

- 出错是否被及时发现？
- 人是否真的有时间与权限纠正？
- 原本节约的执行成本，是否被审核和返工抵消？
- 用户不愿使用，是交互问题、可靠性问题，还是根本没有需要？

这些问题让采用过程成为检验产品假设的一部分，而不是把所有阻力都解释为用户不懂 AI。

## 7. 新岗位的价值，来自判断与衔接，不只来自会调用模型

**节目约 36:47—结束。**

Marco 提到评测维护者、FDE，以及每个工程师对 AI、上下文和评价方法的基础理解。可迁移的价值在于：把业务问题转成清楚的要求，把现实反馈变成可复用的验证，再把系统放进组织中可靠运行。

这不构成对就业数量、薪资或某个岗位长期前景的统计结论，也不意味着这些角色的全部概念都由这一轮 AI 才创造。

访谈最后鼓励亲自尝试工具，而不只观看演示。这里的实践并不必然是制造一个大型应用；一个足够小、能够说明输入、成功条件和失败方式的任务，也可以训练判断。

## 本次学习的落点

这期把企业 AI 中常见的三个跳跃拆开了：

- 会写查询，不等于理解企业数据。
- 能返回结果，不等于满足业务要求。
- 有独立身份，不等于权限已经安全。

解决这些问题需要明确上下文、业务标准、授权边界和真实反馈。模型进步不会使这些职责消失，反而让它们更决定最终产品是否值得使用。
