# 用吃豆人检验决策模型：何时普通 LLM 已够用，何时值得蒸馏一个端侧专家

这期教程的标题很容易被理解成“普通模型全面替代 Jev”。但英文教学主体给出的结论更窄，也更有价值：**先在自己的任务上找到有效替代方案，再决定哪些成本、延迟或部署条件值得自己控制。**[1]

鸭哥用吃豆人式游戏比较托管决策模型、普通语言模型和专门蒸馏的小模型。本文结合音频与配套代码仓文档学习实验设计，没有运行这些模型或复现游戏成绩。

## 1. 模型没有看屏幕，而是在读适配层提供的状态

**节目约 06:01—10:06。**

游戏中的模型接收到的是当前状态的文字描述，以及可以选择的方向。描述包括附近危险、豆子距离等信息；模型并不是直接看一段视频后自主理解整个游戏。

因此，这个系统至少有三个组成部分：

- 游戏引擎维护真实状态。
- 适配层把状态变成模型可以读取的输入。
- 模型在允许选项中选择一个动作。

这使问题更接近“给定状态，作一个低延迟决策”，而不是端到端视觉控制。比较时，各玩家使用相同的当前状态信息，不给某个玩家额外的未来信息。[2][3]

共享事实并不意味着不同模型的 Token 数或内部提示完全相同。分词器、系统提示和服务端实现仍然可能不同。

## 2. 两种时钟，测量的是两种能力

仓库区分两种运行方式：[3]

| 时钟 | 游戏怎样运行 | 结果包含什么 |
| --- | --- | --- |
| `realtime` | 游戏继续前进，晚到的动作可能过期 | 决策质量与实际延迟共同决定表现 |
| `lockstep` | 游戏停下来等待回答 | 更偏向隔离观察决策质量 |

常规比较使用固定种子 100—109、十局游戏、每局五分钟上限、1 倍速和真实时钟。得分是每局平均吃掉的豆子数；延迟是决策时间中位数。[3]

这解释了为什么一个更会思考的大模型，不一定更会玩实时游戏。它可能作出更好的选择，却在答案返回前已经错过路口。

反过来，如果让游戏等待，大模型得到的高分就不能与真实时钟成绩直接混在一张排行榜里。这个区分同样适用于真实系统：离线决策质量与线上响应时限，是两种约束。

## 3. 普通模型能不能成为有效基线

课程与配套文档报告，在相同的当前状态输入下，一些普通小型聊天模型配合受约束的 JSON 输出，可以达到或超过 Jev 的吃豆人成绩。[1][2]

摘取与课程主线有关的数据：

| 玩家 | 平均吃豆数 | 决策 p50 |
| --- | ---: | ---: |
| Jev 1.13.0，托管服务 | 178 | 115 ms |
| Phi-4-mini，普通模型 | 232 | 187 ms |
| 蒸馏的 0.8B 专家模型 | 425 | 55 ms |

这些是作者测量值，不是本文实验。配套文档说明，本地玩家运行在 M3 Ultra，Jev 经公网调用；因此延迟反映的是具体部署路径，不能直接解释成纯模型算法的固有速度。[3]

受约束输出解决了一部分语法问题，但 JSON 可解析不等于动作正确。作者在测试中观察到的零无效输出，也不构成对所有输入永不失败的证明。实际系统仍需检查合法动作、超时和过期结果。

最重要的习惯是先建立基线。若简单规则或现成模型已经满足任务，追逐一个新名称未必创造额外价值；若某项要求不能满足，再针对它优化。

## 4. 蒸馏把慢判断搬到离线阶段，但没有消除成本

**节目约 14:24—20:11。**

课程先展示前缀复用、批量提问和直接读取选项分数等优化，再用更大的模型离线产生训练标签，训练一个较小的学生。[1]

配套蒸馏指南给出的流程是：访问游戏状态、由教师标注、构造训练样本、训练 LoRA、导出 GGUF、接入推理环境并评估。[4]

这里有一个音频演示容易让人忽略的重要条件：教师标注时可以看到每个候选动作对应的五秒模拟未来；学生参与正式比较时，只能读取当前状态。[3][4]

因此，教师使用了更丰富的信息来制作标签。这不是同一输入条件下老师和学生的直接能力比较，也不能把带未来信息的成绩混进不带未来信息的排行榜。

仓库说明，训练状态来自不同策略到达的位置，并为训练、验证和最终游戏评估设置不同种子。原始训练数据没有公开，本次没有独立核验真实样本是否完全满足划分要求；公开的是重新生成数据与训练的流程。[4]

学生模型三轮真实时钟结果为 441、467、366，均值约 424.67，四舍五入为 425。本次重算确认了这一数值。相对 178 的“两倍多”，说的是该设置下的平均吃豆数，不是通用智能提高两倍。

## 5. 更擅长吃豆人，不等于更擅长所有判断

课程同时测量了与吃豆人无关的 194 道通用判断题。蒸馏模型准确率为 0.53，同尺寸 Tev1 为 0.66。[1][3]

这说明该专家模型不能被当作通用决策模型的完整替代品。但也不能把 13 个百分点差异全部归因于“专项微调造成遗忘”：课程明确说明，学生从普通 Qwen3.5-0.8B base 开始，并未经历 Tev1 那样的通用决策训练。

也就是说，初始模型、训练配方和任务特化都可能影响结果。若要精确判断微调导致了多少损失，需要同一个模型在微调前后的匹配比较。

配套文档还区分了“与教师选项一致”和“最终游戏表现”。前者有助于检查学习情况，但相同的动作不一定是唯一正确动作；业务真正关心的通常是最终任务结果，而不只是模仿准确率。

## 6. 手机能离线运行，不意味着手机也有 55 ms 延迟

**节目约 18:40—21:15。**

课程展示了把 0.8B 模型放到 iPhone 离线运行的方向。这里的价值是部署控制与本地执行，而不是把桌面结果原样移植到手机。

配套 README 描述的 iPhone 片段约 29 秒，给出约半秒一次决策的演示量级；结果汇总页另有约 400 ms 的概述。本文未复测，不将这些近似值合并成一个精确基准。[2][3]

无论采用哪一处描述，都不能把 M3 Ultra 的 55 ms 写成 iPhone 成绩。短录屏也不能代替十局统计、持续运行、功耗和热状态测试。

此外，部署还需要保持分词器、系统提示、输出协议与训练条件相匹配。配套指南对 GGUF 导出和 Ollama 版本差异有具体要求。[4] “权重下载成功”不等于整个推理接口已经兼容。

## 7. 怎样判断要不要从托管模型转向自有模型

课程并没有建议仅为节约一点调用费用就迁移。它更强调，从产品不能妥协的一项要求开始判断：

- 是否必须离线或在设备上执行？
- 是否有严格的响应时限？
- 某个专用任务是否明显比通用能力重要？
- 是否有足够好的状态表示、标签和评测方法？
- 自己承担训练、更新、监控和维护以后，总成本是否仍然合适？

反过来，零配置、广泛判断能力、维护简便可能正是托管服务的价值。自己持有模型获得的是调整取舍的空间，不是免费获得所有优点。

配套结果文档也披露了真实时钟的波动、后台负载和托管服务状态影响。[3] 所以，迁移判断最好来自同一时段、配对任务和真实部署路径，而不是跨不同日期挑选最漂亮的一次结果。

## 本次学习的落点

这期真正可以迁移的方法，是把热门技术拆成：长期存在的问题、当下的产品包装、可比较的替代方案，以及必须承担的代价。

在这个案例里，长期问题是低延迟、低成本的判断；产品名称会变化，但状态表示、基线、时钟、数据划分和实际验收方法仍然有用。看完演示与自己完成实验不是一回事，本文也不把代码文档核对写成实机复现。
