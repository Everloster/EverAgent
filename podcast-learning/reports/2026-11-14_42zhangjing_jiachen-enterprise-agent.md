# 42章经对谈贺嘉琛：企业需要的不是更多 Agent，而是能够共同学习的工作系统

这期访谈最值得研究的，不是又出现一个“全自动 Agent”产品，而是一个组织问题：**如果每个人的助手都更能干，为什么公司未必整体更高效？**

曲凯与 Afk.surf 创始人贺嘉琛，从 AFFiNE 的产品经历聊到企业 Agent、工作流、模型训练和人才组织。[1] 嘉宾的主线是：个人任务可以由个人助手完成，但企业还需要减少重复劳动、对齐共同目标，并把好方法沉淀为可复用的能力。

本文基于覆盖访谈开场至结束致谢的私有转写，以及官方节目说明。音频末尾约 40 秒没有转写覆盖，不作为内容依据；转写疑点与审计口径见文末。涉及产品能力、客户采用和未来趋势的判断，均按嘉宾观点记录，不当成已经独立验证的事实。

## 1. 从编辑工作空间，到跨工具完成任务

**对应节目约 01:49—13:41。**

贺嘉琛回顾 AFFiNE 时，将早期机会概括为：把文档、画布和其他信息形式放进一个工作空间，使 AI 更自然地检索和处理这些材料。随后，随着模型接管更多工具，具体编辑界面也可能成为限制——用户要的是事情完成，而不一定是在某个固定画布里继续操作。

这是嘉宾解释自身转向的一条产品脉络：从辅助某种编辑工作，转向能跨通信入口、软件和操作环境行动的 Agent。其所谓“无处不在”，重点不是界面完全消失，而是**任务身份和进度不应被某一个入口割裂**。

但从这条脉络不能直接推出编辑器或 GUI 将失去价值。可检查的界面仍然帮助人表达约束、审阅结果和处理例外。这里更合理的学习结论是：界面应该围绕任务的发现、检查与控制重新分工，而不是简单地把聊天框换成另一个入口。

嘉宾提到的项目成绩与商业化经历属于访谈自述；本文不据此补写融资、收购或市场份额结论。

## 2. 企业场景的特殊性：重复任务与共同目标

**对应节目约 13:41—20:52。**

嘉宾认为，面向互不相关个人的助手，不一定能仅凭用户更多就获得更强的任务复用；而企业中，不同员工经常处理相同资料、相似流程，并最终服务于一定的组织目标，因此更有机会产生跨任务学习。

这个论点可以拆为三个条件：

1. **有可重复的工作**：多个人反复阅读同一份代码、资料或业务状态。
2. **能识别好的执行方式**：不只是知道某人调用了工具，还知道任务有没有完成、哪里返工、哪种结果被接受。
3. **有资格复用这些经验**：相关数据和操作必须处在恰当的授权范围内。

其中前两项是嘉宾论证的重点，第三项是企业落地时不可省略的限制。企业拥有一些共同目标，并不意味着部门目标天然一致，也不意味着员工、客户或合作伙伴的数据可以无差别共享。

在商业上，嘉宾更愿意靠近能够衡量的企业价值：用更低成本完成工作，让客户愿意改造现有系统并为结果付费。其对 C 端平台竞争、渠道与供应链成本的讨论，是解释创业选择的观点，不是“所有 C 端 Agent 都不存在壁垒”的普遍结论。

## 3. “一个共同 Agent”不等于全公司共享一段聊天

**对应节目约 06:00—08:00、30:00—33:32。**

访谈设想的共同 Agent，既要高并发服务不同员工，又要保留个人的记忆与运行环境，同时学习企业内发生的工作。

因此，应把它理解为**共享能力与组织级观测，而非所有人的信息完全混在一起**。一个逻辑服务可以有多个会话、工作区和权限域；“同一个 Agent”并没有规定它必须是单个进程或单份模型上下文。

嘉宾举出一种假设：若一百个人分别让自己的 Agent 阅读同一份代码，就会产生重复处理；共同系统则有机会复用一次阅读形成的状态或经验。这个例子用于解释目标，并不是一项已经测得百倍收益的实验。

真正需要追问的是：哪一部分能共享？

- 公司公开给所有员工的代码说明，可能适合在组织内复用。
- 个人沟通、客户隐私或受限业务资料，需要按权限处理。
- 一个人的偏好可以改善其个人体验，但未必应变成全公司的默认规则。
- 一个团队的成功做法，可能只在特定产品、客户或时间段内有效。

所以，企业共同学习需要同时保留经验的来源、适用范围和撤销方式，不能只追求“知道得更多”。

## 4. 个人效率提高，为什么会放大组织噪声

**对应节目约 20:52—26:11。**

访谈提出一个很有解释力的假设：产品经理让 AI 把一句需求扩成几百页 PRD，工程师再让另一个 AI 把这份文档缩成一句话。每个人似乎都完成了更多产出，但真实的需求讨论被跳过去，组织只多了一次膨胀和压缩。

这不是反对文档，而是指出**文档数量不是协作质量**。若生成材料没有保留决策原因、边界和验收条件，后续摘要可能把最重要的分歧抹平。

嘉宾主张，让产品、设计和工程更直接地面对共同的可运行产物：例如以代码库为基础，通过实时预览修改最终结果。角色的变化不只是给原岗位配一个助手，而是让设计、产品与实现之间的交付链缩短。

本文的延伸判断是：这类改造仍需要保留一份可检查的共同约定。看见同一个界面，不等于理解了同一项业务要求；原型跑起来，也不等于权限、数据迁移和异常处理已经满足交付标准。

可以把协作目标从“我完成了多少文档”改为“我们减少了多少误解、等待和返工”，但这些指标需要真实业务测量，节目没有提供可以直接复用的量化结论。

## 5. 工作流、缓存、记忆和训练：不能把所有复用叫作学习

**对应节目约 26:11—33:32。**

嘉宾认为，模型变强后，一些原本用于补足模型能力的工作流、提示与 Skills 可能很快过时；同时，缓存和小模型训练会让重复执行更便宜。

这里需要把几种机制拆开：

| 机制 | 复用的是什么 | 不自动意味着什么 |
| --- | --- | --- |
| 固定工作流 | 显式步骤与控制逻辑 | 不会自动适应所有新任务 |
| Prompt / KV Cache | 已处理前缀的中间计算状态 | 不是保存并直接返回任意最终答案，也不更新模型权重 |
| 外部记忆或知识库 | 可检索的事实、经验或偏好 | 不代表这些内容已被参数化学习 |
| 轨迹蒸馏、微调 | 从例子中训练出的模型行为 | 不保证继承老师的全部能力或原任务授权 |

OpenAI 的缓存文档说明，复用要求匹配已渲染的提示前缀，后续新增输入仍需处理，并继续生成新的响应。[4] 因此，节目中关于“把以前做过的事情复用下来”的趋势判断，不能直接解释成缓存保证业务输出完全相同。

同样，模型更擅长调用工具，也不意味着业务流程中的硬约束应该删除。付款审批、访问权限、失败重试和幂等性，不只是为了弥补模型不聪明而存在。可以与[常驻 Agent 的控制面隔离](../../ai-learning/reports/knowledge_reports/常驻Agent安全_控制面隔离与权限交集_深度解析_20261115.md)对照：决定怎么做的策略可以更灵活，决定最多允许做什么的边界仍需要存在。

## 6. 小模型的机会：不是赢所有榜单，而是复现已验证的好方法

**对应节目约 33:32—40:02。**

嘉宾回顾了对应用公司训练模型的态度变化：如果目标只是与前沿厂商竞争通用能力，数据、算力和团队能力都构成困难；但若已经拥有高质量任务轨迹和用户反馈，就可能训练一个更快、更便宜的执行模型。

访谈重点介绍了两类模型：

- **Task Routing Model**：学习强模型做过的任务路径，并结合用户选择过的执行偏好，将重复任务变成较低成本的响应。
- **面向企业内部任务的 Worker Model**：适应特定操作环境与工作需要。其规模和能力属于嘉宾自述，本文没有取得训练或部署证据。

“肌肉记忆”是嘉宾用于说明第一类模型的比喻：第一次完成新任务需要较多推理，反复出现的可靠路径则可以被更便宜的模型学习。

这一方向与[Decision Models 的非生成式判断接口](../../ai-learning/reports/knowledge_reports/DecisionModels_非生成式决策与概率接口_深度解析_20261115.md)可以相互启发，但不应据此声称 AFK 已使用某个具体框架或检查点。节目并未披露足以重现其训练系统的实现细节。

这里至少有两个应保留的区分：

1. **老师做过，不等于老师做对了。** 轨迹进入训练数据前，仍要知道任务结果是否满足业务条件。
2. **用户偏好，不等于成功标准。** 在多条正确路径之间选择更合习惯的一条，是偏好学习；把用户喜欢但业务错误的操作当成正确示范，则会积累问题。

此外，企业愿意接入系统，不等于任意接口操作都已获授权。所谓“更少限制”的内部执行能力，仍要受资源所有权、业务许可与审计边界约束。

## 7. 关于软件消失、模型普惠与组织人才的判断

**对应节目约 40:02—49:12。**

嘉宾提出较强的趋势判断：更多软件逻辑可能被模型与动态生成的程序吸收，模型供给也可能在未来几年发生明显变化。其商业选择，是在当前阶段帮助客户用现有能力创造价值，而不是等待最终格局确定。

这些判断有启发性，但不宜转成确定的时间表。复刻一段功能逻辑的成本下降，并不自动消除数据、合规、分发、可靠性和组织迁移成本。模型能生成程序，也不等于程序在目标环境中已经安全正确。

访谈最后回到人才组织。贺嘉琛把能够让成员放开手脚、真正做事并成长的环境，视为创业的重要回报；项目商业结果之外，团队成员之后能够承担更大的技术和产品责任，也构成经验积累。

这使全篇形成一种呼应：企业 Agent 的目标不是堆积更多输出，人类组织的价值也不只是一次结果；更值得观察的是，系统有没有让好方法更容易出现、被验证并传播。

## 8. 本次学习留下的四个问题

如果要评估一个“企业持续学习 Agent”，我会优先问：

1. 学到的内容究竟进入缓存、外部记忆，还是模型权重？怎样删除或撤回？
2. 哪些结果被认定为成功，谁有资格给出这个判断？
3. 经验从一个员工传播给另一个员工时，权限和适用条件怎样保留？
4. 收益体现为 Token 变便宜，还是组织返工、等待和错误真的减少？

这些问题比“是不是同一个 Agent”更接近产品能否长期工作的原因。节目提供了一条有价值的创业与技术假设，但回答这些问题还需要具体实现和业务证据。
