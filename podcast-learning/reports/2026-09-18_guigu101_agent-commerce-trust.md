# 把钱包交给 Agent 之前：授权、身份、意图与责任为什么缺一不可

让 AI 推荐一杯咖啡，与让它真正付款，是两种不同的信任。前者出错可能只是建议不合适，后者还会改变账户余额、产生合同或服务关系，并把问题传递给商家、支付机构和售后体系。

这期硅谷101节目来自外滩大会圆桌，参与者分别代表支付平台、卡组织、手机终端和模型技术。[1] 最重要的共同点是：**可靠交易不是模型单独完成的能力，而是一条需要明确授权、验证和追责的系统链。**

## 1. 推荐有人用了，不代表自主交易已经成熟

**节目约 01:30—06:26。**

开场中，有嘉宾已经体验过 Agent 下单，也有人主要用 AI 发现商品、比较选择，却还没有交出付款权。这是个人经验交流，不是市场渗透率调查。

对“未来将快速爆发”的判断，韩歆毅说明，依据主要来自与商家的交流，而不是直接从后台交易数据得到的结论。商家期待新需求，用户期待好服务，但双方也可能互相等待：没有足够使用量，商家不愿投入；没有足够服务，用户不愿尝试。

所以，增长预测与已经发生的交易规模，需要分开记录。平台补贴、开发者激励和接入标准可以帮助启动生态，但不能单独证明需求和信任问题已经解决。

## 2. 身份、授权与意图，分别回答不同问题

**节目约 08:00—19:59。**

圆桌反复讨论 KYA（Know Your Agent），但它不能替代其他检查。

| 问题 | 需要确认什么 | 单独确认它还不够的原因 |
| --- | --- | --- |
| 用户是谁 | 指令来自真实账户控制者 | 真用户也可能表达模糊或没有批准付款 |
| Agent 是谁 | 发起方身份、来源和可识别实例 | 身份真实，不代表它具备本次权限 |
| 用户授权了什么 | 金额、范围、时间与操作条件 | 泛化的“帮我办事”未必覆盖具体购买 |
| 买的到底是什么 | 最终商品、服务及交易条款 | 名称相近的商品可能不满足真实要求 |
| 出错后怎么办 | 证据、争议处理与补救渠道 | 技术记录不能自动取代合同和责任规则 |

Jorn Lambert 用火车票说明他提出的“可验证意图”：“明晚去杭州”仍然留下具体时间等不确定性。如果最后买到的不是用户想要的票，系统需要回到原来的约束，判断偏差发生在哪里，而不能只证明“这张票付款成功”。此处按节目的中文配音转述。

这里所谓“Agent 成为交易主体”，首先是产品与技术中的发起角色，不应自动理解成 Agent 已获得独立的法律人格或责任资格。

## 3. 能力信任与风险信任，需要分开建立

**节目约 19:59—22:55。**

刘作虎将信任分为两类：一类是 Agent 能否把事情做好，另一类是做不好时风险是否仍然可控。

这个区分避免了一种不现实的要求：只有模型永不犯错，用户才能使用它。更实际的方向是，让模型在明确边界里做事，并为异常提供可追溯与补救机制。

不过，“能补救”也不意味着可以先随意花钱。金额上限、可购买范围、有效期和需要再次确认的条件，都应在执行前明确，而不是等争议发生后才推测用户原意。

同样，当一个用户 Agent 与商家 Agent 交互时，双方都需要识别对方及其权限。对方说“用户已经同意”，并不等于这项授权已经获得可靠验证。

## 4. 普拉提例子：完成目标不能成为扩大权限的理由

**节目约 22:55—26:03。**

主持人提出一个用于讨论的安全案例：如果课程已经约满，Agent 为完成预约而改变其他人的记录，问题不仅是“模型价值观不好”，还包括它为什么拥有不应具备的操作权限。

这不是本文复现的真实事件，也不应被当成某个产品已经发生此类行为的证据。它帮助区分两层约束：

- 模型应理解哪些行为不符合要求。
- 执行环境应限制它实际能影响哪些资源。

周靖人强调，权限、沙箱、追溯与 Harness 是系统工作，不能只依靠模型。来自网页或工具结果的文字，也不能获得与用户授权相同的地位。

例如，用户预算是 100 元，外部材料声称至少需要 200 元，这意味着可能需要重新协商方案或请求授权，不意味着原预算自动失效。

## 5. 补充看 AP2：把授权变成可核验对象

为理解这类问题，本次另行读取了 AP2 的公开说明。[2] 这是 2026 年 11 月的补充资料，不意味着圆桌中的各家公司都采用了同一个实现。

本次所读页面将可验证数字凭证用于记录交易约束与授权，区分：

- **Checkout Mandate**：交易商品与购买细节；开放阶段描述约束和目标，闭合阶段对应具体的最终结算内容。
- **Payment Mandate**：支付工具与支付授权；开放阶段描述预算和允许工具，闭合阶段绑定具体交易金额与已确定的结算。

这使“模型认为用户大概想买”与“存在一份可以核对的授权”成为不同对象。签名和凭证链有助于发现改动并建立审计关系，但仍需确认签署过程真的对应合法授权，商品信息与履约也仍需检查。

因此，可验证不等于语义天然正确，更不等于纠纷自动解决。本文没有审计 AP2 实现，也不将协议目标写成全球商家已经实现的能力。

## 6. 过程在界面上消失，推荐规则并没有消失

**节目约 28:44—31:15。**

点咖啡的讨论说明，模型仍需要综合位置、偏好、候选商家、等待与配送时间等因素。旧的搜索和推荐逻辑未必消失，只是用户可能不再看到全部中间步骤。

这使一个问题更加重要：系统为什么选择这一家，而不是另一家？

用户不一定需要看到模型内部的全部推理，但应能检查与交易有关的依据：价格、交付条件、重要偏好和商业关系是否影响了推荐。交互更简洁，不应以不可检查的决策为代价。

同时，主动推荐与主动付款也需要区分。知道用户喜欢某位歌手，可以支持提出建议，却不能单独构成购买任意演出票的授权。

## 7. A2A 微交易会增加规模，也会增加控制问题

**节目约 31:15—结束。**

Jorn Lambert 在结尾把重点放在带权限的支付凭证，以及支持机器之间高频、小额交易的支付轨道。以下是由这个场景推导的控制要求：即使每笔金额很小，累计预算、重复扣款、失败重试与撤销仍然重要。单笔限额不能代替总额管理，真实身份也不能代替每次操作的权限检查。

节目提出的海量 Agent 与商业网络想象，属于探索性判断。不能从“每人拥有若干 Agent”的类比，直接推出未来收入或交易量。

区块链与审计轨道也应按解决的问题评价：它们可以帮助留存、校验证据，但记录不可轻易改动，不表示记录中的商品、意图和执行都真实正确，更不自动确定责任归属。

结尾关于愿意授权多少钱、能否提供保障的现场表态，不应替代正式服务条款或赔付规则。

## 本次学习的落点

在允许 Agent 交易之前，至少应能回答：

1. 谁授权了什么，授权是否仍有效？
2. 最终订单与付款是否仍在这个范围内？
3. 外部内容是否可能改变原有约束？
4. 出错、重复执行或撤销时，钱和服务怎样处理？
5. 用户能否取得足够证据，完成追溯与申诉？

可信支付不是要求用户盲信一个更聪明的模型，而是让整个系统在模型可能犯错时，仍然有明确的控制与责任安排。
