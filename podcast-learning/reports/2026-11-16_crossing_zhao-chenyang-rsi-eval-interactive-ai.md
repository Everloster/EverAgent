# 赵晨阳谈 RSI 与交互式 AI：让模型优化模型，真正要建好的是评测、状态与责任

这期节目里，赵晨阳一方面非常兴奋于模型改善推理系统、Computer Use 和语音交互的能力，另一方面反复强调评测、代码规则、人的责任与技术收益的分配。[1] 这两种态度并不矛盾：**模型越能自己试办法，就越需要把“怎样算有效”“现在处于什么状态”“出了问题谁处理”变成可执行的约束。**

本文不把十个 Aha Moments 改写成十大趋势预测，而是从访谈中重构三条技术链：

1. **自优化链**：模型提出改动 → 独立验证 → 人工审查 → 新版本成为下一轮起点。
2. **交互链**：观测世界 → 组织上下文 → 推理和执行 → 向用户反馈 → 接收打断或修正。
3. **治理链**：明确标准 → 授予权限 → 承担维护责任 → 让规则制定者也接受约束。

赵晨阳的观点以节目为来源；实现机制与可核查结果另引官方资料，本文的推导和自拟例子则单独说明。

## 2. “用模型优化模型”，至少包含三种不同事情

### 2.1 节目使用的是一个偏工程的 RSI 定义

开场中，赵晨阳将模型参与本代部署、下一代训练与研发，看作 RSI 的雏形。其例子包括：模型优化推理 kernel、参与数据筛选、帮助探索架构，使后续模型迭代减少对人工逐步操作的依赖。[1，约 01:16—06:36]

这里需要分清三个层次：

| 层次 | 被改变的对象 | 可以合理期待的收益 | 不能直接推出什么 |
| --- | --- | --- | --- |
| 推理系统优化 | kernel、调度、缓存、数据传输 | 同一模型运行更快或更便宜 | 模型知识和推理能力自动增强 |
| 辅助训练与研究 | 数据、实验代码、训练配方等 | 人能探索更多方案，研发等待减少 | 新模型必然更强，或无需研究者判断 |
| 自主持续改进 | 系统还能自行改进改进方法，并可靠评价 | 更强的研究自动化可能性 | 已经出现无上限、无需人和物理资源的能力增长 |

“RSI 已到来”在节目中包含了嘉宾自己的定义和立场。接受第一层已发生的工程实践，并不要求同时接受第三层所有强预测。

### 2.2 一个可以核对的例子：OpenRSI × SGLang-Omni

本次读取的官方合作文章，描述了一套改善语音和多模态服务性能的循环：人提出研究任务并负责约束和最终合并，Agent 将提案转成可执行基准、连续提出修改并测试，独立 verifier 检查增益，维护者再审查代码与证据。[2]

这里有两种不同的“基线”：单次搜索的 reward 始终相对任务的冻结基线计算，当前最好结果是后续候选要超过的门槛；跨 PR 的后续工作，则在已经合入的代码上继续。不能把每次最好结果都当成重新计算增幅的分母。

文章明确说，这项工作的主要对象是**模型周围的服务运行时**，不修改模型权重。系统设计、任务定义和最终审查仍有人参与。因此，“模型在优化 AI 基础设施”有具体证据；“模型已经独立设计下一代智能”则不是这份材料证明的内容。

可把一个合格的循环写成下面的职责关系：

```text
人确定：任务、输入分布、资源预算、不可回退条件
                ↓
Agent：提出假设 → 修改 → 运行实验 → 解释结果
                ↓
独立验证：冻结基线、干净环境、质量与延迟检查
                ↓
维护者：审查实现、可维护性与适用范围
                ↓
合入的新版本 → 下一轮基线
```

这里“独立”不能仅理解为让另一个模型说一句“通过”。关键是验证材料、评分器和结果读取不能被候选实现随意修改；结果应能回到具体代码、输入和测量记录。

## 3. Evaluation 是核心，但不是一句“测得出来就一定优化得好”

### 3.1 目标函数之外，还需要完整的约束

赵晨阳用 ASR 错误率不能变差、性能要提高说明优化条件，随后又补充：不能为了改善一个模型而拖慢另一个模型，也不能留下过多难维护的配置。[1，约 06:36—13:49]

这些补充非常关键。一个“更快”的实现可能只是：少算了必要步骤、改变了采样行为、只服务容易输入，或者让吞吐提高却恶化了尾延迟。

因此，性能优化更适合表达为一个约束问题：

\[
\max_x\;\mathrm{Throughput}(x)
\quad\text{subject to}\quad
\begin{cases}
\mathrm{Quality}(x)\geq q_{\min}\\
\mathrm{Latency}_{p95}(x)\leq \ell_{\max}\\
\mathrm{Memory}(x)\leq m_{\max}\\
\mathrm{Compatibility}(x)=\mathrm{true}
\end{cases}
\]

这里 \(x\) 是候选代码与配置；吞吐是优化目标；\(q_{\min}\)、\(\ell_{\max}\)、\(m_{\max}\) 分别是任务预先定义的质量、尾延迟和内存条件。具体项目还可能需要稳定性、启动时间、其他模型回归与安全边界。

一个便宜、自动化的 evaluator 能让搜索更快，但若它测错目标，自动化只会更快地沿错误方向搜索。“能评估”是重要条件，不是发现可行改进、保持所有业务要求的充分保证。

### 3.2 WER 不是“随便数一百个汉字错几个”

WER 的标准形式是：

\[
\mathrm{WER}=\frac{S+D+I}{N}
\]

- \(S\)：词替换次数。
- \(D\)：词删除次数。
- \(I\)：词插入次数。
- \(N\)：参考转写中的词数。[6]

需要先对参考和识别结果进行序列对齐。分词、大小写、数字、标点和其他文本归一化方式，都会改变结果。中文若按字计算，通常讨论的是 CER；采用什么分词方案的中文 WER，必须写清楚，不能与 CER 混用。

WER 也可能超过 100%：参考只有一个词，识别保留这个词却额外插入两个词，错误率就是 2/1。节目把它简化为错字率，是为了口头解释，工程评测不能省略真实口径。

对于 TTS，若通过“合成语音 → ASR 转写 → 与输入文本比较”得到 WER，测量还经过一个识别器。低 WER 不能充分证明韵律自然、音色稳定、情绪表达准确；高 WER 也需要分辨来自合成还是识别环节。[2]

此外，一处否定词的错误可能比几个普通词错误更影响任务。平均 WER 之外，应按产品风险检查专名、数字、指令否定以及重要语义。

### 3.3 数字应该怎样校准：1700% 与公开结果不能混在一起

节目提到，一个约 80M 参数的 TTS 模型在一个周末获得“性能提升 1700%”。但所读材料没有给出这次具体实验的模型唯一标识、硬件、性能指标、输入分布与基线提交。[1] 本文未能独立确认这个数值。

如果按通常的增幅定义，“提升 1700%”意味着新值为旧值的 18 倍；但口述也可能混用增幅与倍数，在原始测量缺失时，不应替嘉宾补出确定的换算结果。

另一个可读到的公开材料是 OpenRSI 合作报告。它报告了跨八个模型、十四个合入 PR 的结果，但不能用这些结果替代上述 80M 案例。[2] 表中每行比较相应模型首个 OpenRSI PR 之前、最后一个 PR 之后的 main 提交范围，每轮 128 个请求；这个提交范围可能包含其他人的改动。以下摘取其中四行：

| 官方报告中的范围 | H100 非流式／流式吞吐变化 | 影响解释的条件 |
| --- | --- | --- |
| CosyVoice3 | +44.4%／+46.2% | 是相应提交范围的整体比较，不能和某个独立 PR 的收益混为一谈 |
| MOSS-TTS | +48.5%／+76.3% | 范围还含其他改动、依赖升级与镜像变化；其中 #2859 增加约 41 秒启动时间和 3.7 GiB 峰值显存 |
| Qwen3-ASR | +14.2%／+5.0% | 混有依赖升级，部分流式尾延迟上升 |
| Ming3-TTS 0.5B | +326.5%／+93.9% | 范围包含额外 PR，基线有采样 bug，测量复用了参考录音；流式设计有人参与 |

这些是作者披露的结果与限制，不是本报告的独立性能测量。文章还将“搜索阶段相对冻结基线的最佳 reward”和“真实合入提交前后的收益”分开，二者也不能直接比较。

这反而使材料更有学习价值：可信的性能报告不只给最大数字，还给出哪些改动混在一起、什么条件变了，以及哪里付出了代价。

## 4. 为什么运行时还有大量可优化的空间

“模型写 kernel”容易让人只想到高深的 GPU 算法。OpenRSI 的公开案例显示，许多收益来自模型计算外围的等待与重复工作：[2]

- 等待线程忙轮询，占用其他阶段需要的 CPU 核；改为休眠让资源回到真正的工作。
- Tensor 在阶段边界反复转成 Python list，再重建为 Tensor；减少这种转换可以降低搬运和对象管理开销。
- 计算了没有调用者使用的结果，或重复提取参考音频特征。
- 大量小 GPU kernel 逐个发射，CPU 调度成为开销；融合与 CUDA Graph 可以降低重复启动成本。
- 不同阶段相互等待，能够重叠的预填充和解码没有及时启动。

这些优化适合 Agent 探索，是因为不少假设可以被隔离成小改动，反复测量和回退，比较结果也相对便宜。

### 局部快十八倍，整个请求可能只快四倍

以下是自拟计算。假设一个请求 80% 的时间花在某个可优化部分，剩余 20% 完全不变；该部分快了 18 倍：

\[
\mathrm{Speedup}_{\mathrm{end-to-end}}
=\frac{1}{(1-f)+f/s}
=\frac{1}{0.2+0.8/18}\approx4.09
\]

其中 \(f=0.8\) 是原耗时占比，\(s=18\) 是局部加速比。这里假设工作量和其他条件不变、没有新增瓶颈，不是对节目实验的估计。

它说明了为什么必须同时看 kernel、完整模型与端到端任务。局部优化成功后，瓶颈会迁移到其他计算、传输、排队或审核环节；更多便宜推理也不自动创造更好的研究假设。

## 5. Computer Use：前缀共享说的是什么，图像又改变了什么

### 5.1 KV Cache 为什么关心前缀，而不只是相同文字

**对应节目约 33:22—41:25。**

对通常的因果自回归模型，一个位置的内部表示会受到它之前的上下文影响。因此：

```text
请求一：A + B
请求二：A + C
```

可以在相应条件下复用前缀 A 的 KV 状态。但：

```text
请求三：A + C
请求四：B + C
```

虽然都有尾部 C，C 之前的上下文不同，其模型状态通常不能直接互换。

SGLang 的 RadixAttention 将 Token 序列与 KV Tensor 的对应关系组织在 radix tree 中，寻找可复用的前缀，并结合缓存淘汰和调度策略减少重复工作。[3] 这保存的是计算状态，不是“这个问题以前的答案”。

实际复用还要求模型、相关配置、位置与输入表示等条件匹配，并且缓存条目仍然存在。文本相同不是在任意两个服务实例之间交换缓存的完整保证，缓存共享也不能跨越数据授权边界。

### 5.2 “图片不能共享”是一种过强的概括

节目以截图频繁变化说明 Computer Use 的多模态输入成本。[1] 这里应作更精确的限定：**两张看起来很像的截图，不保证变成相同的视觉输入，也不保证产生可复用的语言模型 KV 前缀。**

但不能反推“多模态完全不能缓存”。SGLang 原始说明已经指出，RadixAttention 可以扩展到 image tokens。[3] 还需要区分几种复用：

- 相同原始媒体的下载或预处理缓存。
- 相同输入和编码器条件下的视觉 Embedding 复用。
- 满足完整前缀条件的语言模型 KV Cache 复用。

鼠标移动后截图变化，可能使某类媒体缓存失效，却不一定让请求中的固定系统提示、工具说明和其他前缀都失去复用机会。具体发生什么，取决于输入组织与实际实现。

### 5.3 无障碍信息降低了部分观测成本，不是截图的通用替代品

赵晨阳以无障碍信息解释自己的使用体验：把部分界面结构转成文本，再在需要时配合截图，可以降低操作成本。[1] 下文讨论这种设计的机制；本次没有核验其使用的闭源客户端实际采取了哪条输入路径。

这种方式有两个合理动机：让 Agent 更容易定位控件；减少仅凭像素理解界面的负担。但是否能提供完整信息，取决于应用暴露了什么。自绘画布、视觉关系和没有充分语义标记的控件，仍可能需要图像。

而且，结构化文本只在序列化稳定、前部内容没变化时才有良好前缀复用；动态 ID、时间戳和无意义重排也会破坏复用。不能把“文本”与“高缓存命中率”直接画等号。

因此，这一段最可迁移的工程思路是：**为任务选择成本与可靠性合适的观测表示，而不是坚持所有东西都截图，或所有东西都只读文本。**

## 6. 交互式语音：三种路线和四种不同的“中断”

### 6.1 原生全双工、轮次式 Omni、级联分别在做什么

**对应节目约 41:25—47:35。**

SGLang-Omni 的固定版本指南将三种策略区分如下：[4]

| 路线 | 主要组成 | 谁决定何时回复 | 主要取舍 |
| --- | --- | --- | --- |
| 原生全双工 | 模型持续接收音频并产生输出 | 模型及其原生交互机制 | 依赖相应模型、状态与运行时支持 |
| 轮次式 Omni | 一个多模态模型处理每轮输入并回复 | 系统的轮次控制与模型 | 模型理解音频，不自动意味着同时听说 |
| 流式级联 | ASR → LLM → TTS，加 VAD 和会话管理 | 各阶段与控制逻辑协作 | 组件可独立替换，但需管理跨阶段延迟与状态 |

三者可以使用相近的外部实时协议，所以不能从“有 `/v1/realtime`”或“能边播边收麦克风”推断模型一定原生全双工。

在该版本中，应进一步查询 `GET /v1/realtime/capabilities`：`native_full_duplex` 描述交互策略，`supports_cancel`、`supports_truncate` 等字段描述具体控制能力。连接入口相同，能力组合仍然可能不同。[4]

同样，轮次式和级联系统并非只能让用户手工按暂停：本次所读指南已经包含说话检测、语义轮次判断与插话中断路径。节目中的分类适合解释总体路线，具体能力应按模型和版本核实。[4]

VAD（语音活动检测）主要识别是否在说话；“用户是否已经表达完”则还涉及语义。停顿可能是思考、换气或犹豫，不应一律当作发言结束。

### 6.2 一次“打断”至少涉及四件事

假设用户听到回答一半，开始纠正问题。系统要协调：

1. **识别新输入**：确实是用户插话，而不是回声或噪声。
2. **终止旧计算**：按支持能力取消旧的 LLM/TTS/模型响应。
3. **停止旧播放**：客户端清空或丢弃旧音频，包括取消后晚到的分块。
4. **修正对话历史**：模型后续看到的是用户实际听到的部分，而不是完整生成但未播放的长回答。

少做任意一步，都可能造成“明明打断了，旧回答仍继续”“模型以为自己解释过，用户却没听见”等问题。

SGLang-Omni 的级联说明将 `conversation.item.truncate` 与播放进度联系起来：客户端报告已播放的音频位置，服务端据对应的词或句子边界保留历史。具体粒度取决于对齐器与 profile；不能只按生成的全部文本更新历史。[4]

若客户端不报告 `audio_end_ms`，服务端默认只能按**已经发送的音频**截取历史，这可能领先于用户实际听到的位置。只支持句子边界时，被打断的半句话会整句舍弃；有词对齐或截断音频的 ASR 校准时，才能保留更细的已听部分。这里的“已听历史”是依据播放记录和对齐结果重建的，不能理解成服务端天然知道用户听到了每一个词。[4]

不同原生模型的能力也不同。例如，该提交中的 PersonaPlex session 路径对 `response.cancel` 和 `conversation.item.truncate` 返回 `not_supported`，客户端只能静音，模型仍会继续。**静音只说明用户听不见，不证明模型计算已经停止，也不等于历史已经截断。**[4]

### 6.3 “更自然”的评测不能只有一个延迟数字

至少应分开观察：

- 用户停顿时，系统是否过早抢话。
- 用户说完后，多久开始出声，多久才给出真正回应问题的内容。
- 插话开始后，旧语音还继续多久。
- 插话结束后，系统是否根据新信息继续，而非恢复旧答案。
- 音频播放是否出现缓冲不足和卡顿。
- 内容正确性、遗漏、音色与韵律是否满足要求。

这份指南保留 Full-Duplex-Bench 的官方评分作为参考，另提供 `unified-score` 的统一时序指标。后者将提前出声记为 `early_start`，不让抢话通过负延迟被截成零而获利；无响应样本也不会悄悄从延迟分母中消失。[4]

但这里的 `response` 只表示：用户结束前没有词起始，结束后窗口内至少出现一个识别出的词。**一句预设词也可能被算作响应，它不保证语义有效。** 停顿时始终沉默的系统又可能获得很好的“不抢话”分数，因此必须同时看回应率、时序与内容质量。打断评测还要报告 `exercised_rate`：打断发生时模型本来没在说话，就没有真正测到“停止正在说的话”这项能力。[4]

这些时序来自接收音频的模拟播放与 ASR／VAD 对齐，不是麦克风到扬声器的完整声学延迟实测。项目的统一评分、原始官方评分和真实产品体验，应保留各自定义。

### 6.4 TTS as a Tool：值得说出的内容，不等于全部输出

赵晨阳指出，面向代码与复杂任务的 LLM 可能产生大量文字，逐 Token 朗读会造成冗长甚至读错表情、格式等问题。其设想是将 TTS 当成工具，让模型决定哪一部分内容需要说出来。[1]

这体现了显示渠道与语音渠道的不同用途：屏幕可以保留详细表格、来源和下一步操作，语音更适合简短回应与必要确认。

但不能简单地认为增加一个工具定义就完成了设计。还要测试模型是否会调用、参数是否正确、是否遗漏用户必须知道的限制，以及额外思考是否让响应变慢。节目描述的工具调用不足和思考延迟是其经验，不是本报告对特定模型的当前能力评测。

## 7. Voxt：模型能力如何经过产品入口变成日常价值

**对应节目约 47:35—53:24。**

赵晨阳对语音输入的兴奋，来自一个完整过程：ASR 把声音变成文本，LLM 根据上下文与词典整理，产品把结果送到正在工作的输入位置，而不必反复复制、切换窗口和粘贴。[1]

Voxt 的固定版本资料确认了转写、翻译、改写以及可选择本地或远程模型的路径。[5] 其中 Transcribe 可以直接输出 ASR 文本，LLM 润色是可选步骤；Translate 和 Rewrite 才需要配置语言模型。启用润色后，需要把两项质量分别测量：

- **识别质量**：原本说了什么，有没有错字、漏字或专名错误。
- **改写忠实度**：润色有没有改变否定、数字、观点或说话者意图。

LLM 把句子改得更通顺，不代表原文更准确。术语词典能减少一些错误，却也可能在遇到同音异义词时过度替换。因此，保留原始识别文本、允许纠正与查看改写结果，比只展示一份漂亮最终文本更重要。

### 一个容易误读的性能口径

Voxt README 用 32.3 秒到 2.6 秒说明长口述的停说后等待约缩短 92%。追溯同一提交的评测记录，这两个数来自 **M4、24 GB 内存的 Mac** 上，`asr.accurate` 对一段 **4 分 46 秒拼接测试音频**的比较；原始片段是干净的 TTS 合成语音，不是真实用户长口述。[5][7]

直接比较的是两种 ASR 路径：实时接收音频、结束后统一做一次 Final，需要等 32.3 秒；录制过程中分成十段处理，结束后仅处理剩余部分，等待 2.6 秒。两行来自文档标出的较低内存压力运行，机器仍有 swap；它们也不是“离线整段识别”的那一行，后者当次为 43.8 秒。[7]

因此，约 92% 是这组条件下**停说后的 ASR 等待缩短**，不包含后续 LLM 润色、文本插入，也不表示总计算量减少同样比例。边说边处理改变了工作发生的时间；真实口述、短录音、不同硬件与后台负载，还需分别评估。

此外，“本地 ASR”不自动意味着全程本地。Voxt 可以配置云端语音 API，也可以把文本送到所选语言模型；隐私范围由实际配置决定。本文没有安装该软件，不据 README 的设计承诺证明其实际安全性。[5]

## 8. 六项可复现的小检查：把几个直觉变成明确条件

以下全部是**自拟教学例子**，不是 SGLang、Kimi 或节目中的性能数据。本次实际运行了六个断言，覆盖下面的关系：

| 检查 | 输入与条件 | 结果 |
| --- | --- | --- |
| 性能候选必须先过门槛 | 限制 WER ≤ 0.05、p95 ≤ 200 ms；三个候选中最快的两个分别回退质量与尾延迟 | 只保留较慢但同时满足条件的候选 |
| 公共前缀 | `[1,2,3]` 与 `[1,2,4]` | 两个前缀 Token 相同 |
| 相同尾部 | `[1,2,9]` 与 `[4,5,9]` | 没有公共前缀；尾部相同不改变这个结果 |
| WER 上限 | 一个参考词被保留，额外插入两个词 | WER=2，即 200% |
| 局部与整体加速 | 80% 原耗时部分加速 18 倍 | 整体约 4.09 倍 |
| 旧音频迟到 | 当前响应是 r2，网络又收到 r1 的旧分块 | 不再播放 r1 分块 |

最小门槛检查可以写成：

```python
candidates = [
    {"name": "fast_wrong", "rate": 300, "wer": .08, "p95_ms": 160},
    {"name": "fast_tail",  "rate": 250, "wer": .04, "p95_ms": 280},
    {"name": "balanced",   "rate": 120, "wer": .04, "p95_ms": 180},
]
eligible = [c for c in candidates
            if c["wer"] <= .05 and c["p95_ms"] <= 200]
assert [c["name"] for c in eligible] == ["balanced"]
```

这个例子只检查布尔筛选逻辑，没有模拟测量噪声或置信区间。在真实实验里，阈值、样本与测量方式要提前确定，并处理结果的不确定性；不能在看见候选结果后不断挪动门槛。

公共前缀例子只验证序列匹配，音频例子只验证响应标识过滤，都不等于已经实现真正的 KV Cache 或全双工系统。

## 9. 代码治理：统一标准的意义，不是某一条风格天然正确

**对应节目约 13:49—18:00、53:24—结束。**

赵晨阳观察到，AI 让低质量改动也更容易成批产生，维护者的审核负担上升。其选择是明确代码风格和合并要求，并强调自己也必须遵守。[1]

应把两项主张分开：

- 统一、可说明、可执行的规则，有助于减少协作中的反复争论。
- 某条具体规则是否减少 bug，仍需要证据，不能只因为维护者偏好它就视为通用最佳实践。

例如，节目用 `if` 必须配 `else` 等规则说明一致性。本文不把这些风格示例推广为所有项目的正确规则。更值得迁移的是：规则应有明确作用域，贡献者能预先看到，维护者不能为自己的改动开暗门。

对 AI 贡献，至少需要有人能解释问题、审查范围、测试和维护责任。Agent 写出了代码，不意味着批准合并的人可以把责任全部交回工具；反过来，承担责任也不意味着为了果断而省略不确定性。

BDFL 是一种项目治理安排，不自动证明决策正确。项目还需要公开的标准、反馈渠道和对维护权的约束。技术权威与无限权力不是一回事。

## 10. 历史、客服与廉价智能：为什么最后仍然回到人的选择

节目后半段借《大明王朝1566》《万历十五年》《挣扎的帝国：元与明》讨论组织、权责和规则，又将其联系到开源社区。[1] 可以保留其治理启示：规则应当约束制定者，权力应对应可追溯的责任。

但电视剧解释、个人读史心得和组织普遍规律不是同一层证据。转写里若干历史人名、年份与事件关系存在疑点；本文不据这些细节建立历史结论，也不将“组织只会从上往下出问题”等绝对表述当成已经验证的定律。

客服案例则提示另一个边界：**会对话不等于能拍板。** 一个客服 Agent 可能擅长解释条款，却没有权限退款、例外审批或承诺补偿。两个 Agent 来回沟通，并不会凭空创造授权。有效产品需要定义何时升级给有权限的人，用户能否知道卡在哪里，以及谁负责后续处理。

这不能被简化成“模型谨慎就是不负责”。医疗、金融或其他高风险问题中，拒绝作出没有根据的决定可能正是必要边界。负责的系统应该在边界内提供明确帮助和升级路径，而不是装出永远确定的口气。

关于 UBI、财富集中和人的自由，赵晨阳表达的是对未来制度安排的担忧，不是经济学因果关系已经得到证明。带条件的救助、普遍基本收入和个人慈善并非相同机制；不能从一个未经本次独立核实的社会事件，直接推出所有分配制度都将限制自由。

但一个问题值得留下：推理更便宜、模型更强，是技术供给的变化；谁能使用、谁获得收益、谁有权说不，则还取决于制度与产品选择。节目里关于家人、健康、游戏和时间的自我反思，使这条线没有停留在抽象口号：效率提高以后，人仍需要决定哪些关系和体验不应继续让位给工作。

## 11. 本次学习最值得继续验证的事

如果要把这期的启发带回实际项目，我会优先选择三个小而清楚的研究问题：

1. **给一个真实优化任务建立冻结基线与独立验证。** 看性能增益是否在相同配置下复现，并保留质量、尾延迟和维护成本。
2. **记录一次 Agent 请求中真正共享的前缀。** 比较稳定的输入组织与无意义重排，而不是只追求更大的上下文窗口。
3. **测试语音打断后的三种状态是否一致。** 模型生成了什么、服务端发送了什么、用户实际听到了什么，后续历史应依据哪一个更新？

这些是后续实验设想，本次没有部署 GPU 或实时语音服务。资料共同指向的工程重点是：模型越能承担搜索和执行，问题定义、验证边界、状态管理和责任安排越需要明确。
