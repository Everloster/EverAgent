## 一、Today 中国首发：第一个正式上线的国产 Personal Agent

Today（todayai.cn）9 月 24 日 18:00 国区上线，基础版永久免费，新用户送 1 亿 token+1 个月 Pro。团队：高策（技术，前连续创业者，做模型基础设施/向量数据库）+ Suki（产品，前 Monica——即 Manus 前身团队）。时间线：去年 10 月想法→今年 2 月组队→4 月内测→9 月首发（"国内第一个做 Personal AI 的团队"——从时间线和产品完成度两方面主张）。两大特点：**Memory（有记忆，能记住你）+ Proactive（主动做事）**。

新用户不需要 formal 地学习工具——"把它当成你在酒吧认识的新朋友，你怎么和新朋友打交道就怎么和 Today 打交道。"

## 二、市场时机：共识窗口极快与"better OpenCloud"

Instinct 半年估值 5000 万→100 亿美金（<10 万用户）；Muse 发布即登顶。高策的模式观察：**AI 应用层达成共识的速度非常快**（coding: Copilot→Cursor→Devin→Work→Claude Cowork/Manus→WorkBuddy/Codex 跟进；personal agent 同样：Muse 年初开发花大半年**主要花在解决隐私问题上**，各家产品几乎同时 ready）。共同机会的通俗版："给普通人做一个方便使用的小龙虾（agent）。"大家的产品定位都是 **better OpenCloud**——OpenCloud 证明了 agent 长程能力在 coding 以外的价值，但 self-host 极难、产品体验差；Muse/Instinct/Today 看到的都是"以好体验交付"。

**为什么现在发布**：完备度 vs go-to-market 的 trade-off——之前以为有较长非共识期，但海外验证了提前发布的价值（Instinct 没做营销[?]、纯邀请码增长照样好）；更重要的是"大家都还没有 PMF，真用的人极少且全是 early adopter"——提前发布能看到更多场景。Suki：行业内"圈子自嗨"，普通人远未普及——**Personal AI 可能是跨越鸿沟的产物（Power User→普通人）**。

## 三、两个人的路径判断

**Suki（Monica→Today）**：Monica 是插件形态——"插件直接住在了用户的意图和执行发生的那个点上，把意图递到执行的执行成本极低"——这是 Monica 能成的原因，也是 Today 延续的（缩短意图到执行的距离）。做个人助理的需求信念来自"过去只有董事/总裁配助理，但每个人都有琐事"（小红的助理知道他要靠窗的机票）。当时没做是因为技术不到——"**做产品不能站在遥远的未来（会成为先烈），要站在技术成熟度的前夜**"；笃定的方向是 memory（过去一年 memory 论文数量爆发=业界在突破）。

**高策（基础设施→Today）**：做底层基础设施、一直手写代码（复杂度和智能要求高，AI 写不好）——**26 年 2 月某模型[?]发布后"智能有一个跃升的感觉，在我此前要手写代码的领域它完全没有任何问题，甚至已经是 AGI 了，唯一需要在乎的是 cost"**（成本遵循 Scaling Law 每年降 10 倍）。推论：模型不再成为 bottleneck→想象一两年后"一个廉价、比普通人强的智能在你手机上"。更远的想象：**内容 on-demand 创造**——现在消费的内容都是人类提前生产的（UGC+分发），三五年后"你需要消费内容时 AI 按需创造"——完全不同的 pattern。

## 四、需求观察：从通用往 niche 泛化

上一代从 niche 往上做（Glean 从 Enterprise Search、Otter.ai 从录音）；这代 personal agent **先从通用需求出发**（email/日程/电话订票），需求本身面向所有人再自然泛化——邮件处理好在 Town 上能泛化到 parents（美国家长跟学校的大量邮件沟通）和 founders（日程繁忙+信息过滤+会议重叠检测）；**育儿场景从产品指标看留存非常好**（国内也成立）。

**数字资产前提**：Personal Agent 需要你在赛博世界有足够多数字资产——不用邮件、网上没足迹的人，agent 无法低成本了解你（onboarding 门槛极高）；OpenCloud 从程序员起步正因如此。"只让高净值人群受益的产品无法 scale"——需要物理世界 context 与线上 context 统一的入口，在那之前先从数字资产多的人开始。

**Personal AI 的对立面不是工作，是高委托成本**：过去委托 agent 要给大量上下文；这代产品直接进入你的生活、连了你的应用、知道你的关系网络——"很多时候一句话就能把事情干完"。中国人的生活和工作本来就难分（越忙越模糊）；**从生活泛化到工作，比反向容易**。记忆案例：让 Codex/Manus 调研技术只知道客观角度，Today 知道"我做过向量数据库、基础扎实"→会介绍更基础的细节。

## 五、大厂竞争观与商业模式

**大厂最擅长的不是看见也不是坚持**——听说千问、豆包年中探索过 OpenCloud 方向，很快就放弃了；大厂擅长的是"高举高打拿资源烧钱"（TAM 够大时用不计成本投入吃下市场）。而 personal agent 现在 **TAM 极小、没有 PMF**——参照：AI 办公三大件（钉钉 40 亿+飞书 30 亿+企微约 30 亿）加起来不到 100 亿，"大厂核心业务里一年几十亿的业务不值得押"。Meta 是例外（愿意赌不确定方向，元宇宙先例；这次 Muse 用户口碑罕见地好）。

**商业模式的方向问题**：Muse 探索收 SaaS 集成分成（成为入口收佣金）——"这样的导向一定有问题：你会以交易成功率优化产品（为收入负责），它甚至已经开始推广告了。"**Town 的订阅制可能更适合创业公司**：从具体 connector（email）出发把场景做透、付费意愿强、像工具类产品一样 scale，投流也好做。

## 六、名字与身份：单 agent vs 多 agent

**名字很重要**：Suki 的助理叫 Niki（它自己选的）；高策的叫左巨（与爱人名字"右威"镜像）；潘乱的叫文和；某投资人的叫齐俊元[?]——"每天命令齐俊元干活"。Instinct/Town 给每个 agent 一个邮箱地址——**有了 ID 和名字，agent 的 identity 才自然发生**；亲密关系"一定希望它专门面向你而存在，而不是别人也能用到的东西"。

**高策的多 agent 实验（去年 12 月）**：养了设计总管/产品总管/项目总管三个 agent——最后只跟项目总管聊，因为"上下文 all in one place，不需要像现实生活一样反复交代给三个角色"。多 agent（Grok Bot 幕僚长+多角色/国内 Rapt[?]）本质是**另一种手动管理 context**（像 Codex 的 session：用户显式管理上下文）；"未来 personal agent 大概率是**单 session 无限增长的主 chat**——微信里我们也不会动不动 new 一个 session"。成本账：Grok Bot 有 60K token 在 Slack[?]里互相 DM，拉群成本极高——"只有 Power User 才能用好"。**Suki 两点补充**：①养一群小龙虾多是情绪价值（看小弟干活），实际浪费 token——"不同角色协同也是成本，协同花的也是你的钱"；②多 agent 的真价值在**互相监督**（需要 eval/测试的场景）——日常 personal agent 用是杀鸡用牛刀；**multi-agent 可以是背后的 architecture，产品暴露出来的概念一定是一个自然的 agent**——"我对左巨有强烈的情感连接，很难再对另一个 agent 投入相同心血"。

## 七、Context：收集与利用率

八仙过海：海外生态开放（接 Google Workspace 拿高质量上下文）；**国内安卓手机"就是一个人一生的缩影"**——端侧 context 超乎想象。千问搞眼镜/录音卡片/桌面机器人。**更重要的后半段：context 利用率**（像训练讲 GPU 利用率）——相同 context 经 harness/产品处理拿到更高价值信号=壁垒。**Town 的邮件为什么格外好**：处理一封邮件用五层 subagent 的深 workflow（决定处理与否→draft 怎么写）；**rubrics 例：发件箱的信息密度远高于收件箱**（发件箱是你对别人的意图——自我介绍、清晰描述；收件箱是别人对你的意图）——海量这样的先验规则构成对场景的记忆。人每天处理的是 delta（增量信息），增量×记忆=主动传达/过滤/处理，考验工程架构。

## 八、Memory+Proactive 联动（核心设计）

**没有记忆的主动=骚扰；没有主动的记忆=档案。**记忆的学界做法：Instinct 被逆向——有专门的 Timeline（daily/weekly 记录）；Town 用 consolidation（每天总结）+recent updates。**delta 来自三处：chat history、connector、录音（物理世界 context）**；时间锚定=发生时间≠记录时间（"二月份公司没了，九月份记录下来——两个时刻都重要"）。不同数据用不同基础设施：人与人的关系适合图（Perplexity 的记忆就是图设计）、timeline 天生时序——融合+召回是难题；两个前沿思路：①让模型自己决定用什么基础设施召回（把记忆的基础设施"训"进去[?]——代价是探索成本高、latency 长）；②Jina founder[?]：每个 query 单独构建 context（放弃 KVCache 的降成本，换取简化问题）。

**Proactive 四维度**（Suki）：①对用户本身的理解；②对用户反馈的学习（聪明下属被指出错误会自我调教）；③频次（过高=push 骚扰）；④时效性（去年的关注今天可能毫不重要）。本质是"**agent-driven 的推荐系统，但比推荐系统复杂**"：带执行属性、目标主观多维、**停留时长一定不是优化目标**（它要解决问题而不是让你多待）——前期没法 A/B 实验，非常考验产品 owner 对信息架构的认知。类比：proactive 有两种下属——纯执行型（现在很多产品的"proactive"其实只是 schedule task，要交代全部细节）vs **理解公司愿景和底层价值观的下属**（从用户 context 抽取"对你重要的东西"并分优先级）。Aha 案例：让 Today 推荐保健品——"你应该吃维生素 D，因为你工作时长太长、日照时间太短"（健康×工作多类 context 交叉）。

## 九、泛化性怀疑：产品经理的价值

高策的核心观点：**模型的泛化性没有想象中强**。证据：①自家交互 bench 上跑分最高的模型不是现在的 SOTA；②Muse 也训练自己的 Muse Spark 1.3（browser use+交互表达）；③小米开源的 RL 过程可见数据配比 60-70% 是 coding、3.5% 是 chat——"你很难相信它 chat 上表现非常好"；④开源模型指令跟随差（"说话短一点"不会短——训练 pattern 决定，推理时 system prompt 抢救不回来）。**推论：personal agent 就算模型 AGI 了，也很难完全交给模型——需要很重的人类产品设计/先验知识（rubrics）指导，先验就是壁垒之一。"模型同质化越来越重，模型成为基建以后，产品的价值、产品经理的价值越来越大。"**（例证：Anthropic 完全靠 harness/产品在卖 token。）

**意图识别**：传统"前面叠意图小模型"难维护（泛化产品会叠几千个意图、上下文在子模型间割裂）；Manus 的上下文感知状态机有意思（25 年 7 月博客：知道你要用浏览器就把工具喂到模型嘴边，疑似 sidecar 实现）。

## 十、招聘、选型、隐私

- **最稀缺的人**：懂 agent/harness+懂模型（harness 优化需要知道模型怎么工作）+懂产品——三者兼备才能端到端 co-design；每个角色都应三方面或多或少了解、各有侧重。（梦想请 Manus 的 Peak[?]过来。）
- **模型选型**：DeepSeek 做 deep research 子 agent 很好（快+便宜+"Respect，很厉害的模型公司"）；Kimi K3 和 GPT-5.3[?]长程任务好（不劣于海外次时代 SOTA 如 Opus 4.8[?]）；**交互上坦白说大家都不行**。
- **隐私**：记忆完全透明（能看到记了什么）、可删除任何内容/文件、注销可清空全部记忆。

## 十一、执行闭环与愿景

信息获取的主动（web search 推论文）→做事的主动（会前准备）→**多类交叉的主动**（维生素 D）。下一步是**执行闭环：提醒→准备→确认→执行**——"你生成的 to-do 能不能直接变成任务自动跑？我最后只需 verify 结果对不对。"当 token 成本足够低，"做错了 decline 也没多少成本"——最终连 approve 都不需要（学 Claude Code 的 auto 模式：根据你历史同意的权限学习，同类命令不再问）。潘乱的对照吐槽：各家录音硬件主打 summary"跟听写员上网的感觉一样"[?]——"出了 summary 不应该再往前来多干点活吗？帮我抢票才是我关心的。"

**废话问题**：模型爱说废话（token 越多任务完成率越高→训练导向如此），但 personal agent 里话多=提高用户认知负担——"这要模型训练解决，但现在 personal agent 连 PMF 都没有，专门干这个划不来（短期问题）。"

**打法之辨**：Muse 最大优势是有钱（24 小时云电脑、agent in sandbox 架构成本高但迭代快——"扎克伯格有钱且认为这是正确的"）；创业公司该学 Town（产品完成度最高、PMF 真实、付费转化好——"尽管现在没人讨论 Town 了"：**短期被高估、长期被低估**）。Notion 广度打法（blocks 通用能力+KOL 模板传播+一万多个模板降低二次传播门槛）vs Town 深度打法；模板复制对 personal agent 可能不成立（需求太个性化）。**从通用往 niche 做比反向好**（Town 也是通用产品找到了 email 这个 killer feature）；单一垂直 agent 危险（过拟合——移动互联网的垂直社区/垂直电商下场）；健康 context 和工作 context 有化学反应，"化学反应只能发生在通用这一层"。

**三个典型 use case**：①约会："下午几点约谁谁谁"→直接 book Calendar+发邮件（"我绝不可能让 Codex 帮我约会"）；②recording 聊完直接带上下文布置给同事（转交的委托成本极高）；③**长期目标**（学外语：沟通目标+进程→长周期计划+schedule task→发现 delay 自动调松日程→发现兴趣转向自动换课程）——"需要持续个性化反馈+长周期跟踪的体验，显著好于 Codex 类产品。"关键观察：**"Today 的记忆+主动性机制，让委托成本低于完成小而不起眼事情的总成本——这之后很多事才有可能交给 AI。"**

**愿景**：Today is your day——"不是给你带来另一个 AI 焦虑的产品，而是主动认识你、理解你的另一个朋友"；高策版："**这个世界上有一款产品，它是为了降低对你注意力的干扰而存在的 AI——希望被提及时说'它让我有更多时间去生活、去散步、去踢球'，而不是'工作效率又变高了、可以做更多工作了'。**"（潘乱：工作提效只会让你接受更多任务；日常杂事省出来的时间才真的属于自己。）
