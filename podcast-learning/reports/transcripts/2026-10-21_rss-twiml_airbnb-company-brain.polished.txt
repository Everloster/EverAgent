## 1. Airbnb 的 AI 生产力目标同时要求速度与 craft（00:04–00:07）

Ahmad Al-Dahle 认为公司的 AI 工作方式会继承组织文化。Airbnb 强调 craft，因此不能只看 PR 数量、token 用量和交付速度，还要看 defect ratio、可靠性与最终体验。速度必须有方向，AI 使用量上升时，质量约束也要同步进入工作流。

企业要让 Agent 真正工作，需要把内部工具暴露成可调用能力，把代码、政策和领域知识组织成按任务可取得的 context。一个产品工程师修改支付或定价系统时，代码并不是全部；法规、政策、历史决策和隐含工作方式也决定 PR 是否合理。

## 2. Project Everest 从工作流中捕获隐性知识（00:07–00:14）

Everest 被描述成“company brain”。它最初服务产品工程师，随后扩展到产品、设计等角色。员工在使用 AI 完成工作时，系统从流程中收集没有进入正式文档的 institutional knowledge，逐步形成共享 context pool 或 company context graph。

这并不等于把所有对话写成 Markdown。Agent 会产生大量文档，旧信息、局部经验和错误做法会污染后续任务。Al-Dahle 认为维持系统方向的核心是 eval：用稳定任务比较启用 Everest 前后的完成速度和准确性，例如非定价专家能否在复杂定价域中正确实现新规则。

数据结构仍在探索。Markdown 的优势是模型熟悉文件系统；纯 vector search 难以支撑全公司规模；简单堆文件会让模型找到过时信息。更可能的方向是混合检索和 progressive disclosure：先提供完成下一步所需的最小 context，再让 Agent 根据新状态请求更多，而不是一次塞满上下文。

## 3. 多模型与任务 eval 比绑定单一供应商更实际（00:14–00:19）

Airbnb 从单一工具很快转向 multi-model。内部 AirChat、工程师自选工具、自建 product harness 和修改过的开源组件并存。团队用一组 Airbnb 真实工程任务比较开放与闭源模型，观察 cost、quality、speed 的 Pareto frontier。

评估并不容易。任务是否完成可以二元判断，代码质量和正确性却更细。virtual judge 容易把不同模型都评在 92%–93% 附近；若 frontier 与非 frontier 模型没有分离，可能是模型都够用，也可能是任务太简单或 judge 缺少信号。Al-Dahle 更倾向先怀疑 eval 是否足够难。

## 4. Token 是采用信号，不是业务价值（00:19–00:24）

他反对用 token leaderboard 管理工程师。完全不用 token 说明需要帮助；极端使用也要检查是否把所有子任务都交给最高价 frontier model、最高思考档，造成不必要的慢和贵。使用量只能说明行为，不能说明产出。

Airbnb 尝试观察下游结果：PR throughput、缺陷与可靠性，以及 roadmap 是否压缩、项目能否更早交付。每个指标都有混杂因素，所以公司没有宣称找到完美因果度量。更深的变化是工作方式：过去 MLE、工程师、设计、产品、法务和政策团队依次交接文档，现在可以更早生成 prototype，让讨论围绕可运行对象展开。

## 5. 客服 Agent 的难题是多方调解，不是知识问答（00:25–00:36）

Airbnb 是两边市场。支付、保险、供需、房东和旅客共同构成信任系统。Agent 可以离线检测支付争议、欺诈和质量问题，也能处理简单客服任务。Al-Dahle 称约 50% 的客服 ticket 已由 AI 直接解决，并强调对用户透明标识 AI；该数字是公司口播，节目没有提供外部统计口径。

最难的问题不是“预订能否修改”，而是房东与旅客发生利益冲突。双方可能提交无法现场验证的证据，甚至用 AI 修改图片；平台还要遵守退款与公平政策，不能简单偏向一方。这是部分可观测、带对抗性的多方 mediation。Airbnb 在复杂 case 中仍依赖人类判断，Agent 先覆盖信息查询、操作卡片和较明确的长尾任务。

客服体验也有心理约束。有些用户无论任务多简单都只愿意找人，这不是模型能力不足，而是信任与预期问题。产品目标不是强行把 AI 放到每个人面前，而是在用户需要时快速完成任务，并保留升级到人的路径。

## 6. Agentic search 应增强探索，不应替用户拍板（00:37–00:45）

Airbnb 测试自然语言搜索，但不认为所有用户都想面对聊天框。很多人知道城市、人数和日期，只想快速看到选项；旅行又常是多人、跨数周的探索过程，用户会反复收藏、比较、讨论和返回。高价值预订需要信任，单次“最优答案”会剥夺重要的 agency。

因此，Agent 更适合把图片、评价、偏好和隐含条件用于筛选，同时继续提供可视化、多选项和排序控制。第三方个人 Agent 或 MCP 入口也要按 case 判断：便利并非旅行的唯一目标，平台还承担支付、保险、客服和纠纷解决。一个随机服务即使能代订，也未必能提供相同信任。

## 7. Everest 仍是早期系统，开放问题比定型答案更多（00:45–00:52）

在模型和平台选择上，Airbnb 同时使用商业、开放和自建能力，持续用内部 eval 比较，而不是预设永久赢家。Everest 的存储、检索、策展和过期机制尚未定型；Al-Dahle 将它描述为开端，而不是已解决企业知识管理。

这期访谈给出的稳定原则是：从真实工作流提取知识；用任务表现决定知识是否有价值；按需暴露 context；用质量和业务结果约束速度；在高风险、多方争议和信任场景保留人类判断。
