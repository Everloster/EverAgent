## 开场：为什么讲这期——我们的"战绩"

今天我们来讲清楚为什么 Jev 不值得那么关注，以及更重要的问题：每当有这样一个新技术的时候，我们怎么样判断——它究竟是下一个技术范式、是值得我们关注和重点投入的，还是它其实只不过是一个泡沫，或者说只是一个 hype、一个过度的关注。

大家如果回忆的话，过去两三年 AI 圈有各种各样这样的概念，比如说上一阵的小龙虾（OpenClaw）、MCP、RAG、LangChain、fine-tune 等等等等。所有的这些概念，我们都是带着时间戳，旗帜鲜明地在它刚出的时候就直接反对它——说它们虽然现在得到那么多关注、那么多大佬说这个东西多么多么重要，但是我们断定它一定会凉，大家不值得关注。而像 Agent、Claude Code、Skill 这样的技术范式，我们也是在第一时间就呼吁大家去紧密关注它，因为它真的很重要。

比如说在 2025 年的 2 月份，那个时候 Anthropic 内部还没有关注 Claude Code、所有人的注意力都集中在 3.7 那个模型上的时候，我们就跟大家说，Claude Code 其实是一个非常非常值得关注的技术范式。那之后的发展大家也看到了：可能过了半年，大家开始疯狂地吹捧 Claude Code，很多自媒体博主也因为去讲 Claude Code 而蹿红。但如果你一直关注我们的文章、关注我们的社区，你早就看到了这一点——你既不会在错误的技术上浪费时间和注意力，也会在正确的技术上加大投入。

那这期视频，我就先把这套方法完整地教给大家，并且跟大家讲清楚为什么会产生这样的 hype；以后你再看到类似的叙事框架，一眼就能看出来它的 hype 机制到底是怎么产生的，这非常有助于你提升判断力。

在这里我还有一个请求：如果你只是想来杠一下、不打算看我的视频就直接杠的话，请你直接离开。我不需要你带来的流量，不需要你带来的关注，我也懒得去跟你解释。如果你看完了视频、觉得我哪里说得不对，我非常愿意跟你讨论。

## 最重点：Jev 到底该跟谁比？

那好，我们先说最重点：怎么样去判断一个新技术好还是不好。最重要的那件事，就是看它到底应该跟什么去进行比较。

比如说 Jev 这个技术，在它自己的叙事框架里边，是跟现在的大语言模型去比较——跟前沿大语言模型比较，然后通过比较得出来：它的速度更快、它的成本更低。这就好像邵艾伦[?]去跟马斯克比较搏击一样：你找一个维度，当然是可以比的。但问题是，Jev 的竞争对手是 GPT-6 吗？不是。因为 Jev——如果你看它的机制和它要做的事情——它是一个 prefill[?] 这样的模型，它是没有 auto-regressive 的机制的（这一点你不需要关注）。那应该去比较吗？不应该。

我在这里就不说技术语言了。像以前一样，我的文章其实已经早就发到社区了，社区里边有专门的技术语言和技术讨论；在视频面前，我尽量不用技术语言。在这里你就知道：Jev 本身是一个非常简单、非常小的东西。而你如果用本地的小模型，可以做到比 Jev 的精度更高、比 Jev 的一致性更好、比 Jev 的速度更快、比 Jev 的成本更低——当然可能不能四个维度同时满足，但你这样一放，就会发现：Jev 虽然不错，但它没有一个特别突出的亮点，它也没有吊打其他的替代方案，它就是一个泯然众人的解决方案而已。可是它的这个技术叙事，把它拿去跟大语言模型比较它最擅长的事情，大家就觉得它好像很厉害。

## 判断新技术的五步法

这事听起来其实并不难，对吧？但为什么它会引起很多哪怕看上去很懂技术的人的错判呢？这就涉及到我们判断一个新技术的五层。我必须要把这个讲清楚：这种叙事框架的陷阱到底在哪儿，以及为什么大家会陷入这个叙事陷阱。

这五层分别是：你看到一个新技术，第一，先要理解这个新技术是什么；第二，你要知道它适用的范围和不适用的范围是什么；第三，你要有一个自己的比较框架——你要在什么维度上衡量它好还是不好；第四，也是最重要的，它到底应该跟什么技术去进行对标。因为技术出现总是为了做一件事；而你做一件事——你让邵艾伦[?]去跟马斯克比较搏击，当然是不合适的。哪怕我们认为搏击很重要，在搏击这个维度下，邵艾伦[?]也可以去跟另外一个搏击博主或者健身博主比较搏击；他去跟马斯克比较搏击这个行为，我们都知道是碰瓷。但是如果放到技术上，我们就看不出来这一点了。一会儿我们会讲为什么大家看不出来。

这还涉及到一个很重要的点，就是脑补——尤其在中文圈。我们中文的这些科技博主们特别喜欢脑补，而我们的观众似乎也特别吃这一套，我也不知道为什么，但我会把这个现象给大家分析清楚。

第五步就是：在你前四步都做完了以后，你去决定一下这个东西对你到底有没有用、到底需不需要关注。

## 用五步法走一遍 Jev

那我们回到 Jev 本身。我先用 Jev 做案例，回头还可以用别的东西做案例，帮大家看清楚这五步分别是怎么做的。

Jev 本身——again，不用技术语言——它做的事情是什么？就是把你现在的状态给到这个模型，然后你给它几个选项，它帮你生成这几个选项对应的概率，然后你就可以直接去做了。这个技术本身的抽象是什么呢？它其实是个 if-else，或者说一个 case when（如果你用 SQL 的话）：我给你一个 input，你给我输出一些 output，以及针对这些 output 的不同概率。想做到这一个计算，其实有很多个方法：比如说在最近的 auto-regressive 模型之前的 BERT，比如说 GPT 加上一个 JSON mode，比如说用一些本地小模型直接去取 logits、然后进行归一化——全都可以做到这件事情，Jev 只是这些手段的其中之一[?]。这是我们理解它的技术本质。

然后我们看到它的适用范围。Jev 本身[?]也去讲了它什么地方适用、什么地方不适用：它在那种很短的、需要直接回答的地方用得比较好。

第三，你针对这样一个技术，应该在什么维度上衡量它。对于这样一个我们可以叫做"AI referee"的技术，我们一般从四个角度衡量：第一是你的判断质量——判断准不准，precision、recall 这些东西；第二是延迟，你快不快；第三是一致性——每次给你一个相同的东西，你是不是稳定，同样的输入能不能得到同样的输出，因为我们要判断公允[?]，在它的使用场景下，我们需要这个东西可复现；最后是你需要可以校准——当这个东西不像我们想象的那样时，我能不能很有效地进行校准。当然在这个技术之外，我们还可以评估成本，但成本这件事你知道是不断下降的，所以我们通常会先评估技术好不好，成本再单独看。

定义好这个标准之后，我们再去看它的 alternative。Jev 去跟 GPT 比较，但完成这个任务，我们真正有的 alternative 是什么？我们会发现有好多个。甚至网上有段子：我其实有一个类似的、Python 自带的"Jev"，叫 random——生成一个随机数，然后直接分布[?]，那其实做的和 Jev 差不多。这个时候我们在质量和一致性上去比较，会发现 Jev 在很多任务上和这个 random 没有一个质变——质量上没有吊打 random，那就和猜差不多。在这种情况下它到底有多有用，就非常值得商榷了。

而在这么多种不同的技术路径里，我们也能看到：用一个本地小模型去取 logits、做归一化处理，在刚刚说的那四个维度下都是很好的。而且它有一个额外的好处：Jev 是它自己的服务，你有时需要用云端——它是一个网络服务，就是你给自己的系统平添了一个外部组件，而且这个外部组件你还打不开、还不可以调。但本地小模型既是自己的，又可以调。所以说在很多地方，Jev 都是被其他 solution 吊打的，而且它也没有什么新意。

那这个时候，我们就可以得出判断：Jev 不值得我们学习，不值得我们花这么多时间去关注它。

## 一个 hype 是怎么产生的：三个成因

可为什么中文网络就产生了这样的热潮呢？这就是这期视频的第二个点：一个 hype 到底是怎么产生的。大家注意，Jev 本身的网站其实做得非常好；marketing 那些东西我们都不说，那些都是 tactics，我们要研究的是 hype 产生的本质机制，以及过去为什么很多东西都会产生这样的事。

成因一：挑一个"碰瓷式"的比较对象，再讲一个打开想象力的叙事。Jev 很聪明：他把自己跟 GPT 去比较，而且比较的维度是大家需要的，比如成本、比如速度——因为大家现在很多人开始用 agents 以后，发现自己需要在这上面优化，而很多人是不知道提升速度和降低成本的方法的，比如说用本地小模型的 logits 加归一化，这个东西大家是不知道的。所以它告诉了大家一个新的、不知道的东西。然后它的叙事框架一打开，用了一个很聪明的做法：大语言模型是针对人类进行 RLHF 的（Reinforcement Learning with Human Feedback），而它自己说，自己是针对机器进行优化的。这个叙事打开了大家的想象力，大家马上就开始脑补：这是一个新的技术范式，然后我们未来就会有一个 AI 对 AI 的世界了，就不需要什么是让人看得懂的东西了。注意，这都是大家脑补出来的。

那这个叙事为什么不成立？因为所谓的 machine native 的世界——不针对人进行优化、而针对机器进行优化——是整个过去二三十年所有软件、所有程序所做的事：你的程序不就是跟机器说的吗？程序不就是给机器看的吗？你所有的函数都是对着机器的，不是对着人的，只是人要去写这个东西。机器和机器之间的交流，本来就是通过数据、通过所谓 machine native 的最优化方式在进行的。把大语言模型和机器结合，所有的 agents 不都是在做这件事吗？包括我们说的各种替代方案，也都是在这件事。Jev 并没有在这件事上往前多做多少，也没有提出什么所谓的全新技术范式。可是因为它的叙事，大家就直接掉进去了，对这个叙事框架本身不再质疑。

成因二：博主只做到第一二层，而叙事天然利于传播。绝大多数技术博主在这里面起到了推波助澜的作用：他们其实没有第三层和第四层的能力，没有办法找到它的 best alternative，因为他们见得不够多。他们有能力看到 Jev 以后去读论文、看原文、甚至自己 implement 一下、试用一下——他们能做好第一步和第二步。首先这已经很难了，大多数人做不到这一步。可问题是，当你做了第一步第二步、但没有第三步第四步的时候，你就陷入了它的技术陷阱：你会觉得它说的东西是真的，或者虽有夸大成分但总体成立，而且你是顺着它的叙事逻辑在往下说——你在它的叙事框架里面。这时你还会产生一种虚妄：这个技术范式别人没去看，我去看了，而且我看懂了——于是你变成了它整个叙事框架的一个传播者。

再叠加一层：过去那么多 AI 技术，能传播到我们面前的，一定是符合一定的时代特征、符合一定的人性——我们需要这个叙事框架，所以它天然有利于传播。一个技术博主讲这件事，他的内容天然就会被流量放大：一段时间内我们会看到所有人都在吹小龙虾，不吹小龙虾的人可能都看不见了；因为大家那个时候就想听一个小龙虾的叙事、或者想听一个 Jev 这样的叙事。这样的内容叠加上流量的分发机制，就会不断地轰炸我们。这是 hype 产生的第二点：这个叙事天然有利于传播，以及它会被这些所谓懂技术的博主进一步强化。

成因三：做到第三四层的人和第零层的人，结论可能是一样的。你做了第三层第四层，和你连第一层第二层都没做，得到的结论很可能是一样的。你可能是一个完全不学习、固执的人，你说"Jev 这种东西不值得关注"；做了第一层第二层的人就说：你这个人没有学习就去否定这个技术，没看懂这个叙事就去否定这个叙事，这是不合理的，你是一个草包。但看懂第三层第四层的人会说：我既懂了它的技术，又看懂了它的叙事，我得出来的结论是它不值得关注。第一层第二层的人听到你的结论，可能就已经不想听你说的话了——他们哪有注意力[?]去听你为什么这么觉得。第三层第四层的人，也很容易在这样的传播中成为一个被攻击的对象。比如我去年发的那个视频——讲炮轰[?] MCP：MCP 是什么、MCP 的短板，以及 MCP 为什么不是一个稳定的叙事框架、可一定会有一个叙事框架——下面就有人直接说"我想把你收藏进 Shabillis[?] 里边"，然后给了一堆似是而非的攻击。因为他觉得自己在第一层第二层，而我是第零层——他拒绝承认我可能知道第一层第二层的东西、而我是从第三层第四层的角度去否定这件事的。

这就是 hype 的第三个成因。它会导致很多懂的人——比如说田元栋[?]——他明知道 Jev 不好，但是他会站出来去说"没必要"[?]：他说了以后还会受很多误解，又没有时间像我一样跟大家把这个事完全解释清楚。这就会导致很长一段时间里，大家听到的都是对 Jev 的肯定声音。本来心智不坚的人，看到这些东西、又不知道为什么不应该关注的时候，你就无脑地跟进去了——就像你之前无脑跟小龙虾一样，就像你之前无脑采用 RAG、LangChain、fine-tune 一样，投入很多错误的时间精力。这对企业的管理层尤其是致命的。

## 迁移运用：MCP、LangChain、小龙虾，与判断力怎么习得

那好，这一段希望讲清楚了 hype 的成因。我们再讲一下怎么样运用这个逻辑。最重要的，就是找到它真正应该比较的对象。

比如 MCP。我们在 MCP 的视频里，先想清楚它的机制和机制的短板：把你所有该确定性的东西 pass in 到这个 context 里边，其实非常不利于 debug，也非常不利于我们稳定地操纵电脑——这个东西就应该确定性地去调用。所以 Skill 最后很好地弥补了这一点，我们就说 Skill 是可以很好地取代 MCP 的。

比如 LangChain。我们的文章里讲清楚了：为什么我们过去学计算机的时候先学 framework，但在 AI 里边不应该先学 framework——它背后其实有一个 design philosophy，我们不应该直接无脑地继承；而且因为 AI 变得太快、底层是不稳的，你在上面用一个 framework，其实是把一个简单的东西搞复杂，非常不利于我们开发。

再比如小龙虾。我们会说，它的黑盒机制和对话窗口，天然导致它在复杂任务、长线任务、或者我们想调用它的 memory 的时候，一定会有各种各样的问题；并且它那种"养"法非常不适合普通人——它该有的脚手架其实是没有的。第三个问题是过程的可观测性：你把一个简单的任务交给 AI，它直接做完了，你不需要观测任何东西；但稍稍复杂一点的东西，你这个时候就会想：它到底是在干嘛？是鬼打墙了，还是在反复思考、不断尝试新方案？调用了什么工具？改了什么文件？出了什么错？这些其实都很重要，尤其是涉及到你的一些关键的技术资产或者知识资产的时候。在专业的 agent 类[?]工具里面，这些改动都是可见的、并且可控制的；但是在聊天软件里面，你看到的是一个"正在输入"、或者是一个小菊花[?]。这个问题在越复杂的任务上越严重，因为在复杂的任务上——（此处原始音频缺约 9 秒，00:13:47–00:13:56，论述不完整）——鸭哥就直接开发了一个 OpenCode[?]，还开发了这个 OpenCode[?] 对应的 iOS 客户端和安卓客户端。就是说，你用我们的 OpenCode[?]，就是一个比小龙虾更好的 alternative，而且那个开发其实也不是一个很复杂的开发。

在 MCP、LangChain、RAG、fine-tune 的过程中，我们都是深度使用了这个技术、尝试了这个技术，拿出了评价框架，然后拿出了更好的 alternative；而且我们还要给大家讲清楚，为什么大家天然会觉得这个东西是好的——它们自带的叙事框架为什么吸引人，以及为什么这个叙事框架其实是错误的。大家如果感兴趣我们当时做的具体技术判断、以及我们怎么样用这五层的方法去看每一个技术，我在社区的文章里都写得非常清楚，当时的文章也都贴在那里，欢迎大家直接去社区看。

最后我想跟大家讲：想清楚这些事以后，我发现有两件事其实很难弥补、但我们想尽可能弥补。第一，你的第四层非常非常吃功力：我可能能做到第一层第二层，也许在 AI 的帮助下能做到第三层，但我很难做到第四层。因为你知道，吃过见过，你才知道什么东西是重要的；你真的知道其他的 alternative，你才能找到一个 alternative；你真的知道 Jev 应该跟什么比较、小龙虾应该跟什么比较，你才能找到那个东西。而且最好你还能把它实现出来，去证明你说的这个东西是真的。比如鸭哥在对比小龙虾的时候，真的去做了一个 OpenCode[?]，大家用了以后发现就是比小龙虾好用，然后大家才知道你说的是真的。不然你空口无凭——可能你想的也是错的，或者说做出来以后发现根本就不是那么一回事，是你没有理解清楚这个技术范式本身是什么。所以这件事是鸭哥的功力，是我不具备的东西。

第二，我们发现想把这个东西教给学员也很难，因为它背后是很大的基本功和很多的实践。鸭哥每当有一个新技术，他就天然地想去尝试、天然地想去思考、天然地想跟他之前脑子里的所有知识去对比。这件事如果我们没教、直接教了一个结论——"Jev 不值得关注"——反而会让学员显得像卡逼[?]：当他身边所有人都在说"Jev 好棒啊、Jev 是下一个技术范式啊"，他去说"Jev 不值得关注，我给你看鸭哥的文章吧"——第一，别人不会去看鸭哥的文章；第二，别人可能就会觉得他是一个站在第零层的人。

那怎么办呢？今年年底课程刷新的时候——鸭哥正好也 gap 回来了嘛，他 4 月份到 10 月份正在干[?]——我们会专门把这部分进行一个"复杂化"：之前我们是想方设法地简单化，告诉大家正确答案、告诉正确答案背后的原因，然后就行了；现在，我们可能会先教大家怎么样做出来一个更好的 Jev——其实鸭哥已经做了，他用了很多本地的模型去做了归一化、做了测试，你也可以做。做完以后，你可以先顺着这个叙事去讲：你不需要站在一个非常清醒的角度去告诉大家"你们都是错的"，你可以说"大家说得对，Jev 确实很重要，但是我给你一个更好用的 Jev，我们来比较，然后它就是更好用"。这件事我们都可以教给大家。与此同时，当你通过这种方式取得信任以后，你可以再说："其实这件事也不是那么重要，我们去做更重要的事吧。"因为有了前面大家对你的技术的了解、和大家对你的技术的信任，你说的话会更有分量，你在这个时候再想做什么改变，也更容易做——而不是做坐在那边批判大家的人。坐在旁边批判大家的人，一般在公司里边是不太受喜欢的。
