## 开场：半年十倍估值，一门外界看不清的生意

一文：Hello 大家好，欢迎回到硅谷101，我是一文。很多投资人在和我们聊天的时候都提到了他们最近很关注的一个赛道，那就是数据。随着模型能力的不断提升，模型公司对训练数据的需求也变得越来越复杂、越来越具体，硅谷因此出现了一批增长很快的数据公司，专门为这些模型公司提供服务。比如由三名二十多岁的年轻人创办的 AfterQuery，今年 4 月宣布 A 轮融资的时候估值还是 3 亿美元，到了 9 月，新一轮融资就已经把它的估值推到了 32 亿美元——不到半年涨了 10 倍之多，创下了 YC 旗下公司从启动到成为独角兽的最快纪录。那我们更熟悉的几家大型数据公司，估值也已经达到了百亿美元的级别：去年 Meta 入股 Scale AI 的时候给出的估值超过 290 亿美元；Mercor 去年 10 月这轮融资的估值也达到了 100 亿美元。但这些高估值背后的数据生意到底是怎么做的，外界其实很难看清。所以我也很好奇：这些公司究竟在卖什么，模型公司又为什么愿意给那么多钱呢？

一文：过去提到数据标注，大家很容易想到给图片打标签、给模型的回答打分这些人工标注。现在数据公司还需要请来各类行业专家，把他们的知识和工作经验转化成 AI 可以学习的任务。其中一类重要的数据，是请专家写清楚：一个回答、一份工作成果到底满足哪些条件才算好。这套评分标准，也就是我们经常听到的 Rubric。再往前一步，数据公司还要搭出让 AI 实际动手的环境，配上任务、工具和反馈机制，让它在里面操作软件、反复尝试，并且根据结果学习。这就是强化学习环境，也就是我们经常听到的 RL Environment。与此同时，新的 AI 评测也层出不穷，从金融、法律等等垂直领域，到让 agent 完成一整套工作流程，模型要参加的考试是越来越多了。但榜单上的分数提高了，究竟代表哪些能力变强了？针对榜单做优化，什么时候会让模型更好用，什么时候又会变成单纯的刷分行为？这期播客我们就想把这些问题聊清楚：今天聊大模型数据范式迁移，人工标注转向可验证的 RL 环境。

## 数据公司的三种基因：招聘平台、众包标注与合成数据

一文：允中要不要跟我们讲一下，现在市面上的数据公司零零总总，你觉得大致的一个分类是什么样的？

何允中：这里面有几个大的玩家，还有一些新秀，有一些几个人的 shop。在我看来最有意思的是，大家基因可能不太一样。比如说有做招聘出身的，像是 Mercor、Handshake；Scale 是这种传统数商，从众包网络出身的。然后也有一些新的是做合成的，还有最新的一些可能是某些领域公司转行做数据了。这里面值得说一下的是具身（智能）[?]：具身现在的行业状况是，有很多做模型的公司暂时没赚到钱，但是它花了很大量的精力、投资做数据，然后就顺便做起了数据生意。很多各行各业的人也发现了自己数据的价值，然后转行来做这么一个数据公司。我觉得大致有这么几个分类。

何允中：几个大的玩家，比如像是 Mercor、Surge、Scale，基本上试图什么东西都能 cover。除此之外，其实一些新秀玩家把一些领域做得比较好的，像是 Bespoke[?] 或者 Snorkel[?]，他们可能比较偏 research 跟 engineering 一点，我猜测他们主要生产代码或者是 task[?] 这一类的环境，抓住了今年的这么一个风口。另外我还看到一些小的公司，他们可能解决了一些垂直领域的问题，甚至可能不像我们是做标注数据的，就是一些 broker——比如说可能是好莱坞的一个人，他有特别多的版权数据，他知道怎么把这东西卖出去。就有零零总总不同领域的东西。然后现在最新兴起的，可能就是做这些垂直领域、把一个领域做得特别好，可能是由一些领域专家组成的。大概是这么几个分类吧。我会觉得机会还很多，大的数商有大的数商的优势——想进入一个领域有比较多的资源——我觉得整个饼是越来越大的。

一文：你讲到说像 Mercor 这样的公司是所谓的招聘公司，这个能不能再给我们具体讲一下，招聘是一个什么样的商业模式？

何允中：Surge 应该不是，但是 Mercor 它是做招聘起家的，它有自己的一个自动 AI 面试的产品。它自己主打的一个重点就是说，我能够在比较短的时间内找到足够量的专家，有这么一个专家网络。然后 Surge 我觉得更多的是把这个东西 in-house。这里反正有一些取舍吧，基本上每个数商都需要面临这么一些取舍：如果我是自己完全全职培养的人，那他肯定能力强一点，但是这个灵活度就不够，性能[?]可能会差一点；如果是更多依靠众包的网络，那么可能我的灵活性大一点，但每个人的质量就比较难保障。然后这里面就涉及到一些质检的问题了，比如说像 Scale 这些公司的一些优势就是说，我们有一些质检的经验，不光是在数据上，也在人上。

一文：允中要不要讲一下你是什么时候加入 Scale 的？从当时到现在，整个市场你觉得对于数据的需求有发生什么变化吗？

何允中：对，故事还挺好玩的。当时我是在 Meta 入股之前签的 offer，我一到人就走了[?]，所以我经历了整个大模型行业——不管从人才的战争还有薪酬体系——都开始 go crazy 的这么一个故事。当时我来之前，我的老板刘斌[?]跟我说，有这么一个技术，各家 Lab 都在做，但每个人都做得不太一样，说你赶紧进来，我就能跟你讲，然后我们在这里好好做些研究。然后我来了，那个时候是 Rubric Data，那个时候还比较新，可能一年多之前；现在 Rubric 感觉已经过时了，大家都在讲 RL Environment 各种各样的东西。就是这一年确实经历了非常多的变化。

## 从预训练到后训练：Rubric 与 RL 环境是什么

一文：其实我们关注这个话题，也是因为大概从 2024 年到现在，感觉整个对于数据的需求发生了一个比较大的变化。因为 24 年之前我们在聊数据的时候，大家想到的很多还是人工标注，就是一些比较基础的数据，我们会需要非常多的数据来做 pre-train、来训练模型。但是从 2024 年——其实 Mercor[?] 之前有提到过——是因为 DeepSeek 的兴起，导致整个行业转移到了一个所谓的 Agentic Data：我们会需要像你刚刚说的 Rubric，然后包括 RL 环境，现在就是更多真实工作流数据。能不能帮我们先梳理一下这几个概念？我们先讲一下，这个行业从 crowdsourcing data，就是这些人工标注数据，到 agentic 数据，中间是经历了一个什么样的变化？

何允中：对，首先说明一下，pre-training 还是很重要的。不过确实从我身边的人的兴趣来说，大家经历了一个 shift：大家觉得 pre-training 感觉干得有点无聊了，就是再继续 scale、调数据配比。那个时候是 o 系列模型出来了，大家都在做 reasoning，发现这个 RL 跑通了嘛，一下子大家兴趣都在 RL 上。然后 RL 比较有意思的一个问题就是说，我需要一个可验证的信号。可验证的信号在代码或者数学——尤其是最早的推理模型是从数学上做出来——就很简单，我这个选择题答错答对了就知道了，或者就是一个数字算出来。但是之后大家就在想，我数学可以做 RL 了，我在其他领域呢？比如像是医疗、金融，或者更基础的指令遵循，这里我能不能做 RL？

何允中：这里它存在的一个问题就是说，它是有一些客观标答的；不像在之前的一个阶段，大家做 RLHF 就是 reward model，可能没什么标答，只是把大家的喜好学出来。然后这里面其实就有个标答，只是它这个标答比较不结构化：就好像我去答历史考题，历史考题是有标答的，但每个人的写法可能都不太一样，我很难做这个 pattern match，就是说 ABCD 检查你有没有答对。这个时候就是一个 rubric 方式：相当于我让一个 TA 拿着教授写的打分规则来给你打分。因为这个打分规则是提前标好的、是教授写的，所以这个 TA 也不需要特别聪明。这是整个大模型数据中的一个核心概念，叫 weak-to-strong supervision——我能不能用弱模型来监督强模型？它这里成立的条件就是说，我有个专家把他脑海里的知识给写下来了，这样弱的模型拿着它改卷就行了。这就是 rubric data。这个东西应该火了很长一段时间，现在还很重要的。但是这里面很快就把各个专家领域的 rubric——就比较容易获得的——收集得比较干净了。看到比如说 Mercor[?] 或者 Surge 的崛起，其实跟这一块的专家 rubric 有关系。

何允中：但是再往前走，大家就需要动手了。比如现在做这种代码模型，或者像 Berkeley[?] 他们做的 ALE——虽然它不是做代码，但它需要动手，要解各种各样的问题——就不再是验证你一个聊天的输出了。我需要在一个 agent 的 setting 之下，给它一些工具，还有一些更复杂的验证方式。它还包含了 rubric，但可能我需要检查这个环境里面的变量是不是执行了、这个数据库是不是写入了或者被删除了。甚至如果我生成一些文档，里面可能有些图，这个东西我还是需要 rubric，但我需要一个 agent 来检查，那就变得更加多样了。现在大家可能追求的比较大的一个方向就是环境：它不光是我标注好的一些打分规则了，而是说我可能包含了一整套——我要做什么、在什么样的环境里面做，包括了它需要的一些工具、需要执行的一些沙盒，以及还有一套跟 task 比较相关的验证方式。验证方式非常多样，比如有 programmatic check，有 rubric，还有 preference——我让人选我比较喜欢哪一种。这里面我暂时还没有看到形成特别大的共识，又看到有点像当年 rubric 时代，每一家要的东西都不一样。比如像 Terminal Bench，他们就不要 rubric，就是纯 programmatic。这里面又有不同的流派，还挺有意思的。

## 从 Vibe Coding 到 Vibe Everything：详解 Agents' Last Exam

一文：这个很有意思。一铀要不要从 ALE 的具体例子来跟我们讲一下需要哪些要素？

孙一铀：其实我跟允中的看法有一点反过来了：允中认为现在 rubric 差不多已经做到头了，但我的看法是，rubric 这一块——专家那种主观的判断——其实还做得远远不够。我可以先从 ALE 的初衷讲一下。ALE 当时建立的初衷就跟允中讲的一样：我们怎么样把 vibe coding 迅速发展的趋势推广到 vibe everything。当时 vibe coding 为什么发展那么快？就是因为当时有非常非常多的 benchmark 都在 coding 这个领域，而且 coding 比较容易 verify，它是一个确定性的 rubric，大家为了刷这个榜，所以在 coding 上面的发展非常迅猛。那么用同样的思路，我们如果在其他各个领域上——尤其是工程、能够客观打分的这些领域上——能够建立各种各样的评测体系，你是刷分，但你只要刷的是有意义的分、是有意义的题，那模型带来的提升对于人的日常工作来说就是实打实的提升。这就是我们当时想建立这样一个（benchmark）的初衷。当然世界上大家职业各式各样，实在太多了，浩如烟海，所以我们只是在第一个版本里面给出了一个相对来说覆盖面比较广的初次尝试。然后我们还会继续努力，希望把它覆盖得更广一些，到某一天希望它能成为真正的 last exam——当你解决这个 benchmark 的时候，基本上就能解决人类社会在某些领域真正有益的问题。

何允中：我同意一铀的观点，各个领域的训练肯定是远远没有到头的，很多东西都可能还没有被 rubric 的方式表征出来，所以这里面还有很大的空间。可能我刚刚说 rubric 到头了，更多的是个行业趋势吧：就是这种静态的单轮或者多轮聊天，出一个文本，然后用 rubric 来检查它，就是纯知识类的。甚至也不是说到头了，因为毕竟还有不同的 Lab，每家的水平都不一样。只是说今年的一个大趋势是在做 coding，然后 coding 逐渐转向了（环境）……就是纯这种文本的 rubric，我看到需求当然小了一点，但还是很大，还是有很多东西没解决。

孙一铀：允中刚好提到了，对于很多文本上的输出，比如说文章写得好不好，你可能有一些打分点。但是事实上对于工程领域的一些产出，我们发现：除非你把输入固定得特别死，不然它的输出其实有非常非常多的可能性。我举个例子，你让它生成一个游戏，甚至有些数学解法都不是唯一的。这种情况下如果你给一个确定性的评判——一定要跟你这个 ground truth 来对比——那很多时候就会造成不一致的问题。所以我们怎么样定义这个 rubric，让它能够兼容这种多种答案的输出，其实这也是我们在构建 benchmark 中遇到的问题，也是未来想要去思考、解决的一个方向。

孙一铀：稍微抛砖引玉一下我的一个想法：未来的发展可能就是，比如说人类对于一些好玩、好看，没有办法把它固化下来成为一个可以被量化的指标，比如游戏好不好玩。但实际上有些游戏（设计）的入门教科书里，其实有各种各样的评判方式，比如说奖励曲线是不是平滑、符合大脑多巴胺的（机制），有一些科学的指标可以去量化这个"好玩"和"好看"。但我在目前的 benchmark 上还没有看到一个做得特别完整的、公开出来的评测体系，因为难度确实非常高，需要专家更加深度的参与。所以这一点我也想看看允中那边，在数据公司里有没有看到这个趋势，或者怎么去解决这一类的问题。

何允中：对，这个问题特别好，这也是我们每天绞尽脑汁的问题。其实整个 rubric，或者说整个大模型的验证体系，我觉得整体上是有这么一个思路：大家希望左脚踩右脚——当我的模型变强了，我这个验证器也变强了；验证器变强之后，我就可以允许一些更复杂的 rubric。比如如果我是一个很弱的验证器，那我就只能写一些"一个傻子都能看出来是对还是错"的 rubric；但是随着模型能力的提升，我的 rubric 就可以写得越来越模糊，可以把更多的知识交给验证器来解决。但我觉得这里总体的思路还是说，rubric 加上验证这两块加起来的知识和能力，应该比我要训练的模型要多，不然就达不到训练模型的目的了。

何允中：回到比如说 video game 这种特别特别主观的东西，我觉得未来可能是这样的：你可能很难以很显式的条件一条一条写下来"一个好的游戏是怎么样的"，它可能有多种（答案）的可能，所以这个时候我的 rubric 就会被迫写得更加模糊。这个东西 by the way 其实不是我们想要的——通常来说我们会建议 rubric 写得越严谨越好——但是在某些领域你可能就必须要写得很模糊，这个时候需要验证的模型自己做一些主观的判断。那这个验证的模型，我觉得甚至有可能是专门训练一个 reward model。我知道在不少 Lab 里面——这大概不是客户透露给我们的东西，是我自己的一些经验——比如生图有两个部分：一个是 instruction following，有没有遵循我的要求，比如图里面有猫有狗、有一个背景板写了哪几个字，这个时候我会有 rubric，我就写"这里要有一只猫、那里有只狗"，甚至跑一下 OCR 把那个字提出来，看看是不是我想要的那几个字，这一块属于 rubric。但还有一块是说，这个字要写得好、这个猫要是一只可爱的猫——这种东西我可以写成 rubric，但它非常主观，那我可能甚至专门训练一个模型，这个模型可能掌握了一些人类的主观体验[?]。这些东西可能跟 rubric 结合在一起，大概率这个问题如果要解决的话，可能是这么一个混合的方向。

## Rubric 与环境如何配合：人与 Agent 的分工

一文：我们刚刚好像把 rubric 和环境这两个事情放在对立面来说，但听起来，一是它们可以结合在一起使用，二是有没有一些任务是用 rubric 来做会比较好、或者用环境来做比较好？

孙一铀：我觉得这个肯定是不能拆开来讲的。环境或者说任务数据，它只是一个执行的基准，但 rubric 是最终用来打分、用来奖励模型做得好还是不好，所以它肯定是相辅相成、必须结合在一起来看的。我个人更希望从一个任务分类的角度去看，而且人和 agent 这两个角色如何合作、分别担任什么角色，这也很重要。我们从历史上来看：最早期 vibe code 刚出来的时候，大家用 Cursor，其实人类也是参与在执行这个代码当中的，agent 只负责执行很小的一个模块的一些写代码；但后来随着 agent 能力越来越强，你给它一个非常模糊的（需求），它能够完成一个非常大的 project 的时候，人和 agent 的角色又产生了一些变化。现在可以大致分成两类：人负责决策，agent 负责执行；人把你决策的东西说得越清楚，agent 就能做得越好。

孙一铀：就着这两个分类，我们来看 rubric 该如何去设置。如果我们需要 agent 参与的角色只是执行——你如果把一个任务说得很清楚，它的输出基本上是固定的、唯一性的——那这个东西的 rubric 就是一个确定性的 rubric，打分完全可以基于一个你自己做出来的成品来进行，因为一般会有 ground truth 基准。如果我们讨论未来（数据）需要（做什么）：人的这个决策的部分会不会也被 agent 慢慢取代？那这一部分我觉得会回到之前允中说的——大家现在反而没太重视这些 rubric，因为决策很多是非常模糊、很难去量化的。而且允中说，你对于一个具体的 domain——猫可不可爱——可以 train 一个这样的 verifier；但是对于尤其是一个上市公司领导层的决策，你该如何去 train 一个 reward model？它每天的任务都在变，你很难收集到足够的数据来训练出这样一个 reward model 替你做这样的决策。所以我个人认为，这一块的模型发展还有很长的路需要去走，而且这可能会成为一个未来发展趋势。

何允中：这里我特别同意。比如 ALE 的这个方案，我觉得就是面向未来。比如"猫可不可爱"，我要是在 Meta，有一些用户行为的反馈，我可以训练这个模型；但是公司的决策，我就很难收到这些数据了。像 ALE 这种，让大家把以往做过的东西还有决策交上来，其实是一个方案。我会觉得以后收数据，可能是大家怎么样找到好的激励方式，让大家把一些重要的东西交出来，尽量能够回溯当时这些重要的决策。

## 从做评测到卖数据：benchmark 的生意

一文：非常有意思。我想再追溯一下评测近几年整个的发展，以及它和卖数据之间的关系。其实我和两位私下都聊过，卖 benchmark 和卖数据这两件事情，大家都觉得不能混为一谈。Scale 之前推出了 Humanity's Last Exam（HLE）这个评测，能不能给我们讲一下这个评测，以及你觉得它和数据之间是怎么样联系起来的？

何允中：这是个好问题。我觉得从原理上来说，评测体现的是模型距离我们想要的理想状态中间的这个 gap，它更多的是一个科学研究的基准——我想要模型在哪、它现在没到哪。但是这个事情跟卖数据联系起来也比较有意思：因为很多时候，提升模型能力的数据和它榜单的评测方式是息息相关的。这里面可能比较难的是找到一个平衡：如果我生产大量跟这个榜单差不多的数据，那可能就是在 benchmaxxing；但大模型训练还是有各种各样的维度，如果我想要提升某一类的能力，我需要抓住某一个维度，那它跟 benchmark 肯定有一定的相关性。这个是大家需要找到的一个平衡。因为大家对 AGI 的期待太高了，觉得人能做到的事情它都能做到，那么我在各种各样的领域都可以想到一些方式构造一个 benchmark，然后发现这个模型距离理想（状态）[?]当中还有一些差距。通常构造这个 benchmark 的人对于这块领域认识比较深，那么就自然会给他一定卖数据的权威性，大家会比较相信你手上卖的数据，这个生意就这么产生了。我相信一铀应该也有（这种经历）——就 ALE 现在做得火，应该也有不少人想问你卖不卖数据，或者有可能 VC 也想找你投资，结果逐渐逐渐地就成了一个生意。我觉得也有好有坏吧，这个生态其实还比较野蛮发展，有多少是在做科学、多少在做生意[?]，我觉得确实需要仔细权衡一下。但这确实有很多的利益驱动，所以现在是个挺繁荣的市场。

孙一铀：对。这里我也是要给大家敲个警钟。允中提到了现在做 benchmark 的人会收到各种各样的诱惑，要把 benchmark 数据拿去卖了；我甚至私下听到有些数据公司在做（买卖）评测的数据[?]。当然这个是大家千万不能碰的一条线：不能让你做的生意污染你这个 benchmark 的权威性，不然的话你不仅毁了你的 benchmark，也毁了其他人的模型。我个人认为 benchmark 和卖数据这两个东西角色是不一样的，在这个生态系统的地位上，我认为 benchmark 面向的是未来，做数据面向的是现在。benchmark 是面向未来大家还期望这个模型公司去解决什么目前还没有解决的问题。其实 ALE——我们在今年一月份、二月份做的时候——特别害怕 benchmark 做得太难导致失去意义，因为当时的模型很多基本上平均分只有 10% 到 20%，大部分题目都只拿到零分，我们很担心这样的评测会失去意义。但事实上没有必要担心这个事情，因为 benchmark 本身就是要面向未来的模型去做的；数据的话，更多是去解决这个 benchmark 所产生的一些需求，比如说现在大家在刷这个榜单，然后怎么样去把这东西做好。我认为 benchmaxxing——（只要）它不是直接污染你这个 benchmark，然后你这个 benchmark 刷的又是有意义的榜单，只要这个 benchmark 和真实用户的体验非常接近——我觉得 benchmaxxing 不一定是一个贬义词。

## 什么样的评测值得刷：核心能力、真实场景与分布难题

一文：benchmaxxing 这件事其实特别有意思，因为一方面我们确实需要一个评测的基准，另一方面你又不希望模型公司为了刷评测而去刷评测。我觉得这里很自然就产生一个问题：什么样的评测才是有意义的评测？我们现在一周就感觉可以看到很多新的 benchmark。从模型公司的角度来说，他们应该怎么样去选、去刷哪些评测，或者把哪些评测作为他们下一步提升模型能力的目标？从你们供应商还有 researcher 的角度来看，你是怎么样看待这件事情的？

何允中：我觉得做模型能力提升，最大的 ROI 还是我要放在能力上。这些能力提升了，它应该是汇集到各个 benchmark（的分数）上。当然可能有些人有不同观点，因为对于一些模型厂商来说应用也非常重要：比如如果我的这个 benchmark 比较贴近一个应用场景，他们其实有动机把这个场景做好，对他们也是有益的。最有意义的事情是，大家至少口头上还是奔着 AGI 去的，那我应该考虑哪一些核心的认知能力是我需要提高的。它体现在 benchmark 上就是说，我可以看到一些泛化性：如果我做了一个提高，它只涨这个、别的都不涨，那可能有一些不好。所以回到一开始的问题，未必是说怎样的一个 benchmark 是最好的，而是不同的 benchmark 测试了不同的东西，我可能要关注的是哪一些共同的能力能够让他们一起提升，而不是只专注于优化同一个 benchmark。

孙一铀：另外再回到 benchmark 本身的问题。我倒是觉得，除此之外大家确实会关心一些贴近场景的 benchmark：如果这些场景是大家在意的、确实反映了用户体验，这也是个好 benchmark，它未必那么 universal、未必那么大朝着 AGI 去，但它确实体现了大家的体验。在这个角度上来说，benchmark 肯定是千奇百怪，你总会找到一个场景。我觉得可能是两个要素：一是这个场景的 gap 是不是体现了一个非常具体的能力缺陷——如果只是因为这一个场景的一些场景知识不太懂，同时这个场景又不太重要，比如我在一个犄角旮旯里面解了一个很奇怪的智力题、出了一个 benchmark，这个能力提升了未必代表模型本身的认知能力提升了，那可能就不是一个好的 benchmark。另外一块就是说，就算不反映核心能力，它至少反映一个大家在意的场景。比如现在特别火的是 personal assistant，就是进入这个 MUSE[?]，这是一个很具体的场景，大家都希望有这么一个东西。那么这个 benchmark 甚至未必测的是模型本身，它可能还测了你的 harness；最后这个 benchmark 甚至不是为了卖模型的训练数据，而是告诉你我的 harness 错在哪，可能我可以做些工程优化。贴近大家需求场景的 benchmark 也是好的 benchmark。所以在我看来，一个是反映核心的认知能力，一种是贴合场景，当然两个都有的话是最好的。

孙一铀：我觉得最重要的、现在大模型公司很看重的一个，就是 benchmark 的分布。大家应该可能都听说过 Artificial Analysis 这个评测体系，他们做的事情很简单，就是把各家 benchmark 给不同的权重，然后综合到一起得到一个分数。但这样它就存在一个问题：这个分布的权重是不是真的是大伙需要的权重？权重以什么方式进行迭代？这都是挺主观的事情。大家质疑的更多不是这个模型本身，而是质疑这个榜单本身。我现在倾向于认为，大家可能（是）benchmark 还不够好，做到大家心目中要的 distribution 的那种级别，很难达到一个 ground truth。所以现在很厉害的模型厂商，比如 Anthropic 或者 OpenAI，他们都会倾向于自建一个评测体系，让它更接近他们心目中的分布，只不过第三方的制衡[?]可以让他们对外发布的时候更有说服力一些。当然比如说允中说的，一个垂直领域的（benchmark）肯定是非常重要的，因为这个就是面向下一类群体，它的分布就是那个群体每天在做的事情；如果能把那个分数刷高——比如金融、法律，他们律师每天做的事情能把那个做扎实了——那他们（做）法律只需要看这一个 benchmark。

何允中：（但一个 benchmark）不能代表真实的认知[?]。比如之前有一些 benchmark 是测 agent 智力的，就是玩那种小游戏、ARC challenge 那种游戏——ARC-2、ARC-3 这种。它这个 benchmark 的初衷是说，觉得能解这些游戏是人类智力的一个体现；但没想到这个智力其实也可以做得特别特化，我一个小模型也能把它搞出来。还挺有意思的。

一文：那有没有什么特别 niche 的 benchmark，大众不太了解、但其实非常有用（能）测试模型能力的例子？

何允中：我可以举个我们的例子。我们有一些 benchmark 可能不太经常出现在大家的榜单上，比如我们前一阵子做的 drug discovery，还有一个跟 AI tutor 相关的，它可能关心的是一个比较小的垂直领域。但跟我和各个 Lab 的交流（来看），负责相关领域的团队通常就会有这么一个人，他会看市面上跟他领域相关的评测，都会把它收回来。另外一个就是说，这个 benchmark 最后上不上榜单、火不火，其实也有很多随机因素。比如 AA 就有一个很好玩的事：AA 用了我们做的一个榜单叫 SWE Atlas。我们当时做了几个不同风味的 SWE Atlas（子集），其中有 Q&A——就是代码仓库问答——还有代码重构，还有写 test。只不过我们是分三个阶段推出的，Q&A 先推出，推出之后我们还没来得及把另外两个推出、把它们合在一起，然后 somehow 那个 Q&A 就先被 AA 捡去了。Q&A 上了 AA 之后，大家就开始 cite 这个东西，突然间这一块的需求就变大了。我们当时想得很不理解：Q&A 是最简单的一个场景，我们花了那么多心血做了更复杂的 benchmark，结果就是因为可能是时间关系，还有的时候是某一个 Lab 用了、碰巧它的分好。这里面其实是有一些随机因素的：你在这个榜单上、大家在 tech report 上看到的东西有一定随机性，AA 收这些榜单有一些随机性。最后就是你没看到的东西，背后可能也有人在用。这个生态水还比较深，还比较复杂一点。

一文：明白。我还想再问一下，就你刚才提到的大家对于 Artificial Analysis 这样榜单的质疑，你说（它）不接近于大家理想中的分布，这个分布现在有没有一个共识呢？因为我理解每个模型公司对于分布的需求其实也不太一样。在这种情况下，我们怎么样去理解这个理想状态下的分布？它应该比较接近真实世界的一些任务，还是说是别的分布？

孙一铀：我觉得真实的分布，本质上就是大家的用户体验。假设世界上存在这样一个 ground truth——真实分布的真实打分——其实有点类似于 LM Arena 这种模式：你每天 prompt 这个 agent 的时候，能够有多条模型一起在执行，然后给它们打分，这是最真实的评价。但现实生活中能够做到这样的榜单（很难），有以下这种因素：LM Arena 之前能做好，是因为之前的 QA 很快、开销很低，你给它一个问题，它能够几秒钟之内给你一个答案，你很快就能进行打分；但现在在 agent 的时代，一个长程任务动辄几个小时，一个用户也没有那么多的"超能力"，每次执行一个任务都连着开几个 agent 一起去执行，然后也没有个机制把反馈收集起来。所以大家的评价很多都是偏主观的，很难拿到这样一个真正的 ground truth。但如果说有哪家公司或者有某种方式解决了这个问题，那肯定很厉害。我相信他们大模型公司内部肯定是有这样一个机制的：让它有几个版本的模型，然后有一些用户真实用了这个东西，然后去测……然后你这个评测分数的分布接近于这个东西，那它就是一个很好的 benchmark。

孙一铀：我听到一些比较有意思的：很多评测 benchmark 跟我线上做 A/B test 测出来的结果是不一样的，用户的反馈跟评测有时候不太一样，甚至很难说哪个好，因为用户有时候也比较主观。像这种聊天的，你可能给他特别多 factual 的东西，versus 给他很多 clickbait——说他爱听的话——可能结果也不一样。所以这块还是挺复杂。

何允中：对，是这样的。就像 Claude Code，我觉得在 Arena 上分数一直遥遥领先[?]，就是因为我觉得 Claude Code 它有个特点：尤其中文用户或者英文用户，它给出来的 output 的 format 更贴近于人们心目中想看到的，就非常容易去理解。相反的，Codex 可能执行得更细致一些，但是输出的东西就没有那么（容易）被人理解，相对来说没那么容易理解，所以稍微吃了点亏。但我个人体验（作为）用户下来，他们两个可能不相上下，其实我个人还更偏好 OpenAI 那边一点，因为它做得更细致、犯的错误更少。所以这个确实也是很主观的一个事情——怎么去定义好这个 distribution。

一文：所以在这种情况下，模型公司还会把 benchmark 视为判断自己模型能力的一个标准吗？

何允中：他们肯定也是在乎外部的评价。不同模型公司——我先说美国那家大的，他们肯定是倾向于自建为主，就是自家的 evaluation 团队，因为他们有这个能力去建。但是对于一些刚成立的、或者相对没有那么有名气的 frontier labs，或者不是头部的 frontier labs，他们肯定会非常依赖于外部的评测，因为它内部的评测团队可能没有那么有经验、或者那么完善，或者说他们的人力资源更希望投入到模型的训练和开发当中，而不是去直接（做评测）[?]。所以每个公司的标准[?]都不太一样。

何允中：其实我的个人判断是说，当一个产品逐渐成熟之后，或者当你积累了一定体量的用户之后，最后你其实关心的还是用户增长。比如我之前其实做了很多年在 Meta 做搜索跟推荐，逐渐地就变成了一个类似搜索推荐的问题：你看什么样的指标跟用户增长最相关，最后就是朝着赚钱的方向走的。现在可能真正能够评测到这个能力的 Lab 不太多，需要一定的用户体量；可能在聊天这个场景就比较成熟了，但是在这些 agent 的场景上能做到这个程度就更复杂一点。大模型跟传统搜推不太一样的地方就在于说，它的场景很复杂：就算我能够在 chat 场景做好很好的 A/B test，甚至训这个 reward model 来朝用户喜欢的方向发展，我总会有新的东西出来，而且大家一直在看新的东西。比如现在大家都在卷科学发现——科学发现，我不可能有足够量的科学家给我显著的 A/B test 的结果，必须还是要依靠场景构造 benchmark。我会说，因为大家对这里应用场景的期待太高了，场景增长的速度赶不上我在这个领域用户沉淀的速度，还是有大量的需求要依靠 benchmark 来做评价标准。但我会觉得在某一些领域沉淀下来之后，大家会有更多的线上评测体系，然后可能会像传统的互联网增长，看看哪些指标跟用户的 DAU 增长更相关。

## 两三人的小团队为什么有机会：合成环境与垂直采购

一文：能不能深入讲一下数据采购这件事情？我觉得有几个点非常有意思。第一，你提到刚才有很多小的公司其实是现在一个创业机会——为什么我们看到很多最近新起的四五个人、甚至两三个人的数据创业公司拿到了非常高的估值？是不是因为他们的目标就是这些非常垂直领域的数据？

何允中：对，我觉得这里可能有几块问题。首先，最近兴起的这些 RL environment 的公司，其实更多的是在做合成。因为整个数据行业已经从找人标注慢慢过渡，你要交付的是一整套环境，这个环境可能需要大量的工程工作在里面。很多在合成的技术栈上做得比较好的小团队，其实可以在比较短的时间交付大量的合成环境。这些未必是不好的：合成有时候你也可以基于一些强的模型、或者基于一些半成品的 artifact，做出一些好东西来。现在这里是一块增长。但是再往下走，这里面比较有意思的是：这个东西之所以能成立，是因为大家今年的主题是在卷代码。软件行业是最奇怪的一个：它非常 open，有大量的公开资料，而且我们生产数据的公司（里）大家都懂代码，所以就比较好解决，让一些小团队有很多机会可以自己造很多数据。但是我觉得再往后面走，这些其他领域的垂类就更复杂了。

何允中：这里面我会看到有一些公司，他们可能解决两个不同的问题。比如像我们做后训练数据，其实在我看来是两个问题：第一是采购，就是我把原材料买回来——就好像 ALE 让大家上传，这是一个比较新的激励机制[?]；然后加工，就是我们再把它标注，或者通过一些 agent pipeline 把它做成适合大模型训练的环境。在垂直领域问题上，采购其实变得越来越复杂。甚至代码领域，其实采购一些私域的代码仓库（也不容易）。如果是做芯片设计的，我可能要把整个芯片设计的环境给造出来，当中可能涉及一些商业软件，那我怎么样把这些商业软件的版权拿到、把它包在里面，就是一个问题。还有比如做 DevOps，我要是一个系统工程师，要操作 AWS 之类的，然后有公司做了一整套 AWS 模拟器。每个垂类的环境都有一些很深的东西，你可能要采购、可能要定制软件。大家抓住一两个垂类把这个东西做好，其实创造了很多新的机会。

一文：明白。垂直场景，比如 drug discovery 这些生物医药方面的，还有一些具体行业的评测，我们可能没有足够的场景或者足够好的评测，在这种情况下我们有足够好的数据吗？

何允中：这里其实有一个难点：每个领域需要一些人把它的专业知识吐出来之外，我还需要这个领域的东西。像药物发现，我可能需要很多私有的数据库。这里面我觉得是目前这个行业一个大的卡点：你先要能把这些东西买到，（手上有了原材料）才能把它做成数据[?]。ALE 其实很大程度上是在解决这个问题。

孙一铀：对，ALE 就是希望大家能够以众包的方式，让专家把之前自己做过的 project 交上来。当然这里面有一些不符合规范的我们都筛掉了，因为他们甚至把一些非常非常（敏感）的东西都交上来了，比如法院的一些证据什么的，就是非常（不合适），我们尽量把这个都筛掉了。比如我们现在在 V2 中也尝试去收一些数据，比如 Steam 上的游戏库。就游戏开发的一个任务：一个名不见经传[?]、赚了大概几千人付费[?]的一个 mobile 游戏，它要价能要到两三百万人民币一条。我觉得哪家数据公司或者做 benchmark 的都没有这个财力去做这个事情。游戏公司会要价要到两三百万人民币一条，要这个游戏的源码。比如很多公司想采一些游戏的视频然后做些标注，游戏视频可能是版权数据，这里有一个巨大的采购问题。我觉得这里是一个商业机会[?]，我现在其实看到不少 startup 在解决这些问题。就绝大多数数商[?]，我们自己也在投入做一些采购方面的工作，但总体上来说，我觉得这里有很巨大的问题没有被解决。

一文：有哪些现在非常热门的垂类是数据非常少的？

何允中：我会说至少医疗算一个，数据比较敏感——谁能拿到大量的病例数据，那就非常有优势。

一文：对，因为其实也有很多新闻讲到，可能在法律或者金融这些领域，会有一些之前离职的员工去分享他们的工作流。不过工作流数据和医疗数据里这些病人的 data 还是不太一样。

何允中：是的，各个领域（都不一样）。我甚至觉得，现在大家之所以都在说金融、医疗，只是因为跟大家比较息息相关吧，大家多少还懂一点。其实这个世界上有很多我都不知道的行业，你真的要跟他们聊才知道。比如我才知道，做药物研发，大家还会交易这些分子，一个分子还能倒腾几手，这里面还要做 DD（尽调）[?]。所以可能没有做（这些领域的数据），只是因为大家不知道。

孙一铀：对。我们在做 ALE V2，想要把比如一个领域做深的时候，会尝试先捋一个领域它会有哪些工作流，会有一个树状的结构。尤其在生物学这一方面，Nature 这个 publication 有自然的分类，它对子学科分类，然后把这个树展开到第三级的时候大概有 3000 个节点。然后我们也做了一下工作，把现在已有的市面上 life 和 bio 的 benchmark 已经覆盖了多少做了一个统计——大概可能 10%、5% 都不到。现在它连一个成型的、覆盖面完全的 benchmark 市面上都没有，更别说是针对这个去做相应的数据。

## 模型自己造数据之后，外部数商为什么还会存在

一文：那像我们刚刚提到的这些做合成数据的小公司，他们能赚钱的周期有多长呢？听起来好像都是这几年新出现的公司，这些数据的生命周期有多长呢？

何允中：这是个好问题。至少现在需求还是挺大的。未来可能说，这一波 coding 讲完了，那他们需要新的品类，大家能不能抓住下一个机会？而且下一个机会可能跟你现在的运行模式不太一样。比如我自己会觉得采购会很重要，那么采购能力比较差的可能就比较难。或者就像一铀他们，你可能有些新的激励机制让大家把东西交进来。以前的激励机制是招聘平台、或者就给你一个小时工，但以后可能有新的激励机制，谁能把这些东西玩得转，可能会继续有一些优势。

一文：这个地方我想问允中你的看法。因为我个人认为，随着模型能力越来越强，模型公司自己内部创造数据的能力也越来越强。你说这个饼是越来越大的，但有没有可能出现一个情况：这个饼面向非头部公司的机会，门槛反而是越来越高的、入场券是越来越难拿的？就是数学这块领域，之前大家只要去影印那些奥数课本，就能够批量造出大量数据，但这些数据现在基本上是零价值。所以你是怎么看待这个趋势、未来数据公司的发展方向？

何允中：我会觉得，从第一性原则上来说还有巨量的问题没有解决。你想这个世界上还有多少东西没被蒸馏干净，是巨大的机会。但是如果你就看现在大家是怎么运行这个事情，当然会越来越难，因为越来越多的玩家进来了。我觉得大家如果只盯着我手上的工作，这个一定是越来越难做的：就算这个 Lab 不自己做，越来越多竞争对手进来，你的 margin 也会越来越低。所以在我看来，一个好的数商其实最后解决的是个研发问题，就好像一个软件公司一样：我要提前投入未来大家需要的东西，赚到钱之后再投入下一个东西。

何允中：在 Lab 本身，我有个暴论：可能 Lab 未必有最好的基因来解决数据的问题。这里面可能有几块。比如合成数据，按理说很多就是 Lab research 的本职工作了，尤其是搞后训练，大部分时间都在搞数据——买数据、核数据、验证数据、洗数据。但是这个领域你会觉得，为什么外面的人会有机会呢？somehow 今年的这一波增长都来自于一些懂行的人，在外面把这个数据合了再卖回去，所以这个事情是存在的。我觉得一方面是因为大模型公司现在有太多的钱了，你自己造、外面买其实也不矛盾。但是在更长远上来说，其实有很多问题可能模型公司没有太好的基因解决。比如如果我要采购，要把一些行业的东西先采购回来、蒸馏出来，这个时候我会觉得大的 Lab 未必有那么大的优势，它甚至可能会有一些 conflict of interest：比如一方面把你的 FDE（forward deployed engineer）派到了人家企业里面，另一方面你有一拨人在搞这个企业数据，那么我会觉得，如果我是一个企业，我是不太放心把我的数据交给你的。出于这些原因，有一些东西可能 Lab 不太适合自己做，它可能还是需要第三方的人帮它做一些采购，或者深入到一些行业领域里面去。

何允中：我会觉得一个数商真正要做的事情是研发：看看未来还有哪些行业是重要的，这些行业有哪些东西值得投入，把东西买回来，然后自己先投入 R&D 把这个行业的问题研究清楚，然后再把它做成 benchmark 或者说数据，甚至证明这个东西的有效性，然后再转手卖给 Lab。从 Lab 来说，大家的 deadline 都很死：如果我是一个 Lab 的 research（员），你让我花半年的时间来解决一个行业，可能有时候大家其实没有自由度。这个时候你看到那边有一个数商说"我把那个行业的东西搞清楚了，你要不要"，大家通常都会看一眼。所以我觉得其实长期来说，拼的还是一个研发能力。

一文：你觉得这个趋势对于大模型公司来说会持续吗？现在模型公司里面也有自己的数据团队，但你觉得他们更愿意从第三方那里收数据，而不是自己去造环境、造数据？

何允中：这里我觉得可能不矛盾。最后模型公司最高的优先级还是把东西做好，如果他们自己能生产好的数据的话，有可能会倾向于自己生产。只是现在大方向上来看，这个世界上还有太多的工作流没有被吃透[?]清楚，那么对外部数商的依赖我觉得是长期存在的。甚至一个大模型实验室自己可能未必想要投入那么多的资源、做得这么重，可能更 prefer 灵活一点。缺点（反过来）就是说，大家可能希望更多的东西是第一方的，不希望所有人都能从数商那里获得这些能力，所以从这个角度来看会有一定的动机自己研发。比如现在很多 Lab 在做 expert matching，就是说你把人派到我这里来，也有这么一些趋势。我自己也会觉得说，现在有太多东西没有被解决了，不管是谁把这些问题解决了，那他一定有赚钱的机会，跟在哪里发生不是很有所谓。现在是机会多、饼在变大的这么一个阶段。

一文：但这也是大家对于数据一直有的一个问题：如果一个第三方供应商把同样的数据卖给不同的模型公司，那中间怎么样去区分呢？

何允中：这里通常来说有个比较简单的解决方案：你可以花多点钱把这个数据买断。

## 数据买回来怎么用：SFT、RL、模型训模型与难度适配

一文：你觉得对于模型公司来说，在从数据供应商那里收到那么多数据的情况下，他们怎么样去使用这些数据？这个流程能不能给我们讲一下？

何允中：一般来说它有一些比较固定的训练方式，我们把它叫 training recipe。比如比较简单的数据，可能就是直接 SFT——我把对的答案给它就行了。然后像是 rubric 这一种，可能就是在做强化学习，因为不停地有一个模型在给它打分。比较有意思的是现在这些 RL 环境，比如最近大家在卷的一些特别长程的任务。现在今年的一个主题是 RSI，就是 recursive self-improvement，它其实是个 buzzword，就是说 AI 自己研发自己。大家最近就在看那些（任务）：我跑一把可能要跑个几天、一个星期，其中你可能要有个 GPU 真的在上面（跑）、模型训模型的任务。这里的训练方式其实就开始变得有一些模糊了，我们也在一起研究这里面的训练方式要怎么搞。但是我自己觉得，这里面还没有太多的共识，所以还有很多有意思的空间。对于数商来说，有时候也不完全是造一个模拟的 task 这么简单，你还要考虑模型公司拿去要怎么训，然后针对它怎么训可能还要有一些定制。

一文：对，这一块我也比较好奇。如果说你就是为了 benchmaxx，你拿 ALE 的一些任务直接去训练，类似做一批这样的数据，那你怎么保证这个数据训练出来，模型能力、泛化能力是能够提升、能够被迁移到其他的任务上去的？有没有一些比较系统化、科学化的方法来做这样的验证？如何在不吹[?]一个模型（的情况）之上，能够评判这个数据能给模型带来怎样的提升？

何允中：对，我觉得这里其实有一些技术。比如现在如果我要造一个环境，大家最怕的就是 reward hack——它有捷径：明明我没有完成这个 task，我可能做了一些手脚，结果 somehow 我的分可以打得很高。我训出来的模型肯定会变成一个耍滑头的模型，这种东西肯定是不希望发生的。那么通常来说会有一些技术，我可以用 agent 来做 red team：我会让一些比较强的模型来试试看，能不能在这个 task 里面找到捷径。另外，这里面很多是我自己的个人猜想，不代表 Scale 或者任何客户：在训练这些东西的时候，很多 benchmark 我们可能只关心最后有没有完成这个任务——我们的验证器是围绕这些东西设计的——但是我怎么样完成它，这些东西可能也会在模型训练里面有一些关键作用。一个比较 trivial 的例子就是 budget：比如我训模型的时候，我会关心它是不是消耗了过多的 token、或者用了这些步数[?]。那么我们在训练它——比如拿 ALE 的（任务）数据训练的时候——最后 reward 会很复杂：不是说我把这东西解出来就行了，我可能还关注它消耗了多少资源，最后在各种各样维度检查 reward、防止它作弊。这些东西结合起来才能完成一个训练的 recipe。其实就感觉也没那么简单，这些可能是训练数据更多要考虑的问题：我的这些数据能不能导出一个比较好的训练方式。

一文：能不能讲一下像 RSI，或者刚才我们也提到很多 new lab[?]，在这些情况下做这些训练，需要的数据有什么不一样吗？或者需要的定制有什么不一样吗？

何允中：通常来说，最常见的定制其实是难度。大家做 benchmark 的时候，一般来说至少希望它不那么饱和，那就意味着越难越好；但也不一定，比方一铀说的，也不要完全解不出来——benchmark 的难度更多的是一个客观反映行业难度的事情。但是在我训模型的时候需要做一个特化：这个难度对它的模型要是适中的。我们有时候会做这个事情：模型厂商会把他甚至还没有发布的模型给我们，然后我们帮他筛数据——这个题目对他来说不能太难也不能太简单。因为现在做强化学习是让模型在上面自己试，如果试对了的话他就能学到一些东西；那我给他题太难了，他啥也做不出来，肯定就不行。所以在这个难度上会做一些适配。然后另外可能我们会做一些轨迹采集：比如你把你的模型轨迹给我们，我们可能把这些轨迹采集出来，帮你做一些筛选，甚至我们想办法用人给你搞一些可以解这些问题的轨迹，这样你可以拿回去不需要做强化学习，直接照着这个轨迹做 SFT。针对它的训练需求，其实也有一些特化的工作。

## SWE-bench Verified 争议、数据污染与专家造假

一文：OK。接下来还想再聊一下数据污染的问题。今年二月的时候，OpenAI 宣布停止报告它在 SWE-bench Verified 里面的分数。这个其实也是一套评测，具体来说就是让 AI 修复真实开源软件里面的项目问题，再通过测试来判断它有没有修好。当时 OpenAI 主要指出了两类问题：一类是测试本身可能会有缺陷，比如有的功能上正确的解法也会被判错；另一类就是数据污染——这个我觉得很有意思：他们发现在特定提示下面，模型能够复现部分题目原本的人类修复代码，也就是说模型很可能在训练过程当中就已经接触过相关内容了，所以这个分数就变得有点难解释了。我想问一下两位是怎么理解数据污染这个问题的？

何允中：就 SWE-bench 这一类数据其实有一个问题：它可能甚至还不是污染，就是它 task 可能就做得不够好。比如有时候有一些错误是假错误——可能我的测试脚本要求的太多了，或者是我的 task 没讲清楚，有这么一些类型的原因。另外一个污染可能是说，模型预训练[?]的时候把这些东西都训练进去了，这里面其实是有一些技术可以检测到这些东西的。我想 ALE 上面应该会有些这种经验。要不然他（OpenAI）说不采用 SWE-bench——他是连 SWE-bench Verified 也不采用。

孙一铀：就是当一个 benchmark——我印象中它是在过去的六个月内只从 74% 提升到了 80%——然后剩下的一些问题可能是脚本写得太 harsh 了，或者题目本身就是不可解，或者会有各种各样的问题，它剩下的可能 20% 都集中在这个问题上，那这个 benchmark 本身可能就失去了对比的意义。

孙一铀：ALE 也没有解决一个问题，这个也想跟允中探讨一下：当一个专家本身提交上来的材料是错的时候，我该如何去预防这个问题？这个是我们真实发生过的。我们专家五花八门，当然这种（情况）很少见[?]：他是为了提交这个任务、为了拿到作者（身份），因为我们的奖励机制就是你提交了这个东西、我们接纳了你这个任务，就能被纳为作者列表的一部分。确实是有人为了提交而提交，然后他甚至（用）agent 去合成一堆乱七八糟数据，甚至有些数据交上来我肉眼看出来它就是编的。这个东西确实对我们的工作造成了很大的困扰，这是一个特别大的问题。（规模上来）总是有人（造假）[?]，总是可以靠人解决的。

何允中：这里有个特别有意思的问题。比如一铀提到了我给他这个 authorship 是一种奖励机制，那它会带来一定的问题。上规模[?]，那更原始的，比如我就给你小时工，那大家也有一些偷懒作弊的方案。我会觉得这个奖励机制是个特别特别难的问题。长远来说，比如我的目标是把人类都蒸馏干净，那怎么样设计一个好的奖励机制，把大家的目标都 align？我觉得这里其实有特别大的空间，可能是个巨大的 research area。我自己心中可能有一些方案，proof of work：比如我要求你把做这个东西的一整段工作流程全部都录下来，你必须要做到多少时长或者怎么样。不同形式的问题有不同形式的奖励和验证机制，这里面其实有很多玩法值得大家探索。

一文：这里面其实也涉及到一个更大的问题：很多数据本来也就是公开数据，就是网上的一些资料、公开代码这些东西。所以这些数据是不是本身就注定了会有污染？一般是怎么样处理这些情况的？

孙一铀：其实最简单的污染，你直接问 agent 他都能找到，公开数据其实还好检测。我觉得最难的是编造数据：比如让你去做一个化学模拟，他根本就没有跑过这个任务，他自己编了一套似是而非的东西，你没有个几个月根本查不出来这个问题，因为它看上去很真。什么时候能发现这个问题？当所有的 agent 能力至少远超这个问题本身的时候，发现所有的答案做出来是一样的，但是跟这个正式答案[?]是不一致的，这个时候我们就会查出问题，但这个周期会非常长。但是你让另外一个专家去验证这个问题，成本又非常非常高，因为这个问题本身都是要专家花一个多礼拜或者两个礼拜才能做出来的。

何允中：对。然后那个验证的专家，你要保证他——验证的专家他本身也会为了一些东西偷奸耍滑，说"哎，他就是对的"。

一文：所以每个涉及到专家评测都会有这个问题吗？

何允中：对，都会。众包的 benchmark 为什么难做，就是难做在这里——人性是非常复杂的。

孙一铀：是。我觉得这里验证可能甚至只是（其中）一环[?]。我自己觉得确实在奖励机制上（可以做文章）：比如如果你就让他在那老老实实待够 12 个小时[?]，你给我合成假数据也要把每一步都给我交出来，要求你必须做这么多的动作，那他可能就没有那么大的动机给你合假数据了。这些是比较值得研究的方向。

## 真实工作流、并购拿数据与研发飞轮：行业下一步

一文：嗯，很有意思。其实我本来是想问一下真实工作流的数据，但是听下来大家现在还是在卷 coding 数据是吗？不是在做真的 workflow？我理解像 Mercor 这样的公司有在卖一些真的 workflow 的数据，但听下来 coding 现在还是这个赛道最卷的。

孙一铀：其实（要看）您怎么定义真实工作流的数据。真实工作流的数据本质上都能够被化归到一个 coding 的问题。比如 3D 建模这个问题，其实有很多——比如 FreeCAD 什么的——都提供了现成的 API 让你去做这个事情。这不是传统意义上的 coding——让你去写一段代码去解一个 LeetCode 这种 coding 题——它是用 coding 去解决真实 workflow。所以只要有足够的 MCP/API 调用，本质上 95% 以上的任务都能够被化归到 coding 的问题上。

何允中：对。可能有一些小的（差别），可以看它这个 task 本身要的是什么东西、涉及到的一些环节是什么，能把它归结到不同领域的工作流上去。但就我（同意）一铀说的，现在你让 agent 来做事情，代码就是它的手跟脚，所以归根结底 coding 肯定是其中的一环。

一文：明白。你们觉得在私有数据需求依然很大的情况下，未来的数据公司会不会从卷采购本身变成卷并购——就是去收购一些垂直领域的公司？

何允中：对，不评论 Scale AI。我是听说有一块很大的 private equity business：以前大家是 flip 公司，现在 flip 公司的一个新的方式就是，我买了这个公司，然后用 AI 让它提效，把一些人裁了，之后把这个公司的价值做上去再把它卖了。现在就多了一层：除了我买这个公司可以把它重组打包、用 AI 提效之外，我还能把它的数据发掘出来，它的数据还能卖一些钱。所以让整个买公司的行业又多了一个玩法。很自然地，数商或者传统做 private equity 的公司也在看这个数据怎么能够卖钱，然后就兴起了一整个领域。我甚至觉得说，如果真的未来五年、十年还是这个速度发展，大家还没有遇到瓶颈的话，把各个行业的东西都给拿出来，可能这个东西跟大模型本身就是世界上最大的两个行业。当然这是比较极端的——这个 AI doomer's view[?] 可能会导出这么一个世界。

一文：是的。但是听起来数据行业本身变化也非常快，就像我们刚才提到的从 rubric data 到 RL 环境的这样一个变化。所以有什么信号会让你觉得，有某一个领域或者某一个赛道可以持续地增长吗？

何允中：我会觉得，首先还有很多没有解决的问题，机会还是很多的；另外一方面有越来越多的玩家进来了，比如每年都有很多新的 new lab，资本市场还是以这个方式运作的话，这个饼是越来越大的。但是这个数据（生意）变化很快，不太像是一个我可以躺在一个地方一直吃老本的生意。数商要疯狂地迭代自己，那么最后可能是拼大家的 R&D 的能力，或者说谁能把这个 R&D 的能力本身固化、做成一个 flywheel——我有一个流水线可以一直在发掘新的东西，也许这个是未来最大的优势。但就这东西上来说，我会觉得现在是百花齐放，未来机会还很多。

孙一铀：这我也是从一些地方听说：数商的估值空间一般没有传统的公司来得大，因为它很难把杠杆保持住，让你以很轻松的方式、在一个积累的用户量情况下就能躺在那里吃老本挣钱——就像 Facebook、Google 的一些生意[?]，它已经有积累大量用户，就能躺在这些 APP 上变现。但数据生意，领导者必须持续地去思考、去迭代，因为模型迭代速度太恐怖了。

一文：你觉得你们现在在做 ALE 2.0 的时候，最难的是什么？

孙一铀：我觉得学术上相对容易一些，比他们 Scale 要好做一些[?]，因为他们给我们的数据很多都是无偿的。但是我能够想象得出，我如果是一家数商去收这个数据，这些都是天文数字——那些收上来的原始项目和代码。而且很难找到一个很好的奖励机制[?]，让这些专家能够自愿地把这个交上来。我拿 Mercor 他们官网上给专家一个小时的价格来说，比如制造业的工程师大概一两百刀一个小时，这种价格就限定了他不可能招到特别特别高级的工程师。但是为什么学术界好做？因为我们能够自然而然地吸引到一些这种级别的人来帮我们收集数据，因为他们不求钱，图的是大家一起把这个事情做好，图的是革命[?]。所以这个奖励制度不一样，就导致你能吸引到的人不一样，你的上游是不一样的。

一文：OK，很有意思。好呀，那我们就到这里结束吧。谢谢允中，谢谢一铀参加我们的节目。

何允中/孙一铀：谢谢一文。谢谢，谢谢。
