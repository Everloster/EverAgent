## 孙宇涛自我介绍与研究经历：为什么对架构创新最感兴趣

张小珺：这次我邀请了清华大学的 PhD Candidate（博士候选人）、上海创智学院璞锐学者孙宇涛，将由他带领大家一起来学习和阅读最近大家关注度非常高的 Kimi K3 的论文，之后宇涛还会带大家读一系列的论文。宇涛，你能不能先给大家做一个自我介绍，并且介绍一下你的研究方向？

孙宇涛：好的，各位观众朋友，大家下午好，我是来自清华大学的孙宇涛。我博士期间的主要研究方向是大模型的架构和预训练，博士课题是从 2023 年开始的，从那个时候我们主要研究大模型架构的一系列工作。那个时间点应该是 ChatGPT 刚刚发布一段时间，但我们的架构研究其实从 ChatGPT 发布之前差不多就开始了。这两三年我的主要研究方向，就是尝试解决大模型在推理环节的一些低效性，所以我们主要的研究方向都是围绕推理高效性来展开的。大家也可以注意到，在模型架构这个方面，整个业界的研究方向也是逐渐从性能为导向，变成以效率为导向，这里面其实有一些范式上的变化：在 Vision 时代或者说 ImageNet 时代，大家还会尝试去做更精妙的一些架构，来提升模型本身的表现；但在大模型时代，我们逐渐发现，对模型的性能而言，模型的参数量永远是最主要的一个因素，模型架构本身的改进，相对于模型参数量本身的提升，带来的性能提升是相当微小的。但不同的架构在模型推理方面的性能差异是巨大的，这个也主要决定了模型最后部署的价格，所以这两年大家主要在这个方向上去努力。

孙宇涛：对于我而言，我们是在 2023 年开始探索线性注意力这个方向的。我们的 RetNet 这个工作，从现在这个阶段来看，主要解决了两个问题。第一个问题是，线性注意力怎么能在一些比较 general 的场景下，尽量去逼近全注意力的性能。Linear attention 刚提出来的时候，主要是想用一个 linear kernel，以 kernelized 的方式去拟合二次复杂度的全注意力这样的 attention，所以在之前那个时代，linear attention 对位置信息其实是不够敏感的。其实在那个时代，linear attention 和 RNN 只是在形式上比较相似，但从建模的特性上来讲，RNN 其实还是比较强调 locality 的一些表示。所以在那个时代，我们在 RetNet 上比较早地引入了一个 decay（衰减）的机制，这样可以让线性注意力在一个有限的状态空间里，尽量去建模那些对最后的结果贡献足够大的信息。然后这个工作刚开始的 motivation，除了模型性能以外，我们当时也是比较早地提出了一种 chunk recurrent 的线性注意力 chunkwise[?] 计算形式，也就是 chunk 的计算形式。因为对线性注意力来说，如果把这个整个的状态都展开，在 token 这个维度去做递归的计算，它从效率上并不是最优的；但如果仿照注意力这种计算方式去建模，它又享受不到整体计算复杂度带来的优势。所以我们当时是在并行表示——像全注意力这样的并行计算形式——和全递归的计算形式之间，找到了一个 trade-off，也就是块递归（chunk recurrent）这样的计算形式。chunkwise 既可以拿到整体计算复杂度上的收益，同时我们能在 chunk 层面尽量多地调用 Tensor Core，把 local 的计算密度都拿满，这是我们提出的一个比较有效的计算方式。大家其实可以关注到，之后所有线性注意力的改进工作，都是基于 chunk recurrent 这样的计算形式去计算的，包括 Mamba2、Gated DeltaNet，包括来到今天的 Kimi Linear（KDA）这样的计算模式——在这个大的计算模式之上，又带来一些新的比较细节上的变化，这个可能今天后面会更详细地来讨论。当然，从现在这个视角看，纯线性注意力作为纯线性注意力的模型而言，无疑是一个比较失败的尝试，因为无论如何，这个比较有限的 context，都难以在长上下文[?]中和全注意力有比较完全相同的性能——这个在今天这个时间点我们都知道是不可能的。当时我们在 2023 年也注意到了这个现象，所以我们就尝试从全线性注意力转到 hybrid attention 这样的架构形式。Hybrid attention 顾名思义很简单，包括 Kimi Linear（KDA）其实也是这样，就是用一些线性注意力和一些全注意力组合起来，作为一个模型的架构。这个本质上听起来像是一个工程上的 trade-off，也是一个比较工程的解法。虽然如此，我们当时就发现一个现象——这个也是目前大家公认的——混合注意力虽然从架构上来讲是一种 trade-off，但从最后模型本身的表现来说并不是一个 trade-off。包括大家其实发现，在保持一定全注意力比例的基础上，整个模型其实是可以获得无损、甚至更好的长上下文表现。也就是说，在混合注意力模型的架构中，我们并没有牺牲一定的全注意力模型能力来换取工程上的收益，所以从这个角度上来讲，也是因为这个实验上的结论，从而导致混合注意力现在被大规模地利用起来。（张小珺：这是你的第一篇工作吧？）对对对，是的。

孙宇涛：后来我们会发现，混合注意力其实在工程上是一个百分之百[?] work 的方法，我觉得其实没有问题，当然直到今天它 work 得也还是不错。当然了，对一个博士生来讲，这个东西虽然比较 work，大家也愿意去说，但从 taste[?] 上其实感觉就差点意思，而且感觉也不够有趣。当时我们觉得，如果只是把这两种注意力模型结合起来的话，它有这么几个问题，最大的问题就是它在推理上的加速比，永远和混合比是正交的——或者说也不是正交，就是完全成正比的。现在大家比较常用的混合比例大概是 3 比 1，也就是全注意力在整个模型里大概占四分之一这样的比例。如果说我们认为四分之一是一个比较无损、也是一个比较极限的比例，那其实我们很难拿到更大的加速比：无论是做 prefill 还是做 decode，我们最多的加速比也就是四倍。当然我们做纯线性注意力的时候，希望的是更高的加速比，而混合注意力其实只是一个常数级别的改进，所以当时觉得可能不是很有意思，后来就做了 YOCO 这样的一个工作。当时我们的一个 motivation，是我们从第一性原理去思考：为什么纯线性注意力没有办法获得和纯全注意力一样的性能？原因也很简单，我们至少希望模型有一些比较基本的能力，比如说我们至少有一个可以获取全文信息的能力，所以在这个场景下，全上下文的 KV cache 这一点是没有办法去省掉的。既然 KV cache 没有省掉，我们能不能从另一个维度去省？从 token 长度这个维度没有办法去节省，我们就找到了另外一条节省的方向，就是从层间这样去节省。所以 YOCO 当时做的，就是所有层共用一份 KV cache 这样的一个架构方式。另外一个就是从模型计算的角度，每一个 token 在 decode 的过程当中，它的计算密度是没有办法去减少的，因为我们希望它保持一定的全注意力计算能力，这样它才能达到我们希望的长上下文水平，所以我们提出的另一个东西，就是希望把模型的计算和存储解耦开来。所以当时我们可以看到，虽然我们只有一份 KV cache，但是可以保持一个多层复合[?]的计算结构。在这个基础上，我们当时的 YOCO 架构，就是只保留一份 KV cache，但是可以获得和全注意力或者混合注意力基本上等价的模型计算结果。这个架构还有另外一个优势：我们在 prefill 的时候，可以直接跳过全注意力的计算。Prefill 就是模型处理用户输入的这样一个阶段，我们本质上只是希望可以拿到模型的 KV cache，这个 KV cache 是用于后续 decode 的一系列 hidden states，所以 prefill 的唯一目的就是去得到模型的 KV cache，因为 prefill 阶段我们是没有必要解码出每一个位置的 next token prediction 的。所以在 prefill 阶段我们就可以直接跳过 cross attention，但是在 decode 阶段，我们可以保持和传统模型一样的一个计算能力。（张小珺：这个标题也挺有意思的。）对，这个也是致敬 You Only Look Once，当然后来后面也有一系列致敬的工作。（张小珺：你只能缓存一次，是吧？）对，是的，从 KV cache 的存储角度，这个基本上已经达到极致了。我们都同意，如果从 token-wise 角度我们必须能保证的话，一份其实就是最少了，不可能再少了，所以从 KV cache 角度这是一个比较极限的结果。

孙宇涛：然后讲一下我个人的第三篇工作。在这个工作里，我们其实是从一个更通用的角度来考虑问题：模型的推理开销主要就分为三个部分，就是 prefill 的时间开销、decode 的开销，和 KV cache 的存储开销，这三个是最主要的模型推理开销，不可能有第四个。YOCO 这个工作我们主要解决的是 prefill 和 KV cache，但是没有解决 decode；decode 的话，后续大家会尝试用 sparse attention 的方式去解决，不过 K3 目前其实是没有用 sparse attention，所以这块今天就先不讲了。然后我们后面的一个工作，是和另一个赛道比较相似的工作，也就是 loop language model。顾名思义，就是我们在保持一个固定的模型参数大小的情况下，通过多次迭代来提升模型的 FLOPs，从而去提升模型的总能力。loop 这一系列的工作，主要目的就是可以在保持一个比较小的模型参数的基础上，取得比同参数的模型好更多的一个效果。但是传统的 loop language model 在 decode 的情况下，它的成本其实是难以忍受的，因为它只是省了模型参数，其实并没有省计算，而且在相同计算下，它其实是并不如把参数展开、或者说用一个更大的但是不去 loop 的模型的最后总的效果好。传统的 loop language model 其实还有一个问题，就是它的 KV cache 存储会随着模型推理深度的增加而增加，所以最后总的算下来，loop language model 所带来的总的 KV cache 其实是相当大的。Universal YOCO（YOCO-U）这个工作，其实就是在这个 YOCO 架构的基础上，去做一个位置上的改变，也就是我们把 loop 的单元变成一个很 efficient 的单元，从而避免推理的时候一些额外的、或者比较大的成本，但能保持模型效果比较稳定的一个增长。解法也很简单：对 YOCO 而言，毫无疑问它是一个混合注意力架构，但我们的混合注意力方式不是一个交错式的结构，它是一个两端的结构，也就是说模型的前期是一个全线性注意力，但模型的后期是一个全注意力这样的架构。所以我们的选择，是把 loop 这样的一个架构只集中在线性注意力这样的位置，这样的话我们对整体 KV cache 的增长是比较小的，因为 linear attention 本身的 KV cache 其实是微乎其微的。第二个就是，线性注意力它不仅省存储，其实也是省计算的：在长上下文这样的一个场景下，它带来的额外计算是相当小的；虽然 linear attention 所带来的 attention decode 的计算是相当小的，但从 in general 的模型能力上——比如说模型的 perplexity，或者从模型的 scaling behavior——它是可以获得足够接近全注意力的模型能力的。所以我们这个架构其实可以达到的一个效果是：用差不多两倍于原模型的计算强度，我们基本上就可以获得两倍左右的性能提升，但我们的模型存储和模型的 KV cache，还是保持和原模型差不多这样的一个推理开销。这是我第三个工作，因为去年开始 loop language model 是大家比较热议的一个话题，然后我们在这方面做了一些探索。

张小珺：所以你从 2023 年一开始读博，你的研究方向就一直在架构创新上，对吧？而这次 K3，它在 LLM 的架构和预训练上也做了很多工作，这也是我们今天来找你带我们读论文的原因。你为什么一直对架构创新比较感兴趣？

孙宇涛：对，是的。因为 Kimi Linear 刚发布的时候，当时我们之间其实也有一些讨论，其实这项工作的连续性还是比较强的，包括 Kimi Linear 其实也是比较原封不动地搬到了 K3 的一个总 backbone[?] 里面。我觉得（为什么对架构创新感兴趣）有两方面吧。从个人角度，我觉得架构创新比较有意思，比较好玩，因为别的层面的工作，工程性的因素会更强一些。当然架构创新也有一些比较工程性的因素，但它的工程性主要来源于你需要做一些 kernel 上的 co-design[?]；不过即使是 kernel 上的 co-design，其实我们之前也提到了，比如说我们提出的 chunk recurrent 这样的计算形式，它本身其实也是 kernel 层面的一个创新，所以我觉得这个事情比较有意思，而且它比较能起到一个四两拨千斤的效果，我觉得对博士生来讲是一个相当好的研究领域——当然在 2023 年是这样的，到 2026 年的话，可能架构创新能做的其实是越来越少的，这个是从个人层面带来的一个考虑。然后从整个领域的角度而言，我觉得其实全注意力当时是一个非常大的瓶颈：如果说大模型推理要大规模地应用，Attention 这个东西是一定需要解决的，而且我们相信是一定可以解决的。所以在那个时间我们觉得，从整个行业来讲，架构创新是对于模型部署而言最重要的事情。

## K3 论文讲解的框架与脉络

**张小珺**：其实是一起来读 Kimi K3 论文，但你对于这篇论文有很多自己的想法，所以你也做了一个不一样的分享结构，并不是完全根据这篇论文展开。能不能介绍一下你整体分享的结构和逻辑？

**孙宇涛**：我一般想 Talk 的主要逻辑，就是从模型本身、比如说从一篇论文本身出发。当然所有论文都是建立在之前无数个 Related Work 的基础之上，所以我会去选，比如一篇论文它有几方面的贡献，若干贡献的背后各有一条历史研究的脉络。对，我一般的风格是会把这个脉络打开，这样达到的一个效果就是：如果只看这篇论文，你会知道它是这样做的，但可能不太清楚它为什么这样做，或者说历史上大家是怎么做的、为什么最后达到了这个结构。我觉得从一个比较重要的点展开，从观众的角度是一个比较好的学习方式，这样讨论也会更综合一些，因为如果只是一个点，意义是不够大的。

当然模型架构这块可能篇幅会比较多，一个是因为 Kimi K3 本身做了比较多的模型架构方面的创新工作，另一个是模型架构这一块的研究脉络其实相当清晰，每一个部分都有一些比较固定的 credit，我们可以拆成一个个点，然后给大家讲出来。后面也会有一些关于 infra 的内容，因为现在其实都比较依赖 infra 和模型架构的 co-design，这两块是密不可分的。别的一些，比如说 pretrain data 的话，大家肯定都是比较秘密的状态，paper 里也没有写，我也不会讲这个 paper 里除了公开内容以外的一些东西，所以这块就会涉及得少一些。

**张小珺**：那你的罗列结构让我感觉到，其实我们最后看到的是 K3 的一个呈现，但它其实是有很多人的 credit 的，不只是 Kimi 一家公司，对吧？

**孙宇涛**：对，是的。这也是现在做 frontier 这些模型一个有意思的地方，它要吸收很多之前其他人的工作，然后我们也把 credit 都给到大家。我们这篇讲解就是，除了你能理解 K3，也能理解它是怎么来的，对吧。我觉得做一个公司，比较科学的方式就是，如果你最后想把这个模型做好，你肯定是要集百家之长；当然如果只想用自己的工作，那可能就没有必要了，基于这样一个目的去做工作，可能就会错过别人做得比较好的工作。因为无论如何，整个行业都是由大家集体推动的。所以我觉得这也是 Kimi K3 一个比较好的点，包括它之前的一些 paper 也是这样的，我觉得比较客观、比较真实，就是把前人的一些工作用一个比较可靠的方式引出来，不会说想办法去削弱之前一些人的贡献，这其实是它做得比较好的一个点。

**张小珺**：所以我们这次是从 K3 出发，然后其实是串联起了不管是十几篇论文也好、技术报告也好，还是比如说苏剑林老师的博客也好，就是有很多的那种……那我很期待，我们开始吧。

## 领读·导读：sequence depth width 三维 scaling 叙事

好，Kimi K3 从前面它的主要卖点来说，我觉得可以从几个方面讲，它有一个比较大的概括。首先它说了它的一些结果，这些结果特别好，而且这些数都摆在这里，其实没有太多可以解读的。那为什么能达到这样的结果？Kimi K3 主要 claim 的是三个维度的 scaling，当然我觉得最重要的还是模型大小的 scaling——它做到了 2.8T 这样的模型大小，而且是一个比较有效的 scaling 结果。什么叫无效呢？无效的 scaling 我今天就可以给你做：我晚上回去起一个 2.8T 的模型 unit[?]，跑个 100B 的 token，然后就可以放出来了，这显然是无效的。所以 scaling 永远要建立在有效的基础上，Kimi K3 就是在 2.8T 这个 scale 上做了一个有效的 scaling。这个模型参数大小，包括模型激活，来到了 100B 左右的量级——在 Kimi K3 发布的时间点，其实是比国内开源模型的其他几家要大很多的。然后它另一个扩展是模型上下文长度的扩展，在这个维度它做到了 1M 这样的量级，1M 自然可以获得更大的上下文窗口，去解决更复杂的任务。所以从模型总的来看，我觉得还是遵循一个第一性原理：更大的模型才有更大的智能上限，如果别的东西没有做太错的话。大家可以看到，模型参数大小还是解决模型智能最本质的参数量。当然如果只看 benchmark，你有无数种方式去达到一个对内或者对外满意的结果，但从模型能力的本质上说，模型参数大小还是最有效的方式，而 Kimi K3 是一个相当早期、或者说相当成功地达到了这样一个量级。

然后到模型结构章节。模型结构这块，Kimi K3 其实是综合了 Kimi 整个团队、包括整个业界过去一年以来比较重要的一系列创新。这跟 K2 不一样：K2 当时 Kimi 的发力方向主要是模型 scaling 本身，或者说模型架构的一些创新，所以 K2 当时主要沿用的是 DeepSeek-V3 的结构；但 K3 就跟 K2 大不一样了，Kimi K3 本身引入了很多比较新的、或者说比较创新的设计元素——自己的也好、别人的也好，有些比较创新的 setting，或者说比较细节的条约，这块其实做了很多比较充足的准备，所以从观感上来看跟 K2 的感觉是很不一样的。首先是 Hybrid Attention。Hybrid Attention 我刚刚也讨论过一些，我们可以翻回头来，从 Kimi 本身的写作 writing 看起。这块我会先讲一下线性注意力在过去三四年以来的历史发展状态，因为你如果直接读 Kimi Delta Attention，会发现它的公式相当复杂——对不同的项具体是怎么来的、它具体承担什么样的作用，如果直接看公式，你会发现它特别特别长，比如说比经典的 attention 要复杂很多，而它每一项背后都有一个历史性的因素，或者说都是大家从对整个模型结构的探索中最后得到的结果。所以如果想了解 Kimi Delta Attention 最后是怎么设计出来的，我们还是有必要去探索之前的线性注意力经过了怎样的发展阶段。

然后让我们再回到 RetNet，这是刚开始必不可少的一个线性注意力发展阶段。刚开始的线性注意力非常非常简单：把 K、V 乘出来得到一个外积，然后把它加起来，所以刚开始的线性注意力其实比 RetNet 还要更简单。RetNet 在线性注意力的基础上引入了一个衰减项，这个衰减跟 token 的位置有关，这样就把 linear attention 从一个 position invariant、位置无关的角度变成了位置有关。位置有关最主要的方式，一个就是可以加 RoPE，另一个就是可以加衰减项——因为无论如何，语言的特性就是更近的位置有更高的权重，所以如果我们想在有限的上下文理解上达到更好的结果，衰减项是必不可少的。这是线性注意力比较前期的一个经验，这个衰减项之后所有的工作基本上都保持住了。另一个主要的影响就是 chunk-wise recurrent 的计算形式。因为如果我们只是做偏学术性的研究、或者说只是发 paper 的话，其实大家不会从一刚开始就比较强调 kernel 足够高的一个效率；但我们的发现是，完全使用递归的形式去计算，它其实特别慢，在训练过程中甚至直接要比 parallel 形式[?]——类似全量 attention 一比一[?]这样的计算方式——还要慢；但如果我们直接用这种 parallel 形式，就感觉十分傻：因为在训练之后就相当于完全没有享受到线性注意力的收益，它跟全量 attention 一比一[?]的计算强度是一模一样的，甚至还要更高——因为可能有一些别的处理，或者说我们的 kernel 写得没有 Flash 的好，这些都是有可能的。所以我们当时觉得，无论如何都要找到一个比较可靠的计算 pattern，在足够发挥 GPU 能力的同时，享受到一个复杂度上的加速，所以当时我们就做了这样一个事情。

RetNet 之后有两个比较重要的节点。一个是 Mamba，Mamba 当时是把位置无关的衰减变成了位置有关的衰减；接下来就是 DeltaNet。当然这个概念不是松林提出的，DeltaNet 是之前的一个工作，松林是在 DeltaNet 的基础上开发了一个突浪动作锐的[?]——其实就一句话：如何能让 DeltaNet 转化为一个 GPU 可计算的 chunk recurrent 计算模式。当时松林去做这方面工作的时候，我还稍微有点疑惑，我说看上去好像 DeltaNet 不太可以并行，他说可以并行，并且他已经搞定了。所以从 GPU efficiency 的角度，DeltaNet 主要是解决 infra 上的一个困难，而且这个解决方式我觉得还是一个比较本质的方式。DeltaNet 刚出来的时候，我们当时尝试去解决（这个问题），因为当时我们知道线性注意力在处理全上下文的能力上不如全注意力，所以当时有两个方案：第一个方案就是我直接认输，就去认定线性注意力不可能匹敌全注意力——可能当时我是这种心态，我当时意识到从线性注意力的视角出发很难匹敌全注意力；当然松林是另一个想法，他当时觉得还可以再努力，可以努力去提升线性注意力本身的一个常识爱门[?]容量，从而获得更好的结果。DeltaNet 当时就是这样的目的：通过这种方式，我们可以获得比之前的 RetNet 更好的常识爱门[?]容量能力，本质上也就是在相同的 KV cache 大小的情况下，从算法上提高了线性注意力的上下文容量。当时 DeltaNet 是没有做位置衰减的，从 perplexity 或者说从 benchmark 上它的结果不是特别好，所以我觉得一个比较显然的事情就是：既然我们知道位置衰减这个事情本身可以帮助模型总的能力，那为什么不把这个衰减和 DeltaNet 这样一个更高容量的 linear attention 结合起来？Gated DeltaNet 正是这么做的——结合 delta rule 这样一个更高的线性注意力计算容量，同时给它带来一个衰减，同时融合这两个，我们就可以得到一个更优的线性注意力表达形式。

这里就可以看到，如果没有 α_t 这项的话，它其实就是一个比较经典的 DeltaNet；引入衰减之后，我们就可以得到 Gated DeltaNet 这样的一个形式。大家就可以注意到，这个表达形式其实已经比刚开始的线性注意力要复杂很多了：如果把 S_{t-1} 后面的一个系数完全消掉，其实就是最经典的 linear attention；RetNet 和 Mamba 是把这项消掉的，得到的一个结果就是我对上一个时间点的历史状态进行一个衰减，这就是之前的 RetNet 和 Mamba 的结果；然后 DeltaNet 是引入了 gated delta rule 这样的一个方案，写成递归形式的话又额外再增加了一项，这样的复杂度就慢慢叠加了上去。我们再回到 Kimi Linear，它其实在 Gated DeltaNet 的基础上又变了一个东西，大家可以去对比一下是怎么引入的——主要的区别其实就在衰减项上。比如说在 RetNet、Mamba-2 和 Gated DeltaNet 的情况下——当然了，线性注意力是分 head 的，一般的线性注意力也是分 head 的，但我们一般写公式会考虑只有一个 head 的情况——如果只有一个 head，Gated DeltaNet 也好、之前的工作也好，这个衰减项其实是一个标量。也就是说，我整个 head 遵循的衰减系数是一致的，这样的好处是它在 kernel 上比较容易、写 kernel 比较方便；如果把 decay 拆成更 refined 的形式再去写 kernel，它其实是一个不太好处理的项，这是出于写 kernel 的方面。从模型能力方面，当然我们毋庸置疑：把一个标量的衰减变成 channel-wise 衰减，严格来说是能力更强的。Kimi Delta Attention 其实就是把 Gated DeltaNet 的衰减项从一个标量变成一个更 fine-grained control 的量，这样每个 channel 可以的衰减系数是不一样的，这样可以带来一个严格更好的能力上限——因为从公式上来讲它是严格更好的：无论如何，channel-wise 的 decay 是可以退化到一个比较均匀的 decay 的，是严格更强的模型能力，会带来更好的效果。

当然，对 Kimi Delta Attention 来说，更强的模型能力其实是有一些代价的，它的代价就是写 kernel 会更麻烦一些。麻烦的点就在于，我们不能说作为 decay 一项[?]，其他部分可以用一个比较方便的方式去利用 Tensor Core 来进行计算：如果是一个标量的衰减项，它的处理会特别特别容易，一个 tile 就只有一个变量就完事了；但如果把它从标量变成 channel-wise，它的处理难度就会增加很多。这样的处理难度，也会带来在 Kimi K3 里边一个更细节的 co-design 处理。这样就来到了 lower bound 的 decay——为什么有这个东西，两方面的原因：一方面我们可以认为从算法层面，希望它不要 decay 得太快；但从 paper 本身而言，它其实是为了和 kernel 进行一个 co-design。原因在于，我们想去处理更 fine-grained 的 decay 的话，需要在这个数值上做一个比较巧妙的处理，也就是对于 Q 和 K 而言，我们会做一个 decay 倒数的一个变换。我可以举个例子，最简单的例子就是 -2 可以表示为 3-5。这其实跟 RoPE 的思想是比较一致的：RoPE 在 inference 上一个特别方便的地方，就是它可以通过绝对位置变换去表示相对位置变换，这样整个计算会容易很多；RoPE 的思路其实就是用绝对位置来表示相对位置，所以对于衰减而言，它其实也可以用绝对位置来表示相对位置。也就是说，比如我们有一个衰减项，它是 α 的平方这样的一个衰减项——当然这个衰减项可能是第 0 个 token 对第 2 个 token 的，或者说第 100 个 token 对第 102 个 token 的——所以如果我们想用绝对位置的话，就会选择让 Q 先做一个比较大的衰减，然后让 K 往上提升得比较大……

## 领读·线性注意力前世今生（RetNet Gated DeltaNet Kimi Linear）

比如说我让 Q 做一个 3/4 方的衰减的提升，然后让 K 做一个 5/4 方的反衰减，这样通过乘法结合律，我们就可以得出和原来的 Delta Rule 比较等价的形式。但这就带来一个问题：对于 Kimi Delta Attention 来说，它会对 QK 的其中一边除一个很小的数，对另一边乘一个很小的数。这可能没有关系，它无非就是 decay 到 0，并不会带来数值上的问题——当然我们也不希望它 decay 到 0。从数值精度上来讲，我们希望把它控制在 BF16 的精度范围内，这样利用 RoPE 那种用绝对位置来表示相对位置编码的方式才是有效的。所以为了让衰减在一个固定的 chunk 内部控制在一定的精度范围内，我们需要从数学上把它控制住。比如 Kimi Linear 这块是一个 16 个 token 的 tile，我们就希望衰减在这 16 个 token 的 range 里边不要超出 BF16 的范围。当然 BF16 的精度范围是我们已知的，可以通过它反解出在 16 个 token 的区间内我们最多可以衰减到多大的量，Kimi Delta Attention 就大概选了这样的一个量。这块我们可以去证明：就在 16 个 token 的 tile 里，衰减是不会超出 BF16 的 dynamic range 的。这块对 decay 设 lower bound，更像是一种 co-design——我们通过模型算法层面的一些控制，让它在一定 tile 的内部不要出现数值方面的问题，这样整个 kernelize 的方式会更加通畅。当然，如果不去限制，kernel 肯定也有自己的写法，只是那种写法可能就会低效一些。所以为了保证一个高效的实现，Kimi Delta Attention 采用了在一定的 tile chunk 内控制它最大系数——就是衰减程度——的方式。Kimi Delta Attention 大概就是这样。其实 Delta Rule 这条线也很简单：第一，KDA 把 GDN 这样的一个计算方式扩展了它的计算能力；而为了扩展计算能力，会带来一些额外的 infra 上的麻烦，然后他们在模型的表达范围内采取了一些限制[?]，让它满足 kernelize 的方式，最后得到了 Kimi K3 采用的形式。

下一个环节是 Gated MLA。顾名思义，它就是把两块的模型结合了起来。MLA 可能大家都已经很熟悉了，是 DeepSeek-V2 刚开始去用的，主要目的是减少一些 KV cache 的开销。MLA 的这个配置后面主要是被 DeepSeek-V3 和 Kimi K2 采用；当然 DeepSeek-V4 没有用，但 Kimi K2 也用了。Kimi 的同学们认为，MLA 在全注意力这样的 scope 内部，至少还是一个可以接受的形式，或者说没有必要去改动的形式，所以 K3 还是采用了跟 K2 一样的形式，然后在这个 MLA 的基础上增加了一个 Gated 的操作。Gated Attention 最早应该是 Qwen 团队刚开始去用的；从 Qwen 这个团队论文的标题也可以看出 Gated Attention 当时主要解决的是哪些问题，比如说 non-linearity——Gated Attention 可以带来额外的计算强度，然后 sparsity 和 Attention-Sink-Free——这个东西可能并不是那么显然，这个就得具体看它的 paper。但是 whatever，我觉得 Gated Attention 大家最 buy-in 的一个点就是它的训练稳定性，而且这个训练稳定性是一个被广泛验证过的形式。大家可以从 Qwen 的训练图里去看到，对于一个 pre-train 的 run 而言，我们还是希望它越稳越好：从模型能力上，如果不是最优，也没有关系，因为模型能力其实最主要的因素是模型的参数大小，所以好一点、差一点都不如稳定性要重要——如果稳定性不好的话，它会带来很多麻烦的问题，甚至比较大的问题就是你整个 run 训崩了，前面整个的 checkpoint 都废掉了，这个我觉得对于任何团队而言都是不可以接受的。所以如果说一个方法能比较有效地提升模型的稳定性，这还是一个大家比较愿意采用的技术。然后 Qwen 的 Gated Attention——Qwen3 应该是没有用，后来的 Qwen3-Next，包括 Qwen3.5、3.6 应该都采用了这样的一个架构。虽然它会带来一定的额外计算开销，但是它对模型的稳定性会带来特别大的好处。这个是对之前 Qwen 团队的一个工作——Qwen 是在 GQA 上引入的嘛。但这个设计其实无论是跟 GQA 或者说 MLA，本身都是一个正交的设计方式，所以 Kimi K3 把这块做了一个结合：把 Gated Attention 的这样一种稳定性的方式引入到 MLA 当中，这样它本身不会破坏 MLA 本身的推理性质，同时可以提升模型的一个训练稳定性。

这里张小珺插话：为什么 V4 没有再继续沿用 MLA 了呀？你觉得 MLA 在未来还会成为共识吗？因为我记得罗福莉之前跟我说过，她觉得在 Agent 时代 MLA 应该会被替代。孙宇涛回答说，因为他们有别的东西了嘛。我们先从技术上讲，MLA 本身就是 MQA 的一个等价的形式，所以 MLA 其实本质上并没有带来新的东西，它只是一条更好的隧道[?]。大家其实没有发现的一点是，如果大家想把 MLA 用好的话，想达到相同的计算效果，其实要增加更多的投影的计算去弥补这方面的损失。所以我个人认为，MLA 主要拿到的收益，其实可以被更好的 GQA 参数设计基本上拿到绝大多数。那为什么 DeepSeek 没有继续沿用 MLA？因为 DeepSeek-V4 后面主要推 sparse 嘛，sparse 跟 MLA 其实不是一个百分之百兼容的东西，尤其是在 prefill 阶段；而且他们其实是用了 MLA 等价的 MQA 形式，因为从数学上来讲，MLA 本质上就是一个大号的 MQA，所以 DeepSeek V4 用的是一个大号的 MQA，我觉得本质上区别不是很大。罗福莉当时是在 MiMo-V2-Flash[?] 里面采取的是 MTP。她觉得 MLA 对于 Chat 来说是一个优秀的模型结构，但是她觉得不那么适合 agent 的方式：MLA 在设计之初，为了达到很好的访存和计算的比例，在当时的 H 系列芯片上实现既不浪费算力、又打破访存瓶颈，是按这个架构设计的，然后就发现计算冗余的实在太多了，她觉得 MTP 能够更有效地利用起来。这个其实是一个比较 reasonable 的点，就是 MLA 在推理阶段的计算其实是大大浪费掉的，它的计算是远大于它实际的降幅[?]能力的，所以对于计算而言，这块是有一定的浪费。罗福莉主要的讨论点就是，这种计算模式它跟 MTP 的收益不是正交的，甚至它可能是互相冲突的——因为 MTP 本质上就是用更多的 token 同时去计算，然后在 memory-bound 的这样一个条件下，主要逐渐往提高 compute-bound 的方向去推，所以对于 MLA 和 MTP 的组合，加速比会大大减小。我觉得它从来也没有是共识，它只是一个选择。但 K3 在这边起码它选择沿用的是 MLA，我觉得 K3 是 reasonable 的：因为 K2 当时主要是 follow DeepSeek，他们当时的选择是先不做模型架构的创新，先把结果跑出来；然后如果从 K2 到 K3，我觉得从工程或者说组织管理上，能跑的东西就不要动——如果 MLA 不是一个特别大的问题，可能就暂时不会动。但我觉得未来也不一定，我觉得这块是一个比较暂态的状态。当然了，MLA 也不是没有好处，所以我觉得都还好。张小珺再问：所以它是加强了 MLA 的可控性？孙宇涛答：对，Gate 主要是提升 MLA 本身的训练稳定性，这块跟 MLA 是正交的，就是任何 full attention 其实都可以用。

我们现在讲到 2.2 对吧，就是 Attention Residual（AttnRes）。Attention Residual 其实当时还挺火的，但是如果从 attention residual 这样的研究脉络来讲的话，我反而会认为 Hyper-Connections 是一个相当好的工作。这块主要讨论的就是在一个比较深度的模型当中的、深层到浅层的一个连接方式。因为它叫 attention residual，本质上跟 ResNet 其实都有一个比较深刻的连接关系。ResNet 本身解决的就是模型能力在模型参数增长的情况下，至少可以达到一个不退化的效果；包括从稳定性角度，无论从模型稳定性还是模型能力上，ResNet 本质上都会比之前的一些工作有本质性的提升——不过这个大家都很熟悉了。然后大家其实没有注意到的是，ResNet 其实是有两个版本的：一个是 CVPR 的版本，一个是 ECCV 的版本。其实在 ResNet 那个时代，恺明就已经讨论过 Post-LN 和 Pre-LN 和训练稳定性的关系了。而这个其实也可以追溯到 BERT 时代：BERT 时代大家还是会更常用 Post-LN，大家会觉得 Post-LN 的结果可能会稍微好一些；但是在模型逐渐增大的情况下，大家会发现 Post-LN 有梯度消失的问题，或者说有训练不够稳定的问题，所以大家后面就会逐渐采取 Pre-LN 这样的残差连接手段。然后 Attention Residual，之前苏剑林讨论过一样的观点：Attention Residual 绝对不是 Pre-LN 到另外一个 LN 摆放方式的区别——这样的话其实这个风险是很大的，因为一旦你触及了 Post-LN 之前的问题，对整个大的 run 大家肯定是不敢上的。所以 Attention Residual 当时强调的就是，它一定是 Pre-LN 的一个超集——就是它至少是可以退化到 Pre-LN，它严格上是比 Pre-LN 更强的一个结果。这块主要就是简单讨论一下 residual 这条研究线之前大概是怎么来的。

然后 Hyper-Connections，我觉得这个工作是相当有意思的，很早以前是 Seed 团队提出的。其实我觉得无论是 TPSeq[?] 后来做的改进也好，和 C2[?] 也好，本质上其实都是从这篇工作来的。它主要讨论的一个点就是，我们在 Pre-LN 的基础上如何去增加模型残差的容量，从而去提升模型的表达能力。当然，我之前也跟 Hyper-Connections 一作的同学交流过，我说我觉得这个工作本身从技术上还是很好的，但是它一个最大的问题就是它 paper 写得太抽象了，不太容易读。Hyper-Connections 我觉得本质上就可以说一句话：我们在 residual 这个分支上，去用比模型 hidden state 更大的一个容量，来表示这个模型在推理深度上的一个状态。所以说如果我们有更大的容量，它一定是有更好的一个效果的。我觉得 Hyper-Connections 从思想上相当简洁，但是这个 paper 可能形式相对复杂了一点，所以当时这个工作其实并没有出圈，可能只是对大家做架构或者说技术层面的同学去了解的。但是后来这个 mHC 可能就比 HC 本身要火了很多——当然我觉得最重要的原因还是当时这个 mHC 是 DeepSeek 提的，我觉得可能没有别的原因。所以在 Hyper-Connections 之后，大家会尝试去从模型本身的连接方式来提升模型能力。因为从 Hyper-Connections 包括 Hidden Residual[?]，它们一个比较好的点就是对于推理来说基本是免费的：也就是说在模型的 inference 阶段，它其实几乎不会增加任何的推理开销，看起来它就可以拿到更好的一个模型结果。这个其实是大家喜闻乐见的，因为一旦涉及到……

## 领读·Gated MLA 与 Attention Residuals

我们通过更慢的一个实现也好、更慢的模型架构设计也好，去取得模型更好的表现，那这会儿就带来一个自然的隧道[?]：就是我为什么不能去扩更大的 size？这样还简单一些。所以说一切通过更慢的模型实现去提升模型效果的做法，其实都是会被 fully question 的。甚至说对于一些保守的、或者说不是自己提的设计，大家就会愿意去用——对于这种模型设计，它可能在推理阶段是几乎免费的，这样的话大家上的时候没有什么压力，而且它其实和模型参数本身的提升并不冲突[?]。然后 Hyper-Connections 这个维度[?]，其实还有一个比较绕不过的，就是 DenseNet。DenseNet 是一个更早的工作，是黄高老师在 ResNet 之后提出来的，它其实是一种连接方式。DenseNet 和 Attention Residuals 在思想上关系相当密切。只不过 ResNet 的 residual 只是层和层之间的一个连接方式，而 DenseNet 是在深层要去查看所有浅层的状态，然后再把它聚合起来。而且在 DenseNet 时代，因为那个时代其实没有 attention，或者说大家也没有过度重视 attention 本身的能力，所以 DenseNet 里边主要是一个大的 linear，去把之前所有的 hidden state 聚合到一起。到了 attention 时代，DenseNet 那个实现本身是不快的，因为它中间对于连接的处理会带来大量额外的计算。但是大家会发现问题：我们可以把 DenseNet 里边一些比较 heavyweight 的部件变成更 lightweight 的部件，这样就诞生了 Attention Residuals 这样的工作。它最大的优势是相比 DenseNet 一个更 efficient 的架构。我们可以通过一些更深层次的 infra co-design，比如说用 block attention 的方式去解耦掉模型的深度——因为如果只是全注意力的话，上层会跟底下所有层去交互，这其实也是之前一个比较大的问题：模型越深，这块的 overhead 越不合理；而 block attention 在这块做了解耦。所以整体上一方面是 attention 本身的计算比较 lightweight，第二方面是它解耦了深度，最后总地看起来，它其实是一个比较灵巧、但又切实能提升模型能力的组件。这块可以看一些 scaling 的结果：block attention 因为解耦了深度，严格来说表达能力肯定是不如 full Attention Residual 好的，但这里大家 claim 的点是它其实并没有损失太多能力，而且对 baseline 来说是一个比较显著的状态[?]。然后 Attention Residuals 这块主要应该是上一个技术 paper 里讲的，K3 这块应该没有做太多特殊的处理，大概就是这样。

**张小珺**：你刚才讲的这几个，你觉得哪个创新性是最强的？**孙宇涛**：其实我更喜欢 DenseNet 和 Hyper-Connections。为什么？因为 DenseNet 是一个相当早的工作，在那个时代大家考虑连接的问题——我觉得本质上 residual 考虑的问题，DenseNet 其实都考虑到了，只不过当时没有 attention 而已。然后 Hyper-Connections 相当于是把这个东西在 transformer 时代重新带了回来，让大家在连接方式上重新去讨论如何有一个更强的连接方式，从而提升模型的性能。我觉得后面的工作当然会有一些 co-design、或者说模型稳定性的问题，但大的框架其实是之前的工作已经定好的。

**张小珺**：然后 Latent MoE 应该是年初英伟达他们一个团队去提出的。**孙宇涛**：对，我觉得这块一个比较大的好处[?]是：包括大家如果熟悉 DeepSeek-V3 的同学其实都知道，训练 MoE 无论从模型稳定性、训练方式，包括从硬件上，都是很大的挑战，而最大的挑战就是 MoE 的 All-to-All Dispatch——其实在 EP 的情况下它的 overhead 是相当大的。也就是为了解决这个问题，我们不得不引入 DualPipe 这样一个比较高效的通信方式，去降低 All-to-All 的开销。包括其实不同的 All-to-All、不同的 MoE 设计架构方式，不仅影响了模型架构本身，甚至影响了底层不同 infra 的一些设计选型，这个后面会在 infra 那块做更多的讨论。但是 Latent MoE 本质上的东西就在于：我们是否可以把 All-to-All Dispatch 这块的开销减小。因为 All-to-All Dispatch 需要把 hidden state 分发到各个专家卡上，而且这个通信量会随着 expert 激活的数量和模型 hidden state 的大小并行地去增长。Latent MoE 的思想就是：在把通信量减少的同时，去保持模型的表达能力。它的方式就是把 dispatch 的 hidden state 减小——可能减小 2 倍、减少 4 倍这样的量。当然，如果我们直接减小它的 hidden dimension，后面模型 MoE 这部分的参数量可能就要随之增长，去弥补 latent dimension 减小带来的参数量损失，这里边就有两种方式：第一种是提升 FFN 的 intermediate dimension，通过提升 FFN 本身的参数量，把之前降的那部分弥补回来；另一种是我们进一步把模型拆碎，用更多的 expert 和更多的激活，来弥补参数量的减少。最后我们可以看下来，当然在英伟达那个 paper 里，它其实结果是更好的。总的来说就是一句话：一个恰当设计的 Latent MoE configuration，其实是可以完全保持 Standard MoE 的结果的。也就是说，我们可以在模型能力完全相同、甚至还能好一点的 context 底下，去减小模型的 latent、减少模型的通信开销。而且通信开销在训练和推理中是不一样的：训练因为我们主要优化的是 throughput，可以用一些 overlap 的手段把通信这部分弥补掉；对于 inference latency 来讲，尽管我们可以用一些手段去掩盖通信开销，但这个时间是避免不了的，因为它整体在 critical path 上。所以从模型的 efficiency 上来讲，推理的收益其实比训练的收益要大，当然训练也有一定的收益。所以说如果 Latent MoE 不是一个 trade-off——就是我们不需要去三分号[?]牺牲模型的表达能力来降低通信的话——它其实还是一个 free lunch 或者类似 free lunch 的结构。所以 Kimi K3 其实是 follow 了这样一个结构。

当然，在 Latent MoE 之上还有一些比较细节的改进。针对这样的改进，我们可以讨论一个比较经典的问题，说起来也很简单，就是两个矩阵连乘——这是非常非常基本的单元。两个矩阵连乘其实在模型表达能力上是最优的，因为两个矩阵连乘严格来说是可以合并成一个的；但优化性质上其实并不是这样：两个矩阵连乘经常会出现模型训练不稳定的问题。所以两个矩阵连乘一般中间都会搭配一些稳定性的手段——本质上也是先做一个 low projection 的投影，然后再把它打回来，它本质上也是两个 linear 连乘的方式，中间一般会采取一个 normalization 把中间的 hidden state 控制住，从而提升模型整体训练的稳定性。所以就是 TL;DR，很简单：一般来说，在模型架构的设计当中，如果你不得不把两个矩阵连乘拆开来写、而不是合并到一起的话，中间一定要加一个类似 normalization 的手段。这个思想，一个是 MLA 里有个设计，然后这块的 Latent MoE 其实也是类似的道理。归根结底，Latent MoE 是先把这个模型的 hidden state 通过一个 linear projection 压到一个低维的状态，然后在这个 linear projection 的基础上进行后面的一些计算。当然对 FFN 来说，第一个计算也是一个 linear projection，所以这块就会出现两个 linear projection 连乘的情况，所以我们需要一个 RMSNorm 来控制它。

然后下边就是 SiTU-GLU，这个设计大家看起来可能没有那么直观，其实也跟之前的一些设计有关系。大家会发现，对于大模型训练来说，FFN 这块 MLP 中间的 hidden state 是一个特别容易 activation explode 的状态；而且这个东西一个是跟优化器有关，另一个是跟模型精度有关——在模型精度更低的情况下，中间的 hidden state 更容易出现 outlier。为了解决这个问题，GPT-OSS 其实刚开始采用了一个特别简单的做法：就是把最简单的 SwiGLU、就是没有 bounded 的那块，直接通过一个 clip 控制——比如说设一个 clip 的值，比如 5 到 10，把它 clip 到这样一个程度，这样就可以从数学上比较严格地把它的上限控制住。然后 clip 是一个比较粗暴的做法，你如果把这个 hard clip 变成 soft clip，你就会比较自然地得到 tanh 这样的一个算子，因为 tanh 它 somehow 就是一个 soft clip：如果你指定一个下界、指定一个上界，它可以用一个比较平滑的方式让你逼近你希望设定的上界。所以从这个角度上来讲，我就可以把它理解为一个 clip 的升级版；但这个升级版具体在模型表达能力上有多大影响，我觉得是另一回事，而且这个肯定是需要具体的实验去证明的。但 whatever，我觉得 soft clip 还是一个比较安全的做法。从 SwiGLU 开始，首先把一个比较自由的 linear projection 改成了一个 tanh bounded 的形式；另一块就是 SwiGLU，因为 SwiGLU 它前面就是一个 linear 的结果，然后再加一个 SwiGLU 的结果，这个 Swish 我们又可以拆成 sigmoid 和一个 linear projection，当然这块它是一个共享位置[?]的状态。所以 SiTU-GLU 相当于把所有中间可能出现 unbounded 的环节，都通过 tanh 的上下界放缩框住，这样就可以给整个 MLP 中间的结果一个严格的数学上界，从而保持模型的训练稳定性。当然这块我觉得可能还有一些别的 concern：比如说我们发现其实如果用 Muon 的话，其实是会更容易出现 outlier 的，你控制中间的结果值，总不是一个比较错的现象[?]。当然如果我说 Muon 更容易 outlier，苏建林一定会反对，他肯定会说：对于任何优化器来说，都一定会出现 outlier，因为你从模型架构上是控制不了的。

**张小珺**：所以说如果想直接从模型架构下手，怎么苏建林跟你观点不一样？**孙宇涛**：这个他没有说，但我猜到他会这么说。因为这块其实之前在 Kimi K2 的那个 MuonClip 里也做过类似的讨论：大家如果之前对 Kimi K2 或者 Moonlight 有印象的话，当时就会说，就是因为用了 Muon 优化器，所以 QK logits 更容易去爆炸，所以 Moonlight 采用了一种对 QK 比较特化的处理方式，来压制模型的 outlier。然后在那个时间点大家就问：为什么我们之前用 Adam 训练的时候不翘架[?]、没这个东西，之前的 QK logits 都很稳、不需要额外的处理，但是 Muon 为什么要特殊处理？当然苏建林就是这么回复的：他说从严格来说，Adam 也不是完全稳定的，当时 DeepSeek-V3 可能 somehow 也有一些不稳定的现象，当然这并没有影响模型最终的结果。他当时对 MuonClip 的观点是：如果说在 Muon 训练[?]里有可能出现的 outlier 现象，它严格来说就是容易出现的，只不过可能是出现的早晚问题。所以说为了严格地限制模型的行为，还是从模型架构本身去做限制，是一个根本性的方案，他当然是这样一个观点。所以这块他肯定也是相同的观点：我们为什么不直接在 architecture 上做一些改变，把整体的 bound 都限制住就完事了，也不需要去纠结更复杂的优化细节？其实我觉得是一个道理，所以我觉得他应该还会这么说。**张小珺**：Muon 是对 K2 的一个沿用，对吧？**孙宇涛**：对对对。

## 领读·Stable LatentMoE SiTU-GLU 与 Muon

这块相比 K2 没有做太多的改进。Muon 当时比较严重的问题就是它其实控制不住——对，控制不住，中间还会出现 activation outlier。更早的一个版本是个更粗放的方案，当时连 VDK 都没有加，所以 Moonlight 做的比较率先的事情，就是把 VDK 这样的一个因素首先引入到比较大规模的模型训练里，这样的话在更长的 run 里边是可以保持住的。另外在 K2 的时候，就是在这个 VDK 的 Muon 技术上额外搞了一个 QK-Clip 的放缩方式，这两个加起来，就是 Kimi 团队在优化器上一个比较完整的工作。当然现在大家用 Muon 的方式比较多了，但是大家解决的方式不太一样：比如说你用 MLA，就没有办法去加 QK-norm——QK-norm 是可以严格限制 QK 这块的边界的——所以为了适配 MLA 和 Muon 的结合，当时 Kimi K2 引入了 QK-Clip 这样的操作。当然大家可以注意到，比如说 DeepSeek-V4，包括 StepFun 那些应该都是用了 Muon，然后在 Muon 的基础上，因为他们用的又是 GQA、没有用 MLA，所以直接用 QK-norm，本质上是一个更简单的办法，就是尝试去控制 Muon 带来的额外 outlier。这个 outlier 在 QK 那块更容易出现，但也一定会在 MLP 这块出现，相当于采取了不同的方式：QK 那块通过 clip 也好、normalization 也好把它限制住，底下 MLP 这块会用一些更 lightweight 的手段，Kimi 现在就是通过设计的一个激活函数把它限制住，大概就是这样一个思想。

然后 Quantile Balancing 的话，这个没有发什么论文，是苏剑林在他自己的博客里去讲的。它主要是可以 follow 到之前的 loss-free routing 的方式：主要的控制方法就是只通过一个 bias，而不是通过一个偏整体的 loss 控制方式，来去解决模型 expert 负载均衡的问题。当时 loss-free 大家比较奇怪的一个问题，就是这个 bias 的变量直接决定了每个 token 选哪些 expert，但这个更新方式 somehow 是有些 ad hoc 的，就是他采取了一个比较启发式的更新方案来做 bias 的更新。一个问题就是它其实没有一个比较严格的数学收敛标准；另一个就是它和主模型的更新，给大家一个感觉是可能没有那么耦合，但这个形式本身还是可以 work 的，整体 work 得还不错。在整体 work 不错的情况下，当时 loss-free 其实有几个问题可能是没有完全解决的。最主要的问题就是，在使用 loss-free 的时候，大家可能会采取把模型最底下几层——一层或者三层——的 MoE 去掉的方案，主要原因就在于 loss-free 这样的控制方案对于底层的模型来说 work 得不是很好。正是因为 loss-free 整体没有做整体的一个 coding[?]，所以它可能会采取一些别的方式来弥补模型在大规模训练中碰到的问题。而 Quantile Balancing 主要是尝试用一个更 principled 的思想，来解决模型 MoE 负载稳定性这样的问题。loss-free 的 update 方式肯定是经过大量调整之后得到的一个 work 还不错的方案，所以它本质上也很简单：如果某个专家激活得多了，就把 bias 往下砍一点；如果激活得少了，就往上加一点。之前的 loss-free 是一个比较启发式的方案去做，而 Kimi 团队用更 principled 的方案——我们能不能直接通过一个线性规划的方式直接推导出来，这个 bias 应该长什么样？答案就是可以推出来，而且推出来的具体方式也跟之前的 expert choice 有一定的关系。

然后 Quantile Balancing 经过一系列推导，最后得到一个一步的形式：比如说对于一个 step 内部的一个整体的激活，我们可以求一个 bias，而这个 bias 本身就是一个让模型可以负载均衡的方案。他博客里又写到了，为了去避免信息泄露——也就是我们不能让任意一个 token 获得其他 token 的信息——所以这个 bias 并不会在当前 step 使用，而是会在下一步去使用，这个是 Quantile Balancing 中间的一个细节。苏剑林博客里主要提到的优点，首先是他不需要调参数：loss-free 是有一个类似的 learning rate 的更新方式的，这样的话 QB 少了一个参数，整体看起来会更加 principled 一些；第二个优点就是，它对于负载均衡 balance 这样的能力，其实是一个更优的能力。他这块的博客里就会贴出一个图：对于第一层而言——因为我刚刚也提到，为了兼容 loss-free balance，之前大家会把前几层搞成 dense、不用 MoE 这样的方法去把这个东西规避掉——如果是 QB 这种方式的话，其实就没有必要去规避这样的一个问题了，它其实就可以直接把第一层变得 balance。这个其实可以发现，前底层用 dense 并不是一个 ground truth 上一定要这么去做的方式，而是它在 loss-free 这样的 context 底下不得不采用的方式。如果你不采用 loss-free，直接采用加辅助 loss 的方案——比如说前面 MoE 的工作其实就是采用直接求 loss 的方案——对第一层也会没有问题。所以这块的话，QB 主要就是可以处理到之前 loss-free 一些比较失效的情况。当然他博客里也提到，如果本来 s3sjd[?] 就比较 work 的情况下，这个 QB 也是比较 work 的；而且他博客里也可以证明，比较正常的情况其实可以推出来说，这个 QB 如果我们不采用直接去均衡、去采用一些梯度更新的方案的话，其实是可以和 loss-free 做到一个相当等价的数学形式的。

然后这块其实还有一个细节，是之前的那个博客里没有去提及的。简单来说，就是为了在整个 batch 上——因为现在大模型训练一个 batch 会特别大，比如说 4M（token）可能都会比较小，可能到几十 M 这样的量级——QB 需要在几十 M 的 token 之间（求分位数）。如果对于一个精确的计算，我们需要把所有 token 的激活情况都存下来，这个其实是相当 heavy 的，甚至在工程上是不可能的。当时博客里提出的方案是：每个 GPU 都去做一个 local 的分位数计算，然后再把不同 GPU 的分位数——也不一定是不同 GPU 了，反正就是得把一个大的 batch 切碎，在一个小的 batch 里去求分位数——这个分位数最后再做一个 pooling。然后 QB 在 K3 这个 paper 里其实有一些不太一样的变化：它并不是按 token 去切 chunk 的——当然也有可能是我理解错——它其实是对模型的值域切一个 chunk。也就是说，比如说对于 sigmoid 的计算，它一定是在 0 到 1 之间的，所以我们就可以在 0 到 1、或者说 -1 到 1 这样的趋向范围内切成 n 个桶，然后在桶里边去进行 histogram 的一个统计。这样一个统计值的好处，就是它可以是一个常数范围、常数级的存储大小就可以做的一个计算，而且它的计算代价会比朴素的实现要高效很多，也可以比较好地去处理在大规模 DeepEP 的分布式架构底下的扩展，是一个比较容易扩展的状态。这个其实是相当于 K3 后来放出来之前、在博客里没有去详细讨论的一个技术，对 QB 来说是一个比较必要的实现方式。归根结底就是，naive 的实现基本上是不可行的，所以必须用一些工程上可行的方式，去把它比较精确地解出来。

然后到 2.4 了，那就是 vision 这块，其实没啥好处的。它主要讨论的一个点，就是是否有必要用一个已有的 vision encoder，去做这个 ViT vision encoder 的一个初始化。用已有的 ViT 的话——比如用 SigLIP 2 这样比较大规模训练的一个 vision encoder——它的好处就是它收敛[?]得会比较快。但是 Kimi K3 中间讨论的一个问题就是，如果直接用这个 SigLIP 初始化的话，它的模型的不稳定性会比直接从头初始化[?]来得大。也不一定是模型不稳定性，因为不稳定是一个比较相对、甚至不是一个严格被定义的东西，只是大家一般会去看 gradient norm 这样的一个分布，中间有一些东西是大家比较 concern 的，比如说它的尖刺多不多，甚至说它本身的 norm 大不大。这个团队会发现，如果说我们直接 from scratch 训练，可能会多用一些算力，但是至少第一，它最后的结果是不会有损的：如果我们经过恰当[?]的训练，它不会带来更差的结果，甚至可能会带来差不多甚至更好的结果；所以第二个它主要 claim 的点，就是原生[?]会带来一个更好的兼容性，那就会体现在 gradient norm 会更加稳定。我觉得其实可能有一个类似的观察，就是 SigLIP 它其实是用 Adam 来训练的，之前大家其实也讨论过一个比较相关的话题：用 Adam 训练的模型反过来用 Muon 去训练、用 Muon 训练的模型是否可以再用 Adam 去训[?]。当然最后的结论就是，肯定是原生的方式最好；用别的方式的话，如果想达到原有水平[?]，可能就得做一些处理，或者说它是有一些限制的。所以可能对 Kimi K3 而言，他们是希望去采用一个全 Muon 的优化方式，这样对模型整体训练的稳定性也好、它的兼容性也好，是一个更优的状态。

说到这里，我们等会儿去讲一下最早那个：它用的是纯线性注意力机制，没有用任何的 sparse attention——就是线性注意力、全注意力和 sparse attention，你可以对应（报告的）3.1 和 3.2。对，就是为什么不用 sparse attention？用了会有什么好处，或者说会有什么问题？这个其实一方面是跟模型架构有关，另一方面其实也跟每一代 GPU 硬件的 feature 有关。比如说 DeepSeek-V3.2 那种 DeepSeek Sparse Attention——一个是 3.2 用的，一个是 GLM-5 也用了 DeepSeek Sparse Attention 这样一个架构——DeepSeek sparse 其实到最后在 decode 里边的加速是特别特别小的，原因就在于 sparse 求 index 这一步是相当昂贵的，而且在 Blackwell 的硬件情况下，越先进的硬件这个 overhead 越大，甚至其实在 decode 当中，这种 sparse attention 的方案跟 full attention 并不会带来一个显著的加速。为了解决这个问题，当时 GLM 团队做了一个工作叫 index cache：它当时的做法就是把求解 index——就是求解哪一部分、哪些 token 需要算 attention——这样的一个操作，把不同层之间共享起来，比如说每四层、每八层做一个共享。只要用这样的方法，它其实才可以比较有效地减小 sparse 本身带来的开销；只有 sparse attention 本身的开销足够小的情况下，其实才能带来一些比较可观的算法上的收益。sparse attention 这块其实我们也做了一些相关的工作，大概是一个类似的结论，当然我们做得更极端：我们在 UQ[?] 的架构上直接做 elaborate[?] sparse attention 的话，因为我们之前的 KV cache 是一次性（once）的，所以我们当时采取的方式就是把 sparse index 这一步也做成一次性的，也就是说把每层的 index 直接分摊到所有层上，这样的话其实那个开销就会特别特别小，这样我们才能吃到 sparse attention 本身的一个计算收益。然后我们再回到 Kimi K3，为什么它不去采用？第一个就是我们认为，每层都用 sparse attention 这样一个比较简易的方案，其实在 Blackwell 上它的收益是特别特别小的。为了解决这个问题，无论是 index cache 的解法还是我们的解法，其实结论都一样，就是我们需要把多层的 sparse 的结果来去跨层进行复用。跨层比较简单的方式就是相邻的层去跨，但相邻的层去跨层的话，对于 hybrid attention——就是对于线性注意力和全注意力 interleave 的方式——其实并不是一个显然的（方案），因为对于这种 hybrid attention，不同的 full attention 它并不是挨着的，每个 full attention 中间其实隔了很多个线性注意力的（层）。所以在隔很多层线性注意力的情况下，这种 index 的 share 是否有效、加速比是否足够高，这个其实是相当 questionable 的。其实还有个问题，就是 sparse attention 它基本上是没有办法进行 from scratch 训练[?]的，sparse attention 大家现在一般采用的都是 post-train、从 full attention 进行转化的一个方式。不排除 Kimi K3 可能未来会把已有的 full attention 的部分来进行 sparse attention 转化，当然如果他们用了 MLA 的话，这个会更难一些。

## 领读·Native Vision 与 Pre-Training（WSD RNoPE）

所以我觉得主要就两个原因：一个是想拿到实际加速比，这对 hybrid attention 来说其实是一个 non-trivial 的事情，想拿到实际加速比可能需要做更多的工作；第二个是它跟 pre-train 并不是一个比较兼容的状态。所以说这个其实留一个接口，之后再做也行。张小珺：我刚才讲的这些——不管是架构创新、训练还是推理工程——你觉得中间有哪些 tradeoff？我觉得 hybrid attention 主要的 tradeoff，就是要去调线性注意力和全注意力的比例：线性注意力比例越大，加速比肯定越高；但如果想达到一个偏无损的加速状态、同时又想获得加速，3:1 在实验上就是一个比较 work 的方案，这块就是主要的一个 tradeoff。sparse 严格来说大概率不会带来更强的表达能力，它其实跟 hybrid 架构是另一条线的事——只不过如果你坚持不用 hybrid，那你可能就不得不采取一些别的方案。

张小珺：我听到这里的感受是，现在的模型训练好像没有一个巨大的所谓范式创新，但它把之前很多的工作都融合起来，然后再寻找一个可能的更优解，不知道这种感受对不对？对，我觉得其实问题不大，而且不完全是技术的原因。为什么呢？因为大家现在都叫 Transformer，但什么时候还是 Transformer，其实是没办法清晰定义的。哲学上还有一个对应的概念，就是忒修斯之船：2017 年这个船刚开始行驶的时候，是 Transformer；但这个船刚开始是怎么拼起来的？它是 attention 加 residual 这些东西拼起来的，包括 stack layer 这种方式，在 Transformer 之前其实也并不是全新的概念。所以这个船刚建起来的时候，我们认为 Transformer 是一个 milestone。但这个船已经行驶了八年九年了，在慢慢行驶的过程中，我们会把某些部分换掉。其实我们现在看，到 2026 年，它跟 Transformer 的相似度已经是很低了，你是不是还把这个东西叫做 Transformer？当然这是哲学上的问题，但从现在来看，大家还是会叫；不过我觉得如果历史的走向有些不同的变化，可能也就不叫了。

张小珺：我们上面讲的这些，你觉得它总体来说是一个什么样的工作？我觉得这个东西很难定义，它是一个偏综合性的工作。一般大家会把比较有创意性的单点突破专门拿出来讨论，之前也有过专门讨论。中间其实比较大的就几点：第一个是注意力怎么设计，这是一个点；第二个是 MoE 这块有没有一些更好的设计；第三个是优化器；第四个可能就是中间的一些连接方式。这些你放到 ResNet 时代，单拿出来可能就是一个架构了。我觉得在 ResNet 时代肯定是这样的，但在 Transformer 时代可能并不是——你把这个东西综合起来，最后再把它跑出来，它才有意义。因为之前大家做架构，比如说在 ImageNet 上跑，跑得足够高了，其实就是一个 milestone；但在这个时代你想把实际的东西跑出来，要做的东西就特别特别多：你得做 scaling 的验证，把各个工程的东西搞定，把 data 搞定，然后你把这个 paper 或者说把这个架构做出来，大家才会 buy in。当然我觉得从研究方面，我 personally 是不会太去关注的，因为我觉得架构的验证是有一个严格的标准的，或者说不需要把这些东西凑在一起；但是从非技术角度看，它现在就是这样一个状态。

张小珺：架构方面相比于 K2 至少是不一样的，你觉得为什么 K2 到 K3 变化这么大？我觉得是个战略的问题。其实 K2 在那个时间点他们也可以不一样，只不过当时主要的重心是把模型跑出来，所以 K2 到 K3 这个中间，他们有更多的时间去做了很多的优化调整。K2 本身是做得不错的，包括 K2 当时大家主要考虑的问题，比如说怎么把 MoE 训出来、怎么有效地把模型 scale 上去——因为 K2 就是 one trillion，当时 one trillion 比之前的比如 DeepSeek V3 还是要大一些的，在那个时间应该也是一个相当大的模型。所以当时他们解决的是这样的问题：先把 base model 整体的一个 pipeline 做稳，然后在稳的基础上，K3 再去追求一些更精益求精的优化。至于从这些亮点工作反推团队的状态：如果只是 Kimi 的架构团队或者预训练团队，我觉得没什么变化，一直就是一个样；但对于整体公司而言，还是有战略性侧重的。侧重点就是 K2 当时 Kimi 团队主要的诉求还是把 base model 做稳，先把能力做出来、先不去考虑更高的 efficiency 也好、更精益求精的创新也好。当然这些团队内部是一直在做的，只不过看什么时候亮出来——研究工作是一个更长期的工作，可能要看放在哪个模型里跟它一起结合。

接下来是预训练和后训练的部分。post-training 是一个偏工程或者说偏具体场景的东西，报告里也没有写太多，这块可能不会讲太多；pre-training 和 post-training 的话，我觉得主要是一些经验性或者说一些 know-how 的东西，主要的创新可能是前面多一些，中间会有一些比较有意思、可以讨论的点，我会专门拿出来讨论。然后我们就一个一个来。Scaling law 的话，我觉得一个比较值得讨论的点，就是用什么样的 learning rate 策略。这个其实最开始就是 MiniCPM 当时那个 paper 提出的 WSD，MiniCPM 之后，我觉得几乎所有团队都在用 WSD 这样一个方案。我们可以去学习 MiniCPM 当时是怎么考虑这个问题的。简单来说，WSD 考虑的一个问题就是：我们如何能把 data schedule 和 learning rate schedule 结合起来。MiniCPM 刚开始讨论的问题，就是 WSD 和 cosine decay 是可以取得一个比较相近的结果——比如我们从一个更高的学习率到一个更低的学习率，中间怎么去调配，对最后的结果其实影响没有那么大。所以在这种情况下，MiniCPM 这个工作的看法就是：中间具体 decay 的方式对结果影响不是特别大。既然具体 decay 的方式对最后的结果影响没有那么大，这块我们就可以跟 data pipeline 做一些联动的方案。因为在实际训练中我们还是会发现，包括在这个图里可以看到，在 decay 阶段，模型 loss 的衰减速度，比大学习率稳步去跑时 loss 的下降速度要大很多。所以之前大家会认为 cool down 这个阶段其实是模型学习最快的一个阶段。MiniCPM 当时采用的策略就是：既然 cool down 这个阶段是模型学习最快的状态，那我们为什么不把更多更好的数据放在 cool down 这个阶段来训练？这样可能会比所有 data 均匀分布、learning rate schedule 也均匀分布，取得一个更好的效果。这就是当时 MiniCPM 包括 WSD 提出的一个背景。我觉得这个还是挺有意思的：一方面它讨论了一个 non-trivial 的问题，就是为什么我们要采取不同的 learning rate decay 的方式——一个是为什么要这么去做，另一个是 decay 的不同阶段具体承担什么样的 role；然后利用不同 learning rate decay 阶段的行为，跟 data 的具体策略来结合，这样最后可以取得一个更好的结果。

然后 Kimi K3 这块，其实他们讨论了一个不太一样的事情，就是他们为什么不去用 WSD，这个在 WSD 之后的一些 paper 里也是讨论到的。因为 WSD 除了可以用更好的 data schedule，还有一个额外的好处：前面的 learning rate 其实是不变化的，既然它不去变化，它跟你整体要训练的 FLOPs 和 token 量就是无关的；因为无关，也就是说我们可以在模型训练的过程中更自由地选取最后实际的 config。比如说我们刚开始可能预定要跑某个实际 token 量，但如果跑到中间，训练策略改变了、或者公司的策略改变了、或者要更早发版或更晚发版，WSD 这样一个方案我们就可以更自由地在中间进行切换，而不用在刚开始就把整个模型要训的 token 量定死。但它带来的一个没有讨论的问题是：我们虽然可以任意地选择实际要跑的 token 数，你实际的 learning rate 是跟你要跑的 token 数有关系的。比如说把 6e-4 作为一个比较稳定的 schedule，你跑 10T 可能 6e-4 是最优的，你跑 20T 可能就是 3e-4 是最优的。所以从最优的角度考虑，任意去扩展 token 数，可能并没有大家想的那么有效。这块 Kimi K3 的 paper 其实就讨论这个问题：WSD 实际 schedule 调节的难度其实和 VTK[?] 是一样的，而且它并不一定好去调整；而且任意去选取最后训练的 token 量这个事情，也不一定只有 WSD 才能做到，我们用别的方式也是可以做到的。基于这些原因，他们其实可以选择一个更简单的方案，cosine decay 的方案就是更好调：它只有两个变量，一个就是你要跑多少 token，一个就是你的 maximal learning rate 具体设多少；但如果 WSD 的话，其实就会多一个变量，就是你要 decay 的比例具体是多少。所以从调参的角度来讲，cosine decay 是一个更容易去调参的方案。所以他们在 paper 里就写到，因为发现 cosine decay 能更好地找到一个 hyperparameter setting，他们最后采取的也可以算是一个比较经典的 learning rate decay 的方式——而且这个在大家都用 WSD 的情况下，是一个不太一样的 setting，是一个不太一样的 learning rate schedule 的策略。另外，Kimi 团队也对比了从 K2 到 K3 整体的 scaling efficiency。首先 K3 比 K2 大了很多，总参数从 1T 左右到了 2.8T，大了不到三倍；然后激活量是从 32.6B 到 104B，其实是比三倍要更多的。所以从模型参数上，毫无疑问它是比 Kimi K2 强很多的一个模型。最后他们团队给出了一个 scaling law 的结果：K3 比 K2 最后在 scaling efficiency 上是 2.5 倍这样一个量级。不过对于一个简单的 dense model，它的 scaling efficiency 本来就是一个比较经典讨论的问题，之前很多 OpenAI 的 scaling law、Chinchilla 的 scaling law，包括一些比较新的 scaling law 其实都讨论过这样的问题。当然这块比较值得注意的一点，是大家其实也问过 Kimi K2 到 K3 这样的 scaling behavior 是不是固定 data 的，我记得他们的回答是应该不是，paper 里应该没有直接写是不是。当然也可以理解，K3 和 K2 用的 data 肯定不可能是一样的，所以我觉得这块大概的意思应该是：有一个不一样的 data recipe。这个整体的 scaling efficiency 其实已经是综合了模型架构、综合了 training recipe，然后再叠加上模型的数据测量[?]之后总的一个结果，总的结果作为一个大的综合的结果。

## 领读·Post-Training（RL 与多教师蒸馏）

……是比 K2 要高了很多的。接下来是长上下文。Kimi K3 是一个原生支持 1M 长上下文的模型，这块比较有意思的点就是位置编码如何选取。从最开始比较传统的 Transformer 架构来说，大家都会用 RoPE 来做位置编码，但用 RoPE 的话，在长上下文扩展的时候有个问题：RoPE 有一个具体的参数是需要做调整的，如果不做调整、直接拿 RoPE 去扩长上下文，就会显得没有那么有效——这是 RoPE 时代大家一个经典的做法。当然，如果你还是用全注意力，或者说你不引入线性注意力，这个策略不会有太大改变，也就是说你还是得在不同的长度 setting 下去调不同的 RoPE 参数。但这个事情在混合模型里是可以改变的，最早是 Cohere 团队的一个工作，主要讲了这样一个点，他们的结论也很简单：因为 Hybrid Attention 的排布方式，对于 Linear Attention 来说它已经引入了位置信息——无论你用 RoPE 也好、gated sliding window 也好、Linear Attention 也好，在线性注意力这样的一个阶段，其实位置信息已经被引入了。所以说在 Hybrid Attention 的 setting 下，如果我们可以把 Full Attention 从 RoPE 改成 NoPE，也就是在全注意力的情况下把位置编码去掉，一个是可以带来更好的模型表现，第二个是它在长上下文上更容易扩展——也就是说 NoPE 在模型扩展的情况下，不需要调整任何模型架构的参数，就可以达到长上下文的效果。这个效果无疑是很优雅的，因为我们会觉得模型架构的参数选择，当然是跟具体长度没有关系的，也没有任何理论去支持我们为什么要在不同的长度 recipe 下采取不一样的参数，而这种架构就可以有效地避免这一点。我是比较早看到的，可能看到第二天就去复现了一下——当时看到就觉得特别有道理，复现了也很 work，我当时就觉得这肯定是在混合注意力里边比较好的一个方式。我在会议里还审到了一篇文章，当时直接给了一个 strong accept。我感觉我这几年可能也都没有给过几个 strong accept，因为我觉得这确实是一个很有效、也是一个很优雅的解决方案。

然后这里也可以讨论一个大家之前理解错误的问题：RoPE 本质上带来的是 recency bias，RoPE 它 work 最有效的点，是它对 short context 的建模能力特别有效，但它其实对长文来说是没有帮助的，甚至有负面影响。有一些观点会认为长文表现是 RoPE 引入的，这个其实是错误的——RoPE 并不带来任何长文能力，它甚至是损害长文能力的。所以说 Kimi K3 会把长上下文里 Full Attention 这块的 RoPE 直接下掉，下掉之后，你直接测外推都会好很多；如果用 RoPE 的话，你扩长度需要调参数，而不用调参数，它的外推效果也很好，长上下文的效果也没有任何问题，甚至还要更好。这其实是在混合注意力的 context 下一个相当优美的解决方案，所以 Kimi K3 也用了这样的一个解决方案。

然后 Post-training。首先其实可以讨论的一个问题就是，低精度训练应该在什么阶段去引入，这个大家采取的策略是不太一样的：比如说 DeepSeek-V3，他们是一开始就用 FP8 来训练的；DeepSeek-V4 直接用 W4A8 来做预训练；但 Kimi 这块采取的策略不太一样，他们是首先用高精度去训练，然后在 SFT 阶段再把低精度的 QAT 引入进来。这样至少有两点值得讨论。第一个就是从项目而言——抛开技术角度，从整个项目的管理而言——大规模的训练采取更高精度，肯定是一个更保险的方案，对不对？因为它无论如何也不会错，而且更大规模的训练，是很难提前被充分验证得特别精确的，这是从项目管理角度的一个优势。第二个就是从技术角度，我们是否有必要从刚开始就用低精度训练？起码从我的实验[?]而言，应该也是没有必要的，Kimi 可能他们发现也是没有必要的。也就是说，对于低精度训练而言，本身就是从 from scratch 一开始就引入，并不会带来任何模型能力的提升；也就是说 W4A8 你在什么时候引入，只要你过了一定量的训练，它最后的结果可能都差不多。所以在 SFT 阶段引入，是一个更保险、在技术上也不会带来额外损失的方式。RL 这块，因为 Kimi 其实从很早以前就比较重视 RL，从 Kimi K1.5 到 K2.5，他们其实一直在做一些比较持续的创新，在 K3 这边也会比较充分地引入进来，这些其实都是一些比较成熟的方案了，这块就不太展开去讨论了。

然后 4.1.3 的话，这块可以讨论一下 OPD。OPD 刚开始也是董老师团队这边比较早去讨论的一个方式，就是研究院的、微软研究院的。然后 MiniLLM，这个是顾宇轩做的，他去年也是清华特奖，这是他在董老师、在微软研究院这边去做的。其实 OPD 从刚开始大家用起来，和后面大家实际在工程中用的方式不太一样，这个可以讨论一下：OPD 刚开始的 motivation 是什么，后来大家又是怎么做的。当时 OPD 讨论的 context 是蒸馏。蒸馏有两种，一个是黑盒蒸馏——黑盒蒸馏就是大家现在比较采取的方式，拿一个 API，我们不知道模型内部的状态，也拿不到模型推理的 logits，对于外界来说这种模型完全只是一个黑盒，我们只能拿到它的输入和输出；然后白盒蒸馏就是另一种蒸馏方式，我们可以获取到模型本身，也可以任意地拿到模型推理过程中我们想得到的任何状态。在这个场景下，我们如何去做蒸馏、是否可以做到比黑盒蒸馏更好的一个表现——MiniLLM 当时采取的方式就是反其道而行：之前大家采取的方案，是让 Teacher 去生成答案，然后再把这个生成答案用 SFT 的、Forward KD 的方式，把它引入到 Student 的模型里；MiniLLM 是反过来做的，也就是让学生去生成答案，然后让 Teacher 做一个每步的纠正。直观来讲其实就有两种：一个是老师讲课，你把老师讲课的结果学进来；第二个就是你自己去做题，自己去写中间的推理过程，然后老师会把你中间推理哪里做得不对指出来，告诉你怎么去做，这个叫 Reverse KL。后来 Thinking Machine Lab 给它起的另一个名字就叫 on-policy distillation，就是大家会意识到这是一个从蒸馏角度比较有效的方式：我们不直接去学习模型的答案，而是在 Student 自己的推理过程中，让教师模型逐步地去 verify、或者说去纠正学生模型的推理方式。这个范式刚开始其实是为了蒸馏来使用的，无论你是做白盒的一些实验的时候，还是包括从公司的角度——你可以有一个 Pro 的版本，也可以有一个 Flash 的版本，然后 Flash 的版本可以用 OPD 的方式来蒸馏更大的模型的结果，从而获得比 from scratch 训练的 Flash 模型更好的表现，从而在比较便宜的模型这一档获得更强的竞争力。这个是 OPD 刚开始的一个 motivation。

但是其实后来大家更常用的一个方式，不是去做蒸馏，原因在于：如果你想做蒸馏的话，你至少得有一个大模型，然后再去学习、训练一个小模型；但如果说你想去蒸馏，比如说蒸馏一些黑盒的模型，这套方案是完全不可用的。从公司或者说从项目策略上来讲，如果我们不是基于一个大模型来训练一个更快、更小的小模型的话——因为现在大家都不是这个 setting，大家一般都是搞一个旗舰模型然后就完事了，然后把它作为 inference 服务——在这个场景下，就不存在大到小蒸馏的这样的一个行为了。然后大家逐渐采用的蒸馏方式，就是自己蒸馏自己。为什么要自己蒸馏自己呢？我觉得还是两部分，一个是非技术层面的，一个是技术层面的。从非技术层面的原因的话，我觉得这个技术可以让整个 Post-train 团队的管理变得更加简单：Post-train 的合并其实是一个比较 highway[?] 的东西，因为 Post-train 跟 Pre-train 是不一样的——Pre-train 我只要把数据合起来，然后一块去干就完事了；但大家一般做 Post-train 的话，会用一些更复杂或者更先进的一些训练策略，而且这些策略可能会不太容易训那场[?]，如果再直接去做合并的话，可能会有一些难度。所以说基于项目管理策略的话，on-policy distillation 其实就是一个比较好的策略，能把整个 Post-train 团队的管理变得简化一些。然后从技术角度的话，比如说大家训 RL，它一般有不同的策略：比如说你训 Math，它可能就是一个 verifiable reward；然后如果你有些 preference 的一些需求，可能就会有一些 reward model 来去做；如果你再想扩展这个 RL 的别的能力，可能每个能力对于 RL 来说，它的 reward 都是一个独特的 reward。因为 Post-train 一般大家都会专项突破，然后你想把专项模型的不同 reward 直接拿进来一块一锅烩，它其实是比 Pre-train 的难度要大的——也不是说完全不可能，还是有可能的。但是 OPD 的话，它就会变得很简单：我们可以把不同的 reward model、或者说不同的 RL 范式，简化成不同的模型，这个事情就容易很多了。因为对于 RL 策略、或者说对于这个 data，它是一个高度异构的状态，但是对于模型来说，它是一个高度同构的状态——因为现在我们也不会为了不同的任务去专门设计不同的模型架构，如果模型都长这样的话，我们再做一个 Multi-teacher 的合并，这个就会容易很多。不过这个也不是 K3 首先去用的，这个是一个大家现在比较 widely accepted 的做法，我印象应该 MiniLLM……大家现在应该都是这么去做的。

然后 Quantization，刚刚讲过了。Draft Model 这块，其实我觉得还是挺有意思的，这块还是可以额外去有一些延伸的工作，因为我觉得这块 K3 目前优化的还不是很完善。之前小米他们推出了一个能达到 1000 TPS 的方案，那个主要是用了两个技术：一个就是 TileLang 团队做的、可以高度融合不同阶段的一个算子，这样的话其实可以获得比传统 vLLM 推理方式强很多的推理效率——传统那个可能达到三四百 TPS；然后小米这个是基于 TileLang 团队的那一个结果，再加上基于 TileRT 的一个结果，再加上 D-Flash[?] 这个投机推理带来的额外的加速比，最后能带来一个比原模型强很多的推理速度。这个其实主要服务的，是对一些可以付出更高的成本、但是想拿到更强推理速度的这一波用户去做的。因为它本质上，如果说是为了整体的输入铺[?]的服务的话，这个其实它的收益会强很多；但是如果你是小 batch size、但是大的输入铺[?]的，这套方案是会强很多的。然后这样的话，刨开 TileRT 那方面的贡献，最后就落到了如何去做更好的 MTP，或者说做更好的 Draft Model。这块有一些有历史脉络的工作，刚开始就是 EAGLE-3 和 MTP。EAGLE-3 和 MTP 它主要的方法就是：因为刚开始 Speculative Decoding 提出的时候，大家还是用一个没有关系的小模型，然后来去 speculate 比较大的模型，这样的话其实有一个问题，就是你无法充分地去利用大模型中间的一些 Hidden State；如果说你可以利用大模型中间的 Hidden State 的话，你其实就可以把小模型做得更小，或者说在相同的参数底下，你的接受率做得更高。

## 领读·Infrastructure（KDA Kernel 与分布式训练）

最后可以带来总体更强的一个推理效率，MTP 和 EAGLE-3 其实都是这样一个思想，当然 MTP 如果从 from scratch 训的话，它还有一些别的好处。DFlash 会更有意思一些，因为它把传统的 Language Model 和去年比较火的 Diffusion Language Model 这两条脉络联系了起来。Diffusion Language Model 刚提出来的时候，大家主要的 claim 就是：它在单用户、或者说 batch size 比较小的情况下，可以获得比传统 Language Model 快很多的推理效率。但它之前最大的有两个问题：第一，如果 from scratch 训练，它整体的训练效率不够高，结果很难和传统的 AR Language Model 相匹敌；第二，它只能打小 batch size 的 throughput，如果是多用户、最后追求总 throughput 的场景，Diffusion Language Model 其实并没有优势。所以 DFlash 当时主要就是统一了这两者：试图利用 Diffusion Language Model 更快的一个推理方式，进一步去优化 MTP 或者 Draft Model 这块的加速比，最后可以得到一个更优的、总的单用户 throughput。当然，MTP 这块其实是之前我跟陈剑——就是做 DFlash 的那个同学——也交流过，他当时提了一个对整个模型很重要的点：即使我们用 DFlash 这种更先进的 Draft Model 策略，它跟预训练的关系仍然是很大的。也就是说 Draft Model 需要先利用大模型一定的推理能力，在这个基础上再去用 Draft Model 进一步放大。所以对 MTP 来说，需要在 pre-training 阶段就给 MTP 提供一个接口，这个接口对下游 Draft Model 的提升会特别有帮助，这部分是要在 pre-training 阶段就引入的。当然 Draft Model 自己也是需要做一些特化处理的，比如说我们可以用一个 KL loss 来替代比较传统的 next-token prediction，这样在原模型 verify 的过程中可以对得更齐，进一步提升 Draft Model 接受的效率。这块我觉得之后还会有更深层次的工作，我猜，因为这肯定不是 MTP 的终点。后面这个 RL task 的话就比较 specific，对于不同的任务有不同的具体策略，这块只要看原文就好了。

接下来的一大块就是 Infra。现在对模型架构设计来说，关键的设计是需要和 Infra 进行 co-design 的：一个是 co-design 本身，另一个是模型架构会影响整体 Infra 传输的设计。这块包括跟 DeepSeek 这一系列的 Infra 是有一些设计上的区别，我觉得也是一个比较有意义的点。首先就是 KDA——KDA 在前面其实已经讨论过了：我们如果想追求更高的 chunk 效率，就需要对 KDA 的衰减系数做出一定的限制，这样就可以用一个更好的 kernel 设计形式，带来更强的 kernel level 的效率。

这块多出来的一个点是 CP，我觉得 Linear Attention 的 CP 是可以简单讨论一下的。比如说对于 sliding window 或者 full attention 而言，CP 从概念上是相当容易的：对 full attention 来说，现在有一些比较经典的算法，比如你可以用 Ring Attention，或者用 Zigzag Attention，因为 attention 本身的计算模式是够简单的，而且很多地方是省不了的，我至少得把跨 GPU 的所有 KV cache 都拿到一个 GPU 上，这是一个比较简单的概念。但是对于 Linear Attention 的 CP 而言，概念其实就更复杂。大框架还是回到最经典的 chunkwise recurrent：首先我们都同意，chunkwise recurrent 对 Linear Attention 是一个必备的算法；对一个正常的、单机不开 CP 的训练场景，它其实就是两部分——可以拆成比较小的、比如 16 或 64 tile 的一个 chunk，chunk 之间用 decay 的方式去计算，chunk 内部用比较 parallel 的方式去计算，KDA 也是这么做的，KDA 那个 decay 的限制，主要就是解决 chunk 内部可以用 parallel 计算的高效性。所以对单机的 Linear Attention 来说，就是一个 chunk 内部用并行、chunk 之间用串行的计算 pattern。但是对于 CP 来说，Linear Attention 有一个比较有意思的方式：chunk 本身是可以任意拆分的，也就是说不同的 chunk 的数字——比如你想 512 个 token 一个 chunk，或者 8K token 一个 chunk——在数学上是完全等价的。这就跟早年一些比较拼接式的方案不一样：有一些工作会尝试 chunk 之间用 Linear Attention、chunk 内部用 full attention，用这种策略的话，chunk 的大小就跟你具体的模型 architecture design 有关了，但纯 Linear Attention 其实是无关的。既然无关，我们就可以对 chunk 的层次做比较任意的处理：比如对单机来说，chunk 是一步拆分的，就按 16 tile 去拆，16 tile 内部用并行方式计算；但它并没有限制你 chunk 只能拆一次，它的思想是：比如有一个 1M 特别长的 chunk，我们可以拆成 8K 放一张卡、8K 放一张卡，这样就构建了一个以大 chunk 为单元、不同 GPU 之间采取递归计算的结构。拿到 8K 的拆分方式之后，我们还可以在内部进一步去拆分。所以在 Linear Attention 里，我们没有任何限制说一个 chunk 中间要怎么计算：对一个比较小的 chunk，parallel 是比较优的实现；但如果拆的 chunk 足够大，我们可以采取 chunk 套 chunk 的方式去计算。也就是说，对 Linear Attention 的 CP，我们做的是一个层次性的 chunk：首先在不同机器上做一个 chunk，在一个机器内再在 kernel 里做一个 chunk，通过这样的双层 chunk 形式，组成对 Linear Attention 一个比较大的 CP。这个主要还是来源于 chunk Linear Attention 的 chunk 可以任意拆分的特性，由此带来了 Linear Attention 的 CP 方案，是跟 full attention 不太一样的处理方式，这个是可以讨论一下的。上面这个是 CP、或者说 kernel 侧的一个 Infra 方案。

接下来其实就会从分布式训练的角度，讨论我们如何优化它的分布式方案。这块我们后面就可以发现，它跟 DeepSeek-V3 的方案稍微有些区别，这个区别主要来源于不同的 MoE 架构。首先 5.2.1 这部分，Kimi 团队带来了一个基于 DeepEP 进一步延伸的 EP 计算方案。他们主要的 claim 是：对传统的 EP——因为我们现在都用 dropless EP，就是对每一个 token 而言，我选哪个专家是不受整体约束的，想选哪个选哪个——这样汇总起来会发现，不同专家的负载是不一样的，既然不一样，就会带来一些问题。第一个问题，对 EP 而言，每个 GPU 分到的 token 数不一样，token 数不一样，它整体的执行时间就不一样；执行时间一旦不一样，它就会互相等，互相等就会浪费 GPU 的算力。第二个问题，如果不同卡上的 token 数是不确定的，对 GPU 的通信来说会额外多一个阶段：我们首先需要告诉所有 GPU 你要接收多少 token，它再把这个 token 发过去。基于这两个阶段，传统 EP 严格来说当然不是一个最优的方案。如果完全为了 Infra，最优的方案就是带 drop 的 EP，也就是说每个 token 都要受到全局的影响；在受到全局影响的情况下，我们可以通过一系列 allocation 的方式，从模型的角度让每个 expert 都分到完全均匀的 token，通过模型的方式让它达到完全的 balance，理想情况其实就是这样的。所以如果在 Infra 层面完全均衡是最优的，那 Infra 的策略就是努力把 Infra 从非最优导向最优，同时保持模型能力不下降——因为如果 drop token，大家现在都不会用，它对模型能力的损失还是相当明显的。MoonEP 就采取了一个我觉得比较高端的方案：它把模型 EP 的方式变成了一个更动态的方式。之前比较经典的方案，比如我有 128 个专家，如果我们 EP8、可能每张卡放 16 个专家，这是一个比较静态的方式；MoonEP 采取的是一个动态性的方式，它会有一些冗余的专家，通过额外冗余的专家，从数学上是可以证明存在一个策略，我们只需要增加一个小比例的冗余专家，就可以保证 token 数的完全对齐。我感觉这像是一个比较经典的数据结构与算法的问题，这个是可以证明到的。他们可以证明到这一点，就可以得到一个结论：我们通过少量的冗余专家，就可以达到所有卡上都据算[?]的这样一个效果。具体如何达到？他们采取了 online planning 的方式，提前去规划哪些卡应该有哪些冗余专家，在这种情况下，就可以对不同卡上的 token 数做到完全的均衡。当然，即使从卡的角度是均衡的，它也并不代表专家层面是均衡的，因为这个算法只保证了每张卡的 token 数是一定的，但并不保证每个专家是一定的，因为一张卡里有多个专家。如果还想保证每个专家都是一定的，那就没有办法了，就只能采取有损的策略去优化；如果大家不希望有损，这个上限可能就卡到这里。所以在这两者中间，可以找一些更优的处理方式。这块是 Kimi 团队带来的一个比较有意思的创新。

接下来这块就是 Memory-Efficient Training，我觉得这块比较有意思。首先他们从软件工程的层面带来了一个比较简单的方案：我们可以更细粒度地去控制每个部件应该采取 activation、还是采取 offloading 的策略。这块不一样的一点是，Kimi K3 采取了大规模的 offloading，中间计算得到的结果会 offload 到 CPU 上。这其实是一个 non-trivial 的东西，因为理论上想让 offloading 不拖慢模型的训练，它是有一定条件的：你得保证 CPU 和 GPU 之间的通信满足某个不等式，这样你才有完全用计算 overlap 通信的可能。Kimi K3 把所有可以 offload 的东西都用 FP8 去存，这样它可以省一倍，可能才能从一个边界跨到另一个边界；具体这个边界怎么算，就跟具体的卡、具体的机器环境，也跟具体的模型 config 有关系。后面一方面，他们需要去优化 attention residual 本身的一个运发[?]的关系，这个其实在 attention residual 的 paper 里也讨论过；然后我觉得一个是 PP、一个是通信的 overlap 手段，这块其实跟 DeepSeek 是不太一样的方案。

因为首先，比如说从 DeepSeek-V3 的角度来讲，它采取了两个不太一样的、至少是 non-trivial 的方式，一个就是比较细粒度的 MoE 角度的 overlap。MoE 中间有两个通信，一个是 dispatch、一个是 combine，这两个通信的 overhead 是比较大的——其实在 Blackwell 上又不太一样，但无论如何它是一个比较大的开销。DeepSeek-V3 在 MoE 的 overlap 这块会拆得特别细，具体的方式，就是会把这个 MoE 上一个 batch 的 forward、还有 backward，和下一个 MoE 的 forward 融合起来，通过重排序计算的先后顺序，从而达到把所有的这个大的……

## 领读·Mooncake 与推理优化

这个 dispatch 和 combine 的计算，跟 dispatch 和 combine 的通信，都想藏起来。想达到这点的话，其实需要特别精细、也特别复杂的方式，做一些软件工程上的优化，这个其实在 Megatron-Core[?] 里边也讨论过类似的事情：因为这个事情想做得足够好的话，我们需要把所有 forward 和 backward 的计算从原子计算的层面就拆开，然后手工进行重新排布，我觉得这个还是有一定难度的。然后另一个就是 DeepSeek-V3 采用的 DualPipe 策略，也就是为了缓解 PP 的气泡和不同 activation 不均匀的问题，他们采取了 DualPipe 的一个 pipeline 的排布方式；当然除了 DualPipe，还有个 DualPipe-V，它们达到的效果是一样的，它从逻辑上会更简单一些。起码从公开的、他们写到的里边，Kimi K3 是没有采取这两个优化方式的，他们采用的其实是一些别的方式。

第一个就是如何去隐藏通信，这个就跟实际的模型架构选型有关系。因为 Kimi K3 采用了 LatentMoE，而 LatentMoE 本身是极大地降低了通信开销的，所以它在整个计算开销里边减小了特别多。因为通信开销减小了特别多，所以如果想把它 overlap 掉就会变得容易很多——我们没有必要再去跟另一个 batch 的计算做 overlap，可以采取一个 batch 内部更简单的 overlap 手段，就可以把通信很好地隐藏掉。Kimi K3 具体采用的方式，是把 MoE 前向和后向的通信跟 shared expert 的计算 overlap 在一起。因为 shared expert 现在大多数都有，而且 shared expert 是有一定的计算量的；正是因为通信的开销减小了，所以它才能被 shared expert 以一个比较简单的方式 overlap 掉。但如果你用传统的 MoE，它的通信开销就会特别大，特别大的话你用 shared expert 去 overlap 就很难 overlap 掉；如果 shared expert overlap 不掉的话，你就必须把另一个 batch 拿进来，这样才能完美地把通信都隐藏掉。用不一样的 MoE 架构，带来了不一样的 overlap 策略，这个策略带来一个好处，就是推理的 critical path 的 latency 它是免费的；从训练架构上，因为通信量更小了，我们就可以采取更简单的一个策略来排布通信的气泡。其实还有另一个问题：就是我们即使通过更复杂的方法完美地把通信藏掉，它其实也不是完全无损的，因为即使是完美的通信和计算隐藏，计算也会相对地慢一些。针对这个问题 DeepEP 也做了类似的优化，DeepEP 的优化方式就是用一个足够少的 SM 的占用，来获得更大的一个整体的通信 throughput，从而让这块的 overlap 跑得更快，所以这块是一个很不一样的设计方式。

另一个设计方式就是 PP 的处理，其实是不太一样的。因为如果用 DualPipe 或者 DualPipe-V 这样的一个 PP 的排布方式的话，不同 PP rank 之间相对还是一个比较对称的状态；如果你用单向的 PP 的话，它其实就不太对称。不太对称的话就有两种解决方式：第一种就是让它变得对称；第二个方法其实就 Kimi 这篇 paper 里讨论到的，我们可以把不均衡的部分 transfer 掉。因为比较朴素的 PP，比如说前面的 PP rank 它会进入得更早，它积累的 batch 就会更多，它的 activation 的压力就会越大。Kimi K3 采用的方式是，把 memory 占用比较大的一些 PP rank 上的内容，直接让它存到占用比较小的 PP rank 上，通过这种比较 lightweight 的方式，规避了更复杂的 DualPipe 的设计方式。

再往后其实就是 Muon 的一些优化。因为 Muon 是需要全矩阵去做 Newton-Schulz 迭代的，所以如果用传统的 Adam——因为 Adam 相当于你是把所有参数都摊平、之后再去切的，而且 Adam 是 element-wise 的优化，所以你怎么切都不会影响模型优化的结果——但是对于 Muon 来说它是有影响的，因为在某个 rank 上，我是需要把一个矩阵所有的参数都保存下来的，所以这块需要做一些处理，才能让 Muon 比较好地在 optimizer 这个角度切起来。对，然后多模态这个 infra 也是一个比较有意思的点。因为其实从 infra 的角度，纯的 language model，大家想把它优化得足够好也是需要相当多 effort 的，这刚刚也讨论了很多；但是对于多模态而言，你每引入多模态的一项功能，它的 infra 难度其实都是直线提升的。这块的问题就是如何把 Vision Encoder 做好。Vision Encoder 做好的话，它提出两个问题：第一个就是，对于现在的 Vision Encoder，大家会对 Vision Token 做一定的压缩，比如说 Vision Token 最后输入到大模型里边的话可能是 8K token，但是你输入之前可能是 32K token，就是说 Vision Encoder 接入模型的过程中其实是有做一个压缩的，但是这个压缩在 Vision Encoder 内部是没有做的，所以它在内部计算的时候就会更长。所以为了解决更长的问题，可能你对于模型主干不需要开 CP 的话，你可能对于 Vision Encoder 就需要开 CP，所以这块是需要做一些额外的 infra 处理的。

然后 PP 这个就更有意思了。大家其实注意到一个问题：我们做 VL Native Training 的时候，VL 的 Token 其实只是有一个比例的，比如说对于某些卡来说它是一个纯文本的状态，对于另一张卡它可能是一个全视觉的、VL 比例相当大的状态。如果是这种情况的话，你还是会出现一个对不同卡不均匀的现象，然后这个现象不仅会影响 DP，PP 也是会受影响的。因为 PP 的话，我们首先要保证不同 PP rank 之间是一个比较均匀的状态，这样它的流水线才能打得足够满；不然的话，如果我们在这里引入了一个新的 Vision Encoder，第一个 PP 的计算强度就会显著增强，它就会破坏整体这个流水线。为了规避这个行为，Kimi K3 采用的一个方式就是把 Vision Encoder 不去放在 PP 的刚开头，它是会放在中间或者尾巴上。所以在前面的这个 Vision Encoder 或者说比较浅层的 Language Model 跑的过程中，中间的 PP 它是闲时的，它就会把中间闲时的这部分利用上，提前把 Vision Encoder 后面的一些步骤提前算出来，通过这种方式规避掉第一个 PP 带来的足够大的一个气泡。这个是在 PP 的层面需要做的一个优化。它这边论文真的写得好详细啊。是的，就是这些细节东西其实是需要去处理的：如果你不处理的话，你写出来大家就会觉得这个事情肯定没有问题、可以去这么做；然后有一些没写的部分，大家就会去追问。如果有些团队的组织密度没有那么足够，说我自己就能把这个事情搞定，大家一部分就会沉迷于小道消息嘛，就会私下里打听这些东西到底是怎么处理的；如果你写出来这个事情，其实大家就不需要去找小道消息了。如果它写出来了，再复现难吗？我觉得 Infra 上的事情本质上没有什么难的，因为它本身就是一个高度确定性的东西，我觉得所有 Infra 方面的事情本质上都是一个确定性的东西。但是你如果想自己提出来的话，它就对你本身分析 profiling 的方式，或者说对于你本身的组织密度，或者说你团队氛围，就有比较高的一个要求。但是你如果整个 Infra 团队比较好，你还是可以自己搞出来的；但是如果不行的话，你就尝试去 follow 一些比较好的工程实践的 practice，但如果这个事情都搞不定，我觉得就可能不太应该了。

前面 Infra 主要就翻了三部分：一个是 pre-train，pre-train 前面主要是讨论了一些大规模分布式情况下比较复杂的优化方式；然后后面的话就是两部分，一个就是 RL，还有一个就是 Inference。RL 因为它本身就是涉及大量 Inference 的，所以在这两个中间其实是有一些 overlap 的。然后 RL 本身一个不太一样的点，就是它需要对大规模 Sandbox 有一些比较细的要求——对，但这其实就算是一个更工程的东西了，这块其实就是一些比较细的处理，去处理不同的 Sandbox：对于 RL 的 task 来说，你每一个 trajectory 可能都对应一个它自己的 Docker，所以说如何去管理大规模 Docker，其实是这块比较麻烦的一个问题。我觉得这个 Kimi K3 比较有意思的就是，它会时不时给你蹦出来一些比较有意思的东西。对，我觉得这块比较有意思的东西，当然也不一定是刚才他提的这块可以省一个 Gradient Buffer，对，这块相当于是一个比较 tricky 的东西。因为对于一个完整的 RL 来说，它有好几部分的 model：比如说你至少有一个 policy model，然后你还有一个 Reference model；你的 policy model 它还有对应的一个 Gradient 和 Optimizer；当然如果你还想做 Reward model 的话，它还会再多一个 model，所以其实这块就会多特别特别多 model。然后 Kimi K3 这块有两个比较有意思的事情，一个就是它不同 model 之间——因为你放一个 model，它对于 GPU 来说还是一个很大的 memory——所以它这块相当于把两部分 memory 拖到一块来，就对于 Reference model 而言，他们发现它可以跟 Gradient Buffer 合起来。因为首先对 Reference model 它是没有 T2[?] 的；然后在你求 Objective 的过程中，你是没有 Gradient 的，等你有了 Gradient 之后，这个 Reference model 就不会去用了。对，所以说它这块用了一个 Gradient Buffer，for non-policy model for forwarding，这块是一个比较有意思的东西。然后上下楼[?]，就感觉是一些比较常规的处理方式。

然后我觉得 Inference 目前不会有太多的一个东西，因为主体的这个 Inference 优化，它其实是 vLLM 或者 SGLang 这样专门讨论的一些内容。这块其实讲的就是，对于 Kimi K3 的架构所带来的增量，在这个现代的推理引擎中是如何去处理的。首先就是 Linear Attention，它在现代的这个 Inference Engine 里有一个麻烦，就是它的 Prefix Cache 是一个比较麻烦的点。因为对于 Full Attention 来说，相当于每个位置它都有一个 Cache，所以下一个位置的 Cache 一定是上一个 Cache 的一个简单的增量，所以说在这种情况下 Prefix Cache 会简单很多。但是对于 Linear Attention 来说的话，它有一个比较麻烦的特性：就是 Linear Attention 它每一步，是会在原来上一步的 carry cache 的基础上做一个覆写的，也就是说对于每一步而言，它的 Prefix State 其实都是不一样的。所以说如果我们把每一步都存起来，那 Linear Attention 的好处就完全没有了；但是你如果完全不存的话，你就完全没有办法去享受到 Prefix Cache 所带来的好处。对，然后这块，对目前对于 Linear Attention 采用的策略，就是按照 Block 去切，就是每个 Block 去做一个 Prefix Caching。然后同样的话，我们还需要一个 Non-Trivial 的点，就是 vLLM 这样的一个 Page KV 的实现方式，从工程上或者从概念上，它最简单的一个分布方式是不考虑层和层之间的异质性的。所以其实从去年还是前年，如果想直接在 vLLM 里去引入混合架构的话，它在 Infra 上并不是一个容易的事情；而且因为现在 Inference Engine 越来越 Heavy 了，简单的一些改法会把整个 Inference Engine 搞得特别特别的乱。当然现在这个 Inference Engine 可能都有一些比较先进的管理方式了，但是这个就是需要去透露[?]处理一下：因为对于 Full Attention 层面来说是按配置管理的，但是对于 Linear 层面或者 Sliding Window 的话，它就不能按照配置管理，因为它并不存在一个长久的、对于 token 而言的一个 carry cache 的产生方式，这个本身对于 vLLM 的设计来说，其实是需要做一些兼容性的处理的。然后我觉得后面就是一些适配性的一些优化，因为 Decoding 的优化其实跟 Prefill 或者说跟 Training 不太一样，所以这块对于每个环节都需要做一些额外的 Colonize[?] 的一个配置，但我觉得这块都是可以去做的，而且我觉得应该是一个确定性比较高的事情。然后后面就是 Evaluation 了，我觉得 Evaluation 这个没啥好讲的，就是好呗。

## 收尾与总结

**孙宇涛**（接上）：……特别好，就是在每个环节都好，后面主要就是这样的一个状态，应该就没啥了。

**张小珺**：觉得 K3 让你最 impressive 的地方是哪里？
**孙宇涛**：个人而言，我觉得 impressive 的一点，就是他们把这个激活搞得特别特别大，足足有 100B，比我预期的还是要大一些。这个依赖的是什么能力呢？这个不依赖任何能力，就是你具体定多少激活——这本身不是一个技术性的东西，就看你想达到什么阶段的效果。我觉得 K3 还是比较有魄力：在已有的开源模型 size 的基础上，他们要提升一个数量级，所以他们比上一代的激活其实是多了三倍多。我觉得这个决定是一个非技术性的决定，但是这个是要有一定的魄力的，因为杨植麟喜欢说"有概率的非共识"。
**张小珺**：你觉得在 K3 上能看到他们什么样的 different bets，或者说创新？
**孙宇涛**：我觉得也没啥，因为有价值的技术创新他们都单写了一个 paper 了。所以 K3 刚出来的时候，我主要就 surprise 这个 size，别的我都和我一起[?]。你刚才给大家也展示了好多他们历史的 paper，其实中间就已经发出来了，对吧？但是他们把它优化到了一个更大的模型上。我其实的一个观点就是，科学研究是不存在跳跃性的提升的，只是说大家习惯把这个技术渐进提升的某些节点看成一个 milestone，我一直是这么认为的：技术永远是慢慢去提升，然后靠公司里的所有人、项目里的所有人，包括整个业界的同学一块去推动的，所以从这个角度讲，没有什么 milestone。

**张小珺**：有人说 Kimi 的研究方式相对比较科学，你觉得认同吗？你怎么解释？
**孙宇涛**：首先我是认可的，但具体认可的方式，我觉得主要来源于他们内部的一些管理方式。当然有些是公开的、大家都知道的：Kimi 其实在公开里边，是大家认可的、最强调"模型内科"的一个团队。就是 Kimi 他们一直尝试让这个 pre-training 变得更加科学，比如说让不同行为的 trace 可以用更可靠的方式去获取到；让模型的不稳定性，或者说模型 collapse 这个现象，可以更明确地去归因。所以他们其实一直去强调"模型内科"这样的 case，我觉得这个其实是他们科学化的一个体现，没有任何问题。我觉得科学对应的就是不科学——什么是不科学的？这个事情讨论清楚了，大家就知道什么是科学的、什么是不科学的。我觉得不科学的方式就是：如果从整体项目的角度，你想去推一个东西、你想证明某个东西是有效的——我觉得这个东西不存在任何疑问，因为学术创新，或者说从学术论文管理的角度，大家都是有明确标准的：你得有明确的 ablation，你得有足够的变量的控制，你得用更科学的方式去说明你这个东西是有效的。我觉得基于某些利益需求，然后把科学的方式都干掉了，这就是不科学，不特指任何技术。我一直强调的就是，Kimi 这个团队非常团结，非常能把劲往一处使。如果大家是这样的 motivation，你的判断方式自然而然就是科学。

**张小珺**：最近也是 V4 发布的时间，K3 和 V4，你觉得他们的区别是什么？能不能做一些对比？
**孙宇涛**：我觉得是不同层面。从模型定位也好，从刚刚咱们比较详细讨论的 infra 上的一些区别也好，从模型角度层面区别还是比较大的，完全也不是一个东西。我觉得比较好的一个 case，就是 DeepSeek 现在出了两档：一档是 1.2T 的，另一个是一个更小的 size。DeepSeek 我觉得目前还是更强调性价比的，他们那个 Flash 模型做得还是挺好的。但 Kimi，我觉得他们目前主要的精力还是尝试去提升开源模型能力的上限，而不是去考虑这个模型的性价比——也不是完全不考虑，至少说模型的性价比不是一个最首要的考虑条件。当然也可以看到，现在 K3 的 API 相当贵，比别的模型贵多了。
**张小珺**：照这个趋势发展下去，Kimi 和 DeepSeek 会分化吗？
**孙宇涛**：我觉得技术层面的东西，只要大家不笨，都是知道什么是好、什么是不好。我觉得组织团队的走向，还是取决于人的选择，我觉得就是这么简单。我觉得技术上这个东西不存在太多 debate 的：好就是好，不好就是不好，这个是有明确的客观标准的；但对于组织而言、对于人而言，这个是比较模糊的。
**张小珺**：你觉得 K3 相比之前所有模型来说，不一样在哪里？它有架构创新，创新性更强？
**孙宇涛**：我觉得两方面。从技术的层面来说的话，我们可以讨论很多很多，它中间有一些创新也好、有一些取巧也好，这个对于技术同学而言是可以去讨论的。但这个东西是不是成为里程碑，它是个非技术的问题，所以说它最大的变量是你最后的一个能力。拿 DeepSeek V3 来说，比如说它那些 R1 这些东西，我觉得就是简单开花[?]。我觉得最大的问题是，它其实是国内第一个把模型 scale 到一定程度、并且把 RL 全球数[?]打通的。因为在 K3 之前，可能最大的就是千问 72B，这个其实是从模型 size 上一个比较大的推进。因为有 size 它才有智能，所以 K3 你把激活多了三倍、把模型也扩了快三倍，它就是下一个 level，我觉得这个就没有任何问题。
**张小珺**：所以它核心是 size、有效的 scaling？
**孙宇涛**：对，其实是这样。这完全是一个靠团队来去做起来的东西。因为把模型增大这件事最简单——如果取巧来看，我就把模型几个数字调大一点，就可以达到一个更大的 size，但这个不解决任何问题。从技术上来讲，它不是一个太大的创新，因为扩大模型 size 本身不是创新，你把这个东西做 work，它才有创新。

**张小珺**：你觉得新团队现在再去重做一个模型，还有时间窗口或者机会吗？
**孙宇涛**：我觉得如果这个团队足够好、这个团队的氛围足够好、然后单兵作战能力足够强，是有机会的。但这个条件我觉得大概率是不存在的，所以后面的事情也就不存在。为什么不存在？因为好的人其实已经进去了，怎么说呢——好的人和好的组织文化想达成，我觉得是有历史的局限的，就是你不是想达成就能达成的。氛围这个事情真的是有点虚，很难去描述它。
**张小珺**：我觉得也不虚。我觉得就是取决于这个 leader 的 taste，或者说 leader 的性格，是绝大多数影响到整个团队的氛围的。我觉得 Kimi 有一个特点，是所有人好像都不怕杨植麟吧？
**孙宇涛**：对啊，为什么要怕呢？谁有道理谁说了算吧。对，它还是非常集体的一个工作，不是一个个人的工作，不依赖于个人英雄主义。

**张小珺**：你觉得未来模型的发展方向，你有没有什么预测？比如说半年之后、一年之后？
**孙宇涛**：模型 size 毫无疑问还会继续扩大。我说一下我的判断，我的判断比较暴论：大模型可能没有太本质的创新，后面都是一些改良性的进步，然后它会做到一个什么样的水平呢？做到多大 size，对应的是什么样的性能呢？我觉得重要的就是大家去定义什么能力、去定义——只要大家能定义一个能力，就能去达到。因为大家之前定义的方式，比如说就是强 coding、agent coding，这些东西是清晰定义出来的，然后大家就可以去做到。这个取决于大家怎么去定义这个能力，或者说从商业化角度大家注重什么能力：只要它能清晰定义这个任务本身，它的能力就能够达成。我觉得如果是纯 language 的，应该没有太大问题。
**张小珺**：它能达到所谓的 AGI 吗？
**孙宇涛**：我觉得 AGI 最大的问题就是它没有被 well defined，所以只要能够定义，它就能达到，后面都是一系列的优化工作。当然，如果说你定义 AGI 是具身、是真实物理世界交互，我觉得这个事情肯定还是 gap 更大的；但如果你还是在 language model 的 scope 里讨论问题，我觉得问题不大。
**张小珺**：你觉得它最后会是一个多大的模型呢？还是说它无限大、无限往上叠上去？
**孙宇涛**：这个事情肯定是不可能的。首先，对于训练的数据量，包括说我们已知的——我觉得从抽签[?]来讲，就是人类互联网上能集结到的所有的信息量，这个是有限的，这个事情是不可能无限提升的。基于这个 case 来讲，从数学理论上，你想吃掉一个足够大的数据量，你模型不可能是无限的，也没有必要是无限的。所以说这个能带来一个更宽的 bound，然后这个宽的 bound 可能上下会更好；更窄的 bound 是在什么情况下？就是我们对模型具体在任务上的一个感知，可能会没有那么充分，这个是一个更窄的 bound。或者说如果未来有更难的任务，它必须有更大的 size，那可能就会退化到更宽的那个 bound 里。对，但是无论如何，不可能是无限的。
**张小珺**：你觉得它最后会有多大？这个模型现在是 6 到 2.8[?]，以后呢？
**孙宇涛**：必然的，肯定还是有更大的。所以如果想完全 match，必然的、肯定还是可以再大一些的，但是更大的话，这个就不确定了。
**张小珺**：你现在为什么去探索世界模型了？
**孙宇涛**：这个主要是一个 personal 的东西。因为我觉得大模型不存在太大的改良空间、改进空间，没有大的突破的话，就没有大的这个 credit。所以我觉得对于个人来说，可能从职业上来讲，不是一个能做出太大贡献的领域。这个我有理贩[?]的问题——这玩意儿问题更大，但我觉得至少是一个新的东西。
