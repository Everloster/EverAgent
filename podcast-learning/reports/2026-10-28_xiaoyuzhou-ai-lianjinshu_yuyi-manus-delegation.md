# 余一聊 Manus：怎样把任务真正交给 Agent

## ⚡ 速览

- 主 Agent 要替人承担协调与验收。
- 旧规则要重测，可靠运行的机制要留下。
- 少盯进度，但保留自己形成判断的过程。

## 概览：AI 能做更多，为什么人反而更累

一个常见的工作场景是：同时打开几个 Agent，让一个查资料、一个写代码、一个审稿。每个窗口都在产出，人却忙着搬运信息、追问进展、解释报错，最后还要亲自判断谁真的做完了。工具增加了，协调工作也增加了。

这期《AI 炼金术》提供了一个具体的使用者视角。刚加入 Manus 的余一与主持人任鑫、徐文浩讨论：她怎样把分散的监控、研究、日程和审核交给不同机器人，再只跟一个主 Agent 沟通；为什么开始怀疑积累了一年的 Harness；以及加入一个全员重度使用 AI 的团队之后，工作和招聘发生了什么变化。节目于 2026 年 10 月 28 日发布，标注时长 85 分 51 秒。[^episode]

**最有价值的变化，是把“谁来协调、谁来验收”也纳入委托。** 不过，整期节目并没有证明所有事情已经可以无人照管。主持人仍然交不出去视频剪辑；余一的面试预约流程仍有最终确认；她准备清理 Harness 的对照实验，也尚未给出结果。这几个限制，恰好帮助我们把经验变成可检验的设计，而不是新的口号。

下文把能调用工具、持续完成任务的 AI 助手称为 Agent；Bot 指承担特定职责的机器人。Harness 则是围绕模型的运行配置与机制，例如项目指令、工具接入、任务状态和检查步骤。它既包含可以精简的文字，也包含维持可靠运行的程序。

本文完整阅读了正片的机器转写，并以官方节目简介校正章节和专名。节目外的工程解释另与 Manus、OpenAI 的原始文章及产品文档对照。嘉宾自述、主持人推论、厂商产品说明和本文建议分别标明；没有把使用体验当成独立测评。

## 从个人能力到团队合作

余一离开腾讯研究院的解释，是越来越难忍受自己只是旁观者。这里有一个比跳槽更值得讨论的转折：AI 带来的“什么都能做”，没有自动变成“什么都值得自己做”。她观察到，重度用户经历最初的兴奋后，开始遇到精力和质量的限制。自己加上一组 Agent 可以拓宽能力，却未必能同时把所有方向做好。她因此希望加入一个目标、工作节奏和产品判断相近的团队。[^opening]

她把新问题描述为“人、Agent、人、Agent”之间怎样合作。单个人会写提示词，不代表两个人带着各自的知识库、工具和助手，就能够低摩擦地协作。谁掌握哪部分资料、谁能提出需求、谁负责执行和验收，都需要重新安排。

她选择 Manus，也包含非常具体的个人条件：与团队已有长期产品反馈关系；彼此熟悉，能够快速开始工作；希望参与全球化产品；自己想做的事与岗位方向有重合。她介绍的新工作以产品和社区为主，把重度用户的需要与实践反馈给产品团队。**这解释了她为什么适合这个位置，不能据此推导 Manus 对所有人都是最佳选择。**[^choice]

[推测] 本期的主线可以理解为一次注意力重新分配：把反复操作、状态追踪和信息传递交给系统，把人的精力放在问题选择、质量判断和真实用户交流上。后面的架构和组织案例，都是这一目标的不同实现。

## 把协调工作也交出去

### 主 Agent 应当接住结果，而不只是转发消息

余一举的第一个例子是抓取微博。主 Agent 与她把链路跑通后，把经验和代码交给一个监控 Bot，让它完成后续工作。她不用重新到另一个窗口解释一遍背景。进一步，她把常用 Bot 与具体的 CLI、模型、知识库、目录和 Skill 绑定，让分工从“有时能想起来调用”变得更固定。[^delegation]

这件事的技术元素并不新：工具调用、经验复用、任务分派早已存在。她看重的是这些元素组成了稳定、容易使用的入口。自己只跟“AI 余一”说话，由它安排其他机器人，并尽量承担结果验收。节目中的“90% 与 100% 委托”，表达的是**人是否还被卡在每次任务的中间环节**，不是经过统计的自动化成功率。

这种主 Agent 也不是绝对不干活。她后来明确区分：简单任务可以直接做；复杂判断调用已有的本地能力；不知道该怎么做的新任务，可以先一起探索，跑通后再交出去。这比“永远只规划、不执行”的僵硬分工更贴近她的实际使用。[^routing]

### 把进度搬进聊天软件，并没有消除负担

节目后半段，她批评一种体验：把 CLI 的工具调用和结果切成多条消息，送到另一个聊天窗口。界面变了，用户仍然要从大量过程文本中推断发生了什么；失败停在哪里，也未必讲得清楚。她参与打磨的则是另一类沟通：什么时候该打扰人、应提供什么结果、怎样让人放心，以及怎样适应人处理信息较慢的事实。[^communication]

[推测] 一个称职的主 Agent 至少要分清三种消息：已经完成、需要人作决定、暂时失败且正在恢复。每一种都应带足够的依据。例如“报告已完成”应链接可读正文并说明核验范围；“需要决定”应指出哪一个选择影响结果。单纯把几十条执行日志缩短，仍然可能把判断工作留给人。

这与已有的 [ADE 与 Harness 区分](../wiki/concepts/ade-vs-harness.md)相呼应：执行循环能运行，不等于管理这些循环的人已经轻松。本文沿用其关于人与 Agent 管理工作流的区分，不据此评价具体工具的当前能力。<!-- [[ade-vs-harness]] -->

## 委托不等于降低底线

主持人的反例很重要：封面里的人脸不对，可以让另一个模型检查并退回重做；视频剪辑却仍然反复出错，调试了较长时间后还需要自己介入。**可自动检查的局部质量，与需要理解节奏、语义和观众体验的整体质量，交接难度不同。**“生成成功”不能代替“作品合格”。[^acceptance]

余一说自己使用 AI 的“下限比较低”，语境主要是：一些事情如果 AI 不做，她原本就不会做；或者几个版本都能接受，没有必要为自己在意而用户不在意的细节反复修改。她愿意把多个版本交给真实市场反馈。这里的“帮到 5% 就很开心”，同样是个人接受程度的表达，不是收益测量。

但她紧接着区分了容错率低的任务。她会单独设置审核角色，用更强的模型执行已有的质量原则，再把通过审核的结果送给主 Agent。过去把“记得审核”写进提示词，执行并不稳定；拆出明确的审核节点后，她更容易看出哪一步实际发生了。[^acceptance]

这给深度研究任务的启发很直接：可以接受标题风格不完全合口味，却不能接受来源没读、关键事实错误，或者一小时的访谈被压成漏掉主要论证的短摘要。**应该降低的是不必要的个人打磨，研究底线仍由任务要求决定。**

[推测] 把审核做成固定节点，比只写一句“请仔细检查”更容易验收，但仍有两个漏洞。第一，必须确认审核角色真的执行过，不能只听生成者转述。第二，审核模型也可能漏看原材料，或者与生成模型共享同一种错误。审核结果应绑定实际作品和来源，而不是把“有第二个模型”直接当成质量证明。

## 先确认能不能做成

巡店系统的案例说明了另一个成本口径。余一转述，一位没有计算机背景、来自物业管理领域的经营者，用 Manus 做出了供门店使用的系统。她询问成本时，对方强调：关键并非便宜多少，而是原先根本不会做。后续再请 IT 介入，将原型完善为内部平台，并考虑更便宜的实现。[^prototype]

她自己的习惯也类似：先用容易上手的产品探索，判断需求能否实现、是否值得打磨；方向成立后，再让其他工具或开发者介入，优化成本和稳定性。这个顺序减少了“还不知道有没有用，就先花很多时间搭框架”的风险。

[推测] 这里应把两笔账分开。第一笔是探索成本：多久能看到一个可判断的结果？第二笔是持续运行成本：维护、监控、返工和人工验收需要多少投入？首个原型更快，不代表规模化运行一定更便宜。节目没有提供这套巡店系统的源码、故障率、维护成本或正式验收记录，因此案例只能支持“降低尝试门槛”的可能性，不能证明生产可靠性。

对学习型项目，也可采用这个顺序：先完成一篇有用的报告，再决定哪些重复步骤值得固化；先观察实际失败，再补最小的规则。否则，流程可能越来越完整，读者得到的知识却没有相应增加。

## 组织怎样让上下文流动

### 有共享资料，还要有人接住下一步

余一描述的团队反馈流程，比“公司里每个人都有 AI 账号”更具体：反馈进入 Slack 后，机器人帮助分级、找到可能负责的人、检索过去类似问题和相关上下文；Notion 等资料成为背景来源。入职时，她也先问内部机器人，了解近期会议、产品进展和该找谁沟通。[^organization]

这条链路至少涉及四件事：信息进入、补齐背景、找到责任人、形成下一步行动。只把历史聊天全部存下来，通常只能解决第一件事的一部分。资料可检索，也不等于检索出的信息仍然有效，更不等于某个人已接受任务。

主持人追问了一个容易被忽略的组织问题：如果每个人都往群里放几个 Bot，沟通对象会不会翻倍？余一的回答是，按她当时观察，常态机器人只有若干个，创建权限集中在少数人手里；不同机器人承担产品反馈、通用帮助等职责。她没有描述一个所有人无限增添机器人的无约束系统。[^organization]

### 团队的快，也包含人的条件

她把快乐归于几种变化：不用再说服同事接受 AI；需求能迅速得到响应；遇到不合适的方向可以放下重来；产品、运营等角色能直接做出工具，再由开发者审查和合并。她提到“20 分钟后就能去测试”的体验，是个别工作情境的自述，不是整个团队的平均交付时间。[^team]

[推测] 这样的速度同时依赖工具和组织：谁可以提出改变、谁可以审查、谁愿意承担技术支持，都影响反馈速度。因此，不能把她的满意度全部归因于某一个模型或聊天入口。她自己也说明处在入职甜蜜期，对更细的内部机制仍在了解。

Manus 的公开 Projects 文档提供了一个有用的边界：项目成员共享主指令和知识文件，并不因此自动看到彼此所有任务；具体任务仍需单独邀请。文档也区分了指令更新与文件更新的生效时间。**共享背景、共享工作现场、共享权限是三个分别需要安排的问题。**这些产品说明能解释一种设计方式，不能反过来证明余一描述的内部机器人使用了同一实现。[^projects]

## 一个入口背后可以有多个上下文

### Agent 需要可工作的环境

“Agent as person”是余一用来设计产品的比喻：既然希望它持续工作，就给它自己的工具、知识库、通信渠道和记忆维护方式。她尤其强调不要与人争抢工作环境。节目中甚至出现了 AI 剪视频打断录制设备的插曲，主持人也谈到将 AI 工作放在另一台机器上的做法。[^environment]

这里不必接受“Agent 就是人”的强命题，也能得到工程启发：任务运行需要稳定的现场、可用的资源和清楚的访问边界。**独立工作环境能减少桌面干扰，但不会自动解决权限、凭据、故障恢复和成本问题。**节目提到电话、银行卡等资源，是设计设想的一部分，不意味着应给每个 Agent 无限制的账户权限。

值机是另一个鲜明例子。她说，自己聊到的五位用户中，有三位把它当作第一次真正感到“完整委托”的时刻：给出需求和偏好后，直接得到登机牌。主持人马上补上前提：身份信息等必要上下文已经准备好了。这是一个五人交谈样本中的观察，不能当作普遍用户分布。[^routing]

面试预约的案例进一步说明，完整委托仍可包含必要的人类决定。她让 Agent 找简历、讨论候选人、协调日历；时间谈好后，仍要与她确认，再发邀请。这种确认决定是否对外作出承诺，与频繁询问每一个机械操作并不等价。

### 研究任务的分工，比共享一大段聊天更关键

她描述的信息处理链条是：不同 Bot 监控邮件、X 等来源；主 Agent 判断哪些只需浏览、哪些值得深挖；研究角色调用既有 CLI 和研究 Skill；较复杂的判断再使用相应能力。她感到更稳定的，是这一整套分工终于能持续运作，而不是某个提示词突然包办所有任务。[^routing]

[推测] 因此，“只跟一个 Agent 聊天”应首先理解为一个统一的沟通入口和协调责任。背后的工作单元仍可以有各自的上下文、工具和任务记录。对外看起来连续，不要求内部共用同一个无限增长的会话。

Manus 的 Wide Research 原文描述了类似的分层：主控拆解任务，子 Agent 各有独立环境和上下文，由主控收集并整合结果。这个结构适合可以独立调查的多个对象；该文章也提醒，强顺序依赖的任务和较小任务未必适合展开很多子 Agent。文章中“没有质量衰减”等表述属于厂商宣传，本报告不把它当作已验证的普遍结论。[^wide]

对于共享上下文，可以继续阅读已有的[多设备、多 Agent 上下文与会话续接报告](../../ai-learning/reports/knowledge_reports/多设备多Agent共享Context与会话续接_Manus实践与架构边界_深度解析_20261029.md)。本期新增的重点是：共享机制最终应减少用户搬运信息、盯进展的工作，而不是只让更多会话读到同一批文件。

## 旧规则该怎样删

### 她提出了清理计划，还没有给出实验结论

余一举了一个具体触发点：使用 Manus 2.0 做视频时，一句话得到的效果很好，加入自己已有的 Skill 反而像在给模型添麻烦。由此，她怀疑过去积累的一部分上下文已经成为负担。她准备把旧 Harness 移到另一个文件夹，以更小的上下文重跑之前的任务；也已经让 AI 按“证明哪些应保留”的思路做审查，但在录制时尚未看完结果。[^harness]

这段话能支持两件事：她观察到一个不加旧 Skill 更满意的案例；她希望通过对照重新判断规则价值。它**不能支持“她已删完全部 Harness，而且总体效果更好”**，更不能证明换任何模型都应裸跑。

### OpenAI 与 Manus 原文，针对的是不同层面

OpenAI 关于 GPT-6 Astra 的技术博客，要求重新审视 Skill 描述、常驻项目指令和任务提示。过宽的触发条件会让模型读入无关技能；过长的配方可能限制新模型；每次改动都强制读取一摞文档、反复测试，会增加耗时。文章同时强调说明完成条件，以及按任务需要逐步加载材料。它还特意提醒：同一仓库可能由不同模型使用，适合一个模型的指导不一定适合另一个。[^openai]

Manus 在 2025 年的 Context Engineering 文章则解释了执行系统为什么仍需要设计：用文件系统保存可再次读取的信息；保留失败动作和错误反馈；让长期目标保持可见；注意工具定义变化对缓存和动作选择的影响。作者明确将这些写成团队经验，而非普遍真理。[^context]

两篇文章放在一起，更合理的问题是：**哪些内容在替模型规定已经不必要的步骤，哪些机制仍在提供模型本身无法凭空获得的事实、反馈和执行条件？**

| 面临的内容 | 更合适的处理 |
|---|---|
| 过期的模型补丁、重复提醒、无关必读清单 | 删除或缩小适用范围，再看任务结果 |
| 专题方法、复杂工具说明 | 保留明确入口，按任务读取 |
| 用户偏好、来源、业务事实 | 保留事实出处与更新方式，避免重复冲突 |
| 权限、任务状态、结果核验、错误记录 | 根据真实职责维护；不因提示词变短而一并撤掉 |

这是本文的工程建议，不是嘉宾已经实现的架构。尤其不能把 Manus 当年关于稳定工具定义的经验，机械解释为“永远不能按需发现工具”：工具暴露方式、缓存机制和模型能力会变化，具体选择仍要在实际 Harness 中测量。

### 用小规模对照，决定一条规则值不值

[待验证] 对报告生产流程，下一次可以选少量已有原材料的代表任务，比较现有配置与精简配置。固定输入、模型、工具和输出要求，每组在新会话中重复运行，改变的仅是被审查的指令；不同模型分开比较。

先看报告是否读完核心材料、有没有事实错误、能否独立阅读，再看人工介入次数、返工时间、耗时和 Token。一个更短、更快但漏掉半期播客的报告，应当判为退步。找到差异后，逐项加回必要规则或删除无效规则，比每次重新跑一套庞大的全库评估更容易解释。

这次学习任务没有运行上述对照，因此不宣布精简配置已经胜出，也不据此修改现有报告流程。

## 把好结果说清楚

“提示词又回来了”的意思，不是重新堆一套复杂操作说明。余一说，她越来越多地打磨一句能定义目标的话：做什么才算对、什么是自己要的、为什么做这件事。她愿意把实现方法交给 AI，但仍要参与评价。[^standards]

配合讲解做特效是她的例子。过去不断指导怎样加特效，效果不理想；当她改为说明“特效要服务于讲解的内容和情绪”，模型开始给出更合适、甚至超出她预想的设计。这里的变化，是把可探索的实现空间留给模型，同时给出选择依据。

[推测] 有效标准通常需要三样东西配合：明确用途、能辨认的好坏例子、实际检查结果的方式。一句话可以抓住用途，却未必足以衡量成品。就像“让报告适合人读”还需要落实为：解释术语、保留重要例子、引用可点击、事实与推断分开、没有乱码和内部审计标签堆在正文。

主持人进一步提出“人类只剩给 AI 做对齐”的判断。它可以帮助思考目标设定的重要性，但本期没有证明所有专业工作都将只剩这一项。真实业务中的责任承担、现场观察、人与人的信任和学习，仍然在后面的讨论里反复出现。

## 省下操作，保留学习

这期最容易被“全面委托”掩盖的一段，是余一主动把一些事情接了回来。

过去，她可以让 AI 写口播稿，自己照着念。现在，只要是自己出镜，她希望先把脑中的想法讲一遍，让 AI 整理成脚本，再去表达。她承认这可能更慢，效果也未必立刻更好，但这能让自己真正思考，保持判断好坏的能力。对于完全交给 AI 的内容，则接受另一种分工。[^learning]

这并不矛盾：让人一直修文件名、搬资料，通常没有多少学习价值；让人形成论点、辨认证据不足、解释为何采用某个结论，则可能正是学习任务的目的。**生产效率与学习收益不能只用同一项“节省多少时间”衡量。**

她也不再追求所有事都亲手掌握，而是希望做好长处，让擅长其他领域的人或 Agent 承接相应部分。主持人用 know who 来概括这种变化：知道该找谁合作，也是一种能力。这仍依赖对问题和结果有基本判断；否则，委托很容易变成对看起来专业的输出照单全收。

[推测] 对深度学习报告，一个实用的安排是让 Agent 完成资料整理、核验和成稿，把读者的时间留给少数真正重要的问题：哪条结论改变了原有判断？哪个反例仍解释不了？下次要观察什么，才能判断它是否成立？这也解释了为什么报告的结尾需要追问，而不只是一份完成清单。

## 招聘与社区都要回到真实作品

### 招聘：看做过什么，再观察怎样解决问题

余一没有把 AI 对初级岗位的影响概括成“还要不要招人”的简单答案。她对比了两种经验：以前需要替实习生找活；现在希望招到能发现问题、主动探索的人。筛选时先看作品和与 AI 一起做过的项目，再问如果获得工具、资源和团队支持，想实现什么。[^hiring]

她还会追问项目没开始或失败的具体原因，以及候选人是否尝试处理数据和工具问题。对合适的候选人，提供一笔产品积分和一至两天时间，让对方做出一点东西。她认为作品本身，以及解释选择、失败和改进的过程，都能提供判断依据。

[推测] 这一方法有价值，也需要避免两种偏差。不能把“花过很多 Token”当作能力代理；资源使用量可能反映预算，也可能反映低效。也不能因为模型很强，就先验认定所有失败都来自候选人。更有区分度的证据，是能否描述问题、尝试可行路线、识别局限，并解释实际交付物。

### 社区：把用户实践翻译成产品问题

她设想的社区工作包括：分享团队自身怎样使用 AI；与真实付费、做项目的用户交流；鼓励大家展示做成的东西和有用的细节；把反馈重新带回团队。她希望同时理解用户和产品，使交流不止停留在宣传层面。[^community]

这里又回到节目开头的“旁观者”问题。她感到自己的经验终于有一个能接住它的产品团队：用户遇到的问题可以影响产品，产品改变又可以让用户尝试新做法。她最后谈到的快乐，也来自人的支持，而不只是 Token 充足。

[推测] 社区若要帮助产品学习，应同时保留成功案例和失败条件。只收集漂亮成品，容易让团队误以为真实用户都能顺利完成任务。更值得持续记录的是：用户原先想做什么、卡在哪里、得到什么帮助、结果后来是否继续使用。节目谈的是工作方向与初步观察，尚未提供社区运行成效。

## Limitations：证据到哪里为止

- **主要证据是访谈自述。** 嘉宾刚入职，自己也承认处于甜蜜期；巡店系统、其他用户体验和团队表现没有独立运行记录或长期数据。
- **正片已通读，音频未逐音人工核听。** 转写有 2,562 段，时间戳与重复检查无错误；正片告别到约 1:22:32。末段歌词前有 65 秒空隙，识别内容不可靠；RSS 时长为 1:25:51，ASR 末段结束于 1:24:19。片尾音乐未补写，不用它证明内容覆盖。
- **专名以官方节目简介优先校正。** Grok Bot、Cue 等采用节目方拼法；若干转写中的人名、产品比较和模型名称仍无法可靠确定，校读稿保留不确定标记，报告不依赖它们作判断。
- **口述比例不是测评指标。** 90%/100% 委托、5% 帮助等表达使用感受；五人中三人提到值机是很小的交流样本；20 分钟响应与一至两天作品任务各有具体语境。
- **没有验证删规则后的总体收益。** 既没有嘉宾完整的对照实验结果，也没有本项目此次重跑后的实测。相关建议均标为待验证。
- **一手产品文档也有边界。** Manus 工程文章反映相应时期的团队实践；Wide Research 的性能宣传未作复现；Projects 文档的具体配置更新语义应以当前产品行为再次核实。它们不是访谈中内部实现的直接证据。

## 思考与追问

**真正理解了什么？** 一个主 Agent 的价值，在于减少用户的协调与验收负担；要做到这一点，需要明确分工、可工作的环境和可信的结果反馈。与此同时，旧指令应接受重新验证，用户需要形成判断的学习过程也应被保留。

**还有什么没有搞懂？** 第一，主 Agent 的自动验收能达到什么可靠程度，特别是生成与审核模型共享盲区时？第二，在相同任务、模型和工具下，删掉哪些规则能减少耗时而不损失事实与内容覆盖？第三，当信息源和 Bot 变多时，主 Agent 如何避免成为新的排队瓶颈，又不把筛选工作退回给用户？

**下一步读什么或做什么？** 先读下方 OpenAI 与 Manus 两篇工程原文，核对它们分别在讨论哪一层问题。若后续开展本项目优化，由承担该任务的 Agent 选择少量固定学习材料做两组对照，同时记录质量与人工介入；该实验目前挂起，未在本次学习任务中执行。上述三个问题已汇入[播客未解问题池](../wiki/open-questions.md)。
