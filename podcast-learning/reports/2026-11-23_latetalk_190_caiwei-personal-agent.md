# 蔡伟谈灵光 2.0：托管事项、服务供给与个人 Agent 的责任边界

## 概述

蔡伟将灵光的助理目标组织为持续事项：跟踪变化、判断时机、执行已允许动作。模型、运行时、产品表达、服务供给和安全授权共同决定能否办成。

“连接支付宝为何做不了全部事情”揭示第三方合作与授权约束。事项数、执行次数和早期留存描述使用现象，还未说明多少事项得到可靠管理。 [节目](https://podcast.latepost.com/190)

**提炼句：** 托付一件事，意味着它有状态、边界和结果。

## 取景框 f(x)

**x｜问题：** 把一件事长期托给个人 Agent，与收到一条提醒有什么不同？模型能理解需求之后，哪些条件仍决定它能否办成？

**f｜取景框：** 从事项生命周期看助理：目标和上下文会变，事件触发跟进，权限可能撤销，结果需要确认。对话是信息载体，事项才是管理责任的单位。

**f(x)｜判断变化：** 评价时沿创建、等待、触发、执行和结束查看状态。更强模型不能替服务方开放接口，托管数量也不能替代履约结果。

## 从信息表达开始，为什么走到了托管事项

主持人最初把变化概括为 Coding Agent 转向 Personal Agent。蔡伟认为，灵光从一开始就在做个人信息助理：用代码把信息呈现为结构化、可交互的内容，再把这种能力开放给用户创作“闪应用”。用户既做工具，也制作可以送给别人、分享给朋友的互动内容，随后形成灵光圈这一社区方向。[约 01:12—06:50](https://podcast.latepost.com/190)

这个起点很重要。写代码在这里是表达信息和交互的手段，不能仅凭底层使用 coding 能力，就认定产品一直服务专业程序员。对移动端，等待多久、屏幕是否合适、用户能否直接使用，是产品成立的条件。蔡伟提到，桌面用户可能等待几分钟，手机用户更容易离开；这些时间是他的体验判断，未提供统一的等待阈值实验。

接下来，Claude Code 给他的是完成长程任务的启发。他回忆用它安排股票关注和微信通知，背后还接入了第三方工具。OpenClaw 则让团队看到对话之外的持续跟进：在合适时候发现变化、联系用户、询问意见或执行已允许的动作。[约 06:58—14:40](https://podcast.latepost.com/190)

这个区别最终进入灵光的产品单位。蔡伟说，团队内部将持续管理的事项称为 `thread`；界面中的“帮你管”围绕一个事项组织上下文、提醒和后续动作。聊天可以是输入方式，事项则让用户看见某件事一直在被处理。[约 48:39—51:19](https://podcast.latepost.com/190)

**本文分析：** 事项需要把历史接到下一次动作。用户新增要求时更新目标，外部事件到来时更新状态，触发跟进时再检查当前允许的动作与结束条件。家庭日程、工作沟通和学习任务不能因为出现在同一段聊天里，就共用一套目标和权限。以事项呈现可以帮助用户看见这些边界，运行时是否真正维护它们仍须另验。

## “主动”需要时机判断，也需要等待和执行控制

蔡伟对好助理的描述很具体：它应了解用户，在合适时间给出有用信息，并知道哪些事要先请示。消息发多了使人烦，发少了又会漏掉应提醒的事。主动性的难点因此不是增加定时通知数量，而是判断什么变化值得打扰这个人。[约 22:30—26:24](https://podcast.latepost.com/190)

访谈描述的 Agent Runtime 需要处理几种触发：用户指定的时间、外部事件、用户状态变化。团队还要考虑工具调用、任务推进和后续反馈。它们共同决定，助手是在一次回答结束后停止，还是可以继续跟踪事项。

团队曾尝试以 OpenClaw 为基础，随后放弃这条方案。按蔡伟的解释，它们的产品目标不同：一套围绕操纵用户电脑的系统，与面向移动端、生产规模的持续个人助理，对扩展性和可控性的要求不同。访谈说这段尝试花了一两个月；这属于团队经验，不能推出 OpenClaw 普遍无法承担生产工作。[约 19:46—22:30](https://podcast.latepost.com/190)

模型能力、运行时和产品表达的配合，可以沿一个实际事项来理解：

| 环节 | 需要解决的对象 | 失败后用户看到什么 |
| --- | --- | --- |
| 理解事项 | 用户真正关心什么，哪些上下文相关 | 信息很多，却总抓错重点 |
| 持续观察 | 哪些来源和事件能更新状态 | 事项挂着，却没有跟进 |
| 时机判断 | 何时提醒、何时继续等、何时询问 | 消息过多，或漏掉关键变化 |
| 执行动作 | 哪个服务能做，是否具备授权 | 提案看起来可行，实际办不了 |
| 展示结果 | 怎样让用户看懂进度、结果和下一步 | 推送吸引人，详情却难以阅读 |

这是根据访谈重构的分析表，不是灵光公开的 API schema。节目后半段还承认，部分详情页较粗糙，用户可以提出修改，但有些人不知道自己能这样做。由此可见，模型会生成内容之后，还需要默认呈现和能力发现，不能把所有适配工作都留给用户继续提示。[约 55:45—57:40](https://podcast.latepost.com/190)

这条线也能与[有截止时间的 Personal Agent](../../ai-learning/reports/knowledge_reports/Personal_Agent_时间感与异步追问_截止时间与交付控制_深度解析_20261123.md)对照：模型可以边问边做，时钟提醒可以改善规划，但触发、回复绑定和到点交付仍由程序控制。访谈中的“有眼力劲儿”是目标；它需要可检查的机制才能落到产品里。

## 服务供给与授权，为什么决定可做的范围

蔡伟把“供给”解释为可连接的工具和服务。它与智能不同：一个模型可以理解用户需求，却没有可调用的接口；接口已经存在，也可能尚未获得商业合作方或用户的授权。

支付宝相关生态给灵光较低成本的接入起点，但用户把“连接支付宝”理解成“获得支付宝内全部服务”。蔡伟明确说，第三方服务的能力不能因为同属一个入口就默认拿来用。这让所谓部门墙成为一个更具体的问题：到底是技术未接通、合作未完成、服务方未授权，还是用户没有授予本次动作？[约 26:24—30:30、51:19—55:45](https://podcast.latepost.com/190)

这些失败的修复方式不同。换更强模型可能改善理解，不能替第三方开放能力；增加一条 MCP 连接，也不能自动建立交易责任或完整授权。蔡伟对服务逐步开放保持乐观，这是他基于合作过程的判断，不是对全行业接口覆盖率的统计。

授权还要按动作判断。访谈当时，付款必须提示用户并得到最后授权；连接邮箱、钉钉等服务，并不意味着允许助手任意使用所有私人信息。官方 shownotes 介绍了 APASS 的密钥与 Agent 分离托管、查看与撤销授权等设计。本文没有读取它的完整实现或独立安全测试，所以把这些作为产品方的机制说明，不写成已经证明不存在泄露和越权。[约 24:00—32:30及官方附录](https://podcast.latepost.com/190)

**本文分析：** 用户对一个目标的同意，至少要落到服务范围、动作类型和授权有效期。助手能读取资料，不应自然扩展为能替用户发送、购买或对外承诺。对持续事项，撤销授权还需要进入运行时：已排队但未执行的动作要怎样处理，下一次触发怎样检查新的权限，用户怎样知道已经发生的动作。这些是要验证的执行合同，访谈没有公开足够细节来回答。

在约 01:09，主持人问小商家能否直接把 MCP 接口登记到灵光。蔡伟当时回答尚未开放、正在考虑。这表明协议支持和自助接入平台是不同层次；本报告不根据那次回答判断后来是否已经开放。

## 常驻工作为何可能便宜，哪些账仍不能算

常驻个人助理不等于每一秒都用大模型推理。蔡伟解释，后台工作可以容忍较长延迟，有机会通过批处理、调度和削峰填谷提高 GPU 利用率；不同任务也可以选择不同尺寸的模型和硬件。相比要求用户在前台立即等到答案，后台任务有另一种调度空间。[约 32:30—37:40](https://podcast.latepost.com/190)

这段话回答的是成本机制，未提供可复算的完整账单。主持人引用的“每个日活用户每月四美元”等外部估计，其原始统计口径在这里尚未明确；蔡伟没有透露灵光的具体单位成本，并指出他不知道比较对象采用的产品和统计范围。因此，不能从节目得出“常驻 Agent 一定比聊天便宜多少”。

要比较这种服务，至少需要分开以下成本：

- 保留任务状态和数据的成本；
- 被时间或事件唤醒后进行模型推理的成本；
- 调用外部服务、执行工具和验证结果的成本；
- 用户要求立即响应时，为低延迟留出的计算余量。

这是本文的成本拆解。后台延迟可以放宽，不代表所有动作都能随意推迟：临近会议的资料、航班变化、付款确认各有不同期限。固定提醒、复杂研究与高风险执行也不能按消息数量简单等价。

蔡伟说底层仍采用资源池，并通过隔离提供用户级环境。由此不能把“每个用户有云主机”解释为独占一台物理服务器，也不能把资源池本身等同于不安全。需要检验的是实际数据、进程、凭据和权限边界，访谈没有提供可独立复现的隔离测试。

## 初期使用反馈支持什么，尚不能证明什么

按蔡伟的观察，用户用得好的连接常有较丰富的个人上下文：账单、办公消息、日历、邮箱和网盘。钉钉相关需求在当时连接需求中排到前三。工作与生活被放到同一个事项管理入口，有人顺势把多种场景都托管进来。[约 39:40—42:50、57:40—01:02:30](https://podcast.latepost.com/190)

这个观察支持“上下文来源影响产品能做什么”，还不能证明“收集越多越好”。信息需要与当前事项有关，还需要用户理解其用途。一个助手既可能因为缺上下文而误判，也可能因为使用了不相关或越界的上下文而造成新的错误。

访谈中的几个数据应保留原来的条件：

| 观察 | 来源与时点 | 解读边界 |
| --- | --- | --- |
| 2.0 留存超过团队预期 | 蔡伟描述上线后一周多的反馈 | 没有给出 cohort、具体留存率、样本量或长期曲线 |
| Android、鸿蒙占比上升，iOS 占比下降 | 团队当时的观察 | 蔡伟同时提出了产品更普惠与 iOS 体验较差两种可能，并未确定原因 |
| 2.0 三类平台留存相近，1.0 的 iOS 高十多个点 | 蔡伟口述比较 | 未提供同口径分群和统计方法，不能单独用来证明跨人群泛化 |
| 超过 160 万托管事项、超过 300 万执行 | 主持人引用当时已公布数据，蔡伟确认事项数是核心指标 | 托管数不等于活跃用户数，执行次数也不等于成功履约次数 |

最后一组数字位于约 01:31:56。它们不能直接相除得到人均使用量或任务成功率；事项可能被多次跟踪，同一用户也可能托管多个事项。

**本文判断：** 用事项数比只看聊天次数更接近产品主张，但还需要区分创建后闲置、持续活跃、按时完成、错误执行和用户撤销。数量增长可以反映需求与信任，也可能由推荐入口或重复创建产生。要证明实际价值，还需要看用户节省的工作、漏提醒与误提醒，以及执行失败后的负担。

## 个人 Agent 是入口，但不必让所有选择消失

蔡伟预计，个人 Agent 可能成为国民级应用，但不认为所有前台应用都应消失。有人知道要买什么，希望尽快履约；有人享受比较、浏览和选择。这些都是用户价值，不能只用减少点击次数评价。[约 37:40—48:39](https://podcast.latepost.com/190)

在他的商业模式设想中，一条线是生产力价值，用户为节省的工作付费；另一条线是连接与决策价值，可能由商家支付佣金或广告费用。采访时具体收费方式还在考虑，并非已经确定的价格计划。[约 01:02:30—01:10:16](https://podcast.latepost.com/190)

这里有一个值得继续研究的利益关系：助手替用户选择，又从商家得到收入时，推荐怎样保持对用户负责？本文认为，用户应能够识别推荐依据、付费影响与可替代选项。这是从商业激励推导的要求，不是访谈已经给出的灵光功能。

上下文积累、使用磨合和服务生态，在蔡伟看来会带来迁移成本与壁垒。他预测主流个人 Agent 不会很多，并谈到持续领先三到六个月的重要性。它们是竞争判断；访谈未提供足以计算市场集中度或确定窗口期的数据。

手机和可穿戴设备是另一条路径。它们可能拥有更多用户状态，却同时面临硬件生产、渠道、品牌和合作限制。接入手机中已有应用也不能自然消除服务方的许可与安全问题。这个领域可以有多种技术与商业路径，蔡伟没有将灵光目前的 App 形态称为唯一终点。[约 01:35:25—01:41:30](https://podcast.latepost.com/190)

## 从“帮你盯”到“帮你管”，验收条件也要改变

节目末尾，蔡伟将“盯”视为“管”的子集。盯住变化后告诉用户，主要交付是信息；进一步管理事项，还会涉及持续执行和结果责任。他用私人医生团队等例子描述理想的托付感，这是一种产品愿景，不构成灵光具备专业诊疗能力的证据。[约 01:43:07—01:51:57](https://podcast.latepost.com/190)

下一阶段，他希望托管事项再上一个数量级，并看到更多职业、城市和年龄的用户实际减少生活负担。规模目标与这些使用结果应分开观察。用户建了一千万个事项，和其中多少事项得到可靠管理，仍是不同问题。

验证一个托管事项时，可以沿它的生命周期检查：创建时目标是否明确，等待时依赖是否仍有效，触发后使用的是哪份上下文和授权，结束时交付了什么结果。保存聊天历史提供回查材料，保存这些状态才让后续工作有明确的接续位置。

持续管理仍受当前授权约束。服务或权限变化之后，后续触发需要按新状态决定是否执行；结束事项也要确认外部结果。这与[Performance Factory 的跨阶段任务记录](../../ai-learning/reports/knowledge_reports/OpenAI_Performance_Factory_性能回退调查与生产恢复_深度解析_20261123.md)形成对照：保存任务状态使工作能继续，真实结果才支持完成判断。

**资料范围：** 节目于 2026-11-23 发布，规模和留存来自上线后一周多的观察。服务、安全设计与内部统计为产品方说明，未给出完整实现或独立测试。
