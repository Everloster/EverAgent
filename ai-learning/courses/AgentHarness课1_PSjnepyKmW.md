# AgentHarness 课 1：Agent Harness 入门：一个 turn 的一生

## 场景 1：开场：新员工上岗第一天

大家好，欢迎来到今天的课程！在正式进入技术细节之前，咱们先一起想象一个画面：一位新员工，上班第一天，站在公司门口。他手里只有一个聪明的大脑，其他什么都没有。今天这节课，我们就跟着这位新员工，把 Agent 开发里最核心的一个概念彻底搞明白。  先把类比立起来：模型，也就是 LLM，就是这位刚入职的新员工。他非常聪明，什么问题都能对答如流，但他对这家公司一无所知——没有工位、没有电脑，连打印纸放在哪儿都不知道。  那 Agent Harness 是什么呢？就是公司为这位新员工准备好的一切：工位、办公用品，再加上流程制度。键盘鼠标是工具，报销审批是流程。一句话总结：模型负责思考，harness 负责让思考真正落地。  这里有一个关键分工要特别注意：新员工只会做决定。要不要领个新显示器、这份申请该不该提交，这些判断由他来拍板；但真正去领东西、去跑审批流程的，是 harness 在背后操办。请把这句话记牢，它就是我们整节课的主线。  今天这节课，我们的目标就两个：第一，彻底搞清楚 harness 到底是什么、包含哪些东西；第二，完整看清一个 turn 从生到死的全过程。前提条件是你用过 LLM API、已经理解 function calling 的报文循环——满足这两条，这节课就是为你量身定制的。准备好了吗？我们马上出发！

## 场景 2：Harness 的定义与边界

好，接下来我们进入今天的核心概念——Harness 的定义与边界。这一页是整门课的地基，把它搞清楚，后面所有的内容都会顺畅很多。  先看定义：模型权重之外的一切脚手架，都是 Harness。还记得我们的类比吗？模型就是新员工的大脑，报到那天他只带了个脑子来。那工位、电脑、办公用品、公司的流程制度，这些是谁准备的？对，全是 Harness。除了脑子，Everything else，都算 Harness。  那模型到底干什么活？说出来你可能不信，它只负责一件事——决定下一步做什么。就像新员工坐在工位上，每个 turn 都在做判断：这个任务是直接回复，还是发起一次 function calling 去调工具？决策归大脑，其他一概不管。  反过来看，Harness 的活儿就具体多了。prompt 组装，相当于帮新员工把 system 提示和任务单整理好放在桌上；工具执行，就是把电话和电脑递到他手边，真正跑 function calling 的是 Harness；上下文管理，是定期帮他清理桌面，别让历史资料堆成山把窗口塞爆；权限审批，则是涉及敏感操作时，先走一道公司流程。这四件事，一件都不是模型干的。  最后送大家一句口诀：大脑归模型，其余归 Harness。以后再分不清某件事该谁做，就用这句话一筛——需要「想」的，交给模型；剩下的执行、组装、管理、审批，全是 Harness 的活。记住这句，这一页就拿下了。

## 场景 3：Turn 上半场：从用户输入到工具调用

好，接下来我们把一个 turn 的上半场拆开看，看看从用户输入到工具调用，这一路到底发生了什么。一切从用户输入开始——比如用户说一句『帮我查一下明天的天气』，这句话一进来，harness 立刻开工了。  harness 要做的第一件事，就是组装 prompt。还记得我们的类比吗？harness 就像新员工的工位，它得给新员工备好一份『上岗资料包』。资料包里有三件材料：system 提示词，告诉新员工『你是谁、做事的规矩是什么』；对话历史，让他知道前面聊过什么；还有工具清单，相当于工位上能用的设备列表。三件齐了，prompt 才算组装完成。  接下来，harness 通过 LLM 客户端，把这份组装好的 prompt 发给模型——相当于把资料包递到新员工手里，让他开始干活。  模型看完资料，返回的往往不是最终答案，而是一个工具调用请求：要调用哪个函数、参数是什么。就像新员工举手汇报：『我需要先调天气查询工具，城市参数是北京』——你看，函数名和参数他都想好了。  但这里有个特别容易踩的坑：此刻工具还没有执行！模型返回的只是它的『想法』，真正动手去调用，是下半场的事——新员工说要打电话，不代表电话已经打出去了。好，上半场小结一下：输入进来，组装三件材料，发给模型，拿回一个工具调用请求。下半场我们就看这个请求是怎么被真正执行的。

## 场景 4：Turn 下半场：执行工具直到最终回答

上一页我们看到，turn 的上半场，模型只是递出一张 tool call 的申请单，然后它就停在那里了。那活儿谁来干？现在进入下半场——harness 接棒，一路执行工具，直到拿到最终回答。  还是新员工上岗那个类比：新员工递了申请单，公司要先审批，审批通过才真实去办事，办完把结果回传给他。他看完结果，可能又递一张新的申请单，如此往复，直到他不再需要申请，直接给出答复。下半场，就是这套办事流程的翻版。  第一步，解析参数。harness 拿到模型返回的 tool call，取出函数名和入参。注意，模型吐出来的本质上只是一段 JSON 文本——参数格式对不对、类型合不合法，都得 harness 自己校验兜底，千万别无脑信任模型。  第二步，权限审批。这是很多同学容易忽略的一关：工具不是想调就能调的。就像新员工的申请单必须先盖章——涉及删数据、发邮件、花钱这类操作，harness 必须先过权限这道门禁，通过了才放行。  第三步，真实执行。审批通过后，harness 才真正去调用这个函数，拿到结果——从头到尾动手干活的都是 harness，模型只是那个动嘴下单的新员工。第四步，把结果作为 tool message 写回 messages 上下文，相当于办事结果回传到新员工桌上，他手里的材料又厚了一沓。  接下来，harness 附上完整的工具结果，再次调用 LLM。这时就看模型的反应了：如果它说还要调工具，就回到第一步，循环再来一轮——一个 turn 里跑上好几圈是常态；如果不再调工具，模型直接生成最终回答，这个 turn 才算正式结束。所以判断一个 turn 有没有收口，就看一条：模型还发不发 tool call。到这里，turn 的完整闭环我们就讲完了。

## 场景 5：循环里的四件套

现在我们把 harness 这个工位「拆开」看看：新员工每转一圈 turn，背后其实是四位「同事」在默默接力，撑起了整个循环。这一页，我们就来逐一认识这四件套。  第一位，prompt 组装器，相当于每天早上给新员工准备晨会资料包的同事。它把 system 指令、历史对话、工具清单这几样拼成一份完整的请求——让模型一坐到工位上就清楚：我是谁、聊到哪儿了、手头有哪些工具可以用。  第二位，LLM 客户端，就是工位上的直通电话。所有和模型的通信都归它管：把组装好的请求发出去，再把模型的响应接回来。网络重试、超时处理这些琐事它全包了，模型只管专心「思考」。  第三位，工具执行器，像部门的审批窗口。模型说想调用某个工具？先过它这一关：解析参数、检查权限，审批通过之后才真正执行。function calling 能不能安全落地，就看这位同事把不把得住门了。  最后一位，上下文账本，就是新员工的工作记事本。每一步的输入输出它都如实记录，同时还要管理有限的上下文窗口——记不下了就得及时整理归档。你看，一个 turn 转下来：组装请求、呼叫模型、执行工具、记录账本，四位同事无缝接力，这就是 Agent Harness 的完整骨架。

## 场景 6：分工：大脑与手脚记事本

讲到这里，我们把模型和 Agent Harness 的分工收个口。三个问题：谁思考？谁动手？谁记事？答案就在这张图里，我们一块一块来看。  先看大脑，也就是 LLM。大脑只做决策：每一步要么发起一次 function calling，要么直接给出回答——就这两件事。就像我们说的那位新员工，他负责想“下一步该干什么”，但他自己从来不动手。  那谁动手？harness。模型说“帮我调这个工具”，真正去执行 function calling、拿到结果、再把结果喂回给模型的，是 harness。它就是公司给新员工配的工位和办公用品——电话、电脑、内部系统，跑腿的活儿全包了。  记事本，还是 harness 的活。为什么？因为 LLM 本身没有记忆——一个 turn 结束，它就把之前的事忘得干干净净。所以 harness 要把全部历史都记着：system prompt、每一轮对话、每次工具的调用和返回，每次请求都原样带给模型。就像新员工上岗第一天，总得有人帮他把“刚才老板交代了什么”记下来。  所以请记住这句话：大脑再聪明，没有手脚和记事本，也干不成事。光有一个聪明的 LLM，Agent 是跑不起来的——真正把一切串起来的，是那个默默执行、默默记账的 Agent Harness。这个“大脑＋手脚＋记事本”的分工，就是我们理解整个 Agent 的地基。

## 场景 7：为什么同一模型配不同 harness 天差地别

好，那我们回到开场留下的那个问题：同一个模型，为什么配上不同的 harness，表现会天差地别？答案其实就藏在我们一直用的那个比方里。  同一个大脑，配上不同的工位与流程，产出完全不同。新员工还是那个新员工，但如果工位乱七八糟、办公用品缺三少四、流程制度一团糟，再聪明也干不出活来。模型本身没变，变的是它周围这套环境。具体来说，一个糟糕的 harness 主要在三个地方拖后腿。  第一个，prompt 组装差。相当于给新员工的工单缺页少行——约束没带全、工具描述直接被丢掉了。你让它做 function calling，它连工具说明书都没拿到，当然只能瞎猜。模型看到的信息是残缺的，输出自然不靠谱。  第二个，报错处理粗糙。工具调用报了个错，harness 既不重试也没有兜底策略，直接把整个 turn 判了死刑。这就好比新员工第一次刷卡进门失败，公司直接让他回家——这活儿还怎么干？一次报错就断送整个 turn，太亏了。  第三个，上下文管理不当。长任务跑着跑着，历史消息越堆越多，重要的约束和中间结论被挤出 context 窗口，模型就开始失忆——前面明明说好的事，后面全忘了。就像工位上的关键单据被新文件一层层压住，要用的时候怎么翻都找不到。  所以这一页请大家记住这句话：评价一个 agent 的能力，要看模型，更要看 harness。以后看到 agent 表现拉胯，先别急着换模型，回头检查一下它的工位配得怎么样——很多时候，问题不在大脑，而在环境。

**q1. 下列关于 Agent Harness 的说法，最准确的一项是？**

- A. Harness 指的是 LLM 自身的推理与规划能力
- B. Harness 是一套用于训练和微调模型的数据管线
- C. Harness 是围绕 LLM 搭建的工程环境，负责 prompt 组装、工具执行、上下文管理与 turn 循环调度 ✅
- D. Harness 是运行在浏览器里的模型聊天界面

> 解析：C 正确：harness 的职责边界是「模型之外」的一切工程设施，即类比中的工位、办公用品和流程制度。A 错在把模型自身能力（新员工的本事）当成了 harness；B 混淆了训练侧与推理运行侧，harness 不负责训练模型；D 只描述了一种可能的 UI 形态，属于 harness 的皮而非定义。

**q2. 一个典型 agent turn 循环中，下列步骤的正确顺序是？① LLM 返回 function call 或文本回复 ② Harness 组装 prompt 与上下文并发给 LLM ③ Harness 执行被调用的工具，把结果追加进上下文 ④ LLM 基于更新后的上下文继续生成，直到给出最终回答**

- A. ① → ② → ③ → ④
- B. ② → ① → ③ → ④ ✅
- C. ② → ③ → ① → ④
- D. ③ → ② → ① → ④

> 解析：正确顺序是 B：必须先由 harness 发起请求（②），LLM 才能有响应（①）；若响应是 function call，则由 harness 执行工具并把结果回填上下文（③），LLM 再基于新上下文继续生成（④），如此往复直到最终回答。A 把响应放在请求之前，因果颠倒；C 让工具执行先于 LLM 发起调用，时序错误；D 一上来就执行工具，毫无依据。

**q3. 关于 harness 四件套的职责分工，下列说法正确的有？（多选）**

- A. system prompt 负责告诉模型「你是谁、该干什么、按什么规矩干」 ✅
- B. tools（function calling 定义）负责声明模型可调用的外部能力，但工具的实际执行者是 harness ✅
- C. 上下文管理负责决定哪些历史消息和工具结果进入下一轮 prompt，并控制 token 预算 ✅
- D. turn 循环的发起与终止由 LLM 自主控制，harness 只是被动等待

> 解析：A、B、C 均正确：system prompt 是新员工的岗位说明书，tools 定义是放在工位上的办公用品清单（模型只「点单」，harness 负责「跑腿」执行），上下文管理决定哪些工作记录留在桌上。D 错误：LLM 无法自己发起网络请求或驱动循环——每一轮调用都由 harness 发起；模型最多通过给出最终回答来「示意」可以停了，真正决定继续循环还是收工的是 harness。

**q4. 按「新员工上岗第一天」的类比，下列模型与 harness 的对应关系正确的是？**

- A. 新员工对应 harness，工位和流程制度对应 LLM
- B. 新员工对应 function calling，办公用品对应 system prompt
- C. 新员工对应上下文管理，办公用品对应 LLM
- D. 新员工对应 LLM（会思考、会干活但人生地不熟），工位、办公用品和流程制度对应 harness ✅

> 解析：D 正确：LLM 是那个聪明但「人生地不熟」的新员工——能力很强，但不知道公司规则、找不到工具、也没人推着它走流程；harness 则是它周围的一切：工位（运行环境）、办公用品（tools 等资源）和流程制度（turn 循环与规范）。A 把两者的关系完全颠倒；B、C 的对应关系属于错位搭配，混淆了各组件的角色。
