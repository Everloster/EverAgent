## 场景 1：开场与定位：从 PagedAttention 到内存管理

大家好，欢迎来到 vLLM 源码深潜的第四讲。前三讲里，我们搞清楚了 PagedAttention 怎么'切'、调度器怎么'排'；今天我们把镜头拉近一格，去看一个更底层的问题——显存管理。这一讲的主题就是：从 PagedAttention 到内存管理，vLLM 是如何在 block 层面上精打细算地用好每一块 GPU 显存的。  老规矩，先把地基夯实。PagedAttention 把每个请求的 KV cache 切成固定大小的 block，像操作系统按页管理内存那样按需分配，从根上消除了预留整段显存带来的碎片浪费；调度器则决定 prefill 和 decode 的先后顺序、batch 怎么拼。'切'和'排'这两件事，前三讲都已经解决了。  但一直有个角色躲在镜头外——block 自己。它被谁创建、被谁管理？所以本讲的主线，就是追踪一个 block 的一生。  具体是四个问题：block 从哪来、如何分配与复用？什么时候淘汰？显存放不下了又怎么办？把这四问答清楚，你就真正摸到了 vLLM 显存管理的内核。  路线图也先亮出来，五个模块，逐层深入：第一站 block pool，所有 block 的'总仓库'；第二站前缀哈希链，看 prefix caching 如何命中共享；第三站 Copy-on-Write，也就是写时复制，解决共享 block 的写入冲突；第四站 LRU 淘汰，决定谁给新数据腾位置；最后一站 KV offload，显存告急时把冷数据下放到 CPU。每一站我都会配一个生活化的类比，帮大家建立直觉。  整讲的类比基调也先立起来：vLLM 的显存，就像一座图书馆的书架；每一个 block，就是书架上的一格。接下来五个模块回答的其实就是——这一格怎么登记上架、怎么被多人共享、怎么腾空、书架满了往哪儿搬。画面感有了，我们就正式出发，先去第一站：block pool。

## 场景 2：Block Pool：物理块的分配与回收

刚才我们看完了调度器，它解决的是“谁能进 GPU 跑”的问题。那请求进来之后，KV cache 的显存到底怎么分、怎么还？这就要请出今天的核心角色——block pool，物理块池，专门负责物理块的分配与回收。  先看定义：block pool 是 vLLM 启动时预分配好的 GPU 物理块池。打个比方，就是一栋合租房：房间数在开工那天就定死了——启动时把 KV cache 显存一次性切成固定大小的块，默认每块装 16 个 token 的 KV，之后不再扩建。而住客，也就是各个请求，随住随走。  看这个池子。任意时刻，每个块只有两种状态：空闲 free，挂在空闲列表上；或者已分配 in-use。旁边的 Req A 和 Req B，各自维护一张 block table，把自己的逻辑块映射到池子里的物理块。注意一个关键点：物理块完全不要求连续——逻辑上连续、物理上散着住，这正是 PagedAttention 分页思想在工程上的落地。  第一步，分配 alloc。请求要装新 token 的 KV，就从空闲列表里取一块。节奏上是这样的：prefill 阶段按 prompt 长度一次性算好需要几块、批量领走；decode 阶段每生成一个 token 就往块里填一格，填满 16 个，再向池子要下一块。永远按需领取，不多占一间房。  第二步，释放 free。请求一生成完毕，它名下的所有块立刻归还池子，马上就能分给排队中的下一位，没有任何清理延迟。所以最下面这行收益就顺理成章了：按块、按需分配，我们不再需要为每个请求按 max_len 预留一整段连续显存。传统方案里，这种预留加上碎片，能白白浪费六到八成的 KV cache 显存；换成 block pool，浪费能压到 4% 以下。有了这个池子打底，下一页我们就能聊更有意思的玩法——块不但能借，还能共享，也就是 prefix caching。

## 场景 3：前缀哈希链：相同前缀必然相同哈希

接下来是 prefix caching 最核心的一环：系统到底怎么判断两个请求的前缀是相同的？总不能每个新请求都拿着已有的 KV 逐 token 去比对吧。vLLM 的答案就写在这个标题里——链式哈希，一句话：相同前缀，必然算出相同哈希。  先用一个直觉类比热身。想象两本书，只要开头几章的内容完全一样，那它们目录的前几行就必然一样——因为目录是对内容的摘要，前面的内容没变，摘要自然不会变。哈希链在这里扮演的就是这个'目录'的角色，而且是一章一行、逐级累积的那种。  看具体的构造规则。第 i 块的哈希 h_i，等于把前一块的哈希 h_{i-1} 和本块的 token 内容拼在一起，再做一次 hash。精妙之处在于：h_{i-1} 本身已经浓缩了前面所有块的信息，所以每一块的哈希都在逐块累积整个前缀的信息——前面任何一块变了，后面所有哈希全会跟着变。  于是推论水到渠成：只要两个请求的前缀相同，它们的哈希链就逐块一致。注意，这不是'大概率相同'，而是数学上的必然——hash 是确定性函数，相同的输入永远给出相同的输出。'前缀是否相同'这个语义判断，就这样被转化成了'哈希是否相等'。  看下面这两条请求。请求 A 和请求 B 的前三个块是共享前缀，所以从 h₁ 到 h₃，两条哈希链严丝合缝地完全重合——这一段，就是可以直接复用 KV 的部分。  到了第四块，token 内容不同了，哈希立刻分叉：h₄ᴬ 和 h₄ᴮ 各走各的，后面的后缀各自延伸，再无交集。复用的边界就是分叉点——分叉之前全部可复用，分叉之后全部不可复用，一刀切齐，清清楚楚。  这正是 vLLM 的实现：每个块算出哈希后，拿去 block pool 里查表——命中了，说明这段前缀的 KV 已经有人算过，直接复用，整段 prefill 跳过；没命中，就老老实实重算。就像图书馆的共享书架：不用翻开书逐页核对，凭书名编号一查，就知道这本书是不是已经有人放上去了。  所以这一页，就是整个 prefix caching 得以成立的数学根基：链式哈希把'前缀语义相同'的判断，压缩成了一次 O(1) 的查表操作。把这条哈希链吃透，后面我们讲 LRU 淘汰、Copy-on-Write 时，你会发现所有机制都挂在这条链上。

## 场景 4：写时复制 CoW：共享前缀块的安全写入

上一页我们看到 prefix caching 能让多个请求共享相同的前缀块，省下大量重复的 KV cache。但问题马上就来了：块是共享的，请求总要生成新 token、总要往块里写——那怎么保证请求 A 写的东西不污染请求 B？这就轮到今天的主角登场：Copy-on-Write，写时复制。  先建立一个直觉。想象合租的室友共享同一份文档：原件放在桌上大家都能看，但它是只读的。谁要修改怎么办？先去复印一份，在自己的复印件上随便改，原件永远不动。这样既省了纸，又互不影响。CoW 就是把这套合租规则搬进了 vLLM 的 block pool。  看左边第一阶段，共享阶段。请求 A 和请求 B 命中了相同前缀，都指向 Block #7。注意这个块上标着 ref = 2、只读——引用计数为 2，说明有两个请求在共用它。在 vLLM 里这是硬性规则：只要 ref 大于 1，这个块就是只读的，谁都不能直接写入，否则就会踩坏别人的 KV cache。  再看右边第二阶段，写入被触发的时刻。请求 A 要生成新 token，必须写块了，vLLM 这才动手复制：从 block pool 分配一个新块，把 Block #7 的内容拷贝过去，得到 Block #7′。请求 A 改为指向这个可写的副本，继续追加新 token；原块的 ref 从 2 减到 1，只剩请求 B 在引用。从此两边各自独占，彻底互不污染。  这里有个容易被忽略的细节：原块的 ref 减到 0，并不会立刻释放显存——它还必须被 prefix cache 命中过、确认失去复用价值之后，才会被 LRU 真正淘汰释放。整套机制的设计哲学就写在屏幕下方这句话里：共享尽可能久，复制尽可能晚。因为每一次 CoW 复制都是一份实打实的显存开销，能拖到最后一刻，就绝不提前拷。

## 场景 5：Prefix Cache 与 LRU 淘汰

刚才我们把 PagedAttention 的 block 管理和 block pool 讲清楚了，接下来看 vLLM 在这之上叠的一层关键优化——Prefix Cache 与 LRU 淘汰。这一页回答两个工程问题：前缀块怎么复用，以及显存吃紧时怎么回收。  先建立直觉。这个机制就像图书馆的共享书架：最近被人翻过的书，管理员会摆在最顺手的位置。Prefix Cache 也一样——最近被命中过的前缀块，在淘汰队列里排得越靠前，就越不容易被清理掉。  具体机制分三步。第一步，所有被缓存的前缀块进入一个 LRU 排序队列，按最近访问时间排好。注意'命中即刷新至队首'这八个字——只要某个块的前缀被新请求匹配到，它就立刻浮到队首，相当于自动续命。  第二步是真正的收益所在。新请求进来时，调度器先做前缀匹配，命中缓存的部分直接复用已有 KV，跳过对应 token 的 prefill 计算。对多轮对话、长 system prompt 这类高度重复的前缀，首 token 延迟和重复的显存占用都会显著下降——同样的 KV 不用再算一遍、也不用再存一份。  第三步回答'显存满了怎么办'。当 block pool 供不应求，就从 LRU 队列最久未用的那一端淘汰块，把显存归还给 block pool，供新请求分配复用。本质就是冷数据给热数据让位，这是缓存管理的经典套路。  最后看这条时间线把机制串起来：块 A 刚被访问，上浮到队首 MRU 端；块 B 待在中间原地不动；块 C 一直无人问津，牢牢守在淘汰端——显存一紧张，它就是第一个出局的。一句话总结这一页：命中缓存省掉 prefill，显存吃紧就按 LRU 从队尾回收，让最热的前缀始终占着最'顺手'的那块显存。下一页我们看这套机制和调度器、以及 KV offload 策略怎么联动。

**q1. 在 vLLM 的 prefix caching 实现中，一个 KV block 的哈希值由哪些输入组成？为什么相同前缀的块哈希必然相同？**

- A. 仅由当前块内的 token IDs 组成；因为相同 token 序列在同一块内出现时结果一致
- B. 由前缀块的哈希值、当前块的 token IDs（及 padding 等辅助信息）链式叠加组成；前缀相同则链上每一级输入都相同，哈希必然一致 ✅
- C. 由 request_id 和采样参数组成；因为不同请求的前缀需要隔离开
- D. 由物理块号和 GPU 显存地址组成；因为哈希需要唯一定位一块物理存储

> 解析：块哈希是链式（哈希链）构造的：第 N 块的哈希 = hash(第 N-1 块的哈希, 第 N 块的 token IDs, padding 等附加信息)。只要两个请求的前缀完全相同，链上每一级的输入逐块相同，哈希必然逐块相同，因此能在 block pool 中直接命中已缓存的 KV（图书馆共享书架：同一本书的所有人共用一个书架格子）。A 缺少前缀维度，相同 token 出现在不同上下文中会错误命中；C 引入 request_id 会破坏跨请求共享，违背 prefix caching 的初衷；D 将内容哈希与物理位置绑定，块被换位置后哈希就失效，且新分配的地址无法预先得知。

**q2. 关于 Copy-on-Write（CoW，写时复制）的触发时机与复制后的引用计数变化，下列说法正确的是？**

- A. 在 fork 发生时（如 parallel sampling 分支共享前缀块）立即复制物理块，新块引用计数置为 1
- B. fork 时只把共享块的引用计数加 1、不复制；当某个分支需要向共享块追加写入 token 时才真正分配新块，原块引用计数减 1，新块引用计数为 1 ✅
- C. 每个 decode step 结束都触发一次 CoW，保证各采样分支的数据完全隔离
- D. 触发 CoW 后，原块和新块的引用计数都加 1，由双方共同持有

> 解析：CoW 的核心是“先共享、写时才分家”：fork（分支采样共享前缀）时 scheduler 仅执行 ref_cnt += 1，物理块不复制——就像合租房分摊房租，先一起住省钱；只有当某一方要“改造房间”（append 新 token 进共享块）时，才为写方分配一块新物理块并复制旧数据，随后原块 ref_cnt -= 1，新块 ref_cnt = 1。A 错在 fork 时就复制，那样 CoW 就退化成了 eager copy，失去节省显存的意义；C 错在只读分支永远不会触发复制，与 decode step 无关；D 错在计数方向：复制恰恰是把一个共享持有拆成两个独立持有，各自计数，而不是双方共同持有两块。

**q3. 关于 LRU（最近最少使用）淘汰逻辑，下列说法正确的有？（多选）**

- A. 只淘汰引用计数为 0 的 cached 块，即没有任何正在运行的请求还在使用的块 ✅
- B. 在所有可淘汰块中，优先牺牲最近最少被访问/命中的冷块，即冷热分层、冷货先出 ✅
- C. 被淘汰的块会被标记为 free 并归还 block pool，其物理存储可重新分配给新请求使用 ✅
- D. 被淘汰块的 KV 数据会自动 swap 到 CPU 显存缓冲区，等下次前缀命中时再换回 GPU，实现零重算

> 解析：LRU 淘汰的两条硬约束：一是安全边界——只有引用计数为 0（没有在跑请求依赖）的 cached 块才可淘汰（A 对）；二是选择策略——按最近访问时间排序，优先牺牲最冷的块（B 对，类比仓库冷热分层，最久没人动的冷货先腾货架）。被淘汰块的归宿：状态从 cached 转为 free，物理块归还 block pool，等新 allocation 分配后原 KV 数据被直接覆盖丢弃（C 对）。D 是常见混淆点：LRU evict 不等于 KV offload，淘汰路径上没有“自动搬到 CPU”这回事，数据就是被丢掉的；swap 到 CPU 属于 preemption（抢占）处理被换出序列的机制，与 prefix cache 的 LRU 淘汰是两条独立路径。若想淘汰后还能零重算，需要专门的 KV offload / 二级缓存设计，而非默认 LRU 行为。

## 场景 7：KV Offload：冷块下沉到 CPU 与磁盘

刚才我们讲了 prefix caching 用 LRU 管理 GPU 上的 block pool，但有个现实问题绕不开：显存就那么大，冷前缀迟早会把 block pool 挤满，挤掉的可能正是下一个请求要用的块。KV offload 就是来解这个问题的——让冷块离开 GPU，下沉到 CPU 内存甚至磁盘。  老规矩，先建立直觉。把它想成仓库的冷热分层：常取的货放门口货架，随手就能拿到，但货架就那么几排；滞销货搬去郊区大仓，空间大、租金便宜，代价是取一趟要跑远路。KV cache 的 block 也是同一个逻辑——按被取用的频率来分层安置。  先看什么算热块。两类：一类是正被活跃请求引用的 block，这是硬约束，绝对不能搬，搬走请求直接崩；另一类是刚被 LRU 命中的前缀块，说明它们还畅销，大概率马上会被复用，留在 GPU 的 block pool 里最划算。  反过来，冷块就是那些在 LRU 队列里长期没被命中的前缀块——占着显存不干活，典型的滞销货。KV offload 的动作就是把这些块逐层下沉：先搬到 CPU 内存，再往下可以到磁盘。这一步腾出来的 GPU block，就能回去服务新请求的分配。  顺着这条分层链路自上而下看三级：GPU 显存，快而小，只放热块；CPU 内存，容量中等、延迟中等，数据走 PCIe 搬运；磁盘，大而慢，但每 GB 的成本最低。每往下一级，本质上都是在用延迟换容量。  当然，这笔交易是有代价的。CPU 内存和磁盘确实更大更便宜，可一旦某个冷块又被命中，你必须先把它搬回 GPU 才能参与 attention 计算——多走一次 PCIe，延迟比直接命中显存高一个量级。所以这一页的核心就一句话：热块留 GPU，冷块按 LRU 的冷热程度逐层下沉，本质是用重取的延迟，换缓存的容量。带着这个分层模型，我们接下来看具体的 offload 策略和参数怎么配。

## 场景 8：总结：一张图串起内存管理全链路

好，我们来到这一讲的最后一页。从 PagedAttention 的分页思想出发，我们一路讲了 block 的分配、共享、命中和换入换出。现在，用五个机制、五个类比，把整条内存管理链路串成一张图，快速收个尾。  第一个，block pool——合租房模式。显存被切成固定大小的 block，按需分房，序列结束退房即回收，房间立刻租给下一位。它带来的最大收益是把外部碎片几乎清零，vLLM 论文里 KV cache 的浪费率被压到了 4% 以内，这是整条链路的地基。  第二个，哈希链。每个 block 的身份由前缀哈希串联自己的内容哈希构成，所以目录相同，页码必然相同——prefix caching 从此有了判定依据：哈希链对得上，KV 直接复用；对不上，老老实实重算。一条哈希链，省掉的可能就是一整段 prefill 的计算。  第三个，Copy-on-Write——要改先复印。多个序列共享同一个 block 时，谁要写谁先复制一份新块，其余人继续共享旧块。在并行采样、beam search 这种一个 prompt 派生多条序列的场景里，共享安全又省钱，CoW 就是那道安全阀。  第四个，LRU 加 offload——冷热分层。热块常驻显存这个书架，冷块搬去 CPU 内存甚至磁盘这个远仓，要用时再搬回来。访问频率决定它住在哪一层，本质就是让每一兆显存都花在刀刃上。  最后是延伸方向。听懂类比只是第一步，建议大家课后对照 vLLM 源码验证今天的机制：看 block_manager 里 free list 和引用计数怎么维护，看 kv_connector 怎么把 offload 对接到真实的存储后端。源码一读，这些类比就都落地成代码了。这一讲到这里就全部结束了——按需分房、复用有据、改先复印、冷热分层，这十六个字就是今天的全部。在下课之前，我想留一个开放的问题给大家想一想。
