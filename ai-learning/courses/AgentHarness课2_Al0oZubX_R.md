# AgentHarness 课 2：Agent Harness 三大设计哲学

## 场景 1：开场：同一条街的三家餐厅

大家好，欢迎来到第 2 讲——Harness 怎么造。刚才我们已经搞清楚了 turn 循环怎么转，今天要往深处再迈一步，问一个更根本的问题：造 harness 的时候，内核到底该做多重？有趣的是，OpenAI 的 codex、deepseek-harness 和 pi，对这同一个问题给出了三种截然不同的答案——就像同一条街上，开着三家气质完全不同的餐厅。  第一家，OpenAI 的 codex，像街边的标准化连锁店：中央厨房、统一流程，从点单到出餐一条龙全配好，功能齐全——不管你走进哪家门店，吃到的都是同一个味儿。  第二家，deepseek-harness，像美食广场：水电、桌椅这些基建由广场统一提供，但每个摊位自己做自己的菜——共享基建、各摊自治，想卖什么，摊主自己说了算。  第三家，pi，像一人主理的小料亭：一张操作台、一份极简菜单，老板一个人全权负责——花哨谈不上，但想加个新菜、改个做法，转身就能动手，极简又灵活。  连锁店、美食广场、小料亭——这就是我们今天的路线图：接下来八分钟，先看清三家的真实长相，再用三个关键问题挨个对照，最后聊聊我自己的选择。请大家带着一个问题听：换作是你来造 harness，会选哪家？好，我们出发。

## 场景 2：codex：巨石哲学——中央厨房连锁店

看完前面那家店，我们来看这条街上的另一位选手——codex。它的风格完全不同，走的是'中央厨房标准化连锁'路线：统一配菜、统一流程、安全出餐，整条供应链都攥在自己手里。带着这个画面，我们来看它的五个要点。  第一个要点，巨石架构。codex 用 Rust 写了一百多个模块，最后编译成一个单一的二进制庞然大物。就像中央厨房把采购、切配、烹饪、打包全部整合在同一个屋檐下——不外包、不分散，所有环节一栋楼里搞定。  第二个要点更硬核：把安全做进内核。codex 内置了一个执行策略引擎，agent 每一步要执行的动作，都得先经过它统一审批，批准了才能放行。就像食品安全总监站在流水线旁边，每道菜出餐前都要过他这一关——安全不是贴在墙上的标语，而是长在流程里的。  第三个要点，多平台沙箱矩阵。macOS、Linux、WASM 三个平台都有对应的沙箱，装上就能安全运行。这就像连锁品牌开到哪座城市，出品都是同一个标准——不管你在哪家门店点单，安全的下限是有保障的。  当然，中央厨房不是没有代价。第四点，复杂度代价：代码体量非常大，想读懂它、想在里面改一处逻辑，都不容易。整合度高就意味着牵一发动全身，这是巨石架构要交的学费。  那它适合谁呢？追求产品级严谨、想要开箱安全感的团队——拿到手就是一个安全默认配置齐全的产品，不用自己从头搭防护。好，codex 这家'中央厨房'我们逛完了：巨石整合、内核级安全、多平台沙箱，代价是复杂度高。记住这组关键词，等会儿对比下一家店的时候，感受会更明显。

## 场景 3：deepseek-harness：插件哲学——美食广场档口

看完上一家，咱们走进这条街的第二家——deepseek-harness。它的设计哲学一句话就能说清：一切皆插件。这一页用了一个特别接地气的类比来讲它——美食广场。  大家都逛过美食广场吧？一个大空间、几十个档口，想吃啥自己挑。deepseek-harness 就不走'大而全餐厅'的路线，它做的是'广场'本身。  广场得有管理方。deepseek-harness 的核心只干两件事：统一规矩、提供地基。它自己不开火炒菜，但保证每个档口都按规范经营——水电、收银、卫生标准全给你铺好。  再来逛档口：LSP 档口管代码补全和跳转，终端档口专门跑 shell，Git 档口负责提交和 diff。每个档口只专注一道拿手菜，各显神通。这样的能力域档口一共有五十多个，全部即插即拔——想用什么能力，插上对应的能力域包就行。  这个模式最大的好处是生态灵活：今天想换个补全引擎？拔掉旧档口、插个新档口，地基完全不用动。换工具不用换地基，这就是美食广场式的自由。  但有得必有失。抽象层一多，出了问题排障就得穿过一整条插件链，一层一层往下扒，debug 的路径会明显变长。这是插件哲学必须付的账单。  所以这一页总结下来：deepseek-harness 适合想快速拼装能力、生态优先的团队——像逛美食广场一样按需取用。记住这个画面：管理方定规矩，档口各显神通。接下来咱们去看这条街的第三家，比比看谁家的路子更适合你。

## 场景 4：pi：极简哲学——一人小料亭

接下来，我们来看这条街上最特别的一家店——pi。前面聊的框架多少都带着点'大店'的气象，而 pi 走了完全相反的路线：不扩张、不堆功能，就是一家一人经营的小料亭。它的经营哲学只有一句话：内核越小，越不容易被淘汰。  先看最硬核的一点：pi 的核心 agent loop，一个文件就讲清楚了。从读入你的指令，到调用模型、执行工具、返回结果，整个循环打开一个文件从头读到尾。想看懂它的底座？不用翻整个工程，读一个文件就够了。  第二点，pi 不内置权限系统。沙箱、权限、各种扩展能力，全部外置，按需外接。就像这家小料亭不设包间、不办宴席——你要什么服务，自己带过来，店方只负责把核心那一口做到极致。  为什么坚持做得这么小？因为 pi 相信：内核越小，越长寿。你看那些一人经营的小料亭，为什么能开几十年？因为菜单短、摊子小，什么都看得见、管得住。功能越少，要维护的东西就越少，被时代淘汰的概率自然也就越低。  当然，极简是有代价的：安全和扩展，都得自己动手搭。没有现成的权限体系，没有配套的沙箱，一切都靠你自己来。所以 pi 适合的，不是追求开箱即用的用户，而是那些想彻底看懂、并完全掌控底座的工程师。这就是 pi——一家小而清醒的料亭：菜单极短，但每一道菜，你都看得明明白白。

## 场景 5：关键问题一：安全边界放哪

接下来，我们把三家 harness 放在一起对照，看看第一个关键问题：安全边界放在哪。同一个问题，codex、deepseek-harness、pi 给出了三种完全不同的答案，路线差异非常大。  先看 codex，它把安全放在内核——策略引擎和沙箱矩阵随内核一起分发，装上就自带整套安全约束，想绕都绕不开。就像我们那条街的连锁店：总部品控，所有分店的食材、流程、卫生标准全部统一锁定，店长没有自由发挥的空间。  deepseek-harness 走中间路线：安全放在插件层，权限能力域按需挂载。内核默认很轻、什么都干不了；要读写文件，挂上文件权限域；要联网，再挂网络权限域。这就像档口自检——进货验货老板自己来，灵活，但安全水平全看档口自己的功力。  pi 最彻底，干脆把安全外置——沙箱环境交给使用者自备。框架只管跑好 agent loop，隔离和资源限制你自己搭、自己负责。这就是料亭客人自慎：店主只管把菜做好，你能吃多少、生熟怎么搭，客人自己心里得有数。  所以注意，这个问题没有标准答案：取决于你信谁、信到什么程度。信框架厂商的统一管控，选 codex；信自己的组装能力，选 deepseek-harness；信使用者的判断力，选 pi。三条路线没有高下，只有信任放在哪一层的取舍。那么你自己的项目，会把信任放在哪一层呢？我们来听听大家的想法。

## 场景 6：关键问题二：扩展机制怎么做

接下来我们看关键问题二：扩展机制怎么做？说白了，就是这条街的三家餐厅，各自怎么上新菜。我们挨家看。  第一家，codex，走的是官方路线：扩展直接进代码库，由内核统一保证。类比就是连锁总部统一上新菜——每道菜都过总部品控，味道稳定可靠，但上新节奏自然由官方说了算。  第二家，deepseek-harness，做的是社区插件市场：能力域包即插即用，社区共建共享。好比美食城里各个档口自主换菜单——想要什么新风味，装个档口就行，生态的丰富度靠大家一起堆出来。  第三家，pi，主打自写扩展：极简内核之外，能力全部自由定制。就像料亭老板随心情加菜——今天想做道隐藏菜，自己动手写一个就行。自由度拉满，但菜好不好吃，得自己兜底。  所以页面底下这句话就是本页的题眼：越官方越稳，越自由越要自己负责。三条路线没有绝对的高下，选哪条，取决于你更想要确定性，还是掌控感。

## 场景 7：复杂度预算与选型直觉

好，我们来到第三个关键问题，也是最有哲学味的一个——复杂度预算投给谁？是内核、插件层，还是使用者自己？还是回到那条街上的三家餐厅，看看它们各自怎么花这笔预算。  先看第一家 codex，它像全包式餐厅：你坐下点单就好，后厨怎么炒、食材怎么管，这些复杂度全部收进内核。用户最省心，开箱即用；代价是，你想进后厨改菜谱，门槛可不低。  第二家 deepseek-harness 是美食广场：内核只出场地和水电，复杂度摊到一个个插件摊位上，每个摊主自己管自己的灶台。换来的是生态灵活，加个新摊位很快；当然，卫生水平就得看摊主自觉了。  第三家 pi 是自助厨房：店方干脆把锅碗瓢盆都交给你，复杂度整个还给使用者。换来的是内核极度精简、长寿稳定——店不折腾菜谱，你想做满汉全席还是煮泡面，全凭自己的本事。  所以选型直觉就是对号入座：重合规、要稳定交付，选 codex；拼生态、要快迭代，选 deepseek-harness；要深度掌控、做研究，选 pi。请记住一句话——复杂度不会消失，只会转移。没有最好的框架，只有和你团队哲学最合拍的那一家。

**q1. 课程用'同一条街的三家餐厅'类比三种 harness 哲学。其中'流程标准化、后厨物理隔离、上菜前层层质检'的连锁老字号，对应哪个项目的哲学？**

- A. codex——制度与沙箱优先，默认不信任 agent 运行环境 ✅
- B. deepseek-harness——工具层逐次把关，harness 承担更多责任
- C. pi——明档大排档，把边界交给使用者自己
- D. 三者只是风格偏好不同，与安全边界放法无关

> 解析：codex 的哲学是把安全做成标准化制度：OS 级 sandbox 默认只读、敏感操作需审批升级，正如老字号的'后厨隔离 + 层层质检'。B 对应'服务员替你逐单把关'的现炒餐厅（安全边界在工具层），C 对应'自己端盘子、自己负责'的大排档（边界交给使用者）。D 错在三种哲学的核心分水岭恰恰就是安全边界放在哪、复杂度花在哪，并非单纯的风格偏好。

**q2. 关于安全边界的三种放法与各自复杂度预算的投向，下列说法正确的有哪些？（多选）**

- A. codex：边界放在系统层（沙箱 + 审批升级），复杂度主要投向 sandbox 与权限分级 ✅
- B. deepseek-harness：边界放在工具层（每次工具调用先过 harness 检查），复杂度主要投向工具封装与校验逻辑 ✅
- C. pi：边界放在使用者手里（几乎不加护栏），复杂度主要投向把 agent loop 做到极简透明 ✅
- D. 三家的复杂度预算投向基本相同，都是优先堆 prompt 模板和插件系统

> 解析：三种哲学的分水岭正是'边界放哪、复杂度花哪'：codex 把预算花在系统级隔离与审批分级上；deepseek-harness 花在工具层的逐次检查与上下文工程上；pi 几乎不设边界，把预算花在单文件、零依赖的极简 loop 上。D 错误：复杂度投向恰是三家差异最大的地方，没有一家把大头花在 prompt 模板或插件系统上。

**q3. 团队画像：3 人小团队、成员全是资深工程师、维护单仓库内部工具、agent 运行环境完全可控、最看重迭代速度与 loop 透明度、反感黑盒护栏。按选型直觉，最应优先尝试哪种哲学？**

- A. codex 的制度优先哲学：先上沙箱和审批，再谈效率
- B. deepseek-harness 的工具层把关哲学：每个工具调用都过检查
- C. pi 的'边界交给使用者'哲学：极简透明，护栏最小化 ✅
- D. 先三家并行跑分对比数据后再决定

> 解析：环境完全可控 + 使用者资深 + 追求透明与迭代速度，意味着系统级与工具级边界的边际收益低、还会拖慢节奏，pi 的极简哲学最匹配。若是不可信环境、团队新人多或产出需审计，A（codex）与 B（deepseek-harness）才是更优解。D 属于过度工程：选型直觉应基于团队画像直接匹配哲学，而非先做全量对比。
