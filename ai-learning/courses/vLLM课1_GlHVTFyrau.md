## 场景 1：开场：LLM 推理服务的"显存焦虑"

各位同学，大家好，欢迎来到今天的课程。今天我们要聊一个非常现实的话题——LLM 推理服务的“显存焦虑”。如果你做过大模型部署，一定见过这样的场景：GPU 算力还剩一大半，显存却先爆了。这节课，我们就来彻底拆解这个问题，并给出工程上的解法。  先看现实困境。线上推理服务通常面对三个事实：并发用户多、GPU 显存有限，而最关键的是第三点——瓶颈往往不是“算不快”，而是“装不下”。大量显存被 KV Cache，也就是推理过程中缓存下来的历史键值对，占得满满当当，新请求挤不进来，算力就只能干耗着。  打个生活化的比方，这就像春运候车厅：乘客就是源源不断的请求，座位就是有限的显存。更糟糕的是，不少座位还被行李占着——这些行李，就是被白白浪费掉的显存。想上车的人再多，座位被占死了，整体吞吐量就是上不去。  那有没有办法把这座候车厅管得更聪明呢？答案是 vLLM——UC Berkeley 开源的高吞吐 LLM 推理引擎。它的核心武器叫 PagedAttention，一句话解释：把操作系统里的分页管理思想搬进显存管理，让每一块显存都被精打细算地用起来。同样的 GPU，能装下多得多的并发请求。  来看本课的路线图，一共四站：第一站，算清 KV Cache 的显存账单，看看显存到底被谁吃掉了；第二站，剖析传统分配方式里的浪费；第三站，讲 vLLM 的分页块管理，看看 block 机制如何把浪费压到最低；最后一站是 Prefix Caching，也就是前缀缓存复用，让重复的提问前缀直接复用，进一步省显存、提速度。好，那我们现在就出发，进入第一站：KV Cache 显存账单。

## 场景 2：KV Cache：为什么它是"显存大户"

接下来我们进入推理侧最核心的话题之一——KV Cache，也就是注意力 Key 和 Value 的缓存。很多人以为大模型推理的显存瓶颈在模型权重，其实真正的『隐形大户』往往是它。这一页，我们把它为什么吃显存讲透。  先看它是什么。大模型是自回归生成——每吐出一个 token，注意力都要回看之前全部历史。KV Cache 做的事情就是：把每一步算好的 Key 和 Value 缓存下来，免去逐 token 重算全部历史，每个新 token 只需增量计算。注意屏幕上这四个字——只增不减。缓存随生成不断累积，而且旧数据绝不能丢，丢了上下文就断档了。  给大家一个直观的类比：做长篇阅读理解时边读边记笔记。读到哪记到哪，笔记越积越厚，但你随时要翻回去查前文，所以一页都不能扔。KV Cache 就是模型的这本『笔记』——正文越长，笔记越厚，占地越大。  那这本笔记到底多能吃显存？看这张条形图，条件是 7B 模型、FP16 精度、batch = 1。上下文 2K 时，KV Cache 只有 1 GB 出头，14 GB 的权重是绝对大头；拉长到 8K，缓存膨胀到 4 GB 左右；到了 32K，KV Cache 直接反超模型权重本身。关键在于：权重是固定开销，而 KV Cache 随序列长度线性增长——拉长上下文，两条线迟早交叉。  所以这一页的结论请记牢：KV Cache 随序列长度和并发数线性增长，长文本、高并发场景下可以轻松反超模型权重。换句话说，推理的显存瓶颈往往不在权重，而在 KV Cache。把这个痛点想明白，我们才能理解 vLLM 的 PagedAttention 到底在优化什么——下一页见分晓。

## 场景 3：传统方案的浪费：预留、碎片与空闲

前面我们梳理了 KV Cache 的显存开销，它确实是推理过程中的头号显存大户。那么传统推理框架是怎么管理这些 KV Cache 的？为什么说这种方式天生就带着浪费？这一页，我们把传统方案的问题彻底拆开来看。  传统做法可以概括成三句话：每个请求一进来，就为它预留一整块连续显存；预留多大？不看实际会生成多长，而是按「最大可能长度」的上限来算；而且在请求结束之前，这块容量全程锁死，谁也动不了。就像酒店为每位客人预留一整层楼——哪怕你只住一间房，整层都归你。结果可想而知：楼层很快就订满了，后来的客人只能排队。  这种预留机制带来三大浪费。第一，内部碎片：预留按上限来，实际生成的序列往往短得多，块内多余空间从头到尾空着。第二，外部碎片：请求长短不一、来去不定，显存里留下一个个零散的空闲块，总量加起来不少，但想找一块连续大块却越来越难。第三，预留浪费：很多请求没到上限就结束了，没用完的余量却要锁到最后一刻，别的请求眼睁睁看着也用不上。  三项浪费叠在一起，就得到屏幕上这个扎心的数字：传统方案的实际显存利用率只有 20% 到 40%。换句话说，大部分显存被白白锁死。显存不够，能同时服务的请求数就上不去，batch size 受限，吞吐量自然也高不了。注意，这不是硬件不够，而是管理方式的问题。  那出路在哪里？其实操作系统几十年前就交出了答卷——虚拟内存加按需分页：用到哪、分到哪，而不是一次性占满。KV Cache 的管理能不能也照此办理？这正是 vLLM 的 PagedAttention 登场的契机。带着这个问题，我们看下一页。

## 场景 4：PagedAttention：像操作系统一样管显存

前面我们看到，KV Cache——也就是推理时缓存的 Key 和 Value 张量——是显存消耗的大头。接下来看 vLLM 的招牌设计：PagedAttention，一句话概括，就是像操作系统管理内存那样来管理显存。  先看核心思想。传统做法要为每条请求按最大长度预留一整段连续显存，就像酒店为一位客人提前预留一整层房间——人没住满，房间也只能空着，浪费巨大。PagedAttention 的做法是：把每个序列的 KV Cache 切成固定大小的 block，也就是逻辑块；物理块则按需分配、用到哪块拿哪块。这样一来，逻辑上连续、物理上离散，不再为不确定的未来买单。  这个思路的灵感直接来自操作系统的虚拟内存分页：程序以为自己在用一段连续内存，实际上数据散落在物理内存各处，全靠页表把逻辑地址和物理地址串起来。PagedAttention 里的 block table 就扮演页表的角色——每条请求一张映射表，记录每个逻辑块对应哪个物理块，而且随着 token 不断生成动态追加。注意力计算时查一下这张表，就能把离散的块拼回完整的 KV Cache。  这套机制换来什么？看这三个数字：显存碎片浪费压到 4% 以下；同样的显存能承载更高的并发请求数；端到端吞吐量直接提升 2 到 4 倍。对线上推理服务来说，这就是实打实的成本下降和容量提升。  最后对照这张表总结：传统连续分配碎片率高、显存利用率低、最大并发受限，胜在实现简单；PagedAttention 碎片率不到 4%，利用率和并发能力都大幅提升，代价是实现复杂度略高。但用一点工程复杂度换 2 到 4 倍吞吐，这笔账怎么算都划算。记住这一页的核心公式：KV Cache 分块存储，加上 block table 映射，等于显存利用率最大化。带着这个机制，我们接下来看它在工程上还能玩出什么新花样。

## 场景 5：测验一：显存账单与分页机制

好了，前面我们花了不少功夫算这笔「显存账单」，也拆解了 PagedAttention 的分页思路。现在轮到你自己上手检验一下了——测验一共三道题，都是围绕刚才讲过的内容。请先别回翻课件，凭自己当下的理解独立作答，不确定的题也大胆选出你的判断。  提交之后，我会带着你逐题复盘：答对的地方帮你把思路钉牢，答错的地方我们就当场讲透。开始吧，我在这里等你交卷。

**q1. 在不做任何优化的传统大模型推理中，KV Cache（键值缓存，为避免重复计算而缓存的注意力键值向量）的显存开销，随序列长度与并发请求数的变化规律是？**

- A. 仅与序列长度成线性关系，与并发请求数基本无关
- B. 与序列长度的平方成正比，与并发请求数线性相关
- C. 与序列长度、并发请求数均成线性关系，总开销约为单条序列开销乘以并发数 ✅
- D. 与序列长度无关，随并发请求数呈对数增长

> 解析：推理时每处理一个 token，都要为所有层缓存其对应的 K、V 向量，因此单条请求的 KV Cache 开销随序列长度线性增长；而每个并发请求各自维护一份独立的 KV Cache，所以总开销约为『单条序列开销 × 并发数』的量级。选项 A 忽略了并发数的叠加效应；选项 B 混淆了注意力计算复杂度（与序列长度平方相关）与缓存存储开销（线性）；选项 D 的两个规律均不成立。这就是为什么长序列和高并发场景下，KV Cache 会成为显存的主要账单。

**q2. 传统推理系统为每个请求按最大序列长度预留一段连续显存来存放 KV Cache（类似酒店为不确定住几天的客人整层预留房间）。下列关于由此产生的显存浪费及 PagedAttention 分块存储效果的描述，哪些是正确的？**

- A. 预留浪费：序列实际长度远小于预留上限时，大量显存被闲置，这类浪费可占总显存的 60%-80% ✅
- B. 外部碎片：反复分配与释放大小不一的连续显存块，导致空闲显存被切碎而难以复用 ✅
- C. 权重冗余：每个并发请求都会复制一份完整的模型权重，造成数 GB 级浪费
- D. PagedAttention 按 block 分块按需分配，可显著缓解预留浪费与外部碎片，但单个 block 内未填满的槽位仍会残留少量浪费 ✅

> 解析：传统连续预留方式带来两大类浪费：一是预留浪费（按最大长度预留、实际用不满，如同为短住客预留长租房间），二是外部碎片（连续大块反复分配释放后空闲显存被切碎）。vLLM 论文指出这类浪费可使 KV Cache 实际利用率仅 20%-40%，即浪费占比可达 60%-80%，故 A、B 正确。C 错误：模型权重在所有请求间全局共享一份，与并发数无关，分块存储解决的也不是权重问题。D 正确：PagedAttention 仿照操作系统虚拟内存的按需分页思想，将 KV Cache 切成固定大小 block、用到哪分到哪，消除了绝大部分预留与碎片浪费，但 block 边界处的未满槽位（类比酒店每个房间仍有空床位）造成的尾部浪费只能减小、无法归零。

**q3. 在 vLLM 的 PagedAttention 机制中，每个序列对应一张 block table（块表），其核心作用是？**

- A. 对 KV Cache 的数值做低比特量化，压缩存储体积
- B. 维护逻辑块到物理块的映射关系，使序列在逻辑上连续、在物理显存上离散分布 ✅
- C. 检测不同请求的公共前缀并自动合并为共享 block
- D. 在 GPU 显存不足时将不活跃的 block 换出到 CPU 内存

> 解析：block table 类比操作系统中的页表：序列被划分为固定大小的逻辑 block，block table 记录第 i 个逻辑块实际存放在哪个物理显存块上。注意力计算时按表寻址即可找到真实的 K、V 数据，因此 KV Cache 无需占用一段连续显存，可以像拼积木一样按需分配到显存的任意空位。选项 A 是量化技术的作用；选项 C 描述的是 Prefix Caching 的前缀复用策略，由独立的哈希匹配与引用计数机制实现，并非 block table 的职责；选项 D 是 CPU-GPU swap（换页卸载）机制的功能。

## 场景 6：Prefix Caching：会记常客的咖啡店

接下来我们看一个立竿见影的优化手段——Prefix Caching，前缀缓存。它的思路就像这家"会记常客的咖啡店"：你是老主顾，店员早就把你的基础配方背下来了，这次只需要补一句"换成燕麦奶"，绝大部分工序根本不用重做。对应到推理里就是一句话：重复的部分，不再算第二遍。  那什么样的负载最需要它？看这边——典型场景是大量请求共享同一前缀。最常见的三种：第一，系统提示词固定不变，每条请求都带着同一段 system prompt；第二，多轮对话，历史消息每一轮都原样重发，越聊越长；第三，few-shot 示例完全相同。这些重复前缀，每次都触发一遍一模一样的 prefill 预填充计算——浪费就在这里。  Prefix Caching 的机制一句话讲清：相同前缀的 KV block，直接命中缓存、复用现成结果，跳过计算。注意这里的关键词——copy-on-write，写时才复制。多个请求先逻辑上共享同一份 KV block，谁的生成阶段要真正往这个块里写内容了，才为它复制一份出来。这样既省内存，又不会互相污染，非常优雅。  我们对着下面这张图走一遍。一条 Prompt 进来，被切成一个个 block：P1、P2、P3 是前缀块，在缓存里全部命中，打勾、跳过计算；N1、N2 是新增块，只有这一小段需要真正做 prefill。所以收益直接体现在两点：TTFT，也就是首 token 延迟，显著下降；同时省去了重复的 prefill 计算，GPU 算力被腾出来服务更多请求。  落到实战，vLLM 里就是一个开关：enable_prefix_caching。如果你的业务正好是前面说的形态——system prompt 统一、多轮对话为主——打开它基本是白赚的收益；反过来，如果每条请求前缀都天差地别，缓存命中率为零，开了也不会有提升。一句话总结本页：前缀相同就复用 KV block，只算新增部分，延迟和算力双省。

## 场景 7：总结：一张图串起 vLLM 显存之道

好，我们来到这节课的最后一页。前面我们把 vLLM 的显存机制一步一步拆开了讲，现在用一张图，把整条显存之道重新串起来，顺便送大家一份可以直接落地的速查清单。  先看知识链条回顾。整节课其实就是在回答一个问题：显存到底去哪儿了？起点是 KV Cache——推理时缓存注意力键值的那块显存，它是推理显存占用的大头。接着，传统的连续分配就像酒店整层预留房间，按最大长度预留，结果预留空间大量闲置，浪费严重。于是 vLLM 拿出两招：第一招，PagedAttention，把 KV Cache 切成一个个 block 分页块，像拼乐高一样按需分配、随取随用；第二招，Prefix Caching，把多轮对话里不变的前缀缓存起来复用，就像咖啡店记住常客的配方，直接省掉重复劳动。问题、浪费、管理、复用——这条链，大家闭上眼睛也要能讲出来。  那什么场景下 vLLM 的收益最大？三个速判标准：第一，高并发 API 服务——请求多，显存块按需分配，吞吐提升最立竿见影；第二，长上下文任务——序列越长，分页管理省下的碎片浪费越可观；第三，多轮对话——Prefix Caching 让公共前缀只算一次。你的业务只要踩中其中一条，就值得认真评估 vLLM。  落地部署时，这三个参数一句话记住：gpu_memory_utilization，预留显存比例的上限，常设 0.9 左右，给系统和测量误差留点余量；max_model_len，单条请求的最大长度，直接决定 KV Cache 的容量上限，按业务实际需要设，别无脑拉满；enable_prefix_caching，多轮对话场景建议打开，前缀复用的收益马上就能看到。  最后，把这节课压缩成一句话送给大家：显存不是省出来的，是「管」出来的。省显存的本质不是抠抠搜搜，而是让每一块显存都用在刀刃上。想继续深挖的同学，课后去读 vLLM 的原始论文《Efficient Memory Management for LLM Serving with PagedAttention》和官方文档，就在这一页的延伸阅读里。感谢大家这节课的专注和投入。下课前留一个开放的问题：这种「靠管理、不靠堆资源」的思路，除了显存，还能用在你手头的哪些系统上？

**q1. 某团队在生产环境部署了一个多轮对话客服机器人，遇到两个痛点：一是 GPU 显存吃紧，KV Cache 占用大且碎片多；二是用户反馈首字延迟（TTFT）偏高。已知该机器人所有请求都携带相同的 system prompt，且多轮对话会反复携带历史上下文。以下哪种优化组合最应该优先采用？**

- A. 依赖 vLLM 默认的 PagedAttention（以 block 为单位按需分配 KV Cache 显存，像酒店按间分房而非整层预留）缓解显存压力，同时开启 Prefix Caching（复用共享前缀已算好的 KV Cache，像咖啡店记住常客配方免得重新问）来降低首字延迟 ✅
- B. 手动调小 batch size 以降低显存占用，同时彻底关闭 KV Cache，让每生成一个 token 都重新计算全部上下文，用重复计算换取显存节省
- C. 关闭 Prefix Caching，改为对每条请求独立完整重算前缀，以规避缓存复用可能带来的推理错误
- D. 增大 max_seq_len 并持续提高并发数来压榨显存利用率，首字延迟问题留待后续做模型量化时一并解决

> 解析：A 正确：显存吃紧的根源是 KV Cache 的预留浪费与碎片，PagedAttention 以 block（固定大小的显存块）为粒度管理 KV Cache，近乎零浪费，省出的显存可容纳更多并发请求，直接缓解显存压力；同时该场景满足 Prefix Caching 的适用前提——所有请求共享相同 system prompt，多轮对话还会反复携带历史上下文，缓存可命中并直接复用前缀的 KV Cache，跳过重复的 prefill 计算，显著降低首字延迟。B 错误：关闭 KV Cache 会让每个 token 的生成都重算全部上下文，延迟随序列长度急剧恶化，属于灾难性做法。C 错误：Prefix Caching 正是为共享前缀场景设计的，缓存以 block 为单位按内容哈希匹配，安全可控，主动关闭等于放弃最大优化机会。D 错误：增大并发反而加剧显存竞争，且并未触及 TTFT 偏高的根本原因（前缀被反复重算）。

**q2. 关于 vLLM 性能提升的本质与 Prefix Caching 的适用前提，以下说法正确的有哪些？（多选）**

- A. vLLM 吞吐提升的本质在于 PagedAttention 对 KV Cache 显存做近乎无浪费的精细管理（类似酒店按 block 分配房间而非整层预留），从而能在同样显存里塞下更大 batch，而不是让单次矩阵运算本身变快 ✅
- B. Prefix Caching 生效的前提是请求之间存在共享前缀（例如相同的 system prompt 或多轮对话的历史上下文）；若请求前缀互不相同，缓存命中率趋近于零，收益可忽略 ✅
- C. Prefix Caching 降低首字延迟的原理是优化了 GPU kernel 的计算效率，让 prefill 阶段的矩阵乘法跑得更快
- D. 即使所有请求的前缀完全不同，开启 Prefix Caching 也能带来显著的吞吐提升

> 解析：A 正确：这是必须辨析的本质问题——vLLM 的吞吐收益来自显存管理优化：传统方式为每条请求按最大长度预留连续 KV Cache，造成大量闲置与碎片（像整层预留房间却只住几个客人）；PagedAttention 以 block 为单位按需分配，把浪费的显存转化为可容纳的并发请求数，本质是省显存换吞吐，而非加速计算。B 正确：Prefix Caching 依赖请求间前缀的 block 级匹配命中，共享前缀（相同 system prompt、多轮历史）是前提条件，如同咖啡店记住常客配方只对常客有效，路人生意帮不上忙。C 错误：Prefix Caching 的机制是直接复用已缓存前缀的 KV Cache、跳过对这段前缀的重复 prefill 计算，属于少算而非算得快，与 kernel 计算加速无关。D 错误：与 B 直接矛盾，前缀互不相同时命中率为零，不仅无收益，还承担少量哈希计算与缓存管理的额外开销。
