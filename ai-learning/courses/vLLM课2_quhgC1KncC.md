# vLLM 课 2：vLLM 调度器入门：连续批处理

> OpenMAIC 互动课堂讲义导出（2026-09-09，共 6 场景）。配音频互动版：http://localhost:3000/classroom/quhgC1KncC

## 场景 1：static batching 为什么浪费

前面我们把 PagedAttention 讲完了，KV Cache 的显存问题算是解决了。但一个推理服务光显存管得好还不够——请求怎么排队、怎么组 batch，同样决定吞吐量。这一页我们就来看最朴素的方案 static batching：它到底浪费在哪儿？  先用一个生活类比建立直觉。static batching 就像食堂打饭窗口：要凑满一整批人才统一开餐，整批一起开始、一起结束。你先吃完了不能走，窗口也不会中途放新人进来——一切以'这一整批'为单位，中途不进不出。  由此带来第一个浪费：新请求进不了队。batch 一旦组好就开始跑，中途到达的新请求必须等当前整批全部跑完，才有机会进队。高峰期你的请求明明很短，TTFT——也就是首 token 延迟——却被前面整批的尾巴硬生生拖长。这就是为什么 static batching 的延迟表现会随负载剧烈抖动。  第二个浪费更隐蔽：短请求被迫陪跑。同一个批次里，有的请求只生成 10 个 token，有的要生成 1000 个，但整批必须步调一致地迭代。先做完的序列不能离开，要一直陪到最长的那个请求结束——就像你只要了一碗面，却得等隔壁桌吃完满汉全席才能一起起身。  结果就是屏幕上这句话：先做完的序列空占着 batch 槽位，这些槽位已经不再产出 token，但 GPU 还在为整批做计算，算力被白白闲置。一句话总结这一页：PagedAttention 管好了显存，接下来轮到调度器来管排队。怎么让做完的请求立刻退出、排队的新请求立刻补位？这正是 continuous batching 要解决的问题，我们接着往下看。

## 场景 2：continuous batching：每个 step 动态换人

刚才我们看到 static batching 的死穴：一批必须等最慢的那个请求生成完，槽位全程空转等着。解法就是这页的 continuous batching，中文叫连续批处理。核心思想一句话：每个 decoding step 结束，就重新组一次 batch，动态换人。  先用收费站建立直觉。一条车道，一辆车交完费，栏杆立刻抬起来，放下一辆车进站——车道全程不空转。continuous batching 对 GPU 的 batch 槽位做的就是这个：谁生成完了立刻走人，位置马上让给排队的请求。  看时间线上这一步。step t 时，A、B、C 三个请求在同一个 batch 里并行解码。这一步 A 率先输出了结束符——注意，A 立刻退出，一毫秒都不多占，完全不等 B 和 C。这就是和 static batching 最本质的区别：退出粒度从整批变成了单个请求。  切到 step t+1：排队中的请求 E 马上补进 A 腾出来的槽位，B 和 C 继续自己的解码。中间这个槽位交接是无缝的——GPU 每一步都是满 batch 在算，再也不存在空转的等待窗口。  支撑这一切的是调度器，它在每个 step 做三个决策：谁进——排队的新请求即时加入；谁留——没生成完的继续解码；谁出——完成的退出，空槽立即交给排队请求。补充一点，vLLM 还实现了 preemption，也就是抢占：显存吃紧时，可以把正在解码的请求先换出去，腾出资源保住其他请求。  效果就是屏幕上这行：请求即到即算、排队不积压，GPU 利用率上去了，请求时延也降下来了。同样一张卡，吞吐相比 static batching 能高出数倍。记住收费站这幅画面——每步换人、车道不空——这就是 vLLM 高吞吐的调度基石。

## 场景 3：TTFT 与吞吐的取舍

前面我们用 PagedAttention 和 KV Cache 解决了显存问题，接下来上升到调度层，看一对绕不开的矛盾。先定义第一个指标：TTFT，Time To First Token，首 token 时延——从你按下发送到第一个字蹦出来要等多久。它是用户感知等待的核心指标：用户对“第一个字什么时候出现”极其敏感，聊天框转圈三秒还没出字，你心里已经在骂这服务太卡了，哪怕后面生成得飞快。  另一端是吞吐，throughput，单位时间内整个系统完成的 token 总量。注意关键区别：它算的是所有请求加起来的总产出，不是单个请求的速度。所以这两个指标，一个管单个用户等得久不久，一个管整台机器卖了多少货——视角完全不同，矛盾就藏在这里。  矛盾具体从哪来？回忆一下每个请求的两个阶段：Prefill，预填充，是新请求刚进来，要把整个 prompt 一次性算完、生成 KV Cache，大批量、计算密集，是个重活；旁边的 Decoding，解码，是老请求拿着现成的 KV Cache 一个 token 一个 token 往外蹦，细水长流。一个是大块头，一个是慢性子，但它们抢的是同一块 GPU 的同一份算力。  问题就出在这：一个长 prompt 的 prefill 一上 GPU，瞬间就能把算力吃满。这时候正在 decoding 的老请求只能停下来干等，token 间隔被拉长；同时排在后面新进来的请求，TTFT 也跟着被一起推高——所有人都变慢了。就像食堂只有一个打饭窗口，前面来了位要打包二十份餐的师傅，窗口被占死，整条队伍一厘米都挪不动。  所以这一页的取舍本质，归结成一个问题：调度器手里的算力，是先分给刚排队的新请求去做 prefill，压低 TTFT？还是先喂给正在生成中的老请求做 decoding，保住吞吐？vLLM 的调度策略，本质上就是在这两端之间找平衡。记住这张图——下一页我们就来看，vLLM 具体是怎么切这块蛋糕的。

## 场景 4：抢占 preemption 与 KV Cache 重算的代价

前面我们看了 continuous batching 的调度过程，接下来看一个绕不开的问题——preemption，抢占。说白了就是'请某些请求让位'，而让位的代价，可能比你想象的大得多。  先看一个类比：收费站车流爆满，车道不够用了，怎么办？只能请一部分车倒退出站，重新排队、重新缴费，再通行。注意——之前排的队、缴的费，全部作废。这就是抢占的直观画面。  映射到系统里：当显存吃紧、新请求还在排队时，调度器会强制抢占优先级较低的请求，把它从 GPU 上踢下来。整个链条分四步：显存放不下、触发抢占、KV Cache 被回收、恢复时重算。我们逐步过一遍。  第一步，显存吃紧——PagedAttention 的块池里，新的 KV Cache 块申请不下来了；第二步，触发抢占，低优先级请求让位；第三步，这个请求的 KV Cache 被直接释放，或者换出（swap）到 CPU 内存。  真正的代价在第四步：被抢占的请求恢复运行时，KV Cache 已经不在了，只能把整个 prompt 从头再跑一遍 prefill。也就是说，之前那次 prefill 的算力，等于白烧了。  所以记住这条调度目标：尽量避免频繁触发抢占。换算很简单——抢占一次，约等于白算一次 prefill，这个请求的 TTFT 直接翻倍。后面讲 chunked prefill 和调度策略时，都要守住这条底线。

## 场景 5：chunked prefill：一句话直觉

上一页我们看到，长 prefill 就像一辆重型卡车，一进 batch 就把算力和显存全占了，正在 decoding 的请求只能干等。这一页，chunked prefill 的直觉，一句话就能讲清楚。  这句话就是：长提示切成小块逐步处理，不必一次占满显存和算力。大家看图上的块1、块2、块3——一条几万 token 的长 prompt，被切成固定大小的小块，一次只算一块。算完一块，中间还能把资源让出来。  生活里的类比就是大货车分批卸货。一辆大卡车横在整条车道上慢慢卸，后面的车全被堵死；改成每趟只卸几箱、卸完就把车道让出来，整条路就基本保持畅通。长 prefill 切块之后，就是这个效果。  落到系统上，第一个好处：decoding 不再被长 prefill 长时间阻塞。prefill 分块进入调度，和 decoding 穿插执行——已经在生成的请求可以持续往外吐 token，用户端就不会出现那种卡住好几秒、然后突然蹦出一大段的体验。  第二个好处，正好呼应上一页的结论：TTFT 与吞吐的取舍变得更平滑，不再二选一。块调小，decoding 更流畅；块调大，prefill 的整体吞吐更高。你可以在这个中间地带自由选平衡点。所以记住四个字：化整为零——把霸道的长 prefill 拆成乖乖排队的小块，整个系统就顺了。这就是 chunked prefill 的全部直觉。

**q1. static batching（静态批处理，一个 batch 的请求一起进、一起出）存在哪“两大浪费”？**

- A. 显存占用过高和带宽利用率低
- B. 短请求被迫陪跑等长请求（延迟浪费），已完成请求仍占着 batch 名额（吞吐浪费） ✅
- C. 模型权重加载过慢和权重冗余拷贝
- D. Tokenizer 编码开销和解码开销过大

> 解析：static batching 就像食堂拼桌：一桌人必须等吃得最慢的那位离席，整桌才能翻台。两大浪费：(1) 快的请求早已生成完毕，却要陪慢请求等到最后，白白多等（延迟浪费）；(2) 先完成的请求仍占着 slot，新请求进不来，GPU 算力空转（吞吐浪费）。A、C、D 描述的是其他类型的开销，均不是 static batching 的核心问题。

**q2. continuous batching（连续批处理）的调度粒度细化到每个 decoding step。以下哪项最准确地描述了它的“动态换人”机制？**

- A. 等整个 batch 所有请求全部生成完毕后，再一次性换入新请求
- B. 每个 iteration/step 结束时检查 batch：完成的请求立即移出并释放 KV Cache，等待队列中的请求立刻补位 ✅
- C. 按请求优先级定期对整个 batch 做全量重排
- D. 将所有请求的 prefill 与 decode 阶段强制合并为一次执行

> 解析：continuous batching 就像收费站车道：一辆车过杆后立刻放行下一辆，不必等整队车全部通过。调度器在 iteration 粒度上操作：每步检查哪些请求已生成出结束符，将其移出并释放 KV Cache blocks，同时把等待队列中的新请求（先做 prefill 再 decode）填入空位，因此 GPU 每一步都保持满负荷。A 是 static batching 的做法；C 的全量重排和 D 的阶段合并都不是它的机制。

**q3. 显存不足时，vLLM 调度器可能触发 preemption（抢占，即暂停某个运行中的请求）。若被抢占的请求通过“重算”方式恢复，其主要代价是什么？**

- A. 只需保存少量中间变量，恢复代价几乎可以忽略
- B. KV Cache 被释放，恢复时须重新执行完整 prefill，把已生成部分的所有 KV 重算一遍 ✅
- C. 只需从上次中断的 token 处继续 decode，无需任何重算
- D. 需要重新加载一遍模型权重才能继续推理

> 解析：preemption 的重算恢复方式：被抢占请求的 KV Cache blocks 被释放以腾出显存救急，请求回到等待队列；当它被重新调度时，必须从头重跑 prefill，把 prompt 加已生成部分的所有 KV 全部重算出来——相当于之前算好的 KV 全部白费，额外计算开销与请求长度成正比。（另一条路是 Swap：把 KV 换出到 CPU 内存，代价是 PCIe 搬运带宽而非重算。）A 低估了代价，C 错在 KV 依赖前面的结果、无法凭空续算，D 与抢占无关。

**q4. chunked prefill（分块预填充，将长 prompt 的 prefill 切成多个小块、分散到多个 step 执行）的核心直觉是什么？**

- A. 减少 prompt 的总 token 数，从源头节省计算量
- B. 把一次性的大块 prefill 计算拆散，与 decode 混跑，避免长 prompt 独占 GPU 造成其他请求解码卡顿 ✅
- C. 让每个请求占用的 KV Cache 变得更小，从而能同时容纳更多请求
- D. 彻底消除 prefill 阶段的计算量，只保留 decode 计算

> 解析：chunked prefill 的直觉：一条超长 prompt 的 prefill 是一笔“大额付款”，一次性付清会卡住后面所有人。把它切成小块、摊到多个 step 与 decode 混跑，虽然该请求的 TTFT（首 token 延迟）略有上升，但避免了同 batch 其他请求的 decode 被长时间阻塞，减少时延毛刺、让 TPOT（每 token 生成时间）更平稳，在时延与吞吐之间取得更好的平衡。注意它并不减少总计算量（A、D 错），也不缩小该请求 KV Cache 的最终总量（C 错，只是边算边存）。
