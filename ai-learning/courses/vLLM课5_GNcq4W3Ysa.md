# vLLM 课 5：vLLM 执行层：Forward Step 全景

> OpenMAIC 互动课堂讲义导出（2026-09-10，共 8 场景）。配音频互动版：http://localhost:3000/classroom/GNcq4W3Ysa

## 场景 1：开场：执行层在哪里

大家好，欢迎继续今天的课程。到目前为止，我们已经把 vLLM 的调度器和内存管理都拆解清楚了。接下来，我们把镜头推向离 GPU 最近的地方，回答一个新的问题：执行层到底在哪里？  先回顾一下我们刚刚讲完的调度器。每一步开始之前，调度器会做好决定：这一步要跑哪些请求、每个请求用哪些 KV block。做完这些，它交出一份执行名单。但请注意——名单只是名单，到这一刻为止，GPU 还一个数都没有算。  这就引出今天的核心问题：这份名单上的请求，如何真正在 GPU 上算完一次 forward？这就是执行层的职责。在 vLLM 源码里，它对应的是 model runner——也就是真正调用 GPU 干活的那一层。一批请求、一次前向，这就是一个 forward step。  要跑好这个 forward step，执行层要干三件事。第一，组装张量：把一批长短不一的请求拼成规整的输入，让 GPU 一次吃下。第二，选 attention 后端：FlashAttention 还是 FlashInfer，要根据场景挑最合适的。第三，加速 decode：decode 阶段每步计算量小、启动开销占比高，于是用 CUDA graph——把整步执行'录下来'，之后直接'重放'。后面我们就按这三件事逐一展开。  在展开之前，先给大家一个直觉抓手——厨房类比。组装张量，就像备菜：把食材洗好切好，摆成标准规格；选 attention 后端，就像选灶台：猛火灶还是电磁炉，看你要炒什么菜；CUDA graph 加速 decode，就像大厨把整套动作录成录像，徒弟照着一比一出菜，又快又稳。带着这幅画面，我们进入第一节：组装张量。

## 场景 2：Model Runner：把请求装进 GPU

前面我们看到，调度器把一批请求凑成了 batch，内存管理器也把 KV Cache 的块都分配好了。但这时候 GPU 还不能直接开火——还差一道关键的备菜工序，这就是 model runner 干的活：把这批请求翻译成 GPU 能直接吃的张量。  先用一个生活化的类比建立直觉：把 GPU 想成厨房里的一口大锅，每个请求就是一张订单。备菜流水线干三件事——把多个订单的食材切好、拼到同一盘子里，然后一起下锅。model runner 就是这条流水线：它把多个请求的数据拼成一大盘，让 GPU 一次性开炒。  第一步，拼 token。批内多个请求各自新产出的 token，我们把它首尾相接、拼成一条输入序列，得到的就是 input_ids 张量。注意，是「一条长序列」，不是一堆独立的短序列——GPU 喜欢一口吃一整盘。  第二步，组 position。token 刚才是硬拼在一起的，但每个 token 在自己原来的请求里，其实是有着固定位置的。所以我们要给每个 token 贴一张「序号标签」，标清楚它在原序列里的真实位置，这就是 positions 张量。少了这张标签，模型就分不清谁是谁、排在哪了。  第三步，装 KV block table。还记得前面讲的分页式 KV Cache 吗？每个请求的历史 key 和 value 是分散存放在一个个块里的。所以还要给 attention 递一张「仓储地图」——KV block table，告诉它每个请求的历史 KV 分别放在哪些块上，算注意力的时候自己去取上下文。  到这里，input_ids、positions、KV block table 三样张量备齐，模型这口锅才算真正开火。大家可以在脑子里过一遍这个厨房画面：切好、拼盘、递上菜单，锅一热就能炒。接下来我们就去看，这口锅到底是怎么炒的。

## 场景 3：Attention Backend：可插拔的灶台

前面我们把调度器和内存管理都讲清楚了——什么时候上灶、食材怎么切块存放。现在我们往前站一步，来到真正开火的地方：attention backend。这一页的类比我特别喜欢——它就是一个可插拔的灶台。  先给个准确定义：attention backend，是真正执行 attention 计算的算子库。注意，调度器只决定什么时候算，内存管理只管 KV block table 怎么组织，而真正对矩阵做乘法、算 softmax 的，是这一层。vLLM 的关键设计，是把它抽象成一个统一接口，底下的实现可以随时替换。  看这张图，我们从上往下读。最上面的调用方是 model runner，它像拿着菜谱的厨师：菜谱上只写'这道菜大火爆炒'，至于火是燃气还是电磁，它一概不操心。  中间这层，是统一的 Attention 接口——我把它叫标准火口，协议固定不变。就像家里的插座是统一规格，插台灯还是插冰箱，都不用动墙里的线。正是这一层，把底下的所有差异挡在了外面。  底下就是两台现成的灶：FlashAttention 是燃气灶，老牌、火力稳定，是目前的默认选择；FlashInfer 是电磁炉，更年轻，kernel 迭代快，对新硬件的适配常常更激进。因为火口是统一的，今天用燃气、明天换电磁，拔下来插上就行。  那为什么非要做成可插拔的？三个原因。第一，硬件代次不同：A100 和 H100 架构差异不小，各有各的适配，一口灶烧不了所有的菜。第二，算子迭代快：attention kernel 这几年一直在卷，今天的最优实现，明年可能就被超越。第三，也是最关键的——接口隔离变化：底下怎么换，上层的调度和内存管理完全无感，一行代码都不用动。  所以这一页就用一句话记住：换灶，不换菜谱。哪天出了新硬件、更强的 kernel，想让 vLLM 跑得更快，很多时候只要切一个 backend，菜谱原封不动——这就是接口抽象真正的价值。

## 场景 4：CUDA Graph：把 decode 录成录像

接下来我们看 decode 阶段的另一个关键优化——CUDA Graph。它的思路一句话就能概括：把 decode 录成录像。  先看问题出在哪。decode 每一步的动作几乎一模一样，但 CPU 却要每一步重新启动上百个小 kernel。打个比方，这就像每次做菜之前，都得把整本菜谱重新背一遍——菜还是那道菜，背菜谱的时间却每顿都要重新付一次。  这就是左边的逐步启动，也就是 Eager 模式：CPU 逐个 launch 上百个 kernel，每一次 launch 都有固定的启动开销，而且 decode 每一步都要重复支付。注意，这些开销不产生任何计算，纯粹是管理成本，步数一多就非常可观。  CUDA Graph 的做法就聪明了：既然每步动作都一样，那就把一整步的 GPU 动作提前录成一张图，相当于把做菜的全过程拍成录像。真正执行 decode 的时候，不再逐个启动，而是直接重放——一次提交、整段执行，启动开销只付一次。  不过天下没有免费的午餐：录制的时候，batch 大小这些形状必须固定下来，因为录像里每个动作都是定死的。这也解释了 vLLM 里为什么要把 batch 按档位分桶。小结一下这一页——CUDA Graph 用先录像、后重放的方式，把 decode 每步重复的 kernel 启动开销一次性消除，代价是形状必须固定。带着这个直觉，我们继续往下看。

## 场景 5：torch.compile 与 piecewise cudagraph

看完了调度器和内存管理，接下来我们聊让 model runner 真正跑得快的两件武器：torch.compile 和 piecewise cudagraph。先说 torch.compile——它做的本质事情，是把你的 PyTorch 代码编译成一份更快的执行计划。就像厨房的备菜流水线：提前把菜洗好、切好、按顺序摆好，真正开火时一路顺畅。算子被融合、调度被优化，同样的计算，执行路径短了一大截。  那是不是所有阶段都值得这样编译呢？先看 prefill。prefill 的特点是每批长短多变——这批可能两百个 token，下批三千个，形状完全动态。形状一变，精心编译好的计划就可能失效，反而要付出重新编译的代价。所以对 prefill 来说，灵活地执行每一批，才是更划算的选择。  decode 就完全是另一副面孔了。它每步只算一个 token，batch 定下来之后形状就固定了，同样的计算一遍又一遍地重复。这正是 CUDA graph 的主场——所谓 CUDA graph，就是把一整段 GPU 操作录成一盘'录像带'：录制一次，之后每一步直接重放，省掉了 CPU 反复下发指令的开销。想想我们前面讲的 KV block table 查找，每步都在做几乎一样的事，录像重放再合适不过。  但这里有个现实问题：vLLM 希望把 attention 段交给 FlashAttention、FlashInfer 这些可插拔后端，不能把整段计算一刀切录死。于是就有了 piecewise cudagraph——按段切分。形状固定的段落交给 CUDA graph 录制重放，attention 段留出来，继续走可插拔的后端。既拿到录像重放的速度，又保留了后端的灵活性。  最后用一个类比帮大家把这页钉在脑子里：乐高预拼装。piecewise cudagraph 就像拼乐高之前，把最常用的组合提前拼成一个个模块，真正创作时直接嵌进作品；而需要自由发挥的部分，保留散件随时拼。所以请记住三句话：prefill 灵活执行，decode 录像重放，attention 留给专用后端。这份直觉建立起来，后面再深入细节就容易多了。

## 场景 6：混相批的执行挑战

上一部分我们把 vLLM 的调度器和内存管理都理顺了，但真正把请求放到 GPU 上跑的时候，还有一个绕不开的矛盾——混相批。所谓混相批，就是同一个 batch 里同时装着 prefill 和 decode 两类请求：prefill 负责把整段 prompt 一次算完，decode 则一步一步往外吐 token。这两类活儿的脾气完全不同，硬塞进同一个锅里，麻烦就来了。  先看 prefill 这一边。它的特点是算得重：整段输入要一次性算完，是典型的计算密集型任务。就好比厨房里的大锅爆炒——一整锅菜全倒进去，火力全开，一次炒完。跑 prefill 的时候，GPU 的算力被吃得满满的。  再看 decode，它算得轻：每一步只算 1 个 token，真正的瓶颈不在计算，而在读写 KV cache，是访存为主的任务。这就像小火慢炖——一次只舀一小勺，大部分时间锅都在那儿等着，火力根本没开足。  矛盾就在这儿：爆炒的和慢炖的挤在同一个灶台上。prefill 一进来，算力被占满，decode 只能干等，延迟就上去了；反过来，一群 decode 占着 batch 的位置，prefill 排不进去，吞吐又下来了。两边互相拖慢，怎么排都难受。  更麻烦的还在后面——CUDA graph。可以把 CUDA graph 理解成一段录像：把一串 GPU 操作提前录下来，重放时省掉 CPU 逐条下发的开销。但录像只能原样重放，形状是固定的；而混相批每一步的形状都在变——prefill 长短不一，decode 的数量也在涨落。想用这段录像，要么把形状 padding 补齐、白白浪费算力，要么按不同形状分别录一堆图，管理成本直线上升。  vLLM 的应对是两条腿走路：一是统一调度，让 prefill 和 decode 在同一套调度框架下排队，不再各开各的灶台；二是分段图，也就是 piecewise cudagraph——只对形状稳定的段落做分段捕获，形状多变的部分照常执行。这样，录像加速的好处照拿，形状多变的麻烦绕开，吞吐与延迟两者兼顾。这一页大家记住一句话就够了：混相批是矛盾本身，统一调度加分段图就是 vLLM 的解法。

## 场景 7：小测验：执行层要点

好，执行层这一讲的内容到这里就讲完了——从 model runner 备菜组张量，到 backend 像零件一样插拔，再到 CUDA graph 的录像重放，我们一路走下来。现在轮到你自己上手检验了。  接下来是一个小测验，有单选也有多选。不用紧张，凭你刚才的理解独立作答就好，先别翻前面的内容。提交之后我会陪你逐题复盘，哪里卡住了我们一起拆开看。开始吧！

**q1. model runner 在每次前向计算前要像厨房备菜一样把张量备齐。下列哪些属于它组装输入张量时必须准备的三要素？（多选）**

- A. 输入 token IDs（要下锅的“菜”） ✅
- B. 每个 token 的位置信息 positions（每道菜的“标签”） ✅
- C. KV block table（指向 paged KV cache 分块的“货架位置图”） ✅
- D. 优化器状态与学习率

> 解析：model runner 的核心职责是把调度结果翻译成模型能吃的张量：三要素是 token IDs、positions、KV block table（记录每个序列的 KV 数据散落在哪些物理块上）。这三样备齐，模型就能像拿到备好的菜一样直接下锅。D 错误：推理阶段没有训练，不存在优化器状态和 学习率，这是训练侧的概念，与执行层无关。

**q2. vLLM 中 attention backend（如 FlashAttention、FlashInfer，即注意力计算的具体实现库）可以像换零件一样插拔替换，其根本原因是：**

- A. 只要实现统一的输入输出张量接口，不同 backend 即可互换，按硬件与场景选最优实现 ✅
- B. 所有 backend 的数值结果完全一致，没有任何精度差异
- C. 这些 backend 共享同一份 CUDA 源代码，只是名字不同
- D. vLLM 在每次请求时随机选择一个 backend，所以随时能换

> 解析：可插拔的关键是接口标准化：vLLM 定义了统一的 attention 调用协议（输入 Q/K/V 和 KV block table，输出注意力结果），任何实现该协议的库都能接入，就像厨房里备菜标准统一，换一个厨师也能直接开工。B 错误：不同实现在数值精度上确有细微差异，只是误差在可接受范围内；C 错误：它们是各自独立的库，源码并不共享；D 错误：backend 是按配置和硬件能力选择的，不是随机切换。

**q3. decode 阶段每个 token 的计算量很小，瓶颈在 CPU 逐个下发 kernel 的开销。CUDA graph（把一串 GPU 操作录成一张可整体重放的图）加速 decode 的机制是：**

- A. 一次性录制整段 kernel 启动序列，之后像录像重放一样整体一次下发，消除逐个 launch 的 CPU 开销 ✅
- B. 把多个 batch 的请求合并成一个大 kernel，增加单次计算量
- C. 通过降低浮点数精度来减少总计算量
- D. 把模型权重预先复制到 CPU 内存以加快访问

> 解析：CUDA graph 像乐高预拼装：先把一整串 kernel 的执行顺序录下来，之后一条命令整段重放，GPU 拿到的是完整指令序列，省掉了 CPU 一个个 launch 的小步慢跑。decode 每 step 只有几十个小 kernel，launch 开销占比极高，所以收益最大。B 错误：合并不是 CUDA graph 做的事；C 错误：精度与 graph 无关，计算量不变；D 错误：权重放 CPU 只会更慢，方向完全反了。

**q4. 关于 piecewise cudagraph（把模型按 attention 边界切成分段，部分捕获部分直执行的策略）下 prefill 与 decode 的分工，下列说法正确的有哪些？（多选）**

- A. prefill 阶段序列长度多变、形状不固定，整图捕获不划算，交给 torch.compile 或 eager 执行 ✅
- B. decode 阶段计算形状固定（可按预设 batch size 档位），适合用 CUDA graph 录制并重放 ✅
- C. piecewise 把模型在 attention 算子处切开，attention 段直执行，其余连续段可被捕获成图 ✅
- D. piecewise 策略要求 decode 也必须走 eager 模式，才能保证计算正确性

> 解析：piecewise 的分工逻辑：prefill 像现场处理不同尺寸的食材，形状千变万化，录制统一录像不现实，所以用 torch.compile 或 eager；decode 像标准化的预制菜，每个 step 形状固定，最适合录像重放。具体做法是以 attention 为边界切段——attention 段依赖动态的 KV block table 难以整图捕获，故直执行；其余 GEMM 等规整段则捕获成图。D 错误：恰恰相反，decode 正是 CUDA graph 的最大受益者，走 eager 会重新陷入逐个 launch 的开销。

## 场景 8：总结与回顾

好，我们来到了本讲的收尾。今天内容不少，我们用一张图把主线串起来，做个总结与回顾，帮大家把这四块拼图重新装回脑子里。  先看第一块，Model Runner，我们给它起了个外号叫「备菜」。token、position、block table，这些推理原料要在开火前一次备齐——就像厨房的备菜流水线，菜切好、调料码好，真正炒菜的时候才不会手忙脚乱。  第二块，Attention Backend，关键词是「可插拔」。FlashAttention、FlashInfer 随时换，接口不变。就像家里的插座是统一标准，什么牌子的电器都能即插即用，上层完全不用改代码。  第三块，CUDA Graph，「录像重放」。一次录制，反复重放，专治 decode 阶段每次都从头启动的开销。就像把整套做菜流程录成视频，之后照着录像一步步放就行，不用每次重新想下一步该干嘛。  第四块是今天的点睛之笔——Piecewise 策略。prefill 长度多变，就灵活执行；decode 形状固定，就走录像重放。这就是乐高式预拼装：灵活段加录像段，两边各取所长，拼出最优解。  下一讲我们讲输出处理与流式返回——模型算完 token 之后，这些结果是怎么流式地送回用户手里的。模型算完了，故事还没完，我们留了这个接口给下一讲。  好，本讲到这里就正式收束了。备菜、可插拔、录像重放、分段执行——这四块拼起来，就是 vLLM 高效推理的执行层全貌。恭喜大家坚持到最后，下课前我想留一个问题给大家。
