## 场景 1：开场：一个请求的一生

大家好，欢迎来到 vLLM 系列的第 3 讲。前两讲我们一直低着头研究单个零件，今天我们抬起头看全局——跟着一个请求，完整走一遍它在 vLLM 里的一生。  出发之前，先清点一下行李。KV Cache 帮我们缓存历史 token 的计算结果，避免重复劳动；PagedAttention 把显存像书页一样分页管理，告别碎片；continuous batching 让新请求随到随算、动态进出批次。这三块地基已经就位，今天它们会在沿途每一站默默出力。  故事的起点，是我们再熟悉不过的一行调用：客户端发来 POST /v1/chat/completions。从这扇门进来，vLLM 内部就开始了一场接力赛——请求要经过好几跳，每一跳谁负责、干什么活，就是我们今天要拆开看清楚的主线。  而故事的终点，是 token 以 SSE 的方式流式返回——SSE 就是 Server-Sent Events，服务器单向推送。模型算出一个 token 就吐回一个，用户看到的就是熟悉的打字机效果。从进门到出门，这条完整路径，就是我们今天要一起画出来的地图。  为了让大家好记，这一讲全程用一个类比：把 vLLM 想成一家餐厅。请求就是一位来点单的客人，前台、后厨、传菜员对应 vLLM 里各司其职的组件，token 呢，就是一道道陆续端上桌的菜。学完这节课，你要能独立画出请求经过的每一跳，并说清每一跳由谁负责。好，客人已经到门口了，我们从餐厅的前台开始接待。

## 场景 2：四类进程：像一家餐厅的分工

前面我们聊的都是引擎内部的算法，现在把视角拉高一层，看看 vLLM 在系统层面是怎么组织的。这一页我们用一家餐厅来打比方——四类进程，就像餐厅里的四个角色，各司其职，配合默契。  第一位是餐厅前台，对应 API Server 进程。它负责接收 HTTP 请求、做鉴权——也就是验证来访者身份，最后把生成结果组装成流式响应，一个 token 一个 token 地端给客户端。注意，前台只管接待，它不进厨房。  第二位是大堂经理，对应 DP 协调。DP 就是 Data Parallelism，数据并行。当后厨不止一个的时候，它负责把请求合理地分派到多个数据并行的后厨，让负载尽量均衡——就像大堂经理把客人安排到合适的那一桌。  第三位是后厨本厨，EngineCore 进程，整个系统最核心的角色。它只专注两件事：调度和 GPU 计算，也就是跑 forward 前向传播和 sample 采样。我们前面学过的 PagedAttention、continuous batching，都是在这口锅里炒菜的。  最后一位是传菜员，也就是输出处理。GPU 算出来的其实只是一串 token 编号，要经过 detokenize——反 tokenize，把 token 还原成人类可读的文本，再端给客户端。菜炒好了，总得有人端上桌，对吧？  那为什么要拆成四个独立进程，而不是一个大进程全包了？关键就在最后这句话：互不阻塞。前台被慢请求堵住，后厨照样炒菜；后厨在跑 forward，传菜员照样出餐。任何一环变慢，都不会拖垮其他环节——这就是进程级隔离带来的稳定性和吞吐。好，这张餐厅分工图请大家记牢，接下来我们看这些进程之间具体是怎么通信协作的。

## 场景 3：请求的八跳旅程

刚才我们看清了 vLLM 的两个进程是怎么分工的，现在让我们跟着一个请求，完整走一遍它的旅程。一个请求从 HTTP 进来，到最后以 SSE 流式返回出去，中间要经过八个关键跳点——我把它叫做「请求的八跳旅程」。  整条链路可以想象成一家餐厅：前台接单、备料，传送带把订单递进后厨，后厨开火烹饪，最后传菜员一道一道上菜。对应到 vLLM：前台就是 ApiEngine 进程，后厨就是 EngineCore 进程，中间靠 ZMQ 这条传送带连接。  先看前台，也就是 ApiEngine 进程，它负责前四跳。第一跳，HTTP 接收，把客户端的请求接住；第二跳，解析参数，读出你要点哪道「菜」——也就是模型名，还有 temperature、top_p 这些采样参数；第三跳，tokenize，把对话文本切成 token id 序列——记住，模型只认数字，不认文字，所以这一步是备料的关键。  第四跳是一条关键的分界线：ZMQ 队列。ApiEngine 和 EngineCore 是两个完全独立的进程，彼此不共享内存，所有请求都要靠这条「跨进程传送带」递进后厨。理解了这一步，前面架构图里那条进程边界就落到实处了。  订单进了后厨，就轮到 EngineCore 进程了。第五跳，调度成批——后厨把多张订单凑成一锅 batch，一起塞进显存，这正是我们前面讲过的 continuous batching 在干活；第六跳，GPU forward，正式开火烹饪，算出 logits。  第七跳，采样：从 logits 里挑出概率合适的下一个 token。到这里，这道「菜」就算炒出了第一口。  第八跳，流式返回：detokenize 把 token 还原成文字，再通过 SSE 逐 token 推给客户端——就像传菜员一道一道上菜。之后每 forward 一次、采样一次、吐一个字，循环往复，直到生成结束。记住这条流水线：HTTP 进、SSE 出，前台备料、后厨烹饪。接下来，我们就逐段把这八跳拆开看细节。

## 场景 4：EngineCore 内部：三线程流水线

上一页我们看到 vLLM v1 把 EngineCore 拆成了独立进程，那这个进程的盖子打开之后，里面到底跑着什么？答案很紧凑：三条线程，组成一条流水线。我们一条一条来看。  第一条是输入线程。它的职责非常单一：通过 ZMQ——一种高性能的进程间消息通道——接收外部发来的请求，同时也接收取消信号，比如客户端主动断开连接。收到之后，它只做一件事：把请求放进等待队列，绝不恋战。为什么？因为收消息是 I/O 操作，速度慢、不可控，如果让主线程亲自去等，GPU 就得跟着干等，所以必须外包出去。  第二条是调度主线程，整个 EngineCore 的大脑。它跑在一个 busy loop 里——所谓忙轮询，就是不睡眠、不挂起，CPU 一直占着，醒来就干三件事：调度、拼 batch、发起 forward 和采样。大家之前学过 continuous batching，每一步动态拼接 batch 的逻辑，就发生在这条线程里。这里有个明确的取舍：牺牲一点 CPU 占用，换来迭代之间零切换延迟——GPU 一停，它马上就能喂上下一批任务。  第三条是输出线程。每一步 forward 产出的 token，由它写回 ZMQ，交给外面的输出处理进程去做 detokenize 和流式返回。关键在于它和主循环完全解耦：哪怕输出这一侧再慢，也绝对不会反过来卡住 GPU 的主循环。  最后用一个后厨的类比把三条线串起来：输入线程是收单员，只管接单挂单；调度主线程是掌勺的主厨，一心扑在灶台上翻锅炒菜；输出线程是出菜口，把做好的菜端出去。三个人各管一段，谁也不用等谁。这就是三线程流水线化的价值——GPU 这口灶，尽量一刻都不空转。记住这张图，下一页我们接着看它的上层结构。

## 场景 5：为什么 execute 和 sample 拆成两相

前面我们把 EngineCore 的主循环过了一遍，现在来回答一个架构设计上的关键问题：为什么 vLLM 要把 execute 和 sample 拆成两个独立的相？这个拆分不是随手为之，背后是吞吐和灵活性的双重考虑。  先看 execute 相。在这一相里，forward 会把整个 batch 的所有请求一次性做完前向计算，统一产出 logits——也就是每个位置上、下一个 token 的概率分布。关键词是「整批」：所有请求一起算，GPU 算力一次性吃满，不存在谁等谁的问题。  然后才进入 sample 相。采样这一步，按的是每个请求各自的采样参数——比如这条请求用 temperature 0.7 加 top-p 0.9，那条请求用 top-k 50，各玩各的。但注意，这些差异全部发生在 logits 已经算完之后，采样彼此独立、互不干扰。  那拆开到底赚在哪？我们看这三条收益。第一，forward 整批计算，吞吐最大化，GPU 不会因为请求之间的差异而闲置。第二，采样参数再怎么五花八门，也不拖累主循环——采样只是 logits 之上一个轻量的独立步骤，跟计算彻底解耦。第三条最工程化：两相分离让 CUDA Graph 的捕获变简单了，计算阶段的输入输出形状规整统一，异步调度也更好实现。  最后用餐厅打个比方：后厨不管每桌的口味，先把菜全部炒好——这就是 forward；传菜员再按每桌要求撒调料，要辣的加辣、不吃香菜的挑出来——这就是 sample。炒菜和调味分开，后厨的锅才永远不会停。所以记住这个设计要点：execute 管整批算，sample 管各取所需，计算与采样解耦，吞吐和灵活性就都有了。

## 场景 6：为什么 detokenize 在另一个进程

接下来我们回答一个非常实际的架构问题：vLLM 为什么要把 detokenize——也就是把 token id 还原成人类可读文本的这一步——放到另一个进程里去做，而不是直接在 EngineCore 里顺手完成？这个设计其实藏着很深的性能考量。  第一个原因来自工作本身的性质。detokenize 看起来只是字符串处理，但它其实是实打实的 CPU 密集型工作。而 EngineCore 进程里的主循环是忙轮询——busy polling，也就是不眠不休地转圈，一有新请求就立刻组装 batch 喂给 GPU。如果把字符串处理塞进这个主循环，就相当于在灶台旁边放了一台碎肉机：CPU 被占住了，忙轮询的节奏立刻被打乱，喂 GPU 的速度也就跟着慢下来。  所以 vLLM 的选择是：让 EngineCore 进程保持极度纯粹，只做 forward 和 sample——forward 是神经网络的前向计算，sample 是从概率分布里采样出下一个 token。忙轮询主循环只干这一件事：组装 batch、喂 GPU、收结果、再喂，绝不分心。GPU 越忙，吞吐越高，这是大前提。  那 detokenize 的活儿谁来干？交给一个独立的 Detokenizer 进程。它做的是增量 detokenize：每来一个新的 token id，就立刻还原成一小段文本发下去。注意'增量'这两个字是关键——流式输出场景下，每生成一个 token 都要马上变成文字推给用户，这条路径必须快，而且绝不能被别的计算阻塞，不然用户看到的打字机效果就会一卡一卡。  那两个进程之间怎么配合？靠 ZMQ——一个轻量级的消息队列库，在这里起解耦作用。EngineCore 只要把采样出的 token ids，一串整数序列，往'墙那边'一扔，就回头继续算；Detokenizer 在另一头接住，慢慢还原成文本。计算和文本处理各跑各的事件循环，互不干扰，谁慢了都不拖累谁。  最后用餐厅的类比把这件事钉牢：EngineCore 就是掌勺大厨，必须连续开火，一心只管炒菜，也就是计算；Detokenizer 就是专门的传菜员，负责摆盘、上菜，也就是把 token ids 变成漂亮的文本端给用户。大家想想，如果大厨炒完每个菜还得自己摆盘跑堂，那火肯定断。有了分工，再加上 ZMQ 这个'传菜口'，整个后厨才能全速运转。这一页记住一句话就够了：CPU 密集的 detokenize 搬出主循环，EngineCore 专心喂 GPU，Detokenizer 增量还原、ZMQ 解耦，流式输出才又快又稳。理解了这个分工，后面看输出链路的全景图就水到渠成了。

## 场景 8：知识测验：请求的一生

好了，刚才我们跟着一个 chat 请求走完了它的完整旅程——从 ApiServer 进门，到最后一个字流式送回客户端。现在轮到你自己来检验一下这条链路在脑子里是不是真的串起来了。接下来是一个小测验，题目涉及我们刚才讲的进程分工和请求流转，请独立完成，不要回头看讲义。  别紧张，做错也完全没关系——先凭自己的理解选出答案，提交之后我会陪你逐题复盘，把没吃透的地方讲透。开始吧，我在这儿等你。

**q1. 在 vLLM v1 架构中，一个 chat 请求从客户端发出到收到首个流式回复，依次经历的关键环节顺序是哪个？（tokenize 指把文本切成 token id，detokenize 指把 token id 还原成文本，forward 指模型前向计算）**

- A. ApiServer 收 HTTP → EngineCore 调度+GPU forward/sample → 前端 tokenize → Detokenizer 还原文本 → 前端流式返回
- B. ApiServer 收 HTTP → Detokenizer 先做预处理 → EngineCore 调度+GPU forward/sample → 前端 tokenize → 前端流式返回
- C. ApiServer 收 HTTP → 前端 tokenize → EngineCore 调度+GPU forward/sample → Detokenizer 还原文本 → 前端流式返回 ✅
- D. ApiServer 收 HTTP → 前端 tokenize → Detokenizer 先还原文本 → EngineCore 调度+GPU forward/sample → 前端流式返回

> 解析：正确顺序是 C：模型只消费 token id，所以 tokenize 必须在请求进入 EngineCore 之前由前端完成；EngineCore 内先由 scheduler 组 batch，再驱动 GPU 执行 forward 和 sample；产出的 token id 经 ZMQ 交给 Detokenizer 增量还原成文本，最后由前端以流式方式发回客户端。A 颠倒了因果（先计算后 tokenize 说 不通）；B 把 Detokenizer 当成了入口预处理，它只处理输出不处理输入；D 让『还原文本』发生在生成之前，同样是因果颠倒。

**q2. 关于 vLLM v1 中四类进程（ApiServer、前端 AsyncLLM、EngineCore、Detokenizer）的职责边界，下列说法正确的有哪些？**

- A. ApiServer 负责承接 HTTP/OpenAI 兼容请求并交给前端处理，最终的流式应答也从这条 HTTP 连接写出 ✅
- B. tokenize（把 prompt 切成 token id）由 EngineCore 完成，因为它离 GPU 最近、最了解词表
- C. EngineCore 负责 scheduler 组 batch，并驱动 GPU 执行 forward 和 sample ✅
- D. Detokenizer 负责把生成的 token id 增量还原成文本，属于纯 CPU 工作 ✅

> 解析：A 对：ApiServer 相当于餐厅前台接待，负责收 OpenAI 兼容请求并把结果流式写回；B 错：tokenize 在前端 AsyncLLM 完成，EngineCore 从头到尾只见到 token id，从不接触原始字符串，这正是为了让它专注 GPU 调度与计算；C 对：EngineCore 是后厨，负责 scheduler 组 batch、驱动 forward 与 sample；D 对：Detokenizer 是传菜员，做的是 token id 到文本的增量还原，全程不碰 GPU。

**q3. 关于 EngineCore 内部的多线程分工（execute/sample 拆分）与输出处理独立进程的动机，下列说法正确的有哪些？**

- A. execute 与 sample 拆到不同线程，是因为采样必须独占 GPU 串行执行，拆线程可以提升显存利用率
- B. execute/sample 拆分的动机是：CPU 侧的采样处理可以与下一步的调度和准备重叠，缩短每步整体耗时 ✅
- C. 只要 GPU 算力足够强，把 tokenize、detokenize 全部塞进 EngineCore 也不会影响吞吐
- D. 输出处理独立成 Detokenizer 进程，是因为 detokenize 纯靠 CPU 且耗时随并发请求数线性增长，混在 EngineCore 里会拖慢 GPU 主循环 ✅

> 解析：B 对：sample 阶段常伴随复杂采样参数、结构化输出等 CPU 处理，拆出去可以与 forward 及下一轮调度重叠——后厨继续炒下一道菜，装盘不挡灶台；A 错：拆分的动机是时间重叠，与『独占 GPU』『显存利用率』无关；D 对：detokenize 是纯 CPU 工作且随并发数线性增长，若混在 EngineCore 主循环里会让 GPU 空转等待，所以独立成进程让 EngineCore 专注喂饱 GPU；C 错：吞吐瓶颈往往在 CPU 侧，GPU 再强也架不住引擎循环被 CPU 活阻塞。
