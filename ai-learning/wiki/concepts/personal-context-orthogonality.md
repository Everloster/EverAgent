# Personal Context 正交论：积累如何适应模型变化

> 维护日期：2026-10-29 · 原论证：[Personal Context 正交论与构建指南](../../reports/knowledge_reports/PersonalContext正交论_PC构建指南_20261010.md)

## 这个观点在问什么

模型和工具不断变化，哪些积累仍值得保留？Personal Context 的思路是，把偏好、事实、来源和做事经验整理成可更新、可按需取用的资料，减少每次从头解释。

“正交”在这里是一个讨论视角，**不是数学结论，也不是价值必然上升的规律**。模型升级可能提高这些资料的用途，但前提是信息仍然有效、与任务有关、能被正确读取，并且使用方式获得授权。这是一项条件性互补假说 `[推测]`。

## 事实与经验，都需要维护

原报告用身份、事实、关系、程序、委托五个维度整理 Personal Context。它们适合帮助分类，不能直接充当“价值高低”或“贬值速度”的排序：

| 维度 | 例子 | 怎样避免过时或误用 |
| --- | --- | --- |
| 身份与偏好 | 阅读习惯、表达偏好 | 区分长期偏好与临时要求，允许用户更正 |
| 事实与知识 | 研究结论、决策记录、实验结果 | 带来源、时间与适用范围；过去成立不代表现在仍成立 |
| 关系与协作 | 项目参与方、职责与约定 | 按用途和权限共享，关系变化时更新 |
| 程序与经验 | 操作顺序、排错方法、Skill | 区分领域经验与特定模型补丁，用后续任务检验是否仍有帮助 |
| 委托与授权 | 可以自主完成的动作、需要确认的事项 | 以当前授权为准；积累信任不会自动扩大权限 |

[OpenAI 的指令工程观察](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)说明某些旧步骤可能过度约束新模型；[IBM 的 ALTK-Evolve 实验](https://huggingface.co/blog/ibm-research/altk-evolve-bc)则说明，从轨迹提炼的程序性规则仍能改善特定任务。两者并不矛盾：需要检查的是一条信息在什么条件下有用，而不只是它属于“事实”还是“技巧”。

## 分清保存了什么、这次读了什么

以下是结合[三层 Context 研究](../../reports/knowledge_reports/个人Context与Memory三层架构_OpenViking_手机环境_APP跨对话_深度解析_20261025.md)与[上下文失效研究](../../reports/knowledge_reports/Context_Engineering_失败修复与战略性遗忘_深度解析_20261027.md)采用的工程区分：

| 对象 | 作用 | 例子 |
| --- | --- | --- |
| 原始来源 | 支持回查和重新判断 | 原文、对话、实验输出 |
| 长期 Memory | 保存跨任务可用的信息，包括显式记忆与提炼的经验 | 带适用范围和来源的偏好、事实或操作规则 |
| 索引 | 帮助找到资料，不替代来源 | 目录、关键词、摘要、向量索引 |
| 当前模型输入 | 支持这一步判断，可按需裁剪和重建 | 最新要求、相关材料、必要历史与工具说明 |
| 任务运行状态 | 记录工作进度与真实执行结果 | 待办、已生成文件、checkpoint、操作回执、结果未知的请求 |

例如，报告保存了旧论文的一项结论；新论文出现反例后，概念页应更新，原报告仍可作为历史论证回查，检索结果也应指出更正。下一次任务只需读取相关新旧证据，不必重新输入所有研究对话。

这也是本仓报告、Wiki 和问题池的分工：报告保留完整分析，Wiki 提炼当前理解，问题池记录尚未解决的部分。来源路径和内容校验值有助于追溯，不能单独证明内容正确。

## 多设备、手机与 APP，各自提供什么

[三层研究报告](../../reports/knowledge_reports/个人Context与Memory三层架构_OpenViking_手机环境_APP跨对话_深度解析_20261025.md)区分了三个视角：OpenViking 组织可检索的资料与 Memory；手机提供屏幕、应用等当下环境信息；APP 从对话形成跨会话记忆。手机的一次观察不能直接变成稳定画像，APP 的记忆能力也不能证明它拥有手机全局信息。

[OpenViking session 文档](https://docs.openviking.ai/en/concepts/08-session)描述了消息归档与后台记忆处理。`accepted` 表示受理，所需资料是否可读、后台处理是否完成还要分别检查。文档中的归档能力不能证明它保存了其他 Agent CLI 的完整运行现场。

**[推测] 多设备、多 Agent 可以共用有来源、版本和权限的资料，各自组装工作上下文；任务进度仍由运行系统负责。** 原生 Session 按对应框架恢复；换 Harness 时，则交接最新要求、决定、证据、产物和未完成事项，让新会话继续同一个目标。详见 [Manus 与会话续接报告](../../reports/knowledge_reports/多设备多Agent共享Context与会话续接_Manus实践与架构边界_深度解析_20261029.md)。

## 更正、遗忘与删除

这三件事需要分别处理 `[推测：工程建议]`：

- **更正**：旧结论被推翻时，更新维护该事实的文件，并检查摘要、索引和副本是否仍把旧内容当作当前事实。
- **裁剪或重建上下文**：让模型暂时不读某段历史，仍需保留必要证据、用户约束和未完成操作的真实状态。
- **删除个人信息**：按用户要求处理原始记录及其派生记忆、索引、缓存和副本；仅从本轮输入移除不算完成删除。

依据见[上下文失效报告 §7](../../reports/knowledge_reports/Context_Engineering_失败修复与战略性遗忘_深度解析_20261027.md)。公开知识可以保留更正历史，私人信息的保存与删除仍须遵守其授权范围。

## 还没有证明什么

本仓这组研究还没有证明“积累越多，任务越好”，也没有完成跨设备接班的端到端收益验证。检索命中、文件同步成功、报告通过复核，各自不能替代任务结果。

后续值得观察的具体问题是：新要求能否覆盖旧偏好，接班者能否读取真实产物，结果未知的操作是否会被重复执行，以及节省的工作量能否抵消整理、检索与交接成本。已有分析与待验证部分见[问题池](../open-questions.md)。
