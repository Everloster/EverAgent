# ThinkingBox：把数据库终态评分器变成 RL 奖励——Agent 后训练的可执行奖励链拆解

> **一句话结论**：ThinkingBox 团队的核心洞察是「**数据库终态检查器不是评分器，而是奖励函数**」——先用 507 个有状态业务工作流任务证明「agent 声称完成 ≠ 数据库真的对」，再把同一套**可执行终态判定**搬到一个**与基准完全不相交**的 187 任务训练池上，用 GRPO 训练 Qwen3.8-27B，50 步后 **pass@1 51.70%→60.78%、「20 次全对」的任务数 38→107（2.8×）、每条可靠任务成本 $24.36→$8.00（−67.2%）**；但训练池选择靠**训练前一次性探测的 policy-relative 难度**（训练中不再重探）、20 次评测中“至少成功一次”的任务数由 453 降到 446（观察到的覆盖略降，可能含采样波动）、**成本表明确不含训练成本**，且**可执行奖励只验证可观测状态，不等于真实业务目标**。

> **阅读边界**：本文以 Hugging Face / Microsoft 联合博客《Turning Database Grading into RL Rewards: Post-Training Agents with ThinkingBox》为主线，实际读取一手材料：arXiv:2608.19741 摘要、`microsoft/thinkingbox-training` 仓库 README、`trainer/core/tb_interpret.py`、`docs/data-preparation.md`，以及第一篇博客《The Agent Said It Was Done. The Database Disagreed.》。**未运行训练、未复现评测**；所有性能与成本数字均为项目方自报。

## 1. 问题定义：从「评分器」到「奖励函数」的那一步

### 1.1 第一步：证明「完成声明」不是「完成」

ThinkingBox-Bench 的每个任务给 agent 一个**真实后端**（数据库后端服务）、一组 **MCP 工具**和一个**带私有上下文的模拟 LLM 用户**；任务结束时，评测只检查**数据库里实际留下了什么**。

第一篇博客给出的典型失败：模型把客户工单标记为 **resolved**，但**背后的承运商异常仍然开着** —— 「九次看起来很专业的工具调用，一行错误的数据库记录」。

这条设计的要点是：

- **判据是「需要正确的那条后端记录」，不是「特定的工具调用序列」** → 鼓励模型**发现新的解法路径**，而不是复现人写的、可能次优但正确的解；
- **错误、缺失、多余的副作用都算失败**（extra effects 也罚）；
- 因此**响应级或工具调用级信号并不是端到端完成度的可靠代理**（论文原话：许多失败试验呈现「干净的终止 + 合法的状态变更动作」）。

### 1.2 第二步：把评分器读成奖励函数

博客的原话是这篇工作的转折点：

> 「我们注意到我们造出来的东西。对大多数任务而言，**一个可执行检查可以直接从最终数据库状态返回 1 或 0**。这不只是评分器。**这可以是奖励函数。**」

于是工作分成两段、**用两个不相交的任务集**：

| 阶段 | 任务集 | 用途 |
|---|---|---|
| 评测 | ThinkingBox-Bench 的 **507** 个任务 | 密封基准，**不参与训练** |
| 训练 | ThinkingBox 格式但**在基准之外**的 **187** 个任务 | 用同形态的可执行终态判定作为 reward |

### 1.3 第三步（真正难的那步）：选哪些任务能教

博客点出关键约束：**大多数任务要么已经学会、要么完全做不到，两者都教不了任何东西**。并给出一句可迁移的原则：

> 「**难度是策略相关的：一个任务对当前模型是难的，只到这个模型学会它为止。**」

他们称之为 **offline policy-relative difficulty（离线策略相对难度）**：用**基座策略**一次性估计每个候选任务的成功率，并**在整个训练过程中固定这个训练池**（图 5 的虚线琥珀箭头标出的是「我们没有走的那条路」：在训练中重新探测难度）。

## 2. ThinkingBox 三件套与任务/环境/奖励/数据流

### 2.1 组件

| 组件 | 仓库 / 位置 | 作用 |
|---|---|---|
| 环境框架 | `microsoft/thinkingbox` | 沙箱：隔离的 MCP 兼容工具会话、完整执行轨迹、终态后端状态评估；含 Typesense 与 MCP Session Proxy |
| 基准数据 | `microsoft/thinkingbox-data`（HF 数据集 `microsoft/ThinkingBox-Bench`） | 507 个策略条件工作流；域包括零售、酒店/旅行、汽车保险、neobank 内部 IT、咨询 IT/HR 支持 |
| 训练栈 | `microsoft/thinkingbox-training` | 数据选择、rollout、奖励、与 **VeRL** 的集成 |
| 论文 | arXiv:2608.19741《One Success Isn't Reliability: Thinkingbox, a Sandbox and Benchmark for Agents in Stateful Business Workflows》 | 方法与基准 |
| 评测框架 | OpenEnv（`thinkingbox-eval`） | 507 × 20 的完整评测协议 |

许可：代码 MIT；基准数据 CDLA-Permissive-2.0。**基准里每个任务都是合成重建**（工作流与政策参照真实企业 agent 模式，**客户不是真实的**）。

### 2.2 六阶段数据流（博客图 5 / 图 7 的文字化）

```
① 候选任务（ThinkingBox 格式，来自授权数据源）
        │
        ▼
② 可解性筛查：GPT-5.4 作为 solvability screen
        │  （Qwen3.8-27B 全参训练池使用；更强参考模型可选）
        ▼
③ 基座策略探针：对 base policy 重复跑 n 次 → 成功 k 次
        │  （每次 rollout 都是完整 episode：新后端 + 隔离 MCP 会话
        │   + GPT-5 Chat 扮演的模拟用户）
        ▼
④ 难度分桶：success_probability | k in n ~ Beta(k+½, n−k+½)
        │  取后验质量最大的桶；边界 0.08 / 0.40 / 0.60 / 0.90
        │  [0,0.08) 丢  [0.08,0.40) 留  [0.40,0.60) 留
        │  [0.60,0.90) 留（仅全参 RLFT）  [0.90,1] 丢
        ▼
⑤ 固定训练池（Qwen3.8-27B 全参池 = 187 个任务）
        │  全程不再重探；与 507 基准不相交
        ▼
⑥ 训练循环（每个 group 重复）：
        rollout group（18 groups × 8 rollouts = 144 episodes）
            → episode 结束：沙箱提取后端真实变更 → 确定性检查
            → reward ∈ {0,1}
            → GRPO 更新（token-mean；零方差组按 DAPO 替换；系统错误组 refill）
        ▼
⑦ 用合并后的 checkpoint 独立评测 507 × 20 = 10,140 次尝试
```

### 2.3 为什么 GRPO 需要「混合组」

博客用一条算术事实解释了整篇工作的设计动机：

- 8 个 rollout 全失败 → 奖励向量 `[0,0,0,0,0,0,0,0]`；全成功 → `[1,1,1,1,1,1,1,1]`；
- **两种情况下组内中心化都不产生任务奖励优势**（没有哪条轨迹比另一条更好）→ **零梯度**；
- 混合组如 `[0,0,0,1,1,1,1,1]` 才提供 GRPO 能学习的对比。

**代价是昂贵的**：对有状态 agent，每个 rollout 都要**供给一个隔离后端、跑一次真实工具会话、并额外调用一个模型扮演用户**。博客脚注给出了标准补救（过采样、丢弃退化组、refill，类似 DAPO），但明确指出：**refill 仍然要为每个被丢弃的 rollout 全额付费**。

### 2.4 一个任务走完全程（官方示例）

- 基座探针 **3/8 成功** → 后验 **Beta(3.5, 5.5)**，最大质量 **54.0%** 落在 **Difficult** 桶 → 保留；
- 训练采样时该任务产生奖励组 **`[0,0,0,0,1,1,1,1]`** → 成功轨迹获得高于均值的任务优势，失败轨迹低于均值 → GRPO 有对比可学；
- 论文与文档都强调：**换一个策略模型，同一个任务可能落进不同的难度桶**。

## 3. 评分器与奖励函数拆解

### 3.1 两条奖励路径

| 路径 | 占比（官方定性） | 判定方式 | 风险 |
|---|---|---|---|
| **可执行检查** | 「绝大多数」 | 从终态数据库状态与副作用做**确定性测试**：接受或拒绝 | 只覆盖「可被状态观测到的」需求 |
| **判定辅助检查** | 「少数」 | 当某条**狭窄要求无法从数据库状态干净判定**时，由配置的 **LLM judge** 回答一个**二元 rubric 问题**，再由可执行测试使用该答案 | 引入模型偏差；judge 比例未量化 |

### 3.2 奖励函数的精确定义

- **奖励 = 任务的终态判定**，**与轨迹无关**：「Nothing about the trajectory. The reward is the task's own executable verdict.」
- episode 结束时：沙箱**提取后端实际变更了什么**，对该任务运行确定性检查；
- **任何产生正确终态的轨迹都通过**；**错误、缺失或多余的副作用都失败**；
- **奖励是 1 或 0**（二值），没有部分分。

> **这与「奖励塑形」的做法形成鲜明对比**：他们的奖励**不做加性塑形**，而是「让 GRPO 自己从组内对比里学出偏好」。[分析者推导]

### 3.3 两条奖励路径与「模拟用户」的角色分离

README 明确：「**模拟用户是独立的环境角色，不给 agent 打分。**」即：模拟用户（GPT-5 Chat）只负责扮演真实用户制造多轮交互；打分由可执行检查（少数情况由 judge）承担。

### 3.4 一个具体的可迁移样本（博客图 2）

一个企业酒店预订任务：**旅客要求降级房间，但公司政策要求先获得经理批准**。

- 训练前：base Qwen3.8-27B 在 **20 次尝试中有 15 次**未经批准就改了预订并发了退款；
- 训练后：RL 微调模型在 **20 次全部**保持了预订与支付状态；**19 次**所有期望记录匹配。

> 这是全文最能说明「可执行奖励学到的是**政策约束**而非仅仅『把字段改对』」的例子——因为『未批准就退款』在数据库里同样能形成自洽的终态，只是与期望终态不符。

## 4. 关键数字表（含口径）

### 4.1 训练前后（Qwen3.8-27B，50 步 GRPO）

| 指标 | Base | RL 微调 | 变化 | 口径 |
|---|---|---|---|---|
| **Observed 20/20** | **38（7.50%）** | **107（21.10%）** | **+69 个任务** | 「20 次记录尝试**全部**通过」的任务数；第一篇博客明确「**No estimator, no smoothing**」 |
| **pass@1** | 5,242（51.70%） | 6,163（60.78%） | +9.08 pt | 10,140 次尝试中的成功比例（507 任务 × 20 次） |
| **pass@20** | 453（89.35%） | 446（87.97%） | **−7 个任务** | 「20 次里至少一次通过」的任务数；本轮观察到的 breadth 略降，不能仅凭 20 次试验断言真实支持面永久收缩 |

> **命名陷阱（重要）**：这里有两个方向相反的指标：`pass@20` 是「**20 次里至少成功一次**」，论文的 `pass^20` 与博客的 **Observed 20/20** 是「**20 次全部成功**」。`@` 与上标 `^` 只差一个符号，含义却相反；引用时最好直接写“至少一次”或“20/20 全部通过”。

**读表要点**：

1. **两个指标给出不同排序**：GPT-5.6 Sol 的 pass@1（61.91%）高于 RLFT 的 27B（60.78%），但 20/20 只有 82 < 107；Claude Sonnet 4.6 的 pass@1 更低（59.19%）却 20/20 几乎持平（102）。

3. **第一篇博客的更大样本**：18 个模型、每个 20 次；Kimi-K3 覆盖最广（至少一次 93.89% = 476/507），但 20/20 只有 68（13.41%）。
4. **27B 追近前沿**：RLFT 后 20/20 从 38→107「几乎是三倍」，在成本维度接近 GPT-5.4 / GPT-6 Astra / Claude Opus 5.5。

| 指标 | Base | RL 微调 | 变化 |
|---|---|---|---|
| 20 次全campaign 估算成本 | $925.80 | $855.58 | −7.6% |
| **每次成功尝试成本** | $0.177 | **$0.139** | −21.4% |

### 4.4 训练配置

| 项 | 值 |
|---|---|
| 模型 | Qwen3.8-27B（**全参数** RL 微调） |
| 训练任务池 | **187** 个任务（离线按 policy-relative 难度选出） |
| 算法 | **token-mean GRPO**（VeRL 0.9.0，**打了补丁的 checkout**） |
| 每步 rollout 量 | **18 groups × 8 rollouts = 144 episodes** |
| 硬件 | **24 × H100**（3 节点 × 8 卡），同步训练，参数与优化器 offload |
| 优化器 | **AdamW，lr 1e-6，weight decay 0** |
| 步数 | **50 步** |
| 退化组处理 | 零方差组按 **DAPO** 方式替换（带 refill） |
| 系统错误处理 | **后端超时不等于 agent 错误** → 受影响组**refill**，不计为失败 |
| 评测 | 507 任务 × 20 次（10,140 attempts），合并 checkpoint 后用 **vLLM 8×A100、TP=8、max-model-len 262144** 服务 |

### 4.5 难度分桶

| 桶 | 后验区间 | 处置 |
|---|---|---|
| Rarely solved | [0, 0.08) | 丢 |
| Difficult | [0.08, 0.40) | 留 |
| Intermediate | [0.40, 0.60) | 留 |
| Frequently solved | [0.60, 0.90) | **留（仅全参 RLFT）** |
| Nearly always solved | [0.90, 1] | 丢 |

边界 0.08 / 0.40 / 0.60 / 0.90 是**为本次运行选定的超参**（非普适阈值）。

## 5. 代码与配置证据

### 5.1 `trainer/core/tb_interpret.py`：训练与评测的「解释一致性」

文件头注释即是一份方法说明（读原文）：

- 评测 campaign 的 vLLM 端点用**自己的解析器**解释每次生成（`--reasoning-parser qwen3 --tool-call-parser qwen3_xml`），并在**harness 看到调用之前**把解析出的 XML 参数按请求的工具 schema **定型**；
- **VeRL 自带这两步的独立重实现**；使用它们会让**训练时的对话与基座被测时的对话产生分歧** → 本模块复现服务端解释：
  1. 去特殊 token 反 tokenize；
  2. 从 content 中切出 reasoning（vLLM `qwen3` reasoning parser）；
  3. 从剩余 content 中抽取 tool call（vLLM `qwen3_xml`）；
  4. **把 string 类型的 XML 参数强制转成 JSON schema 类型**；
- 注释给出的原因：**XML 线格式无法承载 JSON 类型**（引用 QwenLM/Qwen3.6#187），所以第 4 步是「让带类型的工具能被调用」的关键；
- 代码里 `coerce_arguments` 的行为：声明为 string 的参数不动、未知参数透传、转换失败则保留原始字符串「以便工具自己的校验去报错」。

> **这是全文最可迁移的工程纪律之一**：**训练时对模型输出的解释，必须与评测时逐字节一致**；否则「奖励衡量的」与「评测衡量的」不是同一个 agent。

### 5.2 `docs/data-preparation.md`：数据契约与防污染机制

- **数据加载器契约**：trainer 接受运行时的 `module:function` 加载器，公共框架已提供严格选择器水合 `thinkingbox.common.hydrator.iter_cases_by_names`；
- **公开样本任务表**：`data/examples/training_tasks.example.yaml` 含 **39** 个可运行选择器，来自 5 个公开开发文件（`airline_tau_bench.py`、`banking.py`、`banking_email.py`、`email_system_org.py`、`mcs_defaults.py`）；
- **数据版本锁定**：该列表 pin 在公开数据 revision `49eacaa530b07177d99acd1d0570ee117d43a20b`，且**其选择器均不出现在 507 任务的 canonical 列表中**；`banking.py` 中另一个函数被上游标记 `skip`，因严格水合会拒绝 skipped case 而被排除；
- **`data/prepare_data.py`**：聚合策略探针 → 用 **Jeffreys 后验**做 policy-relative 难度分类 → 可选启用**更强参考模型的可解性闸门** → **排除基准 UID** → 产出选择或 train/test 划分；
- **输出必须写在仓库之外**（防止把私有池混进公共仓库）。

### 5.3 README 与运行栈

- 环境：**Linux / Python 3.12 / uv**；需要 NVIDIA GPU 与兼容 CUDA/NCCL、本地模型 checkpoint、ThinkingBox 服务、以及**模拟用户与 judge 的 OpenAI 兼容端点**；

## 6. Reward hacking 与污染评估

### 6.1 污染控制（做了什么）

| 机制 | 具体做法 | 出处 |
|---|---|---|
| **基准不进训练** | 「**没有任何 ThinkingBox-Bench 任务进入 RL 训练池**」；用 UID 排除机制（`--exclude-uids`、`exclusion_uids.example.yaml`） | 博客 + data-preparation.md |
| **OOD 声明** | 507 任务的**域、数据库、策略与多数 MCP 工具**在训练中未出现 | 博客 |
| **训练池固定** | 一次性用基座策略探针估计难度，**训练全程不再重探** | 博客（图 5 明示这是「我们没有走的那条路」） |
| **可选参考模型闸门** | 更强模型（GPT-5.4）做可解性筛查 | 博客 + prepare_data.py |
| **公开/私有分离** | 公开样本表（39 任务）仅用于验证接口，**不是**报告所用的 187 任务池 | README + 博客 |
| **评测与训练解释一致** | `tb_interpret.py` 复现评测端解析链路 | 代码 |

### 6.2 污染无法排除的部分（原文自陈）

博客明确写：训练池与基准**共享 ThinkingBox 框架、模拟用户机制、可执行终态评分、部分通用工具与相似任务风格** → **「这些共享元素限制了转移声明的范围」**。

此外：
- **合成数据**：所有基准任务都是合成重建，**客户不是真实的**；
- **模拟用户是 GPT-5 Chat**，judge 也是模型 → 分布与真实用户/真实评审有偏；
- **同域工具与同域后端类型**（虽然任务与数据库不同）仍可能让「工具使用模式」提前泄漏。

### 6.3 Reward hacking 风险清单

| 风险 | 机制 | 原文证据 / 评估 |
|---|---|---|
| **终态正确但过程虚假** | 奖励只看终态记录，不看轨迹 → 直接写终态而不做业务动作也可能得 1 | 原文明确「奖励与轨迹无关」；**这是本设计最核心的 hacking 面**。缓解：博客例子显示「未批准就退款」这类「自洽但违规」的终态会被判失败，因为期望终态包含政策约束 |
| **额外副作用** | 多写一行、多改一列都算失败 | 原文：「错误、缺失或多余的副作用都失败」→ 对 hacking 是**正向**约束 |
| **判据可被绕过**（测试集污染式 hacking） | 若训练任务与评测任务共享同一套检查脚本与数据库 schema，模型可能学会「针对检查器优化」 | 官方通过任务不相交 + UID 排除缓解；但**检查器代码与 schema 家族相同** → [推测] 残留风险 |
| **judge 偏差** | 少数任务的二元 rubric 由 LLM judge 判定 → 模型可学会「迎合 judge 口味」 | 原文只说「少数」，**未量化比例、未报告 judge 与人工的一致率** → 明确空白 |
| **奖励稀疏与零方差** | 全 0 / 全 1 组无梯度 | 缓解：难度分桶 + DAPO 替换 + refill；**代价是 refill 仍要为丢弃的 rollout 全额付费** |
| **策略漂移导致难度带失效** | 难度是**相对 base policy** 估计的；训练 50 步后策略已变，训练池的「中等难度」分布不再成立 | 原文拒绝在训练中重探 → **这是有意选择（成本 vs 分布新鲜度）的权衡**，也是可质疑之处 |
| **可执行 reward ≠ 真实目标** | 终态检查验证「可观测状态」，不验证沟通质量、客户体验、长期后果、政策判断的合理性 | 论文与博客均未主张等价；**必须由使用方自行承担这层差距** |

### 6.4 一个重要的「不可混淆」：可执行 ≠ 真实

论文的核心论断之一是：**许多失败试验「终止干净、状态变更动作合法」，说明响应级/工具调用级信号不是端到端完成度的清晰代理**。这条论断**只说明「弱信号不可靠」**，**不说明「可执行信号就等于真实目标」**。可执行信号验证的是**「你留下的记录是否等于期望记录」**，而真实目标常常还包括「是否做了必要的沟通」「是否在正确时机升级」「是否留下人类可接受的过程」。

## 7. 替代路线比较（6 条）

| 路线 | 相对「可执行终态奖励 + GRPO」的取舍 | 边界 |
|---|---|---|
| **A. 静态单测 / 状态断言**（传统 CI） | 零训练成本、完全确定性、可审计；覆盖面窄、只测已知行为 | 对**开放性业务工作流**几乎无效；ThinkingBox 正是为补这块而生 |
| **B. LLM judge（纯文本评审）** | 成本低、可评「解释质量」等不可执行维度 | 与 agent 自评偏差、与可执行判定不同源；本文只用它覆盖「数据库判不干净」的少数窄要求 |
| **C. RLVR（可验证奖励强化学习）** | ThinkingBox 属于这一族的**领域化实例**：把领域执行器接进 RL | 通用 RLVR 的 verifier 多为「答案对不对」；本文的 verifier 是**有状态数据库终态**，难度更高、价值也更高 |
| **D. GRPO / PPO 等优化器选择** | GRPO 无需 critic、组内对比即可；PPO 需要价值模型 | 本文用 **token-mean GRPO + DAPO 零方差替换**；**未与 PPO / 其他优化器做对照** |
| **E. 离线轨迹蒸馏（拒绝采样 + SFT）** | 成本远低（无需 rollout 基础设施）、稳定；只能模仿**已有成功轨迹**，不探索新解法，且继承 base policy 的覆盖 | 本文数据选择其实**就是拒绝采样的思想**（探针 = 采样），但换成 GRPO 后能利用**失败与成功的对比**；两者的差别正是「是否需要在线探索」 |
| **F. 提示/工程侧优化（少调用、共享前缀、规则前置）** | 见本仓 Cloudflare 成本报告：改代码与路由往往比改训练便宜 | 与 RL 正交：先做工程优化，再考虑后训练 |

**一条选型判断**：[分析者推导]

```
若任务是「有明确终态、可自动判定、且当前策略在一半以上尝试里会成功」
   → 可执行奖励 + GRPO 的收益最大（因为组内天然产生混合奖励）
若任务的成功率长期为 0 或 1
   → 先改 prompt / 工具 / 规则（工程侧），或换更强策略模型；RL 无梯度可学
若判据本身无法写成确定性检查
   → 只能退到 judge 或人工，把「可执行部分」与「不可执行部分」分开建模
```

## 8. 对 EverAgent 的最小迁移实验与 eval

### 8.1 最值得迁移的不是「训练」，而是「判据设计」

EverAgent 的 report-v2 流程**已经有大量机器可判定的检查**（`scripts/report_quality.py check`、`scripts/audit_reports.py`、`git diff --check`、evidence schema 校验）。这些正是「**可执行终态检查**」的现成实例——但目前它们**只用于判定通过/不通过，没有被用作奖励**。

### 8.2 最小迁移实验（按成本从低到高）

**实验 A（零训练成本，强烈建议先做）：把「重复性」纳入报告完成度。**
ThinkingBox 最核心的度量是 **observed k/k**（k 次全对）而非 pass@k。EverAgent 的报告目前**只有一次通过/不通过**的记录 → **建议在 evidence sidecar 里记录同一批报告在 N 次独立复核下的通过数**（例如 `passed_runs: 3/3`），并把「可重复通过率」作为 tier 判据之一。

**实验 B：把 report-v2 的确定性检查做成「可执行 rubric」清单。**
列出**能被脚本判定**的报告属性（示例）：
- 每个 `critical: true` 的 claim 都有非空 `source_ids`，且每个 source 有 `kind` 与 `locator`；
- evidence 通过 `report-evidence-v1` schema 校验；
- `report_quality.py check` 的 error 列表为空（当前会因缺 review 而报错 → 需区分「内容错误」与「流程未完成」）；
- 正文包含约定章节（术语/数据流/表格/Limitations/思考与追问）；
- `git diff --check` 无空白错误；
- 所有 `kind: local` 的 source 指向仓内普通文件、非越界路径、非符号链接（schema 与 check 已有规则）。
→ 这构成一个**二值可执行判据**，可用于**评测**（不需要训练）。

**实验 C（可训练版本，规模可控）：用「报告修复循环」构造 RL 任务。**
- **环境**：一个「报告工单」——给 agent 一份**有已知缺陷的报告**（缺 claim、无来源、章节缺失、锚点错）与可写的检查工具；
- **判据**：修复后上述 B 清单全绿 → reward 1；否则 0；
- **模拟用户**：扮演「审稿人」，提出「这个 claim 的来源在哪」这类追问，迫使多轮交互；
- **任务池**：按 ThinkingBox 的办法，**先对 base policy 探针 n 次**，只保留成功率在 (0.08, 0.90) 的任务（避免全 0/全 1 无梯度）；
- **数据不相交**：报告任务按「仓库/主题/日期」切分，训练任务与评测报告**不重叠**，并用 UID 排除机制显式过滤。

**实验 D（纪律性实验）：解释一致性检查。**
ThinkingBox 的 `tb_interpret.py` 提醒：**同一份模型输出经训练侧与评测侧解析必须得到相同的工具名与参数**。EverAgent 的等价物：**同一份报告草稿经「生成侧解析」与「复核侧解析」应抽出同一组 claim/来源**（例如两侧对「哪些 claim 是 critical」必须一致）。可以用「把生成侧与复核侧的 claim 抽取结果做集合比对」作为一个自动化 parity 断言。

### 8.3 建议的 eval 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **pass@1（单次通过率）** | 单次复核通过比例 | 与业界对齐，但**不可单独使用** |
| **observed k/k（可重复通过率）** | k 次独立复核中全部通过的任务数/比例 | 接近生产可靠性；ThinkingBox 的核心结论即在此列 |
| **漏判 vs 误判混淆矩阵** | 应通过被判不通过（漏）vs 不应通过被放过（误） | 两者代价不同（漏=白干，误=放行坏报告） |
| **判据覆盖率** | 「可执行检查能判定的报告缺陷」占全部缺陷的比例 | 决定奖励能覆盖多少真实质量维度 |
| **reward 与人工判定的相关性** | 可执行分与人工复核结论的一致性（κ） | 防止「优化了指标、没优化质量」 |
| **judge 占比与一致性** | 判定辅助项占比、judge 与人工的一致率 | 对应 ThinkingBox 中未量化的空白 |
| **单位合格产出成本** | （总成本）÷（正确通过的报告数） | 唯一能回答「这套流程值不值」的指标 |
| **探针分布直方图** | 候选任务的成功率分布 | ThinkingBox 建议：多数团队从没看过这张图 |

### 8.4 迁移边界（必须写进方案）

1. **可执行奖励只能覆盖「可被脚本判定」的维度**。EverAgent 的报告质量里，「论证是否充分」「取舍是否合理」「是否值得读」**不可执行** → 这些维度只能靠盲评 + 人工，不能塞进奖励。
2. **不要把「报告通过检查」等同于「报告有价值」**。ThinkingBox 自己就证明了「动作合法 + 终止干净」可能仍然失败；EverAgent 的对应风险是「**格式齐全但没有洞见**」的报告拿到满分。
3. **训练池必须与评测集不相交**，并保留 UID 排除机制（与 ThinkingBox 同法）。
4. **难度是策略相对的**：EverAgent 的判定策略迭代后，原来的「中等难度」任务会变成 0 或 1 → 每次策略换代都要**重新探针**（这与 ThinkingBox 选择「固定训练池」不同，EverAgent 迭代更快，可能更需要定期重探）。
5. **成本表必须把「训练/探针成本」算进去**：ThinkingBox 明确把训练与探针成本**排除**在成本表外；EverAgent 若照搬该口径，会低估总成本。

## 9. Limitations

1. **全部结果为项目方自报**，无独立复现；本次研究未运行训练或评测。
2. **单一模型、单一算法、单一规模**：Qwen3.8-27B、token-mean GRPO、50 步、187 任务、24×H100。**未与 PPO 或其它优化器对照**，也未验证结论能否迁移到更大模型。
3. **训练成本未公开**：成本表明确**排除训练运行成本与策略探针成本** → 「−67.2% 每条可靠任务成本」是**运行侧**口径。
4. **成本数字是「相对服务指数」而非账单**；且服务微调 checkpoint 的推理成本与基座相同。
5. **本轮 pass@20 下降 7 个任务**（453→446），说明 20 次评测中观察到的 breadth 略降；博客把它解释为概率分布向可重复轨迹集中的 sharpening。由于每个任务只有 20 次样本，这不等于证明真实支持面永久收缩，也可能包含抽样波动。
6. **转移声明被原文自我限制**：训练池与基准共享框架、模拟用户机制、可执行评分、部分工具与任务风格 → 「OOD」是**弱 OOD**。
7. **基准全部为合成数据**（客户非真实）；域仅 5 类；真实企业流程的策略歧义与例外未被覆盖。
8. **judge 参与比例未量化**，也**未报告 judge 与人工的一致率** → 无法评估「少数判定辅助项」引入的偏差规模。
9. **未报告 reward hacking 的量化结果**：既没有「模型是否学会了针对检查器优化」的度量，也没有 hacking 尝试的成功率。
10. **「Observed 20/20」只是 20 次观测的字面计数**（原文：no estimator, no smoothing）；论文摘要用 `pass^20` 表示同方向的全成功指标，但公开材料没有给出样本外可靠性的置信区间或平滑估计。
11. **难度带边界是超参**（0.08/0.40/0.60/0.90），且**在训练中不重探** → 训练后期难度分布可能失真；187 任务是从多少候选中筛出、探针成本多少，均未披露。
12. **私有 187 任务池不公开**；公开样本只有 39 个开发任务 → 外部复现者只能用自有任务，数据可比性受限。
13. **符号极易混淆**：`pass@20` 表示至少一次成功，`pass^20` / Observed 20/20 表示全部成功；跨文引用若丢掉 `@` 或上标会把结论读反。
14. 本文标注为 **[分析者推导]** 的内容（命名陷阱、选型判断、迁移实验设计、hacking 面清单）均为我的推断而非原文陈述。

## 10. 思考与追问

1. **「终态正确」与「任务完成」之间还差什么？** 一个 agent 可以把数据库改成期望状态却完全没做业务沟通。ThinkingBox 的终态判定抓不到这类「形式正确、实质缺位」。**能不能设计一类「必须留下沟通痕迹才能通过」的判定**（例如要求某个工单评论存在且引用了正确政策条款）？这类判定的可执行性边界在哪？
2. **难度带是超参，训练池是固定的** —— 50 步之后策略已经变了，是否还有一部分训练任务已经「全 1」而浪费了 rollout？**有没有在线重探的成本收益拐点？**（在有状态 agent 上，每次重探都要付「供给后端 + 真实会话 + 额外模型扮演用户」的全价。）
3. **零方差组的 refill 是纯浪费吗？** 脚注承认 refill 前被丢弃的 rollout 全额付费。可以量化：在这次运行里，**有多少比例的 episode 是被丢弃的**？如果超过 30%，那么「训练池选得准」这件事本身可能就没那么准。
4. **可执行判据会不会诱导「检查器特化」？** 训练任务与评测任务虽然不相交，但**检查器代码家族相同**（同框架的 executable checks）。模型是否可能学到「满足检查器模式的最小改动」而非「完成任务」？**怎样用一组人工构造的「等价但不被检查器认可的正确解」来测这件事？**
5. **judge 的比例与一致性应该被要求公开。** 如果「少数任务」其实是 30%，那么这个系统的奖励质量就主要由模型 judge 决定，而本文几乎没有评估它。**是否应该把 judge 一致率作为该类工作的发布前置条件？**
6. **把「可重复通过率」引入 EverAgent 的报告流程，会带来什么组织成本？** 同一批报告跑 3 次独立复核意味着 3 倍复核预算。**在哪些 tier 上值得？**（也许只有「重要决策材料」才配得上。）
7. **报告质量门的「可执行化」到底能覆盖多少？** EverAgent 的 report-v2 检查大多检查**元数据与结构**（schema、锚点、章节、来源可追溯），而**不检查「论证是否成立」**。如果把「结构合规」当奖励训练，模型会不会产出「结构完美、洞见为零」的报告？**这是否就是报告类任务的 reward hacking 主战场？**
8. **一条更一般的结论**：*「任何能被确定性判定的产物，其质量迭代都应先走工程（改检查器、改生成器），再走 RL（改策略）」*。ThinkingBox 的成本表其实支持这个顺序：**−67.2% 的成本收益，是用 50 步 × 24×H100 的训练换来的** —— 这笔投入是否划算，取决于同一个团队把同样时间花在「改 prompt 与检查器」上的收益。**原论文没有回答这个对比，而它才是决策者真正要的答案。**
9. **模拟用户是 GPT-5 Chat** —— 那么「agent 学会说服模拟用户」会不会被误当成「学会了与真实用户协作」？**换不同的模拟用户模型，20/20 会不会大幅波动？** 这是一个可以立刻做、但没人做的敏感性实验。
10. **这一族的评测范式能不能推广到「非数据库」产物？** 例如 EverAgent 的**报告**：终态是「一份 Markdown 文件」，检查器是脚本 —— 技术上完全可行，难点是**检查器能否覆盖质量维度**。**这可能是该方法论对知识工作最大的未开发空间。**
