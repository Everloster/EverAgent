# AI演义·01 Brook：GPU 很快，为什么普通程序还不容易用上它？

> 本篇展开[《AI演义》主报告的第 1 节](../AI演义_笔记分析与项目整合报告.md#paper-brook)，可以单独阅读。对照材料是讲义第 10 页、播客约 19:39–26:36，以及 2004 年的原论文 *Brook for GPUs: Stream Computing on Graphics Hardware*。

假设你有两列各一百万个数字，任务很简单：把第一列的每个数乘以 2，再加上第二列对应的数。

你听说显卡特别擅长同时做很多计算，于是想把这件事交给它。结果发现，自己首先得学习如何创建纹理、装载着色器、发出一次绘图命令，还得安排计算结果保存到哪里。

你想算一张表，却被要求先学会如何“画图”。

这正是 Brook 面对的处境。它尝试提供一套更适合计算的表达方式：**程序员描述一批数据和要对它们做的运算，编译器与运行时负责把这些表达接到 GPU 上。** 同时，作者还要回答另一个问题：多加了这层软件，最后究竟能快多少？[^paper]

## 1. 显卡为什么会成为计算工具的候选者

先从 GPU 的本职工作看起。

生成一幅图像，要处理大量顶点、片元等数据。片元可以先粗略理解为生成像素过程中的候选记录；显卡往往需要对很多这样的记录执行相似的运算。图形硬件由此发展出了适合批量计算的组织方式。

后来，部分图形处理步骤允许开发者编程：程序员可以写一小段着色器程序，让硬件按自己的规则计算。着色器虽然服务于图形，但其中的加法、乘法、向量运算和读取数据，也可以参与线性代数、物理模拟等工作。

**一段程序对许多份数据反复执行，这种计算形状并不限于图像。**

回到那两列数字。为方便看清，我们先只放三行：

| 位置 | 第一列 x | 第二列 y | 结果：2 × x + y |
|---|---:|---:|---:|
| 第 1 行 | 1 | 10 | 12 |
| 第 2 行 | 2 | 20 | 24 |
| 第 3 行 | 3 | 30 | 36 |

这是本文自拟的教学数据；运算本身来自论文测试的 SAXPY。它是一个基础线性代数操作：用一个共同的数缩放向量 x，再与向量 y 相加。“向量”在这里就是一列数，不必先学更多数学。

关键在于：**算第 3 行不需要等待第 2 行的结果。** 三行可以分别算，一百万行也可以分批交给大量计算单元处理。这就是数据并行：规则相同，数据分开，每份计算有足够的独立性。

如果任务变成“第 3 行必须使用刚算出的第 2 行结果”，情况就不同了。行与行之间出现依赖，程序员需要重新组织算法，甚至接受其中一部分只能依次执行。GPU 很强，并不意味着任意一段程序都能同样受益。

所以，早期通用 GPU 计算要跨过两道门：一是找到适合这种并行组织方式的计算；二是让程序员有办法把计算交给硬件。Brook 主要处理第二道门，并通过编程规则让第一道门变得明确。

## 2. 已经能写着色器，为什么还要 Brook

播客在约 23 分钟处讲到早期 GPU 编程困难。原论文把这件事拆得更细，也帮助我们避免一个常见误解：2004 年并非只有汇编式的着色器代码可写。HLSL、Cg 等语言已经让着色器可以用类似 C 的语法表达。[^paper]

真正的问题是：**写出那段乘法和加法，只解决了整条计算流程的一小部分。**

仍以两列数字为例，采用当时图形接口的程序员，还要安排下面这些事：

| 要完成的计算工作 | 借用图形系统时怎样表达 |
|---|---|
| 把两列数字放到 GPU 可读取的位置 | 把数值装入浮点纹理；纹理此时充当数据容器 |
| 告诉 GPU 每个位置算什么 | 写着色器，读取对应输入，执行乘法和加法 |
| 让这段计算覆盖全部位置 | 设置并发起绘图，让生成的片元触发计算 |
| 保存全部计算结果 | 将着色器输出写入渲染目标，再用于后续计算或取回 |
| 换一种显卡或接口继续运行 | 处理纹理尺寸、输出数量、编译器和接口支持等差异 |

“纹理”原本常用于描述物体表面的颜色等信息，但对这些程序来说，里面存的是待计算的数值。“绘图”也可以只写入显存中的缓冲区，完全不必在屏幕上显示一幅画。

这套办法确实能用。Brook 的论文开篇就列出了此前在 GPU 上做线性代数、物理模拟和光线追踪的研究。它并没有首次发现 GPU 可以做通用计算。

但想采用它的人，通常得同时理解自己的算法和图形系统。科学计算研究者很容易把精力花在纹理打包、接口调用和硬件细节上；同一种麻烦，还会在不同应用里重复出现。

Brook 希望把这部分工作集中放进语言、编译器和运行时。这样的价值，可以从下一步看得很具体。

## 3. 用三个概念，把“一百万行计算”交给系统

Brook 原本是面向流处理器的语言；2004 年这篇论文研究如何把它适配到 GPU。它扩展 C，引入了三个关键概念：stream、kernel、reduction。[^model]

### Stream：先把这一批数据说清楚

在 Brook 中，stream 是一组具有类型和形状的数据记录，可以先理解为“交给系统管理的一批数据”。

两列数字分别构成两个输入 stream，结果构成一个输出 stream。每个位置放一个浮点数；如果做光线追踪，也可以让一个元素包含一条光线的起点、方向等字段。这样，程序员可以围绕自己的问题组织数据。

这里的 stream 指数据集合；它与聊天模型逐字输出答案时所说的网络“流式传输”含义不同。一组已经准备好的数字，同样可以是 Brook stream。

Brook 知道这组数据有多少个元素、每个元素是什么类型、是一维还是二维，才能进一步安排存储和执行。程序员仍需准备输入，但不必亲自将每个字段塞进哪张纹理。

### Kernel：只写“每一行怎么算”

kernel 是作用于 stream 元素的计算函数，也叫“核函数”。这里的“核”是计算步骤，与操作系统内核无关。

我们的例子中，程序员需要表达的核心只有：

```text
对当前这一行：
    result = a × x + y
```

`a` 是所有行共用的数，例如 2；`x` 和 `y` 则来自当前对应位置。调用这个核函数时，Brook 把它作用到整个输出 stream 的各个元素上。程序员不用在函数里再写一个遍历一百万行的外层循环。

这个“隐含的循环”很重要。普通逐行程序先规定了执行顺序；这里表达的是一组独立工作，让系统可以利用 GPU 的并行执行能力。它不承诺一百万行同一瞬间全部算完，具体调度仍受硬件资源限制。

核函数还把每个元素的一串运算集中起来。例如，计算 `a × x + y` 时，乘法产生的中间量可以留在处理器的临时寄存器里，再接着做加法，最后写出结果。寄存器可以先理解为紧邻计算单元的小型临时存储：不用每做一步就把中间结果写回显存、下一步再读出来。原论文把这种局部性列为核函数的一个重要作用。[^model]

这里减少的是 **GPU 内部反复读写中间数据**；后面性能分析还会遇到另一笔成本——**数据在 CPU 和 GPU 之间的搬运**。两处都与数据移动有关，但发生的位置不同。

### 这种方便为什么需要限制

假设每一行除了算自己的结果，还要随意改写另一行的数据，或者共同修改一个全局变量。两项工作谁先执行，就可能影响最终结果。原先能够自由安排的并行计算，会突然多出协调问题。

因此，Brook 的核函数有明确限制。例如，普通输入 stream 和用于按索引读取的 gather stream 都是只读的；不能通过写全局变量等方式，让不同元素的计算产生副作用。

这也不意味着每一行只能读自己的一个数。论文支持 **gather**：某个计算可以按索引读取其他输入元素。读一张不被同时改动的表，和随意改写大家正在使用的表，后果不同。

“输入只读”也不等于每次都必须另建一份结果。论文允许同一条 stream 同时作为普通输入和输出，用于就地计算，前提是它在这个核中不再充当 gather stream。直观地说，“读本行旧值，写本行新值”与“还要随时读取其他行正在被更新的值”，不能混为一谈。[^model]

程序员用这些限制换取可并行执行的保证。至于随机位置更新、复杂共享状态等工作，必须另行组织；论文中的一些高级读改写操作当时还由 CPU 完成。Brook 没有消除算法的依赖关系，也没有包办所有类型的并行程序。[^model]

### Reduction：算完各行之后，怎样得到一个总数

前面的三行产生了三个结果：12、24、36。如果接下来需要的是总和 72，就要从多个元素得到一个结果。这是 reduction，中文常译“规约”。

逐元素的 kernel 适合“每行产生自己的结果”，规约则负责“把很多结果合起来”。不能简单让每一行同时往同一个总数里加：这会重新遇到共享写入的协调问题。

一种容易理解的实现是分层汇总：先让各组求部分和，再把部分和继续合并，直到得到最终结果。Brook 运行时会用多轮处理完成这件事。实际实现每轮合并多少项由系统决定，论文讨论了相应策略。[^model]

规约也不必把整批数据都缩成一个数。若矩阵的每一行分别求和，输出就是一条较小的 stream，每个元素保存一行的总和。原论文据此把矩阵与向量相乘拆成“先逐项相乘，再逐行汇总”：同样的两个基本动作，可以组合成更复杂的计算。[^model]

这里还有一个数学条件：要能够改变分组方式，规约运算需要具有结合性。以普通整数相加的教学例子看，先算 `12 + 24`，或先算 `24 + 36`，总和都是 72。涉及浮点数时还要考虑舍入，不能据此要求所有求和次序都得到逐位相同的结果。

把三个概念放回一个任务，它们就不再是术语表：**stream 装数据，kernel 对各份数据执行运算，需要汇总时再做 reduction。**

## 4. 那些麻烦去了哪里：从一句运算到一次 GPU 执行

程序员少写了图形代码，硬件却仍然是那块硬件。Brook 的编译器与运行时接过了中间工作。

可以沿着我们的计算走一遍：

1. **程序声明输入和输出。** 两列数字进入输入 stream，输出 stream 留给结果；程序定义计算 `a × x + y` 的核函数。
2. **编译器改写计算。** 论文里的编译器 `brcc` 将核函数转成 Cg 着色器，再交给相应厂商的编译器生成 GPU 代码，同时生成与运行时衔接的 C++ 代码。
3. **运行时安排存储与调用。** Brook Runtime，简称 BRT，管理 stream 对应的纹理、装载程序、设置参数，并调用图形接口。
4. **借用绘图流程触发运算。** BRT 发出覆盖所需输出元素的四边形绘制，片元执行着色器；每个位置读取 x、y，计算结果。
5. **结果留下或取回。** 结果写到渲染目标所对应的存储中，供下一步 GPU 计算使用，或者传回 CPU。

这解释了 Brook 改变的位置：**数据并行的计算意图进入语言，映射到图形硬件的细节进入系统实现。** 程序员得到的接口更接近自己要解决的问题。[^implementation]

### 跨平台的意思，要看它承担了哪些差异

论文实现了面向 ATI、NVIDIA 硬件的 DirectX 与 OpenGL 后端，以及 CPU 参考实现。同一套 Brook 表达可以映射到不同后端，免去应用程序直接处理一部分接口差异。

**隐藏硬件细节，不等于取消容量上限。** 论文 §4.1 给出一个具体例子：为了容纳更长的一维 stream，编译器把它折到二维纹理中，再计算每个元素的位置；但当时 ATI 硬件的浮点寻址精度，使这种一维映射最多支持 **131,072 个元素**。这不仅是显存够不够的问题——数值精度不够时，程序可能无法区分相邻地址。[^implementation]

因此，开头“一百万行”描述的是要处理的任务，不是说所有 2004 年的后端都能直接接收一条这么长的一维 stream。采用上述受限映射时，程序还得分批处理。Brook 承担了一部分映射工作，却没有承诺任意数据规模都能无条件运行。

但可运行并不保证同样快。例如，当时某些硬件一次只能输出较少结果，Brook 会把一个多输出核拆成多个着色器分轮执行；复杂结构也可能被拆到多张纹理。

这样可以完成计算，却可能增加数据读取，甚至重复一部分运算。同样，论文中的 OpenGL 后端在保存结果时需要额外复制，而 DirectX 后端可以直接写入相应纹理。这些差别会体现在测试结果里。[^implementation]

这也是理解编程抽象的一条实用线索：看它**替使用者管理了什么，又为此付出了什么成本**。把细节隐藏起来，并不会让成本消失。

## 5. 论文里的“最高约 7 倍”，究竟是哪笔账

说到这里，Brook 看起来很方便，但还需要实验回答：编译出来的程序是否足够快？相比 CPU，值得使用吗？

作者测试了 SAXPY、矩阵向量运算、图像分割、FFT 和光线追踪等应用，比较了不同 Brook 后端、手写 GPU 实现和 CPU 实现。测试设备属于 2004 年环境，包括 ATI Radeon X800 XT Platinum、预发布的 GeForce 6800，以及 3 GHz Pentium 4。CPU 侧的多个基线使用了优化过的数学库。[^performance]

下面从论文 Figure 3 取三个任务，固定比较 **ATI 上的 Brook DirectX 实现与 CPU 基线**，就能看见不同结果：

| 任务 | GPU | CPU | 比值 |
|---|---:|---:|---|
| SAXPY | 4,324 | 624 | 约 6.93 倍 |
| Segment | 12,163 | 2,616 | 约 4.65 倍 |
| FFT | 1,212 | 1,224 | 约 0.99 倍 |

GPU 和 CPU 两列的单位均为 **MFLOPS，即每秒百万次浮点运算**。SAXPY 是前面的向量缩放与相加，Segment 是图像分割计算，FFT 是快速傅里叶变换。这里的倍数是用同一任务的两项吞吐量相除；不同任务的一次完整处理各要多少运算，不能只靠这一列判断。

SAXPY 给出了一个很有力量的结果：基础而简单的运算，通过高级语言表达，在这组测试中也能获得明显加速。FFT 则提醒我们，同样叫“适合数值计算”，实际数据访问、执行组织和优化基线仍会改变结果。论文的 CPU FFT 使用 FFTW3 等已有优化，GPU 没有普遍胜出。

因此，“最高约 7 倍”需要与具体任务、硬件、后端和计时范围一起读。

### 最容易漏掉的条件：这张图没有计入初始上传和最终下载

论文明确说明，Figure 3 的测试**排除了初始 `streamRead` 和最终 `streamWrite` 的耗时**。这两个名字容易让人迷糊：在这里可以理解为，把 CPU 侧数据交给 stream，以及把 stream 结果取回。[^performance]

测试这样安排，能观察主要计算部分的表现；实际应用仍要支付数据搬运成本。作者为此在 §5.2 单独分析了 CPU 与 GPU 的取舍。

用一组自拟时间做演示，区别就很直观。假设 CPU 完成某项工作要 70 毫秒，GPU 计算本身只要 10 毫秒：

| 情况 | 送入数据、发起调用、取回结果 | GPU 计算 | 从开始到拿到结果 |
|---|---:|---:|---:|
| 搬运与调用很少 | 5 毫秒 | 10 毫秒 | 15 毫秒，明显受益 |
| 搬运与调用很多 | 80 毫秒 | 10 毫秒 | 90 毫秒，反而更慢 |

**这些时间仅为教学假设，不是论文实测。** 两种情况下，GPU 计算本身都比 CPU 快 7 倍，用户真正等待的时间却完全不同。

如果数据上传后能留在 GPU 上连续做多步计算，最后才取回结果，搬运成本就有机会被更多工作分摊。相反，只做很少的计算就来回搬，优势容易被抵消。小任务还要考虑调用本身的固定开销。

这也解释了为什么“任务越复杂就一定越适合 GPU”过于简单。SAXPY 本身并不复杂，合适的数据布局和设备内带宽也能带来高吞吐；最终还是要看**计算怎样组织、数据怎样移动，以及比较中到底算了哪些时间**。

### “接近手写代码”，也要按实现看

播客约 25:53 提到 Brook 与手写 GPU 代码的性能比较。论文确实用实验支持了抽象开销可以被控制这一点，但不同后端并不相同。多轮拆分、复制和硬件限制都会影响结果。

这项贡献值得保留的含义是：开发者有机会用更高层的表达，换得接近专门实现的性能，从而减少大量底层编程工作。它并不保证每个任务、每种硬件都达到手写最优结果。

## 6. 为什么人物与组织史能帮助理解这篇论文

播客和讲义还花了一部分篇幅介绍 Ian Buck 与 Pat Hanrahan。把他们放回技术路径，比单列履历更能解释这项工作为何发生。

Brook 论文共有七位作者，来自 Stanford 团队。Ian Buck 是第一作者，Pat Hanrahan 是其中一位作者。这项成果包含语言、编译器、运行时和实验，适合按团队研究来理解。[^paper]

Hanrahan 的经历连接了图形学研究与实际制作系统。他是 Pixar 的早期员工，也是 RenderMan 的主要架构师。RenderMan 中着色器语言的工作，让创作者能够用程序控制表面如何呈现；此后，他在大学中的研究又涉及 GPU 着色语言与更广泛的计算用途。ACM 关于 2019 年图灵奖的公告，明确描述了这条技术路径，也提到了 Brook 对 CUDA 的影响。[^acm]

沿着这条线看，需求在逐步扩大：先希望图像的呈现方式可以编程，再希望同一类可编程硬件能处理更多数值任务。图形产业积累的硬件和工具，为后一类研究提供了条件。

NVIDIA 的历史回顾则记录，Buck 于 2004 年带着相关工作加入 NVIDIA，继续推动 GPU 计算的编程环境。Brook 与 CUDA 的联系，因此既有人才流动，也有编程思想与工程工作的延续。[^history]

不过，Brook 研究原型与后来的 CUDA 平台是不同系统，不能简单写成“Brook 改了个名字”。前者借用当时的图形接口，验证数据并行抽象与实现；后者沿着 GPU 通用计算的方向继续发展，需要硬件、编程环境和工具共同推进。

这段历史让我们看到，一篇论文到广泛可用的平台之间，还有后续工程与产品化。单靠一次实验，无法完成所有这些环节。

## 7. 从 Brook 到 AlexNet：它为下一段故事准备了什么

《AI演义》在 Brook 后面讲 AlexNet，这个安排很有用：先看计算条件怎样改变，再看学习方法如何利用这些条件。

Brook 展示了一个方向：程序员可以通过更适合数值计算的接口使用 GPU，系统也可以在一些任务上保留较好的性能。进入下一篇时，问题就进一步变成：有了可用算力，怎样与数据、模型结构和训练方法结合，解决足够难的学习问题？

因此，这两篇之间的连接应当落在**计算条件与训练实践**上。不能据此说 AlexNet 使用了 Brook，也不能把 2012 年理解为人们首次用 GPU 研究深度学习。

这一节也给后面读模型论文留下一组具体问题：作者改进的是算法表达、内存访问、执行调度，还是数据搬运？它测量一个计算步骤，还是整个训练或推理过程？如果需要换硬件、换数据规模，收益还来自同一个地方吗？

带着这些问题再看后续篇章，GPU 会从背景里一个“很快的零件”，变成一套需要算法和软件共同利用的计算资源。

## 思考与追问

1. 如果某个 GPU 核比 CPU 快 10 倍，你还想看哪几项测量，才能判断自己的应用会不会更快？可以试着把“数据进入—计算—结果离开”补完整。
2. 如果一个接口不允许计算任意改写其他元素，这个限制换来了什么？什么样的算法会因此需要重新设计？
3. 一项研究让硬件“能被使用”，与一个平台让大量开发者“持续用得好”，中间还隔着哪些工具与工程工作？这个问题会在后面的 AI 基础设施篇章中反复出现。
