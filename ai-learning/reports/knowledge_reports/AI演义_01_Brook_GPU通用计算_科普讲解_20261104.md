# AI演义·01｜Brook：让普通计算用上 GPU

[返回总览第 1 节](../AI演义_笔记分析与项目整合报告.md#paper-brook)

假设你有两列各一百万个数字，要把第一列的每个数乘以 2，再加上第二列对应的数。这些计算彼此独立，很适合交给 GPU。但在 2004 年前后的显卡上，写出算式还远远不够：你得把数字装进纹理，编写着色器，发出绘图命令，再想办法取回结果。

*Brook for GPUs: Stream Computing on Graphics Hardware* 试图替程序员承担这些工作。你用接近 C 的语言描述数据和运算，编译器与运行时再把它们转换成 GPU 能执行的图形操作。论文既提出编程方法，也检查这层抽象会付出多少性能代价。[^paper]

## 1. 一批数据，重复同一种运算

GPU 原本用来处理图像。生成画面时，它需要对大量顶点、片元等记录执行相似操作；片元可以先理解为生成像素过程中的候选记录。这种批量工作促使图形硬件发展出适合数据并行的计算方式。

后来，部分图形处理步骤允许编程。着色器里的加法、乘法、向量运算和数据读取，除了生成画面，也能用来做线性代数和物理模拟。前面两列数的计算就是一个例子。先把一百万行缩成三行：

| 位置 | 第一列 x | 第二列 y | 结果：2 × x + y |
|---|---:|---:|---:|
| 第 1 行 | 1 | 10 | 12 |
| 第 2 行 | 2 | 20 | 24 |
| 第 3 行 | 3 | 30 | 36 |

这组数字是教学例子，运算则取自论文测试的 SAXPY：用同一个数缩放向量 x，再加上向量 y。这里的向量就是一列数。

每行只读取本行输入。算第 3 行时不用等第 2 行，系统便可以把许多行分给不同计算单元。规则相同、数据分开，这就是数据并行。若任务改为“第 3 行必须使用第 2 行刚算出的结果”，并行空间就会缩小；程序员需要改变算法的组织方式，或者保留其中必须顺序执行的部分。

Brook 面向的是能按这种方式表达的计算。它让独立工作更容易交给硬件，也通过语言规则限制会破坏独立性的操作。

## 2. 算式之外，还有一整套图形操作

2004 年已经有 HLSL、Cg 等类 C 着色器语言。程序员可以用熟悉的语法写出乘法和加法，困难更多在于怎样准备数据、触发计算和保存结果。[^paper]

| 要完成的计算工作 | 当时借用的图形操作 |
|---|---|
| 将两列数字送到 GPU | 把数值装入浮点纹理 |
| 指定每个位置的运算 | 用着色器读取输入，执行乘加 |
| 让计算覆盖全部位置 | 发起绘图，使生成的片元执行着色器 |
| 保存结果 | 写入渲染目标，供后续计算使用或取回 CPU |
| 换用另一种硬件或接口 | 处理纹理尺寸、输出数量和编译器等差异 |

在这些程序中，纹理充当数值容器，绘图结果可以只写进显存，屏幕上不必出现一幅画。此前的研究已经用这套办法做过线性代数、物理模拟和光线追踪。Brook 延续这些探索，把应用反复需要的图形编程工作放进语言、编译器和运行时，减少每位使用者都要掌握的底层细节。

## 3. Stream、kernel 与 reduction

Brook 原本是面向流处理器的语言，2004 年的工作将它适配到 GPU。理解它的编程方式，可以继续沿着两列数往下走。[^model]

### Stream 保存一批记录

两列输入各是一条 stream，结果是另一条 stream。每条 stream 都有元素类型和形状：本例每个位置放一个浮点数；做光线追踪时，一个元素也可以包含光线起点、方向等字段。

Stream 在这里指一批数据，与网络上传输文字片段的“流式输出”含义不同。Brook 根据类型、元素数量和维度安排存储，程序员准备好数据后，无须再逐字段决定它们该放进哪张纹理。

### Kernel 描述每个元素的计算

Kernel 是作用于 stream 元素的函数，中文常称“核函数”。本例的计算可以写成：

```text
对当前这一行：
    result = a × x + y
```

`a` 是所有行共用的数，`x`、`y` 取自当前位置。调用核函数时，系统把它应用到输出 stream 的各个元素上。遍历整批数据的外层循环由系统安排，具体能同时计算多少项取决于硬件资源。

把一串运算放进同一个 kernel，还能减少中间数据的读写。计算乘加时，乘法的结果可以暂存在计算单元附近的寄存器里，接着参与加法，最后才写回显存。后面讨论的 CPU 与 GPU 之间的数据传输则是另一笔成本。[^model]

### 哪些操作仍然受限

如果各行在计算时随意修改其他行，或共同改写全局变量，结果就可能依赖执行先后。Brook 因此限制跨元素的副作用：普通输入 stream 和按索引读取的 gather stream 都是只读的，核函数不能通过写全局变量等方式改变其他元素的计算。

Gather 允许一个核按索引读取其他输入位置，因此输入不限于“本行的一个数”。读取一张不被同时修改的表，仍然可以保持计算之间的独立性。

论文也允许同一条 stream 同时作为普通输入和输出，进行就地计算，条件是它在该核中不再充当 gather stream。这样可以读取本行旧值、写入本行新值，同时避免其他行读到更新先后的混合状态。更复杂的随机写入需要另行组织，论文中的高级 `ScatterOp`、`GatherOp` 当时还由 CPU 实现。[^model]

### Reduction 将多个结果汇总

三行得到 12、24、36。若最终要的是总和 72，就需要 reduction，即规约。逐元素 kernel 各自写结果，规约再把这些结果合并，避免所有元素同时争着改写同一个总数。

可以分组求部分和，再逐层合并。Brook 运行时用多轮处理完成规约，并决定每轮合并多少项。输出也可以是一条较小的 stream：例如矩阵逐行求和，每个输出元素保存一行的和。论文用“逐项相乘、逐行规约”组合出矩阵与向量相乘。[^model]

改变分组顺序需要运算满足相应的结合性条件。教学例子中的整数相加，无论先算 `12 + 24` 还是 `24 + 36`，总和都是 72；浮点数存在舍入误差，不同归约顺序未必逐位相同。

## 4. 从 Brook 程序到 GPU 执行

现在把数据与核函数一起交给 Brook，系统按下面的过程工作：

1. 程序声明输入、输出 stream 和计算 `a × x + y` 的核函数。
2. 编译器 `brcc` 将核函数转成 Cg 着色器，再由厂商编译器生成 GPU 代码；同时生成连接运行时的 C++ 代码。
3. Brook Runtime（BRT）管理纹理、装载程序、设置参数并调用图形接口。
4. BRT 绘制覆盖输出范围的四边形，使片元执行着色器、读取 x 和 y 并写出结果。
5. 结果留在 GPU 上参与后续计算，或传回 CPU。[^implementation]

这些步骤原本散落在每个应用的图形代码里，现在由 Brook 集中处理。论文实现了面向 ATI、NVIDIA 的 DirectX 和 OpenGL 后端，以及一个 CPU 参考实现。

硬件限制仍会通过映射方式影响程序。为了保存较长的一维 stream，编译器可以将它折进二维纹理，再计算每个元素的地址。当时 ATI 硬件的浮点寻址精度，使论文中的这类一维映射最多支持 **131,072 个元素**。地址精度不足时，相邻元素可能无法被正确区分，增加显存也不能直接解决。[^implementation]

因此，开头的一百万行任务在这种后端上需要分批处理。其他差异也会影响效率：输出数量不足时，一个多输出核要拆成多个着色器，增加读取或重复运算；复杂结构可能分装到多张纹理。论文里的 OpenGL 后端还需要复制输出，而 DirectX 后端可以直接写入相应纹理。这些工作换来了可用性，也要计入实现成本。

## 5. “约 7 倍”对应怎样的测试

论文比较了 Brook 的多个后端、手写 GPU 程序和 CPU 实现。测试使用 2004 年的 ATI Radeon X800 XT Platinum、预发布 GeForce 6800 及 3 GHz Pentium 4，CPU 基线中有优化过的数学库。[^performance]

Figure 3 排除了初始 `streamRead` 和最终 `streamWrite`，即 CPU 侧数据的初始送入和最终取回。下面固定比较 ATI 上的 Brook DirectX 与 CPU，单位都是 MFLOPS（每秒百万次浮点运算）：

| 任务 | GPU | CPU | GPU／CPU |
|---|---:|---:|---|
| SAXPY | 4,324 | 624 | 约 6.93 倍 |
| Segment | 12,163 | 2,616 | 约 4.65 倍 |
| FFT | 1,212 | 1,224 | 约 0.99 倍 |

SAXPY 是前面的向量乘加，Segment 是图像分割计算，FFT 是快速傅里叶变换。比值比较同一任务的吞吐量，不能用来直接比较三个任务完成一次分别要多久。

SAXPY 表明，简单的计算也能通过高级语言表达获得明显加速；FFT 则没有超过使用 FFTW3 等优化的 CPU 基线。数据访问、后端拆分方式和基线实现都会影响结果，“最高约 7 倍”只对应这些条件下的一部分测试。

实际应用还要加回传输与调用时间。用一组假设数据说明：CPU 完成任务要 70 毫秒，GPU 计算本身要 10 毫秒。

| 情况 | 送入数据、发起调用、取回结果 | GPU 计算 | 从开始到拿到结果 |
|---|---:|---:|---:|
| 搬运与调用很少 | 5 毫秒 | 10 毫秒 | 15 毫秒，明显受益 |
| 搬运与调用很多 | 80 毫秒 | 10 毫秒 | 90 毫秒，反而更慢 |

这些时间仅为教学假设。两种情况下，GPU 计算部分都快 7 倍，整项任务却可能更快，也可能更慢。数据上传后若能留在 GPU 上连续计算，最后再取回，就有更多工作分摊传输成本；只做少量运算就反复搬动数据，优势很容易消失。小任务还会受到固定调用开销的影响。

论文也比较了 Brook 与手写 GPU 程序。结果支持在一些任务上用较高层的表达获得接近专门实现的性能，但多轮拆分、复制和硬件限制仍会造成差异。对使用者而言，需要同时衡量少写了多少底层代码，以及自己的任务最终花了多少时间。

## 6. 从图形编程研究走向 CUDA

Brook 论文由 Stanford 团队的七位作者共同完成，Ian Buck 是第一作者，Pat Hanrahan 也是作者之一。它涉及语言、编译器、运行时与实验，需要多方面的工作。[^paper]

Hanrahan 的经历连接着图形学研究和制作系统。他是 Pixar 的早期员工、RenderMan 的主要架构师；着色器语言让创作者能编程控制表面外观，后续研究又扩展到 GPU 着色语言和通用计算。ACM 的 2019 年图灵奖公告将这些工作放在同一条发展路径上，并提到 Brook 对 CUDA 的影响。[^acm]

NVIDIA 的历史回顾记录，Buck 在 2004 年加入公司，继续推动 GPU 计算的编程环境。Brook 与 CUDA 之间既有人才流动，也有编程思想和工程经验的延续。[^history] Brook 是借用图形接口的研究系统，CUDA 则在通用 GPU 计算方向上继续发展，需要后续硬件、工具和平台建设。

下一章会看到，算力变得容易使用之后，训练模型还需要数据、网络结构和学习方法共同配合。AlexNet 使用 GPU 训练卷积网络，与 Brook 的联系在于计算条件的演进，并非直接使用 Brook。GPU 学习研究也早于 2012 年，这个系列选择的是其中能说明问题的转折。
