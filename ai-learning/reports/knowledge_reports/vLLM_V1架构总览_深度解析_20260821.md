# vLLM V1 架构总览：一个请求的一生（骨架篇）

> 本文是 vLLM 源码级学习长线（计划见 `roadmap/vLLM_源码级学习计划_20260821.md`）的阶段 0 产出。
> **版本坐标**：本地 clone `../vllm`（即 `/Users/jabe/workspace/vllm`），checkout 在 **v0.27.1**（2026-08-11 发布，commit `6e448d0`）。本文所有 `file:line` 证据均以该 tag 为准，主会话已对关键位置抽查复核。
> **读法**：骨架篇只到「组件职责 + 调用链 + 数据结构」级，不抠算法与 kernel 细节——那些留给阶段 1-6，本文 §十一会标明每块挂到哪个阶段。

## 一、一句话设计哲学

vLLM V1 的全部进程设计可以概括为：**让 GPU 永不空转**——把一切 CPU 工作（HTTP、tokenize、detokenize、调度、通信序列化）从 GPU 关键路径上剥离，用多进程 + 多线程 + 异步让它们与 GPU forward 全部重叠。

三个支撑决策（后文逐一落地）：

1. **前后端分进程**：API server 进程（asyncio）与 EngineCore 进程（busy loop）之间只过 ZMQ + msgpack，引擎侧永不被 Python GIL 里的 HTTP 栈拖累。
2. **进程内再分线程**：EngineCore 进程内 busy loop 线程只管「调度 → 执行 → 输出」，ZMQ 收发和请求预处理放在两条独立 IO 线程里，与 GPU forward 并行。
3. **一切皆可重叠**：forward 与 structured-output bitmask 计算重叠（execute/sample 两相拆分）、请求初始化与 forward 重叠（预处理在 input IO 线程）、输出序列化与下一步调度重叠（output IO 线程 + buffer 复用）。

## 二、进程架构：四类进程

官方设计文档 `docs/design/arch_overview.md`（已对照代码验证成立）给出的 V1 进程模型：

| 进程类型 | 数量 | 职责 | 代码 |
|---|---|---|---|
| API server | 默认 1；DP 时自动 = DP size；`--api-server-count` 可覆盖 | HTTP、渲染/tokenize、多模态加载（8 线程）、增量 detokenize、SSE 流式返回 | `vllm/entrypoints/openai/api_server.py` |
| EngineCore | 每 DP rank 1 个（默认 1） | 调度器、KV cache 管理、执行协调；busy loop | `vllm/v1/engine/core.py` |
| GPU worker | 每 GPU 1 个；= TP × PP（每 EngineCore） | 加载权重、执行 forward、管理显存 | `vllm/v1/worker/gpu_worker.py` |
| DP coordinator | 仅 DP > 1 时 1 个 | 跨 DP rank 负载均衡 + MoE 同步 forward 协调 | `vllm/v1/engine/coordinator.py` |

进程数公式：**`A + DP + N`（+1 if DP>1）**。例：单机 `vllm serve -tp=4` → 1 + 1 + 4 = **6 进程**；`-tp=2 -dp=4` → 4 + 4 + 8 + 1 = **17 进程**。

每个 API server 与**所有** EngineCore 建立 many-to-many ZMQ 连接（任一前端可路由请求到任一引擎）。进程由前端进程在启动时拉起：`launch_core_engines`（`vllm/v1/engine/utils.py:1054`）→ `EngineCoreProc.run_engine_core`（`core.py:1272`）。

> ⚠️ 官方文档滞后提醒：`docs/design/multiprocessing.md` 还停在 2024-12 的 V0 状态（自称 "Current State (v0)"），不可采信。本线一律以代码为准。

以 `POST /v1/chat/completions` 为例，每一跳都标了 v0.27.1 的代码位置：

| # | 跳 | 位置 |

三个值得记住的细节：

- **stop string 是前端发现的**：EngineCore 只回 token_ids；前端 detokenizer 命中 stop string 而引擎侧未 finish 时，前端回发 abort（`output_processor.py:696-699` → `async_llm.py:706-709`）。
- **增量 detokenize 默认走 Rust**：`tokenizers ≥ 0.22` 时用 `DecodeStream` 的 `FastIncrementalDetokenizer`（`v1/engine/detokenizer.py:168`），纯 Python 版降级为 fallback。
- **客户端断连即 abort**：`generate` 消费循环的 `CancelledError/GeneratorExit` 分支触发 abort（`async_llm.py:611-616`）。

## 四、EngineCore：三线程 + busy loop + step 本体

### 4.1 进程内三线程模型

| 线程 | 职责 | 位置 |
|---|---|---|
| 主线程 | busy loop：`input_queue → step → output_queue` | `core.py:1378` |
| input IO 线程 | ZMQ 收帧 → 解码 → **请求预处理（EngineCoreRequest→Request、grammar 编译）** → `input_queue` | `core.py:1645` |
| output IO 线程 | `output_queue` → msgpack 编码（buffer 复用 + 零拷贝）→ ZMQ 发出 | `core.py:1743` |

busy loop 从不直接碰 ZMQ socket；请求预处理放 IO 线程是刻意设计——`core.py:969-991` 注释明说 "allow request initialization running in parallel with Model forward"。

### 4.2 step() 本体（`core.py:584-614`，已逐行核对）

```python
def step(self):
    if not self.scheduler.has_requests():
        return {}, False
    scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
    future = self.model_executor.execute_model(scheduler_output, non_block=True)
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)  # 与 forward 重叠
    model_output = future.result()
    if model_output is None:                          # execute 与 sample 已拆分
        model_output = self.model_executor.sample_tokens(grammar_output)
    self._process_aborts_queue()                      # 执行期间到达的 abort 先落账
    engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)
    return engine_core_outputs, ...
```

两个架构要点：

- **两相拆分**：`execute_model`（forward）与 `sample_tokens`（采样）是 Executor 上两个独立 RPC（`v1/executor/abstract.py:221,241`），目的是让 grammar bitmask 的 CPU 计算与 GPU forward 重叠。
- **step 有两副面孔**（`core.py:231-233`）：默认 `step`；当 `max_concurrent_batches > 1`（PP 或 async scheduling）时用 `step_with_batch_queue`（`core.py:625-739`）——维护 in-flight batch 队列，「调度新 batch 优先于收割旧 batch」，这是 PP 消泡 + 异步调度的关键机制（细节留阶段 1）。

### 4.3 调度器骨架（深读留阶段 1）

- 队列：`waiting`（优先级队列）+ `skipped_waiting` + `running`（`v1/core/sched/scheduler.py:187-190`）。
- **无 prefill/decode 阶段之分**：V1 调度器眼里每个请求只是让 `num_computed_tokens` 追上目标长度（`scheduler.py:441-450` 注释），chunked prefill 天然统一。
- **抢占 = 重算式**：仅当 `kv_cache_manager.allocate_slots()` 返回 None（KV 不足）时触发，FCFS 抢队尾 / 优先级策略抢最低优先级，被抢者 `num_computed_tokens=0` 放回 waiting 队首（`scheduler.py:576-625`、`_preempt_request` `:1274`）。
- 请求状态机（`v1/request.py:348-371`）：`WAITING → RUNNING → FINISHED_*`，旁路阻塞态 `PREEMPTED` / `WAITING_FOR_REMOTE_KVS`（P/D 分离等 KV 传输）/ `WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR` / `WAITING_FOR_STREAMING_REQ`。
- **structured output 三处介入**：① input IO 线程异步编译 grammar；② step 里 `get_grammar_bitmask` 生成 bitmask（大 batch 线程池并行，`v1/structured_output/__init__.py:244-271`）；③ `update_from_output` 里 `grammar.accept_tokens` 推进 FSM 校验（`scheduler.py:1817-1843`）。

### 4.4 DP 与 coordinator

- **负载均衡**：引擎在 step 前后发布 `(waiting, running, kv_cache_usage)`，coordinator 聚合转发前端；前端 `DPLBAsyncMPClient` 用打分公式选引擎（KV 压力 >50% 时惩罚 waiting 多的，`core_client.py:1493-1501`）。
- **MoE 同步 forward（wave 机制）**：EP 的 all2all 是集合通信，要求所有 DP rank lockstep；空闲 rank 跑 dummy batch 保持同步，all-reduce 确认全局 idle 才暂停，新请求来时 coordinator 广播 `START_DP_WAVE` 唤醒（`coordinator.py:347-365`、`core.py:2133-2188`）。
- **反直觉点**：非 MoE 的 DP rank 不走 wave 机制，直接把 dp_size 当 1 独立跑（`core.py:1307-1318`）——coordinator 的同步只为 MoE/EP 服务。

## 五、执行层四层结构

| 层 | 类 | 职责 | 实例数 |
|---|---|---|---|
| Executor | `v1/executor/abstract.py:37` | 控制面：向 worker 广播 RPC、协调 KV 初始化/编译/warmup；**不碰张量** | 每 EngineCore 1 个 |
| Worker | `v1/worker/gpu_worker.py:128` | 单卡载体：`init_device` / `load_model` / `determine_available_memory` / `compile_or_warm_up_model` / `execute_model`（含 PP 收发） | 每 TP/PP rank 1 进程 |
| ModelRunner | `v1/worker/gpu_model_runner.py:453` | 本 rank 执行大脑：input batch、attention metadata、forward 调度（cudagraph/piecewise/eager）、采样、bookkeeping | 每 Worker 1 个 |
| Model | 如 `LlamaForCausalLM` | 纯 `nn.Module`；构造签名统一为 `__init__(*, vllm_config, prefix="")` | 每 ModelRunner 1 个 |

Executor 按 `distributed_executor_backend` 选型：`uni` / `mp` / `ray` / `external_launcher`（`abstract.py:47-92`）。MultiprocExecutor 用**共享内存 MessageQueue** 广播 RPC（`multiproc_executor.py:151-157,388`），只有 `output_rank`（末个 PP stage 的 TP rank0）回传执行结果。

### 5.1 一次 execute_model 的骨架（`gpu_model_runner.py:4166-4535`）

```
preprocess:  _update_states（增删请求）→ _prepare_inputs（input_ids/positions/…）
             → _determine_batch_execution_and_padding（定 cudagraph 模式/微批）
             → _build_attention_metadata → _preprocess（MM encoder、embeds、PP 同步）
forward:     set_forward_context(...) → _model_forward → model(...)
postprocess: 末 PP stage：hidden_states[logits_indices] → compute_logits → 暂存，返回 None
sample_tokens（第二次 RPC）: grammar bitmask → Sampler/RejectionSampler
             → propose_draft_token_ids（投机草稿）→ _bookkeeping_sync（D2H 写回）
             → ModelRunnerOutput
```

### 5.2 KV cache 显存规划链（阶段 2 的主菜，先记骨架）

启动时四步（`core.py:143` 入口）：① `get_kv_cache_specs` 收集各层 spec → ② `determine_available_memory`：跑一次 dummy forward 做 memory profiling，再估 cudagraph 显存（`gpu_worker.py:460-611`）→ ③ `get_kv_cache_configs` 规划（`v1/core/kv_cache_utils.py`）→ ④ `initialize_from_config` 真正分配 tensor（`gpu_model_runner.py:7541`）。

### 5.3 编译与 cudagraph 挂载点

- 模型类上 `@support_torch_compile` 装饰器（`compilation/decorators.py:86`）→ `VllmBackend` 切图（`compilation/backends.py`）→ piecewise 子图逐段包 cudagraph（`compilation/piecewise_backend.py`、`cuda_graph.py`）。
- 运行时分派：`CudagraphDispatcher` 按 batch descriptor 选 FULL / PIECEWISE / NONE（`v1/cudagraph_dispatcher.py:15`）。
- 捕获时机：启动时 `compile_or_warm_up_model` → `capture_model`（`gpu_model_runner.py:6814`）。

### 5.4 模型解析与配置体系

- **模型 registry**：`ModelConfig.architectures`（来自 HF config）→ 全局 `ModelRegistry`（`model_executor/models/registry.py:1448`）懒加载解析 → 查不到可 fallback 到 transformers 实现。v0.27 起新一代模型实现放新的顶层目录 `vllm/models/`（deepseek_v4、kimi_k3、minimax_m3 等，已核实为上游目录，非 fork 私货）。
- **VllmConfig**：约 25 个子配置的聚合体（`config/vllm.py:331-429`），作为「引擎级全局状态」透传所有层——官方 arch_overview 把这条列为类层次设计的第一决策（新增特性只加配置字段，不改各层构造函数）。
- **平台抽象**：`platforms/`（cuda/rocm/cpu/tpu/xpu）负责设备校验与 attention backend 选择钩子（`platforms/interface.py:373`，CUDA 侧按 capability+配置取最高优先级候选，`platforms/cuda.py:397-456`）。

## 六、通信与序列化

### 6.1 前端 ↔ EngineCore（每对前端-引擎一组）

| 通道 | 前端侧 | 引擎侧 | 方向 |
|---|---|---|---|
| input | ROUTER (bind) | DEALER (connect) | 请求：`(identity, RequestType, payload)` |
| output | PULL | PUSH | `EngineCoreOutputs` |
| handshake | ROUTER | DEALER | 启动握手、交换地址 |

- 序列化：msgspec + msgpack 自定义编解码器（`v1/serial_utils.py:136`）；tensor/ndarray 走 zero-copy 额外 frame；多模态大张量可选 `torch_shm` 共享内存带外通道（`core_client.py:622-629`）。
- 消息类型 `EngineCoreRequestType`：`ADD / ABORT / START_DP_WAVE / UTILITY / EXECUTOR_FAILED / WAKEUP`；`UTILITY` 是通用反射 RPC（reset_prefix_cache、sleep 等都走它，`core.py:1521-1534`）。
- 输出侧极致优化：`encode_into` + bytearray 复用 + MessageTracker 零拷贝（`core.py:1795-1810`）；前端按 `VLLM_V1_OUTPUT_PROC_CHUNK_SIZE` 分块处理防阻塞事件循环（`async_llm.py:691`）。

### 6.2 EngineCore ↔ Worker

Executor 内部通道（非 ZMQ）：MultiprocExecutor 用共享内存 MessageQueue 广播 `(method, args, kwargs)`，worker 侧 `worker_busy_loop` 反射执行（`multiproc_executor.py:997-1022`）。

## 九、v0.27.1 相对「教科书 V1」的新变化

> 教科书描述（2024-2025 年的 V1 设计博客/早期代码）与现状的 diff，读源码时避免被旧印象误导：

1. **V0 彻底删除**：`vllm/engine/llm_engine.py` 和 `async_llm_engine.py` 各只剩 7 行 alias 指向 V1（已逐字核对）。
2. **Entrypoints 目录化大重构**：`serving_chat.py` → `openai/chat_completion/serving.py`；路由分散到各 `api_router.py` 统一挂载。
3. **Renderer 抽象**：tokenize 从引擎侧前移到 serving 之前的渲染层，`InputProcessor` 收的已是 tokenize 完的 EngineInput；raw prompt 入口已 deprecated。
4. **execute_model / sample_tokens 两相拆分**（见 §4.2）。
5. **AsyncScheduler**：调度时用 `num_output_placeholders` 预占产出名额，draft token 先 `[-1]` 占位后回填（`sched/async_scheduler.py:12-70`）。
6. **Model Runner V2**（`v1/worker/gpu/`，experimental）：把 input_batch/sample/spec_decode 等拆成模块的下一代 runner，开关 `use_v2_model_runner`。
7. **ubatching / DBO**：worker 侧把 batch 切 micro-batch 做计算-通信双流 overlap（`worker/ubatching.py:20`），调度层无感知。
8. **容错与弹性**：`enable_fault_tolerance`（worker/engine 双侧 sentinel）、Elastic EP 在线扩缩容（`coordinator.py:311-345`）。
9. **scale_out 前后端分离部署**：渲染放 CPU 节点、引擎放 GPU 节点，新增 `/render`、`/derender` 端点——P/D 分离思想向「渲染层」的外扩。
10. **流式输入/可恢复请求**：多轮会话可以 async generator 持续喂输入（`engine/protocol.py:29`）。
11. **`vllm/models/` 新顶层目录**：新一代模型实现（deepseek_v4、kimi_k3 等）不再塞 `model_executor/models/`。

## 思考与追问

1. **`step_with_batch_queue` 的「填队列优先」策略在 PP 下具体怎么消泡？** in-flight batch 上限 `max_concurrent_batches` 与 PP stage 数的关系、structured output 为何要推迟采样（`deferred_scheduler_output`）——挂阶段 1。
2. **AsyncScheduler 的 placeholder 机制收益边界在哪？** 调度与输出回收解耦后，什么负载下 TTFT/吞吐改善明显、什么负载下反而浪费名额——挂阶段 1（可结合 GPU 实测）。
3. **scale_out 把「渲染」也拆出去独立扩缩，是不是预示服务架构继续向「全链路 disaggregation」演化？** P/D 分离 → KV 传输 → 渲染分离，下一站是不是 sampler/detokenizer 也独立成服务——挂阶段 7，届时结合官方 roadmap 讨论。
