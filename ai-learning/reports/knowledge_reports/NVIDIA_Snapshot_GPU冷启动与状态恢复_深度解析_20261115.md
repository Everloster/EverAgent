# NVIDIA Snapshot：把初始化好的 GPU 进程变成可复用资产

一张空闲 GPU 不等于一个已经能够接收请求的模型副本。推理引擎还要启动进程、加载权重、准备运行时内存、编译和调优内核，甚至捕获 CUDA Graph。若扩容或故障恢复每次都重复这些步骤，资源已经分配出来，服务能力却迟迟不能上线。

NVIDIA Snapshot 的思路是：在兼容条件下保存一个已经完成初始化的 CPU/GPU 工作负载，再恢复它，而不是重做初始化。[1] 理解它的关键，是分清**模型文件、初始化后的运行状态、正在处理的用户请求**这三种不同对象。

## 1. 为什么只缓存权重还不够

模型检查点通常描述权重；一个能服务请求的进程，还包含更多已经完成的工作。

原文将冷启动分成四部分：[1]

1. **Startup**：启动引擎和工作进程、导入库、建立 GPU 间通信等。
2. **Model load**：读取权重，创建张量，并完成加载时需要的转换或重排。
3. **Initialization**：内存分析、KV Cache 与缓冲区准备，以及其他运行时初始化。
4. **Compilation、autotuning、graph capture**：编译、调优并建立可重放执行图。

因此，把权重提前放在高速存储里，只直接优化了其中一部分。Snapshot 保存的是完成这些步骤之后的进程状态，包括 CPU 和 GPU 内存，恢复时可以跳过重复初始化。

这也解释了为什么 Snapshot artifact 未必接近权重大小。原文一个 vLLM / Qwen3-0.6B / TP1 配置的权重为 1.50 GB，快照为 8.13 GB。[1] 快照存的是运行中的工作负载，而不只是参数文件；不能用模型权重大小直接预算快照存储。

## 2. Kubernetes 中谁发起保存与恢复

原文给出三种接口：[1]

| 操作 | 入口 | 含义 |
| --- | --- | --- |
| 保存已经运行的 Pod | `PodSnapshot` | 指定要保存的 Pod |
| 创建、等到就绪后再保存 | `SnapshotJob` | 建立用于快照的初始化工作负载 |
| 从快照创建新 Pod | `nvidia.com/restore-from` 注解 | 指向要使用的 `PodSnapshot` |

工作负载需要一个小型握手：在检查点前暂停，在恢复后继续。这让捕获状态发生在约定的位置，而不是任意一条指令执行到一半就假设能复制。

恢复目标不是任意硬件。文章明确要求相同 GPU 型号和驱动，并满足运行时及检查点兼容条件。支持的多 GPU 例子是在**单节点内部**，将多个 rank 作为一个检查点处理。[1]

所以，不能从“跨节点恢复”推导出“可以在不同 GPU 代际随意迁移”，也不能把单节点多卡支持扩展为任意多节点训练或推理作业的通用迁移承诺。

## 3. 恢复时究竟还有哪些工作

恢复不是瞬时的“指针切换”。原文将它拆为：

- **Agent setup**：定位快照，准备目标 Pod 和 GPU。
- **CRIU restore**：把进程映像从存储读回主机内存。
- **CUDA restore**：将 GPU 状态搬回 GPU 内存。
- **Wake/remap**：适配新节点并唤醒引擎。[1]

大模型恢复仍要搬运大量数据。作者在八卡 MoE 配置中报告，GPU 状态恢复约需 18—29 秒，CPU 进程恢复约需 4.2—10.8 秒。减少编译与初始化后，瓶颈转移到存储和内存传输，是符合机制的结果。[1]

由此可以推导出一种实际部署风险：单个副本恢复很快，并不保证几十个副本同时恢复也一样快。它们可能争用快照存储、网络和节点内存带宽。原文给出了单配置结果，未因此证明大规模同时恢复的尾延迟。

## 4. “恢复副本”不等于“恢复原来的对话”

原文的基准在每次检查点前触发 KV Cache 释放，因此用户请求对应的 KV Cache 不在快照 artifact 中。[1]

这项条件很重要。报告中的加速主要面向**把推理服务准备好**，不能用来声称正在进行的对话可以无缝从原 Token 位置继续。

如果一个产品需要请求级恢复，还要另外处理：

- 哪些用户输入和输出已经被接收或交付。
- 工具调用是否已经产生副作用。
- 重试会不会重复扣费、写入或发送消息。
- 请求状态和流式连接如何续接。

这些是本文由服务生命周期推导的边界，不是原文给出的请求恢复实现。Snapshot 与业务层的重试、幂等和状态管理解决不同问题。

## 5. 怎样正确阅读 8—36 倍的加速

原文基准使用 B200、特定驱动、VAST NFS，以及 vLLM 0.31.0、SGLang 0.5.21、TensorRT LLM 1.3.0。每个配置在同一硬件软件栈上比较冷启动与快照恢复。[1]

摘取三行展示不同规模，单位均为秒或 GB：

| 配置 | 快照大小 GB | 创建快照 s | 冷启动 s | 恢复 s |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-0.6B / vLLM / TP1 | 8.13 | 15.30 | 104.43 | 4.66 |
| GLM-5.3-NVFP4 / vLLM / TEP8 | 604.00 | 282.80 | 393.65 | 28.64 |
| DeepSeek-V4.1-Flash / vLLM / TEP8 | 647.18 | 274.75 | 1,110.65 | 30.96 |

这里的 speedup 是冷启动计时除以恢复计时。DeepSeek 这一行约为 35.87 倍，本次重新计算与原文一致。

但计时边界不包含拉取容器镜像和建立容器运行时；基础设施供给也不是被消除的初始化工作。若用户真正关心“提交扩容请求到副本可用”，还必须加上这些阶段。[1]

用一个**自拟条件**演示：若两条路径都有额外 120 秒的基础设施成本，总体加速变成：

\[
\frac{120+1110.65}{120+30.96}\approx8.15
\]

120 秒不是作者测量值；它只说明同一项局部优化，在更长的端到端流程里会被其他成本稀释。本次已实际计算该结果。

## 6. 创建快照的成本，什么时候能收回

设：

- \(C\)：一个未来副本的冷启动时间。
- \(R\)：一个未来副本的恢复时间。
- \(P\)：为复用快照付出的准备成本。
- \(k\)：后续需要启动的副本次数。

在不计并行和资源争用的简化时间账本里，快照方案节省累计工作时间的条件是：

\[
P+kR<kC\quad\Longleftrightarrow\quad k(C-R)>P
\]

若已经有一个初始化好的副本，\(P\) 可以只计算快照创建。对于表中的 GLM 配置，\(P/(C-R)\approx0.775\)，因此第一次未来恢复就能抵消创建成本。这与原文在所测配置中的观察一致。[1]

但如果需要专门从零创建一个种子副本，\(P\) 还要包含种子的初始化成本；若模型、驱动或运行配置频繁变化，需要重新生成 artifact，复用次数也会下降。原文的“第一次恢复就回本”，不能忽略它所比较的成本边界。

时间账本也不等于云账单：存储占用、带宽费用、预备副本资源与并发恢复都会影响实际成本。

## 7. 与缓存、弹性和安全的关系

Snapshot 可以理解为缓存“已经做完的初始化工作”，但它需要比普通文件缓存更严格的兼容性管理。模型版本、运行时配置、硬件与驱动改变后，旧快照是否还能使用，需要由支持矩阵和验证决定，而不是仅比较模型名称。

它与[EPD 拆分](./vLLM_EPD_多模态编码拆分与数据交接_深度解析_20261115.md)也可以互补：EPD 决定不同服务阶段如何独立扩展，Snapshot 减少兼容副本上线时重复初始化的时间。文章没有给出二者组合后的测量，本文不据此承诺叠加收益。

保存进程内存还带来数据治理问题。即使基准释放了 KV Cache，其他内存中仍可能包含配置、凭据或应用状态。把 artifact 当成普通公共模型权重发布是不合适的。这是由快照内容推导的安全要求；本文未审计 Snapshot 对具体敏感数据的处理。
