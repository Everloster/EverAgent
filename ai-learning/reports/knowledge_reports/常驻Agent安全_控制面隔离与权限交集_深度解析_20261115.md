# 常驻 Agent 怎样安全运行：把能力留给模型，把权限留在模型之外

常驻 Agent 的难题，不只是它可能听信一段恶意文本，而是它能把一次错误判断变成持续发生的操作。它可以修改工作文件、生成程序、调用服务，并在用户离开后继续执行。真正需要回答的是：**模型判断错了，哪些约束仍然有效？发现问题以后，又能切断哪些能力？**

OpenAI 在 2026 年 11 月 12 日的工程文章中，介绍了其内部部署 OpenClaw 的做法：隔离控制面与执行环境，用沙箱约束行动，引入模型审查，并为 Agent 配置独立身份和受限的审计日志。[1] 本文重构这套设计的因果关系，不把内部部署经验当成经过独立验证的通用安全证明。

## 1. 为什么“可信的模型”不是信任边界

普通程序同样会有漏洞，但部署者通常希望它的权限配置保持稳定。常驻 Agent 还会生成新的程序，甚至尝试修改自己的配置。它读取的文档、工具结果与外部网页，也可能影响下一步计划。[1]

这使两类东西必须分开：

- **决定允许做什么的组件**：身份、网络规则、沙箱和配置管理。
- **决定尝试做什么的组件**：模型、执行 Harness，以及模型生成的代码。

前者是控制面，后者是执行环境。OpenAI 的具体做法是支持远程 Harness 执行，让 OpenClaw Gateway 与 Agent Harness 位于不同容器；其内部部署还进一步分开集群。Gateway 负责配置 Agent，Agent 工作负载按不可信代码处理。[1]

这里的“可信”不是“绝无漏洞”，而是一个明确的工程假设：控制逻辑由常规静态代码实现，Agent 不能通过写自己的工作目录来改掉它。若把权限文件放进 Agent 可写目录，再让执行器直接采纳它，所谓安全配置便成了模型可修改的普通输入。

## 2. 四条硬边界，分别限制四种后果

原文将沙箱控制分为网络、文件、进程和秘密四类。[1]

| 边界 | 限制的对象 | 原文中的做法 | 仍需注意的范围 |
| --- | --- | --- | --- |
| 网络 | 可以连接的目的地 | 组织管理的允许列表，以及显式拒绝规则 | 获准访问一个域名，不等于获准执行该域名下所有业务动作 |
| 文件 | 可读、可写的路径 | 只允许写 Agent 工作目录，管理资产只读 | 文件权限不能代替网络数据出口控制 |
| 进程 | 能影响的其他进程 | 使用 Codex Linux 沙箱提供隔离 | 子进程及其生命周期也属于执行管理问题 |
| 秘密 | 凭据如何进入请求 | 使用 credential broker，不直接向 Agent 暴露秘密 | 隐藏凭据不等于限制了凭据代表的所有权限 |

原文同时展示了 `requirements.toml` 与 `config.toml`：前者限制可选择的配置范围，后者选择实际配置。例如，管理员可以限制允许的沙箱模式，不提供无限制运行选项，并禁止用户级配置扩大网络允许列表。[1]

关键不在于某一个配置键，而在于**上层约束不能被下层选择放宽**。即使 Agent 能选择一种工作模式，也只能在组织允许的集合内选择。

秘密管理也体现同一个原则。环境变量过滤只处理环境变量；原文特意说明，这并不能隐藏可访问文件里保存的凭据。把 Token 从环境中移除，却仍允许 Agent 读取存有 Token 的文件，不能算完成凭据隔离。[1]

## 3. 模型审查应当减少人工负担，而不是替代沙箱

OpenAI 为其部署中的 Agent 行动启用 Auto-review：另一个 Agent 监控、批准主 Agent 的动作，让人工注意力集中在有价值的审批上。原文指出，反复要求人点击许可，会造成审查疲劳。[1]

但第二个模型仍然可能判断失误。因此，理解这层设计时，应把模型审查与确定性权限看成不同职责：

- 沙箱回答：**这个动作有没有资格执行？**
- 模型审查回答：**有资格的动作，在当前任务里是否合理？**

下面的关系是本文给出的工程抽象，不是原文公布的内部算法：

\[
\text{可执行动作}=\text{硬策略允许}\ \land\ \text{所需审批通过}
\]

其中“硬策略允许”代表文件、网络、资源范围等确定性检查；“所需审批通过”代表该动作要求的模型或人工批准。两者是交集，不是取一个更宽松的结果。

例如，Agent 被要求整理一个代码仓库中的问题。审查模型可能认为“将诊断资料上传到一个新服务”有助于排障，但若目的地不在允许范围，动作仍应被拒绝。模型对任务价值的判断，不能变成网络策略的修改权限。

反过来，一个域名在允许列表里，也不能证明写操作已经获得用户授权：允许读取代码托管服务，不意味着允许发布项目、邀请成员或修改权限。这是资源可达性与业务授权之间的区别。

## 4. 一个离线示例：批准不能扩大权限

下面是自拟教学模型，只演示判定顺序，不是沙箱实现，也不运行真实网络或文件操作。

```python
ALLOWED = {("issue", "read"), ("workspace", "write")}

def can_run(resource, action, approved, active=True):
    return active and (resource, action) in ALLOWED and approved
```

本次实际运行了五个断言：

| 输入 | 结果 | 说明 |
| --- | --- | --- |
| 读取 issue，审批通过，身份有效 | 允许 | 三个条件同时满足 |
| 写工作目录，审批通过，身份有效 | 允许 | 授权内的写入不必一概禁止 |
| 写 issue，审批通过，身份有效 | 拒绝 | 审批不能创造不存在的写权限 |
| 读取 issue，审批未通过，身份有效 | 拒绝 | 硬策略允许仍不足以执行 |
| 读取 issue，审批通过，身份已停用 | 拒绝 | 历史批准不能覆盖撤销状态 |

五个断言均通过。这个结果只验证示例的布尔逻辑，不证明操作系统沙箱、凭据代理或真实审批系统具备相同保证。

它还提示一个容易遗漏的问题：检查与执行之间可能发生变化。若权限已经撤销，但执行器继续使用旧的批准缓存，上面的逻辑并不能自动解决它。真实系统还需要决定批准绑定哪些具体参数、有效多久，以及执行时是否重新检查。这是由示例推导出的实现问题，原文没有给出这些细节。

## 5. 独立身份、服务账号和日志各自解决什么

原文区分 Agent 身份与服务账号。Agent 身份用于识别具体执行者、关联授权和追踪动作；服务账号提供访问某项服务的凭据，两者应建立关联，而不是互相替代。OpenAI 的实例中，每个 Agent 的唯一身份关联一个 ChatGPT Service Account，使用独立于用户的推理凭据，并可停止其推理访问。[1]

可以把一次动作拆成三种责任：

1. **谁要求的**：用户或组织给出的任务与授权。
2. **谁执行的**：具体 Agent 实例及其配置。
3. **凭什么访问**：代表某个权限范围的服务凭据。

如果所有动作都混用用户账号，事后很难区分用户直接操作与 Agent 自主决定，也难以只撤销一个失常 Agent 而不影响其他工作。

不过，“关掉推理”不必然等于“停止所有副作用”。已经启动的子进程、排入外部系统的任务，或尚未撤销的服务凭据，可能继续工作。这是系统生命周期的推论，不是本文观察到的 OpenAI 故障。停机设计应分别考虑推理、工作负载、网络访问和外部授权。

日志用于把上述关系串起来。原文记录控制面配置变更与 Agent 的所有轮次，同时限制日志访问，因为轮次本身可能含敏感信息。[1] 这意味着观测系统也有自己的权限边界：不能为了审计，把原本受限的数据复制到人人可读的日志平台。

## 6. 学到的不是“一套配置”，而是一种职责分配

这篇文章最值得迁移的设计是：让模型负责提出行动，让不可由模型任意修改的系统决定行动上限。模型审查补充任务语境，身份把操作关联到具体执行者，日志帮助解释发生了什么，撤销机制负责结束授权。

检验自己是否真正理解，可以问三个问题：

- Agent 修改自己的配置文件后，哪个组件仍能阻止权限扩大？
- 凭据对模型不可见时，哪些不当操作仍然可能借凭据代理发生？
- 发现异常后，“停止推理”之外还有哪些正在执行的工作需要处理？

若这些问题只能回答“提示词已经禁止了”，说明约束仍主要停留在模型行为层，而没有落实到执行层。
