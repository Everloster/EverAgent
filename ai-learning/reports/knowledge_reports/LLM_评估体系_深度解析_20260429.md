# LLM 国内外主流评估体系详解：基准评测、Leaderboard 与场景匹配优先级

> 研究日期：2026-04-29  
> 研究对象：大语言模型评估体系、基准测试、国内外主流评测网站、leaderboard 解释与应用场景选型  
> 核心结论：**不存在一个“总榜第一 = 所有场景最好”的评估体系。LLM 评估必须从“能力维度 × 任务场景 × 风险约束 × 成本延迟”四个轴组合判断。**

---

## 0. 执行摘要

LLM 评估从 2020 年的 MMLU 式静态考试，演化到 2026 年的动态、偏好、代码代理、安全、多模态和行业专用评测。早期 leaderboard 更像“高考榜”，今天的评估体系更像“体检报告 + 岗位面试 + 试用期观察”。

如果只看一个榜，最容易犯三类错误：

1. **把静态知识题当成真实产品能力**：MMLU、C-Eval、CMMLU 能测知识覆盖，但不能充分代表长对话、工具调用、代码仓库修改、企业流程执行。
2. **把人类偏好当成事实正确性**：Chatbot Arena / LMArena 很接近用户感知，但偏好票不等于数学正确、代码可运行、法律合规。
3. **把单项高分当成综合能力**：SWE-bench、BFCL、GPQA、MMMU 等只覆盖特定能力，应作为场景准入门槛，而不是全局排名。

本报告建议的评估优先级是：

- **通用聊天 / 用户体验**：LMArena / Chatbot Arena 优先，辅以 MT-Bench / WildBench / HELM Instruct。
- **知识与通用推理**：MMLU-Pro、GPQA、LiveBench、HLE 优先，MMLU 只作历史参照。
- **中文与中国本土场景**：C-Eval、CMMLU、SuperCLUE、OpenCompass 中文榜优先。
- **代码生成**：HumanEval/MBPP 只作入门，BigCodeBench、LiveCodeBench、SWE-bench Verified/Pro 更有实战意义。
- **Agent 与工具调用**：BFCL、τ-bench、SWE-bench、WebArena / OSWorld / GAIA 更接近真实可执行任务。
- **企业选型**：公开榜只做初筛，必须叠加私有任务集、成本、延迟、稳定性、安全与合规评估。

## 2. 层次一：直觉类比

评价一个 LLM，不像评价一台跑车只看最高时速，更像招聘一个复杂岗位的人：

- **MMLU / C-Eval** 像笔试：能看知识面，但笔试高分不代表会做项目。
- **GPQA / HLE** 像专家面试：问题很难，能区分顶尖候选人，但题量和场景仍有限。
- **Chatbot Arena** 像真实用户盲测：很接近“大家更喜欢谁”，但容易受表达风格、品牌、语言和提示分布影响。
- **SWE-bench** 像试用期派一个真实 GitHub issue：能不能改代码、跑测试、修 bug，比答算法题更接近工程岗位。
- **BFCL / WebArena / OSWorld** 像给候选人一个办公系统：看他会不会调用工具、维护上下文、处理失败。
- **HELM / OpenCompass** 像系统化体检：不只看智力，还看安全、偏见、鲁棒性、效率和可复现性。

所以评估的第一原则是：**先问“我要雇它做什么”，再问“哪个榜能代表这个工作”。**

## 3. 层次二：评估体系的基本分类

### 3.1 静态闭卷基准

静态闭卷基准使用固定题集和客观答案，通常以 accuracy、pass@1、exact match 等指标计分。

代表：

- **MMLU**：57 个学科，多项选择题，衡量知识与问题求解。
- **MMLU-Pro**：在 MMLU 基础上提高难度，减少噪声，引入更多选项，更强调推理。
- **C-Eval**：中文多学科考试题，覆盖中学、大学、专业等层级。
- **CMMLU**：中文多任务语言理解，覆盖自然科学、社科、工程、人文等。
- **GSM8K / MATH / AIME**：数学推理。
- **HumanEval / MBPP**：小函数代码生成。

优点：

- 成本低、可复现、容易横向比较。
- 对基础能力和知识覆盖有较强信号。
- 适合快速筛掉明显弱模型。

缺点：

- 容易数据污染和榜单过拟合。
- 多项选择题不等于开放式任务能力。
- 对长上下文、工具调用、真实交互和安全风险覆盖不足。

### 3.2 动态去污染基准

动态基准试图通过持续更新题目、使用近期来源或隐藏测试集，降低训练数据污染。

代表：

- **LiveBench**：使用近期数据源和可客观评分任务，覆盖数学、编码、推理、数据分析、指令遵循、语言等类别。
- **LiveCodeBench**：更聚焦代码能力，题目随时间更新。
- **Humanity's Last Exam (HLE)**：面向专家级闭式问题，试图把难度推到“前沿知识”级别。
- **ARC-AGI / ARC Prize**：强调抽象推理与少样本泛化，争议较大但能补足常规题型盲区。

优点：

- 更抗污染，更能区分前沿模型。
- 题目更新让“背题”收益下降。
- 对 2026 年后的模型选型比老榜更有参考价值。

缺点：

- 新榜样本、稳定性和社区共识需要时间积累。
- 排名可能随版本快速波动。
- 高难闭式题不一定代表真实工作流表现。

### 3.3 人类偏好与 LLM-as-Judge

这一类不只看答案对不对，而看用户或裁判模型更偏好哪个输出。

代表：

- **Chatbot Arena / LMArena**：匿名双模型对战，由用户投票，用 Bradley-Terry / Elo 类模型估计排名。
- **MT-Bench**：多轮对话题集，用强模型裁判打分。
- **AlpacaEval / Arena-Hard / WildBench**：开放式指令跟随和偏好评估。
- **SuperCLUE**：中文语境下结合用户查询、开放式问答、闭式题的综合评估。

优点：

- 更贴近聊天、写作、角色扮演、总结、客服等开放式体验。
- 能捕捉“表达质量、帮助程度、交互感”。
- 对产品经理和应用开发者很有用。

缺点：

- 用户偏好不等于事实正确。
- 可能偏好自信、流畅、礼貌但错误的回答。
- LLM-as-Judge 存在裁判偏差、位置偏差、风格偏差和同源模型偏好。

### 3.4 代码与软件工程基准

代码能力已经从“小函数生成”转向“真实仓库修改”。

代表：

- **HumanEval / MBPP**：经典代码生成入门题。
- **BigCodeBench**：更强调库调用、API 使用和复杂结构。
- **LiveCodeBench**：动态代码题，降低污染风险。
- **SWE-bench / SWE-bench Lite / SWE-bench Verified / SWE-bench Pro**：从真实 GitHub issue 生成修复补丁，用测试判断是否解决问题。
- **Aider polyglot / terminal coding benchmarks**：更接近 coding agent 的命令行工作流。

优点：

- 可执行、可自动评分。
- SWE-bench 类任务接近真实工程修改。
- 对 coding assistant / coding agent 选型非常关键。

缺点：

- 运行成本高，环境构建复杂。
- patch 通过测试不代表代码质量、可维护性、安全性都好。
- 已公开数据集仍会逐渐污染，需要关注 Verified/Pro/动态版本。

### 3.5 Agent、工具调用与工作流评估

2025-2026 年，模型是否会“用工具办事”成为评估重点。

代表：

- **BFCL (Berkeley Function Calling Leaderboard)**：函数调用、API 选择、参数生成、多语言、多函数、多轮工具使用。
- **τ-bench**：面向真实业务流程的 tool-agent 评测，强调策略、状态和交互成功率。
- **GAIA**：需要搜索、推理、工具使用和多步组合的问题。
- **WebArena / VisualWebArena**：在网页环境中完成任务。
- **OSWorld**：在真实或模拟桌面操作系统环境中完成任务。
- **SWE-bench**：也可视为软件工程 agent 评测。

优点：

- 更接近“AI 员工”或“AI 操作员”。
- 能测到工具选择、状态维护、错误恢复、长程规划。
- 对企业自动化、RPA、代码代理、数据分析代理更关键。

缺点：

- 评测运行成本高，复现难度高。
- 结果强依赖 agent harness、工具接口、提示模板和上下文管理，不只是底座模型能力。
- 一个模型在 BFCL 高分，不一定在复杂业务系统里稳定。

### 3.6 安全、对齐与责任评估

安全评估看的是模型在不良输入、偏见、隐私、危险能力、越狱攻击下的行为。

代表：

- **HELM Safety / AIR-Bench**：安全、多指标、透明评估。
- **BBQ / StereoSet / CrowS-Pairs**：偏见与刻板印象。
- **ToxiGen / RealToxicityPrompts**：毒性输出。
- **AdvBench / HarmBench / JailbreakBench**：有害请求、越狱鲁棒性。
- **CyberSecEval、biosecurity / autonomy evals**：高风险能力评估。

优点：

- 企业和公共场景部署必需。
- 能发现“能力强但风险高”的模型。
- 对医疗、金融、教育、政务尤其重要。

缺点：

- 安全边界随政策和攻击方法变化很快。
- 高拒答率不等于真正安全，可能牺牲正常可用性。
- 很多安全结果和系统提示、工具权限、部署策略强相关。

### 3.7 多模态与长上下文评估

现代模型已经不是纯文本模型。评估也必须覆盖图像、视频、音频、文档、屏幕和超长上下文。

代表：

- **MMMU / MMBench / MathVista / ChartQA / DocVQA**：图文理解、学科推理、图表文档问答。
- **Video-MME / MVBench**：视频理解。
- **RULER / Needle-in-a-Haystack / LongBench**：长上下文检索和推理。
- **VHELM / VLMEvalKit / OpenCompass VLM leaderboards**：多模态综合评测框架。

优点：

- 适合文档处理、图表分析、视觉问答、视频理解、桌面自动化。
- 长上下文榜能发现“标称上下文很长但有效利用不足”的模型。

缺点：

- 多模态评分常常更难自动化。
- 长上下文 needle 题可能高估真实文档推理能力。
- 图表、PDF、扫描件、屏幕 UI 的真实复杂度常高于公开题。

## 4. 层次三：国内外主流评测网站与 Leaderboard 解读

### 4.1 国外主流评测网站

| 网站 / 项目 | 核心定位 | 主要信号 | 适合用途 | 注意事项 |
|---|---|---|---|---|
| LMArena / Chatbot Arena | 真人盲测偏好榜 | 用户偏好、开放对话体验 | 通用聊天、写作、创意、客服初筛 | 偏好不等于事实正确；分语言和类别看更好 |
| Stanford HELM | 透明、可复现、多指标评估框架 | 能力、安全、公平、鲁棒、效率 | 研究、合规、模型体检 | 框架严谨但不等于每个最新模型都即时覆盖 |
| Hugging Face Open LLM Leaderboard | 开源模型排行榜 | 标准基准组合 | 开源模型初筛 | 只适合开放模型，榜单版本变化需注明 |
| LiveBench | 动态去污染通用榜 | 近期题、客观评分、多类别 | 前沿模型横向比较 | 新题和版本波动需关注 |
| SWE-bench | 真实 GitHub issue 修复 | 软件工程 agent 能力 | coding agent 选型 | 受 harness 影响大；关注 Verified/Pro |
| BFCL | 函数调用与工具使用 | API 调用准确性、参数生成、多轮工具 | tool-use / agent 平台 | 函数调用只是 agent 的一部分 |
| Papers with Code / EvalPlus | 论文与任务指标聚合 | 各 benchmark 实验结果 | 研究检索 | 结果来源不总是同一协议 |

#### LMArena / Chatbot Arena 怎么读

Chatbot Arena 的关键价值在于“真实用户、匿名对战、偏好投票”。它适合回答：**普通用户更喜欢哪个模型的开放式回答？**

读榜时应看四点：

1. **Overall 不是唯一答案**：Coding、Math、Creative Writing、Long Conversation 等子榜比总榜更有场景意义。
2. **置信区间很重要**：分数接近的模型不要过度解读名次差异。
3. **新模型 preliminary 要谨慎**：样本票数不足时波动大。
4. **偏好票会奖励表达风格**：有时“更像人、更自信、更长”会赢，但未必更准确。

#### HELM 怎么读

HELM 的价值不在于给一个“最强模型”，而在于给一份多维报告。它强调：

- broad coverage：覆盖不同任务、域、语言。
- multi-metric：准确率之外，还看 calibration、robustness、fairness、bias、toxicity、efficiency。
- standardization：同一适配方式、同一评估协议。
- transparency：公开 prompts、responses 和可复现流程。

因此 HELM 更适合研究者、企业架构师和治理团队，而不是只想问“今天哪个模型聊天最好”的用户。

#### Hugging Face Open LLM Leaderboard 怎么读

它更适合开源模型初筛。Open LLM Leaderboard v2 引入更难的组合，如 MMLU-Pro、GPQA、MATH、IFEval、BBH 等，试图缓解旧榜饱和。

关键注意：

- 它更偏“开源模型统一考试”，不是闭源 API 全量排名。
- 版本变化会改变可比性。
- 模型可能针对 leaderboard 优化，最终仍需私有任务验证。

#### LiveBench 怎么读

LiveBench 的优势是动态和客观评分：用近期来源、定期更新问题，尽量减少污染，并避免 LLM judge 在难题上不稳定。

适合用来判断前沿模型是否真的在变强，尤其是数学、编码、推理、数据分析和指令遵循等综合能力。

#### SWE-bench 怎么读

SWE-bench 不是“会不会写代码”的普通测试，而是“能不能在真实仓库里修 issue”。它通常比 HumanEval 更接近 coding agent 的实际价值。

读榜要区分：

- **base model**：只测底座模型在固定 harness 下表现。
- **agent system**：模型 + 检索 + 工具 + 多轮尝试 + review 的系统表现。
- **Verified / Pro**：更强调问题清晰、测试可靠、任务可解和抗污染。

如果你的场景是 IDE 自动补全，SWE-bench 不是唯一指标；如果你的场景是“让 agent 接 issue 自己改仓库”，SWE-bench 权重应非常高。

#### BFCL 怎么读

BFCL 测的是函数调用：模型是否能选对函数、填对参数、处理多函数、并行调用、REST/SQL/Python/Java/JavaScript 等多语言接口。

它适合评估：

- 企业工作流 agent。
- API 编排。
- MCP / function calling / tool use。
- 低代码自动化平台。

但 BFCL 高分并不保证完整 agent 强，因为完整 agent 还需要任务规划、状态管理、权限控制、错误恢复和长期记忆。

### 4.2 国内主流评测网站与体系

| 网站 / 项目 | 核心定位 | 主要信号 | 适合用途 | 注意事项 |
|---|---|---|---|---|
| OpenCompass | 国内重要开源评测平台与榜单 | 多数据集、多模型、中文/英文/多模态/行业 | 中文模型、开源模型、综合能力比较 | 需关注具体榜单和配置 |
| C-Eval | 中文多学科考试评测 | 中文知识与推理 | 中文基础能力、教育/考试场景 | 多项选择题，不代表开放对话 |
| CMMLU | 中文多任务语言理解 | 中文跨学科知识 | 中文模型横向比较 | 仍偏静态闭卷 |
| SuperCLUE | 中文开放式与闭式综合评测 | 中文用户偏好、开放问答、闭式题 | 中文聊天助手、产品体验 | 评测协议和版本需注明 |
| CLUE / FewCLUE | 传统中文 NLP 任务 | 分类、抽取、理解 | 小模型/传统 NLP 参照 | 对现代 LLM 不够完整 |
| CompassArena / 相关中文 Arena | 中文偏好评测 | 中文真实用户偏好 | 中文对话产品 | 样本、题目分布和裁判方式需核验 |

#### OpenCompass 怎么读

OpenCompass 的定位接近“评测工具链 + 榜单 + 中文生态”。它支持大量模型和数据集，覆盖语言、知识、推理、代码、多模态、行业等方向。

它的价值：

- 对中国模型生态覆盖更全，如 Qwen、GLM、ERNIE、Baichuan、InternLM、Spark、MiniMax 等。
- 能复现评测流程，而不仅是看榜。
- 支持 API 和开源模型，适合本地化评测。

注意：

- 不要只看总分，要看具体 benchmark 组合。
- 中文模型在中文榜高分，不代表英文、代码、工具调用、长上下文同样强。
- 多模态和 agent 榜要单独看，不要和纯文本榜混用。

#### C-Eval 怎么读

C-Eval 是中文考试式评测的代表，覆盖 52 个学科和四个难度层级，另有 C-Eval Hard 子集。

适合：

- 中文知识覆盖。
- 中文教育、考试、基础推理。
- 对比中文-oriented 模型与英文模型在中文语境下的差距。

不适合单独决定：

- 企业客服模型。
- 长文档问答。
- 复杂工具调用。
- 创意写作与产品体验。

#### CMMLU 怎么读

CMMLU 与 C-Eval 类似，强调中文多任务、多学科理解。它适合做中文基础能力横向比较，尤其用于判断模型是否真正具备中文文化、社会、工程与人文知识。

但它仍然是静态 benchmark，所以需要和开放式中文偏好评测、企业私有中文任务集结合。

#### SuperCLUE 怎么读

SuperCLUE 的核心价值是把中文开放式场景纳入评估。它关注用户偏好，而不只闭式题 accuracy。

适合：

- 中文通用助手。
- 中文客服、写作、摘要、问答。
- 需要衡量“回答是否让中文用户满意”的场景。

局限：

- 偏好评测仍需防止裁判偏差。
- 结果要结合题目版本和模型版本。

## 5. 主流 Benchmark 逐项解读

### 5.1 MMLU：历史基准，不再足够区分前沿模型

MMLU 发布于 2020 年，覆盖 57 个学科，曾经是 LLM 通用知识评测的事实标准。它的贡献是把“多任务、多学科、少样本能力”统一到一个可比较框架中。

今天的定位：

- 仍可作为基础知识覆盖的历史参照。
- 对中小模型、开源模型初筛仍有用。
- 对前沿闭源模型已明显饱和，不能单独说明能力领先。

适配优先级：

- 基础模型初筛：中。
- 前沿模型比较：低。
- 企业选型：低到中，只作健康检查。

### 5.2 MMLU-Pro：MMLU 的更难版本

MMLU-Pro 用更多选项、更高难度和专家验证来提高区分度，目标是减少 MMLU 饱和和 prompt 敏感问题。

适配优先级：

- 通用知识与复杂推理：高。
- 前沿模型横向比较：中到高。
- 中文场景：低，需要 C-Eval / CMMLU 补充。

### 5.3 GPQA：专家级科学推理

GPQA 由生物、物理、化学领域专家编写，题目数量不大但难度高，并强调“Google-proof”。它尤其适合衡量模型在高难科学问题上的可靠性。

适配优先级：

- 科学研究助手：高。
- 通用聊天：中。
- 企业流程自动化：低到中。

注意：

- GPQA 高分不代表医学、法律、金融等所有专业域都可靠。
- 题量较小，最好结合专业私有题集。

### 5.4 HLE：前沿专家知识压力测试

Humanity's Last Exam 试图构造覆盖广泛专家学科的高难闭式问题。它适合衡量模型是否接近“广谱专家知识”。

适配优先级：

- 前沿模型研究：高。
- AGI 讨论参考：中。
- 企业模型选型：低到中，除非企业任务本身需要专家级闭式知识。

注意：

- HLE 高分不等于 AGI。
- 闭式专家题不等于开放式研究能力或自主任务能力。

### 5.5 GSM8K / MATH / AIME：数学推理

数学 benchmark 能较好测出多步推理、符号操作和 test-time compute 能力。

适配优先级：

- 数学、教育、竞赛、科学推理：高。
- 普通客服：低。
- coding agent：中，因为数学推理和代码推理部分相关。

注意：

- GSM8K 已较饱和。
- AIME 等竞赛题更能区分推理模型，但仍不是业务推理全貌。

### 5.6 IFEval：指令遵循

IFEval 测模型是否严格满足格式、长度、关键词、结构等指令约束。

适配优先级：

- API 输出 JSON、结构化生成：高。
- Agent 工具调用前置：高。
- 创意写作：中。

注意：

- 指令遵循强不代表事实正确。
- 企业系统常需自建格式校验和 retry 机制。

### 5.7 HumanEval / MBPP：代码入门基准

这两个 benchmark 对小函数生成很经典，但越来越像“代码高考基础题”。

适配优先级：

- 代码模型基础筛选：中。
- 真实代码助手：低到中。
- coding agent：低。

### 5.8 BigCodeBench / LiveCodeBench：更实用的代码基准

BigCodeBench 更强调库、API、复杂程序结构；LiveCodeBench 通过动态题降低污染。

适配优先级：

- 代码生成模型：高。
- IDE 助手：高。
- 软件工程 agent：中，需要 SWE-bench 补充。

### 5.9 SWE-bench：真实软件工程能力

SWE-bench 把模型放进真实 GitHub issue 场景，要求生成 patch 并通过测试。

适配优先级：

- coding agent：极高。
- 自动修 bug：极高。
- 普通代码补全：中。

注意：

- harness 影响很大，系统榜和模型榜要分开读。
- 通过测试不等于最佳工程实现。
- Verified/Pro 比原始榜更适合前沿模型比较。

### 5.10 BFCL：函数调用能力

BFCL 衡量模型调用工具的准确性，包括函数选择、参数生成、多函数、多轮、并行调用和不同接口类型。

适配优先级：

- 企业 API agent：极高。
- MCP / function calling 框架：极高。
- 纯聊天：低。

### 5.11 GAIA / WebArena / OSWorld：综合 Agent 任务

这类 benchmark 测的是“在环境里完成任务”，而不只是回答问题。

适配优先级：

- 浏览器 agent：高。
- 桌面 agent：高。
- 多工具研究助手：高。
- 普通问答：低。

注意：

- 系统工程影响超过单一模型。
- 结果需要拆解为模型能力、工具能力、记忆、规划、错误恢复。

### 5.12 MMMU / MMBench / MathVista：多模态理解

多模态 benchmark 测图像、图表、文档、数学图形、科学题等。

适配优先级：

- 文档 OCR + 问答：高。
- 图表分析：高。
- 教育解题：高。
- 纯文本客服：低。

### 5.13 LongBench / RULER / Needle：长上下文

长上下文评估要区分“能放进去”和“能用起来”。

适配优先级：

- 长文档、合同、代码库、知识库：高。
- 普通短聊天：低。

注意：

- Needle-in-a-Haystack 高分只能说明检索能力，不等于长文档综合推理能力。
- 企业长上下文任务要自测引用准确率、遗漏率和权限隔离。

## 6. 评测指标怎么理解

### 6.1 Accuracy

适合闭式题，如 MMLU、C-Eval、GPQA。优点是直观，缺点是无法衡量开放式输出质量。

### 6.2 Pass@k / Pass@1

常用于代码题。Pass@1 更接近用户一次生成体验，Pass@k 更接近“允许多次采样再筛选”的系统能力。

### 6.3 Elo / Bradley-Terry 分数

常用于 Arena 类偏好榜。它表示基于对战胜负估计出的相对强弱，不是百分制。

读法：

- 分数差距大且置信区间不重叠，才说明显著差异。
- 新模型票数少时不要过度解读。
- 子类别分数比总分更贴近具体场景。

### 6.4 Win Rate

常用于偏好评测或 A/B 测试。胜率依赖对手集合，不能脱离比较对象。

### 6.5 Exact Match / F1

常用于问答和信息抽取。适合短答案，不适合开放式解释。

### 6.6 LLM-as-Judge Score

适合开放式评测，但要防偏差：

- 裁判模型可能偏好自己的风格。
- 长答案可能被高估。
- 位置顺序可能影响结果。
- 需要多裁判、多轮、隐藏模型名、人工抽检。

### 6.7 Cost / Latency / Throughput

评估不能只看质量。企业最终关心的是：

```text
有效能力 = 任务成功率 × 稳定性 × 安全性 / (成本 × 延迟 × 运维复杂度)
```

高分模型如果延迟太高、价格太贵、上下文成本失控，在生产中可能不是最优。

## 7. 场景匹配优先级矩阵

### 7.1 总体矩阵

| 场景 | 第一优先评测 | 第二优先评测 | 必须自建评测 | 不应过度依赖 |
|---|---|---|---|---|
| 通用聊天助手 | LMArena 子榜、MT-Bench、WildBench | MMLU-Pro、IFEval、安全榜 | 高频用户 query、拒答边界、品牌语气 | MMLU 总分 |
| 中文聊天 / 中文客服 | SuperCLUE、OpenCompass 中文、C-Eval/CMMLU | LMArena 中文类别、IFEval | 企业中文语料、方言、政策口径 | 英文总榜 |
| 企业知识库问答 | LongBench/RULER、RAG 自测、事实性评测 | MMLU-Pro、中文 benchmark | 私有文档引用准确率、权限隔离、幻觉率 | Chatbot Arena 总榜 |
| 代码补全 | HumanEval、MBPP、BigCodeBench、LiveCodeBench | Aider / repo-level coding eval | 公司代码风格、框架、单测通过率 | 通用聊天榜 |
| 自动修 bug / coding agent | SWE-bench Verified/Pro | BigCodeBench、BFCL | 私有 repo issues、CI 通过率、review 质量 | HumanEval |
| API 工具调用 | BFCL | IFEval、τ-bench、GAIA | 真实 API schema、错误恢复、安全权限 | MMLU |
| 浏览器 / 桌面 agent | WebArena、VisualWebArena、OSWorld | GAIA、BFCL | 内部系统沙盒任务 | 静态考试题 |
| 数学 / 科学推理 | GPQA、AIME、MATH、HLE | LiveBench reasoning/math | 专业题库、可解释推理审核 | 偏好榜 |
| 多模态文档 | MMMU、MMBench、DocVQA、ChartQA | VHELM、OpenCompass VLM | 企业 PDF、扫描件、图表、票据 | 纯文本榜 |
| 安全高风险应用 | HELM Safety、HarmBench、JailbreakBench | BBQ、ToxiGen、CyberSecEval | 政策红线、审计日志、越权测试 | 仅看能力榜 |

### 7.2 企业选型的推荐权重

如果要为企业选一个 LLM，不建议采用“榜单平均分”。更稳妥的权重如下：

| 维度 | 推荐权重 | 说明 |
|---|---:|---|
| 私有任务成功率 | 30% | 最重要，必须用真实任务集 |
| 场景公开榜 | 20% | 只选与业务强相关的榜 |
| 安全与合规 | 15% | 数据、权限、拒答、审计 |
| 成本与延迟 | 15% | token 成本、吞吐、峰值 SLA |
| 稳定性 | 10% | 版本漂移、超时、格式稳定 |
| 可集成性 | 10% | API、工具调用、结构化输出、部署方式 |

### 7.3 模型发布时的“可信评测包”

一个严肃模型发布，最好至少包含：

1. 基础通用能力：MMLU-Pro、GPQA、LiveBench。
2. 数学推理：AIME、MATH 或同类公开题。
3. 代码：HumanEval/MBPP + BigCodeBench/LiveCodeBench。
4. Agent：BFCL，若定位 coding agent 则加 SWE-bench。
5. 中文能力：C-Eval、CMMLU、SuperCLUE 或 OpenCompass 中文榜。
6. 多模态：MMMU、MMBench、ChartQA、DocVQA，视模型能力而定。
7. 安全：HarmBench、JailbreakBench、toxicity/bias 评测。
8. 真实产品 A/B：用户偏好、成功率、人工审核。
9. 成本：吞吐、首 token 延迟、总延迟、上下文长度下的价格。
10. 评测协议：prompt、temperature、shot 数、系统提示、工具设置、模型版本、日期。

## 8. 评估陷阱与反作弊

### 8.1 数据污染

静态公开题可能进入训练集。模型高分可能来自记忆而非泛化。

缓解：

- 使用动态榜，如 LiveBench / LiveCodeBench。
- 使用隐藏测试集。
- 自建私有题集。
- 检查模型对变体题和同构题的鲁棒性。

### 8.2 榜单过拟合

模型可能针对热门榜优化，导致 benchmark 分数提升但真实体验不变。

缓解：

- 多榜交叉验证。
- 关注低相关场景是否同步提升。
- 使用真实业务任务。

### 8.3 Prompt 与评测协议不一致

同一模型在 zero-shot、few-shot、CoT、system prompt、temperature 不同设置下分数差异很大。

缓解：

- 记录完整评测配置。
- 不比较不同协议下的分数。
- 对生产 prompt 单独测试。

### 8.4 LLM-as-Judge 偏差

强模型裁判会偏好某种风格、长度或同源模型。

缓解：

- 多裁判模型。
- 隐藏模型名。
- 随机交换答案顺序。
- 人工抽检争议样本。

### 8.5 Harness 混淆

在 SWE-bench、WebArena、OSWorld 等 agent 榜上，最终成绩可能更多来自系统工程，而不是底座模型。

缓解：

- 分开看 base model eval 和 agent system eval。
- 比较相同 harness 下的模型。
- 比较相同模型在不同 harness 下的变化。

### 8.6 安全与可用性的权衡

模型拒答率高，看似安全，但可能影响正常业务；模型太“听话”，又可能被越狱。

缓解：

- 同时测 harmful refusal 和 benign refusal。
- 建立业务白名单与高风险黑名单。
- 使用权限隔离、工具沙盒和审计日志。

## 9. 一个可复用的评估流程

### 9.1 第一步：定义任务画像

先把业务写成结构化画像：

```yaml
task_profile:
  language: Chinese / English / multilingual
  input_type: text / code / image / pdf / browser / API
  output_type: answer / JSON / patch / action / report
  risk_level: low / medium / high
  latency_budget: seconds
  cost_budget: RMB_per_1k_requests
  failure_cost: low / medium / high
  need_tools: true / false
  need_long_context: true / false
  need_private_deployment: true / false
```

### 9.2 第二步：选择公开榜做初筛

例子：

- 中文客服：SuperCLUE + C-Eval + OpenCompass + safety。
- coding agent：SWE-bench + BigCodeBench + BFCL + latency。
- 文档问答：LongBench + DocVQA/ChartQA + 私有 RAG eval。
- 科研助手：GPQA + HLE + LiveBench + citation accuracy。

### 9.3 第三步：构建私有评测集

私有评测集必须包含：

- 真实高频任务。
- 长尾困难样本。
- 历史事故样本。
- 边界政策样本。
- adversarial / jailbreak 样本。
- 成本和延迟日志。

### 9.4 第四步：上线前灰度 A/B

公开 benchmark 再好，也不能替代真实用户。上线前应做：

- A/B 胜率。
- 任务完成率。
- 用户追问率。
- 人工接管率。
- 幻觉率。
- 格式失败率。
- 安全事件率。

### 9.5 第五步：持续监控

模型版本会变，用户分布会变，攻击方式也会变。评估不是一次性活动，而是持续监控：

- 每次模型升级跑回归测试。
- 每周抽样人工审查。
- 每月更新私有 eval。
- 对失败案例做红队复盘。

## 10. 国内外评估体系的差异

### 10.1 国外体系的优势

- Chatbot Arena、HELM、SWE-bench、BFCL、LiveBench 等形成了多层生态。
- 更强调开源可复现、prompt 透明、社区提交。
- coding agent、tool use、web agent 的评估发展更快。

### 10.2 国内体系的优势

- 中文语境、中文知识、中文考试和本土模型覆盖更好。
- OpenCompass 对国内模型和多模态评测生态支持较强。
- C-Eval、CMMLU、SuperCLUE 能补足 MMLU 对中文语境的不足。

### 10.3 国内体系的短板

- 与真实企业工作流、agent 工具调用、长程任务结合仍需加强。
- 公开榜与私有业务评测之间的桥梁不足。
- 中文安全、政务、金融、医疗等高风险行业 eval 需要更细粒度。

### 10.4 未来融合方向

未来更有价值的中文评估体系应同时具备：

1. 中文本土语料与文化语境。
2. 动态去污染题库。
3. 真实业务工具调用。
4. 多模态文档与表格能力。
5. 安全合规与政策边界。
6. 可复现 harness。
7. 企业私有 eval 接口。

## 11. 最终建议：如何读榜不被榜骗

### 11.1 一句话原则

**看榜时永远问：这个榜测的任务，和我要部署的任务是否同分布？**

### 11.2 决策规则

1. 如果是通用聊天，先看 Arena 类偏好榜，再看安全和事实性。
2. 如果是中文产品，中文榜权重必须高于英文总榜。
3. 如果是代码代理，SWE-bench / BigCodeBench 权重大于 MMLU。
4. 如果是工具调用，BFCL 权重大于普通聊天榜。
5. 如果是长文档，LongBench / RULER 只是初筛，必须自建文档评测。
6. 如果是高风险行业，安全评测和人工审查权重高于能力榜。
7. 如果两个模型公开榜接近，优先选成本低、延迟低、格式稳定、可控性强的。
8. 如果模型版本变了，原评测结论应自动过期。

### 11.3 推荐的最小评测组合

对一个通用 LLM，最小组合可以是：

| 能力 | 推荐评测 |
|---|---|
| 通用知识 | MMLU-Pro |
| 高难推理 | GPQA + LiveBench |
| 指令遵循 | IFEval |
| 用户偏好 | LMArena / MT-Bench / WildBench |
| 中文能力 | C-Eval + CMMLU + SuperCLUE |
| 代码 | BigCodeBench + LiveCodeBench |
| 工具调用 | BFCL |
| 软件工程 | SWE-bench Verified/Pro |
| 安全 | HarmBench / JailbreakBench / HELM Safety |
| 长上下文 | RULER / LongBench + 私有长文档 |

### 读榜提醒

所有 leaderboard 都有时间戳。模型、榜单、题集、评测协议都会变化。引用榜单排名时必须记录：
