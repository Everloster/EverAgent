## 第一部分 · 先建立直觉

### 1. 一个悖论：94% 的参数在睡觉，那造它们干嘛？

先摆一个让所有人第一次听 MoE 都会犯嘀咕的事实：

> **DeepSeek-V3 有 6710 亿（671B）个参数，但每处理一个字，只叫醒其中 370 亿（37B）——大约 5.5%。** 剩下 94.5% 的参数，这一步完全没参与计算。

悖论来了：

- 如果 94.5% 的参数不干活，把它们造出来图什么？纯浪费显存？
- 如果它们其实有用，那"只用 5.5% 算力"的省，又是从哪省出来的？自相矛盾吗？

答案一句话就能说，但要想通需要一栋楼：**参数是"员工花名册"，算力是"今天的出勤表"。MoE 让你雇了一大楼专家，但每个活儿只叫醒最对口的几个。** 花钱的大头在"出勤"（算力），不在"养着"（参数躺显存里几乎不花算力）。这篇文章就是把这栋"按需叫人"的大楼拆开给你看——而且不只是打比方，**我们会真算给你看**。

### 2. 两个主角：一排专家，和门口的分诊台

整个故事只有两个角色，先把分工焊死在脑子里：

| 角色 | 学名 | 它到底是什么 | 它干什么 |
|---|---|---|---|
| 🧑‍⚕️ **一排专家** | Experts（专家） | 一组彼此独立的**小神经网络**，每个就是一个普普通通的 FFN（前馈层） | 各自等着被叫号，处理送上门来的 token |
| 🚦 **分诊台** | Router / Gating（路由/门控） | **一个小矩阵**（一层线性变换） | 看一眼进来的 token，给每个专家打个分，决定"叫哪几个" |

这里要先击碎一个最普遍的误解：

> **"专家"不是人，也没有"神经科""心脏科"的铭牌。** 它就是一个数学结构——一个两层的小网络。说它"擅长某类输入"，是训练之后回头看才发现的统计规律，没人事先指派。分诊台也不是什么聪明 AI，它就是**一个矩阵**，参数量小到可笑（后面会算：Mixtral 的分诊台只有 3 万多个参数，是它所管理的专家的五千分之一）。

一个贴切的类比，全篇都会用它：

> **想象一所医院，大厅里坐着 8 位医生。** 每来一位病人（token），**门口的分诊台先扫一眼，只把他送去最对口的 2 位**；其余 6 位对这位病人"当没看见"——不问诊、不耗时。医院的**总医术储备**是 8 位医生（参数量 = 8 份），但每位病人**实际只占用 2 位医生的时间**（算力 = 2 份）。

> **术语澄清**：MoE = Mixture of Experts（混合专家）。它替换的是 Transformer 每一层里的 **FFN 子层**（注意力层原样不动）。粗暴理解：**把原来铁板一块的 FFN，换成"一排 FFN + 一个分诊台"**。本库 `wiki/concepts/moe_architecture.md` 有独立词条。

## 第二部分 · 跟着一个 token 走一遍（全程手算）

### 3. 30 秒前情提要：token 是什么，FFN 在哪

✦ **一句话**：token = 一个数字向量；Transformer 每一层 = 注意力 + FFN 两段，MoE 只动 FFN 那段。

一个字/词进入模型后，会变成一串数字，叫**向量**——这就是 token 在大楼里的"肉身"。比如词「利率」，在某个玩具模型里可能就是：

```
「利率」= [1.0, 0.0]      （真实模型里是几千维，教学我们用 2 维，原理一模一样）
```

Transformer 每过一层，token 向量被加工两次：先在**注意力**里和别的 token 交换信息（"看看上下文"），再单独经过 **FFN** 做非线性变换（"自己消化"）。MoE 不动注意力，**只把"铁板一块的 FFN"换成"一排小 FFN（专家）+ 分诊台"**。

> 关于注意力那段，本库《长上下文·模型的一生》和 `wiki/concepts/kv_cache.md` 有专门讲解；本篇只管 FFN 这段。

### 4. 全流程：一个 token 的看病之旅，五步（真算）

✦ **一句话**：分诊台打分 → 只留 Top-K → 被叫的专家各自处理 → 按分数加权合并 → 没被叫的专家**一行计算都没做**。

放一个 token 进一栋"3 位专家、每次叫 2 位"的玩具大楼，每一步都算给你看：

```
① 「利率」= [1.0, 0.0] 进门
      │
      ▼
② 分诊台打分（一个矩阵乘法 + softmax）：
      三位专家得分 [0.44, 0.16, 0.40]
      │
      ▼
③ 只留 Top-2：1 号(0.44) 和 3 号(0.40) 上岗；2 号(0.16) 本轮放假
      │
      ▼
④ 1 号、3 号各自处理 token：
      1 号输出 [1.0, 0.0]；3 号输出 [0.0, 2.0]
      │
      ▼
⑤ 按分数加权合并（分数归一化 0.52 / 0.48）：
      0.52 × [1.0, 0.0]  +  0.48 × [0.0, 2.0]  =  [0.52, 0.95]
      │
      ▼
   「利率」带着被两位专家联合诊断过的新向量，出楼，进入下一层
```

**全篇最关键的一步是 ④**：2 号专家这一步的计算量是**零**。不是"算了但乘了个很小的权重"，而是**根本没被调用**——分诊台没叫号，它的矩阵乘法一次都没跑。"参数多、算力不多"的秘密没有任何魔法，就藏在这一步：省，省在"没被叫到的专家真的一行代码都没执行"。

<details>
<summary><code>证据</code>：这五步的完整手算（点开核对每一个数字）</summary>

**② 分诊台打分**。分诊台就是一个矩阵 `W_r`（3 个专家 × 2 维输入）：

```
W_r = [ 1.0  0.0 ]     ← 1 号专家的"口味"
      [ 0.0  0.5 ]     ← 2 号专家的"口味"
      [ 0.9  0.1 ]     ← 3 号专家的"口味"

logits = W_r · [1.0, 0.0] = [1.0, 0.0, 0.9]
softmax([1.0, 0.0, 0.9]) = [0.44, 0.16, 0.40]
  （e¹·⁰=2.72，e⁰=1.00，e⁰·⁹=2.46；各除以总和 6.18）
```

（真实的 router 就是"一层线性 + softmax"，没有更多东西。）

**③ Top-2 选择**：取分数最高的 1 号、3 号；2 号的权重直接置零。

**④ 专家处理**。每个专家就是一个两层 FFN：先升维+非线性，再降维回来。设 1 号是"恒等加工"，3 号是"交换坐标并放大第二维"：

```
1 号：FFN([1.0, 0.0]) = [1.0, 0.0]
3 号：FFN([1.0, 0.0]) = [0.0, 2.0]
2 号：未被调用 → 0 次乘加运算
```

**⑤ 加权合并**。两个上岗分数归一化：0.44/(0.44+0.40) ≈ 0.52，0.40/(0.44+0.40) ≈ 0.48。

```
输出 = 0.52 × [1.0, 0.0] + 0.48 × [0.0, 2.0] = [0.52, 0.95]
```

**写成通式就是所有论文里那行公式**：

```
y = Σ_{i ∈ Top-K} G(x)_i · E_i(x)
```

`E_i(x)` 是第 i 个专家的输出；`G(x)` 是稀疏权重向量——只有 Top-K 个位置非零。非选中专家 `G(x)_i = 0`，所以 `E_i(x)` **不用算**。
（Shazeer et al. 2017, arXiv:1701.06538）

**真实模型的尺寸对照**（教学玩具 → Mixtral 8×7B）：向量维度 2 → 4096；专家数 3 → 8；每次叫 2 位 → 也叫 2 位；每个专家的 FFN 中间层维度 2 → 14336。**机制的每一步完全相同，只是数字变大。**

</details>

### 5. "谁擅长什么"是没人指派的：分工自己长出来

你可能会问：谁规定 1 号医生看这类病、3 号看那类病的？

**没人规定。** 训练开始时，所有专家一模一样，分诊台瞎打分。但在海量数据的反复冲刷下，**只要某位专家偶然对某类 token 处理得稍好，分诊台就会更多地把这类 token 送给它，它越练越专**——分工是**自发涌现**的。研究者事后解剖训练好的模型，才看到"这个专家对数字敏感、那个专家对代码缩进敏感"之类的统计倾向，而且分工往往按**语法/领域**而非人类语义来分。

这既是 MoE 的魅力，也是它一切麻烦的根源——下一部分我们就来看"自发分工"会自发地跑偏成什么样。

## 第三部分 · 三个想不通的地方

### 6. 想不通①：参数多算力少，这笔账是真的吗？——拿 Mixtral 真实 config 手算一遍

✦ **一句话**：真的。用 Mixtral-8x7B 官方 config 逐项加总，46.7B 总参数、每 token 只激活 ~12.9B，账能对上。

光听"8 个专家只叫 2 个"不踏实，我们拿真实模型把账算平。Mixtral-8x7B 的官方 config 写着：32 层、向量维度 4096、每个专家 FFN 中间层 14336、8 个专家、每 token 叫 2 个。（`config`：mistralai/Mixtral-8x7B-v0.1）

**先看一个专家的 FFN 有多少参数**。现代 FFN 是三矩阵结构（升维两个 + 降维一个）：

```
一个专家 ≈ 3 × 4096 × 14336 ≈ 1.76 亿参数
一层 8 个专家 ≈ 14.1 亿
32 层专家的总量 ≈ 451 亿（45.1B）  ← 参数大头全在专家身上
```

**再看不属于专家的部分**（每 token 都要全用的）：注意力 32 层 ≈ 13.4 亿（1.3B）+ 词嵌入/输出 ≈ 2.6 亿 + 分诊台 ≈ 100 万（见下）。加总：

```
45.1B（专家）+ 1.3B（注意力）+ 0.3B（嵌入等）≈ 46.7B  ✓ 与官方 46.7B 分毫不差
```

**每 token 实际激活多少**：注意力全量（1.3B）+ 每层只叫 2 个专家（2/8 = 25% 的专家参数，11.3B）+ 输出头 ≈ **12.9B** ✓ 与官方口径一致。

**这笔账一句话**：参数大头（96%）是专家，所以"8 选 2"把激活量直接砍到 ~1/4——46.7B 的名册，12.9B 的出勤。

<details>
<summary><code>证据</code>：分诊台有多小？</summary>

Mixtral 的分诊台就是一层线性：`4096 × 8 = 32,768` 个参数/层，32 层合计约 **105 万**——是它所管理的专家总量（451 亿）的 **四千三百分之一**。

记住这个反差：**决定"叫谁"的，是一个参数少到可以忽略的小矩阵；被叫的，是占模型 96% 的庞然大物。** 分诊台的全部智慧，就是那 3 万多个数字。

</details>

### 7. 想不通②：省算力为什么就等于"快"？——因为生成是"搬运"游戏

✦ **一句话**：逐字生成时，瓶颈不是算，而是**把参数从显存搬到计算单元**；激活参数小 3.6 倍，每吐一个字要搬的东西就少 3.6 倍。

直觉上"参数多一倍慢一倍"，为什么 MoE 参数涨 8 倍，推理却几乎不慢？关键要分清一次推理的两个阶段（这和本库《Agent 请求全链路》《投机解码深度解析》讲的是同一套机制）：

| 阶段 | 干什么 | 瓶颈 |
|---|---|---|
| **Prefill**（读你的输入） | 一次性并行处理全部输入 token | **算力**（矩阵乘并行打满） |
| **Decode**（逐字往外蹦） | 每步只生成 1 个新 token | **显存带宽**——每蹦一个字，要把用到的全部参数从显存搬一遍 |

Decode 阶段，每生成一个字的"搬运量" ≈ 激活参数 × 每参数字节数。拿 Mixtral 粗算 `[估算]`：

```
稠密 46.7B 模型：每字要搬 46.7B × 2 字节 ≈ 93 GB
MoE 激活 12.9B：每字只搬 12.9B × 2 字节 ≈ 26 GB   ← 少了 3.6 倍
```

显存带宽是硬通货（消费级显卡几百 GB/s，数据中心卡几 TB/s），搬运量直接决定每秒能蹦几个字。**MoE 的"省"，在 decode 阶段直接兑换成了"快"和"便宜"**——这就是 2024 年之后开源前沿模型（Mixtral、DeepSeek、Qwen 系）纷纷转 MoE 的经济学根源。

> 同一机制的另一面：投机解码用"小 draft 模型猜 + 大模型并行验证"来摊薄 decode 搬运，见《投机解码深度解析》；两条路线解决的是同一个瓶颈。

### 8. 想不通③：这栋大楼的一生——分工怎么长出来，又怎么跑偏、被治

✦ **一句话**：自发分工自带马太效应——不加约束，分诊台会把活儿全塞给少数"明星专家"；MoE 的半部技术史就是三代纠偏方案。

**大楼的"出生"**：训练初，专家们一模一样，分诊台瞎指派。但马太效应立刻启动，因果链非常干净：

```
某专家偶然被多分了一点 token → 它练得更充分 → 它对这类 token 打分更高
   → 分诊台更爱派给它 → 它拿到更多 token →（循环放大）
      → 最终：少数专家"过载累死"，多数专家"饿死变废人"   ← 专家崩塌（Expert Collapse）
```

**崩塌的两个真实代价**：① 参数白雇了——饿死的专家没训练充分，671B 的花名册只有一撮在贡献容量；② 拖慢整栋楼——训练时不同专家放在不同 GPU 上，过载专家那块卡累死，其他卡干等（木桶效应）。

**三代解药，一代比一代优雅**：

| 代 | 方案 | 思路 | 副作用 |
|---|---|---|---|
| 一 | **辅助损失**（Aux Loss） | 训练目标里加一条"惩罚不均衡"，逼分诊台雨露均沾 | 这条"额外任务"和"把话说好"的主任务**抢梯度**（Shazeer 2017, arXiv:1701.06538） |
| 一 | **强制限流**（Capacity） | 每位专家设接诊上限，超额 token 直接跳过（走残差） | 被丢弃的 token 没被好好处理（Switch, arXiv:2101.03961） |
| 二 | **专家选 token**（Expert Choice） | 反转方向：每位专家挑自己最想要的 K 个 token，天生均衡 | 需要看到整个序列，**自回归逐字生成时用不了**，没成主流（arXiv:2202.09368） |
| 三 | **无辅助损失均衡**（Loss-Free） | 给每位专家挂一个可调"偏置分"：谁忙了悄悄调低、谁闲了调高 | 偏置**只影响"选谁"、不进梯度、不进输出**——不和主任务打架。DeepSeek-V3 采用，当前 SOTA（arXiv:2408.15664） |

> **一句话串起三代**：从"额外加惩罚"（抢梯度）→"限流丢弃"（伤 token）→"反转选择"（推理用不了）→"挂个偏置悄悄纠偏"（都不伤）。DeepSeek-V3 能把 671B 训出来，一半功劳在这最后一代路由。

## 第四部分 · 工业界的 MoE 长什么样

### 9. 从学术有趣到开源标配：一张对照表

✦ **一句话**：2017 年证明"能跑"，2023 年 Mixtral 证明"开源能打"，2024 年 DeepSeek-V3 证明"能便宜地做到顶级"——MoE 现在是前沿开源模型的标准架构。

| 模型 | 年份 | 专家配置 | 总参 / 激活 | 意义 |
|---|---|---|---|---|
| Sparsely-Gated MoE | 2017 | 2048 专家, K=4 | 最大 137B | 奠基：证明 GPU 上可大规模跑（arXiv:1701.06538） |
| Switch Transformer | 2021 | 2048 专家, **K=1** | 最大 1.6T | 极简主义："只叫 1 个"也能训好（arXiv:2101.03961） |
| **Mixtral 8×7B** | 2023 | 8 专家, K=2 | 46.7B / 12.9B | **开源 MoE 标杆**，多数基准超 LLaMA-2 70B（arXiv:2401.04088） |
| DeepSeek-V2 | 2024 | 160+2 专家, K=6 | 236B / 21B | 细粒度专家 + 共享专家双创新（arXiv:2405.04434） |
| **DeepSeek-V3** | 2024 | 256+1 专家, K=8 | **671B / 37B** | 无辅助损失均衡，以远低训练成本达 Llama-3.1-405B 级性能（arXiv:2412.19437） |

两个趋势值得记住：① **专家越切越细**（8 个 → 256 个，每个专家更小、组合更灵活）；② **出现"共享专家"**——DeepSeek 设 1 个**永远出勤**的共享专家，专装"所有 token 都用得上的通用知识"，其余 256 个稀疏专家专注特化。表里 "256+1" 的 "+1" 就是它。

<details>
<summary><code>证据</code>：DeepSeek-V3 官方 config 里的三个有趣细节（点开看）</summary>

来自 deepseek-ai/DeepSeek-V3 的 config.json：

- **`n_routed_experts: 256, num_experts_per_tok: 8`**：每个 token 从 256 个稀疏专家里叫 8 个（再加 1 个共享专家）。每个专家的中间层只有 2048 维——比 Mixtral 的 14336 小得多，"细粒度"就细在这。
- **`first_k_dense_replace: 3`**：**最前面的 3 层不用 MoE**，用普通稠密 FFN（中间层 18432）。为什么？~~`[推测]` 主流解释：浅层提取的是通用低级特征（词形、句法），几乎所有 token 都需要，分工收益小，稠密反而稳。~~（2026-07-19 更正：查 DeepSeekMoE / V2 / V3 三篇论文原文，"浅层特征通用"一说**均无出处**，属社区事后推测；唯一官方理由是 DeepSeekMoE 论文的"首层负载均衡收敛特别慢"。详见文末「追问深入」。）
- **`num_hidden_layers: 61`**：61 层里 58 层是 MoE——参数爆炸主要发生在中后段，那里装的才是"知识"。

</details>

> **关于 GPT-4 / Gemini 是不是 MoE**：业内普遍推测是，但官方从未披露。凡看到"GPT-4 是 8×220B MoE"这类具体数字，都属 `[推测]`/传闻，不是官方确认。

### 10. 不是免费午餐：省了算力，吃显存

✦ **一句话**：MoE 用"多买显存"换"少花算力"——全部参数必须驻留显存，因为你不知道下一个字会叫谁。

- **名册再厚也得全员在场**：Mixtral 每 token 只算 12.9B，但 46.7B 参数**必须全部装进显存**（bf16 约 90GB，4-bit 量化可压到 ~25GB）——下一个 token 会叫哪两位专家无法预知，谁都不能缺席。
- **专家放多卡，token 要跨卡跑腿**：训练/推理时专家分布在不同 GPU，token 被派来派去产生大量卡间通信（All-to-All），工程实现比稠密模型难一截。

所以 MoE 的账要记完整：**算力省 3.6 倍，显存一分没省，工程复杂度还上去了。** 它在"显存管够、算力/带宽是金"的大模型时代是笔好买卖——这正是当下的现实。

## 第五部分 · 装进脑子

### 11. 一页纸心智模型

```
        一个 token（向量）进来
              │
              ▼
   🚦 分诊台（一个小矩阵）：给 N 个专家打分
              │   只留 Top-K（如 8 选 2）
       ┌──────┼──────┬────────┬─── …（其余专家：本轮 0 次运算）
       ▼      ▼      ✗        ✗
    🧑‍⚕️1号  🧑‍⚕️3号  (放假)   (放假)
       │      │
       └──按分数加权合并──► token 带新向量出楼，进下一层

  ┌───────────────────────────────────────────────┐
  │ 参数 = 花名册（大）  算力 = 出勤表（小）            │
  │ 省在哪：没被叫的专家一行代码都没跑                  │
  │ 快在哪：decode 是搬运游戏，激活小 → 搬得少 → 蹦得快 │
  │ 病在哪：马太效应 → 专家崩塌；三代解药 → 挂偏置纠偏  │
  │ 贵在哪：全员驻显存 + 跨卡通信                      │
  └───────────────────────────────────────────────┘
```

**四句话总纲**：
1. **MoE = 一排普通 FFN + 一个小矩阵分诊台**，替换掉 Transformer 层里铁板一块的 FFN，注意力不动。
2. **省的原理**：参数按专家数涨（名册厚），算力只按 Top-K 涨（出勤少）——Mixtral 实测账：46.7B 名册、12.9B 出勤。
3. **快的原理**：逐字生成的瓶颈是显存搬运，激活参数小 3.6 倍，每字少搬 3.6 倍。
4. **病的原理与解药**：分工自发涌现也自发失衡（专家崩塌）；三代解药演进为"挂偏置悄悄纠偏"（DeepSeek-V3，不抢梯度、不伤 token）。

### 12. 几个容易踩的直觉陷阱

| 直觉陷阱 | 真相 |
|---|---|
| "没被选中的专家，算了但权重是 0" | ❌ **根本没被调用**，乘加运算真为零——省就省在这 |
| "专家是预先设计好的专科（这个管代码、那个管中文）" | ❌ 是训练中**自发涌现**的统计倾向；且分工多按语法/领域，不按人类语义 |
| "分诊台是个聪明的调度 AI" | ❌ 就是**一个矩阵**（Mixtral：每层仅 3.3 万参数），线性层 + softmax |
| "参数多 8 倍，推理就该慢 8 倍" | ❌ Decode 瓶颈是**搬运激活参数**，不是总参数；激活只多 ~1/4 |
| "MoE 又快又省，纯赚" | ❌ 算力省了，**显存一分没省**（全员驻留），跨卡通信还更复杂 |
| "MoE 层数越多越赚" | ❌ DeepSeek-V3 前 3 层特意保持稠密（但"浅层特征通用、分工没收益"是社区推测非官方理由，2026-07-19 更正，见文末） |
| "K=1（只叫 1 个）肯定不行" | ❌ Switch Transformer 证明 K=1 也能训好，还省一半路由开销 |
| "GPT-4 是 8×220B MoE" | ❌ 坊间**推测**，官方从未公布架构 |

## 附 · 用真实 config 复核一遍账（本篇的"实测"）

像《Agent 请求全链路》用一次真实请求验证"脚手架占 99.995%"一样，这里用两个真实 config 把 MoE 最核心的两笔账复核出来（数据：HuggingFace 官方 config.json，2026-07-19 抓取；算术为本文推导）：

**Mixtral-8x7B**（hidden 4096 / 中间层 14336 / 8 专家 / top-2 / 32 层 / GQA 32:8 / vocab 32000）：

| 组成 | 手算 | 量级 |
|---|---|---|
| 一个专家（3 矩阵 FFN） | 3 × 4096 × 14336 | ≈ 1.76 亿 |
| 全部专家（8 × 32 层） | ×8 ×32 | ≈ 451 亿 |
| 注意力（Q/K/V/O × 32 层） | (4096² × 2 + 4096×1024 × 2) × 32 | ≈ 13.4 亿 |
| 嵌入 + 输出头（不共享） | 32000 × 4096 × 2 | ≈ 2.6 亿 |
| 分诊台 | 4096 × 8 × 32 | ≈ 105 万 |
| **总参数** | | **≈ 46.7B ✓**（官方 46.7B） |
| **每 token 激活** | 注意力 13.4 亿 + 2/8 专家 113 亿 + 输出头 1.3 亿 | **≈ 12.9B ✓** |

**DeepSeek-V3**（hidden 7168 / 61 层 / 前 3 层稠密 / 256+1 专家 / top-8 / 专家中间层 2048）：

- 每个稀疏专家：3 × 7168 × 2048 ≈ 4400 万 → 256 个 × 58 层 ≈ **654B**，占总参数 671B 的 97%——参数爆炸几乎全部来自专家阵列。
- 每 token 激活 37B ≈ 总量 5.5%——**比 Mixtral 的 28%（12.9/46.7）更极致**，这是"细粒度 + 共享专家"路线的直接结果。

**两个结论**：① "总参/激活"这对数字不是营销话术，用公开 config 五分钟就能验算；② MoE 的演进方向很清晰——**把专家切得更小更多、把激活率压得更低**，账越做越狠。

## 追问深入（2026-07-19）

### ✅ 前 3 层稠密的真相：无消融证据，"浅层特征通用"是社区推测（已读三篇论文原文）

**结论**：DeepSeek-V3「前 3 层保持稠密 FFN」**没有任何消融实验支撑**，V3 报告连理由都没给；唯一官方解释出自前身 DeepSeekMoE 论文，而且是**工程观察而非性能论证**。流传甚广的"浅层特征通用、不需要专家分工"在三篇论文（DeepSeekMoE / V2 / V3）中**均无出处**，应标注为社区事后推测。

**证据链**（2026-07-19 真读原文）：

- **DeepSeek-V3（arXiv 2412.19437）§2.1.2**：唯一提及处只有一句 "We substitute all FFNs except for the first three layers with MoE layers"，随后只列超参，**无任何解释**。全部消融章节（§4.5.1 MTP、§4.5.2 aux-loss-free 均衡、§4.5.3 batch-wise vs sequence-wise、附录 B FP8）**均无"浅层 MoE 化"对照变体**。
- **DeepSeekMoE（arXiv 2401.06066）§4**：首层稠密的唯一官方理由——"we observe that **the load balance status converges especially slower for the first layer**"（首层负载均衡收敛特别慢）。这是训练工程观察，不等于证明"浅层 MoE 化损害最终性能"。
- **DeepSeek-V2（arXiv 2405.04434）**："Following Dai et al. (2024), we substitute all FFNs except for the first layer with MoE layers"——直接继承，未补理由。

**值得注意**：V2 是前 1 层稠密，V3 扩到前 3 层，但 V3 报告只字未提为何加宽——从"负载均衡收敛慢"的官方线索看，更可能与超大规模下首几层路由/通信稳定性有关（推断，无原文依据），与"特征通用性"叙事无关。

**教训**："浅层特征通用"听上去太合理，以至于被广泛当成官方结论转述——这是"合理推测污染事实层"的典型样本。本报告初版也中招了（正文原写法已更正）。
