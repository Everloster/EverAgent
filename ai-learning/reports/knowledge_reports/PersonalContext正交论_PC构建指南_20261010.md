# Personal Context 正交论：哪些积累值得保留，怎样持续维护

模型升级很快，积累的资料和经验还能用多久？Personal Context 提供了一种思路：把偏好、任务背景、研究结论和做事经验保存下来，让下一次使用 AI 时少解释一些、少犯一些已经犯过的错误。

但“保存了很多”不等于“下次能做好”。事实可能过时，经验可能适得其反，记忆可能在无关场景被调用。本文把“正交论”作为一项**条件性互补假说**：如果资料准确、与任务有关、取用得到授权，且维护和检索成本可接受，模型进步可能提高这些积累的用途。它不是数学上的正交，也不是资产必然升值的规律 `[推测]`。

> **2026-10-30 修订说明**：撤回“事实几乎不贬值、程序普遍高贬值”的排序，以及“委托是终极资产、信任积累就能扩大权限”的表述。重新核对播客关键转写、Anthropic 原文，并引入已读取的 OpenAI 与 IBM 原文作对照；纠正公开仓组件映射，去掉无必要的融资、Star 数和固定维护日程。原文创建日期保留；这次修订不表示所有历史产品信息都重新核实。

## 0. 论点从哪里来，证据能支持到哪里

本文起点是一个学习问题：在模型不断变化时，哪些个人与工作积累更值得持续投入？不同材料回答的是这个问题的不同部分，不能相互替代。

| 来源 | 能提供什么 | 不能证明什么 |
| --- | --- | --- |
| 乱翻书 275 的公开转写 [S1] | 产品经理对个人助手、记忆误用、信任和使用习惯的经验与判断 | 不能当作长期用户实验，也不能把访谈里的产品描述当成当前官方规格 |
| Anthropic 上下文工程文章 [S2] | 按需取用、提示抽象层次、压缩与持久笔记等工程经验 | 不能证明私人资料积累一定改善所有任务 |
| OpenAI 的 GPT-6 Astra 指令文章 [S3] | 旧规则可能过度约束新模型；需要精确路由与明确完成边界 | 不能推出程序性经验全部过时，或所有模型应使用同一配置 |
| IBM ALTK-Evolve 实验 [S4] | 从任务轨迹提炼规则，在特定留出任务上观察到收益 | 不能证明同一规则跨模型永久有效，或个人记忆已具备长期复利 |
| 本仓公开协议 [S5][S6] | 展示来源、报告、知识索引与授权边界怎样分工 | 文件存在、质量门通过都不等于已测得任务收益 |

Laya 的既有研究只用于讨论“行动还是升级处理”的决策类比，不作为个人授权已被模型解决的证据。[S7]

## 1. “正交”是一个提问方式

### 1.1 与模型分开保存，不等于价值与模型无关

个人偏好、研究证据和决策记录，可以保存在某款模型之外。换模型时，它们不会因为权重替换而物理消失。但能不能继续使用，仍取决于格式、检索、权限、语义和任务。

例如，一份“某项服务上个月已经迁移”的记录，即使迁移到更强模型，也可能因没有记录后续回滚而误导排错。相反，一套明确记录版本范围和失败条件的排错步骤，可能连续几代模型都用得上。前者是事实，后者是程序；类别本身不能决定耐久性。

“模型更强，同一份 Context 更有用”有两个可能机制 `[推测]`：模型能从原有资料中完成更复杂的工作；调用成本降低后，原本不值得自动化的任务开始值得做。但增加调用次数不保证增加有效产出，更不保证收益抵消维护成本。Jevons 式需求扩张在这里只是类比，没有本仓长期数据支持。

### 1.2 事实与经验，都有时效和适用范围

| 内容 | 可能保留的价值 | 常见失效方式 | 维护重点 |
| --- | --- | --- | --- |
| 事实与决策记录 | 支持回查当时依据、避免重复调查 | 当前状态改变，旧结论仍被当作现状 | 分清发生时间、记录时间、当前有效性；链接更正 |
| 偏好与约束 | 减少反复解释，适配输出 | 临时要求被当作长期偏好，旧偏好盖过新指令 | 以明确表达为依据，允许更正和撤回 |
| 程序与经验 | 复用领域方法、工具合同、失败诊断 | 特定模型补丁过时，步骤变多反而拖慢任务 | 写明适用任务、模型或接口版本，用真实失败检验去留 |
| 推断与画像 | 在信息不足时提供待验证线索 | 猜测被反复摘要后变成“事实” | 与显式事实分开，保留依据和不确定性 |

这里需要区分**历史真实性**与**当前适用性**。“上月曾采用某方案”可以一直是有效历史；“现在应采用该方案”却可能已失效。保留历史记录，不代表让模型在每次任务中都读取它。

### 1.3 两篇厂商原文为什么看起来方向相反

OpenAI 观察到，针对旧模型累积的详细步骤、过宽 Skill 描述、每次强制通读文档等，可能限制 GPT-6 Astra 的判断或造成额外工作。因此需要重新检查指令。[S3]

IBM 的 ALTK-Evolve 则从训练任务的执行轨迹里提炼操作规则，加入系统提示，模型权重不变。在 τ²-bench 留出集上：[S4]

| 设置 | 规则条件 | Pass⁴ 变化 |
| --- | --- | --- |
| GPT-4.1，Retail 40 个测试任务 | 全部 292 条保留规则 | 57.5% → 67.5% |
| GPT-4.1，Airline 20 个测试任务 | 14 条高支持规则 | 35.0% → 45.0% |
| GPT-5.5，Airline 20 个测试任务 | 从自身轨迹重新提炼规则 | 55.0% → 70.0% |

Pass⁴ 指一个任务在四次尝试中都成功的任务比例，不是“至少成功一次”。GPT-5.5 的实验重新提炼了规则，**不是把 GPT-4.1 的同一套规则直接迁移过去**。不同领域的最佳规则数量也不同；“支持次数”统计规则来自多少个训练任务，不是规则正确的概率。

收益还带来输入成本：原文在完整 base split（含训练与测试任务）上统计了 agent 加用户模拟器的每对话成本，不能把它与留出集成绩当作同一统计样本，也不能把对话轮数略减直接写成实测延迟降低。[S4]

两篇材料共同支持的是一项更具体的原则：**按信息在当前任务中的作用决定去留。** 明确工具合同和有证据的领域方法可能继续有效；为某代模型弱点添加的补丁则需要重验。不能只凭“它是经验”就删除，也不能只凭“以前有效”就永久保留。

## 2. 从个人助手的讨论里，能学到什么

### 2.1 四种产品路线是观察视角，不是价值证明

乱翻书 275 在约 30:14–34:31 讨论了四条路线，以下按节目描述概括，不作当前产品功能承诺：[S1]

| 节目中的产品路线 | 对 Context 的启示 | 仍需验证的部分 |
| --- | --- | --- |
| Town：从邮箱等高频场景逐步交付 | 背景连续、有机会观察用户怎样修改结果 | 信任能否转化为持续使用，以及在何种动作上授权 |
| Instinct：降低从消息发起任务的成本 | 自然交互可以减少输入负担 | 入口便利不等于执行可靠、数据可导出 |
| Grok Bot：多个 Bot 分工协作 | 可以围绕不同职责组织资料和任务 | 多 Agent 协作是否值得额外耗时与 token；节目也提出了这项质疑 |
| Muse：免费与分发推动采用 | 低使用门槛可能扩大真实任务样本 | 用户留存、成本和商业模式能否持续 |

产品投入和融资最多说明参与者的商业预期。它们不能证明 Personal Context 已产生可持续收益，也不能排除抢占入口、补贴或市场情绪等其他解释。旧稿用估值涨幅来证明“这不是炒作”的推论撤回。

### 2.2 记住一件事，和恰当地使用它，是两种能力

节目约 **57:41–58:46** 举了一个历史案例：用户曾提到正在申请签证，新对话问起无关话题，助手却把答复强行绕回签证。嘉宾同时说明这是此前经历，当时的产品可能已经有所改善。[S1]

这个案例支持“记忆调用可能不合时宜”，不能用于估计当前豆包错误率，也不能据此断言其内部采用哪种 Memory 架构。问题不只是记没记住，而是系统是否判断了这条记忆与当前任务有关。

节目约 **02:03:10–02:04:48** 进一步讨论：获取 Context 之后，还要处理、关联和判断时效；上一周成立的事情，这一周可能已经失效。[S1] 这直接反驳了“事实性 Context 几乎不贬值”的旧说法。

也不必把所有资料都先“炼成完整画像”。一个清楚的当前约束，例如“本次只比较开源方案”，可能比复杂的长期画像更有用 `[推测]`。有些任务甚至不需要个人信息；无关时不调用记忆，同样是有效行为。

### 2.3 信任、习惯与授权不能混成一层

节目末尾谈到信任和习惯，也有嘉宾强调中间的 Context 处理机制；这是一组产品判断，不是所有嘉宾一致验证出的市场定律。[S1]

信任是用户对系统的判断，习惯是使用行为，授权则回答“允许谁在什么范围内做什么”。良好交付可能促成用户扩大授权，也可能只是使用户更愿意继续审阅草稿。系统不能替用户完成这个授权决定。

同样，能导出对话不代表能带走原产品的权限。更换产品、工作单位或执行主体时，原来的访问权、数据使用许可和操作授权都需要重新核对。授权可以缩小、到期或撤回。

## 3. 五个维度，帮助分类而非排序

旧稿用 L1–L5 按价值和贬值速度排队。本次保留五个维度作为整理工具，取消层级高低；它们并非彼此排斥的数据库分类，也不要求每个维度建一个文件 `[推测：设计视角]`。

| 维度 | 应回答的问题 | 例子与边界 |
| --- | --- | --- |
| 身份与偏好 | 哪些是用户明确表达、现在仍有效的要求？ | 表达习惯可以记录；不能从一次任务推断人格 |
| 事实与知识 | 依据是什么，何时成立，后来有无更正？ | 研究报告、实验结果、决策记录；不把推测伪装成事实 |
| 关系与协作 | 谁负责什么，哪些约定能在此用途下共享？ | 协作角色和职责；公开人物资料不等于私人关系网 |
| 程序与经验 | 在什么条件下应怎样做，何时停止沿用？ | 排错方法、工具合同、Skill；保留版本与反例 |
| 委托与授权 | 哪些行动已获授权，范围与撤回条件是什么？ | 当前任务和项目协议；信任记录不能自动授予权限 |

Work Context 与 Personal Context 可以有交集，但不能写成严格等式“WC = L2 + L4”。工作中也有身份、关系和授权，个人任务也有程序知识。公司材料或他人资料是否能保存和迁移，受所属组织及使用目的约束，不因记录在个人目录里就成为个人可带走的资产。

### 行动门控为什么不等于授权

Laya 既有研究讨论过 act/escalate 的成本敏感决策。[S7] 把这个思想抽成一个**示意计算**：假设正确行动收益为 +1、错误为 −3、升级处理为 −0.5，且 `p` 是校准后的正确概率，则：

```text
行动的期望收益 = p × 1 + (1 − p) × (−3) = 4p − 3
升级的期望收益 = −0.5
选择行动的条件：4p − 3 > −0.5，即 p > 0.625
```

62.5% 只属于这组人为给定的收益假设。改动损失、概率校准或升级效果，阈值就会变化；不能据此说模型实际已经学会这个阈值。更不能把“预计做对的概率高”当成“已获授权”：未授权的动作，即使预测正确率很高，也不应执行。

## 4. 怎样构建，而不让维护变成负担

### 4.1 分清保存的资料和这次模型读到的内容

Anthropic 将 Context Engineering 描述为持续选择进入模型上下文的信息，强调取用高信号内容、合适的提示抽象层次，以及按需检索。[S2] 在 Personal Context 中，可以据此区分几种职责 `[推测：工程组织]`：

| 对象 | 主要用途 | 不应承担的职责 |
| --- | --- | --- |
| 原始材料 | 回查与重新解释：原文、决策依据、实验输出 | 不要求每次全量进入模型输入 |
| 长期 Memory | 保存跨任务仍有用的事实、偏好与经验 | 不把所有历史自动提升为长期记忆 |
| 索引 | 帮助定位资料、显示时间和状态 | 摘要与路径不是第二份事实来源 |
| 当前上下文 | 放入这一步所需的指令、证据和工具结果 | 不因窗口足够大就装入全部资料 |
| 执行状态 | 记录已完成步骤、真实产物和未决操作 | 不能只靠一段画像或聊天摘要证明事情已做成 |

按需检索也有代价：Anthropic 明确指出，运行时探索可能比预先检索慢，工具和导航不清楚还会造成无效探索。适合的组合通常要同时考虑资料变化速度和任务需要，不能把“尽量少读”机械变成目标。[S2]

### 4.2 四条维护原则

1. **可控制、可导出。** 需要长期复用的记录，尽量使用可检查的格式并保留恢复路径。自持不等于绝对安全；本地或私有仓也需要权限、备份和删除能力 `[推测]`。
2. **找到负责维护的来源。** 一条当前事实应能回到负责更新它的文件；摘要或检索结果发生冲突时，核对来源与时间。路径和 SHA-256 能说明内容出处或是否变化，不能证明内容本身真实。[S5]
3. **更新比堆积重要。** 旧研究可以保留历史并加更正入口；临时偏好要避免变成长久约束。删除个人信息时还要处理派生 Memory、索引、缓存与副本，仅从当前输入裁掉不算完成删除 `[推测]`。
4. **按用途取最小必要部分。** 公开仓保留公开知识和脱敏方法；私人事实不进入公开产物。获得授权的私有资料，可以在合适的受控环境用于任务。“不能公开”与“永远不能进入任何模型输入”是两种不同边界。[S5][S6]

### 4.3 选 Memory 方案时，先查这些问题

旧稿的产品表混合了不同版本的能力与缺少统计口径的融资、Star 数。本次不沿用它们作为选型结论。可以先按机制检查候选系统 `[推测：选型建议]`：

| 机制 | 重点检查什么 |
| --- | --- |
| 模型提取、更新与删除记忆 | 是否保存原始依据；冲突时覆盖了什么；误删和误记能否恢复 |
| 带时间的事实或关系表示 | 能否分清历史状态与当前状态，查询是否使用有效时间 |
| 文件化、可导出的记忆 | 导出是否完整；接收方能否理解语义；权限是否被一并误带过去 |
| 摘要与压缩 | 是否丢掉用户约束、反例和未完成事项；能否回到原始记录 |
| 多 Agent 共享 | 是否区分读写权限、冲突处理和任务执行状态；共享资料是否确实减少重复工作 |

这些问题与选向量库、知识图谱还是 Markdown 并不等价。本文也没有完成全面产品调查，不能声称“没有一个方案解决可迁移授权”。目前只能说：本文引用的证据不足以确认存在可跨产品通用的授权方案。

### 4.4 本仓已经有什么，仍缺少什么证据

以下仅依据公开协议与知识页面，不引用私有仓事实：[S5][S6]

- `PROFILE.md` 类文件用于明确偏好；根 `AGENTS.md` 主要负责执行约束与任务路由，不能整体当作“身份画像”。
- 领域 `reports/` 保存分析，`wiki/` 提炼当前理解；报告混有事实、解释与推断，需要靠来源和更正区分，不能统称为已验证事实库。
- 公开实体页描述人物、机构或产品，不代表项目维护了私人关系和协作历史。
- `AGENTS.md`、Skill 与工具合同保存部分程序经验。反复改过文件，不能单独证明程序知识高贬值，也不能证明改完效果更好。
- 授权边界已经体现在根协议和共享执行协议中。这里没有必要为凑齐“五层”再建 `DELEGATION.md`；重要的是当前执行者是否读到并遵守已存在的授权。

本仓可以展示组织方法、来源和修订记录，尚不足以证明长期使用收益、跨产品授权迁移或跨设备接班效果。检索能命中一页、报告通过复核和任务实际做好，需要分别验证。

### 4.5 从一个会反复发生的任务开始

[推测：起步建议] 不必先建齐五类目录。先选择一项会重复发生的工作，例如每周读技术文章并回答一个研究问题：

1. 保存原文链接和必要证据，写清当时的结论及未解决问题。
2. 下次遇到相同问题，先定位已有记录，再补变化；避免为同一事实维护多份互相矛盾的摘要。
3. 只有某项偏好或方法在后续任务中确实有用，才把它提炼为长期记录。
4. 信息变更、任务失败或维护负担升高时，回查旧记录；不强制每日记录、每周审阅、每月重构。

这样积累的是有实际用途的资料。文件数量、字数和调用次数，都不能代替使用结果。

## 5. 怎么知道这套积累有没有帮助

以下是可用于真实任务的评估设计，**本报告没有运行这些对照，也不报告虚构收益** `[推测]`。

| 问题 | 可观察的现象 | 怎样避免误判 |
| --- | --- | --- |
| 是否减少重复解释？ | 补充背景的次数、首次得到可用结果的耗时 | 同时记录错误假设；少问问题可能只是擅自猜测 |
| 是否用对旧知识？ | 相关证据是否被找到，过时信息是否被识别 | 检索命中不是正确使用，需查看最终答复 |
| 程序经验是否有效？ | 带与不带该经验时，已知失败和相关回归是否变化 | 尽量保持模型、任务和工具一致；用未参与调规则的任务复查 |
| 新要求能否覆盖旧记忆？ | 临时要求、偏好更正和撤回是否得到遵守 | 不能只测顺从旧偏好的例子 |
| 总体是否值得？ | 整理、检索、运行、返工与验收的总投入 | 不只看 token 节省或主观评分；无收益时缩减维护范围 |

不需要每次都开展完整 A/B 实验。日常任务出现具体失败时，先检验相关记录；当要把某条规则推广到多种模型或大规模流程时，再增加相应对照。评估范围应与要作出的决定相匹配。

## 6. 风险与失效条件

- **资料过时或被污染。** 有来源的记录也可能判断错误；关键事实需要核对，派生摘要应随更正更新。
- **画像固化。** 过去偏好覆盖当前要求，或无关记忆反复进入回答。应允许用户明确改写、撤回，检查与当前任务的相关性。
- **迁移名存实亡。** 文件导出成功，但语义、附件、权限或引用关系丢失；不能因此宣称 Context 已可跨产品复用。
- **隐私集中。** 集中资料方便检索，也集中泄露风险。公开/私有分工、按用途共享与删除能力都需要落实；本地推理本身不等于没有泄露风险。
- **收益不足。** 若即时收集少量背景已足够，或维护持续超过节省的工作量，应该缩小积累范围，而非加更多流程证明体系有价值。

这些风险共同限定了“互补假说”：模型能力提升只是其中一个变量，资料质量、任务相关性、权限与成本同样会改变结果。

## 思考与追问

1. **可以保留的认识是什么？** 与具体模型分开保存、有来源且能更新的资料，有机会减少重复工作。事实与经验都值得按使用效果维护，不能按类别预判谁永久有价值。
2. **仍缺少什么证据？** 哪些积累在后续真实任务中持续有用；跨模型换用后收益是否保持；更正、撤回与遗忘能否贯穿原始记录及派生内容。产品投资和厂商经验不能替代这些验证。
3. **下一步最值得观察什么？** 在后续真实研究任务中，看已有材料是否被正确复用、旧结论是否被及时纠正，以及维护是否减少总工作量。先解决可观察的问题，再决定是否需要新的组件。
