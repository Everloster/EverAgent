# 把 Agent 的 KV 缓存放到 NVMe：命中率、保留时间和写入寿命怎样一起算

多轮 Agent 经常发送很长的历史，而每轮真正新加的内容很少。服务端若保留历史对应的模型状态，就能只计算增量；若缓存已经被淘汰，便需要重新计算大段历史。缓存因此影响下一轮什么时候开始，也影响 GPU 被多少重复工作占用。

AMD 与 Embedded LLM 在 vLLM 官方博客报告了一组实验：使用 MoRI 的 UMBP 缓存池，在 16 张 MI355X GPU 上比较同为 1.8 TB 的 DRAM 与 NVMe 池。在他们测试的繁忙 Agent 负载中，同容量 NVMe 的吞吐接近 DRAM。关键条件是命中率接近、读盘可与排队重叠，以及大部分 prompt token 的状态仍由 GPU 缓存提供。它没有证明 NVMe 的访问延迟等同 DRAM。[原文与实验附录](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

## 缓存命中省去了哪部分计算

Transformer 处理 prompt 时，会计算各层的 key、value 等状态。后续生成和复用共同前缀时，可以读取已经算过的状态。prefill 负责处理输入，decode 负责继续生成；外部缓存池主要帮助 prefill 避免重算已知前缀。

原文的命中率按 prompt token 计算，同时计入 GPU 前缀缓存和外部池的命中。因此“命中率 95%”不意味着 95% 的 token 从 SSD 读取。主比较中，GPU 在 48、70、96 个并发会话时分别提供约 96%、90%、79% 的 prompt token，外部池提供约 1%、5%、16%。低读盘占比是解释结果的一项重要条件。[命中定义与数据路径](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

假设总流量不变，命中率从 96% 降到 95%，需要重算的比例从 4% 升到 5%，增加了 25%。这可以解释为什么少量命中损失会明显增加 prefill 工作，但吞吐还由排队、decode、数据传输和其他资源决定，不能把 25% 直接当作整个服务的性能下降。

原文在 Kimi-K3 的 42 次运行中观察到，命中率与吞吐高度相关，并拟合出每多命中一个百分点约增加 1,280 tok/s/GPU 的关系。这个拟合属于该模型、70 会话及这些配置，不能当作所有模型通用的换算公式。

## “没有 DRAM 层”仍然需要缓冲

UMBP 独立进程保存以 key 标识的缓存块，通过 `UMBPStoreConnector` 与 vLLM 的 prefill 引擎连接。新块先写入约 64 GB 的 DRAM 缓冲，缓冲淘汰时进入本地 NVMe 段文件。SSD 上的命中通过 direct I/O 读取到 16 GiB 的 staging buffer，再复制到 GPU。

所以主实验中的 1.8 TB 保留池在 NVMe 上，另有约 80 GB 的主机缓冲。这里 GB 与 GiB 是不同单位，约 80 GB 是原文的近似说法。实验使用 ext4、本地 SSD、io_uring，没有用 Linux page cache 代替读盘；也不是 NVMe-oF 或共享文件系统。[缓存池实现](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

```text
prefill → 小 DRAM 写入缓冲 → NVMe 段文件
               ↓                  ↓
             GPU  ← DRAM 读取暂存 ← 读盘命中
```

文章还把写缓冲降到 4 MiB 做了测试。在 70 会话的一次运行中，吞吐没有下降；另一组机器到 96 会话时，去掉大写缓冲却落后 DRAM 6.7%。这说明写缓冲的需要与负载有关。把轻一点的测试结果推广成“任何负载都不需要主机缓冲”会丢掉关键条件。

## 同容量的比较怎样读

主实验为 1P1D：8 张 GPU 做 prefill，另 8 张做 decode，通过 MoRIIO/RDMA 传输状态。Kimi-K3 的 decode 使用 DSpark，draft token 为 4，并使用 AgentX 配方中的合成接受长度 3.36。KV 为 FP8。每组同容量比较在相同机器、镜像和设置下前后运行，预热后测量一小时。[实验配置](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

| AgentX 并发会话 | DRAM 吞吐 | NVMe 吞吐 | 命中率，DRAM / NVMe | TTFT 中位数，DRAM / NVMe |
| --- | ---: | ---: | ---: | ---: |
| 48 | 12,240 tok/s/GPU | 12,275 | 96.62% / 96.67% | 1.57 / 1.57 秒 |
| 70 | 13,380 | 13,492 | 95.57% / 95.65% | 5.19 / 4.89 秒 |
| 96 | 13,313 | 13,284 | 94.50% / 94.48% | 24.95 / 24.39 秒 |

表中为作者公布的第一组比较。吞吐同时计入输入与输出 token，包含已缓存的 prompt token，分母为全部 16 张 GPU；它不同于只计新生成 token 的 decode 吞吐。TTFT 为从请求开始到首个 token 的时间，包含队列等待。

NVMe 的读取本来更慢，但 vLLM 可以异步加载状态，同时处理其他请求。在繁忙引擎里，请求本来就要等待 prefill 槽位，加载在等待结束前完成，就不必继续拖长这次请求。若队列很短，这部分额外时间就可能直接落到 TTFT 上。

原文引用的单请求比较是另一个条件：Kimi-K2.6、SGLang、128K 前缀及八块盘，其中六块在第二个节点。DRAM 命中约 0.45 秒出首 token，NVMe 约 0.84 秒，重算约 7.7 秒。这个例子说明“比重算划算”，却不能与上表当成同一次 vLLM 测量。

长 prompt 的 kvlab 比较在 70 会话中得到 DRAM 8,162、NVMe 8,110 tok/s/GPU，差约 0.6%。作者同时指出该共享集群单配置的运行间波动约 ±2.5%，且此比较仅运行一次。差值小于这种波动，结果支持本次未观察到明显吞吐损失，不能精确断言两介质的真实差距就是 0.6%。

## 扩大容量带来的收益为什么更大

在 kvlab 的另一组运行中，4.6 TB NVMe 在 70 会话下的吞吐约为 1.0 TB DRAM 的 5.1 倍。这里容量不同，DRAM 命中率已跌到约 52%，NVMe 仍约 93%。文章也提供 1.8 TB DRAM 在类似负载下保留约 91% 命中的结果。这组 5.1 倍主要来自缓存能否留住前缀。[容量与保留时间](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

当缓存太小，重算会占用 prefill，队列增长，会话之间的间隔变长，前缀需要保存更久才能命中。更长间隔又增加淘汰机会，形成相互加重的过程。部署时要看会话恢复间隔和缓存写入速度，不能只看 SSD 顺序读取带宽。

一个粗估关系是：

```text
T ≈ C / W
```

`C` 是可用缓存容量，单位 TB；`W` 是写入速度，单位 TB/小时；`T` 为可保留的小时数。它把持续流量近似成均匀写入，实际 LRU、块复用、checkpoint 和淘汰规则会改变分布。

用文章四舍五入后的 1.8 TB 和 3.5 TB/小时，得到约 31 分钟。对用户暂停两小时再回来的会话，这样的池可能已经失去前缀；若下一轮多在几秒内到达，更长保留时间可能没有同样收益。

原文用真实会话时间建立 LRU 模型，估计一天保留比约半小时少丢约一个百分点的 prompt token，再套用吞吐拟合估计约 10% 收益。这一步连续使用两个拟合模型，而且一天保留的池没有实机运行，应该保留为估算。

## SSD 要按写入寿命一起算

缓存可以重算，但 SSD 仍会磨损。文章在 96 会话下记录每天约 83 TB 写入。两块各 3.84 TB、额定约 1 DWPD 的盘，承担的总写入约为每天 10.8 倍盘容量。DWPD 指每天相当于多少次全盘写入。

按五年、每天一次全盘写入的额定预算粗算，这种负载约 169 天就用完写入预算。它不是预测盘会在第 169 天损坏；实际寿命、写放大、负载与厂商保修条款需要单独判断。[写入与成本估算](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

下面的代码复算原文使用的数量级，价格是文章引用的 2026-11-13 列表价格，不能当作当前采购报价。

```python
capacity_tb, write_tb_per_hour = 1.8, 3.5
observed_tb_per_day = 83  # 原文日写入，小时数值经过四舍五入
physical_drive_tb = 2 * 3.84
retention_minutes = capacity_tb / write_tb_per_hour * 60
dwpd = observed_tb_per_day / physical_drive_tb
rated_budget_days = 5 * 365 / dwpd
nvme_five_year_usd = observed_tb_per_day * 666 + 3400
dram_1_8tb_usd = capacity_tb * 1000 * 42
print(round(retention_minutes, 1), round(dwpd, 1), round(rated_budget_days))
print(round(nvme_five_year_usd), round(dram_1_8tb_usd))
# 30.9 10.8 169
# 58678 75600
```

这个模型假设持续运行五年，每 TB 企业 SSD 为 666 美元，另计约 3,400 美元缓冲 DRAM；server DDR5 按每 GB 42 美元。容量累加到约 83 TB、额定 1 DWPD，就能用同一批盘承担日写入并获得约一天保留。较小 NVMe 池若按磨损频繁替换，在这个简化模型里消耗相近的总盘预算。

文章估计约 5.9 万美元的 NVMe 方案与约 7.6 万美元的 1.8 TB DRAM，并明确排除了电力、机架及承载 SSD 的服务器等费用。83 TB NVMe 是规划算术，最大的实测 NVMe 池只有 4.6 TB。完整采购判断还要计入设备带宽、故障域、冗余和运营费用。

## 实现细节为何会改变结论

第一项是段文件大小。UMBP 追加写块，淘汰单块未必释放文件空间；需要删除整个段文件。4 GiB 的段可能把仍在用的块和冷块一起丢掉。原文把段改为 256 MiB 后，70 会话的命中率从 94.45% 升到 95.65%，吞吐从 11,672 升到 13,492 tok/s/GPU。文件更多也会增加句柄管理开销。

第二项是最近使用记录。GPU 命中了前缀时，外部池可能看不到访问，误把自己的副本当作冷数据。`touch` 将 GPU 命中通知池，刷新块的使用时间。这样，GPU 后来淘汰这个前缀时，池中更有可能还留着副本。

第三项是混合模型状态。Kimi-K3 的线性注意力 KDA 需要 checkpoint，只有普通逐 token KV 还不足以从共享前缀的任意位置恢复。更密的 checkpoint 可以减少重算，也会增加写入。文章测试过淘汰已被后续状态替代的 checkpoint，以降低写入；这些测试使用不同配置，收益不能简单相加。[三项实现经验](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)

版本同样影响调参是否真正生效。MoRI PR #967 修复了 backend policy 忽略 `UMBP_SSD_*` 参数的问题。本次核对 GitHub 记录，该 PR 于 2026-11-17 合并，merge commit 为 `7e23fa2ae5fa42c66e1f1f137d51bc0eb4c6a3d4`。旧构建即使传入小段参数，也可能继续使用默认大段。[官方修复记录](https://github.com/ROCm/mori/pull/967)

原文同时使用关闭 checksum 和 relaxed durability 的性能条件，并列出尚未合入上游的修改。因此复现时要保存准确软件构建、补丁、缓存策略和检查开关，只复制一条启动命令还不足以复现论文式结果。

## 怎样判断自己的服务是否适用

本文推导出的选择条件是：先测真实会话的 prefix 复用间隔、token 命中率、外部池承担的读比例和日写入，再按目标保留时间计算容量与耐久预算。接着比较同容量池的首 token 延迟和吞吐，分别看闲时与繁忙时，最后再测扩大池容量的收益。

如果服务大部分状态都必须从池读取、模型每 token 保存的 KV 大得多，或者没有排队窗口隐藏加载，NVMe 的读取成本可能显著增加。原文没有覆盖外部池承担大多数 token 的同容量比较；所有主实验是 MI355X、UMBP、Kimi-K3 或 DeepSeek-V4-Pro，不能直接推广到任意 dense 模型和硬件。

对 EverAgent 的学习价值，是把“缓存快不快”拆成三个可测问题：状态是否还在、加载能否与其他工作重叠、长期写入能否承担。报告工作台本身不需要这类 GPU 缓存架构。
