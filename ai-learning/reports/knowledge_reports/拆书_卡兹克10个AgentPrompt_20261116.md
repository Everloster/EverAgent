# 卡兹克的 10 类 Agent 提示法：方法拆解与可直接复制的 Prompt

原文是数字生命卡兹克的《分享10个我最近指挥Agent最爱用的Prompt》。作者让 Agent 回看最近两个月的使用记录，整理出十种常用表达。[1]

它们的共同方向，是让 Agent 不只执行眼前指令，还帮助检查问题定义、比较方案、寻找反证，并从项目历史中减少重复付出。**这是一组实践经验，不是经过对照实验验证的“最优提示词”。**

下面提供 **10 段独立可复制的改写版**，逐条对应原文顺序。代码块不是原文逐字转载：本文加入了输入占位符、证据要求、范围控制和完成条件，方便用于真实任务。

**使用方法：**替换 `{{……}}` 中的内容，每次选择符合当前问题的一条即可；不必把十条同时塞进一个任务。没有提供的资料让 Agent 标明缺口，不能靠猜测补齐。提示词也不能代替工具权限、文件隔离和用户授权。

| 你现在遇到的情况 | 选哪一条 |
| --- | --- |
| 修了表面症状，问题还会回来 | [01 根因诊断](#prompt-01) |
| 目标大致清楚，但偏好与取舍没对齐 | [02 澄清并比较方案](#prompt-02) |
| 不确定自己是不是问错了问题 | [03 检查问题定义](#prompt-03) |
| 改一个地方，担心引出其他问题 | [04 推演连带影响](#prompt-04) |
| 现有领域的解法似乎走到尽头 | [05 跨领域借鉴](#prompt-05) |
| 已有方案，需要认真找反例 | [06 反方验证](#prompt-06) |
| 想清理历史包袱，但怕误删设计 | [07 回看设计历史](#prompt-07) |
| 代码能跑，却越来越难理解 | [08 降低接手成本](#prompt-08) |
| 最近变卡、变慢，不知道哪次改动导致 | [09 定位性能回归](#prompt-09) |

<a id="prompt-01"></a>

## 01｜根因诊断：先解释为什么坏，再决定怎么改

**对应原文第 1 条。** “第一性原理”的实用含义，不是要求模型发表抽象议论，而是回到系统目标、约束和可观察的失败。

```text
请调查这个问题：{{现象、报错或失败案例}}。
范围：{{相关功能、文件或系统}}。

先说明正常情况下应该发生什么，再沿输入、状态变化和输出追查偏差。把已观察的事实、待验证的假设、触发条件和候选根因分开，给出能区分这些假设的最小验证。
不要用增加重试、特殊分支或吞掉错误来代替根因解释。
若我已授权修改，实施有证据支持的最小修复，并检查复现用例和相邻行为；否则只给诊断与修复建议。
最后说明：根因、证据、修改范围、验证结果，以及尚未排除的情况。没验证过的，不写成已经修好。
```

**什么时候算有用：**能解释旧行为为什么失败，并且修复后原用例通过；不是仅仅让错误信息消失。

<a id="prompt-02"></a>

## 02｜澄清偏好：让三个方案真的有取舍

**对应原文第 2 条。** 澄清应减少方向上的误差，而不是让用户回答模型本来可以自己查明的事实。

```text
我想实现：{{目标}}。
已知约束与偏好：{{时间、成本、风格、兼容性或其他要求}}。

先检查信息缺口。只有那些会改变方案、且无法从现有资料确认的问题，才需要问我；其余采用合理默认并标明假设。问题尽量合并，不逐项拖延。
对齐后给出 3 个真正不同的方案，说明各自适用条件、主要代价、放弃了什么，以及最小验证方式，不要只是换名字或配色。
根据我的目标推荐一个，并解释选择依据。若实际只有一种合理路线，也请直说另外两种为什么不值得选，不要为了凑数制造方案。
此轮先比较方案，不直接修改或发布。
```

**什么时候算有用：**用户能看懂选择 A 而不是 B，究竟接受了什么代价。

<a id="prompt-03"></a>

## 03｜检查问题定义：别把手段当目标

**对应原文第 3 条。** 这一步不是让 Agent 一律反对用户，而是检验当前问题是否真的指向要解决的困难。

```text
我现在提出的需求是：{{我的问题或拟采取的办法}}。
背景与不能改变的约束：{{背景、目标、限制}}。

先分别写清：我明确要求做什么、可能想达成什么结果、我假设了哪些因果关系。不要把你推测的目标当成我已经确认的目标。
检查当前需求是否只在处理症状，或把某种实现手段当成了目标。若有更值得解决的问题，用现有证据和具体反例说明，并给出一个最小验证办法。
如果当前定义合理，就明确支持它，不要强行重新定义问题。存在多个合理解释时，只问会改变下一步行动的澄清问题。
不要擅自更改我已经明确选择的目标、范围或授权。
```

**什么时候算有用：**找到一个可以验证的错误前提，或确认当前问题值得继续，而不是给出更宏大的口号。可与 [XYBench 学习报告](./XYBench_问题背后的目标与回答重心_深度解析_20261115.md)对读。

<a id="prompt-04"></a>

## 04｜连带影响：沿着具体变化往后看

**对应原文第 4 条。** 二阶、三阶影响需要有中间机制，不能只列一张包罗万象的风险清单。

```text
计划中的改动：{{改动说明}}。
重点场景：{{用户、模块、部署环境或业务流程}}。

从直接变化开始，沿“改变了什么 → 谁受到影响 → 对方会怎样响应 → 后续产生什么结果”的链条，分析重要的二阶、三阶影响。
优先检查接口与数据兼容、其他模块、用户行为、资源消耗、系统复杂度和维护成本；只展开有合理依据的路径。
每项写清成立条件、影响范围、可观察信号和缓解或回滚办法。区分已经证实的影响与条件性推测，不虚构概率。
最后指出最值得先验证的连带影响，并说明它是否足以改变当前方案。此轮不执行改动。
```

**什么时候算有用：**能指出“新功能本身正常，但哪一条依赖或哪种行为可能改变”，并知道如何观察。

<a id="prompt-05"></a>

## 05｜跨领域借鉴：借机制，不只借比喻

**对应原文第 5 条。** 跨领域思考的价值，在于找出相同的约束结构；表面上“很像”，不足以证明方法可迁移。

```text
要解决的问题：{{问题}}。
关键约束与现有做法：{{约束、资源、已经尝试的方法}}。

寻找其他领域中结构相似的问题，而不只是名称相近的案例。对每个值得借鉴的方案，说明它解决的矛盾、起作用的机制，以及这些条件在当前问题中是否成立。
区分可直接迁移、需要改造和不能迁移的部分；给出可靠来源，查不到时明确说未核实，不编造案例。
把最有希望的候选与现有方案比较，说明收益、适配成本、失败边界和一个小规模验证方式。
目标是找到当前约束下更合适的办法，不要声称已经证明全局最优；此轮先研究，不实施。
```

**什么时候算有用：**借来的方法能够对应当前问题中的变量、约束和验证条件，而不只是听起来有启发。

<a id="prompt-06"></a>

## 06｜反方验证：找能改变决策的反证

**对应原文第 6 条。** 认真反对一个方案，不等于必须把它推翻。反证不存在或证据不足，也应该保留这个结果。

```text
当前方案：{{方案}}。
支持它的理由与已知证据：{{理由、数据、已有测试}}。

请从最强、最合理的反对立场审查它。先找出决定方案成立的关键假设，再寻找可以推翻这些假设的证据、反例和边界输入。
优先提出会影响选择的实质问题，不挑无关措辞，也不为了反对而反对。能查证的就查证，不能查证的给出明确的反证测试。
根据结果重新判断：保留、收缩适用范围、修改，还是换方案。解释哪些证据改变了你的判断，哪些只是尚未解决的疑虑。
若没有找到足够反证，请直说；不要把自己生成的批评当成已验证事实。此轮不实施修改。
```

**什么时候算有用：**知道方案依赖哪几个脆弱假设，以及什么结果出现时应该改变决定。

<a id="prompt-07"></a>

## 07｜设计历史：先理解为什么留下，再讨论删除

**对应原文第 7 条。** 原文建议看 Git、关键 PR 和架构演变。本文将默认范围收窄，避免一次清理变成没有边界的全仓考古。

```text
请分析 {{模块或功能路径}} 的设计历史。
关注范围：{{时间段、版本区间或相关问题}}。

从当前行为追到相关提交、PR 讨论和当时的问题，区分有明确依据的设计、兼容要求、临时折中，以及原因仍不清楚的代码。不要仅凭代码年龄或“看起来多余”判定它是历史包袱。
对可简化或移除的候选，检查当前调用方、配置开关、外部兼容约定和测试覆盖；说明原问题是否真的已经消失，并引用可定位的证据。
输出候选清单：位置、原目的、当前必要性、预计收益、潜在影响、验证与回滚办法。
缺少历史证据的单列。只提出建议，未经确认不删除；只有必要时才扩大调查范围。
```

**什么时候算有用：**能够回答“这段代码原来防住什么，今天还需不需要”，而不是仅统计未被搜索命中的函数。

<a id="prompt-08"></a>

## 08｜接手成本：让一个有能力的新同事读得懂

**对应原文第 8 条。** 认知成本很难凭阅读直接精确计时，但可以定位必须在脑中同时记住太多东西的地方。

```text
请以“能力很强、但第一次接触本项目的工程师”的视角，审查 {{模块、功能或目录}}。
典型任务是：{{对方需要理解或修改的事情}}。

沿这个任务实际经过的代码和文档，找出命名歧义、职责交叉、隐藏依赖、过度跳转和没有解释清楚的约束。区分必要的业务复杂性与实现额外制造的复杂性。
每个发现给出具体位置、理解障碍、现有行为，以及不改变外部行为的简化建议。优先考虑统一命名、收拢职责和减少无必要的间接层，不默认引入新框架。
按预计收益和改动成本排序；没有实测就不要编造“节省几小时”。此轮只评估，先不改代码。
```

**什么时候算有用：**新同事能够更直接地解释一条数据或控制路径，而不是仅仅少读几行代码。

<a id="prompt-09"></a>

## 09｜性能回归：先量出慢在哪里，再追到 PR

**对应原文第 9 条。** “找最慢的 PR”有歧义。结合原文的“卡顿”，这里采用**改动造成的运行性能回归**，而不是 PR 等待审核或合并的时间。

```text
请调查 {{开始日期}} 至 {{结束日期}} 期间，影响 {{业务路径或模块}} 的 PR 是否引入性能回归。
本次“慢”指：{{响应延迟、启动、构建、查询、渲染或吞吐指标}}，不是 PR 审核耗时。

先确认可重复的基线、输入、环境和测量方式，再筛选可能相关的 PR，比较变更前后。优先复用现有性能记录、测试或 profiler；不要仅凭改动行数和直觉排名。
有测量证据时列出影响最大的候选、瓶颈、因果依据及最小优化方案；无证据时只列待验证假设和验证计划。
说明噪声、并发及其他同时变化的因素。此轮仅读取和分析；运行基准需在已授权环境中进行，不触碰生产负载。
```

如果你要查的是**研发协作效率**，应改用首次响应、等待评审、返工轮次和合并耗时等时间线数据，不能拿程序 profiler 回答。

<a id="prompt-10"></a>

## 10｜重复返工：把教训变成小而有效的预防措施

**对应原文第 10 条。** 一次失误不一定值得增加永久规则；共同根因需要多个案例支持，自动化也有维护成本。

```text
请复盘 {{开始日期}} 至 {{结束日期}} 在 {{项目或模块}} 中出现的 Bug、返工、回滚和重复修改。

先收集可追溯的案例：触发条件、影响、修复、是否再次发生，以及当时缺失的检查。区分相似表象与共同根因，不把时间接近当成因果关系。
找出有多个案例支持、且可以预防的共性问题，为每类选择最小有效措施：测试、自动检查、清晰规则、文档或按需加载的 Skill。
每项说明覆盖哪些旧案例、如何验证有效、误报与维护成本、何时应当修改或删除。单次特例先留在案例中，不自动升级成全局指令。
先提交复盘与优先建议，不擅自改配置、安装钩子、创建 Skill 或扩大自动化权限。
```

**什么时候算有用：**新措施能解释它预防了哪类真实问题，并有办法检查是否有效，而不是把每次失败都加进一份越来越长的规则文件。

## 这十条背后的方法：从“给答案”转向“给判断过程”

下面是本文对原文的结构重构，不是作者额外提出的理论：

- **1—3：先确认要解决什么。** 根因、偏好和问题定义分别约束了诊断、方案选择和目标判断。
- **4—6：不要过早锁定一种答案。** 连带影响、跨领域方法和反证，帮助发现当前方案遗漏的成本与条件。
- **7—10：把一次修改放回项目的时间里。** 历史意图、接手难度、性能变化和重复返工，影响的都不只是眼前代码是否能跑。

它们改变的是 Agent 要做的工作，而不只是说话风格。例如“请更深入思考”没有给出检查对象；第 7 条要求对照历史意图和当前调用关系，第 9 条要求同条件测量，第 10 条要求拿实际失败案例验证预防措施，因而更容易判断是否完成任务。

不过，提示中出现“找证据”并不保证证据存在，更不保证模型不会误读。实际效果仍依赖资料、工具权限、模型能力，以及人是否检查了关键结果。

## 本文改写时增加了什么

原文的提示较短，适合作者已经建立上下文的会话。为了让这里每段都能独立复制，本文增加了四类内容：

1. **明确输入与范围**：用占位符说明调查对象，避免“全面分析”默认触发全仓扫描。
2. **把证据与假设分开**：要求文件位置、提交、测试或来源；未验证不伪装确定。
3. **说明交付物**：诊断、备选方案、反证或复盘各有不同的完成条件。
4. **区分分析与实施**：删代码、跑负载、改配置和建立长期自动化，需要相应授权。

这些补充是为了让任务更可检查、范围更清楚，不是保证改写版一定比原文效果更好。对已经充分授权、约束明确的任务，可以删掉不必要的重复说明；不要为了模板，让简单问题变成多轮审批。

## 怎样判断 Prompt 真的有帮助

不建议只问另一个模型“这段 Prompt 能打几分”。可以选几项真实、可重复的任务，用相同模型、权限、材料和起点，对比原有提示与某一条改写版：

- 结果是否正确、能否复现？
- 是否找到了原先遗漏的根因或约束？
- 有没有无必要的扫描、追问或范围扩张？
- 时间、Token、人工验收和后续返工成本如何？

没有必要让每个任务都使用全部十条。例如，已有明确复现步骤的小 Bug，可以先用第 1 条；影响多模块的方案，再加第 4 或第 6 条；稳定重复的问题出现后，才考虑第 10 条。

本次完成了原文十条与改写版的对应检查、代码块数量和占位符检查、内链与工作台渲染检查；**没有执行这些提示所描述的全仓审计、删除、性能测试或配置修改，也没有进行 Prompt 效果对照实验。**
