# 浏览器怎样运行 PyTorch 模型

假设要做一个文档问答网页，希望用户打开页面后，模型就在其电脑上处理文档。把 PyTorch 权重文件放到网站上还不够：浏览器要知道怎样执行模型的计算图、怎样调用 GPU，以及输入变长以后如何管理内存。

2026 年 11 月 10 日，PyTorch 介绍了 ExecuTorch 的 WebGPU 后端。它提供了一条仍在 PyTorch 工具链内的部署路径：将模型导出成 `.pte`，由浏览器中的 ExecuTorch 运行时调度 GPU 计算。[1] 这个改变值得研究的地方，是导出、运行时和浏览器之间怎样分工，以及这条路径究竟把哪些成本移到了用户设备上。

## 1. 一个模型，经过两次不同性质的准备

第一段发生在开发者侧：把训练时使用的模型，变成面向部署的计算表示。`torch.export` 得到导出图，ExecuTorch 的转换与分区过程决定哪些子图交给后端，最终保存到 `.pte` 文件。

第二段发生在运行侧：读取模型产物，准备张量存储与计算管线，执行请求。浏览器里，C++ 运行时被编译为 WebAssembly；GPU 上执行的则是 WGSL 计算着色器。`emdawnwebgpu` 将相应调用接到浏览器 WebGPU API。[1][2]

可以用下面的逻辑关系理解；这是处理流程示意，不是实际运行日志：

```text
开发者侧
PyTorch 模型 → 导出图 → 子图分区与转换 → .pte 模型产物
                                               │ 下载
浏览器侧                                       ▼
网页输入 → ExecuTorch Wasm 运行时 → WebGPU 命令 → GPU 计算
                    │                              │
                    └──────── 取得并呈现结果 ───────┘
```

WebAssembly 与 WebGPU 在这里承担不同工作。前者让部署运行时能在浏览器环境执行，后者向 GPU 提交计算。看到 Wasm 文件，不能据此判断主要张量运算都在 CPU；看到 WebGPU 调用，也不能据此判断整张图完全没有 CPU 工作。

所谓“不需要转换到其他框架格式”，是指不必先走 ONNX、TFLite 等另一套模型表示。**导出和针对后端的转换仍然存在**。训练代码里的任意 Python 控制逻辑，也不会因为文件后缀变成 `.pte`，就自动获得浏览器执行能力。

## 2. 为什么 WebGPU 后端里面会出现 Vulkan

固定版本的实现复用了 Vulkan 分区与序列化路径：`.pte` 中可以带有 `VH00` 头和 `VK00` FlatBuffer，delegate 标识也沿用 `VulkanBackend`。WebGPU 运行时再按自己的方式分配 buffer、建立管线并执行 WGSL；它不会把这些名字理解成必须在浏览器里直接运行 Vulkan 程序。[2]

这是一种复用已有基础设施的设计。模型图的描述格式、算子的执行实现和最终硬件 API，可以处于不同层。浏览器负责将 WebGPU 计算映射到其支持的平台后端；开发者面对的是共同接口，但仍需满足设备实际提供的功能和限制。[1][4]

因此，“同一份模型产物跨设备运行”更适合理解成减少了按平台重新导出的工作。它不保证不同设备具有相同的速度、内存上限、浮点行为或算子可用性。

一个实际的排障顺序是先定位失败发生在哪层：导出图是否成立、子图是否正确分区、GPU 管线是否能建立、运行时形状是否受支持，最后才检查结果质量。只说“浏览器不支持模型”，往往把几种不同问题混在了一起。

## 3. 有这个算子，不等于这个算子的所有用法都能上 GPU

README 列出超过一百个注册算子符号，同时提醒：注册表覆盖面不等于任意模型的端到端兼容性。[2] 一个算子的名称之外，还有数据类型、参数、形状、融合方式和图中位置等条件。

源码提供了两个很具体的例子：[3]

| 检查 | 固定版本中的限制 | 为什么只看名字不够 |
|---|---|---|
| `arange` | 起点、终点或步长由图节点动态给出时，不交给这里的 WebGPU 实现 | 该内核不会据此重新调整输出长度 |
| `native_layer_norm` | 除最后一维外，其他被归一化维度需要为 1，并通过继承的检查 | 当前内核并没有实现任意多维归一化形式 |

这些检查的目标，是把不支持的形式留在 CPU 路径，避免进入 delegate 后才失败。能否完成剩余计算，仍取决于整个部署产物是否带有所需执行支持。

这里还有一处需要同时读文档与代码：README 将导出前端概括为较薄的 Vulkan 包装，并说更窄的 WebGPU 能力策略由集成方另行处理；但同一提交的 `partitioner.py` 已有 `_WEBGPU_OP_FEATURES`，把 WebGPU 特定的数据类型和形状约束传给 Vulkan 分区器。[2][3] **不能把 README 的概括读成“完全没有 WebGPU 专属检查”，也不能把这些局部检查读成完整兼容性证明。**

对一个新的文档问答模型，导出成功后还应查看实际分区。如果某一段需要 CPU，前后段在不同执行域之间的交接、同步和数据表示转换可能成为开销。具体代价取决于设备与实现，不能简单拿“GPU 算子的速度”代表整张图的速度。

## 4. Prefill 和 decode 为什么需要不同的计算策略

自回归文本模型先处理输入上下文，再逐步生成输出。前者通常称为 prefill，后者称为 decode。

Prefill 可以把多个输入位置组织成较大的矩阵运算；逐 Token decode 的矩阵形状和并行机会不同，还要读取此前的 KV 状态。后端因此根据实际形状选择不同内核。README 中对应的设计包括 prefill 的分块 GEMM、decode 的协作 GEMV，以及注意力和缓存相关优化。[2]

这说明后端优化并不只是把 CPU 上的一个循环改写成着色器。它还要决定怎样分块、怎样复用局部数据、如何减少小计算的启动开销，以及哪些缓冲区可以继续使用。

也因此，一组实现可能在长输入上提速明显，在短输入上收益较小；生成长度、上下文长度和模型结构变化后，瓶颈还会改变。某个 prefill 加速比，并不是整个交互请求的统一加速比。

## 5. “快 4—7 倍”究竟与什么相比

原博客给出的比较条件如下：[1]

| 项目 | 原文条件 |
|---|---|
| 设备与浏览器 | Apple M1 Pro，Google Chrome |
| 模型 | 量化 Llama 3.2 1B、Qwen3-0.6B |
| CPU 基线 | ExecuTorch Wasm + 多线程 XNNPACK |
| 输入 | 128 至 8K 上下文 Token；两后端使用相同 Token ID |
| 统计与时钟 | 3 次预热后测 5 次，取中位数；两边都用墙钟时间 |
| GPU 数值设置 | 4-bit 分组权重，组大小 64，fp32 激活 |
| CPU 数值设置 | 4-bit 权重，8-bit 动态量化激活 |

在这些条件下，作者报告 prefill 提速 4—7 倍、decode 提速 2—10 倍。它衡量的是两套具体执行路径，**不等于相同数值计算仅更换硬件后的纯粹速度比较**：两边的激活表示不同。使用相同输入，也不自动证明输出逐位一致或所有任务质量相同。

预热后的测量还排除了部分首次运行开销。用户第一次打开页面，可能仍需下载模型、初始化 Wasm、建立 GPU 管线。若真正关心“打开页面到得到第一条可用答案”，就应把这些阶段单独记录。

固定版本 README 还列有另一组数据：2026 年 7 月，M4 Pro、Chrome Canary、GPU timestamp queries，3 次预热后测 3 次。[2] 这组数据的设备、测量时钟、模型产物和样本数都不同，不能将其绝对吞吐量与博客里的 CPU 结果拼接成新的加速比。

本报告没有复现上述性能结果。它们足以说明作者已经验证过有价值的 GPU 路径，尚不足以保证所有浏览器、手机和模型都具有同样收益。

## 6. 动态形状支持，为什么还可能占用很大的内存

该后端支持运行时改变形状，但张量存储采用按最大形状分配、执行时调整实际维度和工作组的方式。[1][2] 所以“这次只用了短输入”不必然意味着预留容量也相应缩小。

可以用一个自拟的 KV Cache 例子理解容量问题。假设采用普通、未压缩的 K/V 存储，参数为：

- 16 层，批量为 1。
- 每层 8 个 KV 头，每头 64 维。
- 最大序列长度 8,192，每个数值 2 字节。

K 和 V 各存一份，所需容量为：

```text
2 × 层数 × 批量 × 序列长度 × KV 头数 × 头维度 × 每值字节数
= 2 × 16 × 1 × 8192 × 8 × 64 × 2
= 268,435,456 字节
= 256 MiB
```

若只按 128 个位置计算，同样公式得到 4 MiB。但假如这份缓存按最大窗口预分配，当前只处理 128 个位置，并不会自动释放其余容量。这里的数字是教学设定，**不是 Llama 或本文后端某个导出配置的实测内存**。

KV 之外还要考虑权重、激活、临时工作区、模型加载时的主机侧副本，以及网页本身。4-bit 权重也不意味着运行时所有张量都只用 4 bit；量化比例、未量化的部分和其他数据结构仍有成本。

WebGPU 又有独立的 adapter/device 功能与资源限制。[4] 机器物理内存充足，不代表某个 buffer、绑定方式或工作组配置就被当前浏览器接受。因此，模型文件能下载下来，与运行时能够分配并执行，是两次不同的检查。

## 7. 本地推理怎样改变隐私、离线与部署责任

把推理放在用户设备上，可以使提示词、文档和输出不必发送给远程模型服务。博客以 Playground 展示这条本地数据路径。[1] 但一个任意网站是否上传输入，还由页面代码、统计服务、云端回退和产品配置决定；WebGPU 本身不负责禁止网页联网。

离线使用也有前置条件：运行时和模型等资源必须已经可取得。将 `.pte` 放在 CDN 上解决的是分发，不能单凭它证明第一次访问或下一次断网打开页面都能成功。产品需要明确哪些资源已缓存、缓存失效后怎样处理，以及是否允许回退到云端。

对兼容性，WebGPU 规范给出了更细的边界：`navigator.gpu` 提供入口，`requestAdapter()` 可以返回空，adapter 公开功能和限制，设备也可能丢失。[4] 一个界面应区分“不支持此路径”“初始化失败”和“推理中断”，不要把它们都显示成正在生成。

这些要求并不否定浏览器部署的价值。它降低了安装门槛，也把部分服务端成本转移到用户的内存、计算、下载等待和电量上。对较小模型、特定任务或不愿上传内容的用户，这种取舍可能合适；需要大模型、长上下文或大量并发的任务，则未必适合完全放进一个标签页。

## 8. 从一次演示走向可用页面，怎样验证

如果试做一个本地文档问答页面，我会让验证覆盖以下过程，而不只测一个成功生成的片段：

| 场景 | 需要观察的结果 |
|---|---|
| 第一次访问 | 模型下载、运行时初始化、首次答案的总等待 |
| 重复使用 | 预热后的 prefill、decode 与整体响应时间 |
| 文档逐渐变长 | 内存峰值、最大窗口、超出限制后的反馈 |
| 模型更换或部分算子留在 CPU | 结果质量、执行分区与交接成本 |
| 标签页或 GPU 设备状态改变 | 能否报告中断、重新初始化，以及避免呈现残缺结果 |
| 本地与云端组合 | 用户是否能理解实际的数据去向 |

这些是根据数据路径提出的实验设计，本次没有实施浏览器 GPU 测试。

文章还展示了视觉、语音和设备上适配器训练等工作流。[1][2] 它们说明后端的用途不止聊天；但推理能运行，不代表同一模型、同一设备上的训练也自动可行。训练还涉及反向算子、优化器状态和更大的工作内存，应作为另一项工作负载验证。

ExecuTorch WebGPU 的价值，在于把 PyTorch 导出、轻量运行时和浏览器 GPU 连成了一条可复用路径。采用时最应保留的区别是：模型产物的可移植性、算子与形状的兼容性、真实设备的资源预算，以及用户最终感受到的交付效果。
