# 无状态的鹦鹉，怎么学会了连续对话和自己用工具？

> **这篇讲什么**：跟着一次带工具的对话，把 Agent 的执行循环、连续对话、上下文膨胀、缓存、Message Threads 和流式交付接起来。
>
> **贯穿例子**：“查一下 2026 年 6 月杭州空调销量。”随后追问：“那和 5 月相比呢？”文中的 12,000 台、10,000 台均为合成示例，不是真实市场数据。
>
> **怎么读**：顺读看因果链；快速回顾看每节“✦ 一句话”和最后的一页纸；报文与版本细节在折叠块中。产品能力核验截至 2026-11-03。

## 第一部分 · 两个角色，一次完整往返

### 1. 鹦鹉有本领，管家有记录和执行权

✦ **一句话：模型负责根据上下文作出判断；Harness 负责提供上下文、执行工具、把结果交回模型。**

想象一只博学、善于推理，却不会自动记住每次接待过程的鹦鹉。它能读纸条、写纸条；要查数据库、读文件，必须通过外面的管家。

管家每次把“规则 + 工具说明 + 相关历史 + 你的问题”组织成一张纸条。鹦鹉读完，可能写出答案，也可能写“我需要查一下销量”。管家替它查，带回结果，鹦鹉再继续判断。

| 角色 | 对应什么 | 核心职责 |
|---|---|---|
| 🦜 鹦鹉 | LLM，大语言模型 | 理解材料、推理，生成答案或工具调用请求 |
| 🎩 管家 | Agent Harness，运行与编排层 | 维护会话、组装上下文、管理权限、执行工具、控制循环 |

**“无状态”针对的是会话连续性，不是说模型没有知识或推理能力。** 训练获得的本领在模型参数里；你刚才查了哪座城市、工具返回多少台，则要由运行系统提供。一次普通推理，不会自动把这些对话事实写成模型参数中的私人记忆。

同样，模型与模型服务不是一回事：**模型不自带可靠的会话记忆，外层服务却完全可以保存会话和计算状态。** 后面的 Threads 与缓存，就发生在这些不同层次。

Claude Code 官方把 Agent 的工作概括为“收集上下文—采取行动—验证结果”的循环，Harness 则是围绕模型提供工具、管理上下文的那一层。[^loop]

### 2. 从一句问题，到一次真正的工具执行

✦ **一句话：工具调用是模型写出的申请单；真正改变外部世界的是执行这张单子的程序。**

现在发出那条问题：**“查一下 2026 年 6 月杭州空调销量。”**

```text
① 用户提问
  ↓
② 管家准备上下文：问题、规则、get_sales 工具说明
  ↓
③ 鹦鹉输出：调用 get_sales(city="杭州", month="2026-06")
  ↓
④ 管家检查工具、参数与权限，执行查询
  ↓
⑤ 工具返回：12000台；范围为同一组虚构门店
  ↓
⑥ 管家回填结果，再请求模型
  ↓
⑦ 鹦鹉解释结果，管家把答案交给用户
```

第③步是整个 Agent 最关键的分界线。模型并没有联网查询，它生成的是一个**结构化调用意图**。第④步才发生真实执行。屏幕上“我来查一下”的自然语言，既不能替代调用对象，也不能证明查询已经开始。

为什么要分开？因为**知道该做什么，与有权执行什么，不是同一回事**。模型可以提出申请；运行系统仍要检查工具是否存在、参数是否符合要求、当前用户是否有权访问对应数据。参数符合 schema，只说明格式合规，不证明业务授权正确。

<details>
<summary>证据：Claude 的工具请求与结果怎样配对</summary>

下面是按官方字段形状编写的响应片段，ID、工具名和数据为教学示例：

```json
{
  "stop_reason": "tool_use",
  "content": [{
    "type": "tool_use",
    "id": "toolu_demo_june",
    "name": "get_sales",
    "input": {"city": "杭州", "month": "2026-06"}
  }]
}
```

执行结果作为另一条消息回填：

```json
{
  "role": "user",
  "content": [{
    "type": "tool_result",
    "tool_use_id": "toolu_demo_june",
    "content": "合成示例：杭州同一组虚构门店，6月销量12000台。"
  }]
}
```

`tool_use_id` 绑定对应的调用。这里的 `user` 是协议角色，不表示这份数据由人手敲。普通无线程调用还要带回此前的 assistant 内容块；不能只抽出一个数字，丢掉调用关系和协议要求保留的状态。[^tools]

</details>

工具失败时，返回错误也是正常反馈：模型可以补参数、改查法，或说明目前查不到。若结果还不足以回答，流程从第③步再走一次。

这就是 **agentic loop**：

> **判断 → 请求行动 → 执行 → 观察结果 → 再判断。**

一次用户任务因此可能包含多次模型请求和工具调用。SDK 可以帮你运行循环，但没有消除这些职责。多个查询互不依赖时，也可以并行执行，再把对应结果交回。

工具也不一定都在你的电脑上。**客户端工具**由应用执行；**服务端工具**由供应商平台执行。模型、工具和 Harness 是职责划分，不是要求它们一定部署在三台机器上。[^tools]

## 第二部分 · 连续对话，究竟连续在哪里

### 3. “那上个月呢？”为什么不是一句没头没尾的话

✦ **一句话：上一轮的提问、回答和工具结果继续参与本轮输入，所以模型能理解追问。**

你追问：“那和 5 月相比呢？”

模型能知道“那”指杭州空调销量，是因为后续上下文里包含相关历史。若只给它这句追问、不提供背景，也没有可恢复历史的服务端引用，它就没有可靠依据确定比较对象。

最直观的实现是维护一个 `messages` 数组：

```text
user       查一下杭州6月空调销量
assistant  请求 get_sales(杭州, 6月)
user       tool_result：12000台，同一组门店
assistant  解释6月结果
user       那和5月相比呢？                 ← 追加的新问题
assistant  请求 get_sales(杭州, 5月)
user       tool_result：10000台，同一口径
assistant  6月多2000台，较5月增加20%
```

最后的 20% 来自 `(12000 − 10000) / 10000`。保持城市、单位和门店范围一致，才使这个比较有意义；会计算不等于会自动核对统计口径。

在传统的无会话状态 API 中，管家每轮把需要的历史重新提交。于是，模型看起来“记得”，实际是**本轮输入重新提供了先前事实**。

旧篇用“整本账被反复重发”解释这个过程，直觉很好，但需要补一个边界：

> **每轮需要上下文，不意味着客户端每轮都必须重新上传全部上下文。**

API 也可以在服务端保管历史，让后续请求通过 ID 续接。两种方式传输的内容不同，但都必须让模型获得本轮所需的逻辑上下文。Message Threads 就是后一种做法。

### 4. 为什么只问了一句话，输入却有几万 token

✦ **一句话：模型看到的是完整工作上下文，不只是聊天框里的用户文字。**

一次请求的输入可以拆成：

```text
规则与系统指令
+ 工具名称、描述和参数定义
+ 相关项目资料、检索片段
+ 历史提问、模型输出、工具结果
+ 当前问题
```

这些材料都可能占用 token。token 是模型的处理单位，不固定等于一个汉字或单词；图像、文档也有对应输入开销。本轮生成的输出同样要占上下文窗口。[^window]

在销量查询里，问题只有十几个字，工具却可能返回几百行门店明细。这些明细随后又成为下一轮输入。因此，**读入一次长工具结果，可能影响后续很多轮，而不只影响当前这一轮**。

未做整理时，历史大致遵循：

```text
下一轮历史 = 当前历史 + 模型输出 + 新工具结果或用户消息
```

这解释了膨胀，却不意味着历史只能增加：筛选、清理和摘要可以改变后续上下文。工程上真正要问的是：**哪些内容还值得继续带着？**

还有一个容易混淆的地方：文件存在于项目里，不等于模型已经读过；工具已经安装，也不等于完整工具定义已经加载。只有实际进入本轮上下文的内容，才是这次判断的依据。Claude Code 的 `/context` 用来观察这些占用，而不是查看模型训练过多少知识。[^loop]

<details>
<summary>把 Skills、MCP、子 Agent 放回这一层理解</summary>

| 机制 | 作用 | 对上下文的影响 |
|---|---|---|
| Skills | 按需提供工作方法、参考资料或脚本 | 描述用于发现，完整内容在需要时加载 |
| MCP | 连接外部工具和服务的协议 | 工具定义和返回结果可能进入上下文；接入不等于获得全部权限 |
| 子 Agent | 把一部分任务交给另一运行实例 | 使用自己的上下文，向主会话返回结果或摘要；fork 可以带入已有历史副本 |

子 Agent 可以隔离大量读取结果，但需要额外模型调用、任务交接与结果检查。**它是在用额外工作换取分工和上下文隔离，不是免费扩容。**[^loop]

</details>

## 第三部分 · 三个“为什么还能快”的问题

### 5. 无状态，为什么不等于每轮从头算

✦ **一句话：会话历史由谁提供，与推理引擎能否复用计算，是两个层次。**

鹦鹉需要重新获得材料，不等于处理这些材料时必须把每一步计算都重做。要理解这里，先拆开一次推理：

| 阶段 | 做什么 | 主要可复用的部分 |
|---|---|---|
| **Prefill，预填充** | 处理输入，建立后续生成所需的中间状态 | 已处理过的相同前缀 |
| **Decode，解码** | 继续生成新 token，更新状态 | 先前 token 的 K/V，而不是未来答案 |

**第一层：单轮生成中的 KV Cache。**

在典型自回归 Transformer 中，新 token 要利用此前内容。历史 token 的 key/value 中间表示可以缓存，不必每生成一个 token 就重新计算这些历史 K/V。新 token 仍然要计算，也仍要访问相关历史。[^kv]

**第二层：跨请求的 Prompt Caching。**

第二轮请求，前面可能还是同一套规则、工具说明和历史：

```text
本轮输入 = [符合复用条件的旧前缀] + [未缓存的新内容]
                    ↑                        ↑
             复用前缀计算状态          继续处理，再生成输出
```

这就回答了“输入明明更长，为什么不一定等得更久”：**输入的逻辑长度增长了，但需要重新处理的部分未必同比增长。**

它不是回答缓存。问完 6 月再问 5 月，模型不是把旧答案播放一遍，而是在复用部分前缀状态的基础上处理新问题。

Claude 的提示缓存按 `tools → system → messages` 的前缀组织；匹配条件、最低长度、断点和 TTL 都会影响能否命中。工具、系统规则或前面的消息变化，可能使相应位置之后的缓存失效。把每轮变化的无关内容放到开头，往往会破坏本来稳定的前缀。[^cache]

<details>
<summary>证据与边界：缓存不是免费，也没有把注意力总计算变成线性</summary>

- 当前 Claude 提示缓存默认保留 5 分钟，也提供 1 小时选项；缓存命中会刷新相应 TTL。缓存读取、写入和普通输入的费率不同，具体价格以对应模型为准。[^cache]
- 缓存命中的 token **仍占上下文窗口**。要判断真实命中，看缓存用量字段，而不是凭“第二次感觉快”。[^window]
- “前缀精确匹配”针对服务端提示内容及结构，不能机械理解成“HTTP 随便改一个空格就一定使全部缓存失效”。
- KV Cache 减少历史 K/V 的重复计算，但新 token 对历史的注意力访问仍有成本，缓存本身也占内存。不能笼统说“使用 KV Cache 后，整个序列的注意力总计算变成线性”。这里解释的是通用 Transformer 机制，不是 Claude 内部实现的实测。[^kv]

</details>

### 6. 已经有缓存，为什么还需要 Message Threads

✦ **一句话：Prompt Caching 减少重复计算，Message Threads 减少重复上传和前处理。**

前缀计算命中了缓存，请求仍然可能是一份很大的 JSON。它需要先上传，再经过服务端校验、分词等处理；这些开销并没有因为后面的计算可复用就自动消失。

因此，长会话的首 token 延迟，不只取决于模型算得快不快，还包括请求传输、前处理、排队与响应传回等环节。不同优化作用在不同位置。

2026 年 11 月 2 日，Anthropic 发布 Message Threads 公开 beta：**首次提交完整会话，之后只发新增消息和上一轮响应 ID。**[^threads-news]

用鹦鹉和管家的说法：以前管家每次把整本记录重新递过去；现在服务端暂存前面的记录，管家只需要补交新的一页。模型需要的背景没有减少，重复搬运减少了。

```text
普通方式
第1轮：[规则 + 工具 + 问题]
第2轮：[规则 + 工具 + 问题 + 工具请求 + 工具结果]
第3轮：[规则 + 工具 + 此前会话 + 新追问]

Threads方式
第1轮：完整内容，创建线程
第2轮：上一响应ID + 新工具结果
第3轮：最新响应ID + 新追问
```

**服务端负责把暂存历史与新增内容接起来；Agent 的工具循环仍照常发生。** Threads 没有替管家执行销量查询，也没有取消后续模型调用。

官方公告明确说，Claude 仍使用完整会话，**token 用量不变**。技术文档进一步说明，Threads 不自动开启 Prompt Caching，也不改变标准计价和现有限流。两者是互补机制，不是同一种缓存换了名字。[^threads]

公告报告的收益是：在大多数 Claude Code 用户默认启用 Threads 的情况下，**500k–1M token 请求的首 token 延迟中位数下降约 35%**。这是厂商给出的特定范围统计，不是所有任务总耗时或账单下降 35%，也不能证明某个第三方代理已经启用该功能。[^threads-news]

<details>
<summary>证据：请求怎么续接，为什么还要自己保存历史</summary>

下面只列线程相关字段，不是完整 API 调用：

```text
创建：thread = {type: "create"}
      system、tools、完整 messages

续接：thread = {type: "continue", previous_message_id: "上一响应ID"}
      messages 只含新增消息
```

当前主要约束：

1. continue 不重复发送 `system`、`tools` 或线程已保存的 assistant 内容；修改这些配置时需创建新线程。模型及一组请求配置也须保持一致。
2. 线程仅追加；同一响应 ID 只能续接一次。流式响应即使已收到 ID，也要等 `message_stop` 后再续接。
3. 线程在最后一次请求后 **5 分钟**过期，且保存是 best-effort。应用必须保留自己的完整历史，必要时重新创建；并非所有 404 都是 `thread_not_found`。
4. SDK 线程助手能维护进程内历史、处理部分重放，但不自动重试中断的流，也不替你完成进程外持久化。
5. 内容加密保存在内存，不写持久存储，最后使用后至多 **1 小时**删除。可续接期限与最迟删除期限不同；该功能不具备 ZDR（零数据保留）资格。

来源：[Message Threads](https://platform.claude.com/docs/en/build-with-claude/message-threads)。线程 TTL 与提示缓存 TTL 是两个机制，不能因为都出现“5 分钟”就视为同一份状态。

</details>

### 7. 请求变小了，为什么上下文和账单不一定变小

✦ **一句话：传输量、计算量、窗口占用和费用，是四本不同的账。**

还是比较 5 月的那一轮：

- **传输账**：这次网络上传了多少字节？Threads 主要优化它及相关前处理。
- **计算账**：哪些历史状态需要重新计算？KV/Prompt Cache 优化重复部分。
- **窗口账**：模型本轮使用多少逻辑上下文？缓存和线程都不自动删掉历史。
- **费用账**：普通输入、缓存读写、输出及工具服务，分别按什么规则收费？

所以，**“少上传”不能推出“少占窗口”；“命中缓存”也不能推出“没有输入费用”。** 一个很小的线程续接请求，可以对应一个很大的逻辑上下文。

再分清“本轮占用”和“累计用量”：同一份历史参与了很多次请求，累计输入就可能远大于窗口容量；这并不意味着某一轮超限。

<details>
<summary>字段手算：input_tokens 很小，为什么窗口仍占了 111.3k</summary>

Claude 原始 usage 中，`input_tokens` 是未缓存输入，不等于全部输入。以一组**手算示例**为例：

```text
input_tokens                 =   1,300
cache_creation_input_tokens  =  10,000
cache_read_input_tokens      = 100,000
本轮输入合计                  = 111,300 tokens
```

若总窗口为 1,000,000 tokens，输入占比为 11.13%，整数显示约 11%；减去当前输入得到的名义剩余是 888,700 tokens。窗口还需要容纳输出，不能把这个差值直接当作可任意追加的输入额度。[^window][^cache]

费用则需要各类数量乘以各自费率；输出另计，有些服务端工具还有调用费用。窗口占用比例不是账单比例。`max_tokens` 限制本次输出，也不是上下文窗口大小。

</details>

## 第四部分 · 长会话不能只靠“继续追加”

### 8. 缓存、摘要、清理、记忆，分别改变什么

✦ **一句话：缓存复用计算；摘要和清理改变当前输入；长期记忆保存以后还要取回的信息。**

如果销量工具一次返回了全部门店流水，后面十轮都携带它，即使命中缓存，也仍占窗口，并可能干扰模型抓住关键问题。

第一步通常不是换更大的模型，而是控制材料：比较月总量时，保留总量、范围、单位和来源位置；要分析某家门店时，再取相关明细。**可访问全部资料，不等于每轮都应该读取全部资料。**

再往下，几种机制的分工如下：

| 机制 | 改变什么 | 主要代价或边界 |
|---|---|---|
| **Prompt Caching** | 重复前缀的计算与计价 | 历史仍占窗口，命中有条件 |
| **Message Threads** | 上传历史的方式 | 服务端临时保存，应用仍要留副本 |
| **Context Editing** | 定向移除旧工具结果等内容 | 被移除的内容不再直接可用，还可能使缓存失效 |
| **Compaction** | 用摘要替换一段历史 | 压缩有信息损失，摘要本身也需要生成 |
| **Memory** | 跨会话保存并取回重要记录 | 需要管理来源、更新、权限与过期信息 |

以销量任务为例，合格摘要至少要保留：**同一组门店、6 月 12,000 台、5 月 10,000 台、增幅以 5 月为基数**。只留下“销量上涨 20%”，后续就可能被错误解释为杭州全市场结论。

Compaction 因而不是无损压缩。Context Editing 也不是摘要：它可以把旧结果移除、留下占位提示，而不是替你概括其中的事实。当前 Claude 支持服务端按阈值或按需压缩；工具结果清理可在服务端作用于本次输入，同时让客户端保留原始历史。[^compact][^editing]

**长期 Memory 又多了一层职责。** 下次开新会话时，要继续沿用统计口径、已确认结论和未完成问题，不能指望旧线程永不过期。它们应存在独立记录中，再按任务取回。Claude Memory Tool 就由模型请求文件操作、应用在自己控制的存储上执行；没有把这些记录写进模型权重。[^memory]

RAG（检索增强生成）则是“先检索相关资料，再交给模型使用”的过程。检索对象可以是外部知识或长期记录；**RAG 是取用方式，不等于记忆存储本身**。

<details>
<summary>当前实现的两个关键限制</summary>

**清理可能破坏缓存。** 当前 Context Editing 文档明确指出，工具结果清理会使相关提示前缀缓存失效。减少输入和保留缓存之间需要权衡，不能泛称“服务端清理不会破坏缓存”。[^editing]

**Threads 与 Compaction 不能直接任意叠加。** 当前 Threads 不支持直接结合 Compaction，也不支持大多数 Context Editing；文档列出的 thinking 配置例外不等于允许任意清理。需要摘要时，应用可以用自己生成的摘要建立新线程。[^threads]

thinking 内容块也有模型与协议相关的保留规则。它们是否计入后续上下文、编辑历史是否影响其有效性，不能用“只取可见文字就够了”代替检查。[^window]

</details>

## 第五部分 · 模型写完，离用户拿到结果还有多远

### 9. 流式输出：提早看到，不等于提早做完

✦ **一句话：Streaming 改变输出的交付时机；它不代替工具执行，也不定义整个任务的完成。**

模型逐步生成比较结论，应用可以攒齐再发，也可以边生成边发送。后一种是流式输出。网关、SDK、应用或界面只要有一层整包等待，就可能把它重新变成“一次性显示”。

因此，完整链路上同时存在三条进度：

1. **模型进度**：文字或工具参数生成到了哪里。
2. **执行进度**：工具是否真正运行，任务还缺哪些步骤。
3. **显示进度**：哪些内容已经被客户端解析并展示。

它们不是同一根进度条。模型交出工具调用请求时，本轮生成可能结束，但工具才刚开始；最后一次模型响应结束，也还需要应用检查结果和产物是否完整。

前篇的本地实验很直观：服务器每隔 0.1 秒产生一个字，两种模式各跑 5 次。边生成边发时，首个有效文字事件中位数为 **109.519ms**；攒齐再发则为 **433.304ms**。但全部结束分别为 **431.061ms** 和 **433.373ms**，几乎没变。它测的是本地人为延迟下的交付时机，不是模型或云网关性能；本文引用原有结果，不重跑。[^stream-lab]

#### token、事件、网络块：三个不同单位

Claude 的流式接口通过 SSE（服务端发送事件）交付内容。典型事件顺序是：

```text
message_start
  → content_block_start
  → content_block_delta ...
  → content_block_stop
  → message_delta
  → message_stop
```

一个 token 不保证是一条事件；一条事件可能分几个网络块到达，一次读取也可能取得多条事件，甚至一个 UTF-8 汉字的字节都会被拆开。客户端需要持续解码和组装，不能“收到一块，就把它当一个完整 JSON”。[^stream][^stream-prior]

工具参数也能流式生成。`input_json_delta` 中的 **input 是工具将要收到的输入**，但这些片段仍是模型正在输出的内容。要等必要参数完整并验证后才执行，不能见到半截月份就猜着去查。

这和 Threads 正好是两个方向：

> **Threads：向模型提交新增会话；Streaming：把模型新生成的内容逐步传回。**

<details>
<summary>证据：结束事件与 stop_reason 要一起看</summary>

`message_stop` 表示这条模型响应流结束；为什么停止，还要看 `stop_reason`：

| 值 | 解释 |
|---|---|
| `tool_use` | 需要工具结果；不是用户任务结束 |
| `end_turn` | 模型自然结束本轮；仍要检查业务完成条件 |
| `max_tokens` / `model_context_window_exceeded` | 输出受限制而截断，不能冒充完整答案 |
| `pause_turn` | 服务端工具循环需要后续请求继续 |
| `refusal` | 模型拒绝回答，不是执行成功 |

表为与本文有关的节选。HTTP 已经返回 200 后，流中仍可能出现错误；正常连接结束也不自动证明业务结果完整。[^stop][^stream]

工具参数增量是 partial JSON 字符串，最终 `tool_use.input` 才是对象；不同内容块需按编号分别组装。[^stream]

</details>

### 10. 断线后能不能接着来，取决于保存了哪一种状态

✦ **一句话：恢复显示、恢复会话、恢复任务和重新执行，不是同一种操作。**

查询进行到一半网络断了，先别直接重试。应当判断丢失的是什么：

| 丢失或中断的部分 | 需要什么来恢复 |
|---|---|
| 显示通道断了，结果已生成 | 已保存的最终结果或可补发事件 |
| Message Thread 无法续接 | 应用保存的会话副本，必要时新建线程 |
| 执行进程崩溃 | 任务记录、已执行工具与结果、可恢复检查点 |
| 上次外部操作结果未知 | 查询执行状态与去重机制，而不是盲目重做 |

SSE 的 `Last-Event-ID` 可以表达“之前收到哪条事件”，但 ID 自己不保存事件。服务端必须确实保留相应内容，才有东西补发。它更不能恢复任意中断处的模型计算。[^stream-prior]

在销量任务中，已查过的 6 月结果可能仍可使用。线程失效时重放这些消息，不等于重新调用销量工具；如果接下来还有“发邮件”这一步，区别就更重要：**邮件可能已经发出，只是确认消息丢了，重试会造成重复发送。**

这需要执行层的幂等或去重保护：稳定的操作标识、可查询的结果、明确的重试策略。它不是模型多想一会儿就能自动补上的能力。

同理，关闭页面首先是停止接收，不一定取消后台工作；真正取消要沿模型请求和工具执行传播，已经发生的外部副作用也不会自动撤销。接收方很慢时，还要限制积压队列，把消费压力传给生产方，这就是**背压**。这些都是应用层要实现和验证的职责，网关支持流式、API 支持线程，都不能替代它们。

至此，三个最容易混用的“完成”应当分清：

> **模型响应完成、工具执行完成、应用确认任务交付，是三种不同的判定。**

前两个提供完成判断的证据，第三个仍需依据任务要求确认。用户只要比较销量，就应核对两份数据和计算；如果还要求保存报告，就必须检查文件确实存在且内容正确；没有获得外发授权，不能把“生成好了”理解为“可以发送”。

## 第六部分 · 一页纸心智模型

```text
你提出任务
    │
    ▼
🎩 管家 / Harness
    │  组织：规则 + 工具说明 + 相关历史 + 新问题
    │  提交：完整请求，或通过 Threads 只提交增量
    ▼
🦜 模型根据本轮逻辑上下文判断
    │  推理引擎按条件复用 KV / Prompt Cache
    │
    ├─ 工具调用请求 ──► 管家检查权限并执行
    │                         │
    │                  结果 / 错误回填
    │                         └────────► 再调用模型
    │
    └─ 最终回答 ──► 流式或整包交付 ──► 应用检查任务完成

长会话：筛选 / Editing / Compaction → 控制本轮输入
跨会话：持久记录 / Memory + 检索 → 恢复相关背景
断线后：先查保存的状态 → 区分补看、续接、恢复和重做
```

管家可以位于本机或服务器；工具可以本地或远程执行，部分工具也由模型供应商平台执行；网关位于其中某段网络路径。图中划分的是职责，不是固定部署拓扑。

**五句话总纲：**

1. **模型输出判断与调用意图，Harness 组织执行与反馈。**
2. **连续对话靠上下文延续，不要求每轮重新上传全部历史。**
3. **Threads 少传输，缓存少重算，摘要与清理才会减少本轮材料。**
4. **长期记忆在会话之外保存，再按需进入上下文；不等于给模型参数写日记。**
5. **流结束不是任务完成；可靠恢复取决于记录和执行语义。**

### 几个容易踩的直觉陷阱

| 误解 | 校正 |
|---|---|
| 无状态，所以每轮必然从头重算 | 会话连续性与计算缓存属于不同层次 |
| 请求体小了，token 就少了 | Threads 可缩小请求，逻辑上下文仍相同 |
| 缓存命中，就是把旧答案直接返回 | 复用前缀状态，新答案仍需生成 |
| 服务端清理不会破坏缓存 | 当前工具结果清理也会使相关缓存失效 |
| 有线程或事件 ID，就有可靠恢复 | 必须有对应状态，且知道恢复的是哪一层 |
| 保存了记忆，下次就一定正确 | 旧事实、错误摘要和过期要求都需要更新与核查 |

## 思考与追问

### 我真正理解了什么？

Agent 的连续性不是一种单一的“记忆”：**模型使用上下文，Harness 维护会话，服务端可暂存线程，推理引擎复用计算，应用保存长期记录与执行状态。** 把这些层次分开，就能解释为什么请求可以更小而 token 不少，为什么流结束而任务未完。

### 我还没搞懂什么？

在具体系统中，线程续接失败后是否真有完整历史可用？摘要是否保住了门店范围和比较基数？外部动作已经发生、结果尚未记账时崩溃，怎样避免重复执行？这些需要沿真实实现验证，不能只检查接口名称。

### 下一步读什么或做什么？

用同一组合成销量问题，分别记录**请求字节、输入分类、缓存命中、首条有效内容时间、任务完成状态**。再分别制造线程失效、响应断流和工具超时，观察变化发生在哪一层。本文现有实验只覆盖 JSON 体积与逻辑消息重建；真实模型与恢复实验须另行确定预算和执行边界。
