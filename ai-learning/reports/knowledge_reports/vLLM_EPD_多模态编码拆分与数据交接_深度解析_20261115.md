# vLLM EPD：拆开多模态编码、预填充与解码，真正难的是交接

图片、视频和音频不能直接当成普通文字交给语言模型生成器。它们先经过预处理与编码，变成模型能使用的表示；语言模型再处理提示词、建立生成状态，最后逐个输出 Token。

vLLM 的 EPD 将这三个阶段分开部署。它的价值不是让一道算术题凭空少算几步，而是让不同类型的计算各自调度、扩容和复用。代价则是：**原来在一个进程内隐含成立的数据关系，现在必须由跨实例协议明确保证。**[1]

## 1. E、P、D 分别在忙什么

| 阶段 | 接收什么 | 产出什么 | 典型负载变化 |
| --- | --- | --- | --- |
| Encoder，E | 原始媒体 | 多模态 Embedding 与布局元数据 | 图片数、分辨率、视频帧数、音频长度 |
| Prefill，P | 文本提示与多模态表示 | 后续生成所需状态，包括 KV Cache | 输入长度与请求批次 |
| Decode，D | 已建立的状态 | 逐步生成的输出 Token | 输出长度、并发与交互延迟要求 |

原文支持两种主要形态：**E+PD** 单独拆出编码器，预填充和解码仍放在一起；**E/P/D** 则将三者全部拆开。E 向消费端传 Embedding，P 向 D 传生成状态，两种交接不是同一件事。[1]

图片密集、短回答的任务，可能需要更多 E，而不是更多 D。长篇文本生成则可能相反。拆分使部署者不必为了增加某一阶段的容量，就整套复制其他阶段。

不过，拆分还引入传输、路由、缓冲区管理与新的排队位置。低负载时，这些成本可能超过独立调度的收益。

## 2. 为什么已经传了 Embedding，还会重复处理图片

容易出现的误解是：“编码器已经算完，只要把张量送过去就行。”实际上，消费端还需要知道这些张量怎样放进提示词：占多少占位 Token、对应哪些图片或视频片段、使用什么网格与时间信息。[1]

一种直观实现会同时做两件事：让 E 计算并传输 Embedding，再把原始媒体请求转发给 P。这样 P 虽然不一定再次运行编码器，却可能为了重建输入布局，再次下载、解码、缩放或切分媒体。

因此，原文的 **metadata-only** 优化并不是“消除第二次编码器前向”这么简单，而是消除消费端重复的媒体准备工作。

其交接分成两个通道：

- 请求里保留文本提示、生成参数以及模型需要的媒体布局元数据。
- 真正的 Embedding 仍通过 EC connector 传输。

metadata-only 并不意味着“不传多模态数据”，而是不用原始媒体重新推导已经知道的结构。

不同模态需要的结构也不同：图片可能需要网格信息；视频还涉及时间戳；音频需要 Token 数量和特征长度。小型结构字段可以表示为普通数值 JSON 数组，避免为了传几个数值还序列化整个框架张量。[1]

## 3. 交接协议必须保护张量形状与生命周期

### 形状不能从一个通用隐藏维度猜出来

传输缓冲区有时需要在编码完成之前分配。但不同模态、不同模型的编码输出宽度未必等于语言模型某个统一 hidden size。

原文描述的改进是在初始化时按模态测量输出宽度，并在协议里携带真实形状；NIXL EC 的协议版本也相应更新，生产者和消费者需要一起升级。[1]

这不是纯性能细节。错误的尺寸假设会影响分配、解释与读取张量的方式，因而直接关系到正确性。

### 编码完成不再依赖“生成了一个 Token”

独立 E 不运行语言模型、不维护语言模型的 KV Cache，也不采样输出 Token。原本围绕 Token 生成组织的生命周期，不能不加区分地复用到编码器实例上。

原文的独立 `MMEncoderModelRunner` 管理编码任务的 GPU 完成状态，避免计算仍在进行时就重用缓冲区。相关实现还处理编码器单独运行、检查点分片加载和可选的编码器 CUDA Graph 捕获。[1]

这些改动说明，拆一个阶段并非仅仅给原服务增加一个开关；调度器需要知道这个阶段什么时候真正完成。

## 4. metadata-only 改变了失败恢复的条件

若 P 手里仍有原始媒体，远程 Embedding 传输失败后，某些配置可能回退到本地编码。但 metadata-only 消费端没有那份输入，不能假装具备相同恢复能力。

原文因此强调：当远程结果无法到达、也无法在本地恢复时，应将受影响的请求报告为不可用，而不是走可能终止整个 EngineCore 的不安全回退路径。[1]

可推广的原则是：**优化改变了持有的数据，也就改变了允许采取的恢复策略。**

一个教学场景是：路由器已经将文档媒体替换为元数据引用，E 随后失联。消费端知道有多少占位符，并不代表它能重建文档内容。此时清楚失败，比给出缺失输入上的回答更正确。

原文也修复了传输初始化失败后的共享内存释放问题。资源泄漏不一定让第一条请求失败，却可能在长期服务中积累，说明故障隔离还包括清理路径。

## 5. 跨编码器缓存：省掉重复计算，但仍要交付结果

本地缓存无法覆盖重分配：某张图片在 E0 编码过，下一次却被路由到 E1。E1 本地没有结果，就可能再次计算。

原文通过 Mooncake Store 支持跨编码器复用：本地未命中时查询共享 Store；命中则取得 Embedding，未命中才正常编码并异步发布。发往选定 P 的交付仍使用点对点路径。[1]

这区分了两种成本：**是否重新计算**与**是否还要传输**。共享缓存消除了前者时，后者未必消失。

复用还需要验证输入身份、模型身份与输出张量契约。由此可以推导，生产系统不能只把媒体 URL 当成永远正确的缓存标识：同一地址的内容可能变化，模型或预处理方式也可能变化。采用内容摘要或版本化处理配置是可研究的办法，但本文没有将这些建议写成 vLLM 已实现的具体键格式。

原文当时的初始支持范围包括图片、Model Runner V2、编码器 TP=1，且不支持动态 LoRA；异步发布意味着同时到来的冷请求仍可能重复计算。[1] 所以，“有共享缓存”不等于“全局恰好计算一次”。

## 6. 三组实验回答的是三个不同问题

### 音频 metadata-only：输入路径优化，不是整体拆分对比

在原文给定的 Qwen3-Omni、1E+1PD、并发 64 等设置下，吞吐从 62.21 增至 73.13 请求/秒，平均延迟从 980 降至 853 毫秒。准确率从 75.90% 变成 75.65%，作者明确说差异仍需调查。[1]

这比较的是 **EPD 内部两种音频输入路径**，不能用来证明“EPD 比同机部署快多少”。也不能因为差异只有 0.25 个百分点，就自行宣布准确率完全不变。

### 共享缓存：一次刻意制造重分配的实验

作者在填充缓存后重新分配全部图片，使每个编码器发生本地未命中。在 128 个请求、512 张图片的单次实验中，共享复用把重复图片编码从 512 次降到零，TTFT 的 p50 从 1.209 降到 0.819 秒，TPOT 基本不变。[1]

TTFT 是首 Token 等待时间，TPOT 是后续输出 Token 的时间成本。主要变化发生在生成开始之前，符合省去重复编码的机制。但这是共享复用的有利情景，不代表生产流量一定拥有同样命中率。

### DeepSeek 文档问答：必须把新增的编码器 GPU 计入分母

原文以 512 个 MP-DocVQA 问题比较 8 张 GPU 的 PD 与 12 张 GPU 的 EPD，后者额外增加了四个编码器实例。吞吐口径是**输入加输出 Token，除以时间和全部部署 GPU 数**。[1]

在并发 64—128 时，作者报告 EPD 的每 GPU 吞吐高 6.6%—9.5%，p90 TTFT 低 44%—47%；并发 16 时每 GPU 吞吐更低，并发 32 时接近持平。[1]

这些请求平均约 4,905 个输入 Token、5.2 个输出 Token，明显偏向长输入、短答案。因此结果不能直接外推到长篇文本生成，也不等于纯输出 Token 吞吐提高同样比例。

## 7. 部署判断：先找瓶颈，再拆服务

原文建议先用 E+PD 验证编码器交接，再考虑进一步拆开 D。[1] 这一顺序能减少同时引入的变量。

在选择资源比例前，更有意义的问题是：

- 请求的媒体、输入和输出长度分别怎样分布？
- 时间主要耗在媒体准备、编码、传输、P 排队，还是 D？
- 缓存命中后，路由和序列化是否变成瓶颈？
- P 已有可复用 KV 时，能否避免先做一遍无用的 E？
- 任一阶段故障，能否只失败受影响请求并正确释放资源？

最后一点缓存协调仍是原文列出的后续设计方向：E-first 流程可能在 P 查到可复用状态之前就开始编码；增加一次需求协调能省计算，也会增加冷请求的等待。[1]
