# XYBench：AI 为什么知道更好的答案，却仍然围着错误的问题回答

用户问“怎样买到吸力更强的吸尘器”，可能真正想解决的是“现有吸尘器吸不动灰尘”。如果原因是软管堵塞，推荐更贵的机器并没有抓住问题。即使回答最后顺带说一句“也可以看看软管”，也不能说明它已经把用户带回正确的诊断方向。

Ai2 与合作研究者发布的 XYBench，专门测量这种偏差：用户想达成目标 X，却相信方法 Y 是必要路径，于是只询问 Y。助手需要从上下文识别目标，并决定怎样回应错误前提。[1] 它测量的不只是知识正确性，还包括**把哪一件事放在回答中心**。

## 1. 三种能力不能用一个“答对了”代替

XYBench 将回答拆成三项指标。[1]

| 指标 | 实际在问什么 | 不能据此推出什么 |
| --- | --- | --- |
| Pragmatic solution | 回答是否分别包含面向 Y、面向 X 的解法 | 提到 X 的解法，不代表它是回答重点 |
| Pragmatic emphasis | 回答主要强调 Y、X，还是两者相当 | 强调 X，不代表已解释 Y 为什么不适合 |
| Misconception identification | 是否识别偏差，并引导用户远离错误方法、转向目标 | 不能简单化为检测某个“你错了”的句式 |

用自拟的吸尘器示例比较：

- **回答 A**：主要比较电机功率和新机型号。它回答了 Y，却可能没有解决 X。
- **回答 B**：先建议检查堵塞、密封与滤网，再说明在排除故障后如何考虑换机。它把恢复吸力作为重点，并把购机放在有条件的后续位置。
- **回答 C**：前三段推荐新机，最后提醒“也可能是堵塞”。它包含 X 的线索，但主要仍在优化 Y。

这个区分对长回答尤其重要。回答越长，越容易“什么都提到一点”。如果评测只检查关键词或解法是否出现，C 很可能被算作成功，而读者仍会把大量时间花在错误方向上。

## 2. 数据怎样定义“真正的目标”

作者报告的数据集含 8,115 个问题，由四部分构成：[1]

| 来源 | 数量 | 构造方式 |
| --- | ---: | --- |
| Stack Overflow | 1,557 | 从公开问答与高分、获采纳答案识别目标和解法 |
| Stack Exchange | 184 | 同类公开问答整理 |
| 人工整理例子 | 102 | 人工选择、构造的案例 |
| WikiHow | 6,272 | 依据流程指南生成包含合理误解的问题，再筛选与修订 |

本次重算确认四项之和为 8,115；WikiHow 生成部分约占 **77.29%**。因此，不能把数据集笼统理解成“8,115 条未经加工的真实用户提问”。它结合了公开问答与基于现实流程生成的合成问题。

对于论坛问题，研究者使用最高分的三个回答和可用的获采纳回答，推定潜在目标与可能解法。对于 WikiHow，使用 Sonnet 4.5 生成问题，再补足让专家能够推断目标、但不直接明说目标的上下文。能够通过直接回答字面请求充分解决的问题，被筛掉了。[1]

这两项设计影响了结论的适用范围：

1. **“目标 X”是研究者依据材料建立的参考判断**，不是直接读取了用户内心。
2. **测试集刻意富集 XY 问题**。它能衡量模型处理这种问题的能力，不能告诉我们日常用户请求里有多少比例属于 XY 问题。

如果用它训练“凡事都纠正用户”的助手，就把一个条件能力误当成了默认行为。

## 3. 提到正确解法，与真正转向目标，差距在哪里

主实验是单轮设置，每个问题生成一个回答。被测配置包括 Sonnet 4.6、GPT-5、Gemini 3.1 Pro、Qwen3.5-9B 与 DeepSeek-V4 Pro；人类参考回答单独使用相同指标评估。[1]

作者在 Stack Overflow 子集报告：

- 面向字面请求 Y 的解法，出现在 75%—86% 的模型回答里。
- 面向潜在目标 X 的解法，出现在 59%—71% 的回答里。
- 真正把 X 作为主要重点的回答，只有 35%—41%；47%—57% 仍主要围绕 Y。[1]

这些是不同模型在特定子集上的范围，不能混合成某一个模型的三项分数，也不是本文独立复现实验所得。

它们最直接支持的解释是：**是否知道一个解法，与是否让它主导回答，不是同一件事。** 模型可能同时识别出目标和用户提出的方法，却仍然把顺着用户的字面请求当作更稳妥的回答策略。

这与“缺乏知识”不同。增加更多背景信息，未必足以改变回答的组织和取舍。

## 4. 两个补充实验，把“知道”和“做到”拆开

### 明说目标，仍不保证有效纠偏

作者进行 oracle 实验，将 X 与 Y 都明确提供给模型。在 Stack Overflow 上，Sonnet 4.6 包含 X 解法的比例从 59% 上升到 67%，但误解识别指标从 47% 降至 34%。其他模型也没有一致弥合与人类参考答案的差距。[1]

这一结果不能简单表述成“提供目标让模型变差”。不同指标发生了不同变化，而且博客没有给出足以让本文重新检验显著性的完整逐项数据。它更有价值的启示是：**目标识别之后，还存在响应策略问题**——模型是否解释原方法的局限，是否安排正确的优先级。

### 会选好答案，不等于会写好答案

另一个实验给模型两个候选回答：一个围绕字面请求，一个解释误解并解决潜在目标。在 Stack Overflow 上，六个被测模型选择目标导向答案的比例为 71%—84%；相比之下，主实验中五个模型自由生成的回答，只有 35%—41% 主要关注目标。[1]

选择与生成的任务、参与模型数量并不完全相同，因此不能把两个范围直接相减，当作精确的“能力损失”。但实验说明了多选题可能遗漏的差距：候选答案已经替模型完成了诊断和组织，模型只需识别较好的一份；自由生成则要自己完成整个过程。

这也是为什么评估实际助手时，不能只看它能否在比较题中认出好回答。

## 5. 裁判最难判断的，恰好是回答的重点

XYBench 使用 Sonnet 4.5 作为自动裁判，识别回答中的建议，并判断总体重心。两名人工评审独立标注了 500 个模型回答，用于核验机器判断。[1]

博客报告的人机一致率范围为：

- 解法是否出现：97.5%—100%。
- 是否识别误解：84.6%—93.3%。
- 回答重点：74.2%—79.8%。

越接近“文章把什么放在中心”的判断，一致率越低。它提醒我们：重心是重要构念，却比“某个建议有没有出现”更难稳定测量。

这些一致率是作者报告的汇总，不能直接当成经随机一致校正后的统计量。若进一步用 XYBench 判断几百分点的训练改进，应查看论文中的标注细节、置信区间、裁判稳定性和逐来源结果。本文未将博客中的一致率补写成未读论文才可能提供的结论。

可以与[安全评测中的裁判校准](./AI安全评测_构念效度与裁判校准_深度解析_20261115.md)对照：一个概念值得评估，并不意味着自动裁判已经能无误测量它。

## 6. 怎样迁移到真实助手，又不替用户擅自改目标

从本文材料可以推导出一个有条件的处理顺序：

1. 识别用户明确要求的 Y，并尝试用已有上下文表述目标 X。
2. 检查是否有具体证据表明 Y 不适合 X，而不只凭“我觉得还有更好的办法”。
3. 若证据充分，先解释关键原因，再给出面向 X 的可执行下一步。
4. 若只存在多个合理解释，提出会改变下一步行动的澄清问题。
5. 若用户已明确约束，且 Y 在该约束下合理，就完成 Y，不反复重开讨论。

例如，用户已经说明“软管和滤网都检查过，租赁合同要求更换指定型号”，继续教育用户先修机器，就不是纠偏，而是忽略已给出的信息。

同样，目标导向不意味着越权执行。助手可以建议更合适的方法，但删除数据、对外发布或改变系统权限等动作，仍需要相应授权。识别了用户最终想要什么，不会自动获得实施所有手段的权限。

## 7. 本次学习的结论与边界

XYBench 让一个常被“答案包含正确内容”掩盖的问题变得可测：**回答的选择与组织，也决定了它是否真的有用。** 对助手进行改进时，应分别观察解法覆盖、回答重心和纠偏行为，而不是期待其中一项提高就带动其他两项。

同时，现有基准主要覆盖英文、流程性问题和单轮响应；论坛参考答案、合成样本以及自动裁判都会影响结果。它不是跨语言、长期交互与所有专业任务的统一结论。
