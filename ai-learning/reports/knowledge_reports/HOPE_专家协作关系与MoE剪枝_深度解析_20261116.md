# HOPE 专家剪枝：为什么不能只给每个专家排一个名次

MoE 模型每次只调用一部分专家，却通常要为整个专家池准备权重存储。删掉部分专家，是直接减少这项容量需求的办法。困难在于：单独看起来不重要的几个专家，能不能一起删？

HOPE 的做法，是在校准时记录专家成对出现时的贡献，随后联合选择删除集合。它比只看频率或单个输出强度多保留了一层信息。[1][2] 但“高阶”“误差上界”“无需训练”都需要说明范围：HOPE 实际使用到二阶关系，优化的是代理目标，校准和求解仍有成本。

本报告对照博客、论文 v3 与固定源码，重点解释这些关系。博客中省略的上界系数、理论矩阵与实际矩阵的归一化差别，会影响怎样理解方法，因此单独展开。

## 减少专家数量，首先减少的是权重容量

设一层有 `E` 个可路由专家，每个输入位置选择其中 `K` 个。`E` 决定专家池有多大，`K` 决定这次实际调用多少个。删除一半专家，不必同时把 `K` 减半。

例如，论文实验中的 Qwen3.5-122B-A10B 每层有 256 个专家，选择 8 个；剪掉一半以后，仍可从留下的 128 个中选择 8 个。主要变化是存储更小和路由选择不同，不能据此推导每个 token 的专家计算量减半，或模型必然快两倍。[2]

也不要把“专家删一半”写成“总参数删一半”。用论文给出的约 122B 总参数、116B 专家参数作粗算：

```text
剩余参数 ≈ 122B − 116B × 50% = 64B
若每个权重占 2 字节，理论权重容量约为 128 GB（十进制）
```

这是基于舍入参数量的教学估算，不是本机显存实测；共享专家、注意力、其他模块、KV Cache、激活和运行时工作区要分别计算。论文实验不删除共享专家，固定代码也保留每层至少 `K` 个可选专家。

常规权重常驻的服务方式，可能把省下的空间用于上下文或并发。CPU 卸载和按需加载也是可选部署方式，只是引入另一组传输与等待成本。因此，这里的问题是减少常驻专家权重的代价，而不是宣称 MoE 在任何实现中都必须把全部权重放在单张 GPU 上。

## 从一个专家的分数，走向一组专家的代价

在论文采用的归一化 top-`K` 路由设定中，一层对输入 `x` 的输出是：

```text
h(x) = ∑_{k∈T(x)} g_k(x) f_k(x)
```

`T(x)` 是选中的专家集合，`g_k(x)` 是归一化后的路由权重，`f_k(x)` 是专家输出向量。HOPE 用到的是路由权重与输出范数的乘积，而不是直接把“调用过一次”当成同样重要的一次贡献。

令未选中专家的贡献为零，定义：

```text
a_k(x) = 1[k∈T(x)] × g_k(x) × ‖f_k(x)‖₂
```

这里 `1[条件]` 是指示函数，`‖·‖₂` 表示向量长度。再令二元变量 `p_k=1` 表示删除专家 `k`，`p_k=0` 表示保留。代理目标为：

```text
Z(x,p) = (∑_k p_k a_k(x))²
```

展开平方，就有单项和成对项：

```text
Z = ∑_k p_k a_k² + 2 ∑_{i<j} p_i p_j a_i a_j
```

单个专家的分数只能反映前一部分；后一部分表示两个专家同时被删时增加的联合代价。注意，它只在两者都被删时出现，不能解释成对每一条“被删专家—保留专家”关系直接收取惩罚。

用一个自拟矩阵说明。假设必须从 A、B、C 中删除两个专家，得到的评分矩阵为：

```text
F = [[1,   0.9, 0],
     [0.9, 1,   0],
     [0,   0,   1.2]]
```

| 删除集合 | 只加单个分数 | 使用完整的 `pᵀFp` |
|---|---:|---:|
| A、B | 2.0 | 3.8 |
| A、C | 2.2 | 2.2 |
| B、C | 2.2 | 2.2 |

独立排序会删除 A、B；考虑成对项后，另外两组更便宜。这是联合决策的作用。它并没有证明所有语义上的“合作伙伴”都会一起保留。论文对保留专家的协作分数分析，是实验观察；目标函数本身仍是一个可计算的代理。

## `Z` 不是可以直接套用的完整误差上界

删除原本会被选中的专家后，路由会选入替补，留下的专家权重也可能重新归一化。因此，层输出的变化包括替换专家带来的变化，以及保留专家权重变化带来的变化。[2，§3.2、附录 A]

论文主要处理前者，记为 `Δ_sub`。Theorem 1 给出的关系是：

```text
‖Δ_sub‖₂² ≤ (1 + ρ)² Z
ρ = max_k ‖f_k(x)‖₂ / min_k ‖f_k(x)‖₂
```

`ρ` 衡量该输入下专家输出范数的最大值与最小值之比，使用此式需要分母非零、比值有定义。这个系数用于覆盖未知替补专家的贡献。博客将公式压缩成了 `Z ≥ true error`，读报告时应恢复论文中的系数和误差项范围。[1][2]

一个自拟反例足以说明为何系数不能省。设 top-1 原本选中的专家输出为 1，删除后替补专家输出为 −3，两次路由权重都是 1。此时：

```text
Z = 1
替换后的平方误差 = (1 − (−3))² = 16
ρ = 3，因此 (1 + ρ)² Z = 16
```

带系数的界成立，直接说 `Z` 大于真实误差则不成立。这个例子已用精确有理数复算，不涉及真实模型运行。

另外，论文将重新归一化的影响视为通常较小，附录说明这依赖替补与被删专家的路由质量接近等条件。它不是任意剪枝率下都可忽略的恒等式。降低一个上界或代理目标，也不保证每个输入的真实误差同步下降，更不保证整模型的最终答案保持不变。

## 理论矩阵与实际矩阵，差在分母

如果校准集总共有 `N` 个 token，严格展开其平均代理目标，可得到：

```text
F_all[i,j] = (1/N) ∑_x a_i(x)a_j(x)
(1/N) ∑_x Z(x,p) = pᵀ F_all p
```

这是真正与全量校准 token 平均 `Z` 相等的形式。实际 HOPE 则按该专家对共同被选中的次数 `n_ij` 归一化：

```text
F_cond[i,j] = (1/n_ij) ∑_{x: i,j∈T(x)} a_i(x)a_j(x)
```

未共同出现的专家对取零。作者在论文 §3.4 和附录 A.7 明确说明，这是为了避免罕见、但共同出现时贡献很强的专家对被低估。固定源码的 `build_f_matrix` 也确实将累计范数乘积除以共同激活次数。[2][3]

两种定义并非只差一个统一倍数，因为每对专家的 `n_ij` 不同。例如，一对专家只在 1% 的 token 上共同出现，其条件平均就会是全量平均的 100 倍。这是一种有意改变权重的经验选择，不能继续不加说明地称为原始全量期望的精确等价形式。

它还影响优化问题的性质。全量平均矩阵是外积的平均，因此半正定；逐元素改用不同分母后，则不保证半正定。一个已复算的自拟例子：在 199 个 token 中，两专家共同以贡献 10 出现一次，其余分别以贡献 1 单独出现 99 次。只观察这两个专家，条件矩阵为：

```text
F_cond = [[1.99, 100],
          [100, 1.99]]
```

其特征值为 101.99 和 −98.01。负特征值说明，即便所有元素非负，这个矩阵也未必对应凸目标。这并不否定经验选择，而是解释了为什么求解结果需要按实际优化方法理解。

## 求解器找到的是哪一种解

给定每层删除数量 `B`，目标是：

```text
最小化 pᵀFp
约束：每个 p_k 取 0 或 1，且 ∑_k p_k = B
```

固定版本的实现先允许 `p_k` 在 0 到 1 之间连续取值，用 SciPy SLSQP 优化，再把数值最高的 `B` 个位置设为 1。[3] 这些位置是要删除的专家，别把 1 当成“保留”。

代码使用均匀初值、最多 1,000 次迭代和 (10^{-12}) 的容差。连续松弛、局部求解和最后取整，不是二元全局最优的通用证明。论文报告的松弛与取整结果接近，是这些实验里的现象。

实现中还有一处具体检查需要补在使用环节：`solve_qp` 直接读取 `result.x`，没有先检查优化器的 `success` 状态。准备使用生成的删除集合时，应查看求解是否收敛、约束是否满足，并确认删除数量和模型结构一致。本文只阅读了这段代码，没有执行上游求解器或修改上游实现。

HOPE 与 REAP 的关系也应这样理解：对角项是贡献平方的平均，REAP 使用的是贡献的平均；二者的平方关系相差方差项。论文观察到排序和删除集合很接近，不意味着对任意校准数据都严格相同。

## 实验支持了什么

论文比较三个模型、两类校准材料及多个剪枝率。Tulu3 任务组测试六个剪枝率，SWE-Bench Pro 只测试 10%、25%、50%；合起来是 54 个模型、校准集、剪枝率与评测组的组合。54 不是独立数据集数量。[2]

校准材料分别是 Evol-CodeAlpaca 和原模型在 SWE-bench Verified 上的执行轨迹；SWE-Bench Pro 是另一套评测。论文中的 Pro 评测使用 731 个实例、Harbor 和 OpenHands SDK，单次尝试，固定输入与输出预算。结果反映模型与这套 Agent 执行条件的组合，不是脱离工具和预算的抽象“编码能力分”。

最醒目的案例是 Qwen3.5-35B-A3B 删除 50% 专家后，在相应实验条件中的 Pro 得分：[1][2]

| 模型状态 | 得分，按百分制表示 |
|---|---:|
| 未剪枝 | 约 41.8 |
| HOPE | 约 42.3 |
| REAP | 约 36.2 |

42.3 与 36.2 相差 **6.1 个百分点**，相对增幅约 16.9%；不能混写成同一种百分比。HOPE 与未剪枝模型在这个点上接近，也不足以证明剪枝普遍增强模型。论文对部分结果给出不同校准试验的波动，仍需要避免把小幅均值差当成确定提升。

整体上，作者报告 HOPE 在较高剪枝率下更有优势，低剪枝率时其他方法仍有竞争力。平均名次能总结比较，却隐藏了单个任务的损失；实际部署应优先检查自己不能接受下降的任务。

校准也不是换一批数据都一样。论文中，不同校准集合产生的 HOPE 删除集合平均 Jaccard 相似度约为 0.60；同一配置重复试验则稳定得多。这意味着校准的任务分布仍会影响最终结构。

跨层版本 CHOPE 也没有证明“考虑更多关系必然更好”。附录的初步实验出现了性能明显下降，作者将部分问题归于早期层过度剪枝，并将进一步约束留作后续工作。当前主方法仍是逐层选择，实际只建模专家对，未完整处理跨层与三元以上关系。

## 校准、导出与部署还有哪些实际成本

官方工具分为 `calibrate → solve → prune` 三步，分别得到观测统计、删除集合、较小的模型文件。README 对支持范围有明确要求：堆叠的三维专家权重布局，并说明测试使用了 `transformers==5.2.0`。[3]

读代码可以补上仅看流程名容易漏掉的内容：

- 校准钩子会重算被激活专家的输出，并构造 token、top-`K`、隐藏维度组成的临时张量；因此只遍历一次校准材料，不代表没有额外执行和内存。
- 公共 `calibrate` 对传入的 token 序列做前向计算，不自动生成完整多轮 Agent 轨迹。想覆盖工具调用与长任务，要先准备相应材料。
- `prune` 物理切除专家权重和相应路由行，更新配置，并拒绝留下少于 top-`K` 数量的专家；此版本也拒绝逐层数量不一致的删除集合。
- 导出时部分辅助文件使用指向原模型目录的符号链接。迁移到另一台机器前，要确认模型目录完整可移植，不能只复制权重文件就假定所有依赖都在。

256 个专家的一个 float64 矩阵只有 0.5 MiB，但这只是矩阵本身，还要计共同激活次数、其他统计、临时输出和原模型。论文报告的额外校准时间约 6—7%，属于其测量条件，不能直接当成这份公共实现对所有长序列的固定开销。

部署验证也应分别看权重容量、峰值显存、输出质量与真实请求时延。省出的显存可能允许更大并发，也可能被更长输入占用；相同 top-`K` 下，专家池缩小不自动产生同等幅度的计算加速。

HOPE 最有用的想法，是在做结构压缩时保留联合选择的信息。它提供了比独立排名更丰富的依据，但仍需要合适的校准材料、可靠求解、正确导出，以及任务级验收。把这些条件留在一起，才能判断一次压缩究竟换来了什么。
