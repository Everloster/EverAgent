# NVIDIA Microduck Agentic Robotics：Agent 做准备，RL 学会走路，Sim-to-Real 才是难点

## 一句话结论

Microduck 的“学会走路”不是 Hermes、Nemotron 或 Astra 通过大语言模型直接训练出来的：Agentic AI 负责把需求转成计划、概念图、资产清单、USD 模型、仿真场景与可复现实验配置；真正形成步态、越障和过坡能力的策略，仍然由强化学习算法在 Isaac Lab 等机器人学习框架中，利用 Newton 等物理仿真器生成的大量交互经验训练得到。NVIDIA 官方博客展示的是一条“AI 辅助工程编排—物理仿真—大规模强化学习—本地验证—实机迁移”的完整工作流，而不是“Agent 自主教会机器人走路”的实验；其中 Agent 的直接贡献集中在规划、知识整理、资产生产和流程交接，策略权重更新、奖励优化与运动控制闭环则属于 RL 和物理仿真的职责。

两组来源尤其需要严格拆开。NVIDIA 官方博客描述的是 **Isaac Lab 3.0 与 Newton 组合**下的障碍课程实验；Hugging Face/NVIDIA 教程进一步给出了 Isaac Lab 3.0 的训练、播放、导出和实机部署接口；而 `pollen-robotics/microduck_rl` 是另一条基于 **mjlab、MuJoCo Warp 与 PPO** 的开源实现。后者 README 所称“4096 环境约 1～2 小时得到可用步态”，只能描述这套仓库自己的训练路径，不能移植为 NVIDIA 官方障碍实验的训练时间。两者都涉及 4096 环境、61 维观测、14 关节、BAM 和 sim-to-real，但物理后端、任务注册和代码组织并不相同。

此外，NVIDIA 官方图 10 展示的是物理 Microduck 在瓷砖地面上的行走和转向。这能够证明一个 locomotion policy 曾在实机上运行，不能证明该策略已经可靠完成官方障碍课程中的所有箱子、坡道、狭窄通道和复位要求。官方正文也明确保留了这一边界：仿真到现实仍存在传感器、接触和控制时序差异，需要继续校准和迭代。

## x→f→f(x)：必须区分两种不同的函数映射

整个流程实际上包含两条性质完全不同的映射链。把它们混为一谈，就会得出“Agent 通过写提示词直接学会走路”的错误结论。

### 1. Agentic 工程映射：提示词变成可执行资产

第一条链可以写成：

**x_A = 任务提示词 + Microduck 文档与仓库信息 + 参考图片 + 约束条件**

**f_A = Hermes、Nemotron、Astra 及其调用的本地软件、图像工具、CAD 工具和仿真工具**

**f_A(x_A) = 项目计划、概念图、资产清单、裁剪参考、USD 模型、仿真场景、实验配置与验证材料**

在这条链中，x_A 是人类需求和已有资料；f_A 是由多个模型与工具组合而成的“工程代理函数”；f_A(x_A) 是可供仿真、训练和复核的中间产物。Hermes 和 Nemotron 主要处理前端的规划与分析，Astra 主要处理后端的资产准备。Agent 确实“做了什么”，但它做的是工程编排和内容生产，不是通过语言推理直接生成一组能稳定控制机器人关节的实时动作。

### 2. 强化学习映射：观测变成动作

真正部署到机器人上的控制链是：

**x_t = 当前观测，包括头部相机深度、机器人自身状态，以及具体任务可能使用的命令**

**a_t = f_θ(x_t)**

**x_{t+1} = Newton 或其他物理后端对状态、动作、接触和环境的推演结果**

其中 f_θ 是一张训练后固化的神经网络策略。它接收观测，输出关节位置目标或其他低层控制量；物理引擎把动作转化为机器人身体的运动、碰撞、支撑、失衡和跌倒，再产生下一时刻的观测。训练时，强化学习算法利用这些转移中的奖励更新 θ，部署后则冻结 θ，在线只做前向推理。

因此，“会过坡和障碍”的 f_θ 是强化学习训练出来的控制器，而不是 Hermes 或 Astra 写出的计划。Agent 可以帮助建立环境、选择资产、配置接口、生成训练命令和整理结果，但如果没有明确证据，就不能声称 Agent 设计并优化了奖励函数、执行了策略梯度更新，或者直接把某个提示词映射成了可部署的步态。

还要避免混用不同实验的接口。Hugging Face/NVIDIA 的 Microduck 速度任务明确给出 **61 维观测、14 个关节位置输出**；开源仓库也采用 61 维 actor observation，但其组成是 48 维本体感知加命令，包含三维 twist、四维头部姿态和六维身体姿态。NVIDIA 官方障碍课程只明确说使用“头部相机深度和机器人状态观测”，并没有公布该次障碍策略的完整观测向量、动作缩放或归一化参数。因此，不能把速度任务的 61/14 接口直接当成官方障碍策略的接口事实。

## 一、六阶段工作流：资产、仿真、学习、验证与部署如何衔接

### 阶段一：把一句任务描述变成可执行计划

工作流从 RTX Spark 上的任务提示词开始。提示词需要定义目标、可用资源、预期输出和执行阶段，并要求 Hermes 与 Nemotron 3.5 Bolt 生成逐步计划。官方示例中的计划又细分为六项：研究与规划、概念生成、资产识别、交接准备、资产创建与核验、场景组装与测试。

本地规划首先审查 Microduck 的官方文档与代码仓库，提取机器人能力、资源和未知项。这里的“研究”并不是泛泛生成背景文章，而是为后续任务建立约束清单，例如：

- Microduck 能观测什么、控制哪些关节；
- 当前仿真和实机接口有哪些限制；
- 障碍物尺寸、坡度、间隙与路线如何定义；
- 哪些结论来自官方文档，哪些仍需验证；
- 后续要生成哪些文件，以及每个文件的验收标准。

课程设计同时覆盖运动与感知。它不仅要测试机器人能否迈步、保持平衡和通过受限空间，还要让机器人获得前方障碍信息。概念图由本地图像生成模型产生，Hermes 和 Nemotron 随后分析图中可见资产，为每个对象分配标识、描述特征并生成裁剪图。资产清单还要记录遮挡、截断和无法从图片确定的尺寸，防止后续把视觉猜测伪装成测量事实。

### 阶段二：Astra 把二维概念变成三维资产

概念图中的对象通常只占很小区域，直接裁剪后可能分辨率过低。Astra 先用云端图像编辑隔离对象并生成更清晰的参考图，再与原始裁剪图逐项比较，检查轮廓、比例、颜色和特征是否保持一致。对于图片无法确定的尺寸、隐藏表面和结构细节，官方流程要求将其明确记录为建模假设，而不是无依据补全。

资产生产随后分成两种工具职责：

- FreeCAD 负责基础几何、可编辑 CAD 结构和尺寸关系；
- Blender 负责细节几何、材质以及最终外观；
- Astra 通过程序化执行协调这两个本地应用；
- 结果保存为可编辑模型并导出 USD，同时生成预览和检查结果供复核。

官方计划还设置了一条务实验收线：每个资产要么完成，要么有可证明的阻塞原因，同时至少要有一个可用模型，避免工作流因单个资产失败而完全停摆。需要复用的通用对象也可以从 SimReady Central Library 取得。NVIDIA 称该库提供两千多个无需额外准入的 simulation-ready OpenUSD 资产，但这一数量仍属于厂商说明，而不是本文独立审计的结果。

### 阶段三：在 Isaac Sim 中组装可交互的学习环境

Astra 使用准备好的资产在 Isaac Sim 中组装坡道、平台、箱子、器材箱、木制障碍、工作灯和地面垫等场景。机器人本身也不是一个静态模型：其铰接结构由 links、joints 和 actuators 描述。连接体定义刚体之间的关系，关节限制相对运动，执行器把策略输出转化为关节驱动力，三者共同建立策略动作与机器人运动之间的接口。

Isaac Sim 在这里负责场景编辑、机器人与资产装配、传感器配置以及可视化验证；Omniverse 库提供渲染和传感器仿真能力；Newton 则计算机器人与地面、坡面和障碍物之间的动力学后果。机器人执行动作后，仿真需要回答：身体是否保持直立、脚是否获得足够支撑、重心是否越界、是否发生碰撞、是否跌倒、前进距离是否增加。

官方计划要求测试导航、障碍挑战和 reset，并提供可复现指令与证据。这里的“测试”应理解为环境级和任务级验收，不应自动理解为策略已经通过统计意义上的成功率评估。

### 阶段四：Isaac Lab 训练感知与运动策略

当机器人模型、资产和环境接口准备好后，Isaac Lab 承担策略训练。任务开发者需要明确三件事：机器人观察什么、可以采取什么动作、使用什么奖励引导行为。仿真器在每次尝试中产生状态转移，RL 算法利用这些经验更新共享策略。

官方障碍实验以 Isaac Lab 的 Microduck 示例环境为起点，使用一个已经预训练过的 locomotion policy，再针对坡道和障碍继续训练。这个区分很重要：示例环境提供了基础运动能力，障碍课程中的进一步训练才让策略适应新的地形和视觉条件。该次适配使用 **4096 个并行环境**，运行于 **NVIDIA RTX PRO 6000 Blackwell Workstation Edition GPU**。

这一阶段的早期结果通常包含不稳定步态、碰撞和跌倒。策略不是因为看到了视频就“理解”坡道，而是因为大量失败和成功样本通过奖励被压缩进参数更新。官方没有公开该障碍实验的完整奖励公式、训练曲线、收敛步数、坡道分布、障碍尺寸、跌倒率或最终完成率，因此只能确认其展示行为，不能给出定量结论。

### 阶段五：在本地 RTX Spark 上验证固定策略

训练结束后，策略回到本地 RTX Spark，在 Isaac Sim 中回放。此时参数不再更新，系统只检查选定的 checkpoint 在场景中的行为：能否感知障碍、是否调整动作、是否跌倒、是否碰撞、在哪里停止推进，以及能否完成课程。

官方建议记录课程完成情况、跌倒、碰撞和进展停止的位置，并保存 rollout 视频。这些结果用于决定下一轮应修改环境、资产、奖励还是训练配置。评估与训练的区别必须保持清楚：评估阶段是在检查一个已经学习好的函数 f_θ，而不是继续“教会”机器人；一旦根据失败结果重新修改任务并训练，便进入了下一轮学习。

### 阶段六：从仿真走向物理部署

官方文章明确说，硬件部署细节不在本文主体范围内。真实部署还需要处理仿真与现实之间的差异，例如电机响应延迟、齿轮机械间隙、共享电池负载导致的电压下降、传感器噪声、地面接触差异和控制时序偏差。

Isaac Lab 的 Better Actuator Models（BAM）可以建模伺服响应、回差和电压变化；domain randomization 则在合理范围内随机化物理参数、观测噪声、地形和扰动，使策略不只适应单一的理想条件。随后必须在实机上测试，让失败反过来指导下一轮仿真配置、训练和验证。

因此，官方给出的实机画面是 sim-to-real 链路的证据，而不是整条障碍任务已经完成的证明。官方原文的结论本身就是：这条流程建立了物理部署的基础，但现实差异仍需继续修正。

## 二、Hermes/Nemotron负责规划、Astra负责资产准备，Agent实际做了什么

官方材料给出了较清晰的职责边界，但没有披露 Hermes 与 Nemotron 在每一条提示词上的内部调用链，因此不能把“共同规划”进一步武断地拆成某个固定子任务。这里最稳妥的分工是：

| 角色 | 官方文本支持的职责 | 不应归入其职责的内容 |
|---|---|---|
| Hermes | 与 Nemotron 一起把提示词转成计划；汇总研究、概念图、资产清单和裁剪参考；打包交接材料；自动委派 Astra | 没有证据表明 Hermes 直接更新 RL 策略参数或控制物理机器人 |
| Nemotron 3.5 Bolt | 与 Hermes 共同进行 AI 辅助规划，扩展到研究、路线、尺寸、输出与阶段定义 | 没有证据表明 Nemotron 本身就是步态算法、奖励优化器或实时控制器 |
| Astra | 图像增强与参考核验；协调 FreeCAD 和 Blender；制作、导出与检查资产；在 Isaac Sim 中准备和组装场景 | 没有证据表明 Astra 通过语言推理直接“学会走路”，或在实机上执行运动策略 |
| 本地图像生成模型 | 根据已验证的 Microduck 参考生成障碍课程概念图 | 概念图不是物理仿真资产，也不包含可直接部署的控制策略 |
| Isaac Lab、Newton、Isaac Sim | 提供任务训练、物理计算、场景装配与评估工具 | 它们不是语言 Agent；其职责由框架与求解器承担 |

从“实际完成了什么”的角度看，Agent 的行为链包括：

1. 读取和整理 Microduck 文档、仓库、能力边界与未知项；
2. 把自然语言需求转化为包含尺寸、净空、路线、输出和验收要求的项目计划；
3. 调用本地图像生成模型形成概念图；
4. 从概念图中识别可复用资产，生成对象标识、描述、裁剪图和遮挡记录；
5. 将计划、来源链接、概念图、清单、参考图与执行说明组合成交接包；
6. 核验交接文件后委派 Astra，并等待确认结果；
7. 增强低分辨率参考，同时与原图核对轮廓、比例、颜色和特征；
8. 把无法从图像确定的尺寸与隐藏面标记为假设；
9. 通过程序化执行驱动 FreeCAD 建立几何，通过 Blender 添加细节和材质；
10. 保存可编辑模型、导出 USD、生成预览并检查输出；
11. 在 Isaac Sim 中装配障碍课程，验证机器人能力、导航挑战和 reset；
12. 整理可复现步骤与证据，为训练和本地验证准备输入。

官方还提到 AI agents 可以帮助配置 links、joints 和 actuators。这说明 Agent 适合承担机器人描述与仿真配置层面的辅助工作，但原文没有提供证据，证明最终机器人参数、奖励函数和训练超参数均由 Agent 独立确定。因此，本报告不把“AI 可以帮助配置”扩大为“Agent 已完成全部训练工程”。

同样重要的是，官方计划的验收条款明确写着“不要操作物理硬件”。Agent 在这条工作流中的活动止于数字资产和仿真环境；物理 Microduck 的运行由训练好的策略和机器人端软件完成。部署到机器人后，Hermes、Nemotron 和 Astra 并不在每个控制周期里实时决定关节动作。

这一区分也解释了为什么视频中的步态可以非常有说服力，却不能证明语言 Agent 掌握了运动学：Agent 留下的是可复用的场景、资产和配置，而机器人执行的是训练后导出的策略文件。

## 三、Isaac Lab、Newton、Isaac Sim、Omniverse各自负责什么

这几个名称经常被笼统地称为“NVIDIA 仿真栈”，但它们解决的问题不同。

| 组件 | 核心职责 | 在本流程中的位置 | 不是什么 |
|---|---|---|---|
| **Isaac Lab** | 面向机器人学习的任务定义、观测/动作/奖励配置、环境管理、并行训练、策略评估以及 RL/IL 工作流 | 定义 Microduck 速度或障碍任务，生成大量交互经验并训练共享策略 | 不是资产编辑器，也不是物理求解器，更不是由提示词直接产生步态的 Agent |
| **Newton** | 开源、GPU 加速的物理仿真，计算刚体、关节、驱动、接触、碰撞、摩擦、平衡及动作后果 | 把策略的关节命令落实为机器人运动，并生成下一步状态与接触结果 | 不负责选择动作策略，也不决定奖励如何塑造行为 |
| **Isaac Sim** | 桌面级机器人与环境仿真应用，用于场景装配、机器人配置、传感器和可视化回放 | Astra 组装障碍课程；训练后在本地 RTX Spark 上验证策略 | 不应与 Isaac Lab 的训练任务定义混为一谈；场景搭好不等于策略训练完成 |
| **Omniverse 库** | 提供可集成的渲染、物理和传感器仿真能力，官方流程通过 RTX 渲染生成模拟视觉观测 | 为深度等视觉观测和场景显示提供底层能力 | 不是策略网络，也不承担奖励优化 |
| **RTX Spark** | 本地开发枢纽，承载 AI 辅助规划、资产相关工具和策略验证 | 本地规划与验证；官方图示把大规模训练放在云端 | 不能仅凭它出现在流程图中就推断训练一定在 Spark 本机完成 |

四者的数据流可以概括为：Isaac Lab 定义任务并驱动大量环境；环境把当前观测送给策略；策略输出动作；Newton 计算动作造成的运动和接触；Isaac Sim/Omniverse 提供场景、渲染和传感器数据；采集到的转移用于更新策略；训练完成后再由 Isaac Sim 固定回放并评估。

其中最容易被营销语言模糊的是“Agentic robotics”。在这个案例里，Agentic 部分主要发生在训练之前和训练之外：它把开放需求转成结构化工程任务，降低资产生成与场景装配的人力成本。RL 部分发生在任务定义之后：策略必须反复尝试，从碰撞、跌倒、失衡和进展差异中获取统计信号。两者在资产、配置和接口处衔接，但并不是同一个学习机制。

## 四、4096并行环境里的RL策略怎样学会过坡和障碍

### 1. 4096个环境共享一套策略，而不是生成4096套独立大脑

Isaac Lab 会在 GPU 上同时推进大量相同任务配置的仿真实例。每个实例都有自己的机器人状态、地形、初始姿态、随机扰动和接触结果，但通常共享同一策略网络及其参数。某个实例上的一次尝试产生一条经验，4096 个实例便可以近乎同时提供大量经验。

并行带来的首要收益是采样吞吐：仿真不必按单条轨迹的墙钟时间串行等待，而可以批量推进物理计算、批量收集观测和奖励。它还扩大了状态覆盖范围：机器人会在不同坡面位置、不同坡度、 不同扰动和不同摩擦条件下尝试动作。

但“4096”本身不保证策略质量。环境数量增加的是样本量和场景多样性，不直接等价于成功率提高。如果奖励设计错误、观测缺失或资产物理参数失真，更多并行只会更快地产生同类错误。官方也没有提供“4096 对比少量环境”的消融实验，因此不能据此声称并行度带来了某个幅度的性能提升。

### 2. 一次训练迭代内部发生什么

以官方障碍适配为例，循环可归纳为：

1. 环境重置 Microduck，生成初始机器人状态和前方场景；
2. 渲染器生成头部相机深度，仿真器提供机器人自身状态；
3. 策略网络根据当前观测输出动作；
4. 动作被解释为对机器人关节或其他控制接口的设定；
5. Newton 计算重力、接触、摩擦、关节约束和执行器响应；
6. 机器人产生位移，姿态、速度、深度图和接触状态随之更新；
7. 奖励与终止条件记录这次尝试的进展、稳定性或失败；
8. RL 算法利用整批转移更新共享参数；
9. 新参数继续作用于下一批环境。

Hugging Face/NVIDIA 教程明确指出，Microduck 速度任务输出 14 个关节位置，而官方障碍实验没有公开完整的动作接口。因此可以说明“策略输出低层关节控制量”，却不宜把速度任务的缩放和裁剪参数直接套到障碍策略上。

### 3. 过坡能力不是写出来的，而是物理后果压进参数里的

坡道出现时，Newton 会计算脚与坡面的接触位置、支撑力、摩擦条件、重力投影和机器人姿态变化。若策略仍输出平地行走时相同的动作序列，脚底可能打滑、躯干前倾过度或重心越出支撑区域，随后产生跌倒或速度不足。

训练信号通常会区分几种结果：保持目标方向和高度、获得前进速度、避免异常姿态、避免跌倒、减少无效动作。官方没有公布奖励公式，因此上述内容属于基于任务目标的报告归纳，而不是官方逐项确认的 reward 项。可以确定的是，官方文字明确指出“奖励用于引导学习”，并展示了策略从不稳定步态、碰撞与跌倒逐步改善的过程。

当大量样本都包含类似坡道接触后果时，梯度更新会逐渐改变哪些观测—动作组合更有利。最终表现出来的“抬腿更高、前倾更稳、落脚更准”不是工程师逐帧写入的规则，而是参数对成功与失败样本统计差异的压缩。

### 4. 深度观测让策略有机会对障碍作出反应，而不只是盲走

官方障碍训练同时使用头部相机深度和机器人状态。相比只看关节与 IMU，深度图提供了前方几何信息，例如平台边缘、障碍物轮廓和可通行区域；机器人状态则提供躯干姿态、关节状态和运动历史。

由此可以形成一条闭环：深度图中的障碍变化与当前姿态共同进入策略；策略改变落脚与身体动作；物理仿真返回新的接触和深度观测；奖励再判断这次调整是否带来有效推进或避免失败。由这一闭环可以看出，深度图承担了为策略提供环境信息的关键任务，并未直接由大模型解释成“左转绕开箱子”这样的高层指令。

同样需要保持克制：官方证据支持“深度与状态参与训练”和“视频中完成坡道、障碍场景回放”，但没有证明策略已经形成通用语义地图、显式路径规划器或对任意新障碍都可靠的视觉推理。报告推断而言，它更可能学习了一种在训练分布内具有反应性的感知—运动映射，而不是完整的符号化导航系统。

### 5. 三个来源中的4096不能混成同一项结果

- **NVIDIA 官方博客**：在 RTX PRO 6000 Blackwell Workstation Edition GPU 上使用 4096 个并行环境，以已有 locomotion policy 为起点继续训练坡道和障碍，使用头部相机深度与机器人状态观测。官方未公布训练耗时、奖励曲线和成功率。
- **Hugging Face/NVIDIA 教程**：通过 `--num_envs 4096` 启动 Isaac Lab Microduck 任务，代码示例使用 RSL-RL；其引用配置可在 16 GPU、rough terrain 且启用 backlash 时达到最高 125 万步/秒。这是训练吞吐，不是过坡成功率。
- **`pollen-robotics/microduck_rl` 仓库**：在 mjlab、MuJoCo Warp 与 PPO 上训练 50 Hz 策略，README 称 4096 环境约 1～2 小时可得到可用步态。它使用自己的任务注册、BAM、摩擦随机化、延迟、电池压降和 backlash 实现，物理后端也不是官方博客中的 Newton。

因此，报告中可以说“官方实验确实采用 4096 并行环境”，也可以分别引用其他实现的速度和时间，但绝不能把三者拼接成“某个统一 NVIDIA Microduck 模型在 4096 环境中达到某速度并通过某成功率”。

### 6. 从仿真策略到实机策略，还要经过接口冻结与现实校准

Hugging Face/NVIDIA 教程给出了一条清晰的实机路径：Isaac Lab 回放选定 checkpoint，RSL-RL 播放流程自动导出 TorchScript 和 ONNX；将 `policy.onnx` 复制到 Microduck，通过机器人端运行时加载，再测试站立、慢走、转向和停止。实机接口必须保持观测顺序、归一化和动作缩放一致，否则即使仿真权重完全正确，机器人也会接收到语义错位的输入。

BAM 把理想关节驱动改造成更接近真实伺服的系统，包括电压控制律、反电动势、摩擦、负载相关效应、命令延迟、电池压降和机械回差。Hugging Face 教程还明确列出质量与质心、地面摩擦、关节惯量、编码器偏移、电池电压和命令延迟、地形、外力以及逐关节回差的随机化。开源仓库则采用不同的实现路径：每个关节串联一个无驱动的 backlash hinge，编码器位于回差输出侧，使固件 PD 模拟和关节观测都穿过机械间隙；导出器还会把观测归一化器直接烘焙进 ONNX。两套实现都可以服务于 sim-to-real，但不能互相替换代码或接口。

实机测试还会暴露仿真未覆盖的问题，例如接触面弹性、相机安装偏差、电机温升、电池状态、地面材料和时序抖动。因而仿真成功不是部署终点，而是下一轮实测和再训练的开始。官方特别强调，物理部署仍需进一步修正；这与“Agent 已经独立完成从提示词到可靠实机行为”的说法存在本质区别。

综上，这套工作流最准确的技术表述是：**Agent 把“教机器人过障碍”转化成了可执行的仿真工程，RL 策略在物理反馈中学会如何迈步、保持平衡并对地形和障碍作出调整。** Hermes、Nemotron 和 Astra 提高了计划与资产生产的自动化程度；Isaac Lab、Newton、Isaac Sim 和 Omniverse 则构成训练、计算与验证底座。最终走路的不是提示词，也不是资产清单，而是经过 4096 个乃至更多并行环境训练、经过仿真评估并最终冻结到机器人运行时的策略参数。

## 五、代码证据：真正决定Sim-to-Real的是执行器与观测合同

判断 Microduck 是否真正具备 Sim-to-Real 能力，不能只看仿真场景是否逼真、资产是否由 AI 生成，也不能只看最终能否在实机上走几步。真正决定迁移成败的，是三组可以被代码和实验检查的合同：

1. **观测合同**：策略在每个控制周期究竟收到什么，字段顺序、单位、坐标系、归一化和缺失值如何处理。
2. **动作合同**：14 个关节位置指令以什么单位、比例、限幅和速率发送给执行器。
3. **执行器与时序合同**：电压、电流、反电动势、摩擦、齿隙、电池压降、命令延迟和控制抖动是否落在训练分布内。

[pollen-robotics/microduck_rl](https://github.com/pollen-robotics/microduck_rl) 最有价值之处，正是它公开了这些合同，而不只是展示一个训练完成的动画。

### 5.1 开源仓库给出的可核查基线

该仓库将 Microduck 描述为一台约 **800 g、约 25 cm 高**的开源双足机器人。其实现路线是 **mjlab／MuJoCo Warp + PPO**，而不是 NVIDIA 教程中的 Isaac Lab／Newton 路线。README 声明策略以 **50 Hz** 训练，导出为 **ONNX**，再由 `pollen-robotics/microduck` 中的机载运行时加载执行。

策略接口是：

- **61 维 actor observation**；
- 其中 48 维为本体感知；
- 命令向量包括 `twist(3)`、`head_pose(4)` 和 `body_pose(6)`；
- 输出为 **14 个关节位置指令**。

这 14 个受控伺服关节的布局是固定的：左腿 0—4，颈部与头部 5—8，右腿 9—13。引入 backlash 后，MuJoCo 模型中还会出现额外的无驱动被动铰链，因此“模型中的广义坐标数量”不等于“策略输出的动作维度”；策略仍然只控制 14 个伺服关节。

这里有一个容易被忽略但非常关键的细节：仓库的 ONNX 导出器会把**观测归一化器烘焙进 ONNX 图**。因此，机载端不应随意手工转换 checkpoint，更不能把原始观测直接喂给由导出脚本生成的策略。ONNX 文件本身解决了一部分合同封装问题，却没有自动解决观测字段顺序、动作缩放、关节限位和时序一致性。

### 5.2 BAM 执行器：为什么小型双足尤其依赖执行器建模

`microduck_rl` 的所有主要任务均使用 **BAM M6 执行器模型**描述 Dynamixel XL330 舵机。该模型不是理想位置 PD，而是进一步包含：

- 电压控制规律；
- 反电动势；
- Coulomb 摩擦；
- Stribeck 摩擦；
- 随负载变化的摩擦；
- 电池电压与负载压降；
- 命令延迟；
- 编码器偏差等随机化因素。

这与 Microduck 的尺寸和负载直接相关。约 800 g 的机器人由 14 个小型舵机驱动，地面反作用力、电池压降和减速器摩擦足以改变落脚时机、足端轨迹和重心转移。若仿真中使用理想 PD，而实机使用带摩擦、延迟和压降的舵机，那么即使几何、质心和地形参数都很准确，策略仍可能因执行器相位不同而失稳。

在 Isaac Lab／Newton 路线中，官方教程也使用 Newton-based BAM，并随机化质量与质心、地面摩擦、关节惯量、编码器偏差、电池电压与压降、命令延迟、地形和外力，同时逐关节随机化 backlash。两套实现虽然技术路线不同，却得出了同一个工程判断：**Sim-to-Real 的主要难点不是动作看起来像不像，而执行器实际怎样响应命令。**

### 5.3 ±1° 齿隙不是装饰性参数

`microduck_rl` 为每个主任务提供 Backlash 变体，在每个伺服关节串联 **±1° 机械游隙，即总计 2° 的换向死区**。实现方式不是简单给关节角加噪声，而是：

1. 为每个关节增加名为 `passive_<joint>_backlash` 的无驱动铰链；
2. 让传动链穿过这一被动铰链；
3. 因为真实编码器位于输出侧，固件 PD 仿真和 `joint_pos`、`joint_vel` 观测都必须穿过齿隙读取；
4. 以 `qpos[servo] + qpos[backlash]` 的方式形成可观测关节状态。

这样建模的是“换向前先空走一小段、随后才重新啮合”的非对称机械行为，而不是双向对称的角噪声。其价值在于，训练时策略必须学习如何跨越死区，而不是假设每个位置命令都能立即产生目标角度。

同时必须限制结论：±1° 齿隙只覆盖一类机械误差，不能替代对摩擦、柔性、联轴器间隙、减速器非线性、接触形变和结构松动的实测。

### 5.4 共享观测合同与策略热切换

仓库进一步规定所有策略共享相同的 61 维 actor observation 布局。不同任务不使用某个命令槽时，以零填充，而不是改变张量结构。由此，运行时可以在行走、起身、跌倒恢复、翻滚等策略之间热切换。

这实际上把 ONNX 从“单个神经网络文件”提升为**可替换策略模块的运行时接口**。但“维度相同”只完成了热切换的必要条件，仍不充分。安全热切换至少还要解决：

- 新旧策略的命令语义是否一致；
- 切换瞬间的姿态、速度和估计状态是否连续；
- 是否有站立、支撑足和重心状态门控；
- 旧策略内部时序状态是否需要复位；
- 新策略是否在当前动作饱和率下仍然稳定；
- 切换失败时是否自动回退到保守策略。

README 提供了 `scripts/infer_policy.py` 来预演这种运行时行为，这是有价值的工程证据；但它仍不能替代实机切换时的安全状态机和人工监护。

### 5.5 NVIDIA 官方博客、Hugging Face 教程与开源仓库不能混成同一 benchmark

这三条材料彼此相关，但必须分开解读。

| 路线 | 核心栈 | 公开证据 | 应如何表述 |
|---|---|---|---|
| NVIDIA 官方博客 | Isaac Sim、Isaac Lab、Newton、Omniverse、Astra、RTX Spark | AI 辅助规划、资产生成、场景装配、4096 环境训练、仿真评估及一张实机行走演示 | 一条完整的厂商工程工作流与概念验证，不是独立 benchmark |
| Hugging Face／NVIDIA 教程 | Isaac Lab 3.0、Newton、MJWarp、RSL-RL、RSL-RL playback | 61／14 接口、ONNX 导出、`robotctl` 部署流程、rough／flat 任务与实机演示 | 可操作的训练到部署教程，未给出系统化统计验证 |
| `microduck_rl` | mjlab／MuJoCo Warp、PPO、BAM | 50 Hz、61 维共享合同、14 关节、ONNX、任务集合、齿隙实现、DR 与测试 | 更接近可复现的开源 Sim-to-Real 工程基线，但不是 NVIDIA 训练结果的同一次实验 |

尤其需要强调：

- NVIDIA 博客中的障碍路线训练使用了**头部相机深度与机器人状态观测**；它不能自动等同于 `microduck_rl` 中以本体感知和命令为主的 61 维合同。
- `microduck_rl` 的“4096 环境约 1—2 小时得到可用步态”是 README 给出的操作估计，受 GPU、批量、算法和收敛标准影响，不是统一 benchmark 成绩。
- Hugging Face 教程所称 16 GPU、最高约 125 万步／秒，是特定配置下“rough terrain 且启用 backlash”的训练吞吐指标，不是策略质量或成功率。
- NVIDIA 的物理图 10 证明某个策略可以在实体 Microduck 上行走和转弯，却不证明深度障碍导航已经完成实机验证，更不证明生产安全。
- 三条路线都出现“61 维观测、14 维动作”，只说明接口形状相容，不说明归一化、字段语义、动作缩放或权重可以互换。

因此，报告可以说“这些路线共享一套具有吸引力的接口设计”，但不能说“它们复现了同一个实验”。

## 六、Sim-to-Real 鸿沟：从“参数误差”转向“闭环误差”

Sim-to-Real 不是一个由单一摩擦系数决定的静态误差，而是动作、观测和物理系统组成的闭环误差。即使初始姿态完全一致，一次关节命令的微小时间偏移也可能经由接触和重心转移被放大。

### 6.1 执行器与结构误差

需要辨识的对象至少包括：

- 电压到角度或力矩的实际响应；
- 静摩擦、库仑摩擦和速度相关摩擦；
- 负载下的电池压降；
- 命令传输、固件和舵机内部延迟；
- 换向死区与齿隙；
- 编码器零位、方向和比例误差；
- 关节限位、结构柔性与装配公差。

BAM 和 backlash 解决的是其中一部分，但前提是模型参数来自测量或可信先验。随机化只能覆盖训练时给出的区间，不能自动发现区间之外的失效模式。

### 6.2 接触与动力学误差

小型双足的足端接触面积小，接触点、摩擦锥、足底材料和地面微结构都会影响稳定性。MuJoCo Warp 与 Newton 的求解器不同，关节约束、惯量、碰撞几何和求解容差也可能不同。策略如果在某一种求解器残差特征上过度拟合，换到另一物理后端时可能出现“动作数值相近、落脚结果不同”。

### 6.3 观测与估计误差

本体关节角、速度、IMU、命令和深度图之间存在时间戳差异。真实机器人还存在编码器噪声、通信抖动、相机深度空洞、反光表面、曝光变化、裁剪和视场差异。NVIDIA 官方博客也明确承认，传感器、地面接触和控制时序仍会造成现实差异。

更重要的是，加入深度观测并不会自动得到视觉 Sim-to-Real。必须验证深度图的单位、尺度、对齐、裁剪、有效区域、帧率和延迟与仿真一致。否则策略可能只是学会了仿真深度图的特殊伪影。

### 6.4 任务与场景误差

Astra 生成的 USD、CAD 和材质可以提升场景构建效率，却不自动证明：

- 碰撞几何与实物一致；
- 摩擦和材质标签正确；
- 刚度、柔性和可变形物行为正确；
- 视觉纹理具有正确的尺度和视差；
- 资产在训练域和测试域之间没有泄漏。

在官方流程中，资产生成解决的是“场景从哪里来”，而不是“物理世界已经被正确复现”。

### 6.5 安全与系统误差

真正部署还要处理急停、电流限制、watchdog、通信中断、策略崩溃、异常姿态和热保护。现有教程提供的是加载与监控入口，而不是完整的功能安全论证。物理成功与生产安全之间仍有明显距离。

## 七、Physical RSI 最低验证标准

本文将 **Physical RSI** 理解为“Physical Robot–System Identification”，即在实机上辨识并验证机器人、观测、执行器和控制器组成的完整系统。所给官方材料没有定义一个名为 Physical RSI 的正式行业标准，因此下表不是 NVIDIA 或 Hugging Face 的官方验收条款，而是面向公开研究的最低验证建议。

### 7.1 先冻结软件与接口合同

在接触物理机器人之前，应生成一份机器可读的部署清单，至少包含：

- 机器人序列号、固件版本和舵机批次；
- 训练仓库 commit、依赖版本、随机种子和 checkpoint 哈希；
- 61 维观测的逐字段名称、顺序、单位、坐标系和归一化参数；
- 14 维动作的关节顺序、单位、缩放、限位和变化率限制；
- 策略输入频率、命令输出频率及二者关系；
- ONNX 输入输出名称、shape、数据类型和版本；
- 启用的执行器、backlash、延迟和随机化配置；
- 急停、watchdog、限位、恢复策略和人工接管方式。

应存在自动化测试：向运行时输入已知向量，检查其输出与训练环境逐项一致。仅比较“61 对 14”远远不够。

### 7.2 实机辨识不能被随机化替代

最低限度应测量：

| 对象 | 最低测量项 | 合格依据 |
|---|---|---|
| 舵机响应 | 空载与典型负载下的电压、电流、位置、延迟 | 实测分布与训练随机化包络一致或被更宽范围覆盖 |
| 摩擦 | 启动摩擦、正反向摩擦、速度相关项 | 仿真参数能解释实测误差，而非仅给出一个经验常数 |
| 电池 | 空载、站立、行走的母线电压与压降 | 最坏负载下仍处于策略训练覆盖范围 |
| 齿隙 | 各关节换向死区，至少区分左右方向 | 实测值进入 backlash 模型和训练分布 |
| 编码器 | 零位、方向、比例误差、噪声和丢包 | 修正后观测误差不造成持续关节偏置 |
| 时序 | 50 Hz 周期抖动、端到端延迟、命令丢失 | 实测延迟分布落在模型覆盖范围内 |
| 接触 | 足底材料、地面摩擦、接触稳定性 | 至少在计划部署的地面类型上独立测试 |

“落在训练覆盖范围内”是核心原则。如果真实系统长期位于随机化边界之外，域随机化不能替代重新训练。

### 7.3 分阶段提高实机风险

建议采用四级放行，而不是直接把 rough policy 放到障碍场地：

1. **台架级**：不通电或低负载辨识执行器、确认关节方向和限位。
2. **悬吊／保护架级**：验证站立、慢走、转向、停止和策略切换。
3. **封闭地面级**：在平整地面完成重复任务，记录跌倒、电流、速度和命令跟踪。
4. **任务级**：再引入斜坡、不平地面、推力和真实障碍。

如果项目要发布性能数字，建议每个条件至少在多个独立时段、多个电池荷电状态和至少一台以上同批次机器人上重复，并公开样本数、失败定义和置信区间。厂商 GIF 或单次演示不能替代这些统计。

### 7.4 建议的最低通过线

以下是工程起点，不是官方标准：

- 100% 控制周期能够构造有限、无 NaN、顺序正确的 61 维观测；
- 14 维输出全部通过关节限位、速度和急停检查；
- 实测命令延迟及抖动的分布被训练包络覆盖；
- 平地行走、转向、停止可以在连续运行中重复完成，无不可恢复跌倒；
- 电池最低工作电压和负载压降有实测记录；
- 实机跌倒、推扰和齿隙测试触发率不高于仿真预期；
- 任意策略加载或切换失败都能触发 watchdog 和保守回退；
- 急停和人工接管在每次部署前实际验证；
- 所有运行均保存策略哈希、配置、传感器和关节日志、视频及失败分类。

对于障碍导航，还应单独通过深度传感器合同测试和物理障碍成功率测试。行走策略成功不能替代导航验证。

## 八、Astra 三角色与 Agent harness 的关系

按照 NVIDIA 官方工作流，可将 Astra 的职责归纳为三类。这里的“角色”是工程职责划分，不代表 Astra 已成为独立的学术主体，也不意味着机器人进行了自主闭环进化。

### 8.1 资产构建者

Astra 调用图像处理、FreeCAD 和 Blender，生成可编辑模型、材质、USD 与预览，并保留原始参考图、增强图和建模假设。这能显著降低场景搭建成本，尤其适合需要大量障碍物的研究。

其产物是**人工可审查的工程资产**，不是“机器人已经理解环境并自主进化出硬件”。资产尺寸和隐藏表面如果无法从参考图确定，必须作为假设记录，而不能伪装为测量事实。

### 8.2 场景装配与仿真测试者

Astra 在 Isaac Sim 中组合场景、配置机器人、检查资产、运行仿真并记录可复现说明。它连接的是仿真工具链，不是实机执行器。官方工作流甚至明确要求不操作物理硬件。

其判断仍然受制于碰撞模型、传感器模型和策略配置。场景能够打开、机器人能够在其中移动，不等于训练目标已经达到，更不等于实机可部署。

### 8.3 交接与复现者

Astra 接收 Hermes 与 Nemotron 整理的计划、资产清单和执行说明，再形成可复现输出。真正关键的是它能否把自然语言任务转成版本化文件、配置、测试和证据，而不是生成一段看似合理的说明。

因此，Astra 的可靠工作模式应是“规划—执行—检查—留痕”，其中每一步都应由确定性校验器把关，例如文件存在性、USD 可加载性、碰撞体数量、关节维度、策略输入输出和测试结果。

### 8.4 Agent harness 是治理层，不是物理能力层

Agent harness 可以为 Astra、Hermes 和 Nemotron 提供：

- 工具调用与权限边界；
- 上下文、提示词和参考资料；
- 任务队列、产物目录和版本管理；
- 确定性检查器与回归测试；
- 日志、审批点和失败恢复；
- 训练、导出与部署门禁。

但 harness 不能替代：

- Isaac Lab 或 mjlab 的优化过程；
- Newton 或 MuJoCo Warp 的物理计算；
- 实机传感器和执行器辨识；
- ONNX 与机载运行时的接口验证；
- 急停、限位和人工接管。

在 Agentic Robotics 架构中，Agent harness 应把物理操作设为高风险工具：默认只读或仿真执行，上传策略、加载策略和驱动电机必须经过版本检查与人工批准。官方流程里“AI 自动委派 Astra”和“实机部署需要继续校准”并不矛盾；前者是编排自动化，后者是物理真实性与安全边界。

## 十、反方解释：现有证据还可能意味着什么

### 10.1 “有 61 维观测和 14 维动作，所以模型可以互换”

这是错误结论。维度相同只意味着数组能够对接，不意味着 `twist` 的坐标系、单位、符号、归一化范围、命令时间戳和动作缩放相同。跨路线迁移前必须做逐元素合同测试，不能只依赖 Arena 的 shape 检查。

### 10.2 “使用 BAM，所以执行器问题已经解决”

BAM 提高了模型阶次，但参数仍可能来自名义值、经验区间或另一台机器人。如果质量、齿轮油温、磨损和装配张力不同，错误参数仍会产生系统性偏差。BAM 是可辨识和可随机化的框架，不是免测量证明。

### 10.3 “加了 ±1° 齿隙，所以机械误差已经覆盖”

backlash 解决的是换向死区。它不覆盖摩擦随温度变化、结构弯曲、减速器弹性、线缆拉力、编码器安装偏差和足底磨损。过量随机化还可能使策略过度保守，而精确但失真的模型则可能比合理区间更危险。

### 10.4 “4096 环境或每秒百万步，所以策略一定可靠”

环境数量衡量并行吞吐量，不衡量状态覆盖、奖励设计或真实泛化。真正重要的是采样是否覆盖接触状态、动作饱和、跌倒恢复、延迟长尾和关键步态相位。训练吞吐越高，如果奖励存在漏洞，错误结论也会被更快放大。

### 10.5 “Astra 生成了障碍和策略，所以机器人实现了自主进化”

事实并非如此。Astra 生成或编排的是资产、场景与执行过程；RL 负责优化策略参数；模型代码负责仿真。该流程没有展示机器人根据实机结果自主修改策略、生成新硬件并通过独立验证的闭环。尤其不能把 AI agent 编排工具链描述为机器人本体完成了自主进化。

### 10.6 “视觉上逼真的场景一定能支持深度导航”

渲染质量只覆盖部分感知误差。深度尺度、相机内外参、曝光、遮挡、镜面反射、材质微结构和延迟都可能比颜色纹理更关键。官方流程在 Isaac Sim 中验证了导航行为，却没有在所给材料中证明同一深度策略完成了完整物理障碍路线。

### 10.7 “能走起来就适合生产”

实机行走证明的是运动功能的一部分。生产系统还要求故障检测、急停、远程监督、状态估计、行为边界、版本回滚、可重复标定和独立安全评审。现有材料没有覆盖这些要求。

### 10.8 “开源意味着结果可以独立复现”

仓库公开了任务、配置、脚本和关键机制，这是良好起点；但 README 不是完整实验报告。若要复现 1—2 小时得到可用步态的估计，仍需锁定 GPU、依赖、种子、训练预算、停止标准和 checkpoint。尤其“可用”本身必须被操作化，不能只看视频。

## 十一、工程适用性

### 11.1 当前证据适合的场景

| 场景 | 适用性 | 使用条件 |
|---|---|---|
| 双足 RL 教学与研究 | 高 | 优先使用 `microduck_rl` 固定环境、种子和测试 |
| Isaac Lab／Newton 生态学习 | 高 | 明确采用官方任务配置，不与 mjlab 权重混用 |
| 仿真障碍课程和资产原型 | 高 | 对 USD、碰撞体、摩擦和观测做确定性验证 |
| ONNX 部署接口联调 | 高 | 使用导出脚本并执行逐字段合同测试 |
| 行走与跌倒恢复实机验证 | 有条件适用 | 保护架、限速、限流、急停和人工监护 |
| Microduck Arena 共享挑战 | 较高 | 先确认 61／14 接口、归一化、动作缩放和模型大小 |
| 物理障碍导航 | 尚不充分 | 需要独立完成深度标定和物理成功率验证 |
| 工业、救援或公共空间生产部署 | 不充分 | 需要系统安全、冗余、故障处置和独立验证 |
| 功能安全关键场景 | 不适用 | 现有教程与演示不构成安全认证 |

### 11.2 推荐的工程落地方案

如果目标是尽快获得可复现的 Microduck 行走研究结果，可优先采用 `microduck_rl`：

1. 从 Flat 或 Rough 任务开始；
2. 保持 61／14 接口和 50 Hz 语义不变；
3. 启用经过实机测量的 BAM、摩擦、延迟、电压和 backlash 随机化；
4. 只使用 `scripts/export.py` 生成 ONNX；
5. 在 CPU MuJoCo 中先回放；
6. 在实机前建立参数 manifest 和观测合同测试；
7. 按台架、保护架、平地、任务的顺序逐级放行；
8. 将每个失败样本回灌到参数辨识和下一轮训练。

如果目标是相机深度、复杂障碍和 NVIDIA 工具链，应使用 Isaac Lab／Newton 路线，但需要重新确认该任务究竟采用哪些观测、归一化和动作接口，不能因为名称同为 Microduck 就直接加载 `microduck_rl` 的 ONNX。

### 11.3 Agent harness 的正确位置

Agent harness 应承担“可追溯编排”而非“替代物理验证”：

- 自动收集官方文档、仓库版本和环境配置；
- 为每次实验生成不可变 manifest；
- 对策略输入输出、关节顺序和导出文件运行静态检查；
- 管理训练队列、检查点和评测结果；
- 对实机工具默认设置高权限审批；
- 在异常时阻止策略加载并保留证据；
- 把实机失败映射为下一轮仿真参数与任务设计输入。

这使 Astra、Hermes、Nemotron 的协作可审计，但不改变“策略质量来自优化，物理可信度来自测量，安全来自系统设计”的基本分工。

## 12. Limitations

1. **来源独立性有限。** NVIDIA 官方博客是厂商工程教程，展示工作流与演示，不是由独立实验室复现的 benchmark。
2. **Hugging Face 教程不是统计报告。** 它提供安装、训练、导出和部署步骤，却未公开完整试验次数、置信区间、失败分类和跨机器人泛化结果。
3. **开源 README 仍属于项目方陈述。** 仓库代码使机制更可检查，但本次可用材料主要是 README、任务说明和官方文章，不能替代完整代码审计与复现实验。
4. **物理障碍导航证据不足。** NVIDIA 官方材料展示的是仿真障碍课程和实机行走／转弯，未证明同一深度策略完成实体障碍路线。
5. **两条训练路线不可混算。** mjlab 与 Isaac Lab／Newton 使用不同物理后端、任务配置和训练系统；即使接口相同，也不是同一 checkpoint 或同一性能数字。
6. **50 Hz 的适用范围需限定。** 这是 `microduck_rl` 明确声明的训练频率，不应自动推广到所有 NVIDIA Microduck 配置，也不能替代对实机端到端时延的测量。
7. **61 维并不等于完全兼容。** 观测归一化、动作缩放、坐标系和字段语义必须逐项核对；相同 shape 只是最低层条件。
8. **随机化区间未在给定材料中完整披露。** 无法据此评估参数覆盖是否来自真实测量、是否过宽或是否存在危险盲区。
9. **物理 RSI 表是本文建议。** 它不是官方标准，正式项目仍需依据风险等级、机器人用途和适用法规制定验收门槛。
10. **热切换的安全性证据有限。** 共享合同解决接口兼容，不自动解决姿态相位、估计器状态和回退策略。
11. **实机演示不等于生产验证。** 缺少长期运行、热保护、跌倒损伤、地面泛化、通信故障和多机一致性数据。
12. **Astra 的能力边界必须保留。** 它生成和编排资产，不能被表述为机器人已经自主完成感知—学习—硬件更新的闭环进化。

## 13. 思考与追问

下一步最值得追问的不是“场景还能做多逼真”，而是以下可验证问题：

1. `microduck_rl` 的 61 个观测字段能否导出一份逐项 schema，包括 frame、unit、scale、offset、normalization 和缺失策略？
2. Isaac Lab 教程中的 61 维张量与开源仓库中的 61 维张量逐字段是否相同？深度扩展后分别是多少维？
3. 50 Hz 指观测采样、策略推理、命令发送还是完整控制循环？四者各自抖动是多少？
4. ONNX 导出器除了烘焙观测归一化，是否也处理动作缩放、裁剪和关节顺序？
5. BAM 参数来自数据手册、实测辨识还是手工估计？不同舵机批次之间的分布如何？
6. 实机测得的摩擦、电池压降、编码器误差、命令延迟和 backlash 是否真正覆盖训练随机化区间？
7. 独立留出的物理参数组合——例如训练未同时出现的低电压、高延迟和特定摩擦——是否仍能稳定行走？
8. 行走、跌倒恢复、翻滚等策略热切换时，使用什么状态门控、切换延迟和回退条件？
9. 深度传感器的物理单位、内参、裁剪、有效距离和延迟如何与仿真逐项对齐？
10. 物理障碍路线的完成率、碰撞率、跌倒率、最坏单次失败和安全干预次数是多少？
11. 训练 checkpoint、随机种子、依赖版本、数据集和失败日志能否由第三方完整复现？
12. Agent harness 对实机命令的权限、审计、审批和紧急停止机制是什么？
13. “物理部署完成”的定义是能走几步、通过研究任务、进入受限试点，还是通过生产安全评审？不同定义必须使用不同证据。
14. 当实测参数超出训练包络时，系统应自动拒绝加载策略，还是触发在线再标定？后者本身又需要什么安全边界？

其中前八项决定技术迁移是否成立，后六项决定证据能否支持更宽泛的工程主张。

## 14. 最终结论

Microduck 最有说服力的代码证据并不是一张会走路的渲染图，而是三个相互咬合的工程事实：**BAM 执行器与显式 backlash 让仿真开始接近真实舵机，50 Hz 的共享 61 维观测／14 维动作合同让策略成为可部署、可比较且可热切换的模块，ONNX 与固化归一化则把训练结果封装成机载可消费的软件制品。**

`microduck_rl` 已足以支持一条严肃的开源 Sim-to-Real 研发路线；NVIDIA 与 Hugging Face 材料则展示了 Isaac Lab／Newton、资产生成、训练、导出和实机部署如何组成另一条相关但不同的路线。这些证据共同说明 Sim-to-Real 可以被工程化，却不能证明两条路线是同一实验，也不能把厂商演示提升为独立 benchmark 或生产验证。

最终应采用的判断原则是：**资产负责构造任务，仿真负责提供可重复试验，BAM 与物理辨识负责缩小执行器差异，观测合同负责连接训练和运行时，Physical RSI 与分级实机测试负责建立可信度，Agent harness 负责让整个过程可追溯、可审计。** Astra 可以自动准备场景并加速工程，却不能代替物理测量；仿真可以让机器人反复失败，却不能自动证明策略已适合真实世界。只有当这些层次被分别验证之后，才有资格讨论从研究原型走向受约束的实机试点，而不能跳过证据直接宣称自主闭环进化或生产可用。
