# Cloudflare AI 代码审查推理成本优化：从 2.43 美元到 0.77 美元的完整拆解与口径核验

> **一句话结论**：Cloudflare 把内部 AI code reviewer 的**单次平均成本从 2.43 美元降到 0.77 美元（原文口径 −68%）**，其可迁移的机制是「**先把每次会话首个请求真正打上共享前缀缓存（命中率 14–26% → 91–99.5%），再减少会话内调用次数（16.6 → 1.7–3.4 次），最后才动模型与 effort**」；但 **68% 的分母是「优化前最贵的两周」而非四月基线（均价 1.19 美元，对应降幅约 35%）**，且原文自述「每一步都只是比较变更前后的工作日时段，不是统计上受控的实验」，**所有数字均为厂商自报，无独立验证**。

> **阅读边界**：本文以 Cloudflare 2026-10-19 官方博客《Cutting our inference bill by 68% by being obsessive about optimization》为主线，实际读取其直接链接的一手材料：Cloudflare 2026-04-20《Orchestrating AI Code Review at scale》（架构与四月基线）、《The AI engineering stack we built internally》（模型路由与 Workers AI），以及 Anthropic 官方 Prompt Caching 文档（缓存计费与 TTL 规则）。**未做独立复现，未在本机运行任何被测系统。**

## 1. 问题定义与成本方程

### 1.1 先把「成本」写成方程

Cloudflare 这套系统的一次 review 成本由 Anthropic 风格的 **输入 / 缓存写 / 缓存读 / 输出** 四段构成。按 Anthropic 官方 Prompt Caching 文档（5 分钟 TTL）：**缓存写 = 基准输入价的 1.25×，缓存读 = 0.1×**。

```
一次 review 的成本
  = Σ_{每次 LLM 调用} [ (未缓存输入 token × p_in)
                      + (缓存写入 token × 1.25 × p_in)
                      + (缓存读取 token × 0.1 × p_in)
                      + (输出 token × p_out) ]

又因为「每次调用都把整段会话作为上下文重发」：
  总成本 ≈ 调用次数 C × (单次上下文规模 S 的四段加权) + 输出
```

**这条方程给出三个可动的把手**，Cloudflare 的所有措施都落在这三处：

| 把手 | 含义 | Cloudflare 的对应措施 |
|---|---|---|
| **① 缓存命中率** | 同样内容是否按 0.1× 计价 | 共享前缀 + 消息顺序固定（9/16 改造） |
| **② 调用次数 C** | 每轮是否重发整段上下文 | 并行读文件、去掉无效工具、停止后不再总结、重审跳过 |
| **③ 每 token 价与 effort** | 单位成本 | 模型路由（Opus/Sonnet/Kimi）、effort 分层、去掉昂贵组合 |

### 1.2 优化前钱花在哪（原文的关键自述）

「就在我们开始专注成本优化之前」，AI review 的花费构成是：

| 支出项 | 占比 |
|---|---|
| 输出 token | 约 **23%** |
| 缓存写 | 约 **43%** |
| 缓存读 | 约 **34%** |
| （未缓存输入） | ≈ **0%** |

**结论：几乎全部的钱花在「模型已经看过或马上要再看一遍」的上下文上。** 这就把问题从「怎么让模型更便宜」转成了「怎么让重复内容只按 0.1× 计价、并且少发几次」。

### 1.3 单次会话的结构（code quality reviewer）

- 平均 **16.6 次 LLM 调用/review**；
- 每次调用把整段会话作为上下文重发，导致每次 review 往缓存写 **72k** token、读回 **1.08M** token；
- 随月份推移，**调用次数与上下文规模同时缓慢上升**（见 §2）。

## 2. 优化前：成本为什么从 1.19 涨到 2.43

### 2.1 时间线（自报数据）

| 时点 | 平均每次 review 成本 | 备注 |
|---|---|---|
| 2026-03 | **$1.22** | |
| 2026-04（首篇博客报告值） | **$1.19** | 平均 $1.19 / 中位 $0.98 / P90 $2.36 / P95 $2.93 / P99 $4.45；中位耗时 3m39s，P99 10m21s |
| 2026-06 | **$1.44** | |
| 2026-07 | **$1.74** | |
| 2026-08 | **$2.32**（正文另处写「月底约 $2.46」） | |
| 优化前「最贵的两周」 | **$2.43** | **68% 的分母** |
| 优化后（code quality @ high effort） | **$0.77** | 中位耗时 1m32s |

首篇博客的采样窗口是 **2026-03-10 至 2026-04-09**，覆盖 **131,246 次 review、48,095 个 MR、5,169 个仓库**，平均每个 MR 被审 **2.7 次**，产出 **159,103 条 findings**（约 1.2 条/review）。

### 2.2 涨价的两个来源（原文归因）

**（a）工作负载构成变化（小头）**：落在最高档（full review）的比例从 3 月的 **59%** 升到 8 月的 **65%**。Cloudflare 的解释是「模型变强 → 工程师产出更大更复杂的改动 → 更多落到 full 档」。**注意这是相关而非因果**：也可能是别的因素（如改动规模分布）推高了占比，原文未做控制。

**（b）模型与 effort 变化（大头）**：Cloudflare 自述「我们发现成本增长大部分来自这几个月模型的变化」：

- 8 月初把所有 reviewer 切到 Anthropic 模型：**每次 job $1.38 → $2.03**（理由是内部 eval 显示 Anthropic 在该工作负载上更好）；
- 内部标准审查器 Codex 被换到 **Claude Opus 4.7**：**$0.25 → $0.88/review**，一度比 coordinator 还贵。

### 2.3 一个容易被忽略的事实：高命中率 ≠ 低成本

缓存命中率从 4 月的 **85.7%** 升到 9 月的 **97%**，但**每次 review 的 token 数从 0.91M 涨到 2.99M（三倍以上）**。原文明确：**「高命中率乘以三倍的 token，依然要花很多钱。」**

> **可迁移教训**：缓存命中率是**必要不充分**条件，必须同时盯住 **token 总量**；只优化命中率会得到「命中率 97% 但账单翻倍」的系统。

## 3. 优化链逐项拆解（按发布日期）

原文按「每次发布/配置变更前后对比工作日时段」拆解，明确说明**这不是统计上受控的实验**。以下按其时间线重排，并把每项的**量级、可复现性、副作用**分开标注。

### 3.1 2026-09-14 之前：先学会「钱去哪了」

Cloudflare 从 **9 月 14 日**起让 reviewer 记录**每次 reviewer 首个 LLM 调用的 token 用量**，以及**第一个 system block 按原样发往 provider 时的哈希**。

- 测量结果：**首个请求命中缓存前缀的比例只有 14%–26%**；
- 而事实上**每个会话开头是同一套工具定义与同一份 agent prompt，11k–21k token，在所有仓库都一样**，理应几乎全部命中。

**这是一次典型的「先测流向、再改结构」**：不是先优化 prompt，而是先证明「缓存本该命中却没命中」。

### 3.2 2026-09-16：把共享前缀从易变内容后面挪出来（最大单笔收益）

**根因（OpenCode v1 的实现细节）**：v1 把 agent prompt 与「环境段（工作目录 + 日期）」拼成**一个 block**，并把**唯一的缓存断点放在这个 block 末尾**。共享部分因此从未被单独存储 → **一个仓库的 review 无法复用另一个仓库写入的缓存**。

**修法（9 月 16 日）**：
1. 在每份 agent prompt 末尾加一个标记；
2. 用一个 plugin hook 在该标记处把 block 切成两半，**前半段（所有 job 共享的字节）单独获得一个缓存断点**；
3. 为了保持前半段稳定，**移除一切仓库特定内容**：禁用「可用 skills 列表」，并禁止工具描述在不同 job 之间变化。

**效果**：首个请求的缓存读取率从 **14–26% 升到 91–99.5%**。同日还把内部标准审查器（Codex）的参考索引（内部标准表 + skill 文件 + 参考文件清单）**移进 prompt** —— 此前每个会话要花**前三轮用工具调用去读这些文件**；该 reviewer 的 **LLM 调用数 15.9 → 9.6**，**每次运行成本 $1.12 → $0.72**。

**两项合计把每次 review 从 $2.47 降到 $2.02。**

> **可迁移教训**（对 EverAgent 最直接的一条）：**「缓存断点放在哪」比「缓存前缀有多长」更决定收益**；而**任何排在共享前缀之前的易变内容（时间戳、工作目录、随机 ID、动态注入的技能列表）都会让共享前缀失效**。

### 3.3 2026-09-21 与 09-23：一批「单独都不起眼」的措施（合计约 −$0.20/review）

| 措施 | 原文描述的问题 | 效果 |
|---|---|---|
| **移除子 reviewer 用不到的工具** | 子 reviewer 能看到「发布最终评论」的工具；**57%–76% 的会话里模型尝试调用它**，被服务端校验拒绝后**再花一次调用恢复** | 省掉一次浪费的调用；每个子 reviewer 请求少 **2.9k token** 的工具定义 |
| **并行读文件** | **64% 的 code quality reviewer 回合里模型只做了恰好一次工具调用**（通常是读单个文件） | reviewer 在**第一次响应**里就读完共享上下文与全部 patch，最多 **150 KB** |
| **重审时跳过无变化的 reviewer** | 约 **三分之二** 的 job 是同一 MR 的第二次及以后审查，常有三个 reviewer 无事可做 | full 档重审中：AGENTS.md 审查跳过 **56%**、performance **23%**、documentation **13%** |
| **发布评论后立即停止** | OpenCode 把结果回传给模型**多跑一轮**，重读整段会话写一份没人看的总结 | 每次 job 省约 **$0.07** |
| **区分「慢」与「坏」** | 超时的 reviewer 被当成 provider 故障，用**同样的超时**重新开始 | 配合更长超时与更低 effort，**security reviewer 超时率 1.8% → 几乎为零** |
| **取消已取消的 job** | GitLab 的 Kubernetes executor 在 job 取消时**不给脚本发信号**；在 **446 个被取消 job 的样本中，358 个仍跑到 review 结束** | job 每 **15 秒**自查状态并停止 |

### 3.4 三 reviewer 共享同一首请求（最复杂的一项）

code quality / security / performance 三个 reviewer 现在发出**完全相同的首个请求**：同样的工具、同一份共享规则文件，然后是**包含全部 patch 的 MR**；各自的专属指令放在其后。**其中一个负责写缓存，另两个读它。**

代价：**缓存条目在写入它的响应开始流式返回之前不能被读取**，而三个 reviewer 同时启动 → 第二、第三个要等第一个的响应开始，最多等 **20 秒**。原文的说法是「略微变慢，但每个 reviewer 省约 9 美分」。

### 3.5 模型与 effort 变更（原文称其贡献大于代码改动）

| 变更 | 依据 | 效果 |
|---|---|---|
| **去掉冗余的 model×effort 组合** | coordinator 自 8 月起并行跑三组 model+effort 组合；**同模型下 full 档 medium effort 比其它组合快 20%** → 砍掉另两组 | 精简路由面 |
| **Opus 5.5 medium 替换 Opus 5** | **随机分流**显示在审查结果与 critical findings 上「无可测量差异」 → 切换 | — |
| **Opus 5.5 high 放弃** | high 比 medium 更贵，却**没有带来有意义的 findings 增加** | — |
| **Sonnet 5.5 替换 Sonnet 5** | 10 月 3 日把所有 Sonnet reviewer **50/50 分流**到 Sonnet 5 / 5.5；两天半后：**code quality 每次运行便宜 62%、performance 58%、security 47%**；**两者每 token 同价**，所以收益**全部来自用更少的 token** | full 档上 5.5 版发布的 critical+warning findings 与 5 版**大致相同** → 10 月 5 日全量切换 |
| **code quality 回到 high effort** | 10 月 5 日起 5.5 上 medium/high **50/50 分流**（一天）：**high 每次运行贵 61%，但 critical+warning findings 多 58%** ≈ 每次 review 约 **2 美分** | 因为质量侧认为这些额外 findings「值得」，决定把 code quality 设为 high |

**调用次数的变化**：Sonnet 5.5 medium 下 code quality reviewer **每次运行 1.7 次 LLM 调用**（此前 6.2 次），**过半运行单次调用即结束**，意味着**不会打开仓库里任何其它文件**；high effort 下为 **3.4 次**。Cloudflare 明确表示担心「这会不会让审查变浅」，并在质量章节回应。

**token 结构的变化**：自 9 月初以来，**每次 review 的缓存读 −82%、缓存写 −54%、输出 −67%**。

### 3.6 OpenCode v1 → v2（工程改造，代价很低）

- v2 是从零重写；
- 上线前在**所有 canary 仓库**用 **v1 与 v2 并行跑每一次 review**，做对照性影子模式：**两者在 98% 的被测 MR 上对「是否通过」的判定一致** → 10 月初一次性全量切换并删除 v1 代码；
- 同模型对比：**full 档在 v2 上快约 13%**；
- 另在试验**完全跑在 Durable Objects 上（pi-durable）**。

> **值得单独学的做法**：**影子模式双跑 + 判定一致率（98%）作为切换门槛**。它把「换 agent 框架」这种高风险动作变成一个可度量的灰度过程。

## 4. 68% 的口径核验：分母、时间窗、样本、混淆项

### 4.1 分母核验：68% 的基准是**峰值窗口**，不是四月基线

| 对比基准 | 数值 | 相对 $0.77 的降幅 |
|---|---|---|
| 优化前**最贵的两周**平均 | **$2.43** | **−68%**（原文标题口径） |
| 8 月月底 | ~$2.46（正文另处 $2.44 / $2.32 / $2.47） | −68%…−69% |
| **四月首篇博客的平均值** | **$1.19** | **约 −35%** |
| 四月的中位成本 | $0.98 | 约 −21% |

**结论**：**「68%」使用优化前最贵的两周作为高位基准**；若以四月公布的平均值为基线，降幅约 35%。两者都成立，但表达的是不同时间窗。[分析者推导]

### 4.2 时间窗与样本

- 分母窗口：**优化启动前的两周**（原文未给具体日期，只说「最贵的两周」）；
- 分子：优化后的当前值（**code quality 设为 high effort 之后**的口径）；
- 原文自述**每一步的变化都是「比较变更前后的工作日小时数」**，并明确写「**这不是统计上受控的实验**」；因此**各措施的收益不能相加当作严格归因**。

### 4.3 金额加总与四舍五入的不一致

原文拆解称：「**代码改动贡献 $0.65，模型与 effort 变更贡献 $1.06**」，合计 $1.71；而同段的分母写作「**从 $2.44 降到 $0.77**」，即差值 $1.67；标题口径的 $2.43 → $0.77 差值为 **$1.66**。三处数字彼此差 $0.04–0.05，属四舍五入与取整，**但也说明「68%」的精度不应被当作精确值**。[分析者推导]

另有一处口径需要读者注意：正文写「**40% 的节省来自 reviewer 代码的改动，其余来自模型与 effort 的实验**」，与「$0.65 vs $1.06」（约 38% / 62%）方向一致。

### 4.4 是否同时改变了质量、模型与工作负载？

| 维度 | 是否改变 | 依据 |
|---|---|---|
| **模型** | **是**（Opus 4.7 / Opus 5 / Opus 5.5 / Sonnet 4.6 / Sonnet 5 / Sonnet 5.5 / Kimi K2.5） | 见 §3.5；8 月整体切 Anthropic 模型曾把单次成本推高 $1.38→$2.03 |
| **effort** | **是**（medium ↔ high） | high 相对 medium 每次运行贵 61% |
| **工作负载构成** | **是**（full 档占比 59%→65%；每次 review token 数 0.91M→2.99M） | §2.2、§2.3 |
| **agent 框架** | **是**（OpenCode v1 → v2） | §3.6 |
| **质量** | **声称「没变差」，但有明确损失面** | 见 §5：performance 在 medium 下**确实丢了真实 findings** |

**因此：$2.43 → $0.77 是「代码优化 + 模型/effort 变更 + 框架换代 + 工作负载漂移」的合并结果，不能拆给任何单一因素当因果结论。**

### 4.5 平均成本 ≠ 尾部成本

- 四月的成本分布是公开的：平均 $1.19 / 中位 $0.98 / P90 $2.36 / P95 $2.93 / **P99 $4.45** → **P99 / 平均 ≈ 3.7×**；
- 优化后**只公布了平均值 $0.77**，**没有公布新的成本分位数**，只公布了**耗时**分位数；
- 因此**「平均降 68%」并不代表尾部也降 68%**，也无法验证「巨型重构类 review 是否仍贵得离谱」。

> **这正是任务约束里「不得把平均成本当尾部成本」的具体落点**：Cloudflare 自己在四月就展示了长尾（massive refactor 触发 full 编排），优化后**没有重新公布 P99 成本**。[分析者推导]

## 5. 质量与延迟评估：他们怎么证明「没变差」

### 5.1 现象：findings 数量大幅下降

用 Sonnet 5.5 后（code quality 已在 high effort，security/performance 仍在 medium）：

| reviewer | critical + warning findings 相对 8 月底 |
|---|---|
| code quality（high） | **−40%** |
| security（medium） | **−56%** |
| performance（medium） | **−71%** |
| compliance | **上升** |

**「严重 findings 下降」本身无法区分「真问题被漏掉」与「噪声被剪掉」** —— 这是原文自己提出的问题，并给出两条独立路径。

### 5.2 路径一：作者是否真的动手改（行为代理指标）

方法：取 critical 与 warning findings 的样本，比较**被审查的那次提交**与**作者的下一个 push**；若该 finding 所指的行发生变化，则计为「被采纳」。

- **基线校准**：距离 finding 30–40 行之外的代码，在**每个时期**都约有 **15%** 的概率变化 → 这是「碰巧改动」的基线；
- **结果**：**code quality 的严重 findings 采纳率从 34% 升到 59%**；
- **归一化后的效果**：**每 1,000 次 review 中「导致一次改动的 findings」从 145 降到 132，处于误差范围内**（即「数量与以前相当」）；
- **四个 reviewer 合计**：**每 1,000 次 review 导致改动的严重 findings 从 229 升到 321**。

**如何读这条指标**：它衡量的是「**精确度**（precision）」而不是「召回」。它无法发现「两者都没报的真问题」—— 原文明确承认「作者改动某行只说明他做了什么，不说明这个 finding 是对的」。

### 5.3 路径二：跨厂商盲评（双评审 + 第三方仲裁）

方法：取三个 Sonnet reviewer 的 **657 条 findings** 的**盲化样本**，附上所指 diff、**不告诉评审者来自哪个时期**；由**两家不同厂商的两个模型**评审，分歧交给**第三个模型**仲裁。每条 finding 标注为 important / minor / duplicate / wrong / unverifiable，并标注严重度是否公允（fair / 偏高 / 偏低）。

结果：

| 指标 | 之前 | 现在 | 解读 |
|---|---|---|---|
| **important findings / review** | **0.28** | **0.30** | 区间重叠 → **真实问题数未下降** |
| **严重度被高估的 critical/warning / review** | **0.46** | **0.14** | **下降 70%**，原文称之为「本研究中最清晰的结果」 |
| 消失的构成 | — | — | 主要是 minor、duplicate、以及评审者无法从 diff 验证的条目 |

### 5.4 路径二的负面结论（必须一起读）

- **performance（仍在 medium）确实丢了真实发现**：评审者发现 **important performance issues 每 review 约少 64%**，折算约为 **每 24 次 full 档 review 少一条重要的性能问题**；
- **security 可能也丢了**：约 **−1/4**，但**统计上不显著**；两者都留作「下一步测 high effort」；
- **code quality 在 medium 下更糟**：随机分流显示 **medium 的「被采纳 findings」约为 high 的四分之一** → 因此才把 code quality 定为 high effort。

### 5.5 可靠性与延迟

| 指标 | 之前 | 现在 |
|---|---|---|
| 没有产出结论的 review | 0.79% | **0.27%** |
| security reviewer 重试率 | 3.5% | **0.04%** |
| review 中位耗时 | 4m09s | **1m32s** |
| P99 耗时 | 15m20s | **4m41s** |
| 超过 5 分钟的 review 占比 | 37.9% | **0.7%** |
| full 档中位耗时 | 5m16s | 1m54s |
| lite 档中位耗时 | 2m58s | 1m14s |
| trivial 档中位耗时 | 77s | 30s |

补充：到 8 月时，中位耗时比 4 月**慢 14%**、P99 **慢 48%** —— 原文因此说「这部分工作把我们拉回了原来的水平」。**延迟的改善主要来自「调用次数变少」，不是模型变快。**

### 5.6 质量方法的自我批评（原文原话，值得单列）

> 「两种方法都不完美。作者改动被标记的行只说明他做了改动，不说明这个 finding 是对的。评审者 themselves 也是模型，而且每组只有 35 到 66 条 finding。'现在' 这个窗口也只有一天长。」

**这三条限定同时适用于任何复现者**：样本小、窗口短、裁判也是模型。

## 6. 替代方案：除了 Cloudflare 的做法还能怎么降

以下是**至少两个可直接对照的替代路径**，及其适用边界。

### 替代方案 A：把可判定的检查从 LLM 审查里移出去（规则/静态分析优先）

- **做法**：能被 lint、SAST、类型检查、依赖许可、格式规则判定的项，一律走确定性工具；LLM 只处理「需要理解意图与上下文」的项。Cloudflare 体系里的对应物是 Engineering Codex（内部标准以 codex 规则 + agent skill 形式提供，审查时引用具体规则 ID）与 AGENTS.md reviewer（检查改动是否让 AI 指令过期）。
- **相对优势**：成本可预测（接近 0），延迟极低，且**不会随模型涨价而涨价**；还能显著降低「严重度虚高」类噪声。
- **边界**：规则覆盖不到语义级缺陷（并发、跨服务契约、意图误解）；规则维护本身有成本；**过度规则化会把审查变成「合规检查」而漏掉真 bug**。
- **成本影响**：把 LLM 审查的**触发面**缩小，是「减少调用次数」这个把手的最强形态 —— 但它改变的是工作量构成而非单价。

### 替代方案 B：把负载下沉到自托管/低成本推理（Cloudflare 已在用，但常被忽略）

- **做法**：低风险任务（文档审查、AGENTS.md 生成、轻量推理）交给自家推理平台上的开源模型。
- **Cloudflare 的量化**：**Workers AI 承接 reviewer 约 15% 的流量**，主要是文档审查；**Kimi K2.5 在 Workers AI 上比中档专有模型便宜 77%**；其安全 agent **每天处理 70 亿 token**，若按中档专有模型计费**一年约 240 万美元**，而在 Workers AI 上便宜 77%。另有 **51.47B 输入 token / 361.12M 输出 token** 走 Workers AI。
- **相对优势**：成本与前沿模型脱钩；同网络调用减少跨云延迟。
- **边界**：开源模型在**需要推理能力的复杂/安全敏感审查**上不一定够用；自建推理有运维与容量成本；**把「便宜模型」用在高风险 tier 上，会直接命中 §5.4 那类「真实 findings 下降」的坑**。

### 替代方案 C：减少上下文本身的规模（工具 schema 折叠 + 按需读取）

- **做法**：不把每个工具的 schema 都塞进上下文，而是让模型通过代码发现与调用工具。
- **Cloudflare 的量化**：其 GitLab MCP server 原本暴露 **34 个工具，schema 约占 15,000 token/请求**（在 200K 上下文窗口里是 **7.5%** 的预算）；MCP Server Portal 用 **Code Mode** 把这些折叠成 **2 个 portal 级工具**（`portal_codemode_search` / `portal_codemode_execute`），因此**新增 MCP server 不再增加每次请求的 schema 开销**。
- **边界**：Code Mode 需要沙箱执行能力与更严格的工具权限模型；对工具数量少的场景收益有限；**折叠 schema 会让模型更依赖运行时发现，出错时诊断更难**。

### 替代方案 D：用上下文压缩/摘要代替缓存（缓存不可靠时的退路）

- **做法**：会话内对早期内容做摘要、或只保留与当前决策相关的片段，从而**不依赖 provider 的前缀缓存**也能减少重复计费。
- **相对优势**：不依赖供应商缓存 TTL 与计费政策；对「每次任务都不同、无法共享前缀」的场景（如 EverAgent 的报告生产）更适用。
- **边界**：摘要有信息损失风险，且**质量影响难以用「成本下降」自证**；缓存是**零语义损失**的手段，压缩不是 —— 在可缓存时应优先缓存。

### 替代方案 E：尾部资源治理（成本方程里被漏掉的一项）

取消的 job 仍跑完（446 个样本里 358 个）、超时被当 provider 故障重试、超时重试用同样的超时预算 —— 这些**不产生 review 价值却照常计费**。Cloudflare 的修补（自检状态、区分慢与坏）成本极低但直接作用于尾部与浪费。

## 7. 对 EverAgent 的可执行迁移清单

> 前提判断：**EverAgent 的工作负载形态与 Cloudflare reviewer 差异很大**（Cloudflare 是「同一套仓库上下文在数千仓库间复用」，EverAgent 是「每篇报告/每个任务上下文基本不同」）。因此下表区分 **直接可迁移**、**需改造**、**不适用**。

| # | 迁移项 | 具体动作 | 适用性 | 失效条件 |
|---|---|---|---|---|
| 1 | **先测流向** | 在每次 harness 会话的首个请求记录：provider 侧 `cache_read_input_tokens` / `cache_creation_input_tokens` / `input_tokens`，以及**首个 system block 的哈希**；按周统计命中率 | 直接可迁移 | 无 |
| 2 | **前缀切分与断点位置** | 把「长期不变的项目上下文（AGENTS.md、方法论、常驻指令）」与「本次任务的动态内容」分开；缓存断点只放在稳定前缀末尾 | 需改造（EverAgent 前缀跨任务不复用） | 若每轮都注入时间戳/随机 ID → 命中归零 |
| 3 | **工具 schema 瘦身** | 删除当前 agent 不会调用的工具定义（Cloudflare：每个子 reviewer 省 2.9k token）；必要时用「按需发现」替代全量 schema | 直接可迁移 | 工具集本身频繁变化时无法保证前缀稳定 |
| 4 | **并行读文件** | 首轮一次性读完所需文件（≤150 KB 量级），避免「每回合只读一个文件」的 64% 模式 | 直接可迁移 | 文件过大时需分批 |
| 5 | **输出即停** | 报告正文/评论发出后不再要求模型「再总结一轮」 | 直接可迁移 | 无 |
| 6 | **取消与超时语义** | 任务取消时自检状态（Cloudflare 每 15 秒）；把「超时」与「provider 故障」分开处理，不以相同预算重试 | 直接可迁移 | 无 |
| 7 | **多 agent 共享前缀** | 多个 reviewer 发出**相同首请求**，由一个写缓存、其余读；接受首请求串行带来的等待 | 需改造（EverAgent 多 agent 常共享同一项目上下文，有条件成立） | 若各自 system prompt 差异大则无法共享 |
| 8 | **effort 分层而非统一** | 按任务价值分层：报告初稿 medium、关键章节/复核 high；并像 Cloudflare 那样用 50/50 随机分流量化「多花的钱换回多少 findings」 | 直接可迁移（对应 EverAgent 的 report-v2 tier 与 review 门） | 样本太小时分流结论不稳 |
| 9 | **自建质量门（两层）** | ①行为代理：EverAgent 版「被采纳率」= 报告/建议是否被采纳或据此改动；②盲评抽样：跨模型盲评关键 claim，区分「噪声下降」与「真实问题下降」 | 直接可迁移 | 裁判模型自身偏差；样本 <50 条时只作定性 |
| 10 | **模型路由的成本-质量记录** | 记录每个模型×effort 组合在**本工作负载**上的每 token 价与实测质量，参考 Cloudflare 的「randomized split → 无可测量差异才切换」纪律 | 直接可迁移 | 供应商涨价/下线 |
| 11 | **缓存 TTL 的显式处理** | Anthropic 默认 **5 分钟 TTL**，长时任务需 **1 小时 TTL** 或主动重写；EverAgent 的会话间隔常大于 5 分钟 → **默认状态下缓存命中天然低**，必须显式配置或改用压缩 | 直接可迁移（认知层面） | 供应商改 TTL 或改计费 |
| 12 | **影子模式灰度** | 更换 agent 框架/prompt 时双跑一���，用「判定一致率」作为切换门槛（Cloudflare：98% 一致才全量） | 直接可迁移 | 双跑成本翻倍，需限定窗口 |

### 7.1 对四类具体场景的取舍建议

| 场景 | 最值得先做的 | 不建议先做的 |
|---|---|---|
| **EverAgent 报告生产** | #1 测流向、#5 输出即停、#9 两层质量门、#8 effort 分层 | #2 共享前缀（每篇报告上下文不同，跨任务前缀无法复用） |
| **日报/聚合简报** | #3 工具瘦身、#4 并行读、#5、#12 | 追求缓存命中率（每天上下文都变） |
| **播客/长文精读** | #4 一次性读入（Cloudflare 的 150 KB 量级可直接借用）、#8 effort 分层（摘要 vs 精读）、#9 盲评 | 强依赖 provider 缓存（长任务 + 5 分钟 TTL 是天然冲突） |
| **多 agent harness** | #7 共享前缀（若共享同一项目上下文）、#5、#6、#2（若各 agent 前缀稳定） | 让每个 agent 各自携带完整工具与上下文（Cloudflare 早期就是这样，代价是 7× 复制） |

### 7.2 反方边界（什么时候**不该**照抄）

1. **Cloudflare 的最大收益来自「跨仓库共享同一份 agent prompt」**。EverAgent 的多数任务不具备这个前提 → **照抄「共享前缀」会得到接近零的收益**，反而增加断点管理的复杂度。
2. **Cloudflare 的质量结论建立在「大量真实 review 与真实作者改动」之上**（数十万次 review、14 天窗口）。EverAgent 报告只有几十篇量级，**任何「采纳率」统计都会是小样本**。
3. **Cloudflare 的模型与 effort 组合是针对其工作负载选出的**；同样的「medium 比 high 便宜 61% 但 findings 少 58%」在 EverAgent 上不成立 —— **每个工作负载必须自己测**。
4. **「降成本同时不降质量」在其场景成立，不代表在所有场景成立**：其 security/performance 在 medium 下**确实丢了真实 findings**。这提醒我们：**effort 下调必须配套质量门**。
5. **成本下降部分来自「模型换代与框架换代」**（Opus 5.5、Sonnet 5.5、OpenCode v2）—— 这部分与工程技巧无关，**不可类比**。

## 8. 失效条件

针对本报告提出的每条迁移建议，列出使其**不再成立**的条件：

1. **前缀不稳定**：任何在共享前缀之前插入时间戳、工作目录、随机 ID、动态技能列表的行为，都会让缓存命中率归零（Cloudflare 正是为此禁用了 skills 列表并冻结工具描述）。
2. **缓存 TTL 过期**：默认 **5 分钟** TTL 下，长于 5 分钟才读取的条目等于从未命中；Anthropic 提供 1 小时 TTL 选项，代价是写入价更高（官方表：1h 写入约为基准输入价的 2×，5m 为 1.25×）。→ **缓存是「时序依赖」的优化，不是无条件的**。
3. **token 总量上升抵消命中率收益**：Cloudflare 自己给了反例 —— 命中率 85.7%→97%，但 token 数 0.91M→2.99M，成本仍上涨。
4. **质量样本不足**：其盲评每组只有 **35–66 条**、「现在」窗口只有 **1 天**。小样本下的「无差异」结论**不能外推**。
5. **未受控的前后对比**：其每一步都是「变更前后工作日小时数」比较，**不是随机对照**；在有趋势性变化（工作负载漂移、模型换代）时，归因不可靠。
6. **多 reviewer 共享首请求的启动延迟**：三个 reviewer 并发启动时，后两个最多等 **20 秒**才能读到缓存 → 在强延迟 SLO 场景下这条收益可能被吃掉。
7. **供应商计费政策变化**：缓存读 0.1×、写 1.25× 是当前政策；政策一变，整个成本方程的分母全变。
8. **「更便宜的模型」在长尾任务上失效**：若 reviewer 的重尾来自巨型重构类 MR，用中等 effort 模型处理它们可能直接损失关键发现（Cloudflare 的 performance −64% important findings 就是实例）。
9. **自托管推理的容量与运维**：把负载下沉到自家平台能对冲单价上涨，但容量规划与故障半径成为新的风险面。
10. **框架灰度的双跑成本**：影子模式会带来接近 2× 的运行成本，窗口太长就不划算。

## 9. Limitations

1. **全部数字为 Cloudflare 自报**，无独立第三方复现；本文未运行任何被测系统。
2. **68% 的分母是「最贵的两周」**；以四月平均值 $1.19 为基线则约 −35%（[分析者推导]）。原文另出现 $2.32 / $2.44 / $2.46 / $2.47 多个 8 月数值，彼此略有出入。
3. **各措施收益不可相加为因果归因**：原文明确「每一步比较变更前后的工作日小时数，这不是统计上受控的实验」；「代码 $0.65 / 模型与 effort $1.06」与总差值 $1.66–1.71 亦有 $0.04–0.05 的出入（[分析者推导]）。
4. **平均值代替了尾部**：优化后未公布成本分位数（只公布了耗时分位数），四月 P99/平均 ≈ 3.7× 的长尾是否保留**未知**。
5. **工作负载同时变化**：full 档占比 59%→65%、每次 review token 数 0.91M→2.99M、OpenCode v1→v2、模型与 effort 多次变更 —— **$0.77 与 $2.43 不可归因给任何单一措施**。
6. **质量证据规模有限**：盲评 657 条样本、每组 35–66 条、「现在」窗口仅一天；评审者本身是模型；「作者改了那几行」只证明行为不证明正确性。原文自己列出了这些限制。
7. **存在明确的负面结论**：performance 在 medium 下确实丢了真实发现（−64% important），security 疑似 −1/4 且不显著。
8. **未披露的口径**：优化后的成本分位数、缓存写入失败率、模型输出的方差、缓存条目被驱逐的比例、各 tier 的成本分解、审查结论的人工复核率。
9. **Claude Opus 5.5 比 Opus 5 每 token 更便宜**这一说法来自 Cloudflare 转述 Anthropic 定价，本文未独立核对官方价目表。
10. **可迁移性受限**：其最大收益依赖「跨仓库共享同一份 agent prompt + 同工具集」的复用前提，EverAgent 的多数场景不具备。
11. 本报告中标注为 **[分析者推导]** 的判断（68% 的替代基线、四舍五入不一致、P99/平均比、$0.77 的三类解读）均为我的推断而非原文陈述。

## 10. 思考与追问

1. **「68%」这个标题数字本身是否值得采用？** 以峰值窗口为分母，会让任何「从最差到最好」的系统都显得收益巨大。**是否应强制同时给出「相对期初基线」与「相对峰值」两个口径？** 对 EverAgent 报告的对外数字而言，这是一条值得写进规范的纪律。
2. **缓存收益与「共享前缀」前提的耦合有多紧？** 如果 EverAgent 每篇报告的上下文都不同，是否存在「结构化前缀」（如固定的方法论段、固定报告骨架）可以被真正共享？**哪些段落必须逐字稳定？**
3. **「每轮省一次调用」与「少发上下文」哪个更值钱？** Cloudflare 的 16.6 → 1.7 次调用变化是本轮最大杠杆之一，但其中有多少来自模型变强（Sonnet 5.5 本身更爱一次性回答），多少来自 prompt/编排改造？**如果没有 Sonnet 5.5，调用次数还能降到 1.7 吗？**
4. **质量门该由谁来做？** Cloudflare 用「作者是否真的改了代码」作为行为代理，这对 EverAgent 的等价物是什么 —— 「建议是否被写进报告」「报告是否被复核通过」「复核意见是否被采纳」？**哪一个才是可测的、不自欺的代理？**
5. **盲评的裁判偏差怎么校准？** 用模型判模型会有系统性偏好（偏爱与自身风格相似的输出、偏爱更长的输出）。Cloudflare 用「两家厂商 + 第三方仲裁」缓解，但未报告裁判一致性指标。**EverAgent 是否需要一个人工小样本做裁判校准？**
6. **能否把「成本方程」做成 EverAgent 的常驻仪表盘？** 每次 harness 运行记录四段 token 与调用次数，并按「报告类型 / 模型 / effort」分组，用于回答「哪类任务最贵」「质量换成本的边际在哪」。
7. **多 agent harness 的「共享首请求」在 EverAgent 里是否成立？** 若 coordinator 与各 sub-agent 的 system prompt 差异大，是否可以退一步：**共享「工具定义 + 项目上下文」段，各自指令放其后**（即 Cloudflare 的三 reviewer 模式）？
8. **质量下降会不会先于成本下降出现？** Cloudflare 的数据显示「findings 减少」与「真实问题减少」在 medium effort 下确实同步发生（performance −64%）。**因此成本仪表盘必须与质量仪表盘同屏**，否则会重复「先降成本、后发现漏问题」的路径。
9. **重试与取消的浪费在全库占比多少？** Cloudflare 抽样 446 个取消 job 里 358 个仍在跑（80%）。**EverAgent 的调度器是否有同类的「已取消但仍在消耗」问题？** 这类问题通常比模型选择更便宜地修好。
10. **如果把这套方法卖给平台方而不是自用，最小可行实现是什么？** 我的判断是：**①测流向（首请求哈希 + 缓存命中率）②切分共享前缀并冻结工具描述 ③输出即停 ④并行读文件 ⑤取消自检**这五项，不需要改模型也能拿到大部分「代码侧」收益。
