# A2UI 1.0：Agent 描述界面，应用掌握渲染、数据与执行边界

让 Agent 提交一段长文字，用户再回复“第二项改一下”，往往不如一个可以直接修改的表单。问题是，界面由谁生成、数据放在哪里、用户操作怎样回到 Agent，以及点击之后到底允许做什么。

A2UI 提供了一套描述界面和交互的协议：Agent 发来结构化数据，应用用已经注册的组件渲染。模型可以决定怎样组合界面，却不必把任意前端代码交给应用执行。[1][2]

1.0 版本的重要变化，不只是多了几种控件。它支持更明确的双向函数调用、单条消息初始化界面、同一界面混用目录，并调整了数据绑定与组件元数据的写法。本报告以发布文为入口，主要对照固定提交 `57f961f143da23f4212313e432a64b5843d978f9` 的规范、迁移指南和 JSON Schema 展开；发布页本次直接回源未成功，技术结论以这些一手规范为依据。

## 模型输出的格式，不必就是线上传输的格式

官方将实现分成几个职责：[2][3]

```text
模型或确定性程序选择界面内容
    ↓
Agent SDK 解析、检查，必要时展开宏和转换格式
    ↓
标准 A2UI 消息
    ↓
Core SDK 维护界面与数据状态
    ↓
框架适配器把状态映射到本地组件
```

模型可以直接生成 JSON，也可以用 A2UI Express 这种更紧凑的表示，由 SDK 转成标准消息。程序也可以不经过语言模型，直接构造消息。**用于生成的格式与用于传输的协议，是两层不同选择。**

这样做可以减少模型重复书写组件标识、括号和固定字段的工作，但不能仅凭格式更短就宣布整个应用更快。总等待还包括推理、解析、数据取得、函数调用和渲染。本次没有做 token 或延迟基准。

A2UI 也没有规定必须用 WebSocket。规范要求传输层可靠地保持消息顺序、划清消息边界，并提供元数据机制；交互式应用还需要返回通道。MCP、A2A 或其他传输可以承载这些消息，各自仍有自己的连接与宿主合同。[2]

## Surface 里同时存在组件图和数据模型

Surface 可以理解为一块独立管理的界面。它有自己的 `surfaceId`、组件集合和 JSON 数据模型。组件以平铺列表发送，通过 ID 指向子组件；其中 `id: "root"` 的组件作为界面内容的根。[2]

下面是一个自拟的最小例子。假设渲染器已经注册规范中的 Basic Catalog，并且该 surface 尚不存在：

```json
{
  "version": "1.0",
  "createSurface": {
    "surfaceId": "learning-plan-1",
    "catalogId": "https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json",
    "dataModel": {"form": {"title": "我的学习计划"}},
    "components": [
      {"id": "root", "component": "Column", "children": ["preview", "title"]},
      {"id": "preview", "component": "Text", "text": {"@path": "/form/title"}},
      {"id": "title", "component": "TextField", "label": "报告标题", "value": {"@path": "/form/title"}}
    ]
  }
}
```

1.0 允许初始数据与组件一起放进 `createSurface`。规范要求先应用数据，再解析组件绑定，因此控件第一次读取时就能得到初始值。

后续若只改标题，可以发送：

```json
{
  "version": "1.0",
  "updateDataModel": {
    "surfaceId": "learning-plan-1",
    "path": "/form/title",
    "value": "修改后的学习计划"
  }
}
```

这不需要重新描述整棵组件图。但 `updateDataModel` 是替换指定路径的值，不是任意深度合并；省略 `path` 或使用 `/` 会替换整个根数据模型。若代理用旧快照覆盖根对象，就可能影响用户刚输入的内容，应用需要验证这类并发更新的处理方式。

`updateComponents` 更新的则是组件定义。规范按完整定义替换处理，不能默认把它当成只修改若干属性的补丁。删除一个 surface 会移除其组件与数据；对仍存在的同一 ID 再次 `createSurface`，是状态完整性错误。

## 双向绑定是本地的，回传数据是另一件事

在上面的例子中，输入框和预览文字都绑定 `/form/title`。用户修改输入框时，渲染端立即更新本地数据，预览随之改变。双向绑定本身不要求每次敲键都请求 Agent。[2][4]

需要提交时，可以在按钮的 `action` 属性中配置下面这样的事件。这里是属性片段，不是完整消息：

```json
{
  "event": {
    "name": "confirm_learning_plan",
    "context": {"title": {"@path": "/form/title"}}
  }
}
```

事件触发时，渲染器解析路径，把当时的标题放进发送的上下文。若应用还配置了远程校验或其他函数逻辑，会另行产生调用，不能把“绑定在本地”理解成任何情况下都不联网。

`sendDataModel` 是另一个重要开关。默认关闭；开启后，在向创建该 surface 的 Agent 发送消息时，会通过传输元数据附上**整个 surface 的数据模型**。它不是只发送刚修改的字段，也不是自行产生每次键入的网络请求。

这直接影响隐私设计。后端可以在模型完成布局选择后，把数据库值绑定到界面，避免这些值参与模型生成；但若随后把完整数据模型放进模型上下文，这个好处就消失了。Agent 程序收到数据，与语言模型必须看到数据，仍需区分。

同理，`value: null` 在 `updateDataModel` 中表示删除该路径的键。1.0 要求 `value` 字段存在，省略它是格式错误。不能把缺字段、删除字段、函数尚未完成和函数失败当成同一种状态。

## Catalog 决定可用组件，也决定函数的边界

Catalog 是应用与 Agent 约定的组件和函数目录。它定义允许怎样描述组件，实际渲染和执行则由实现方提供。`catalogId` 是标识符，即使看起来像网址，也不意味着渲染器收到它就应该下载并执行对应代码。[2]

1.0 支持同一 surface 混用目录，组件可以用 `@catalogId` 指定来源。解析顺序是：先看组件的显式目录，再看 surface 的默认目录；两者都没有则报错，不能从能力声明里随便选一个作为默认。混用的目录还必须采用相同协议版本。

函数同样要经过运行时目录查找。`allowedCallers` 指定的是**谁能发起调用**，不是函数代码运行在哪一侧：

| 目录值 | 含义 |
|---|---|
| `rendererOnly` | 只允许渲染端发起，默认值 |
| `agentOnly` | 只允许 Agent 发起，不能当作普通界面动作或属性绑定使用 |
| `rendererOrAgent` | 两侧均可按协议发起 |

这些规则在目录定义里设置，不由模型在每次函数调用里自行改写。`requiresUserActivation` 还可以要求真实的用户动作上下文；按规范，这类函数限制为渲染端调用。它能限制一种调用方式，但不等于已经确认了某项业务操作的全部内容和权限。

因此，允许一个按钮显示，与允许按钮背后的业务修改，是两次不同判断。业务服务仍要检查调用身份、对象权限、当前状态和实际提交的内容。

## 双向 RPC 怎样与正在更新的界面配合

1.0 把两个调用方向明确写进消息名：[2]

| 发起方 | 请求 | 执行侧 | 响应 |
|---|---|---|---|
| Agent | `callRendererFunction` | 渲染端注册的函数 | `rendererFunctionResponse` |
| 渲染端 | `callAgentFunction` | Agent 侧函数 | `agentFunctionResponse` |

请求与响应通过 `functionCallId` 对应。返回结果携带值或错误；即使返回类型是 `void`，Agent 发起的渲染端调用完成后也应得到响应，不能把没有返回当成成功。

这里有一条容易遗漏的细则：顶层 `callRendererFunction` 的调用描述必须显式带 `catalogId`。不要把一般组件绑定可以使用 surface 默认目录的规则，直接套到这个消息上。

消息按到达顺序分派。位于函数调用之前的同步界面和数据更新先生效，但异步函数执行不会阻塞后续所有消息。因此，较早发起的请求不一定较早完成，应用应验证过期返回与较新输入同时出现时的行为。

规范也区分了几种失败：动态属性调用失败会解析为 `null` 并报表达式错误；校验规则失败按无效结果处理；动作管线失败会停止剩余步骤。**已经执行的步骤所产生的效果会保留，不会因为后一步失败就自动回滚。**

这意味着“用户点了一次按钮”未必对应一个天然的业务事务。若动作包含多次外部写入，业务层需要另行考虑重复请求、部分完成和补偿；界面也应把真实状态展示出来。

## 从 0.9 升级时，不能全局替换字段名

迁移指南中的几项变化值得直接核对：[3]

| 位置 | 1.0 的写法或规则 |
|---|---|
| 消息版本 | `"version": "1.0"` |
| 动态数据绑定 | `{"@path": "/form/title"}` |
| 动态函数引用 | 使用 `@call` |
| `updateDataModel` 消息参数 | 仍叫 `path`，不加 `@`；`value` 必填 |
| 列表模板 | `path` 与 `componentId` 保持原名 |
| 组件通用元数据 | `@catalogId`、`@metadata`、`@accessibility`、`@checks` |
| Surface 的默认目录 | 仍是 `createSurface.catalogId` |
| 界面主题 | `createSurface.theme` 移除，由宿主主题处理 |

普通业务对象中的 `path`、`call` 也不应被自动改成指令。保留的 `@` 命名空间、目录参数和消息参数各有含义，盲目字符串替换可能把原本的业务数据变成另一种指令。

1.0 的目录还应声明 `protocolVersion: "1.0"`。旧目录、消息格式、Core SDK、框架适配器和宿主是否支持相应版本，需要一起核对。协议更新，并不替每一层实现完成迁移。

## 格式正确以后，还要验证什么

JSON Schema 可以检查字段和结构，但仅靠它不能证明组件图中的 ID 引用、父子组合、函数注册与业务权限都正确。A2UI 为这些层次提供了不同规则，最终仍要由实际实现落实。

对一个学习计划表单，可以分别验证：初始数据是否正确显示，输入是否留在预期 surface，事件是否带回最新值，未注册函数是否被拒绝，远程校验失败如何呈现，以及中途断开后是否会重复产生业务动作。

无障碍能力也属于验收，而不是给对象加几个字段就结束。规范提供标签、描述和动态播报相关属性，渲染器需要把它们映射到所在平台的实际行为。相同协议可以保留共同交互意图，不保证不同平台每个像素都相同。

A2UI 1.0 最值得借用的设计，是让模型输出、界面状态、渲染组件和业务执行能够分别检查。模型有了更丰富的表达方式，应用仍保留对数据和动作的控制；这两部分同时成立，交互才可能既灵活又可靠。
