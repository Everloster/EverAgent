# 《Agent 演义》19｜建立自己的长期 Agent 工作台

## 概述

长期工作台的价值，是隔天、换设备、遇到中断之后仍能找到正确任务并继续。Orca 用项目、工作区、会话历史与远程入口保存开发现场；T3 用 environment、project、thread、状态管理与远程客户端承接日常工作。自动化应该在这些基本关系清楚之后加入。[^orca][^t3]

本篇不要求把所有设置都打开。先建立一条稳定路径：在哪里执行、怎样准备、如何记录未完工作、用什么完成交付，再把重复部分变成动作或定时任务。

**提炼句：** 长期工作台最有价值的状态，是你回来时知道哪里停了、接下来该做什么。

## 取景框 f(x)

**x｜问题：** 怎样让 Orca 或 T3 成为自己的日常开发工作台，而不是又一处堆积会话的地方？

**f｜取景框：** 从任务的进入、停留、恢复与退出观察产品，把配置服务于这些日常转折。

**f(x)｜判断变化：** 先形成少量能解释的工作约定，再扩大远程与自动化；保存很多历史不等于容易继续工作。

## 先确定自己的常见工作

列出最近常做的几类事情：独立功能、紧急 bug、PR 审查、只读研究。为它们选择默认现场和验收方式，之后再按例外调整。例如独立功能开 worktree，短调查留在现有现场，审查对准明确分支；不必所有任务采用同一个组织模式。

将准备、测试与开发服务做成可回查的项目动作。命令在正确目录运行，服务端口可辨认，失败时知道从哪里看日志。Card Gallery 只有 Test 与 Dev 两条命令，足够练习这套约定，不需要先建复杂配置系统。

## 在 Orca 留下能接着工作的现场

项目与工作区名称说明任务，终端名称说明用途。工作区注释记录当前进度和下一步，比如“API 已改；等待页面验证”，比“进行中”更能帮助明天的自己。

聊天与 CLI 各按个人习惯选择。离开前确认 Agent 是否仍在工作、是否等审批、开发服务是否需要保留。Sleep、自动 hibernation 和删除工作区有不同条件；保留可恢复现场，也要知道恢复的是哪些会话与进程。[^sleep]

会话历史用于找回讨论和继续原生任务。Orca 的 session search 是按 host 开启与建立索引的能力，不能假定所有主机的全部历史都已经可搜。[^history]

完成工作后，审查和交付，再决定保留、休眠或删除现场。工作区越积越多时，先按未完任务和已交付任务整理，不用目录存量来代替进度判断。

## 在 T3 把 thread 状态用清楚

一条 thread 对应一项能命名的工作。Settle 用于当前完成，Snooze 用于稍后处理，Archive 处理不再活跃的历史；它们对后续输入和委派的影响不同。已有 scheduled task 绑定的 thread 被 Archive 后，不能继续把它当有效投递目标。[^threads][^settings]

项目、environment 与 `t3.json` 的覆盖关系应可解释：项目覆盖优先于 environment，之后是仓库配置和默认。使用仓库配置保存可共享的动作与约定，执行主机的账户和个性化覆盖分别管理。[^config]

回来时先看待处理输入、运行状态和实际改动，再继续消息。需要换执行者时，检查关键合同与未完成工作；需要恢复文件时，检查同目录其他 thread，避免把旧 checkpoint 当成通用撤销按钮。

## 远程工作的重点是主机在线

手机、网页和桌面都可以成为进入任务的入口，但执行要有主机承担。先确认代码、Agent 登录、开发服务和任务属于哪台机器，再配置对应连接路线。两套产品都不能靠手机界面把已经关机的执行主机变成在线。[^remote]

T3 文档明确，关闭桌面最后一个窗口会停止本地服务器；需要无人值守时应使用相应 background service。Orca 远程与移动入口也依赖真实运行位置和连接条件。先验证一次短任务与断连后的状态，再安排长时间工作。[^background]

移动端适合查看进度、回应具体问题、检查有限改动。需要理解较大 diff 或跨仓整合时，保留明确待办，回桌面继续。接管之前确认任务，恢复连接之后确认服务器真实状态。

## 稳定之后再自动化

Orca Bots 面向持续任务、事件和外部应用，自动化有触发与投递目标；T3 scheduled tasks 面向定时／webhook 输入，Labs workflows 才进一步组织多阶段执行与人工等待。能力有范围和版本条件，先读对应指南。[^automation]

第一次自动化可以只生成一份容易检查的测试摘要。先确认触发、时区、执行主机与结果位置，再增加修改或发布步骤。人工流程尚不稳定时，定时运行只会更快地重复含糊输入。

## 用日常问题判断配置是否有效

| 转折 | 应该能回答的问题 |
|---|---|
| 开始新工作 | 在哪台主机、哪个分支，怎样准备并测试？ |
| 临时切任务 | 当前 Agent 是否仍在工作，另一项修改放哪里？ |
| 隔天回来 | 已完成什么、还缺什么，当前文件是否变化？ |
| 执行者或连接中断 | 最后确认到哪一步，有没有仍活跃的资源？ |
| 准备交付 | 审查与测试针对哪版代码，意见是否解决？ |
| 清理历史 | 哪些已交付，哪些仍绑定任务或需要恢复？ |

Usage、缓存读与 API-equivalent cost 可以帮助解释消耗，不能代替上述答案，也不能直接当作订阅账单。选择长期工作台时，先试这些转折是否顺手，再评估自动化与统计功能的收益。费用、缓存与推理的技术条件另见附录 B。
