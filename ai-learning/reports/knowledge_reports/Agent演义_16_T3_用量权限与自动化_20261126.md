# 《Agent 演义》16｜T3：用量、权限、自动化与日常维护

## 概述

长期使用 T3，需要管理账户与 provider、权限、用量、定时任务和环境维护。Usage 显示 token、估算费用与额度；scheduled task 和 Labs workflow 则解决不同程度的自动化。[^usage][^settings][^workflow]

专业用户应先把稳定的人工流程整理成项目动作，再决定哪些步骤可定时执行，哪些需要等待人。额度和缓存指标帮助观察使用，不替代真实任务验收或订阅账单。

**提炼句：** 长期工作台要有可解释的默认值，也要有能恢复的使用习惯。

## 取景框 f(x)

**x｜问题：** 怎样让 T3 长期服务高频开发，而不积累不明配置、额度和自动化任务？

**f｜取景框：** 把个人使用分成执行配置、观察与重复工作三部分。

**f(x)｜判断变化：** 先建立清楚的默认与维护入口，再扩大自动化；估算、额度和真正交付分别判断。

## 先明确账户与权限

在目标 environment 的 Providers 中管理接入。多个账户或实例应有容易辨认的用途；模型选择应确认对应 provider、账户与可用模型。

thread 的权限模式决定哪些操作需要审批。计划模式、对话方式和权限不是同一个选择；provider 实际支持的模式也不同。先选择符合当前工作需要的权限，再根据运行中的真实请求处理。[^permissions]

## Usage 看什么

从 Usage 查看 token、cost 和 limits，先选择 environment、时间范围与模型。API-equivalent cost 是估算价值，不等于订阅账单；有些 provider 上报的是未细分费用，模型映射和价格配置也影响显示。[^usage]

| 指标 | 能帮助判断什么 | 不宜直接推断什么 |
|---|---|---|
| token 使用 | 哪些工作消耗了较多上下文与输出 | 工作质量或订阅实际费用 |
| 缓存指标 | 输入复用的观察信号 | 所有切换都能保持缓存 |
| 额度／重置时间 | 何时可继续与使用安排 | API-key 账户一定有订阅额度 |
| API-equivalent cost | 使用量的估算比较 | 当前实际账单 |

额度到达上限时，使用产品提供的 Resume、Resume at reset 或 Snooze 等入口，或确认交接范围后选择其他执行者。切换是否更省、是否更好，需要同一任务和实际计费数据，本卷没有这项排名。

## 重复工作先变成明确动作

项目 Test、Dev 与清理动作适合可重复的本地命令。定时检查文档或失败测试，可以建立 scheduled task；先决定每次新 thread、同 thread 续接，还是同 thread 的新 session。

绑定已有 thread 的任务，应确认它没有被 Archive。定时任务的 schedule、time zone、destination 和结果范围都要检查；创建成功不表示执行主机离线后仍会完成。

Card Gallery 的简单自动化可以整理测试结果与待处理项。最初选择容易复查的输出，把需要发布或业务决定的步骤交给人。

## Scheduled task 与 Labs workflow

单一 prompt 的定时或 webhook 工作适合 scheduled task；多阶段、包含代码步骤与人工等待的流程才考虑 workflow。Workflow 是 Labs 功能，需要在执行服务器上启用，并遵守版本与恢复条件。[^workflow]

```text
自拟流程：检查输入 → 验证项目 → Agent 提出修订 → 人工审查 → 交付
```

每个阶段要有输入、输出与失败处理。先明确流程，再写自动化；不把一个很长的提示当成已经可靠的多阶段系统。

## 配置与维护怎样留得清楚

查看 Settings 的作用范围：device、environment、project 与仓库配置有各自优先级。做改变后记下真正需要长期保留的约定，避免一份全局设置解释不了所有项目。

清理 worktree、captures、logs 与历史资料时先看保护规则；服务重启、更新 provider 和恢复会话也不是同一个动作。遇到问题，从对应 environment、诊断和版本开始定位，不要在多个主机同时试改配置。[^diagnostics]
