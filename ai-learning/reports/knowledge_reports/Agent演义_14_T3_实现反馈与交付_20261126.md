# 《Agent 演义》14｜T3：从实现到反馈与交付

## 概述

T3 把对话、工作文件、diff、浏览器预览和 Git／PR 放在一条工作主线附近。专业用户可以在同一 thread 中看实现、给定位明确的反馈，再对当前版本完成交付。[^diffs][^source]

要用好这组功能，先分清每轮改动、当前未提交改动和整个分支差异。前端预览与测试又需要对准同一现场；发出一条批注只是开始修订，并不等于问题已经解决。

**提炼句：** 从实现到交付，需要让反馈、验证和代码版本始终对应。

## 取景框 f(x)

**x｜问题：** 怎样在 T3 中完成一轮实现、反馈、修订与交付？

**f｜取景框：** 用当前变更范围组织审查，再用同一版文件组织验证。

**f(x)｜判断变化：** 先选择合适的 diff 和预览现场，再决定反馈对象、测试与交付动作。

## 先打开对的差异

Diff pane 的 source picker 可以选择 Turn changes、Uncommitted、Changes 和 Commits。它们分别帮助查看某轮工作、当前未提交修改、整个分支和具体提交。多仓项目还要选择 repository。[^diffs]

在 Card Gallery 中，只看某轮 UI 修改可能遗漏 API 合同变化；检查完整功能时应再看分支层面的改动。拉取或整合带来的其他内容，也不能自然算作该轮 Agent 的独立产出。

## 把批注收集成一轮反馈

在 diff 或 workspace file 选择相关行，写明问题与期望。T3 会把批注放进 composer 的上下文 chips，方便跨文件收集后一起发送。

```text
前端改变 tag 后仍使用旧 page，API 测试却假定新筛选从 page=1 开始。
请统一这项规则，保留 q，并在页面操作与 API 用例中分别验证。
```

这条自拟反馈把文件关系和验收条件连起来。回复“已修改”后，仍要检查实际 diff、测试和页面行为。

## 文件和终端怎样配合

从 Agent 的文件链接、文件选择器或 diff 打开代码，放在对话旁边查看或编辑。外部文件、远程文件和可写范围有不同条件，不要把“能打开”当成“可随意修改”。

测试与开发服务在对应环境的终端运行。确认 cwd，再执行项目动作；检查服务端口是否来自当前 thread 的工作区。终端输出、文件内容与 diff 应解释同一版代码。

## 在浏览器里复查界面

从右侧 Browser 或 Servers 列表打开开发服务，用 element picker 或区域注释带入对象，再说明状态与期望。T3 还提供录制、视口和 browser profile 设置。[^browser]

本卷自拟页面已经在 Orca 浏览器核对搜索与标签组合；这不是 T3 preview 的实测结果。T3 的预览入口与平台条件来自用户指南：桌面本地、网页／手机流式页面和远程 preview tunnel 不应混为一类。

| 你要验收什么 | 查看方式 | 需要对照 |
|---|---|---|
| 接口合同 | API 测试、代码与错误 | 查询、标签、分页、非法输入 |
| 页面状态 | 实际操作与浏览器反馈 | 输入是否保留，是否显示旧结果 |
| 改动范围 | 分支 diff 与文件列表 | 是否包含无关修改 |
| 修订意见 | 批注、实际变更和测试 | 意见是否被真正解决 |

## Git 与 PR 怎样收尾

核对暂存内容和提交说明，再推送到正确仓与分支。创建 PR 时确认 base branch、真实变更和验证说明。Git 凭据与托管服务 API 登录各有职责，一个可用不保证另一个可用。[^source]

PR 页面可以查看 diff、comments、checks 和 commits。新的提交到达后先 Load new commits，再提交审查或决定合并，避免基于旧 head 作判断。

Review guides 是可选的 beta 功能：帮助按顺序理解 PR，不替代你对重要代码和证据的审查。启用和生成会使用相应 Agent，本卷没有执行这类模型调用。

## PR watching 适合什么场景

已有 PR 需要等检查或后续意见时，可以用产品的 watch／babysit 功能持续跟踪。先明确负责的 thread、等待对象和动作范围；子 Agent 与父 thread 对这项能力有不同限制。[^source]

监控事件、修复代码和发布修改是不同阶段。不能只因 watch 已开启就认定它会替你完成所有决策。最终验收仍围绕最新代码、检查与未解决意见。
