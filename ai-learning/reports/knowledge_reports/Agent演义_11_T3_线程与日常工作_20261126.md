# 《Agent 演义》11｜T3：把线程用成日常工作单元

## 概述

T3 的 thread 可以承接一项工作的澄清、实现、审查与后续修订。composer 提供附件、引用、草稿、Queue／Steer 等入口；侧栏的 Settle、Snooze 和 Archive 用于不同阶段的整理。[^threads][^composer]

专业用户最需要建立的是任务边界和输入习惯：一项工作一条主线，临时问题放到侧聊，需要独立结果时另开任务。功能很多，但它们应减少找材料和重复解释的时间。

**提炼句：** 线程整理的是工作主线，输入工具整理的是下一步要交代的材料。

## 取景框 f(x)

**x｜问题：** 高密度使用 T3 时，怎样让线程保持可继续、可查找、可整理？

**f｜取景框：** 按任务生命周期组织线程，再选择最合适的输入与收尾方式。

**f(x)｜判断变化：** 从“哪里有空就发一句”转向明确主线、阶段与相关材料，减少无关历史混入。

## 给一条 thread 一个明确任务

Card Gallery 的搜索功能可以在同一 thread 中讨论合同、实现、验证和修订。题目应说明工作目标，如“搜索与标签组合”，而不是只写一个模型名字。

独立 UI 实验、另一个 bug 或审查意见，可以新开 thread；需要独立改动时同时选 worktree。可以固定常用任务，按项目过滤，再用命令面板搜索标题、分支、PR 和对话内容。[^threads]

## composer 中哪些材料值得带入

| 你要交代什么 | 合适的入口 | 需要补充的判断 |
|---|---|---|
| 另一条工作主线 | thread 引用／上下文 chip | 对方需要哪一段结果 |
| 原始需求或 PR | 链接与对应上下文 | 当前目标与待处理范围 |
| 代码或日志片段 | 文件、引用或附件 | 行号、错误和复现条件 |
| 界面问题 | 图片或浏览器元素 | 页面状态与期望行为 |
| 常用工作指令 | skills／命令与自拟要求 | 适用任务和输入边界 |

引用和附件减少复制，但仍需说明用途。仅附一段长日志，不会自然告诉 Agent 哪个失败最重要。

大段粘贴可能转为文件附件；附件上传到实际 environment，需要完成后再发送。模型和 provider 对输入的支持仍有区别。[^composer]

## Queue 与 Steer 怎样选

要改变当前实现目标，用受支持的 Steer；下一阶段任务用 Queue。默认 Follow-up behavior 在 Chat 设置中，快捷键可以选择相反动作，移动端也有相应发送入口。

例如，“保持查询词并重置分页”是当前功能的补充；“本轮完成后检查移动端布局”是下一阶段。把独立需求全放进当前 turn，会让范围难以验收。

斜杠命令、goal 与普通消息也有不同处理方式，按文档和当前 provider 的支持选择，不因输入框允许文字就认定它可以立即作用于当前执行。

## 草稿、旧提示与侧聊

Recall 适合复用以前发送的文字；Prompt stash 适合暂存当前草稿和材料。恢复草稿后重新核对附件、引用和所属 environment，不把一段旧提示当成完整工作状态。

临时问题可使用 `/side` 或 `/btw` 的侧聊入口。它适合询问正在工作的主线程相关问题；有价值的结论可 Add to chat 或引用回主线。侧聊与主任务可能共享目录和上下文，不能把侧聊自动当成隔离的实现任务。[^threads]

## 任务结束时，三个整理动作别混用

| 动作 | 适合时机 | 关键影响 |
|---|---|---|
| Settle | 当前做完，未来可能继续 | 仍可找回，新消息可重新激活 |
| Snooze | 暂时不想看，稍后处理 | 可以继续后台工作，按条件提前唤醒 |
| Archive | 暂时不接受新工作 | 离开常用侧栏与搜索，恢复前拒绝新消息 |

有定时任务绑定的 thread 不宜仅为“清爽”而 Archive，否则后续运行可能失败。Settle 不等于删除 worktree，也不等于模型进程仍在运行。[^threads]

## 长线程怎样保持可用

阶段性说明已决定什么、当前文件在哪里、下一步做什么。若采用 Edit from here，先分清只回退对话还是连文件一起恢复；后者有工作区隔离和 provider 条件。

更换执行者时，重申最重要的合同，而不是只发“继续”。需要新起点时，再决定压缩、清理或新开 thread。技术细节可以查附录，日常工作先保证这条主线仍然解释当前项目。
