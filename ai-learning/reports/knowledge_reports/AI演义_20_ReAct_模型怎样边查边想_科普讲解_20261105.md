# 《AI演义》20｜ReAct：模型怎样边查边想，把任务做下去？

[返回原报告第 20 节](../AI演义_笔记分析与项目整合报告.md#paper-react) · [上一节：CoT](AI演义_19_CoT_中间步骤怎样帮助模型作答_科普讲解_20261105.md) · [下一节：Tülu 3](../AI演义_笔记分析与项目整合报告.md#paper-tulu3)

上一节的苹果题，解题所需的信息都在题目里。换成下面这个问题，光把步骤写长就不够了：

> Apple Remote 最初是为控制哪个程序设计的？除了这个遥控器，还有什么设备能控制那个程序？

你得先查清“那个程序”是谁，再找到它支持的另一种控制方式。如果第一步把程序认错了，后面推得再顺，也会答错。

**ReAct 研究的，就是让模型在推理过程中采取行动，取得新的观察，再用观察决定下一步。** 名字来自 Reasoning 与 Acting，即推理和行动。2022 年，姚顺雨（Shunyu Yao）、Jeffrey Zhao、Karthik Narasimhan、Yuan Cao 等来自 Princeton 与 Google Research 的作者，把这件事做成了一套可比较、可检查的提示方法。[^paper]

下面沿着论文里的 Apple Remote 案例走一遍，再看它在什么条件下有效、为什么仍会失败。案例和成绩均来自原论文，本篇没有重新运行当年的模型实验。

<a id="why-interaction"></a>

## 1. 会逐步推理之后，还缺了什么？

CoT 可以帮模型拆解问题，却不自动给它补充缺失的事实。在论文 Figure 1 的展示中，只做 CoT 的模型把 Apple Remote 最初控制的对象说成 Apple TV，随后沿着这个错误前提，推到 iPhone、iPad 和 iPod Touch。句子连贯，起点却错了。[^example]

另一条已有路线，是让模型直接给出操作：搜索、打开页面、再搜索。论文把不显式写推理的对照称为 **Act-only，仅行动**。它也能拿到外部返回；困难在于，拿到信息之后，模型是否还记得要解决什么、哪些子问题已经解决。

同一幅图里的 Act-only 完成了几次相关查询，最后却输出 `Finish[yes]`。用户问的是一种设备，“yes”没有回答问题。这个例子说明了作者想拆开的两种困难：**事实可能缺在模型之外，任务的组织也可能断在多步过程之中。**

ReAct 把两条路线接起来：用推理确定查询目标，用查询获得新材料，再据此修正推理。这是它的研究问题；一个展示例能帮助理解问题，却不能证明每次加入推理都会更好。

<a id="apple-remote-walkthrough"></a>

## 2. 跟着一次查询，看反馈怎样改变下一步

论文使用了一个简化的 Wikipedia 接口。先把它看作能查词条的工具，暂时不用关心 API 的写法。下面是 Figure 1 的中文转述，保留关键动作；原图省略的网页返回不在这里补写。[^example]

**第一步：先找程序，别急着猜设备。**

模型写下当前目标：查 Apple Remote，找到它最初要控制的程序。接着输出 `Search[Apple Remote]`。工具执行后，返回的文字提到 **Front Row 媒体中心程序**。

这时模型获得了一个以前未确定的中间结果：“要查的是 Front Row。”它把这个结果放进下一步推理，将任务改成“寻找 Front Row 的其它控制方式”。

**第二步：查不到，也是一种有用的返回。**

模型发出 `Search[Front Row]`。工具没有找到对应词条，而是返回相近名字，包括 Front Row Seat to Earth、Front Row Motorsports 和 **Front Row (software)**。

这次操作没有直接带来答案，但它缩小了问题：目标是软件，查询词需要更具体。模型于是改查 `Search[Front Row (software)]`。

这里发生的变化很关键。最初的计划只是“去查 Front Row”；**真正收到的查找失败和候选词条，使下一次动作变了。** 如果模型从未收到这一返回，而是自己写一句“我查到了一些相似结果”，那只是生成了文字。

**第三步：把信息接回用户的问题。**

新查询返回 Front Row 软件的介绍。原图在这段观察中用了省略号，随后展示的模型推理指出：这个程序可由 Apple Remote 或键盘功能键控制。因此，排除题目已经给出的遥控器，答案是**键盘功能键**。

模型最后输出 `Finish[keyboard function keys]`，结束任务。这里是在复述论文中的历史问答过程，并非核验今天某款 Apple 产品的操作说明。

把全过程收拢起来，就是：

> 先确定要查什么 → 实际查询 → 读回结果或错误 → 调整目标与查询 → 组织答案。

推理为行动提供目的；观察则给推理补充信息、暴露障碍。这两个方向都存在，才是论文所说的“协同”。

<a id="model-tool-observation"></a>

## 3. 谁在想，谁在做，谁在告诉它结果？

读 Agent 的记录时，最容易把三类文字混为一谈。ReAct 对它们的区分很具体：[^mechanism]

| 记录 | 从哪里来 | 对当前任务的作用 |
|---|---|---|
| Thought，推理 | 模型生成 | 拆问题、整理已知信息、决定下一步 |
| Action，动作 | 模型生成操作请求，外部程序执行 | 查询信息或操作环境 |
| Observation，观察 | 工具或环境返回 | 告诉模型这次操作得到什么 |

“我需要查 Front Row”是一段推理，不会自行访问网页。`Search[Front Row]` 是要执行的请求；真正的返回必须等工具执行后，才能作为观察接入上下文。

模型随后看到的上下文，也在逐步变化：原问题、前面的推理和动作、已经收到的观察，都能影响它接下来生成什么。**这份任务过程中的记录，起到了短期工作记忆的作用。** 它不意味着模型的参数已经记住 Front Row，更不意味着另开一个会话就能自动继续。

原论文主要采用少样本提示：人先提供若干“如何完成任务”的示范轨迹，里面有推理、动作和对应观察；模型面对新任务时，再生成自己的推理与动作。这里的“示范”在输入里，这次交互并不更新模型参数。

还有一个容易被流程图藏掉的区别：**写推理通常只改变上下文；执行动作才会访问或改变外部环境。** 查 Wikipedia 是获取信息，文字游戏中的“拿起物品”则会改变游戏状态。不是所有 Action 都会修改现实世界，观察结果也不一定天然真实、完整或有用。

<a id="action-space-and-rhythm"></a>

## 4. 它能做什么，取决于给它什么工具

在 Apple Remote 这类知识问答中，作者只给了三个动作：[^api]

- `search[entity]`：找到对应 Wikipedia 词条时，返回开头 5 句话；找不到时，给出最多 5 个相近词条。
- `lookup[string]`：在当前词条中，逐次找出含指定字符串的句子，类似页面内查找。
- `finish[answer]`：提交答案并结束。

这比“拥有整个互联网”窄得多。词条名不准确、相关信息不在返回的几句话里，都可能导致失败。作者有意使用这样简单的接口，观察模型能否通过明确的推理去组织检索。

换一个环境，动作也会变。文字家务任务中的动作是走到柜子旁、打开抽屉、拿起物品；购物环境中的动作是搜索商品、查看选项、选择规格。ReAct 提供的是组合这些动作与推理的方式，具体能做什么仍由环境接口决定。

**它也不要求每做一步都写一大段思考。** 论文在问答任务中较密集地交替推理和操作；在步骤较多的决策任务中，则让模型只在相关位置写推理。例如，先决定该去哪里找，再连续查看几处地方；找到以后，更新子目标。[^sparse]

因此，学 ReAct 不必把固定的 Thought—Action—Observation 三行当成咒语。值得保留的是：下一步操作有依据，新返回能够进入后续判断，任务进度不会只留在一句开场计划里。

<a id="knowledge-results"></a>

## 5. 加上查询以后，回答一定更准吗？

不一定。论文 Table 1 恰好展示了方向不同的结果。下面都来自 **PaLM 540B，也就是 5,400 亿参数模型**的提示实验：[^qa-results]

| 方法 | HotpotQA：答案精确匹配率 | FEVER：判断准确率 |
|---|---:|---:|
| 普通提示 | 28.7% | 57.1% |
| CoT，仅推理 | 29.4% | 56.3% |
| Act，仅行动 | 25.7% | 58.9% |
| ReAct，推理加行动 | 27.4% | 60.9% |

**HotpotQA** 通常需要把多个 Wikipedia 段落的信息接起来；精确匹配率看最后答案是否匹配参考答案。**FEVER** 给出一项陈述，要判断资料支持它、反驳它，还是信息不足。

两组都采用“只给问题或陈述”的设置，模型没有预先获得支持段落。作者分别给 HotpotQA 6 个、FEVER 3 个示范。

ReAct 在两组中都超过 Act-only，但与 CoT 比较时，FEVER 提高了 **4.6 个百分点**，HotpotQA 反而低了 **2.0 个百分点**。外部信息有帮助，却也带来了搜索失败、信息筛选和多步组织的负担。

作者进一步把 ReAct 与 **CoT-SC，自洽投票**组合。后者对同一问题采样多条 CoT，再选多数答案。两种切换方式各有用途：

- 先用 ReAct，在规定步数内答不出来，再退回 CoT-SC；这组在 HotpotQA 达到 35.1%。
- 先用 CoT-SC，若采样答案不够一致，再交给 ReAct；这组在 FEVER 达到 64.6%。

这说明两种方法可以互补，但组合增加了采样或查询，不能把它的成绩当成一次普通 ReAct 调用的成绩。单独 CoT-SC 的两项成绩为 33.4% 和 60.4%；上述组合的收益也应和它比较。

### 比较这些成绩时，还要看什么？

Table 1 的 CoT-SC 使用 21 条采样轨迹，温度为 0.7。ReAct 转 CoT-SC 的步数上限分别为 HotpotQA 7 步、FEVER 5 步；反向切换时，若 n 条样本中多数答案的出现次数不足 n/2，才调用 ReAct。

同表列出的监督学习系统成绩为 67.5% 和 89.5%，明显高于这些提示方法。但它们使用了专门的训练条件，不能拿来证明在同一资源预算下某一种机制一定更优。

Table 1 及相邻方法段没有明确列出这一组实际评估题数。附录 A.1 明确写出的 500 道 HotpotQA 题，属于另一组 PaLM／GPT-3 对照；官方代码 README 也另列 500 道随机验证题的结果。不能把这些数字拼成同一张实验表。本文主要采用 2023 年 3 月的论文 v3；首版日期为 2022 年 10 月 6 日。[^version]

<a id="failures"></a>

## 6. 查过资料，为什么还是会错？

回到 Apple Remote：查不到 Front Row 后改用更精确的词条名，是一次成功恢复。但同样的接口不保证模型总能想出下一步。

作者人工抽查了 HotpotQA 中 **200 条轨迹**：ReAct 和 CoT 各取 50 条最终答案正确的、50 条错误的。这不是随机抽取全部请求后得到的线上故障率，而是刻意把成功与失败分开观察。[^error-analysis]

在被抽查的 ReAct 错答组中，论文将 47% 归为推理错误，23% 归为搜索结果问题；前一类也包括无法跳出重复思考、重复操作。模型会查资料，不代表它会恢复一个失败的计划。

最值得警惕的，还有**答案碰巧对了，过程却错了**。附录 E.1 给了一个例子：题目问桌游 San Marco 和 About Time 哪个先发布。ReAct 查到了威尼斯的 San Marco 地区，又把 About Time 当成电影，最后输出 San Marco。论文把它归为“最终匹配，但事实或推理有问题”。两个名称都真实存在，查到的却不是题目里的对象。

这个反例补上了 Apple Remote 成功案例的另一面：**外部返回能帮模型纠错，模型也可能把返回认错、用错。** 有查询记录，只能说明发生了查询；还要检查查到的是不是目标、证据是否支持结论。

论文的错误分类表在 ReAct 错答样本中没有标出幻觉，但成功样本里仍有 6% 被归为事实或推理有问题。这个“错答组中为零”绝不能改写成“ReAct 消除了幻觉”。作者还指出，有些参考答案本身已经过时，因此答案匹配率与现实中的正确性也不总是一回事。[^error-analysis]

<a id="decision-making"></a>

## 7. 从查答案，到把一件事做完

查询例子里的观察，主要用来补知识。论文接着问：同样的组织方式，能否帮助模型在一个环境中连续行动，直到完成目标？[^decision-results]

在 **ALFWorld** 文字家务环境里，模型要完成寻找、移动、清洗或冷却物品等任务。它收到的是房间和物品的文字描述，发出的也是文字动作。这组实验不是让机器人在真实房屋里运动。

这样的任务需要维护“做到哪一步”：如果还没拿到物品，就不能直接当成已经拿到；如果已经拿到了，下一步应转向放置或处理。推理在这里承担的是进度管理和子目标切换，不只是解释最后答案。

Figure 1 的胡椒瓶任务很直观：Act-only 对着没有胡椒瓶的水槽重复“拿起”，连续得到“什么也没发生”；ReAct 先按常识寻找可能的位置，找到后才把子目标切到放置，并打开抽屉完成任务。这里展示的是任务组织的差别，不是凭这一例就认定每次都会成功。

作者在 **134 个未见过的测试游戏**上评估，每类任务使用 2 条示范，并比较 6 组提示：

| 设置 | 总体任务成功率 |
|---|---:|
| ReAct，6 组提示的平均 | 57% |
| ReAct，6 组中最佳 | 71% |
| Act-only，6 组中最佳 | 45% |
| BUTLER，原基线 8 次试验中最佳 | 37% |

论文摘要所说的 **提高 34 个百分点**，对应的是 71% 与 37% 的最佳结果差，不是平均成功率从 37% 提高到 71%。BUTLER 是经过模仿学习训练的基线，使用的训练、搜索和提示条件也与 ReAct 不同。按正文描述，Act-only 是从同一批轨迹删掉推理得到的，更直接针对“加入推理有没有帮助”；不过附录提示存在一处标注不一致，不能据此认为所有输入细节都已经核实无误。[^prompt-caveat]

作者还把推理改写成一种较受限制、密集的外部状态反馈，称为 ReAct-IM。这组最佳成功率为 53%，低于 ReAct 的 71%。这项消融支持的是：在这些任务里，常识判断、完成状态检查和下一步子目标有价值。它不是对另一整套机器人系统做了完整复现比较。[^im-ablation]

附录中的失败轨迹进一步说明了这个问题：任务要求放好一把清洗过的刀，ReAct-IM 找到刀后直接放置，遗漏清洗，还继续重复放置。作者提出的一种解释是，“寻找一把干净的刀”这句推理，让模型误把目标状态当成了已经达到的状态。观察会返回，但错误的进度判断仍可能持续下去。

**WebShop** 则提供带真实商品资料的模拟购物网站。作者在 500 条测试指令上，检查选中的商品是否满足全部要求：ReAct 成功率为 **40.0%**，Act-only 为 30.1%，模仿学习基线为 29.1%，加入强化学习的基线为 28.7%；人类专家为 59.6%。

它对任务的帮助，可以在附录 Table 10 中看到：用户指定了口味和 16 包的规格，Act-only 直接购买了另一种口味的 100 包商品；ReAct 则对照条件检查商品选项，选择相应口味与 16 包规格。重要的是把用户条件与页面内容接起来，而不是只找到一个看起来相关的商品。

这几行也说明“有进展”与“可以独立放心办事”之间仍有距离。论文中的购买不会形成真实订单；40.0% 是完成全部条件的成功率，也不能和同表另一个“平均满足多少属性”的分数混用。

<a id="training-and-human-correction"></a>

## 8. 它是在学会使用工具，还是只在照示范做？

主要提示实验中，模型的参数没有改变。它利用预训练中已经获得的能力，再从当前输入的少量示范里学习这次任务的格式和做法。

这对模型能力有要求。论文 Figure 3 中，8B、62B 的 PaLM 仅靠提示时，ReAct 在比较的四种方法中表现最差；同时学着推理和行动，并不轻松。作者随后用 **3,000 条最终答案正确的生成轨迹**微调较小模型，ReAct 才成为图中最好的训练格式。[^finetuning]

这里又回到了前几节不断出现的区别：**上下文里给示范，和拿数据更新参数，是两个不同动作。** 一条已完成的交互轨迹可以成为训练数据；但“执行一次搜索，收到一次返回”本身不等于做了一次强化学习更新。

这组微调还是初步实验，几种方法的训练步数不同，不能当成严格等计算预算的全面胜负结论。它更具体地说明：模型可以通过训练改善利用交互过程的能力，提示窗口和少量示范也确实有限。

论文还展示了一种直接干预过程的方法。在 ALFWorld 的失败案例里，模型臆断另一把钥匙链也在刚才的抽屉中。人删除这句错误推理，并在后面补入寻找其它位置的提示，之后的行动便发生了变化，任务最终完成。[^human-edit]

这不是修改权重，而是修改模型接下来读到的上下文。案例说明可见过程可以成为一个干预入口；它尚未证明“编辑两句话就总能修好 Agent”，更没有证明文字完整揭示了模型内部的计算。

<a id="history-and-reading"></a>

## 9. 放回《AI演义》，这一步改变了什么？

讲义把本节概括为“Agent 从理论到落地”。这个标题抓住了动作与反馈的重要性，但需要放回研究脉络理解：**Agent 概念和语言模型的工具交互都早于 ReAct。** 论文自己讨论了 WebGPT、SayCan、Inner Monologue 等前驱，并明确承接既有闭环交互工作。ReAct 的贡献，是把更灵活的语言推理与行动组织到同一过程中，系统比较组合后的效果。[^history]

作者与组织也能帮助理解研究条件。论文首页注明，姚顺雨在 Google 实习期间完成这项工作，作者同时来自 Princeton 与 Google Research。这里的问题横跨语言推理和环境交互；把人物记成“某个大产品出现之后才开始研究 Agent”，反而会遮住论文自己的时间线。

播客在讲解循环之后，还留下了三段与学习有关的讨论。首先是**怎样选问题**：嘉宾把 CoT、ReAct 放在 ChatGPT 热潮之前，强调研究者有时要发现尚未广受关注的缺口。他把这些直观的想法与公式较多的强化学习工作放在一起比较，是想说明问题定义也有价值，不是在否定复杂研究。本篇没有核查引用量增长，不能用这段评价证明哪类研究必然影响更大。[^lecture]

其次是**怎样持续跟上技术**。主持人问研究者在什么年龄容易出成果，嘉宾先说没有统一答案，既谈年轻研究者少一些历史包袱，也举资深研究者持续学习的反例。讨论随后转到管理岗位：仍然亲手写代码，与把商业流程、人员和指标管得更细，是不同的参与方式。这些属于嘉宾的观察，不是年龄或不同地区工程文化的统计结论。[^lecture]

最后一个例子更具体：嘉宾自己写新产品的前端时，脑中的构想可以直接变成实现；交给别人做，则通常要先写产品需求文档（PRD）、画原型，再让对方理解。他用“压缩—解压”描述这段传递可能损失信息的过程，进而解释为什么偏好更宽的能力跨度、为什么鼓励同事读论文。这个经验不意味着所有团队都应取消文档或分工。它提醒读者，**理解一个想法与把它做出来之间，还有需要亲手解决的问题。**[^lecture]

回到 ReAct，那个值得保留的研究问题仍然很具体：会生成答案和动作以后，怎样让后一次行动真正利用前一次反馈？

沿前后几节看，可以把职责分开：

| 工作 | 主要改变什么 |
|---|---|
| InstructGPT | 用示范和偏好反馈训练回答行为 |
| CoT | 用提示与中间步骤组织解题 |
| ReAct | 在解题中执行动作、取得观察并调整过程 |
| 下一节 Tülu 3 | 进一步把后训练数据、方法和评价整理成可检查的配方 |

这是一条理解问题的阅读路线，不是说后一篇从前一篇的模型权重继续训练。训练、推理组织、环境交互各有作用，可以配合，却不能彼此替代。

<a id="practical-implications"></a>

## 10. 读完之后，怎样判断一个 Agent 是否真的在推进任务？

**[推测／实践建议]** 把论文的成败经验用于今天的工具型任务，可以先检查三个具体问题：

1. **它缺哪条信息？** 像 Apple Remote 案例那样，查询应对应一个尚未解决的子问题。
2. **新返回改变了什么？** 查找失败之后是否换了准确的词条，还是重复同一句计划、同一个动作？
3. **它凭什么结束？** 最终回答是否利用了实际取得的相关证据，实际操作的完成状态是否经过确认？

这比查看记录里有没有“Thought”一词更有辨别力。也要记住，ReAct 原论文没有提供一套完整的权限管理、持久记忆或跨设备会话系统；工具能访问什么、状态保存在哪里、何时应停止，仍是实际系统要解决的问题。

若要进一步验证效果，可以固定同一批小任务和工具，比较 Act-only 与 ReAct：除了成功率，也记录请求次数、重复动作和错误后的恢复情况。这里是一项待做的实验建议，不是本篇已经测得的项目收益。

<a id="questions"></a>

## 思考与追问

1. **已经理解了什么？** 模型写出的计划、工具实际执行的动作和真实返回，是三种不同东西。下一步能利用新返回，才可能根据环境修正过程。
2. **还需要弄清什么？** 失败究竟来自模型不会规划、工具没返回有效信息，还是评价答案已经过时？这些原因不能只看最终成功率来区分。
3. **下一步读什么？** 接着读 [Tülu 3 原章节](../AI演义_笔记分析与项目整合报告.md#paper-tulu3)，看示范、偏好和可验证反馈怎样进入训练配方；若关注本节的交互本身，可从 [作者代码仓库](https://github.com/ysymyth/ReAct)的任务 notebook 开始，但要重新核对今天的模型与接口条件。
