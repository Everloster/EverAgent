# 《Agent 演义》03｜Orca：在聊天与终端之间工作

## 概述

Orca 的 Chat UI 与原始 CLI 服务于不同的使用习惯。Chat 更方便查看结构化回复、工具、模型选项与可视化内容；CLI 保留 Agent 自己的交互方式。选择还受 Agent、机器和会话资格条件影响。[^chat]

对高频用户，更关键的是会话怎样继续：补要求时选择现在处理还是稍后处理，旧任务怎样找回，切换界面后如何确认仍在正确的目录。把这些习惯建立好，比频繁新建会话更有用。

**提炼句：** 会话用得顺手，靠的是明确的任务边界和恢复入口。

## 取景框 f(x)

**x｜问题：** 什么工作适合 Chat，什么工作适合 CLI，怎样在两者之间继续已有任务？

**f｜取景框：** 按反馈形式、交互习惯和执行位置选择 surface，再管理会话生命周期。

**f(x)｜判断变化：** 不把换界面当成换任务；继续工作前核对目录、当前阶段和需要补充的要求。

## 先选一种你愿意长期用的输入方式

需要读长回复、查看工具卡片、附图和选择模型时，Chat UI 更集中。习惯 Agent 的 TUI 快捷键、想直接看它的原生输出时，CLI 更自然。

在 `Settings → Chat UI` 或 `Settings → Agents` 中选择对应 Agent 的 Chat／CLI 偏好。已有会话通常保留原来的 surface；设置更改不是把所有已打开终端立即转换成聊天。文档还区分本地原生聊天、配对服务器和 WSL／SSH 的 terminal-backed 情况。[^chat]

选择只解决“怎么与执行者交互”。任务所在的工作区、模型和账户仍要确认。

## 给正在工作的 Agent 补要求

Card Gallery 的实现还在进行，你想补“改变标签后回到第一页”。若它改变当前实现目标，运行中追加可能合适；若是“这一轮结束后再做移动布局”，排队更容易保持范围。

在发送前读清楚当前发送行为和可用控制。原生 Agent 支持、权限和 turn 状态会影响是否可 steer；终端里输入一段文字，还要经过 Agent TUI 的处理。操作被接受与任务已经改变，是不同阶段。

你可以把补充写成：

```text
补充当前功能的验收条件：改变标签时保留搜索词，并重置到第一页。
继续这轮实现；先确认前端状态与 API 参数采用同一套规则。
```

这是自拟示例，强调目标变化而非重复整段任务。独立的新需求适合排队或开新工作区。

## 找回旧会话

从右侧 Agents 的 Agent Session History 进入历史，先用 Workspace／Project／All 范围缩小搜索，再按任务标题、目录、分支或模型寻找。展开详情能查看首条要求和最近对话，确认自己找对了工作。[^history]

对支持的会话，可以 Resume 到 CLI，或使用 Resume in New Native Chat；反向的 Resume in New CLI 也有相应入口。资格和目录限制按 Agent 与版本不同，不应仅凭菜单名字假定跨机器或跨目录都能恢复。

在需要继续而非新建时，历史入口比复制几句末尾回复更可靠：它能帮助你找回工作目录与原生恢复方式。仍要核对当前文件，因为恢复会话不会撤销别人已经做过的修改。

## 长会话什么时候该分开

一条会话很适合连续完成一项功能：澄清、实现、测试、修订。目标变成另一个独立任务，或你希望得到独立审查意见时，可以新开会话，并交代需要的材料。

清空上下文、压缩上下文、恢复旧会话与更换 surface 作用不同。操作前先问自己要保留什么：只是文件、完整工作历史，还是一个简洁的新起点。涉及原生状态的细节见技术附录 B，不需要在每次日常操作时背一套协议字段。

## 暂时离开与重新回来

工作区 Sleep 服务于以后恢复，终端 Close 则可能结束进程并移除相应界面记录。Agent hibernation 是带条件的实验功能，尤其会检查未完成协作与子任务，不等于任意后台终端自动暂停。[^sleep]

回来时先看当前状态和最后的验收结果。如果会话恢复失败但历史仍可读，重新说明当前文件与待完成阶段，比不加说明地发送“继续”更清楚。
