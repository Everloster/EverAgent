# 无状态的鹦鹉，怎么学会了连续对话和自己用工具？

> **这篇是什么**：一篇面向"懂点技术、但想把 Agent 底层原理一次性想透"的读者的科普。我们不堆概念，而是**跟着一次真实的带工具对话，从头到尾走一遍**，沿途把每个"想不通的地方"就地讲清楚。
>
> **读完你能回答**：
> - LLM 明明是"无状态、只会吐下一个词"的函数，凭什么能记住上文、还能自己调用搜索/读文件？
> - 一次对话里反复用工具，发给模型的内容是不是越滚越大？会撑爆吗？
> - 既然每轮都把几万字的历史重发一遍，推理是不是每次都从头重算？那还怎么快？
> - 工业界用什么办法让它又快又省？
>
> **怎么读**：从头顺读最佳（有主线故事）。赶时间就看每节开头的 **✦ 一句话**，和最后的「一页纸心智模型」。想看代码/报文证据的，展开每节里标了 `证据` 的引用块。
>
> **证据约定**：带 `报文`/`字段`/`数值` 的结论均来自 OpenAI / Anthropic 官方文档（链接见文末），标 `[推测]` 的是推断。文末「附」是一次真实请求的 token 实测。

## 第一部分 · 先建立直觉

### 1. 一个悖论：无状态的鹦鹉，为什么像有记忆？

先说一个几乎所有人都听过、但很少被认真对待的事实：

> **大语言模型（LLM）是一个无状态的纯函数。** 你给它一段文字，它算出"下一个最可能的词"，吐出来。仅此而已。它没有记忆、不能上网、不能读文件、不记得你上一句说了什么。每一次调用，对它来说都是"这辈子第一次见到你"。

这就带来一个悖论：

- 如果它真的"什么都不记得"，那 ChatGPT 为什么能跟你**连续聊十几轮**、还记得你开头说的名字？
- 如果它"不能上网、不能读文件"，那各种 AI 助手为什么能**自己去搜索、自己读代码、自己查数据库**？

答案是：**这些"能力"都不在 LLM 本身，而在它外面那一层工程**。LLM 始终是那只无情的鹦鹉；是外面的"管家"制造了记忆和行动的**幻觉**。这篇文章，就是把这个"管家"和"幻觉"拆开给你看。

### 2. 两个主角：无情的鹦鹉，和它的幕后管家

整个故事只有两个角色，先把它们的分工焊死在脑子里：

| 角色 | 学名 | 它是什么 | 它能做什么 | 它**不能**做什么 |
|---|---|---|---|---|
| 🦜 **鹦鹉** | LLM（大模型） | 一个无状态的推理函数 | 读入一段文字 → 输出下一段文字 | 记忆、上网、执行、调工具 |
| 🎩 **管家** | **Agent Harness** | 夹在你和鹦鹉之间的编排层 | 存历史、拼上下文、执行工具、控制循环 | 自己"思考"（它不产生智能） |

一个贴切的类比：

> **鹦鹉是一位记忆只有 7 秒、但博学惊人的天才。** 它被关在一个没有窗户的房间里，只能通过门缝收纸条、写纸条。
> **管家站在门外。** 每次你（用户）有问题，管家把"你的问题 + 之前所有对话记录"抄成一张大纸条，从门缝塞进去；天才看完，写一张纸条递出来——可能是答案，也可能是"我需要查一下 XX 资料"。如果是后者，管家就**替它跑腿**（去搜索、读文件），把结果连同之前的一切**重新抄一遍**塞回去。如此往复，直到天才写出最终答案。

记住这个画面。下面整篇，都是在讲这位管家**具体怎么抄纸条、怎么跑腿**。

> **术语澄清**：普通的单次问答（"帮我翻译这句话"）用不到管家——一进一出就完了。只有当任务需要**多步行动、调用外部工具**时，Harness 这一层才登场。本库 `wiki/concepts/agent_harness.md` 有独立词条。

## 第二部分 · 跟着一条消息走一遍

现在我们发一个**需要用工具**的问题，全程跟踪它。贯穿全篇的例子：

> 🗣️ 用户问："**查一下 2026 年 6 月杭州空调销量。**"

这个问题模型答不了——它不知道实时销量，得调一个 `get_sales` 工具。看管家怎么运作。

### 3. 全流程：一次带工具的问答，七个动作

✦ **一句话**：你提问 → 管家打包 → 鹦鹉说"我要用工具"（这是意图，不是答案）→ 管家替它跑 → 结果塞回 → 再问鹦鹉 → 循环，直到鹦鹉说人话。

```
①用户提问
   └─► ②管家打包上下文（system + 工具说明 + 历史 + 你的问题），发给 LLM
          └─► ③LLM 输出："我要调 get_sales(month=6, city=杭州)"  ← 注意：是意图，不执行！
                 └─► ④管家解析意图，真正去调用 get_sales 这个 API
                        └─► ⑤管家把返回结果（"销量 12000 台"）追加进上下文
                               └─► ⑥管家把【全部内容】重新发给 LLM
                                      └─► ⑦LLM 这次输出人话："2026年6月杭州空调销量为12000台。"
                                             └─► 管家把答案流式推给你，结束
```

这里**最反直觉、也最关键的一步是 ③**：

> **模型说"我要用工具"时，它并没有执行任何东西。** 它只是输出了一个**结构化的意图对象**——"我想调用名为 `get_sales` 的函数，参数是这些"。真正的执行（联网、查库、跑代码）全是**管家代劳**。鹦鹉永远只动嘴，不动手。

这一步为什么重要？因为它解释了整个 Agent 的安全边界和工程形态：模型永远碰不到真实世界，所有危险动作都经过管家这一层的鉴权、沙盒、审计。

<details>
<summary><code>证据</code>：模型输出的"工具意图"长什么样（点开看真实报文）</summary>

**OpenAI（Chat Completions）**：assistant 消息里带一个 `tool_calls` 数组：
```jsonc
{
  "role": "assistant",
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": { "name": "get_sales", "arguments": "{\"month\":6,\"city\":\"Hangzhou\"}" }
  }]
}
```
> 注意 `arguments` 是**字符串化的 JSON**，用时要 `JSON.parse`。（OpenAI Function calling docs）

**Anthropic（Messages）**：响应的 `stop_reason` 变成 `"tool_use"`，`content` 里出现一个 `tool_use` 块：
```jsonc
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "我需要先查一下销量……" },
    { "type": "tool_use", "id": "toolu_01A...", "name": "get_sales", "input": {"month":6,"city":"Hangzhou"} }
  ]
}
```
> Anthropic 的 `input` 直接是对象；`stop_reason:"tool_use"` 是"循环要不要继续"的判据信号。（Anthropic Tool use docs）

管家执行完工具后，把结果**作为一条新消息追加**回去，靠 ID 配对：
- OpenAI：`{"role":"tool", "tool_call_id":"call_abc123", "content":"{销量:12000}"}`
- Anthropic：在一条 `user` 消息里放 `{"type":"tool_result", "tool_use_id":"toolu_01A...", "content":"..."}`

那个 `tool_call_id` / `tool_use_id` 就是"哪次调用对应哪个结果"的绑定锚。

</details>

### 4. 循环的本质：一个只增不减的数组，被反复重发

把第 3 节的七个动作抽象一下，你会发现它就是一个 **`while` 循环**：**只要模型还在要工具，就执行、追加、重发。**

<details>
<summary><code>证据</code>：Anthropic 官方把这个循环写成了伪代码</summary>

```python
while response.stop_reason == "tool_use":
    tool_results = run_tools(response)        # 管家执行工具
    messages.append(assistant_message)        # 追加模型的 tool_use
    messages.append(tool_results_message)     # 追加 tool_result
    response = client.messages.create(...)    # 带【全量 messages】再请求
# 退出条件：stop_reason 变为 end_turn / max_tokens / stop_sequence / refusal
```
（Anthropic Tool use, "Handling the tool use loop"）

OpenAI Agents SDK 的 `Runner.run()` 讲得更细：每轮调 LLM → 若输出是纯文本且无工具调用则判为 final output 结束；若有 tool_calls 则执行、追加、重跑；超过 `max_turns` 抛 `MaxTurnsExceeded`。（OpenAI Agents SDK docs）

</details>

这个循环里**唯一在变大的东西，就是那个 `messages` 数组**。它像一个**只进不出的账本**：每一步都往里追加（模型的话、工具的结果），然后把**整本账**重新递给鹦鹉。

**四种消息角色**，构成了这本账的全部内容：

| 角色 | 谁产生 | 装什么 |
|---|---|---|
| `system` | 管家 | 规则、身份、（部分）工具约束 |
| `user` | 用户/管家 | 用户输入；**也用来回填工具结果（Anthropic）** |
| `assistant`（纯文本 / 工具调用） | LLM | 最终答案 / 或"调用意图" |
| `tool` 结果 | 管家 | 工具的真实返回 |

记住"**只增不减的账本被反复重发**"这个画面——第三部分的三个问题，全是它的直接推论。

## 第三部分 · 三个想不通的地方

有了主线，现在攻三个最容易卡住的点。它们其实是同一个事实（无状态 + 全量重发）的三个侧面。

### 5. 它凭什么"记得"上文？——记忆是重发造出来的幻觉

✦ **一句话**：模型没有记忆；所谓"记得"，是管家每轮把**全部历史重新塞进去**，让它**当场重读一遍**造出来的。

你追问"那上个月呢？"，模型能接上,不是因为它记得——而是因为管家把"空调销量那一整轮对话 + 你的新追问"打包重发了。模型**当场重读**整本账本，看起来就像"记得"。

- **一次回复结束，管家不清空任何东西。** 你追问的那一刻，只是往账本**再 append 一条 user 消息**，然后把整本账（含之前所有提问、回复、工具往返）重新发出去。
- 这意味着：**"多轮对话"的本质，就是"一个越来越长的账本被反复重发"**。记忆是重读的副产品，不是存储。

<details>
<summary><code>证据</code>：官方多轮写法，字面就是"把上一轮输出 append 回去"</summary>

```python
history = [{"role": "user", "content": "tell me a joke"}]
response = client.chat.completions.create(model=..., messages=history)
history.append(response.choices[0].message)                      # 上一轮 assistant 回复塞回去
history.append({"role": "user", "content": "tell me another"})   # 新追问
second = client.chat.completions.create(model=..., messages=history)  # 全量重发
```
> "By using alternating user and assistant messages, you capture the previous state of a conversation in one request to the model."（OpenAI Conversation state docs）

**一个高频误解**：OpenAI Responses API 的 `previous_response_id` / 服务端 Conversations 对象，不是"省 token 的记忆"。它只是**替你保管历史、免去手动拼数组**，送进模型的上下文一分没少：
> "Even when using previous_response_id, all previous input tokens for responses in the chain are billed as input tokens in the API."（OpenAI Conversation state docs）
> **即"有状态"省的是你的拼接工作，不是模型的输入 token。**

</details>

> **唯一的例外——模型的"思考块"**：模型的内部推理（Anthropic 的 `thinking` 块 / OpenAI reasoning）跨轮处理**依模型而异**。较新模型（如 Anthropic Opus 4.5+ / Sonnet 4.6+）默认保留、计入输入；较早的模型上，一旦来了新的用户追问，之前的思考块会被自动丢弃。但注意：**在一次工具循环内部，思考块必须原样保留**，否则破坏推理连续性。（Anthropic Extended thinking docs）

### 6. 那 token 岂不越滚越多？——是的，必然膨胀

✦ **一句话**：账本只增不减，所以每轮送进模型的 token **必然单向上涨**，这不是 bug，是无状态的直接代价。

因果链非常干净：

```
LLM 无状态  ⇒  每轮必须重发全量历史  ⇒  账本只增不减  ⇒  输入 token 单向上涨
                                                          ⇒ ① 越来越慢（输入越长，处理越久）
                                                          ⇒ ② 越来越贵（按输入 token 计价）
                                                          ⇒ ③ 逼近上下文窗口硬上限 → 溢出报错
```

几个要点：

- **量级感**：一次 10 轮工具调用的任务，最后一轮的输入可能是第一轮的 8~10 倍甚至更多（文末「附」的实测里，一次真实会话从 4 万 token 涨到了 47 万+，膨胀 12 倍以上）。
- **一个放大器：多模态**。图片编码后的 token 远高于等价文字，长对话里塞几张图会**急速**打满窗口。
- **窗口口径**：上下文窗口是 **输入 + 输出 的总和上限**，不是只算输入。所以工程上要预留 10~20% 给输出，管家会设一个"输入安全阈值"提前触发裁剪。
- **一个计费陷阱**：有缓存时，`input_tokens` 和 `cache_read_input_tokens` **不能简单相加**当成本，实际计费口径更复杂（见第 8 节）。

膨胀是真的。但这引出了第 7 个、也是最精妙的问题。

### 7. 膨胀了还能快？——"无状态"和"高效"分处两层，不矛盾

✦ **一句话**：**不是每次从头重算。** 模型语义上"无状态"，但推理引擎运行时用**两级缓存**记住了中间计算结果，跳过重复劳动。

这是全篇最容易混淆的地方，务必拆开：

> **"无状态"是模型权重和 API 语义层面的事**（模型不记得你，靠你重发历史）；
> **"高效"是推理引擎运行时层面的事**（引擎用缓存记住了 K/V，避免重算）。
> 这是**两个不同的抽象层**，一个在讲"接口语义"，一个在讲"内部实现"，完全不冲突。

#### 先拆开一次推理的两个阶段

模型处理一次请求，不是"读完直接出答案"，而是分两段：

| 阶段 | 干什么 | 特征 | 能否复用历史 |
|---|---|---|---|
| **Prefill（预填充）** | 读入**全部输入 token**，为每个算出 K/V（注意力的键值） | 一次性并行，算力密集 | **✅ 能——缓存的战场** |
| **Decode（解码）** | 逐个吐出新 token，每步只算 1 个新 token 的 Q，与历史 K/V 做注意力 | 逐 token 串行，访存密集 | 新 token 要真算，历史 K/V 读缓存 |

"每次从头重算"的担忧，被两级缓存化解在这两个阶段里：

#### 层次一 · 单轮内部：经典 KV Cache

一次生成要吐几百个字。若无缓存，生成第 t 个字都要对前 t-1 个字重算注意力，总量 O(T²)。**KV Cache 的做法**：历史 token 的 K/V **算一次就存住**，生成后续每个字时只增量算新字那一列，每步 O(t)、总量降到 O(T)。

> 这解决的是："**一次回复里，逐字往外蹦时，不重算前面已经蹦出来的字。**"（原理详见本库 `wiki/concepts/kv_cache.md`）

#### 层次二 · 跨轮之间：Prefix Caching（这才是本问的正解）

第二轮请求发进来的是 `[system + 工具说明 + 第一轮全部历史 + 新问题]`。推理引擎一看：**前面这一大段前缀，和上一轮请求逐 token 完全相同！** 于是：

```
第二轮输入 = [system+工具+历史 (与上轮前缀逐token相同)] + [新问题 (几十 token)]
                    ↑                                        ↑
              命中缓存，K/V 直接复用，跳过 prefill        只对这几十个新 token 做 prefill
```

**引擎只对"新增的那一小段"做 prefill，前面几万 token 的 K/V 从缓存直接捞出来。** 这就是为什么第二轮明明输入更长，首字延迟（TTFT）却可能没怎么涨。

> 这解决的是："**跨轮重发全量历史时，相同的前缀不重新计算。**"对应 `kv_cache.md` 里的 Prefix Caching（节省 80%+ TTFT）和 Radix Attention（跨请求共享前缀 KV）。

#### 一个必须点破的边界

Prefix Caching 靠"**逐 token 相同的前缀**"命中。**前缀只要改一个 token，从那个位置往后的缓存全部失效、必须重算。** 所以：

- ✅ `system + 工具 + 历史` 这种**只在末尾追加**的结构，前缀稳定，缓存一路复用；
- ❌ 若每轮在**开头/中间**插入变动内容（动态 RAG 每轮换一段塞前缀、把时间戳放最前面），会**系统性打穿缓存**，让降价形同虚设。

**这解释了一条工程铁律**：管家总把"固定不变的（system/工具说明）"放最前、"每轮变化的（新用户输入）"放最后——就是为了让前缀尽可能长地保持稳定，最大化缓存命中率。

## 第四部分 · 工业界怎么让它又快又省

### 8. token 经济学：改单价 vs 改数量，两轴正交

✦ **一句话**：治理膨胀有两个正交的维度——**让重发不那么贵（改单价）**，和**让历史不那么大（改数量）**，通常叠加使用。

| 机制 | 改的是 | 谁来做 | 怎么起效 | 代价 |
|---|---|---|---|---|
| **① Prompt Caching** | **单价**（不减 token） | 服务端，管家开关 | 命中的前缀按 **0.1×** 计费（Anthropic）；同时跳过 prefill 计算 | 有 TTL（默认 5 分钟）；前缀一变即失效 |
| **② 滑动窗口裁剪** | 数量（删最老） | 管家 | 只保留最近 N 条消息 | 丢早期关键背景 → 答偏 |
| **③ 摘要 / Compaction** | 数量（压成摘要） | 管家**或服务端** | 触发后把历史替换成一个 `<summary>` 块，官方示例把 ~100k 压到 ~2–3k | 摘要有信息损失；需一次额外 LLM 调用 |
| **④ Context Editing** | 数量（清老工具结果） | **服务端自动** | 自动清除老的工具调用/结果（如 `clear_tool_uses`，保留最近几次） | 清掉的工具历史模型不再可见 |

**两点关键理解**：

1. **①（改单价）和 ②③④（改数量）解决不同问题**：前者让"重发全量历史"不那么贵，后者让"历史"本身不那么大。可以也应该叠加。
2. **服务端的裁剪优于客户端手动删**：因为服务端 edit 裁剪时**能保持前缀缓存不失效**；而客户端手动删历史会打断缓存前缀（回想第 7 节的边界），反而触发昂贵的重新计算。

<details>
<summary><code>证据</code>：Prompt Caching 的计费乘数与 Compaction 阈值</summary>

- Prompt caching：5 分钟缓存**写入** = 基础输入价 **1.25×**；1 小时写入 = 2×；缓存**读取（命中）** = **0.1×**。默认 TTL 5 分钟。缓存按 `tools → system → messages` 的前缀顺序命中。（Anthropic Prompt caching docs）
- Compaction：默认 `context_token_threshold=100000`，触发后把历史替换成 `<summary>` 块，官方示例 ~100k → ~2–3k。（Anthropic docs）
- Context editing：官方示例 `trigger.input_tokens=30000`、`keep.tool_uses=3`。（Anthropic context editing docs）
- 循环轮数没有普适默认值：OpenAI Agents SDK 的 `max_turns` 可配、可设 None 关闭；Anthropic 靠 `stop_reason` 自然收敛，无硬编码轮数。

</details>

## 第五部分 · 装进脑子

### 9. 一页纸心智模型

把整篇浓缩成一张图，随时能在脑子里重放：

```
你（用户）
  │ 提问
  ▼
🎩 管家（Harness）──────────────────────────────────┐
  │ 把 [system + 工具说明 + 全部历史 + 你的问题]     │  ← 只增不减的"账本"
  │ 打包成一张大纸条                                  │
  ▼                                                   │ 循环：只要还要工具
🦜 鹦鹉（LLM，无状态）                                │ 就执行→追加→重发
  │ 读完，输出：                                      │
  ├─ "我要用工具 X"（意图，不执行）──► 管家替它跑 ────┤
  └─ 纯文本答案 ──► 管家流式推给你，结束              │
                                                      │
  推理引擎内部（你看不见但很关键）：                   │
  · KV Cache：单轮内逐字生成不重算                     │
  · Prefix Caching：跨轮相同前缀复用、跳过 prefill ───┘
```

**四句话总纲**：
1. **鹦鹉无状态**，只会读入文字、吐出下一段文字，不记忆、不行动。
2. **管家造幻觉**：靠"每轮重发全部历史"造出记忆，靠"替它执行工具"造出行动。
3. **账本必然膨胀**：无状态 → 全量重发 → token 单向上涨，跨轮持续累积。
4. **膨胀≠低效**：推理引擎用 KV Cache + Prefix Caching 跳过重复计算；治理用"改单价 + 改数量"两轴止损。

### 10. 几个容易踩的直觉陷阱

顺手校正几个"想当然"，避免刚建立的心智模型被带偏：

| 直觉陷阱 | 真相 |
|---|---|
| "客户端看不到中间的工具调用" | ❌ 流式协议**原生**就把工具调用事件推给前端（OpenAI `response.function_call_arguments.delta`、Anthropic `input_json_delta`）。是否展示是**产品 UI 选择**，不是协议限制。 |
| "缓存只是提速，不影响成本" | ❌ 漏了最关键的：命中缓存**直接砍计费到 0.1×**。它改的是单价，不是数量。 |
| "上下文治理只能靠客户端自己写代码" | ❌ 2025–2026 年 Anthropic 已把 compaction / context editing **下沉到服务端**，管家开个开关即可。 |
| "循环最多 5~10 轮" | ❌ 没有普适默认值。因框架而异，可配置、可关闭。 |
| "有状态 API 就省 token 了" | ❌ `previous_response_id` 省的是拼接工作，不是输入 token，照旧全量计费。 |
| "无状态就意味着每次从头重算" | ❌ 语义无状态 ≠ 运行时无缓存。引擎用 KV Cache / Prefix Caching 复用中间结果。 |

## 附 · 一次真实请求的 token 实测拆解

理论讲完，用一次真实数据收尾——验证"你的输入只占极小比例、其余全是固定脚手架"到底是不是真的。

**场景**：某 Agent CLI 环境下，在一个项目工作目录里，用户发出的第一句话只有两个字——「你好」。这次请求送进 LLM 的输入，实测 **`input_tokens = 39,671`**（用户打了 2 个字，系统实际灌了近 4 万 token）。

逐块拆解（占比以 39,671 为分母；文本块用现代分词器计数，与模型真实分词器有 ±10% 量级误差；工具定义部分该环境不单独落盘，用"总数 − 已知文本"残差反推，仅精确到量级）：

| # | 组成块 | 消息角色 | 实测 token | 占比 | 装的是什么 |
|---|---|---|---:|---:|---|
| ① | 系统提示 | system | ~444 | 1.1% | Agent 身份、运行规则、安全约束 |
| ② | 能力/技能清单 | developer | ~9,784 | **24.7%** | 当前环境可用能力条目（名称+描述+用法） |
| ③ | 记忆/画像注入 | developer | ~6,269 | **15.8%** | 跨会话记忆说明 + 用户画像摘要 |
| ④ | 上下文管理声明 | developer | ~47 | 0.1% | 自动压缩开关提示 |
| ⑤ | 项目协议注入 | user | ~2,783 | 7.0% | 当前工作目录的项目主协议全文 |
| ⑥ | 环境元信息 | user | ~18 | 0.0% | 日期、时区 |
| ⑦ | **用户真实输入「你好」** | user | **~1** | **0.005%** | ★ 用户真正打的字 |
| ⑧ | 工具定义 + 消息封装 | 服务端注入 | **~20,325** | **51.2%** | 该环境工具集的结构化定义（残差，量级） |
| | **合计** | | **39,671** | 100% | 与实测计费对齐 |

**三个直接印证正文的结论**：

1. **占比最大的是工具定义（~51%）**，超过所有文字说明之和——坐实第 3 节"工具说明是每轮固定携带的开销"。
2. **"给 Agent 装脑子"的两块（能力清单 + 记忆画像 ≈ 40%）** 是第二大头，每轮固定烧掉约 1.6 万 token。
3. **用户的「你好」只占 0.005%（1 个 token），其余 99.995% 全是固定脚手架**——这就是第 2 节"管家每轮先把整套规则+说明书+档案重发一遍"的实证。

**膨胀实测**：同一会话继续跑（读文件、多轮工具往返），`input_tokens` 从 39,671 一路涨到 47 万+，膨胀 12 倍以上——把第 6 节的"8~10 倍"换成了实数；且增量绝大部分来自不断追加的工具结果，与第 8 节"context editing 优先清工具结果"的动机吻合。

**缓存的计费投影**：那次 39,671 的账单里，`cached_input_tokens`（命中、0.1× 计费）+ `cache_creation_input_tokens`（新写入、1.25×）两个字段，正是第 7 节 Prefix Caching 在计费层的体现。随对话增长，命中部分越来越大、复用率越来越高。

## 💭 思考与追问

1. **我真正理解了什么？**
   我把"无状态的鹦鹉为什么像有记忆、还能行动"这个悖论，拆成了**两个角色（无状态 LLM + 编排管家）+ 一个循环（只增不减的账本被反复重发）**。三个连锁推论一次讲清：记忆是重读的幻觉、token 必然膨胀、但膨胀不等于低效（引擎两级缓存 + 治理两轴）。最关键的认知升级是把"无状态"（API 语义层）和"高效"（推理运行时层）**分到两个抽象层**——这消解了它们的表面矛盾。

2. **我还没搞懂什么？**（汇入 open-questions）
   - Compaction 把 100k 压到 2–3k（~40×），被丢掉的工具中间结果若含后续依赖的关键事实，模型如何不"断片"？有没有可证伪的失败模式基准？
   - 动态 RAG 每轮注入不同片段，是否会系统性打穿前缀缓存？RAG 该放前缀还是尾部？
   - 服务端 context editing 清掉的工具历史，与客户端持久化的全量历史，一致性如何对账、审计以哪份为准？

3. **下一步做什么？**
   - 落一个最小可运行 demo（B 类 `ai-practice`），逐轮打印 `messages` 真实 token，画出完整膨胀曲线，并区分"工具结果 vs 固定前缀"的增长速率。
