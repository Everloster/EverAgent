# 读到 TODO 之后，为什么不该直接把它变成新任务

正在修一个问题的 Agent，读到旁边的 TODO，随后去查另一个工单，甚至顺手修改另一段代码。新调查可能有价值，却不一定属于当前任务；如果注释早已过时，它还可能把推理引向错误前提。

[Google 的 Agent Distraction](https://developers.googleblog.com/agent-distraction/)研究了这种现象。它最值得追问的地方，是三个判断经常被混在一起：**代码里提到了一个问题，这个问题现在仍然成立，以及用户希望现在处理它。** 三者需要分别确认。

## 先把研究里的分母放回原处

原文以带工单引用的 TODO/FIXME 为代理信号，将代码读取、后续动作、用户提示和工单状态关联。以下是正文及两张图的核心记录：

| 原文报告 | 对应范围 |
|---|---|
| 13% 接触到引用；6% 触发后续动作 | 前者针对读取源码的会话；后者描述接触引用后的行动 |
| 83% 未被要求 | 已发生相关行动的子集，不是全部会话 |
| 57% 开放、32% 已修复、9% 过时或不修、2% 其他 | 被标为未要求绕路的工单状态分布 |
| 步数 +70%、token +77%、等待 +105% | 经回归调整后的会话比较；图示估计范围分别为 +54%—87%、+60%—96%、+86%—126% |

原文说明使用多向固定效应回归，并按开发者聚类标准误，控制任务、代码复杂度、模型、读取文件量、提示长度和引用出现位置等因素。清理方案检查工单与代码历史；六个月移除数千条已确认过时的引用，人工审查接受率超过 95%。这些是作者结果，本文没有取得其内部样本或重跑分析。[原文](https://developers.googleblog.com/agent-distraction/)

下文是对这些测量的分析，以及用于说明维护方法的自拟例子。

## 注释、现状和任务范围，是三个不同状态

TODO 记录的是某个时间点留下的意图。工单记录问题的跟踪状态；当前用户任务则规定这一次要完成什么。任何一个状态都不应自动代替另两个。

用几种**自拟情况**检验这个区别：

| 情况 | 适合怎样判断 |
|---|---|
| 用户描述了当前故障，但没写工单号 | 工单号缺席，仍可能是本次需要处理的问题 |
| 用户说“不要处理 ISSUE-123” | 工单号出现，也没有赋予处理权限 |
| 工单已修复，但项目仍支持旧依赖版本 | 旧兼容注释可能仍有作用，先查适用条件 |
| 工单仍开放，与当前改动无关 | 开放状态不会自动扩大本次任务范围 |
| 工单被标成重复或无法访问 | 应检查归并关系或记录未知，不能当作无效问题删除 |
| 旁支问题是完成当前修复的必要前提 | 可以说明依赖关系后处理，不能仅因它来自 TODO 就排除 |

原图用“工单 ID 是否出现在用户提示”解释是否被要求的分类，但正文没有披露完整语义判定规则。这些例子指出了一类需要抽查的测量误差：自然语言描述、否定要求和必要依赖，都可能让 ID 匹配与真实任务范围不同。它们不证明作者分类一定错误，而是说明这个代理指标需要什么验证。

同样，“看了工单”和“修改了代码”后果不同。前者可能只是一次有必要的背景核对，后者可能引入行为变化。评价偏离程度，应结合它是否帮助当前任务、花费多少、是否导致额外修改，而不只计数工具调用。

## 回归调整后的成本差异，不等于清理后的保证收益

控制一些可观察因素，能让比较更有解释力，但仍不能等同于随机分配“有无旧 TODO”的实验。任务越难，可能越容易接触复杂历史，也可能本来就需要更多调查；更长的会话又可能产生更多遭遇旁支线索的机会。模型版本、任务粒度及未记录的失败恢复，也可能影响结果。

因此，原文的控制变量是有用的，不能把它们理解成现实中的所有条件都完全相同。统计显著性也不直接回答：在自己的仓库删掉这些注释，究竟能减少多少成本。

百分数还有一个简单但常见的误读。若只为理解量纲，**假设**正常任务消耗 100 个单位、另一组消耗 177 个单位，那么从后者降回前者，降幅是：

\[
\frac{177-100}{177}\approx43.5\%.
\]

“比基线多多少”与“从当前水平能减少多少”分母不同。这只是算术示意，并未证明删除注释就能达到该节省；更不能把会话子集的差异推广成全仓账单的节省。token 数也不能不加条件地换算成金额。

图里的 estimated range 没有注明置信水平，本文沿用“估计范围”，不改称 95% 置信区间。文中的审查接受率则是在衡量清理提案获认可的比例，与清理后 Agent 的速度、正确率是不同结果。

## 为什么工单关闭后，仍要读代码历史

想清理一条注释，最重要的问题是它当初保护了什么条件，以及该条件现在是否消失。

例如，一条注释要求依赖升级后删除兼容分支。上游工单关闭，可能只说明新版本已经修复；只要本项目还承诺支持旧版本，兼容分支就可能仍有必要。反过来，也可能代码已经修好，旧注释留着描述一个不再存在的问题，此时改写或删除有价值。

[Google C++ 风格指南的 TODO 部分](https://google.github.io/styleguide/cppguide.html#TODO_Comments)要求提供可找到上下文的标识，并提醒未来事项写明具体日期或触发事件；它还明确说，TODO 中提到某个人，不代表那个人承诺修复。这些约定有助于保持“参考信息”和“当前责任”的区别。

下面是**自拟改写**：

```cpp
// 原先：TODO(ISSUE-123): remove this workaround.

// 该分支兼容依赖库 2.0 的旧返回格式。
// TODO(ISSUE-123): 最低依赖版本升到 2.1 后，移除此分支，
// 并保留旧返回格式应被拒绝的回归测试。
```

新注释说明了当前存在的理由、移除条件和需要保留的行为检查。它仍需要维护，但读者更容易判断是否与手头任务相关。

查历史可以从文件及注释本身入手。例如下面是只读的**示意命令**，路径与工单号需要换成实际对象：

```bash
git log --follow -p -- path/to/file.cc
git log -S'ISSUE-123' -p -- path/to/file.cc
```

[Git 官方文档](https://git-scm.com/docs/git-log)说明，`--follow` 跟随单个文件越过重命名；`-S` 找的是指定字符串出现次数发生变化的提交。它们能帮助定位引入或删除，但不是完整语义审查：同一行被改写、条件在别的文件中变化、字符串次数不变，都可能需要继续追踪。

删除工单引用与删除旁边的兼容代码，也应作为两项变更分别判断。不能因为前者被确认过时，就顺便移除仍有行为作用的代码。

## 让 Agent 看懂现状，比把全部历史清空更有用

对正在工作的 Agent，可以采用一个简单的处理顺序：先识别当前目标，再判断新线索是否是完成目标所需的信息。只有确有依赖时，才进一步核查状态和历史；无关但可能有价值的问题，可以留作明确的后续事项。

这里不需要为每次只读调查都增加人工审批。更有用的是给出可检查的理由：这次查工单是为了确认哪个依赖？它会改变当前实现的哪项决定？若调查没有帮助，就停止扩大范围。

文件也可以提供这种线索。临时方案写明适用版本，废弃设计写明替代入口，已完成迁移留下当前规范的位置。这样既保留了为什么作出历史决定，也减少把旧说明误当成今天约束的机会。

不宜将所有 TODO 都改写成“立即执行”，也不宜批量清空所有旧注释。前者把维护计划变成任务队列，后者可能删除解释边界条件的资料。判断标准应回到它是否仍准确、是否仍帮助理解代码。

## 怎样在自己的仓库检验这件事

如果要从这篇观察走向本地证据，本文建议使用相同任务、固定代码基线、固定模型与预算，比较保留旧注释和经审查更新注释后的执行。先在隔离副本里做小规模测试，再决定是否推广。

至少同时记录当前任务完成情况、无关调查、无关修改、token 和等待时间。只看速度可能奖励漏做必要检查；只看完成率则可能漏掉大量额外工作。还应让审查者检查被标记为“未要求”的样本，尤其是没有写工单号、包含否定要求或存在必要依赖的任务。

清理提案则需要另一组检查：是否保留仍然成立的条件，是否误删兼容说明，是否把无法访问的工单当作过时。最后再测清理后 Agent 的实际结果，而不是以合并率代替效果。

这是一个待做实验设计。本次没有访问 Google 内部数据，没有运行 Agent 对照实验，也没有批量清理本仓 TODO。报告希望留下的判断方法是：看到历史问题，先弄清它今天是否成立、与当前目标是什么关系，再决定要做什么。
