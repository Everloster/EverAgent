# AI演义·14｜MegaScale：一万张 GPU，怎样一起把模型练完？

[返回原报告第 14 节](../AI演义_笔记分析与项目整合报告.md#paper-megascale) · [上一节：LAION](AI演义_13_LAION_图文怎样变成训练数据_科普讲解_20261105.md) · [下一节：稀疏 MoE](AI演义_15_稀疏MoE_大模型怎样只计算一部分_科普讲解_20261105.md)

一家公司有一万张 GPU，可以把它们分给许多互不相干的任务：这批训练图像模型，那批处理推荐数据，另一批做实验。某个任务出错，其余任务还可能继续跑。

但如果要让这一万张卡共同训练**同一个大模型**，情况就变了。它们分别算出一部分结果，还要把结果交给其他卡；有时许多卡都在等一个迟到的结果。一张卡没有及时完成工作，影响可能沿着依赖关系传遍整个作业。

**MegaScale 研究的是：怎样让这么多 GPU 既能高效协作，又能在数周的训练中不断处理故障、继续推进。** 2024 年，来自 ByteDance 和北京大学的作者介绍了这套生产训练系统。论文报告了 1750 亿参数模型在 12,288 张 GPU 上的性能，也公开了真实训练中遇到的慢节点、程序抖动和恢复案例。[^paper]

沿着一次训练从开跑到长期运行的过程，能看清这篇系统论文为什么不只是“买了很多卡”。

<a id="one-training-job"></a>

## 1. 一次训练，究竟要共同完成什么？

先看一个语言模型的训练步骤。系统取出一批文本，让模型预测接下来的 token；根据预测与训练目标的差距，通过反向传播计算梯度——损失对各参数变化有多敏感。最后由**优化器**结合梯度等信息，决定参数的调整方向与幅度，完成更新。

一批训练数据称为一个 **batch**。处理这批数据并完成一次更新，通常称为一个训练步。完整预训练需要反复执行这样的步骤；一次步骤跑得快，离持续几周都能顺利推进，还有很长一段距离。

模型很大时，参数、梯度、优化器状态和计算中间结果可能装不进单张卡；即使装得下，单卡也可能算得太慢。于是需要多卡分工。困难在于，这些卡最终仍在共同更新一个模型，不能各自改完就走。[^parallel]

这正是讲义和播客提出的两个问题：**训练效率**关心每一步要花多久，**训练稳定性**关心这种效率能否长期保持，以及出问题后损失多少进度。讲义用“算法与系统共同设计”和“深度可观测性”概括 MegaScale 的两条思路。前者改进分工和执行方式，后者帮助发现系统究竟卡在哪里。

<a id="parallel-work"></a>

## 2. 模型怎样分给多张卡？

分工至少有三个方向。先理解它们分别拆什么，再看缩写就容易了。

| 分工方式 | 拆开的是什么 | 必须交换什么 |
|---|---|---|
| 数据并行（DP） | 不同训练样本；多份模型副本分别处理 | 各份计算出的梯度等信息，用来保持更新一致 |
| 流水线并行（PP） | 模型的不同层；前几层和后几层分开执行 | 前向计算的中间结果，以及反向传回的信息 |
| 张量并行（TP） | 同一个大算子里的计算，例如矩阵乘法 | 分块计算所需的输入或结果 |

想象一个**仅用于讲解的 8 卡配置**：一份模型分成前、后两个阶段，每个阶段再由两张卡分担算子，这就用了四张卡。再复制一组同样的四张卡，让两组处理不同数据，便得到八张卡共同训练的安排。这里的“模型副本”由多张卡共同承载，不是每张卡都装着完整模型。

三种分工叠在一起，称为 **3D 并行**。这不是 MegaScale 发明的全新概念；论文建立在 Megatron-LM 等已有工作的基础上，重点是怎样把这些分工在大规模训练中组织好。[^parallel]

还记得[第 11 节的 ZeRO](AI演义_11_ZeRO_多卡怎样分担训练显存_科普讲解_20261105.md)吗？它让数据并行中的各卡分担原本重复保存的训练状态。MegaScale 的背景部分具体介绍了 ZeRO 第二阶段：分片保存优化器状态和梯度。相关通信会包括 **reduce-scatter**，即汇总结果后各留一份分片，以及 **all-gather**，即把各处分片收集起来。这样才能在少占显存的同时取得后续计算所需的数据。

另一个配套办法是**序列并行（SP）**：把部分操作的中间结果沿输入序列分给不同卡，例如 LayerNorm 和 Dropout。这些操作计算量相对不大，却可能占用不少激活显存。它与张量并行配合，解决的侧重点是中间结果的存放。

分工还必须考虑物理位置。张量并行频繁交换数据，论文倾向于把它留在同一台服务器内，利用更快的卡间连接；数据并行和流水线并行更适合跨服务器安排。逻辑上怎么分、物理上放在哪儿，会共同影响通信成本。

## 3. 为什么连模型结构和优化器也要一起改？

如果分工方式不适合硬件，再快的网络也可能一直在替不合理的安排补救。MegaScale 因而不只调整底层执行，还采用了几项算法上的改动。[^algorithm]

**第一项是并行 Transformer block。** 标准串行结构中，Attention 先处理输入，后面的 MLP 再接着处理；MLP 是层内进一步变换表示的网络。并行版本让 Attention 与 MLP 从同一个归一化输入分别出发，随后合并结果，为并行执行创造条件。

这改变了模型的计算结构。它不是把同一个公式换一种写法后，保证所有输入都得到原来的结果。因此，是否值得采用，既要看速度，也要看训练效果。

**第二项是滑动窗口注意力。** 每个 token 主要关注附近窗口中的内容，减少单层里需要处理的关系。多个这样的层叠起来，信息可以传播到更远的位置。但它并不等于每一层仍然直接查看所有位置，效果需要实验检验。

**第三项是用 LAMB 优化器支持更大的 batch。** 这为什么能帮助流水线？

一批数据会再拆成若干小批次，称为 **microbatch**。上游处理后一个小批次时，下游可以处理前一个。流水线刚启动和即将结束时，总有一些阶段暂时没有活干，这些空档叫**流水线气泡**。

关键是让一次更新包含更多可以接续执行的 microbatch。在流水线阶段数、数据并行份数和每个 microbatch 大小不变时，增大 batch 就能延长中间稳定忙碌的阶段，摊薄反复填满、排空流水线的代价。单纯增加数据并行副本、却没有让每条流水线获得更多 microbatch，并不具备这个效果。

但 batch 不能想加多大就加多大。一次更新吸收多少样本，会影响优化过程；减少更新次数，也不能自动保证学到同样的东西。LAMB 的价值正在于作者尝试同时改善训练条件与执行效率，而不是单纯把一个系统参数调大。

作者怎样检查这些改动？受资源限制，论文的收敛微实验使用了 **13B，也就是 130 亿参数模型**：采用并行 block 和滑动窗口注意力后，在超过 100B tokens 的训练中，损失与基线相近；使用四倍 batch 的 LAMB，在约 250B tokens 后达到与 ADAM 相近的损失。[^convergence]

这里的 **loss（损失）**衡量模型在训练目标上的误差。上述结果为这些设置下的训练提供了支持，但并不等于所有下游能力都已验证，也不等于在任何模型、任何 batch 上改动都无代价。尤其要分清：这组 13B 收敛实验，与后面的万卡性能测试，是不同的实验。

## 4. 通信还在那里，为什么能少等一些？

多卡训练要搬数据，传输需要时间。MegaScale 的一个重点，是寻找哪些传输可以和计算同时进行。

例如，过去的安排可能是：把所有分块搬齐，再启动整个矩阵乘法。新的安排可以把大计算拆成小块：第一块需要的数据到手，就开始算；后面的数据继续传，已经算好的部分也可以继续送出。这样一来，部分搬运时间落在计算进行的时间里，便不再全部累加到训练步的耗时上。[^overlap]

这叫**通信与计算重叠**。它的前提是看清依赖关系：某块计算需要的数据没到，就仍然必须等。切块、调度、数据搬运本身也有成本，不能把“重叠”理解为通信时间变成零。

论文分别处理了三类场景：

- **数据并行**：按模型块提前收集参数，并在反向计算之后发起梯度汇总，让一些传输与其他工作重叠。最前面的收集、最后面的汇总，尤其容易成为仍需处理的等待。
- **流水线并行**：原实现中有些发送和接收被绑在一起，较慢的一项会阻塞另一项。MegaScale 拆开这些操作，只保留计算真正需要的依赖，分别异步执行。
- **张量／序列并行**：把矩阵乘法切成小块，与收集、分发数据的操作交错进行。论文利用前馈网络较大的计算量，为隐藏部分通信提供空间。

这里有一个重要区别：有些等待来自任务本身的依赖，有些只是实现把两件可以分开做的事绑住了。系统优化需要先分清两者。

<a id="outside-gpu-kernels"></a>

## 5. 卡准备好了，数据和其他进程却还没准备好

GPU 内部计算很快，不代表它随时都有数据可算。论文还处理了几个容易被忽略的环节。[^plumbing]

**数据准备。** GPU 正在同步本步梯度时，CPU 可以开始准备下一步的数据。同一台服务器内的张量并行工作进程需要相同输入，便由一个数据加载器读取到共享内存，再交给各 GPU，避免每个进程都重复读盘。

**算子执行。** 作者采用 FlashAttention-2，并把某些零碎操作融合，减少启动许多小计算和反复访存的开销。网络等待减少以后，单卡内部的执行效率仍然重要。

**通信组初始化。** 训练开始前，各个工作进程要建立通信关系。小规模时不显眼的全局等待，放大后可能非常昂贵。论文在 2,048 张 NVIDIA Ampere GPU 上测得，原实现初始化约需 **1,047 秒**。替换阻塞式键值服务后降到 **361 秒**；再重新安排初始化顺序、减少不必要的全局屏障，最终降到 **5 秒以内**。在超过万卡的配置上，作者报告了 **30 秒以内**的初始化时间。

这组结果不是“换成 Redis 就从 1,047 秒变成 5 秒”：两步改动分别贡献了效果。初始化变快，也不只是让第一次启动舒服一些；训练频繁恢复、调试和重跑时，每一次都要付这笔成本。

**网络路径。** GPU 分布在不同服务器上，数据还要经过交换机。论文同时考虑网络拓扑、并行组摆放、路径冲突、拥塞和重传。即使每条链路的标称带宽都很高，许多传输挤到同一路径上，实际效果也可能差很多。调整程序分工和调整数据走向，因而是同一个系统问题的两面。

## 6. 55.2% MFU，到底说明了什么？

**MFU（Model FLOPs Utilization）**在这里是一项比值：**实际训练吞吐 ÷ 假设充分用到硬件计算峰值时的理论吞吐**。FLOPs 指浮点运算次数；把模型所需计算量和硬件峰值一起考虑，才能得到这个理论参照。它帮助判断：这套硬件的计算潜力，有多少转成了模型训练的推进速度。[^performance]

它不是“有多少张 GPU 开着”，也不是监控面板上显示繁忙的卡数比例。即使所有卡都在工作，通信、流水线空档、访存和算子执行效率仍会使 MFU 低于 100%。所以，**55.2% MFU 不能翻译为“另外 44.8% 的卡完全没工作”**。

论文表 2 有这样一组对照。两边均为 **175B 模型、12,288 张 GPU、全局 batch 6,144、序列长度 2,048**；基线是作者选定版本的 Megatron-LM，不代表所有未来版本。论文的集群说明使用 NVIDIA Ampere GPU，不能自行换成别的硬件口径。

| 系统 | 每步时间 | 每秒处理的 tokens | MFU |
|---|---:|---:|---:|
| Megatron-LM 基线 | 8.57 秒 | 1,466,800 | 41.2% |
| MegaScale | 6.34 秒 | 1,984,000 | 55.2% |

表中的吞吐可以这样理解：一次更新处理 6,144 条序列，每条 2,048 个 token，共约 1,258 万个 token；用它除以每步约 6.34 秒，就得到每秒约 198 万个 token。**batch 的条数、每条的长度和每步耗时，缺一项就不能算出这个速度。**[^throughput-reading]

MFU 从 41.2% 到 55.2%，提高了 **14 个百分点**，约为基线的 **1.34 倍**。这和“提高 1.34 个百分点”完全不同。每步时间和吞吐数据也支持了它在这组配置中更快的结论。

但这不是完全不改模型与训练方法、只换底层程序的一次对照：MegaScale 包含前面介绍的算法改动。判断总体价值时，应把性能结果与收敛实验一起看。

### 加卡后，效率会一直不变吗？

不一定。表 2 的一组实验把 batch 固定为 6,144，GPU 从 3,072 张增加到 12,288 张。MegaScale 的吞吐上升，但 MFU 从 **59.1% 降到 55.2%**：同一批工作分给更多卡后，每张卡分到的计算减少，通信和等待更难摊薄。这是在检验**强扩展**，即固定工作量后，加资源能快多少。

论文还对 530B 模型做了另一组实验，随着 GPU 增加而按比例增大 batch。在 2,240、4,480、11,200 张卡上，MegaScale 的 MFU 分别为 **54.3%、54.1%、54.3%**。这是**弱扩展**：资源增加时，工作量也跟着增加。两种实验回答的问题不同，不能只拿“MFU 基本不变”来宣称固定任务总能线性加速。[^scaling]

表 2 另列了以处理 300B tokens 为口径的训练时间；那一列也不能直接当作后面数周生产任务的实际完成时间。故障、恢复和训练配方是否相同，需要另外核对。

### 提升来自哪几步？

作者用 175B 模型、256 张 GPU 做了逐步增加优化的实验。下面合并展示表 3 的几个节点：[^ablation]

| 在前一行基础上继续加入的改动 | MFU |
|---|---:|
| Megatron-LM 基线，batch 为 256 | 47.7% |
| 并行 Transformer block、滑动窗口注意力 | 53.3% |
| 再加张量、流水线、数据并行中的通信重叠 | 59.5% |
| 再加高效算子、数据等其他优化 | 62.3% |
| 再换用 LAMB，把 batch 从 256 增至 768 | 65.3% |

这说明收益由多项改动逐步累积；最后一行还同时改变了优化器与 batch。它不是在万卡条件下把每项优化单独打开的实验，不能把这些增量当作任何规模下都能直接相加的收益。网络优化在这组对照的两边都已开启，也不能把整段提升归给网络优化。

最后一行的 batch 是**三倍**；前面 13B 收敛微实验中的 LAMB 是**四倍**。65.3% 与万卡实验的 55.2% 同样来自不同配置。保留这些条件，数字才真正有用。

<a id="why-training-slows"></a>

## 7. 网络没变慢，为什么训练却越跑越慢？

这可能是论文里最值得细读的案例。作者发现，训练越往后，每一步花的时间越长，MFU 随之下降。直觉上很容易怀疑网络：卡都在等通信，当然是网络出了问题？

他们没有停在这个判断，而是逐层缩小范围。[^diagnosis]

1. **先量计算。** 前向、反向和优化器计算本身的耗时没有随训练步数明显增加。
2. **再找最后的等待。** 一步结束前的数据并行梯度汇总变慢了；只要这一步拖延，整步就结束不了。
3. **检查传输。** 网络带宽大体稳定，变慢不能简单归因于链路传得更慢。
4. **比较各进程何时进入汇总。** 有些进程晚一点才到，其他进程必须等它；谁先谁后还会变化，时间差逐渐扩大。
5. **追到上游代码。** 不规则的垃圾回收以及某些 PyTorch 操作带来执行抖动，影响了这些进程进入同步的时机。修改或移除相关代码后，作者不再观察到原先那种明显的 MFU 下降。

也就是说，**时间花在“通信操作里”，不等于根因一定在网络里**。通信既可能在真正传数据，也可能在等参与者到齐。给网络加带宽，未必能解决后一种问题。

这里用到的“深度可观测性”，也就有了具体含义：用低干扰的 CUDA 事件计时记录计算和通信，把不同工作进程的事件放在同一条时间线上，再沿着依赖关系寻找最初的延误。单看平均 GPU 利用率，很容易把这种差异抹平。

作者还遇到过另一类**慢节点**：某些机器完成同样前向计算，总比其他机器多花约 10% 时间。这种差异在多个实验中重复出现，隔离这些机器后整体表现改善。有的慢机器在单卡矩阵乘法小测试里并不明显，真正进入分布式训练才暴露影响。[^stragglers]

还有一类更隐蔽的故障：坏 GPU 卡在通信操作里，导致其他节点接连超时。最后屏幕上可能到处都是报错，但最早出问题的节点反而没有正常留下退出日志。把“谁正在等谁”画出来，才有机会从连锁反应找到源头。

这三种情况提醒我们，运行慢、报超时、没有新日志，都只是症状；定位要靠它们之间的时间和依赖关系。

<a id="recover-training"></a>

## 8. 练到一半坏了，怎样继续？

训练规模足够大、持续时间足够长，就不能把设计建立在“所有部件一直不出错”之上。MegaScale 的办法是让故障可发现、可隔离，并尽快恢复已经做过的工作。[^recovery]

系统中有负责协调的进程、各节点的执行进程，以及与 GPU 工作进程配合的心跳监测。发现异常或心跳超时后，大致经历这样的过程：

**暂停训练作业 → 诊断并找出故障节点 → 隔离故障、补入健康节点 → 从 checkpoint 恢复训练。**

这不是一边完全不停地训练，一边透明地换掉坏卡。恢复会有停顿，也可能需要重做最近尚未保存的训练进度。

诊断本身也要控制成本。检查范围太窄，容易漏掉故障；一出问题就对整个集群做所有测试，又会增加停工时间。论文根据故障信息安排诊断，并结合日志、心跳、网络流量等信号。有些细微异常仍需工程师借助工具处理。

**Checkpoint 可以理解为能继续训练的存档。** 它保存模型参数、优化器等训练状态。MegaScale 先把 GPU 上的状态复制到主机内存，再由后台写入持久存储，减少训练等待写盘的时间。前一步仍会阻塞几秒；只放在主机内存里，也还不等于已经可靠保存。恢复时，共享同一份状态的工作进程不用各自从存储系统重复读取，可以由一个进程读取后再广播给其他进程。

论文展示了一次持续数周、使用超过万卡的生产训练：模型有数千亿参数，训练数据量为数万亿 tokens；期间发生了**超过 100 次训练重启**，损失仍继续收敛。作者报告，超过 90% 的相关软硬件异常可以自动识别和处理，其余问题借助诊断工具解决。[^production]

这份记录里的稳定性，不是“从来没坏过”，而是“多次出错后仍能接着推进”。作者还分别报告：故障发现及诊断测试平均不到 10 分钟，从最近的 checkpoint 追上崩溃前进度可在 15 分钟内完成。论文没有把这两项写成可以直接相加的统一停机时长保证。

另一个结果是**有效训练时间率超过 90%**。作者用训练迭代次数乘以每步训练时间，再除以总训练时间，描述时间中有多少真正花在训练迭代上。这项指标与 MFU 不同：前者关心长时间运行中停工、恢复等损失，后者关心训练推进相对理论计算潜力的效率。前面的 55.2% MFU 性能表，也不能直接当作这次生产任务每一刻都达到的数值。

网络故障则提供了一个具体反例：接口反复断开、恢复，可能让训练停滞。适当调整超时能避免过早退出，但反复掉线的根因还要追到网卡、线缆、交换机之间的链路质量。**更能容忍故障，不等于故障已经被修好。**

<a id="place-in-history"></a>

## 9. MegaScale 在这条发展路线里，补上了什么？

回到前几节的共同问题：如果要训练更强的模型，工作怎样安排才做得完？

- **Scaling Laws 与 Chinchilla**讨论模型规模、训练数据和计算预算怎样分配。
- **ZeRO**处理训练状态的重复存储，让更多显存用于真正需要保存的内容。
- **RefinedWeb 与 LAION**展示原始网页资料怎样变成可用的数据，以及怎样通过训练检验它们。
- **MegaScale**进一步处理这些资源投入之后的执行问题：分工、通信、等待、故障和恢复。

这是问题之间的承接，不表示这些论文按本系列顺序发表，也不表示 MegaScale 的实验一定使用了前两节的数据集。

从历史看，MegaScale 的价值在于公开了万卡单个训练作业的系统设计和生产经验；从方法看，它把模型结构、优化器、执行调度与硬件条件放在一起考虑；从团队条件看，作者能观察到长期、大规模运行才会暴露的故障。这些经验很难只靠一张卡上的漂亮小实验得到。

讲义与访谈强调了这类公开经验的稀缺性。但“首篇公开万卡论文”“某时期只有几家公司能做到”，以及访谈后段拿不同公司的 GPU 数量、带宽和 MFU 所作的比较，涉及更广泛的历史或硬件条件，不能由这篇论文一并证明。本文保留它们提出的问题，不把那些未核定的数字和排名写成事实。

对规模较小的系统，也有可以借鉴的提问方式：等待发生在哪一步？这个进程在传输，还是在等另一个进程？出错后究竟从哪里继续？这些问题不要求先拥有万卡集群。

**[推测]** 对一个由多个程序或 Agent 协作的学习流程，同样可以分别记录有效产出速度、等待原因和失败后需重做的工作。不过，这是从系统设计得到的类比；MegaScale 的吞吐数字、恢复指标和训练并行方案，不能直接迁移为 Agent 编排的性能结论。

[下一节的稀疏 MoE](AI演义_15_稀疏MoE_大模型怎样只计算一部分_科普讲解_20261105.md)会从另一侧接过资源问题：如果想增加模型容量，是否必须让每次输入都经过所有参数？MegaScale 改善大规模训练怎样执行，稀疏 MoE 则讨论一次输入实际调用哪些计算。
