# AI演义·14｜MegaScale：让万卡训练持续运行

[返回总览第 14 节](../AI演义_笔记分析与项目整合报告.md#paper-megascale) · [上一章：LAION](AI演义_13_LAION_图文怎样变成训练数据_科普讲解_20261105.md)

一万张 GPU 分别处理许多任务，与共同训练一个模型，是两种不同的系统要求。单个大作业中，各卡的计算存在依赖，一个结果迟到就可能使许多进程等待。

2024 年，ByteDance 与北京大学的作者在 MegaScale 论文中介绍万卡训练系统，包括 **1750 亿参数模型在12,288张GPU上的性能**，以及数周运行中慢节点、程序抖动和故障恢复的案例。[^paper] 它关心每一步怎样更快，也关心训练能否在多次故障后继续推进。

<a id="one-training-job"></a>

## 1. 从一次更新到长期训练

一次训练步通常处理一批数据，完成前向预测、损失计算、反向传播与参数更新。模型较大时，权重、梯度、优化器状态和激活可能装不进单卡，计算也需要多设备分担。

各卡仍在共同更新一个模型，需要在正确时机交换结果。每步耗时决定短期效率，停工、丢失进度和恢复则影响最终完成时间。论文用算法与系统共同设计改善执行，再用可观测性定位长时间运行中的问题。

<a id="parallel-work"></a>

## 2. 不同并行方式拆分不同对象

| 方式 | 分担什么 | 需要交换什么 |
|---|---|---|
| 数据并行 DP | 不同训练样本 | 梯度等信息，以保持一致更新 |
| 流水线并行 PP | 模型前后不同层 | 激活与反向信息 |
| 张量并行 TP | 同一个大算子的不同部分 | 分块所需输入和结果 |

用一个8卡教学配置说明：模型先分前后两个阶段，每阶段由两卡分担算子，合计四卡；再复制一组四卡处理不同数据，就形成三种并行的组合。模型副本在此由多卡共同承载。3D并行已有 Megatron-LM 等研究基础，MegaScale 进一步优化其规模化执行。[^parallel]

[ZeRO 第二阶段](AI演义_11_ZeRO_多卡怎样分担训练显存_科普讲解_20261105.md)在数据并行组中分片保存梯度和优化器状态，配合 reduce-scatter 和 all-gather。序列并行 SP 则将 LayerNorm、Dropout 等操作的部分中间结果沿序列分担，与张量并行配合节省激活显存。

并行组还要对应物理连接。频繁通信的 TP 倾向于留在服务器内，使用较快卡间链路；DP 与 PP 可跨服务器安排。逻辑分工和设备位置共同影响效率。

<a id="algorithm-and-system"></a>

## 3. 算法也要适合执行方式

MegaScale 不仅优化通信，还改变部分模型与训练设置。[^algorithm]

并行 Transformer block 让 Attention 与 MLP 从同一个归一化输入分别出发，再合并结果，增加可并行的工作；这与先 Attention、后 MLP 的串行计算不同。滑动窗口注意力减少单层读取范围，多层叠加后信息可以传播得更远，但单层不再直接读取所有位置。

LAMB 用于支持更大 batch。一个 batch 拆成多个 microbatch 后，上下游可同时处理不同小批次；流水线填充和排空时的闲置称为气泡。若阶段数、DP份数和microbatch大小不变，增大batch能让中间持续忙碌的时间更长，摊薄气泡。单纯增加DP副本不一定达到同样效果。

这些改动需要检查收敛。论文用 **13B（130亿）模型**做微实验：并行block和窗口注意力在超过 **100B token** 后，与基线loss相近；四倍batch的LAMB在约 **250B token** 后达到与ADAM相近的loss。[^convergence] 这是有限设置下的训练证据，不是后面万卡性能实验的完整下游质量评价。

<a id="overlap"></a>

## 4. 按依赖重叠通信与计算

如果整个矩阵乘法必须等全部分块数据到齐，传输与计算会依次占用时间。切成小块后，第一块收到即可开始计算，其余数据同时传输，完成的结果也能继续发送。依赖没有消失，但部分传输可落在其他计算期间。[^overlap]

论文分别调整三类调度：

- DP按模型块提前收集参数，在反向后汇总梯度，处理首段收集与末段归并的等待。
- PP拆开被绑定的发送和接收，只保留真正的数据依赖，分别异步进行。
- TP／SP把矩阵乘法分块，与数据收集和分发交错，利用较大的前馈计算重叠通信。

切块与调度也有开销。优化需要分清等待来自计算依赖，还是实现把本可分开的操作绑在一起，而不能简单假定通信全部被隐藏。

<a id="outside-gpu-kernels"></a>

## 5. 数据、初始化和网络

GPU同步当前梯度时，CPU可准备下一批数据。同服务器的TP进程需要相同输入，论文用共享内存和单个加载器减少重复读盘。算子侧使用 FlashAttention-2 和融合操作，减少小kernel启动及反复访存。[^plumbing]

通信组初始化也是恢复成本。在 **2,048张Ampere GPU** 上，原实现约需 **1,047秒**；更换阻塞式键值服务后为 **361秒**，再调整初始化顺序、减少全局屏障后降至 **5秒以内**。超过万卡时，作者报告 **30秒以内**。这些收益分属不同改动，不能全归给更换某一个组件。

服务器间网络还涉及拓扑、路径冲突、拥塞与重传。较高标称带宽不保证每次传输都顺畅，并行组摆放也会改变网络压力。

<a id="performance-evidence"></a>

## 6. 性能、扩展和收敛分别看

MFU（Model FLOPs Utilization）比较实际模型训练吞吐与充分利用硬件计算峰值时的理论吞吐。它反映计算潜力转成训练进度的程度，不是开机或繁忙GPU的比例。[^performance]

Table 2 的一组同配置比较使用 **175B模型、12,288张GPU、batch 6,144、序列长度2,048**：

| 系统 | 每步时间 | 每秒处理的token | MFU |
|---|---:|---:|---:|
| Megatron-LM 基线 | 8.57秒 | 1,466,800 | 41.2% |
| MegaScale | 6.34秒 | 1,984,000 | 55.2% |

每步约处理 `6,144 × 2,048 = 12,582,912` token，除以舍入后的6.34秒，约得每秒198万。[^throughput-reading] MFU增加 **14个百分点**，约为基线 **1.34倍**。它不是说其余44.8%的卡未工作，通信、访存和流水线空档都会影响这个比值。

基线为论文选定的 Megatron-LM 版本，MegaScale 又包含算法改动，因此性能表需结合前面的收敛检查理解。

### 强扩展与弱扩展

固定175B模型和batch 6,144，从 **3,072卡增至12,288卡**，吞吐增加，MFU却由 **59.1%降至55.2%**。这属于强扩展：工作量固定，单卡可计算的部分变少，通信更难摊薄。

530B模型的另一组实验随设备增加而增大batch，在 **2,240、4,480、11,200卡**上MFU为 **54.3%、54.1%、54.3%**，属于工作量也增加的弱扩展。[^scaling] 它不能代替固定任务的线性加速验证。Table 2中按处理300B token计算的训练时间，也不是后面生产作业的实测完成时长。

### 优化怎样累积

175B模型、256卡的逐步加优化实验为：[^ablation]

| 累计加入的改动 | MFU |
|---|---:|
| Megatron-LM，batch 256 | 47.7% |
| 并行block和窗口注意力 | 53.3% |
| 再加TP、PP、DP通信重叠 | 59.5% |
| 再加算子、数据等优化 | 62.3% |
| 再用LAMB，batch 256→768 | 65.3% |

这里合并了原表相邻类别，网络优化在双方已开启。最后一步同时改优化器和三倍batch，与13B收敛实验的四倍batch不同；各增量也不能直接套到万卡配置。

<a id="why-training-slows"></a>

## 7. 通信在等待，根因可能在上游

作者发现某次训练越跑越慢，便依次检查计算、最后的梯度汇总、带宽和各进程进入同步的时间。前向、反向和优化器耗时大体稳定，带宽也未明显下降，延迟却来自各进程到达汇总点的时间越来越不齐。

继续向上游追查，发现不规则垃圾回收及部分PyTorch操作引入执行抖动。修改相关代码后，原先明显的MFU下降不再出现。[^diagnosis] 通信操作里的时间既可能用于传数据，也可能在等参与者到齐；单看总耗时会把两者混在一起。

系统用低干扰CUDA事件计时，将不同进程的计算、通信放到同一时间线，沿依赖寻找最早延误。另一类慢节点在相同前向计算上约多花 **10%时间**，单卡矩阵小测试可能看不出来，进入分布式作业才暴露。隔离后整体表现改善。[^stragglers]

坏GPU还可能卡在通信中，使其他节点超时，自己却没有正常退出日志。最后报错最多的位置未必是起点，需要结合依赖关系分析。

<a id="recover-training"></a>

## 8. 从故障中恢复进度

MegaScale 用协调进程、节点执行进程和心跳监测发现异常，然后暂停作业、诊断、隔离故障节点、补入健康节点，并从checkpoint恢复。过程有停顿，也可能重做最近尚未保存的进度。[^recovery]

诊断按故障信息选择范围，结合日志、心跳和网络信号，避免每次都做全套集群测试。细微问题仍需工程师处理。

Checkpoint保存可继续训练的参数和优化器等状态。系统先将GPU状态复制到主机内存，再后台写入持久存储；前一步仍阻塞几秒，主机内存也不等于已可靠落盘。恢复时，共享同一状态的进程可由一个读取后广播，减少重复IO。

一项数周、超过万卡的生产训练使用数千亿参数和数万亿token，经历 **100多次重启**后loss仍继续收敛。作者报告 **90%以上**的相关软硬件异常可自动处理，其余借助诊断工具解决。故障发现及诊断平均 **不到10分钟**，从最近checkpoint追上崩溃前进度可在 **15分钟内**完成；两项不能直接相加成统一停机保证。[^production]

该运行的有效训练时间率也超过 **90%**，按迭代次数乘每步时间、再除总时间计算。它关心长期停工与恢复损失，MFU关心训练相对计算峰值的效率，两个百分比并不相同。前面55.2%的性能表也不代表这项生产作业每时每刻的表现。

反复断开又恢复的链路可能造成停滞。延长超时可减少过早退出，网卡、线缆或交换链路的根因仍需另行修复。

<a id="place-in-history"></a>

## 9. 将资源计划变成持续执行

Scaling Laws选择预算，ZeRO分担状态，数据工程准备材料，MegaScale则公开大规模单作业如何安排分工、通信、等待与恢复。它并未声称实验使用了前两章的数据，也不能独自证明“首篇万卡论文”或同期公司排名。

[推测] 较小的程序或Agent流程也可以分别记录产出速度、等待原因和失败后需要重做的工作，借鉴沿依赖定位问题的方法；训练吞吐和恢复数字不能直接转成Agent编排的性能结论。

<a id="questions"></a>

每步更快但频繁停工的系统，未必更早完成任务。监测时可以同时看持续训练时间、故障恢复和通信等待，确认优化真正减少了总耗时。[下一章稀疏MoE](AI演义_15_稀疏MoE_大模型怎样只计算一部分_科普讲解_20261105.md)会从另一侧处理资源：增加容量时，每个输入是否必须计算所有参数？
