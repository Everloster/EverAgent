# GPT-6 软件维护：从广义侦察到证据驱动清理

> 原文：OpenAI Core Experimentation 团队 Rodrigo Roim，[Maintaining software with the GPT-6 family](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)，2026-10-15。核验日期：2026-10-20。

## x → f → f(x)

- **x：作者在处理什么问题？** 当 coding agent 显著提高代码产出速度后，维护债务也同步增长；传统静态分析难以跨越动态调用、feature flag、历史实验、生产遥测和组织知识，怎样让 agent 安全地发现并清理这些问题？
- **f：作者的回答是什么？** 把软件维护设计成“广义侦察 → 多源证据 → 小型可审查改动 → 人类复核 → 反馈改写提示 → 扩大范围”的循环，并根据任务收益与错误模式选择模型和推理档位。
- **f(x)：接受这个回答后怎样行动？** 不让 agent 直接“大扫除”，而是要求它证明候选项为什么可删、给出生产与历史证据、按小 PR 交付，并用接受率、成本、运行时间和实际资源节省决定是否扩大。**验证状态：原文是一手生产经验并给出大量内部数字，但没有公开数据集、完整候选分母和独立复现。**

## 一页结论

这篇文章表面在讲“用 GPT-6 清理代码”，真正展示的是一种新的维护 Harness：**模型负责跨系统调查和提出证据，人类负责高后果判断，确定性工具负责测量结果。**

最关键的六点：

1. 更强模型的优势不只是写代码，而是能从宽泛目标出发，自主决定去读 Git 历史、PR、Slack、项目跟踪器、feature flag 控制台和生产性能表。
2. 清理任务的核心产物不是 diff，而是“候选项 + 调用链 + 生产值 + 历史理由 + 成本证据 + 风险说明”。
3. 遇到 `Permanent`、kill switch、动态名称和跨服务消费者时，模型应升级给人判断，而不是自行删除。
4. 先以单个小任务校准，再扩大到目录和全仓；review comment 会反向进入下一版提示词。
5. 更贵模型适合发现错误模式，便宜模型可在补齐提示后承担批量扫描。模型升级后应重新评估旧提示，不能永久固化补丁。
6. 维护机会远多于工程带宽，最终瓶颈是优先级。必须用 CPU、CI 分钟、镜像大小或人工时间排序。

## 1. 从“静态分析”转向“证据综合”

传统 dead-code 系统通常组合静态分析与运行时日志，但容易被反射、动态名称、应急路径和未来可能启用的代码误导。原文中的 GPT-5.6 Sol 已能在给定区域和明确验证标准后编写分析工具并清理代码；GPT-6 Astra 的增量在于，它能处理更宽泛的任务合同，自主决定需要哪些证据。

OpenAI 的首个宽泛提示只有一句：

> “Can you help identify and clean up dead code in the repo… feel free to check Slack, Statsig, or any other source you need to confirm that things are indeed no longer being used…”

Astra 随后读取历史 PR、Slack 讨论、内部项目跟踪器和生产性能 profiling 表，并逐项解释删除理由。这里最值得迁移的能力是**上下文选择**：提示没有列出固定文件清单，而是给出目标和证据门槛，让模型寻找足以裁定候选项的 owner。

这与“让模型通读整个仓库”不同。模型需要围绕一个可证伪问题收集材料：

```text
某段代码是否仍有生产调用、动态引用、应急用途或未完成迁移？
```

只有这些问题得到回答，diff 才进入 review。

## 2. 规模化清理取得了什么结果

五名工程师在主要工作之外，用约两周时间协同运行提示变体：

| 结果 | 原文数字 |
|---|---:|
| 合并的维护 PR | 超过 **1,400** 个 |
| 删除代码 | 超过 **80 万行** |
| 某服务容器镜像 | **3.31 GB → 1.72 GB**，下降 **48%** |
| 删除视觉快照变体 | 约 **400** 个 |

这些数字说明 agent 可以把过去昂贵的专项分析变成高吞吐工作流，但不能据此计算平均 PR 质量：原文没有给出总候选数、拒绝 PR 数、回滚数或误删率。

## 3. 更难的任务：清理 stale experiments

过期实验比 dead code 难，因为代码可能仍在运行，资格判断可能变化，flag 还可能是 kill switch。团队为此把提示收紧成一份证据合同：

- 检查 live Statsig 配置、Git 历史和重叠 PR；
- 保留生产 safeguard、kill switch、SDK fallback 与本地 override；
- 查找 enum、常量、wrapper、alias、schema、动态拼接名称和跨服务消费者；
- 每个候选给出生产值、owner、调用点、评估或 CPU 成本；
- 每个清理只创建一个小型 draft PR；
- 不修改线上配置或服务。

结果不是立即修改全仓，而是先生成按 owner 和文件划分的并行工作流报告。模型还发现一个标为 `Permanent` 的全局 feature flag 导致 CPU fan-out。它没有自行删除，而是提交给人类复核；删除后估算为主要受影响服务节省 **0.42% CPU**。

这个案例界定了 agent 的正确角色：**模型可以发现人没注意到的异常，但元数据与实际用途冲突时，结论必须升级。**

## 4. 模型能力、成本与提示词不是固定绑定

团队在超过 **6,000 个文件、100 万行 Python/TypeScript/Go/Rust 代码**的目录上，用同一提示比较三种配置，并人工核验发现：

| 配置 | API 成本 | 接受的发现 | 单个发现成本 |
|---|---:|---:|---:|
| GPT-6 Astra Ultra | **$109.06** | **142** | **$0.77** |
| GPT-6.1 Sol Ultra | **$15.12** | **131** | **$0.12** |
| GPT-6.1 Sol Medium | **$5.27** | **86** | **$0.06** |

Sol Ultra 取得 Astra Ultra **92%** 的发现数，只消耗 **14%** 的 API 成本。但差异不是随机噪声：Astra 更容易发现“作为其它 feature flag 依赖的常量 flag”，Sol 会漏掉这一类。原文的处理不是永远使用 Astra，而是把漏检模式写回提示，让更便宜的模型补齐。

由此可得出一个比“用最强模型”更实用的策略：

```text
强模型发现盲区 → 人类归纳错误模式 → 提示/工具补丁 → 便宜模型批量执行
                                      ↓
                           新模型发布后重新验证是否仍需要补丁
```

## 5. CI 优化说明了为什么要按收益排序

团队让 Codex 读取 CI 历史，列出候选方案，并按“每天预计节省的 CI 分钟”排序。后续落地约 **30 个 CI 优化 PR**：

- median CI 完成时间约 **10 分钟 → 4.5 分钟**；
- P90 约 **12.5 分钟 → 6 分钟**；
- 一个保留全部 63 个测试的 resolver suite，通过补 mock 从 **592.6 秒 → 29.8 秒**，下降约 **95%**。

这说明高吞吐 agent 的新风险不是“找不到优化”，而是候选过多。若没有收益估计，工程团队会把 review 时间浪费在低价值微优化上，甚至合入增加复杂度却没有足够收益的修改。原文也明确承认，部分建议的复杂度超过预期收益。

## 6. 原文六个提示词背后的设计规律

| 提示类型 | 关键设计 |
|---|---|
| Dead code 侦察 | 允许查阅多源证据，不指定固定路径 |
| 定向 stale flag 清理 | 写明 safeguard、kill switch 和一个 PR 一个候选 |
| 全仓审计 | 要求穷尽间接引用，按 owner/workstream 输出报告，禁止线上修改 |
| Flaky test | 明确“找简单、明确的修复”，不要求穷尽 |
| `AGENTS.md` 反事实评估 | 同 snapshot、同模型重放，有无单条指令各跑一次，比较质量、工具、token、耗时与成本 |
| CI 优化 | 读取真实运行历史，按每天节省的 CI 分钟排序 |

共同结构不是长 prompt，而是四个槽位：

```text
目标范围 + 必要证据 + 保留/禁止项 + 可审查交付物
```

其中第五个提示尤其重要：它把长期指令从“看起来合理的文字”变成可做反事实比较的配置代码。这与 EverAgent 现有 ACE Context A/B 的方向一致。

## 7. 对 EverAgent 与私有基础设施仓的含义

以下是基于原文的工程推论，不是 OpenAI 明示结论：

1. **重构前先做维护侦察。** 每个候选删除项必须关联真实调用、owner、Git 历史、行为回放或确定性门禁，不能仅凭“看起来重复”。
2. **按小 workstream 落地。** 根协议、领域路由、skills、scripts、私有 context owner 分开修改，避免一个巨大重写掩盖回归来源。
3. **强模型用于发现模式，主力模型用于批量执行。** 用少量高能力复核识别 GLM 主力模型的系统性漏项，再把结论固化到脚本、schema 或窄提示中。
4. **收益必须可测。** Context 改动测首行动前读取量、skill precision/recall、澄清、工具调用和 P10；基础设施维护测故障率、恢复时间、重复文档与命令成功率。
5. **安全边界不因“清理”失效。** 私有事实、凭据、发布权限和不可逆操作继续由 owner 与确定性机制控制。

## 8. 证据边界与反方判断

- 所有生产数字来自 OpenAI 自述，无法独立复现。
- “findings”经过作者人工接受，但没有统一严重度定义，也没有报告 precision、recall 或候选总量。
- 参与工程师、仓库与任务均非随机样本，成功案例可能存在选择偏差。
- 成本比较使用当时标准 API 价格，且包含 research subagents 与自动 follow-up；不能直接外推到其它 Harness。
- 大规模删除发生在已有强 telemetry、内部搜索、PR review 和 owner 体系的组织。缺少这些基础设施时，宽泛提示的风险更高。
- 原文省略了全仓 stale-experiment prompt 的部分详细说明，无法完整复现。

## 思考与追问

### 1. 我真正理解了什么？

Agent 原生维护的关键不是允许模型大规模改代码，而是让它大规模地产生**可审查证据**。吞吐提高以后，最重要的 Harness 能力变成候选排序、风险升级和反馈闭环。

### 2. 我还没搞懂什么？

- 1,400 个 PR 的拒绝、返工与回滚率是多少？
- 把 Astra 的漏检优势写回提示后，Sol 的 precision/recall 能接近到什么程度？
- 在缺乏生产 telemetry 的开源仓库中，哪些证据可以替代运行时数据？

### 3. 下一步读什么或做什么？

把本文的“证据驱动维护循环”与工具发现的复杂度路由、Deep Review 的分段复核合并，形成下一轮双仓重构的统一参照，而不是分别增加三套流程。
