# 《Agent 演义》18｜同时推进多项工作：分工、监督与整合

## 概述

同时推进几项工作时，难点会从“怎样给 Agent 提要求”转向任务边界、现场归属和最终整合。Orca 提供显式任务编排与 worker 监督；T3 提供独立 thread、worktree、委派和多模型运行。两者都支持并行，但这些入口承担的责任并不相同。[^orca][^t3]

专业用户要先决定工作能否独立完成，再决定是否委派、是否隔离目录、由谁整合。开出多个执行者后，验收仍要回到同一项工程目标。

**提炼句：** 并行工作的收益，取决于能否把独立产出收成一个经过验证的结果。

## 取景框 f(x)

**x｜问题：** 一个人怎样用 Orca 或 T3 同时开发、调查和审查，又保持可控？

**f｜取景框：** 以依赖关系和共享现场判断并行，把任务完成与整合完成分开。

**f(x)｜判断变化：** 不把全部工作平均分给多个 Agent；先找能独立产生结果的部分，并给相互依赖的修改安排顺序。

## 三项工作，不一定要三个写入者

仍以 Card Gallery 为例：扩展搜索字段、调查中文匹配边界、检查分页交互。边界研究可以只读，输出几个具体反例；API 与前端修改需要先对齐查询和分页合同；最终审查应针对整合后的版本。

可采用这样的安排：实现者负责一份主改动；调查者返回输入与预期结果；页面审查者等待可运行版本，再给定位反馈。若 API 与 UI 确实能按确定接口独立开发，才分两个 worktree，预先确定谁负责共同测试。

```text
匹配边界调查 ──具体例子──→ 实现
                              ↓
                         页面与 API 验证
                              ↓
                       整合版本的最终审查
```

这是自拟任务关系。只读调查与实现可并行，依赖当前实现的测试不宜提前宣布通过。

## Orca：把工作列成可监督的任务

在项目中给独立修改安排 worktree，给只读调查安排清楚的会话位置，再把目标、依赖、执行者与结果范围列明。Orca 的编排界面和工具用于派发、监督、消息与收回结果；详细调度机制见附录 C。[^orchestration]

专业用户值得关注的是三类变化：任务何时具备开始条件；worker 是否真的开始；哪些工作在等问题、审批或依赖。任务图能帮你辨认等待，但任务本身仍需要人或 Agent 先建立。所查 Coordinator 循环消费预建任务，不自动把一句需求变成完整分解。

有新信息时，把它送给当前负责者，说明影响的任务与合同。例如调查发现“`.*` 应作为字面输入”，发给实现者的是新增验收约束；发给审查者的是要核对的例子。不要把同一段模糊补充广播后期待各自理解一致。

收回结果时，检查改动位置、测试版本和未完成项。worker 报告完成后，仍须在整合现场审查与运行共同测试。一个审查任务成功发现 bug，既是有效产出，也意味着工程目标还要修订。

## T3：让独立工作有自己的 thread

独立需求通常新建 thread，涉及独立修改再配 worktree。由主线程拆出的工作，可以使用 T3 委派，生成可互动的子 thread；provider 原生子 Agent 则可能只读观察，反馈经父线程处理。先确认是哪一种，才知道去哪里沟通。[^subagents]

在新 thread 中多选模型，会为同一输入生成分开的 thread 和 worktree，适合比较实现方案。它增加的是独立方案与后续审查工作，并不自动整合成一个答案。只想让另一位执行者接着同一项任务，当前 thread 切 provider 更直接。[^threads]

对子任务给出可以独立返回的成果，例如“列出违反搜索合同的输入及对应文件”，而不是“帮主线程看看”。主线程接到结果后负责选择、整合和再验证；子任务的权限上限与父线程相关，父 Stop／Archive 还会影响活跃委派。

## 共享目录最容易误判的两件事

两个 thread 使用同一 checkout，会共享分支和未提交文件。一个 thread 里看到变更，并不说明它由该 thread 产生。独立 worktree 可以区分文件产出，但仍可能共享端口、缓存或本地数据库。

第二个问题发生在回退：你想撤销 A 的一轮修改，B 可能已在同一目录继续工作。回退对话与恢复文件各有条件，恢复应先检查其他使用者。T3 的 checkpoint 安全检查针对这一类关系；产品按钮不能替你决定是否应该覆盖现场。[^restore]

| 情况 | 更合适的组织 | 收回结果时检查 |
|---|---|---|
| 独立调查，不改文件 | 只读会话或子任务 | 例子、依据、影响的要求 |
| 独立功能，改动可区分 | 独立 thread／worktree | 基线、diff、验证与整合方式 |
| 两个方案比较 | 分开的现场 | 同一合同下的取舍与结果 |
| 同一文件连续修订 | 顺序接力 | 旧执行已停，当前文件与要求一致 |
| 整合后审查 | 针对整合版本的审查任务 | 新版测试、未解决意见 |

## 什么时候并行并不划算

任务很小、接口尚未定、多人要改同一核心文件时，协调与整合可能比实现本身更贵。此时先用一个执行者澄清合同，再委派只读调查或最终审查，会比同时开很多写入者容易管理。

源码与用户指南支持上述组织差异，但本轮没有实跑多 Agent 开发，不提供并发吞吐排名。实用的评估方式是挑自己经常做的两项独立工作，观察等待是否减少、结果归属是否清楚、整合是否多出了返工，再决定是否扩大并行。
