# 《Agent 演义》12｜T3：什么时候换模型，什么时候换 Agent

## 概述

T3 的模型选择器可以在一条 thread 中换模型或换 provider，但专业用户更需要判断什么时候值得换。模型选项变化、换一个 Agent 做同一项工作、增加一个并行执行者、开始一项新任务，是四种不同的使用选择。[^composer][^threads]

在已有计划和改动上接续时，换执行者可以保留工作主线；需要独立调查、不同方案比较或单独验收时，新 thread／worktree 往往更清楚。切换后的关键检查是要求、文件和验证条件，而不是是否还在同一个聊天窗口。

**提炼句：** 先决定下一步工作怎样组织，再决定模型菜单怎样选。

## 取景框 f(x)

**x｜问题：** 一项开发工作中，什么时候换模型、换 Agent，什么时候另开线程？

**f｜取景框：** 按下一阶段的责任和独立性选择执行方式，把模型选择放进工作流。

**f(x)｜判断变化：** 不把“换个模型试试”作为所有卡点的默认动作；先判断是输入不足、工作该分工，还是确实需要更换执行者。

## 四种选择，四种用途

| 你现在需要什么 | 操作方向 | 适合的结果组织 |
|---|---|---|
| 同一执行环境继续，调整模型或选项 | 当前 thread 的模型选择器 | 一条工作历史，下一阶段采用新选择 |
| 把已有计划和改动交给另一个 Agent | 当前 thread 切 provider | 保留工作主线，检查交接材料 |
| 同时推进独立调查或审查 | 委派子任务，或新 thread＋worktree | 分开的责任、结果和文件现场 |
| 比较不同实现路线，或开始新任务 | 新 thread；必要时独立 worktree | 不同方案分别验收 |

T3 文档还提供新 thread 中同一 prompt 的多模型运行：在模型选择器中多选后，会创建分开的 thread 与 worktree。它适合方案比较，与一条 thread 内连续换执行者不同。[^threads]

## 先给切换一个明确的理由

假设 Card Gallery 的搜索合同已经讨论清楚，现在要实现 API。你习惯用一个 Agent 制定计划、另一个实现，可以在计划形成后切换 provider；这是一种个人工作方式，不是本卷测出的模型能力排名。

如果当前 Agent 一直改不对标签与分页的关系，先检查要求是否明确：查询是否保留、分页何时归一、结果顺序怎么定义。输入含糊时，更换模型也可能重复同样的问题。

如果需要另一位 Agent 独立判断方案，单独 thread 或委派更合适。独立审查者不必继承上一位的全部判断；你可以只提供目标、当前 diff 与验收条件，让它形成独立意见。

## 在同一 thread 中接续工作

完成当前阶段后，在模型选择器选择下一执行者，再发一条明确的续接要求。例如：

```text
沿已有计划实现搜索 API。
查询同时匹配 title 和 description，忽略大小写，做字面子串匹配。
搜索和 tag 取交集，保留原始顺序；page=0 返回 400。
这轮只修改 api/ 和 tests/，先运行现有测试，再补边界用例。
完成后给出改动文件、测试命令和仍未验证的部分。
```

这是本卷自拟提示，可按项目改写。它把阶段责任和关键条件重新写清楚，减少目标依赖一段很长的旧聊天。

如果 Agent 仍在工作，先决定这条消息是调整当前工作还是下一轮任务。T3 的 Follow-up behavior 提供 Queue 和 Steer，支持范围由 Agent 决定；改变执行者也需要协调当前工作。一般可在阶段结束后交接，减少两个执行者同时解释同一项变更。[^composer]

## 切完后看什么

第一，检查当前模型与 provider 是否是目标选择。项目默认、上次使用的模型和具体选项可能影响新 thread；模型名里相似的标签不一定指向同一个接入。

第二，让下一执行者确认当前文件与关键要求。T3 会转交预算内的历史，长条目和附件、原生 reasoning、工具状态并不全部复制。遗漏的旧材料有检索入口，但关键约束可以直接在新消息中重申。[^handoff]

第三，核对新验证属于当前代码。上一轮的测试输出可作为背景，但代码改过后需要适用的测试。若你切换到审查阶段，让它围绕 diff、合同和失败路径给意见，避免继续扩大实现范围。

这里需要的机制说明只有一层：T3 保留应用 thread，原生 provider 会话按能力复用、恢复或通过历史接力。更详细的协议、推理与缓存条件见[技术附录 B](Agent演义_附录B_上下文推理与缓存_20261126.md)。

## 账户与用量怎样影响选择

同一个 provider 也可能有多个账户或配置实例。先确认目标账户可用、模型可选、权限合适，再把它纳入工作流。达到额度上限时，可以等待产品提供的恢复时间，或在确认交接范围后改用其他执行者。[^usage]

Usage 里的 API-equivalent cost 是按模型价格估计的使用价值，不等于订阅账单。改变模型是否更省、缓存是否更好，不能只从切换速度或聊天窗口看出来；本卷没有真实调用的费用比较。

最实用的经验是把切换放在阶段边界：计划完成、需要实现；实现完成、需要审查；卡点已经被明确描述、需要另一种解法。每次切换都带上下一阶段要负责的具体结果。
