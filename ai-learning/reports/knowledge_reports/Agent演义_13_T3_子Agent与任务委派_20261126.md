# 《Agent 演义》13｜T3：委派、子 Agent 与并行任务

## 概述

T3 区分由产品委派的子 Agent 与 provider 自己生成的原生子 Agent。前者可以有独立 composer、不同执行者、worktree 或 linked machine；后者的观察与交互方式受原生实现约束，常需通过父线程沟通。[^subagents]

专业用户应先决定任务是否独立、结果怎样回主线，再选择委派、另开 thread 或顺序切换。并行适合拆得清楚的工作，独立审查还需要恰当的输入范围。

**提炼句：** 把任务交出去之前，先规定它交回来什么。

## 取景框 f(x)

**x｜问题：** 怎样用 T3 的子 Agent 和委派推进工作，而不把更多线程变成更多协调负担？

**f｜取景框：** 从责任、隔离和回报选择协作方式。

**f(x)｜判断变化：** 不把子 Agent 都当成可随意输入的普通聊天；先辨认类型和权限，再安排工作与反馈。

## 哪种工作值得委派

Card Gallery 可以委派接口实现、界面状态验证和独立审查。接口实现需要明确合同与改动范围；验证者需要当前版本、运行命令和结果标准；审查者需要 diff 与合同，可以独立提出问题。

两个执行者同时修改同一组件，协调成本可能超过并行收益。对高度依赖的任务，先完成前一阶段再接力更清楚。

## 两种子 Agent 怎样不同

| 类型 | 怎么开始 | 你怎样介入 |
|---|---|---|
| T3 委派 | Agent 调用产品的委派工具，可选择 provider、worktree 或 linked machine | 作为有独立 composer 的子 thread 观察和沟通 |
| provider 原生子 Agent | 原生 Agent 在自身执行中创建 | 常为只读观察，消息交给父 thread |

在对话的 subagent card 或 Agents 中查看时间线。web／desktop 可以在右侧面板查看，保持主线程可见；移动端入口按所用版本显示。[^subagents]

## 给委派者的要求

```text
委派一个独立审查任务，只检查搜索、标签和分页合同。
提供当前 diff 与测试说明，不要求它沿用实现者的结论。
返回可复现的问题、对应文件和必要的修订建议。
主线程负责整合，不让审查者同时扩大实现范围。
```

这是自拟协作要求。实际委派能力、是否允许修改与可用模型，由当前 provider、父线程权限和环境决定。

T3 的 `@` 模型引用可以表达希望使用哪个模型进行委派，不一定意味着立即更换父 thread 的模型。使用时检查实际生成的子任务与执行者，而不是只看提示里写了名字。

## 父线程怎样收回结果

先确认子任务状态，再读结果和验证范围。API 与 UI 分别完成后，应有明确的整合现场；共同测试针对整合版本进行。

对子 Agent 的反馈也要送到正确位置。产品委派的子 thread 与原生只读子 Agent 的交互方式不同；如果原生子任务有审批或问题，应按父线程出现的请求处理。

父 Stop、Archive 与子任务生命周期存在联动。T3 文档说明停止父线程会停止其 delegated subagents，归档前需要处理活跃委派。子任务还受父线程权限上限约束。[^subagents]

## 与切换和多模型比较的区别

同 thread 切执行者适合阶段接力；委派适合独立任务回到主线；多模型新 thread 适合分别比较方案；side chat 适合问相关问题。

这些选择各自有结果组织方式，不能因为界面都显示多个 Agent 就视为同一功能。真正的使用标准是：每一项工作由谁负责、在哪修改、怎样验证，以及结果怎样回到最终交付。

原生与应用委派的机制补充见[技术附录 C](Agent演义_附录C_协作投递与恢复_20261126.md)。
