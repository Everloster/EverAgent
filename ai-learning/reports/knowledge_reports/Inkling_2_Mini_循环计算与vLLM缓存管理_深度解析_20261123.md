# Inkling 2 Mini：同一组权重怎样执行三轮，vLLM 又怎样管理缓存

## 概述

Inkling 2 Mini 让中间十二层执行三轮，共享权重，通过消息传递读取前轮信息。vLLM 分轮保存 KV 与卷积状态，融合消息读取和控制器计算，以减少额外开销。

权重存储、计算次数和缓存需求同时变化。固定三轮与可变轮数研究模型有不同合同，减轮、共享 KV 和草稿网络也各自改变运行条件。 [原文](https://vllm.ai/blog/2026-11-20-inkling2-mini)

**提炼句：** 共享权重，仍要分别计算每一轮、保存每一轮的状态。

## 取景框 f(x)

**x｜问题：** 中间层权重重复使用以后，省下了什么，又增加了哪些计算和运行状态？推理引擎怎样保持各轮的正确对应？

**f｜取景框：** 从资源与身份的分离看循环模型：参数决定存什么，层执行决定算什么，运行状态决定下一步读什么。同一组参数不意味着不同轮次具有同一个计算状态。

**f(x)｜判断变化：** “模型较小”只能回答一部分部署问题。选择轮数要比较任务质量、计算量和缓存容量，缓存共享要核对历史读取语义，算子融合要保留消息的接收位置。

## 先数清楚：24 层权重，48 次层执行

模型的文本解码器有 24 层。0—5 层构成前段，6—17 层构成循环核心，18—23 层构成后段。前后各执行一次，中间执行三轮。因此每个 token 的层访问次数为：

```text
L(P) = 6 + 12P + 6
```

这里，`P` 是核心的轮数，`L(P)` 是一次前向过程访问这些文本层的次数。三轮对应 48 次；它不是新增了 48 组独立层权重，也不是生成了 48 个思考 token。图像编码器、消息控制器、专家路由和草稿网络的工作不包含在这个简单计数里。[固定版本配置](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/b85c3cfa615fc413cc9af3379f491b963f3b586a/config.json)、[模型卡](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/b85c3cfa615fc413cc9af3379f491b963f3b586a/README.md)

参数数字也要分开读。vLLM 博文概括为 26B 总参数、3.5B 活跃参数；发布方模型卡写的是 **26.4B 总参数、3.4B 基础活跃参数**，并估计每增加一轮核心执行，相当于再执行约 1.0B 的活跃参数，三轮合计约 5.4B。两份官方材料对基础活跃参数有 0.1B 差异，本文保留原口径，采用模型卡的详细说明解释计算量。

所谓“有效活跃参数”是在描述重复执行的工作量，不能加到总参数上当作额外存储。它也不能代替 FLOPs 或延迟测量：一次注意力计算的成本还受上下文、批量和缓存命中影响；同样的参数规模，实际执行路径未必相同。

每层使用稀疏 MoE，token 从 128 个专家中选择 8 个。稀疏专家减少单次执行涉及的权重，但循环核心再次被访问时仍会执行路由和专家计算。把“稀疏”与“循环”同时放进成本模型，才不会仅凭 3.4B 就把它等同于普通的同规模稠密模型。

## 下一轮怎样接收上一轮的信息

最容易产生的误读，是以为第一轮输出直接成为第二轮输入，第二轮输出再成为第三轮输入。Inkling 的安排更特殊：**每一轮都从前段输出开始，后续轮次通过消息读取前一轮的信息。** 最后一轮完成后，后段继续处理它的结果。[vLLM 架构说明](https://vllm.ai/blog/2026-11-20-inkling2-mini)

可以用一个自拟场景理解这个选择。模型正在处理一段含条件的说明：前段形成对当前 token 的初始表示；第一轮核心做一次较深处理；第二轮保留初始表示作为起点，同时从上一轮的内部表示中读取需要补充的信息。它不必把前一轮的全部结果原封不动带进来。这个例子只说明信息路径，不证明某一轮负责语法、另一轮负责逻辑；官方资料没有给轮次分配这种固定语义。

核心每六层形成一个 attention-residual block，一轮产生两个 block。后续轮次中，每层对注意力的 query、key、value 输入及 MLP 输入分别读取消息。于是，十二层乘四类输入，得到每轮每 token 48 次消息读取。

四类输入分别进入 query、key、value 投影和 MLP，控制当前怎样查询历史、历史怎样被检索、读出什么内容，以及后续怎样变换。消息读取因此要保留接收位置：合并执行可以减少 kernel 开销，却仍要把各份结果送回对应输入。把它们变成一次共同加向量，会改变参考模型的计算路径。

读取之后，一个 rank-64 控制器按通道合并原输入与消息。博文给出的计算可写为：

```text
z = W_down [rms(x), rms(m)]
```
```text
y = (1 - tanh(W_forget z)) ⊙ x + tanh(W_gain z) ⊙ m
```

`x` 是该子层的输入，`m` 是读取到的消息；方括号表示拼接，`W_down` 将它投影到低秩中间表示 `z`。两组投影分别控制原输入和消息的系数；`⊙` 表示逐通道相乘。按原文记法，`rms` 是控制器使用的 RMS 归一化，`y` 是合并结果。

这里的两个系数不是一个概率分布。`tanh` 可以为负，两条系数也不要求相加等于一。因此“忘记多少、加入多少”只是直觉，不能将它解释成在两个来源之间按概率取平均。

## 为什么每轮要有自己的 KV cache

自回归解码时，新 token 会读取历史 token 的 key 和 value。不同轮次的状态经过了不同消息处理，即使投影权重共享，产生的 key、value 也可能不同。第三轮如果读到第一轮的历史缓存，便不再是参考模型指定的计算。

固定三轮模型的缓存数与层访问数相同：前后共 12 个，加上核心十二层的三份，合计 **48 组 KV cache、48 组卷积状态缓存**。配置中短卷积也有历史状态，所以不能只统计注意力缓存。

vLLM 将额外轮次注册成独立的 attention layer，各自拥有缓存。这样，原有 KV 管理器和前缀缓存可以处理它们，无须为了循环另建一套缓存分配逻辑。共享权重属于模型加载与执行层；缓存身份属于运行状态层。把两者分开，现有系统才有机会复用。[vLLM Serving the Loop](https://vllm.ai/blog/2026-11-20-inkling2-mini)

“48 组”还不是显存字节数。模型同时使用滑动窗口和全注意力，缓存的可增长长度不同；卷积状态有自己的形状；还要计算数据类型、KV heads、批量、页面分配和运行时余量。模型卡所说的约 20GB 混合精度 checkpoint，只描述权重文件规模，不能证明某块 20GB 显存的 GPU 能提供一百万 token 的可用上下文。

## vLLM 优化了哪些额外开销

循环增加了消息读取和控制器，如果按四类输入逐项发射多个小 kernel，GPU 会反复承担启动、读写和中间结果的成本。vLLM 把同层四类消息读取合入一个 attention-residual kernel，并将控制器权重堆叠，以 batched GEMM 执行投影；又将部分归一化和门控合并融合。[vLLM 实现说明](https://vllm.ai/blog/2026-11-20-inkling2-mini)

这降低的是执行路径中的额外开销，不等于把三轮数学计算缩成一轮。它还复用了 Inkling 2 Small 周围的融合算子，并适配 Mini 的 2,304 隐藏维度。小批量与多卡情形有进一步的通信融合，但不能仅凭存在融合，就推断所有批量和并行度下都得到同样收益。

数值顺序也是实现的一部分。博文说消息合并使用 FP32，并禁止 FMA contraction 以匹配参考。FMA 将乘加合成一次操作，可能改变舍入结果；是否更快与是否保留参考行为，是两项分别要检查的要求。

作者还区分了局部与端到端验证：给相同输入时，MoE 输出可以逐位一致；完整层访问的隐藏状态仍受归约顺序影响。文中报告了长上下文、数学及多模态测试，但没有提供足够的全部分项数值供本文复算。因此，“某个算子逐位一致”不能扩展成“整个推理系统每个输出 token 必然一致”。

## 可变轮数是另一个研究 checkpoint

`TML-d24-varloop-research` 才允许启动时指定 `loop_num_passes` 和 `loop_share_cache`。固定三轮的 Inkling 2 Mini 拒绝这两个选项。不能为固定模型加一条 override，就当作完成了官方支持的减轮部署。

可变模型在中期训练的后续阶段抽样使用一至五轮，比例为 1:2:6:2:1，后训练仍使用三轮。这使同一套权重下的轮数比较较干净，但三轮获得了更多训练；其他轮数的成绩不能代表为该轮数单独充分训练后的上限。两套 checkpoint 的后续训练不同，发布方也明确提醒不要直接作架构效果的因果比较。[固定版本研究模型卡](https://huggingface.co/thinkingmachines/TML-d24-varloop-research/blob/657b53ba5da7baefe9ff15dca5cd25f5bd3dbaa2/README.md)

博文提供的测量条件是：**一张 GB200、TP1、4K 上下文，仅前向计算**。

| 核心轮数 | batch 1 解码步 | batch 32 解码步 | KV 容量 |
| --- | ---: | ---: | ---: |
| 1 | 1.51 ms | 3.81 ms | 352K tokens |
| 2 | 2.67 ms | 5.92 ms | 233K tokens |
| 3 | 3.85 ms | 8.11 ms | 175K tokens |
| 3，共享 KV | 3.86 ms | 8.10 ms | 194K tokens |

数据来自 [vLLM 原表](https://vllm.ai/blog/2026-11-20-inkling2-mini)。batch 32 一行的“解码步”不是单个请求的完整耗时；表内没有排队、网络、prefill 或工具时间，不能直接换成线上用户每秒得到多少 token。

共享 KV 的行为也有变化：同一核心层的每轮会覆盖当前 token 的 KV，后来 token 读到最后一轮写下的值；卷积状态仍按轮保留。它是一项模型运行方式的改变，不能当作对原来独立缓存计算的无损压缩。

按原表计算，三轮共享 KV 相比三轮独立 KV 的容量提高约 10.9%；一轮相比三轮的容量约为 2.01 倍。前者少于减轮带来的收益，因为仍有卷积状态等开销。本文用 Python 复算了层访问数与这些比例，只验证表中算术，未进行 GPU 测试。

质量也未必逐项随轮数单调上升。例如研究模型卡的 WorldVQA 从四轮 14.3% 到五轮 13.5%，GraphWalks BFS 256K 从二轮 56.0% 到三轮 64.3%，五轮为 63.8%。这些自报结果未附这里可复算的显著性分析，仍提示：部署选择应看目标任务，不宜把“更多轮更好”当成每项测试都成立的保证。

## DSpark 和循环各解决什么

循环是在一个目标 token 的计算中增加层访问；DSpark 是借助草稿网络提出后续 token，再由目标模型验证。两者作用的位置不同。

这里的三层 DSpark 草稿网络读取四个固定访问点的隐藏状态，涉及前段、第二轮、第三轮和最终输出。轮数变化后，这些访问点的对应关系也变化，所以博文规定 DSpark 使用 checkpoint 默认轮数。不能在一轮研究配置上照搬三轮的草稿设置，并宣称官方支持。

博文给出的 Mini 镜像示例使用 `vllm/vllm-openai:inkling-2-mini`、`thinkingmachines/Inkling-2-Mini` 和对应的 reasoning/tool parser。实际部署还应固定镜像 digest 与模型 revision，分别验证文本、图像、工具调用和长上下文。这些启动项还需与相应 checkpoint 的轮数和 parser 合同匹配。

## 这篇文章对工程判断的价值

循环模型把“模型多大”拆成了三个问题：存多少权重，每个 token 执行多少计算，保存多少运行状态。总参数、活跃参数和轮数分别回答一部分，彼此不能代替。

对服务系统，较有价值的做法是给每轮状态明确身份，再在这个边界内融合计算与复用现有缓存设施。对模型选择，真正要比较的是目标任务质量、完整请求延迟与可服务容量。少轮会改变能力，共享 KV 会改变历史读取语义，启用草稿网络又有访问点要求；这些都需要放到同一配置中检验。

后续实机实验可以在研究 checkpoint 的一、二、三轮之间，固定数据集、上下文长度、并发、采样参数和运行时版本，同时记录任务成功率、prefill、解码、峰值显存与端到端延迟。三轮共享 KV 单列，DSpark 使用支持的默认配置单列。这是后续对照实验的设计。
