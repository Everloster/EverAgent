# Codex 参与生产故障调查：从告警、证据到修复与恢复验证

## 概述

OpenAI 将 Codex 接入生产故障调查：对照日志、指标、部署与代码提出原因，形成修复提案，经工程师批准操作，再检查服务是否恢复。Grafana 和 Kubernetes 提供具体查询与执行入口。

告警指出症状，诊断解释原因，部署改变运行状态，恢复检查回答服务是否重新可用。四步需要不同证据，不能用“修复已执行”结束整场调查。 [原文](https://developers.openai.com/blog/production-monitoring-with-codex)

**提炼句：** 修复是否完成，要回到服务结果里看。

## 取景框 f(x)

**x｜问题：** 告警之后，怎样让 Codex 从许多相关记录中找出可检验的原因，并确认一次修复真的恢复了服务？

**f｜取景框：** 从可检验的因果链看事故：哪些请求受影响，何时暴露于哪项变化，这项变化能否解释症状，去掉它之后结果怎样改变。时间、请求范围和版本是连接证据的坐标。

**f(x)｜判断变化：** “刚部署过”成为待检验线索；日志、追踪和指标要说明各自增加了什么证据。修复方案需要动作范围与恢复信号，避免基础设施正常而业务仍有积压。

## 告警把哪一道问题交给 Codex

告警通常表达一个观测条件，例如“支付接口在五分钟内的 5xx 比例超过阈值”。它能确定调查从哪里开始。原因还要通过其他记录来建立。

可以把一次调查的输入写成四部分。

| 输入 | 要回答的问题 |
| --- | --- |
| 告警及其查询 | 哪个服务、哪段时间、哪些请求出现了问题？分母是什么？ |
| 部署与运行状态 | 当时有哪些版本和实例在服务？配置是否改变？ |
| 日志与追踪 | 失败在哪个调用环节出现？相关请求怎样经过服务和依赖？ |
| 对应版本的代码 | 这条执行路径会在什么条件下产生现象？ |

连接证据之前，先确认它们是否描述同一批请求。同一服务名可能覆盖多个区域和租户，“最近部署”可能涉及多个服务，日志时间又可能晚于请求开始。查询应一起保存范围、时间、版本和请求标识：指标用来圈定异常，追踪定位失败环节，再到对应版本的代码检验条件。没有这些对应关系，增加日志数量也可能只是增加互不相干的线索。

这是文章中“给予正确上下文”的工程含义。Grafana 负责让数据源的指标、日志或追踪可查询，Codex 所在执行环境负责调用工具、取得结果和连接源码，模型再根据这些结果推进调查。哪个系统保存原始观测、哪个系统发起动作，需要在集成时讲清楚。[Grafana 数据源文档](https://grafana.com/docs/grafana/latest/datasources/)、[官方文章](https://developers.openai.com/blog/production-monitoring-with-codex)

假设订单服务在 03:01 部署了 r18，03:04 出现超时。调查者可以提出“r18 改了连接池参数”这一假设。支持它还需要几步。

先找到实际服务请求的 r18 实例，确认参数确实生效。再比较新旧实例上的同类请求，检查是否只有新实例异常。随后沿追踪定位等待发生的位置，并阅读 r18 对应代码。若旧实例也同样失败，就应继续检查共享依赖或流量变化。这个自拟例子的作用，是让“刚部署过”成为一个可检验的线索。

## 让解释能被别人检查

文章要求 Codex 的判断附证据与引用。一个可检查的判断至少包含三个相连的东西。

- **观测**。给出查询条件、时间范围与原始结果，例如“r18 的某个请求路径出现连接池等待，追踪 ID 为……”。
- **解释**。说明为什么这些现象支持当前假设，哪些关键条件仍待确认。
- **下一项检验**。找一项能区分当前假设与其他解释的检查，例如在同一流量类别下比较新旧实例。

只引用一张仪表盘的地址，还可能缺少当时的时间范围与筛选器。截图也可能把分母、采样规则或查询表达式藏起来。因此，模型的调查报告最好保存可以重放的查询条件，让工程师能回到数据源检查。这里是对文章证据要求的实现推导，具体保存方式取决于所用平台。

跨来源引用还要防止重复计票。同一批失败请求可能同时出现在服务日志、追踪和错误率图中。这三种视图可以定位不同环节，但共同变化可能来自同一件事。判断依据应写清它们分别提供了什么信息。

文章提到可以增加一个 Reviewer，挑战执行者的根因分析。它提出了可尝试的分工，实际收益需要在同一组事故中比较。Reviewer 如果只读执行者整理好的解释，很容易沿着已经选出的线索继续说。更有检验意义的任务是重新查看关键原始查询，寻找反例，并检查尚未排除的解释。文章建议用历史事故比较单 Agent 和增加 Reviewer 后的耗时、缓解效果与人工纠正次数，正文尚未提供这种对照结果。[官方文章](https://developers.openai.com/blog/production-monitoring-with-codex)

## 只读调查怎样落到实际权限

“让 Agent 先调查”需要执行环境拥有查询权限。文章建议从较小范围开始，按需要增加来源，并通过服务账号控制资源访问。能否执行一个 API 操作，由被接入系统的权限机制决定。[官方文章](https://developers.openai.com/blog/production-monitoring-with-codex)

以 Kubernetes 为例，RBAC 用 Role 或 ClusterRole 描述权限，再用 RoleBinding 或 ClusterRoleBinding 绑定主体。Role 的范围是某个 namespace。权限按 API group、资源和 verbs 授予，而且是加法规则，最终可用权限取决于主体获得的全部绑定。因此，审查一个“只读 Role”还需要一起检查该服务账号的其他绑定。[Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)

下面是说明资源粒度的自拟片段。

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: incident-observer
  namespace: example-service
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch"]
```

Pod 日志通过 `pods/log` 子资源授权。片段只展示 Role，真正接入还需要创建或选择主体并建立绑定，也要按调查目标检查数据源、日志内容和命名空间。这只是权限粒度示例，不包含账号与绑定的完整接入配置。[Kubernetes 对资源与子资源的说明](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources)

读取信息和执行变更可以使用不同的工具接口或凭据。调查结果先形成修复提案，审批确认后再由执行端取得相应权限。这样，权限可以围绕明确动作授予，操作结果也有独立回执。RBAC 负责授权请求，是否批准这次业务修复、是否满足变更条件，仍由应用中的审批与执行流程判断。

## 一份修复方案要足够具体

文章要求提出 bounded solution，并建议配套回滚方案。可执行的提案需要说明对象、修改量、预期效果和观察方式。例如“将 example-service 的 Deployment 恢复到 r17 的 Pod 模板，观察指定区域中的错误率与任务积压”，比“回滚服务看看”更容易审查。

动作范围也决定失败后该怎样处理。恢复一个版本时，可能同时存在新旧实例、尚未结束的任务、旧 schema 和新 schema。工程师应检查依赖条件，选择继续部署修复版本、回滚某一组件或调整配置。批准记录可以绑定具体提案和目标状态，执行前再确认目标仍对应那份提案。这是防止调查完成后环境继续变化的一种实现方式。

Kubernetes 的 Deployment 文档给出了一个容易忽略的细节。Deployment 的新 revision 由 Pod template 改变触发，扩缩容这类更新不会产生新的 revision。回滚到旧 revision 时，恢复的是 Pod template 部分。应用的数据迁移、外部配置和其他资源需要另行核对。旧 ReplicaSet 被清理后，相关 revision 的回滚能力也会丢失。[Deployment 回滚](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-back-a-deployment)、[revisionHistoryLimit](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#revision-history-limit)

所以，回滚方案本身也需要证据。它应写明旧版本是否仍可用、当前数据是否兼容、操作过程中哪些请求会受影响，以及如何判断此次操作完成。生成了一条语法正确的 `kubectl rollout undo` 命令，只能覆盖这份方案中的一小部分。

## 怎样确定服务恢复了

一次变更完成后，控制器可能已经达到声明的状态，业务却仍有残留故障。例如 HTTP 错误率下降了，但任务队列还在积压，之前接收的订单也没有处理完。文章要求沿可信、约定好的恢复信号检查，再决定继续调查或结束事故。[官方文章](https://developers.openai.com/blog/production-monitoring-with-codex)

下面用四个**自拟离线窗口**解释恢复判定。每个窗口都有 10,000 次请求。为了演示，恢复条件设为 HTTP 错误率不超过 1%、失败任务数不超过 20、最旧队列任务等待不超过 120 秒。这些阈值只用于此算例。

| 窗口 | HTTP 错误率 | 失败任务 | 最旧任务等待 | 支持服务已恢复？ |
| --- | ---: | ---: | ---: | --- |
| 变更前 | 0.20% | 12 | 90 秒 | 是 |
| 告警时 | 8.00% | 240 | 1,800 秒 | 否 |
| HTTP 已恢复 | 0.25% | 220 | 2,100 秒 | 否 |
| 服务恢复后 | 0.18% | 10 | 80 秒 | 是 |

第三个窗口给出了一个反例。请求成功率已经回到设定范围，队列等待却继续恶化。此时如果只看 HTTP 图，就会过早结束事故。这组算例检验的是恢复判定的逻辑，数值由人工构造，未测量 Codex 的事故处理能力。

下面的 Python 代码可以复算判定，无需连接外部服务。

```python
from fractions import Fraction

# 每行依次是窗口名、请求数、5xx 数、失败任务数、最旧任务等待秒数。
windows = [
    ("变更前", 10000, 20, 12, 90),
    ("告警时", 10000, 800, 240, 1800),
    ("HTTP 已恢复", 10000, 25, 220, 2100),
    ("服务恢复后", 10000, 18, 10, 80),
]
for name, requests, errors, failed_jobs, oldest_wait in windows:
    recovered = (requests > 0 and
                 Fraction(errors, requests) <= Fraction(1, 100) and
                 failed_jobs <= 20 and oldest_wait <= 120)
    print(name, recovered)
```

实际系统还需要检查观测窗口、请求数量和流量构成。一个没有流量的实例可以显示零错误，某个区域恢复也可能掩盖另一区域仍失败。判断时应保留分母、服务对象与持续时间，并查看用户侧结果。恢复查询应由可信数据源提供，模型生成的解释可以帮助组织材料。

## 把事故变成下一次可以重放的任务

文章建议用有代表性的历史事故排练，再把经验写成 skill 或 plugin。它列出的迭代内容包括减少不必要的数据源、定位人工纠正发生的步骤，以及比较不同 Agent 分工。这让 runbook 的改进依据落在实际调查行为上。[官方文章](https://developers.openai.com/blog/production-monitoring-with-codex)

历史事故的正确答案已经存在，但排练仍可能泄漏答案。若模型能读到事故复盘里写好的根因，测到的主要是如何利用现成结论。一个更有解释力的回放可以固定当时的代码和遥测快照，按工具真实可见的顺序提供信息，记录模型何时提出了什么假设、查询了哪些来源、要求什么额外权限。这是本文对排练设计的推导。

除了“是否找对原因”，还可以记录第一次正确假设出现的时间、重复查询量、需要人工补充的证据、提案范围和恢复判断是否准确。模型选择、工具延迟、查询范围与可用权限也应固定，才能解释两次运行的差别。增加 Reviewer 是否值得，就可以回到这组具体记录判断。

把一次调查保存下来时，至少要能从判断回到当时的查询，从修复回到获批的提案，从“恢复”回到用户侧观测。查询成功、变更执行和业务恢复因此各有自己的回执。后续接手者能沿这条链检查结论，才有条件继续调查或结束事故；具体权限、数据源和恢复阈值仍由服务本身定义。

**资料范围：** 依据 OpenAI 官方文章及 Kubernetes、Grafana 文档。文章提供集成方案，未公布生产事故成功率或不同 Agent 分工的完整对照；示例数据和恢复阈值为教学设定。
