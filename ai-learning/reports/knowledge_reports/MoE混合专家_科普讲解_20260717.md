## 第一部分 · 先建立直觉

### 1. 一个悖论：参数变多，算力却不变，天下哪有这种好事？

先摆一个几乎所有人第一次听 MoE 都会犯嘀咕的事实：

> **DeepSeek-V3 有 6710 亿（671B）个参数，但每处理一个字，只用到其中 370 亿（37B）——大约 5.5%。** 剩下 94.5% 的参数，这一步完全"没上班"。

这就带来一个悖论：

- 如果 94.5% 的参数都不干活，那把它们造出来图什么？纯浪费？
- 如果它们其实有用，那"只用 5.5% 算力"的省，又是从哪省出来的？不是自相矛盾吗？

答案是一句话，但需要一栋楼才能讲清：**参数是"请来的人"，算力是"这次上班的人"。MoE 让你雇了一大帮专家，但每个活儿只叫醒最对口的两三个。** 人多（参数多）不花钱在"养着"，只花钱在"叫醒谁干活"（算力）。这篇文章，就是把这栋"按需叫人"的大楼拆开给你看。

### 2. 两个主角：一栋专家大楼，和门口的分诊台

整个故事只有两个角色，先把分工焊进脑子：

| 角色 | 学名 | 它是什么 | 它干什么 |
|---|---|---|---|
| 🏥 **一排专家** | Experts（专家） | 一组彼此独立的小网络（每个就是一个标准 FFN） | 各自擅长处理某类输入，等着被叫号 |
| 🚦 **分诊台** | Gating / Router（门控/路由） | 一个很小的打分网络 | 看一眼进来的 token，决定"叫哪几个专家" |

一个贴切的类比：

> **想象一所医院，大厅里坐着 8 位专科医生**——神经科、骨科、心脏科……每来一位病人（token），**门口的分诊台（路由）先扫一眼症状，只把他送去最对口的 2 位医生**。其余 6 位对这位病人"当作没看见"，不参与、不耗时。
> 医院的**总接诊能力**是 8 位医生（参数量 = 8 份）；但每位病人**实际只占用 2 位医生的时间**（算力 = 2 份）。

记住这个画面。下面整篇，都是在讲这个分诊台**具体怎么分诊、以及分诊分不好会出什么乱子**。

> **术语澄清**：MoE = Mixture of Experts（混合专家）。它替换的是 Transformer 里的 **FFN 层**（那个"全连接前馈"子层），注意力层原样不动。所以你可以粗暴理解为：**把原来铁板一块的 FFN，换成了"一排 FFN + 一个分诊台"**。本库 `wiki/concepts/moe_architecture.md` 有独立词条。

## 第二部分 · 跟着一个 token 走一遍

现在放一个 token 进大楼，全程跟踪它。贯穿全篇的例子：

> 🔤 一个代表词「**利率**」的 token 进来了（它带着一串数字，即它的向量表示）。

### 3. 全流程：一个 token 的看病之旅，四步

✦ **一句话**：token 进门 → 分诊台给 8 位专家打分 → 只挑分最高的 2 位 → 这 2 位各出一份结果，按分数加权合并 → 出楼。

```
①「利率」token 进门
   └─► ②分诊台打分：给 8 位专家各打一个分（[0.1, 0.7, 0.05, 0.6, ...]）
          └─► ③只留 Top-2：选中 2 号(0.7) 和 4 号(0.6)，其余 6 位置零、不叫
                 └─► ④2 号、4 号各自处理这个 token，得到两份输出
                        └─► ⑤按分数加权合并：0.7×2号结果 + 0.6×4号结果（归一化后）
                               └─► token 带着"被 2 位专家联合诊断过"的新向量，出楼
```

这里**最反直觉、也最关键的是 ③**：

> **8 位专家里，有 6 位这一步的计算量是零。** 不是"算了但权重小"，而是**根本没调用**——分诊台没叫号，它们就不启动。这就是"参数多、算力不多"的机械来源：省，省在"没被叫到的专家一行代码都没跑"。

<details>
<summary><code>证据</code>：这一步用公式写出来长什么样（点开看）</summary>

MoE 层的输出就是"被选中专家的加权和"：

```
y = Σ_{i ∈ Top-K} G(x)_i · E_i(x)
```

- `E_i(x)`：第 i 个专家对输入 x 的输出（一个标准 FFN）
- `G(x)`：门控网络给出的**稀疏**权重向量——只有 Top-K 个位置非零，其余全是 0
- 因为非选中专家的 `G(x)_i = 0`，它们的 `E_i(x)` 干脆不用算

Top-K 通常 K=2（Mixtral）或 K=8（DeepSeek-V3）。这就是 §1 那个"5.5%"的出处：激活的专家数 ÷ 总专家数。
（Shazeer et al. 2017, "Outrageously Large Neural Networks", arXiv:1701.06538）

</details>

### 4. 为什么"分工"是自己学出来的，没人手动指派

你可能会问：谁规定 2 号医生是"神经科"、4 号是"心脏科"的?

答案是：**没人规定。** 训练开始时 8 位专家完全一样、分诊台瞎打分。但在海量数据的反复冲刷下，**只要某位专家偶然对某类 token 处理得稍好，分诊台就会更多地把这类 token 送给它，它就越练越专**——分工是**自发涌现**的，不是人工设计的。

这既是 MoE 的魅力，也是它一切麻烦的根源。下一部分我们就来看，这个"自发分工"会自发地跑偏成什么样。

## 第三部分 · 一个想不通的地方：为什么专家会"旱涝不均"

### 5. 专家崩塌：强者愈强的马太效应

✦ **一句话**：不加约束的话，分诊台会把绝大多数 token 都送给少数几位"明星专家"，其余专家逐渐没活干、变成废人——这叫**专家崩塌（Expert Collapse）**。

因果链非常干净，是一个**正反馈循环（马太效应）**：

```
分诊台随机初始化 → 某专家偶然被多分了一点 token
   → 它训练得更充分 → 对这类 token 打分更高
      → 分诊台更爱把 token 送给它 → 它拿到更多 token …（循环放大）
         → 最终：少数专家"过载"，多数专家"饿死"
```

**失衡的两个真实代价**：

1. **参数白雇了**：饿死的专家没被训练充分，等于你花了 671B 的参数量，却只有一小撮在真正贡献容量。
2. **拖慢整栋楼**：大模型训练时，不同专家分布在不同 GPU 上（叫 Expert Parallelism）。过载专家所在的那块卡累死，其他卡干等着——**木桶效应，最慢的卡决定整体速度**。

所以 MoE 的半部技术史，就是在和这个"旱涝不均"的原罪搏斗。

### 6. 三代解法：从"打补丁"到"改规则"

治理失衡的思路演进了三代，越来越优雅：

| 代 | 名字 | 核心思路 | 一句话点评 |
|---|------|---------|-----------|
| 一代 | **辅助损失**（Aux Loss） | 在训练目标里加一条"惩罚不均衡"的项，逼分诊台雨露均沾 | 有效，但这条"额外任务"会和"把话说好"的主任务**抢梯度**、互相干扰 |
| 一代 | **强制限流**（Capacity + Token Dropping） | 给每位专家设一个接诊上限，超额的 token 直接**跳过**（走残差） | 简单粗暴，代价是被丢弃的 token 没被好好处理 |
| 二代 | **专家选 token**（Expert Choice） | 反转方向：不让 token 挑专家，让每位专家挑自己最想要的 K 个 token | 天生均衡（每人固定接 K 个），但破坏了自回归推理，主流生成模型用不了 |
| 三代 | **无辅助损失均衡**（DeepSeek-V3 采用） | 给每位专家挂一个可调"偏置"，谁忙了就悄悄调低它的分、谁闲了调高 | 当前 SOTA：既均衡，又**不干扰主任务梯度** |

<details>
<summary><code>证据</code>：三代解法的关键论文与机制细节（点开看）</summary>

- **一代·辅助损失**：Shazeer 2017 提出 Importance Loss + Load Loss，用变异系数 CV² 惩罚不均，系数约 0.1。（arXiv:1701.06538）
- **一代·强制限流**：GShard / Switch Transformer 引入 capacity factor（通常 1.0–1.25），超额 token 走残差直通。（Switch Transformer, arXiv:2101.03961）
- **二代·Expert Choice**：Zhou et al. 2022。天然均衡，但"专家选 token"需要看到整个 batch/序列，**自回归逐 token 推理时未来 token 还不存在**，故难用于生成式解码——这是它没成主流的根因。（arXiv:2202.09368）
- **三代·Auxiliary-Loss-Free**：DeepSeek 的 Loss-Free Balancing（arXiv:2408.15664），在 DeepSeek-V3 落地。核心：每个专家维护一个 bias `b_i`，**只影响"选谁"、不参与反向传播、不进入加权输出**——所以不产生与语言建模冲突的干扰梯度。配套把门控从 Softmax 换成 Sigmoid（256 个专家时数值更稳）。（DeepSeek-V3 技术报告, arXiv:2412.19437）

</details>

> **一句话串起来**：从"额外加个惩罚"（会抢梯度）→ "限流丢弃"（会伤 token）→ "反转选择"（推理用不了）→ "挂个偏置悄悄纠偏"（都不伤）。DeepSeek-V3 的成功，一半功劳在这最后一代路由。

## 第四部分 · 工业界的 MoE 长什么样

### 7. 从实验室到开源顶流：一张对照表

✦ **一句话**：MoE 从 2017 年的"学术有趣"，到 2023 年 Mixtral 证明"开源能打"，再到 2024 年 DeepSeek-V3 证明"能便宜地做到顶级"，如今已是前沿开源模型的标准架构之一。

| 模型 | 年份 | 专家配置 | 总参 / 激活参 | 意义 |
|------|------|---------|--------------|------|
| Sparsely-Gated MoE | 2017 | 2048 专家, K=4 | — | 奠基：证明 GPU 上可大规模跑 |
| Switch Transformer | 2021 | 2048 专家, K=1 | 万亿级 | K=1 极简主义，证明"只叫 1 个"也能训好 |
| **Mixtral 8×7B** | 2023 | 8 专家, K=2 | 46.7B / 12.9B | **开源 MoE 标杆**，性能超 LLaMA-2 70B |
| DeepSeek-V2 | 2024 | 160+1 专家, K=6 | 236B / 21B | 细粒度专家 + 共享专家双创新 |
| **DeepSeek-V3** | 2024 | 256+1 专家, K=8 | **671B / 37B** | **无辅助损失均衡**，以远低训练成本达到 Llama-3.1 405B 级性能 |

<details>
<summary><code>证据</code>：两个高频误解的澄清（点开看）</summary>

- **"共享专家"是什么**：DeepSeek/Qwen MoE 设了 1–4 个**永远激活**的"共享专家"，专门装"所有 token 都用得上的通用知识"，让其余稀疏专家专注于特化知识。表里 "256+1" 的 "+1" 就是共享专家。
- **GPT-4 / Gemini 是不是 MoE**：业内**普遍推测**是，但官方从未披露架构细节。凡看到"GPT-4 是 8×220B MoE"这类具体数字，都属 `[推测]`/传闻，非官方确认。

</details>

### 8. 一个必须知道的工程代价：省了算力，但吃显存

MoE 不是免费午餐。它把"算力账"省了，却把"显存账"顶上来了：

- **参数全都得装进显存**。Mixtral 8×7B 虽然每次只算 12.9B，但 46.7B 参数**必须全部驻留显存**（约 90GB，4-bit 量化可降到 ~25GB）——因为你不知道下一个 token 会叫哪两位专家，谁都不能不在场。
- **专家分布在多卡，token 要"跨卡跑腿"**。这产生大量卡间通信（All-to-All）。这也是为什么 MoE 的工程实现，比稠密模型难不少。

> 一句话记住这个 trade-off：**MoE 用"多买显存"换"少花算力"。** 在推理算力比显存更贵的场景，这笔账非常划算——这正是大模型时代的现实。

## 第五部分 · 装进脑子

### 9. 一页纸心智模型

```
        一个 token 进来
             │
             ▼
   🚦 分诊台（Router）：给 N 个专家打分
             │  只留 Top-K（如 8 选 2）
     ┌───────┼───────┬─────────┬─── … （其余专家：本步计算量 = 0）
     ▼       ▼       ✗         ✗
  🧑‍⚕️专家2  🧑‍⚕️专家4   (未叫)   (未叫)
     │       │
     └──加权合并（按分数）──► token 带新向量出楼

  ┌─────────────────────────────────────────┐
  │ 省钱原理：参数=雇了N个 (大)，算力=只叫K个 (小) │
  │ 天生毛病：马太效应 → 少数专家过载、多数饿死    │
  │ 三代解药：辅助损失 → 限流 → 挂偏置纠偏(SOTA)  │
  └─────────────────────────────────────────┘
```

**四句话总纲**：
1. **MoE = 一排专家 + 一个分诊台**，替换掉 Transformer 里铁板一块的 FFN。
2. **省的原理**：参数按专家数增长（雇得多），算力只按 Top-K 增长（叫得少），没被叫的专家零计算。
3. **天生的病**：分工自发涌现，也自发失衡——马太效应导致专家崩塌，浪费参数又拖慢训练。
4. **三代解药**：辅助损失（抢梯度）→ 限流丢弃（伤 token）→ 挂偏置悄悄纠偏（DeepSeek-V3，都不伤，当前 SOTA）。

### 10. 几个容易踩的直觉陷阱

| 直觉陷阱 | 真相 |
|---|---|
| "没被选中的专家，算了但权重是 0" | ❌ 是**根本没调用**，计算量真正为零——省就省在这 |
| "MoE 又快又省，纯赚" | ❌ 省的是算力，代价是**全部参数得驻留显存** + 跨卡通信复杂 |
| "分工是人工设计的（这个专家管代码那个管中文）" | ❌ 分工是训练中**自发涌现**的，没人手动指派 |
| "专家越多越好" | ❌ 专家越多，失衡（崩塌）越难治、通信越贵；有边际递减 |
| "GPT-4 是 8×220B MoE" | ❌ 这是坊间**推测**，官方从未公布架构 |
| "K=1（只叫 1 个）肯定比 K=2 差" | ❌ Switch Transformer 证明 K=1 也能训好，省一半路由开销（但训练更需技巧稳住） |

1. **我真正理解了什么？**
   我把"参数多、算力少"这个悖论，拆成了**一栋按需叫人的专家大楼**：省钱来自"没被叫的专家零计算"，代价是"所有专家得驻留显存"。更重要的是理解了 MoE 的核心矛盾——**分工自发涌现，也自发失衡**——以及三代路由解法是怎么一步步从"打补丁"走到 DeepSeek-V3"挂偏置悄悄纠偏"的。

3. **下一步做什么？**
