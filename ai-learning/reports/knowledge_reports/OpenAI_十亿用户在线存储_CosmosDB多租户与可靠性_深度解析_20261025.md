# OpenAI 十亿用户在线存储：Habitat × Azure Cosmos DB 的多租户、热点与可靠性深度解析

**研究对象**：OpenAI Engineering《Rapidly scaling online storage to serve over 1 billion ChatGPT users (Part II)》及同系列 Part I，并交叉读取 Azure Cosmos DB 官方文档（服务配额、分区、serverless、跨分区吞吐再分配）。OpenAI 页面、搜索索引与订阅源对两篇文章的发布时间/更新时间给出不同元数据，本报告只按 Part I → Part II 的内容顺序讨论，不用这些日期支撑技术结论（见 Limitations）。

## 开头三行：x → f → f(x)

- **x**：OpenAI 的在线存储平台 **Habitat** 要在 **40 个地理区域**为**每周 10 亿+ 人**服务，承载 **500 PB+** 数据、峰值 **7000 万+ 请求/秒**，同时还要让几十个产品团队"不用懂数据库"就能上线功能。这带来三个互相拉扯的问题：**多租户怎么隔离**（一个热租户不能拖垮登录）、**跨区域怎么够快**（计算与存储常在不同区域）、**出事了怎么回得来**（他们真的踩了两次区域级事故）。
- **f**：OpenAI 的回答分两条线。**存储层（Part II）**：先用 Cosmos DB 的原语（逻辑分区键 10K RU/s 上限做背压）→ 发现物理分区才是真正执行限额的地方、**弱分区**（数据增长 → 分区分裂 → 容器总吞吐不变 → 每个分区能分到的吞吐反而变小）→ 退回到**每个用例一个独立容器**换隔离 → 发现这带来"每个新服务都要预扩容、上线日开 SEV 房间"的组织成本 → 又**回到多租户，但这次是"共管容器"**（co-managed container）：给 Azure 提需求做**热点键限流**、**请求分级 QoS**（离线批量降优先级）、**改造版 serverless**（每物理分区 10K RU/s + 基于 RU 用量的分裂）。**读取层（Part II 后半 + Part I）**：靠**就近放置 → 只广泛复制最小最敏感的数据集 → 其余靠集成缓存**，缓存失效靠 **Cosmos DB change feed 做 CDC 全局秒级失效**（明确对标 Meta 的 TAO），再把服务层从 Python 重写成 Rust。整体顺序被总结成一句话："**make it work, make it fast, make it cheap**"。
- **f(x)**：接受 f 之后能得到三个**可核验**的结果：**(a)** 全球读 p50 从约 **120 ms 降到约 10 ms（12×）**，代价是一层依赖 CDC 维持新鲜度的缓存；**(b)** 回退到多租户后"几个月没有再出现 provisioning 或 noisy neighbor 事故"（OpenAI 自述，无独立复核）；**(c)** 最大的 Cosmos DB 账号存**数十 PB、服务 2000 万+ QPS**，OpenAI 称"据我们所知是唯一把这个数据库用到这个规模的公司"。**但必须同时说清**：这些结论**全部来自 OpenAI 与 Azure 的联合叙事**，没有第三方复现；而且其中最关键的两个机制——**改造版 serverless** 与 **Gateway 的 failover 行为修正**——在公开的 Azure 文档里**查不到**（见 §5.3、§六）。**可迁移的是：在 OpenAI 这种租户规模下，默认多租户要有细粒度限流与分级，物理隔离仍是更强但更贵的选项；需要同时追求高命中与低陈旧度时，缓存应有可回放的变更事件；托管服务到了极端规模会转成共同运维。**

## 二、原文问题链：两篇文章各在回答什么

### 2.1 Part I 的问题链：从"库"到"服务"再到"换语言"

`[OpenAI 自述]` S02 的叙事是一条**时间轴**：

1. **起点（DevDay 2023）**：Habitat 是一个 Python 客户端库，直接连 Azure Cosmos DB。目标只有一个——"产品工程师不该需要思考数据库管理"。库负责 schema 查找、路由、鉴权、加密、序列化、请求整形、连接池。`[OpenAI 自述]` 关键设计是**故意做窄**：不暴露任意 SQL，只给 NoSQL API，避免大表扫描与 join。
2. **触发点（2025 年中）**：向后兼容的协议变更已经不可行。S02 举了一个非常具体的例子：为了缩小最关键数据集的区域故障影响面，要把数据迁到一组**跨区域分布的 Cosmos DB 账号**，这需要在客户端里引入路由逻辑、藏在 feature flag 后面、全量下发后再打开——**光协调就花了几天**，shadow 验证又花几天，修一个 bug 再花几天；最后某个团队因为别的原因回滚到旧版有 bug 的客户端，**直接触发了他们本想避免的故障**。
3. **结论一：把存储逻辑抽成独立服务**，换取"部署、可观测性、平台增强的单点控制"，同时集中做访问控制、审计日志、限制对底层存储资源的访问。
4. **结论二：先用 Python 扛**。S02 的原话是"a strategic incursion of technical debt"——首要目标不是成本或资源优化，而是**解除产品开发者阻塞、拿到平台稳定性**。他们还押了一注："我们赌等到必须离开 Python 的时候，Codex 和 GPT 会让这次迁移变得可行。这注最后押对了。"
5. **结论三：Python 服务的主要敌人是尾延迟**。原因不是网络，而是 **asyncio 调度延迟**——GIL 让并发不等于 CPU 并行，而 Habitat 还要做路由、压缩、加密、校验、下游健康检查、请求影子、hedging 等一堆 CPU 密集工作。`[OpenAI 自述]` 高负载下"哪怕 modest 的并发数也足以产生显著的调度抖动，长达数百毫秒，个别情况几秒"。解决办法很土但有效：**每个进程只服务很少的并发请求，靠海量进程横向扩展**。
6. **结论四：Rust 重写**。`[OpenAI 自述]` "At its peak, Python helped us serve more than 20 million requests every second." **2026 年 Q2，2 名工程师 + Codex + GPT-5.5 重写整个服务**；新服务已处理 **95% 生产请求**，**CPU 效率 6×、内存效率 15×**，平均与尾延迟都显著更低。

### 2.2 Part II 的问题链：从"能用"到"共管"

`[OpenAI 自述]` S01 的方法论原句："first become reliable enough for mission-critical product traffic, then fast enough for global users, and, finally, to deftly operate at massive scale."

Part II 回答的是**存储层（Azure Cosmos DB）**怎么在 OpenAI 规模下可用，主线是**多租户的三阶段循环**：

```
Phase I  依赖 Cosmos DB 原语
         单一默认容器 + 客户端自选分区键 + 10K RU/s 逻辑分区上限做背压
              ↓ 问题 A：热点分区键（user_id / workspace_id 撞车）
              ↓ 问题 B：noisy neighbor（逻辑分区与物理分区限额混算）
              ↓ 问题 C：弱分区（存储增长 → 分区分裂 → 每分区吞吐反而变少）
Phase II 独占容器换隔离
         关键新用例各自一个容器 + 脚本按物理分区数同步容器总吞吐
              ↓ 问题 D：缺少稳定聚合增长（新用例 0→1M QPS = 基线的 1000×）
              ↓ 问题 E：容量规划落到每个产品团队（上线忘记预扩容 → SEV 房间）
Phase III 多租户默认 + 具备数据搬移能力（与 Azure 联合造）
         热点键限流 + 请求分级 QoS + 改造版 serverless（10K RU/s/物理分区 + RU 用量分裂）
              ↓ 结果：回到一个共享容器，产品团队不再需要预先/持续容量规划
```

`[分析者推断]` 这条曲线的形状本身就是本报告最想强调的一点：**OpenAI 不是"从单租户演进到多租户"，而是"多租户 → 单租户 → 多租户（但换掉了实现方式）"**。第一次回到多租户之所以失败，不是因为多租户思想有问题，而是因为**当时的隔离手段只有"物理分容器"一种**；当 Azure 补上了**热点限流、分级 QoS、可按 RU 分裂的 serverless** 三件武器后，多租户才重新可行。**隔离手段决定多租户是否可用，而不是反过来。**

### 3.2 Cosmos DB 分层与"限额到底在哪里生效"

`[云厂商事实]` S03 的官方限额表：

| 资源 | 限额 |
|---|---|
| 每容器最大 RU/s（专用吞吐模式） | **1,000,000**（可提 support ticket 提高） |
| 每数据库最大 RU/s（共享吞吐模式） | **1,000,000**（同上） |
| 每分区（逻辑与物理）最大 RU/s | **10,000** |
| 每逻辑分区全部 item 的存储 | **20 GB** |
| 不同逻辑分区键数量 | 无限 |
| 每容器存储 | 无限 |
| 每 1 GB 所需最小 RU/s | 1 RU/s |

`[云厂商事实]` S06：10,000 RU/s 是**物理分区**的上限，因此逻辑分区也继承同一上限（每个逻辑分区只落在一个物理分区里）；而容器预配的吞吐是**近似均分到各物理分区**上的。

`[OpenAI 自述]` S01 补充了"限额在哪里真正生效"这一层：**文档写的是逻辑分区键 10K RU/s，但实际执行限额的是物理分区**——"logical partitions are unable to reach 10,000 RU/s"。它们与同一物理分区上共置的其它逻辑分区**共享**该物理分区的限额。

`[交叉印证]` **弱分区机制**（weak partitions）在两边对上了：
- OpenAI 侧：数据量增长 → 物理分区分裂 → 物理分区总数增加，而**容器总预配吞吐不变** → 分裂后的每个分区分到的吞吐更少 → "**存储量增长本身就会降低活跃负载的吞吐容量，即使请求速率与用量都没变**"。
- Azure 侧：容器吞吐**近似均分**到物理分区（S06），且分区**在达到存储上限时分裂，每个子分区拿到一半吞吐**（S01 OpenAI 描述 + S04 的分裂行为描述）。

```
        容器预配吞吐 100,000 RU/s（固定不变）
   ┌──────────┬──────────┬──────────┐   ← 数据增长前：3 个物理分区
   │ 33,333   │ 33,333   │ 33,333   │
   └──────────┴──────────┴──────────┘
        存储到达上限 → 分裂（子分区各拿一半吞吐）
   ┌────────┬────────┬────────┬────────┬────────┬────────┐
   │ 16,666 │ 16,666 │ 16,666 │ 16,666 │ 16,666 │ 16,666 │  ← 总吞吐仍 100,000
   └────────┴────────┴────────┴────────┴────────┴────────┘
   ⇒ 每个物理分区的吞吐上限从 33,333 降到 16,666（且受 10,000 硬顶约束）
   ⇒ 请求量没涨，"每个分区能扛的"却降了一半
```

`[分析者推断]` 这解释了为什么 OpenAI 在 Phase II 专门写了一个"按容器物理分区数同步容器总吞吐"的控制面脚本——而 `[云厂商事实]` S04 显示 Azure 本身就有**跨分区吞吐再分配**这一官方能力：物理分区最多 10,000 RU/s，可对目标分区设到 20,000 RU/s，超过 10,000 会触发自动分裂并把吞吐均分给新分区。**OpenAI 的"弱分区管理脚本"极可能就是对这层官方能力的封装与自动化**（原文未明说其实现，故标 `[推测]`）。

## 四、核心机制深读

### 4.1 多租户三阶段：三个被放弃的方案

`[OpenAI 自述]` S01 明确写了这个循环："we went through a circular journey from using one multi-tenant Azure Cosmos DB container to provisioning single-tenant backing containers to reverting to a multi-tenant container by default."

**Phase I 的三个具体故障模式**：

| 故障 | 机制 | 后果 |
|---|---|---|
| **分区键碰撞** | 早期 API 把逻辑分区键选择权交给客户端，`user_id` / `workspace_id` 这类高频键在不同产品里撞车，共享同一套限额 | "**这个设计限制了单个用户的整体吞吐**" |
| **Noisy neighbor** | 限额在物理分区执行，同物理分区上的逻辑分区互相挤占 | "niche product features 的负载打断了核心登录与注册流程" |
| **弱分区** | 存储增长 → 分区分裂 → 容器总吞吐不变 → 每分区吞吐缩水 | 与请求量无关的容量退化 |

`[OpenAI 自述]` 顺带提到一个**前史**：在迁到 Habitat/Cosmos DB 之前他们在 Postgres 上遇到过同类问题——"一个热组织或热键能拖垮整个数据库"，为此花了大量精力做热键缓存与"在缓存 miss 上加租约（leases）"。

**Phase II 的两个组织性代价**：

1. **失去稳定聚合增长（lack of stable aggregate growth）**。`[OpenAI 自述]` 在共享容器里，"某个新用例从 0 QPS 涨到 100 万 QPS，通常不会显著改变总聚合用量"；但在独占容器上，同样的涨幅**可能是基线的 1000 倍**（基线只有内部 dogfooding）。于是每个团队都得自己预扩容。
2. **容量规划变成组织问题**。"Product teams would often ship their features to production and forget to pre-scale and we'd sit in **SEV rooms on launch day** attempting to scale up containers last minute." 监控独占容器还需要" intimately product knowledge of when traffic would shift or grow"；而各团队投入的 diligence 差异巨大，"This failed to scale organizationally"。

**Phase III 的三件新武器**（均为 OpenAI 与 Azure 联合开发）：

| 武器 | 机制 | 解决 |
|---|---|---|
| **热点键限流（hot key throttling）** | 先限最热的键，防止 noisy neighbor 吃光某物理分区的全部吞吐 | 把"一个热键 → 全站爆炸半径"降级 |
| **请求分级 QoS** | 给请求分层，**离线负载（批量写入、数据导出）降优先级、先被限流**，从而保护面向终端用户的高优先级交互请求 | 离线任务不再挤掉交互流量 |
| **改造版 serverless** | 旧的 serverless 只按存储量伸缩、且**每物理分区限 5K RU/s**；新版让**每个物理分区可扩到 10K RU/s**，并引入**基于 RU 用量的分裂**（不再只按存储分裂） | 弱分区问题，且**不必再手工监控与扩容容器** |

`[交叉印证]` `[云厂商事实]` S05：公开的 serverless 文档写明"A serverless container begins with a throughput of 5,000 RU/s. **Each physical partition within a serverless container can handle up to 5,000 RU/s**"——与 OpenAI 描述的**旧** serverless 限制完全一致；而 OpenAI 说的**新版**（10K RU/s/物理分区 + RU 用量分裂）**在公开文档中未查到**。`[待验证]` 这几乎可以肯定是**为 OpenAI 定制的增强版或预览能力**，其可用范围、是否 GA、其它租户能否使用均未知。

### 4.2 读路径：三层策略与其容量天花板

`[OpenAI 自述]` S01：`[读]` 占了 Habitat 请求的 **90% 以上**，因此三层策略全部围绕读展开。

**第一层：就近放置（store data near users when capacity allows）**
`[OpenAI 自述]` OpenAI 在多个 Azure 区域有账号以满足**数据驻留（data residency）**要求；但即使没有驻留要求，同区域也能降延迟。**现实约束是物理云容量**："Due to the size of our data sets, many regions cannot accommodate the massive storage footprint required for their proportional share of user traffic." 在数据中心容量、电力或制冷紧张的区域，存在一个**直接取舍**：把容量留给同置存储以降低延迟，还是拿去做更多 serving compute、把存储请求路由得更远。`[分析者推断]` 这意味着**"就近"不是架构选择而是容量拍卖的结果**——延迟优化与成本/容量在区域层面直接冲突。

**第二层：只广泛复制最小、最敏感的数据集**
`[OpenAI 自述]` 对"每个请求都要用"的**认证元数据**这类最敏感负载，用**拥有大量次要区域的高复制账号**（部分账号复制到**全部 40 个 Azure 区域**，部分至少每洲一个）来压低 compute↔Habitat 的 RTT。代价是"必须**提前于原计划**在 Habitat 里建了一套透明的数据搬移与路由层，以便在不同复制拓扑的账号之间搬数据"；而且这条路**最终也受容量约束，只能覆盖少数手工挑选的数据集**。

**第三层：其余全部靠集成缓存**
`[OpenAI 自述]` Habitat 的负载"压倒性地偏读"，应用不断拉取 settings、state 等属性，**一小撮高频类型贡献了不相称的流量**，非常适合分布式缓存。

### 4.3 缓存失效：CDC 是正确性的来源，不是加速的来源

`[OpenAI 自述]` S01 把缓存失效讲成一次**明确的取舍**：

- **纯 TTL**：短 TTL → 陈旧度低但命中率高不了（条目很快过期）；长 TTL → 命中率高但长时间返回陈旧数据，**导致用户体验差与产品行为不可预测**。
- **写时显式失效**：新鲜度大幅提升，但"很难做对"——**部分失败会留下陈旧缓存**；多区域部署会进一步放大（跨区域网络更不可靠，缓存与底层存储复制赛跑）。
- **OpenAI 的选择**：走 **Meta TAO 的路子**——用 **Cosmos DB change feed 做 CDC**，**全球范围内数秒内传播失效**，兼顾高命中率与低陈旧度。机制是：一个服务消费 change feed，在底层数据更新时对**本地缓存**执行失效，下次读取即 miss 并回填最新版本。

`[分析者推断]` 这一层是整套读路径里最显眼的**新鲜度敏感**部分：缓存命中时，失效是否及时直接决定读到的是不是旧值。多区域复制的一致性级别、故障切换与回源路径同样可能影响正确性，不能把全部正确性只归到 CDC。把缓存失效建立在 change feed 上，等于把缓存新鲜度绑定到其投递与重放语义上——因此 OpenAI 在 CDC 平台上的可靠性投入（见 §4.4）也是缓存新鲜度投入。

### 4.4 CDC 平台：从"一个特性"到"一个平台"

`[OpenAI 自述]` S01 给出规模：每秒**百万级**捕获变更、跨**数千个容器**与**数百万个容器分区**，流经**上百个 Kafka topic**，同时支撑最终一致的二级索引、数据搬移管道、离线分析与实时产品特性。

`[OpenAI 自述]` 客户端体验被刻意做窄：想监听"我的某类行被改了"，客户端只需注册一个回调；至于"数据在哪些 Cosmos 账号/容器里""哪个区域跑着 CDC 服务部署""CDC worker、Kafka、消费者怎么扩"，由内部控制面处理。

`[OpenAI 自述]` 可靠性工程清单（可直接当 checklist 用）：使用**副本区域 + 低优先级 feed 读取**以保护延迟敏感的 Habitat 流量；worker 崩溃、容器问题、租约存储错误、无效配置、目标端失败在大规模机队里"持续发生"；因此加固了 **CDC worker 生命周期与租约处理**、**隔离不同流之间的故障**、为配置变更与发布加防护、用**死信队列**防止永久投递失败造成队头阻塞、通过**切换到备用 Cosmos 区域**容忍区域故障。`[OpenAI 自述]` 甚至为此**改了 Azure 的 CDC SDK**：把 checkpoint 在内存里批处理、只周期性落盘。

`[分析者推断]` 这里有一个值得单独记下的工程模式：**当一个托管服务在你的规模下成为瓶颈时，可行的做法是直接改它的 SDK**，而不是等厂商排期——前提是你和厂商的关系已经到了"直接 page 对方"的程度（§6）。这既是能力也是**依赖锁定风险**：OpenAI 的读性能改进（12×）有一部分是建立在"能改 Cosmos DB SDK"这个前提上的，**这个前提无法被第三方复制**。

### 4.5 Rust 重写与代理层开销

`[OpenAI 自述]` S02：Rust 服务的收益是"**removing overhead in the Habitat service itself**"。S01 在读性能一节也把"Reduce proxy overhead with Rust"列为三大设计变更之一。

`[OpenAI 自述]` S02 另外两个与存储无关但决定尾延迟的细节，值得单独记：
- **连接池复用顺序（LIFO→FIFO）**：Python `aiohttp` 的 `TCPConnector` 默认**后进先出**复用连接，本来是合理默认（让新建的突发连接去空闲超时），但在他们的场景里形成**亚稳态失效（metastable failure）**——慢的、已过载的服务更晚归还连接，于是**后续请求更频繁地选中它们**，流量逐步集中到已经吃力的 pod 上，形成正反馈。改成 **FIFO** 后打破了回路，连稳态方差也降了。今天主要靠 **Istio + Envoy** 提供连接池与服务端负载感知均衡。
- **Envoy 做连接 fan-in**：把 Python 的 HTTP/1 升级到 HTTP/2 用多路复用，再池化并延长连接寿命；顺带给**限流与熔断**提供集中实现点（放在每个 Python 进程里效果会差很多）。`[OpenAI 自述]` 副作用是：进程数量多一个数量级后，"thundering herd"变得容易发生——日常部署若不减速会造成明显 CPU 抖动，**连接泄漏能靠打满 NAT 网关拖垮网络**。

## 六、事故时间线与恢复

`[OpenAI 自述]` S01 披露了两次区域级事故，**间隔约一个月**，且**第二次由第一次的恢复动作引发**：

| 时间 | 事件 | 机制 | 后果 / 修复 |
|---|---|---|---|
| **2024 年底** | **区域断电**：一个最大 Cosmos DB 账号的主 Azure 区域发生电力故障 | 主区域不可用 | 切换演练中他们发现**最大账号要花数小时才能切到次区域**——这个规模**他们自己和 Azure 团队都没测过** |
| **约一个月后** | **回切踩踏（failback stampede）** | 把账号切回原区域时触发另一场严重事故。**gateway 模式客户端处理 failover 的一个怪癖**：**所有客户端立即建立连接并把请求发往原区域，尽管只有一部分物理分区真的迁回去了** | 连接踩踏压垮原区域的 Cosmos DB Gateway |

`[OpenAI 自述]` 两次事故都走了完整的事件管理流程，定位了根因并部署了修复。但 OpenAI 的判断是：**"这些事故是更大的系统性问题的症状"**——即"托管服务与我们的团队、以及与 Azure Cosmos DB 团队的**协作与测试方式**之间的错配"。

`[OpenAI 自述]` 后续的"共同管理"（co-managed）机制：

- 共享测试、共享 dashboard、**直接工程沟通渠道**（甚至"通过 Teams 互发消息"），以及**越过支持层级直接 page 对方**；
- 双方**联合监控 Habitat 的每一层**，从服务层一直到 Cosmos DB 的物理存储层；
- 在一个"**生产规模但非生产**"的 Cosmos DB 账号上做变更测试；
- 共同迭代 SDK，共同确定账号的扩缩容最佳实践。

`[OpenAI 自述]` 一年来的联合工程内容：改进 Cosmos DB **控制面与 Gateway 的可扩展性**；给 Gateway 加**负载保护**与**元数据缓存**以保护元数据分区；通过**连接池与更高的连接复用**降低 Python habitat-service 机队对 Gateway 的压力；**就近共置**负载；用**不同 VPC 隔离关键负载与离线负载**。

`[分析者推断]` **这次事故链是本报告认为对"Agent 状态存储"最有价值的一段**：它把一个反直觉的事实摆出来——**"回切"（failback）不是"故障恢复的自然镜像"，它是一个独立的、可能更危险的变更**。常见的事故预案只写"如何切走"，不写"如何切回"，而 OpenAI 的教训是切回路径需要**单独设计、单独压测、单独限流**。这一条几乎与后端技术栈无关，是纯粹的运维方法论。

## 七、关键设计决策与被放弃的方案

`[分析者推断]` 按"被放弃的方案 / 保留的代价"来重排，Part I+II 至少包含以下五组权衡：

| # | 被放弃的方案 | 为什么放弃 | 保留的代价 |
|---|---|---|---|
| 1 | **单租户（每用例/每服务一个容器）** | 隔离最好，但失去稳定聚合增长 → 每个团队要预扩容 → 上线日开 SEV 房间；容量规划的组织成本随团队数增长而失控 | 回到多租户后必须靠**限流 + 分级 QoS** 替代物理隔离，隔离强度弱于独占容器 |
| 2 | **旧的 serverless 模式** | 只按存储量伸缩、每物理分区限 5K RU/s | 需要 Azure 定制增强版（公开不可得）才能用 |
| 3 | **Python 服务** | GIL + asyncio 调度延迟 → 尾延迟不可控；CPU/内存效率不足 | 2025 年整年承担技术债；最终靠 2 人 + Codex + GPT-5.5 才完成 Rust 重写 |
| 4 | **客户端库形态** | 协议变更需要跨数十个服务协调（数天），一次回滚就能引发事故 | 迁移期同时存在两套形态的复杂度 |
| 5 | **任意 SQL / 复杂查询** | 一次昂贵的热路径查询就能打挂数据库（Postgres 时期的历史教训） | 复杂查询必须走**离线路径**（Rockset），客户端要自己扩容 Rockset 实例 |
| 6 | **纯 TTL 缓存** | 命中率与陈旧度不可兼得 | 必须引入 CDC 失效链路，把缓存正确性绑定到 change feed |

`[OpenAI 自述]` 还有一条"放弃强 API"的总纲：S02 明确写"**The lack of a powerful API is an explicit tradeoff in Habitat's design**"——目标不是能力最强，而是"**simple, predictable, constant-work requests**"，因为"fanout 不可预测的请求在运维上是危险的：它们让隔离与负载均衡变复杂，并引入难以扩展的延迟悬崖"。

`[OpenAI 自述]` 对象/边模型同样有边界：Habitat 把**对象与它的直接边共置在同一存储分区**（便于水平扩展），但**不做跨对象的图遍历**——"任何一跳都可能需要从两个完全不同的 Azure Cosmos DB 账号取数，而它们在不同区域"。

## 八、与替代存储路线的有边界比较

`[分析者推断]` OpenAI 的选择不是"Cosmos DB 最好"，而是"**在当时的规模与约束下，这个组合的改造速度最快**"。把替代路线放在同一张表上：

| 路线 | 相对 Habitat×Cosmos DB 的优势 | 劣势 | OpenAI 为何没选（原文依据） |
|---|---|---|---|
| **自建分布式存储（如 Bigtable / Spanner 类）** | 分片与多区域复制完全可控；SLA 与容量不受厂商掣肘 | 要自建运维与一致性栈；在 OpenAI 的增长速率下不现实 | S02："我们连成熟平台都在边建边扩"；S01 承认"托管服务"路线在起步阶段让业务跑得更快 |
| **Postgres / 关系库** | 查询表达力强、可审查、易做复杂分析 | S02 明确：昂贵查询频繁打挂数据库；成本不均衡（写 SQL 便宜，跑 SQL 贵） | S02 把 Postgres 迁走作为背景；Habitat 走 NoSQL + 窄 API |
| **DynamoDB 类托管 KV** | 同样是"托管 + 分片 + 按需" | 无等价公开的多租户热点限流/分级 QoS/增强 serverless 能力（`[待验证]` 未系统比较）；迁移动作成本高 | 原文未正面比较，仅正面选择了 Cosmos DB |
| **S3 / 对象存储 + 自建索引** | 容量与成本最优，适合冷数据与一次性分析 | 不适合毫秒级点查与高频状态读写；一致性模型与热点问题需自建 | S02 用 Rockset 做**离线二级视图**而非在线主存 |
| **自研存算分离（RocksDB + Raft）** | 可为 bulky 数据类型优化，降低闪存容量需求 | **峰值 QPS 更低**；需自研 | S01"Looking ahead"：**已在研**的 exabyte 级在线存储系统，采用 **Rockset 的 RocksDB Cloud 内核 + Raft 复制**，**实现与 Cosmos DB 相同的文档模型**，用**存算分离 + 物理复制**换取更少的闪存容量，代价是更低的峰值 QPS |

`[分析者推断]` 最后一行特别值得注意：**OpenAI 并没有停在托管服务上**——他们的下一步是"**同样的文档模型，但换成自研的存算分离内核**"。这说明他们真正认可的是**文档数据模型 + 服务层抽象**，而不是 Cosmos DB 本身；Cosmos DB 是**当前阶段的实现**，而 12× 延迟改进里有相当一部分是**把云厂商能力接进自己服务层**换来的。

## 九、对 Agent 状态存储 / memory / context service 的可迁移启示

`[分析者推断]` 本节是本报告面向 EverAgent 的落点。每条都注明了迁移条件，避免把 OpenAI 的规模结论直接搬过来。

### 9.1 状态存储：会话与线程状态

1. **把"每会话一个分区"当作默认设计，而不是让客户端选分区键。** `[锚点 S01]` OpenAI 早期把逻辑分区键选择权交给客户端，直接导致 `user_id`/`workspace_id` 撞车。Agent 场景同理：**`session_id` / `thread_id` / `agent_id` 极易成为全局热点**。可迁移做法是**在服务端做键合成**（如 `hash(user)+hash(session)`、或带盐前缀），避免单一大租户/单一大会话占满一个物理分区。
2. **"容器/账号的吞吐预算是全局资源"要有显式的分配层。** `[锚点 S01]` Phase II 的教训是隔离靠物理分容器代价太高；Phase III 靠限流与分级解决。映射到 Agent harness：**离线任务（批量索引、批量重放 trace、评测跑批）必须与交互请求分级**，否则评测会吃掉线上请求的预算。
3. **限流的粒度要在"热点键"一级，而不只是在租户一级。** `[锚点 S01]` hot key throttling 是他们专门为 Phase III 做的三件武器之一。Agent 场景的热点键通常是**某个超长会话、某个被反复读取的大 context、某个共享的 system prompt 派生状态**。

### 9.2 Memory 与 context service

4. **需要同时追求高命中率与低陈旧度时，优先考虑事件驱动失效，并保留 TTL 兜底。** `[锚点 S01]` 纯 TTL 的命中率/陈旧度难以兼得；写时逐点失效在多区域与部分失败下也很难做对；OpenAI 用 **Cosmos DB change feed 做 CDC 秒级失效**。对 Agent memory 服务的直接映射是：memory 写入产生可消费、可重放的变更事件，读缓存以该事件为主要失效源，TTL 作为陈旧度上界。对一致性要求较低或规模较小的场景，版本校验、短 TTL 或不缓存仍可能更简单。
5. **"小工作集"是缓存收益的前提，Agent 场景恰好满足。** `[锚点 S01]` "一小撮高频类型贡献了不相称的流量"。Agent 的 context/memory 读取同样高度集中于 settings、工具定义、会话摘要、长期记忆条目——**这正是分布式缓存最划算的形状**。
6. **长上下文与 KV/状态分层要显式设计。** `[分析者推断]` OpenAI 用"只广泛复制最小最敏感的数据集（认证元数据）+ 其余靠缓存"来管理跨区成本。Agent 侧对应的问题是：**哪些状态必须"任何一次请求都能立刻读到"（如权限、路由、模型配置），哪些可以"就近缓存 + 失效"（会话历史、长期记忆）**。这个划分应写进架构，而不是默认全部跨区复制。

### 9.3 隔离与多租户

7. **多租户隔离可组合使用：热点键限流、请求分级、物理分容器、独立账号。** `[锚点 S01]` 它们大致从低成本软隔离走向高成本强隔离；OpenAI 的 Phase III 让限流与 QoS 成为默认手段，但关键租户仍可保留物理隔离。Agent harness 里的租户通常对应“用户 / 工作区 / 团队”，应按爆炸半径、合规和成本选择组合，而不是固定排序后一刀切。
8. **容量规划不能落在每个产品团队头上。** `[锚点 S01]` "This failed to scale organizationally"。对应到 EverAgent：**任何要求每个 skill 或每个 agent 负责人手工预估容量的机制都会失效**；应提供基于历史用量的自动分配。

### 9.4 灾备与恢复

9. **"切回"必须作为独立变更来设计和压测。** `[锚点 S01]` 2024 年底的区域断电之后约一个月，**回切动作本身引发了第二场事故**，原因是 gateway 模式客户端的 failover 行为怪癖——所有客户端立即连回原区域，尽管只有部分物理分区迁回。**可迁移做法**：把 failback 当成一次"流量切换"来设计（灰度、分批、带限流），而不是当成"故障恢复的自然镜像"。
10. **托管服务到一定规模就不再是托管服务。** `[锚点 S01]` "When companies grow to OpenAI's scale, managed services become less 'managed'." 对 EverAgent 的含义：**选型时要评估"出问题时我能否自己改"**——能否拿到直连工程渠道、能否自建生产规模的非生产环境做演练、能否在厂商排期之外改 SDK。**这条能力是规模带来的，不是选型能买到的。**
11. **"直接 page 对方"是可靠性资产。** `[锚点 S01]` 双方甚至绕开支持层级互相告警。对个人/小团队的现实映射：**至少要有一个可直通服务商的联系人**，否则跨组织故障永远卡在工单里。

### 9.5 适用边界：哪些不能照搬

| 不可照搬 | 原因 |
|---|---|
| 从“单账号 2000 万+ QPS”反推容器拓扑 | S03 的 1,000,000 RU/s 是可申请提高的默认限额，且平均 RU/请求与定制配额未知；公开材料不足以判断容器数量 |
| "改造版 serverless" | 公开文档查不到（§5.3），不是通用能力 |
| "改 Azure CDC SDK" | 依赖与厂商的深度绑定，无法复制 |
| "用 2 人 + Codex + GPT-5.5 重写 Rust 服务" | 前提是**已有**被验证的架构、明确的重写范围与高质量代码模型；`[推测]` 顺序不能颠倒——先定架构边界，再谈用模型重写 |
| "缓存 + CDC 失效" | 需要底层存储提供**有序、可回放的变更流**；没有 change feed 的存储（多数 KV/Postgres）需要另建 outbox/事件表，工作量不小 |
| 把 OpenAI 的 12× 当作一般规律 | 它是**特定基线（120ms p50）+ 特定缓存覆盖率 + 特定区域布局**下的结果，且**没有给出未命中路径的延迟** |

## 十一、思考与追问

### 11.1 我真正理解了什么

- **多租户不是单纯“要不要”的问题，而是默认共享到什么程度、哪些租户需要更强隔离。** OpenAI 的三阶段循环说明：早期内建原语不足以控制热点与 noisy neighbor，全面物理分容器又把容量规划成本推给产品团队；等热点限流、分级 QoS 与新的 serverless 机制加入后，默认多租户才重新可行。**隔离手段与组织成本共同决定落地方式。**
- **"限额写在文档上"和"限额在哪里执行"是两件事。** 文档写逻辑分区键 10K RU/s，实际执行在物理分区；由此产生的"弱分区"（存储涨 → 分区裂 → 每分区吞吐缩）可以在**请求量完全不变**的情况下吃掉容量。**任何按"逻辑分区"思考容量的人都会算错。**
- **缓存的收益与新鲜度要一起设计。** OpenAI 用 CDC 秒级失效替代“只靠 TTL 猜新鲜度”，说明高命中缓存会把变更投递、重放和失效失败一起带进系统设计；这是一致性与可用性的权衡，不能只当作事后性能优化。
- **回切是独立风险源。** 两次事故间隔一个月、第二次由第一次的恢复动作引发——这条教训与后端技术栈完全无关，是**变更管理**问题。

### 11.2 我还没搞懂什么

- **20M QPS 对应多少 RU/s、多少容器与什么定制配额**？公开的默认限额可申请提高，原文又没有给平均 RU/请求或容器布局，因此当前无法从 QPS 推回拓扑。
- **12× 读延迟里有多少来自缓存命中、多少来自 Rust 代理层**？两者被并列写成"three major design changes"，但没有拆分归因。
- **CDC 失效链路的端到端延迟与失败语义**：change feed 消费 → 失效广播 → 本地缓存 miss → 回源，**这条链上任一环失败时的数据正确性保证是什么**？OpenAI 写了 CDC 自身的可靠性清单，但**没写"失效没到"时的兜底**。
- **改造版 serverless 是否会成为 GA**，还是 OpenAI 专属？
- **多租户共享容器在 OpenAI 规模下的隔离边界**：hot key throttling 与 QoS 分级能挡住"一租户吃掉整个物理分区"，但**隔离强度与独占容器相差多少**、误配的爆炸半径多大？

### 11.3 下一步读什么或做什么

1. 继续追踪 Microsoft Learn 是否公开 OpenAI 所述的 10K RU/s 改造版 serverless 与 Gateway failover 修正；当前公开 serverless 页面仍是每物理分区 5K RU/s。
2. 找 OpenAI 2024 年底区域断电的**第三方或 Azure 侧**事后说明，核对"数小时切换"与"回切踩踏"的细节。
3. 读 Part I/II 的**图注与图内数据**（Figure 01–05），补上 120ms→10ms 的构成拆分、Phase 切换时间线与热点/弱分区示意。
4. 评估一个可落地问题：**EverAgent 的 context/memory 存储是否具备"有序可回放的变更流"**（决定 §9.2 第 4 条能否采用）。
5. 设计一次最小验证：对同一组 Agent 任务，用"纯 TTL 缓存"与"事件驱动失效 + TTL 兜底"两种方案对比陈旧度分布，验证 OpenAI 的取舍在本项目负载下是否成立。
