# 如何用 Agent 设计 Agent 友好的 CLI：从真实用户任务到独立验收的工程闭环

把一个 CLI 交给 Agent，返回 JSON，再看见它成功运行几条命令，并不足以说明这个工具能够解决用户问题。真正困难的部分是：用户说得不完整时怎样确定目标，请求超时后怎样避免重复写入，工具说成功时怎样核实结果，以及改好一个案例后怎样知道没有破坏其他工作流。

本报告的核心建议是：**让真实用户任务定义成功，让作者 Agent 实现最小能力，让独立使用者 Agent 黑盒完成任务，让可信验证器检查实际状态，再用失败证据推动受控迭代。** CLI、SDK 和 MCP 是实现这条链路的不同入口，不是最终目的。

这不是一个已经被证明普适最优的架构。它是对官方工程资料与开发者实践的综合：对于本地只读工具，保持简洁；对于远端、长任务和高风险写操作，再增加必要的协调、审批与恢复机制。效果应通过相同任务、权限和预算下的比较来判断，而不是由接口流派决定。

## 一、研究问题、方法与证据边界

本报告回答两个相连的问题：怎样利用 Agent 参与工具设计；怎样证明设计出来的工具能帮助另一个 Agent 安全完成真实任务。前者是开发过程，后者是产品能力，不能用“代码已经生成”代替。

资料选择以直接支撑机制的一手来源为主，包括 Anthropic 的工具设计与评测文章、OpenAI 的工程与评测资料、Vercel 的 CLI 指南，以及 GitHub、Google Cloud、AWS、HashiCorp、Stripe 的具体接口文档。独立作者包括 Mario Zechner、Armin Ronacher、Simon Willison 和 Justin Poehnelt。搜索用于发现材料，论证依据是可读正文中的相关部分，不把搜索摘要当作已读证据。

资料阅读与关键来源复核日期为 **2026-11-17（北京时间）**。长文按问题选择相关章节，PDF 阅读任务选择、工具设计与人工介入章节。部分网页的直连读取被拒绝或未完整返回，改用能够取得正文的公开网页读取方式；未把失败返回当作阅读成功。本报告不评选最新 API 版本，也不依赖某个厂商当时的 beta 参数。

全文区分三种证据：

- **官方资料与团队自述**：支持它们公开描述的契约和工程经验；内部统计或团队估算不自动外推。
- **个人实践与判断**：保留作者的场景和局限，不写成行业定论。
- **本文综合建议**：任务卡、职责隔离、验收分层及阶段安排是本报告的设计建议，不冒充某篇来源已验证的完整方案。

本次完成的是文献研究与工程方案，**没有实现示例 CLI，没有运行 Agent 对照基准，也没有证明成功率、成本或生产率收益**。文中的报表任务、命令和 JSON 均为自拟示意。

## 二、关键发现：工具设计需要一条闭环

Anthropic 在《Writing effective tools for agents》中把工具看作确定性软件与非确定性使用者之间的契约：先做原型，用真实任务评测，观察错误，再改善描述、边界和返回信息。它还建议记录工具调用、耗时、token 和错误，并使用留出任务检查改进是否泛化。[1]

《Demystifying evals for AI agents》进一步区分任务、一次尝试、执行轨迹和环境结果。文章举例：Agent 在最终回答中说机票订好了，与环境中确实存在预订，是两件不同的事。[2] 对 CLI 而言，退出码、成功文字和作者的完成总结都只是证据的一部分，最终仍要核实用户需要的状态。

OpenAI 的《Harness engineering》把工程师的重要工作放在环境、约束和反馈上：让 Agent 能启动隔离的应用、查询日志指标、理解结构化知识，并把关键约束机械化执行。[3] 这是具体团队的实践，不是“所有工程团队都应取消人工评审”的证明。

这些资料共同支持以下研究方向：

```text
真实用户任务与约束
        ↓
领域能力与成功定义
        ↓
作者 Agent 实现最小纵向切片
        ↓
独立使用者 Agent 经公开接口处理任务
        ↓
可信验证器检查目标状态和禁止变化
        ↓
轨迹分析 → 失败归因 → 最小修复 → 回归与留出集
        ↓
经授权的真实服务验收与持续监测
```

“作者、使用者、验证器分离”首先是职责、上下文和权限的分离，不要求部署一个持续运行的多 Agent 群。同一个模型的隔离会话也可以承担不同角色；换成不同模型只能增加观察角度，不能替代客观验证。

### 顶级团队与开发者的分歧，怎样转化成设计判断

| 来源 | 直接支持的判断 | 不能由此推出的结论 |

| Anthropic 工具设计与评测 [1][2] | 用任务评测改工具，区分轨迹和真实结果 | 某种命令语法对所有模型最优 |
| OpenAI harness engineering [3] | 改善环境可读性与可执行约束，让反馈更可靠 | 厂商估计的效率提升可以普遍复现 |

| Armin Ronacher [23] | harness 与工具执行环境有不同信任和文件系统边界 | 一个 Shell 就能替代图像注入、子 Agent 等所有原生能力 |

## 三、从用户任务出发：先写清楚什么算解决了问题

容易走错的起点是“把 API 全做成命令”。更好的起点是：用户目前哪个完整工作流很痛苦，什么结果会让他认为问题确实解决了？

Anthropic 与 OpenAI 的通用实践都建议先找简单可行方案，再按需要增加复杂度。若确定性查询或脚本足够，不必让 Agent 每次重新推理；若现有工具已满足任务，也不必为接口新颖而重写。[4][5]

### 任务契约卡

建议从获得授权使用的工作记录、手工操作和用户反馈中提炼任务，而不是只由作者 Agent 编造理想案例。

| 项目 | 应写清的内容 |
|---|---|
| 用户原话 | 保留用户表达，不只留工程师改写后的命令需求 |
| 初始状态 | 已有资源、数据、身份和环境 |
| 目标结果 | 需要交付的信息、制品或状态变化 |
| 成功证据 | 用什么独立证据证明结果成立 |
| 不变量 | 哪些资源、配置和数据绝对不能改变 |
| 授权范围 | 可以读取什么，哪些操作需另行批准 |
| 歧义处理 | 哪些信息缺失时必须澄清，不能猜测 |
| 预算 | 时间、费用、调用量和数据暴露边界 |
| 恢复与停止 | 何时可重试，何时先核对，何时交还人类 |

Agent 可以起草任务卡，但不能替用户决定业务规则。选哪个同名客户、允许重跑哪个任务、是否接受额外费用，都需要已确认的领域规则或用户判断。

### 贯穿案例：诊断并按批准重跑报表任务（自拟）

用户请求：

> 找出昨天失败的报表任务并解释原因；先不要重跑。等我确认后，只重跑指定任务，把正确的结果文件交给我。

成功条件不是“实现了重跑命令”，而是找到授权范围内的相关失败，依据证据解释原因，未批准前不重跑；批准后只执行指定任务，网络故障不造成重复执行，最后交付可获取、内容正确的文件。

“昨天”必须由已知用户时区换算为明确时间区间；同名报表或多个环境有歧义时需要澄清。文件生成成功但无法交给用户，仍没有完成整个工作流。

### 选一个最小纵向切片

第一个切片可以只读：**查找失败任务 → 检查状态和日志 → 交付有证据的诊断**。第二个切片再增加：**审批 → 重跑精确任务 → 等待或恢复 → 验证并交付制品**。

优先考虑用户价值、频率、失败代价、可验证性和实现成本，不追求命令覆盖率。切片可以暂时只读，但应该完成一个真实问题，而不是只证明 API 能连接。

## 四、领域能力先于命令，CLI／MCP／SDK 是适配层

“查找失败任务”“解释失败”“重跑已批准任务”“核对结果”是领域能力，未必与 API 端点一一对应。Anthropic 建议围绕高价值工作流设计工具，而非机械包装全部底层函数。[1]

合理的折中是：提供稳定、可组合的基础能力；对反复出现且语义明确的工作流增加有边界的组合能力。组合不能隐藏收费、通知、发布或权限扩大。

```text
领域规则／输入验证／权限／状态转换／审计
                         ↓
                  CLI   SDK   MCP
```

业务与权限内核应尽可能共用，避免 CLI 检查审批而 SDK 不检查，或 Agent 模式与人类模式执行不同业务规则。适配层可以不同，必要约束不能只存在于帮助文字中。

| 接口 | 优势场景 | 主要成本或边界 |
|---|---|---|
| CLI／Shell | 本地文件、现有工具链、管道、可复现工程操作 | 转义、进程和环境差异，较大的执行权限面 |
| SDK | 类型检查、批量处理、复杂循环与恢复 | 语言依赖和版本维护 |
| MCP | 跨客户端发现与结构化调用、远端集成 | 客户端差异、认证、工具发现和运维开销 |
| 沙箱 Code Mode | 大工具集、动态发现、上下文外批处理 | 安全运行时、资源限制、持久化和调试 |

Mario 的实践与代码执行方案在一点上相通：能在执行环境中筛选、聚合和传递的数据，不必反复经过模型。[20][21][22] 因而应比较数据在哪里处理、凭据由谁持有、权限在哪里执行，而不是简单宣布 CLI 战胜 MCP。

还需区分“供 Agent 调用的 CLI”和“终端里运行的 Agent”。后者可能有优秀交互体验，却因为提示框、编辑器、分页器和不稳定输出而不适合被另一个 Agent 自动调用。

## 五、作者、使用者与可信验证器：怎样分开而不徒增系统

### 作者 Agent：构建能力，但不拥有最终判定权

作者可以读取公开任务、领域规则、源码、开发测试和已公开失败案例，负责实现、帮助、Schema、开发测试与版本制品。它不能自行重定义成功，不能修改受保护的验收器，也不能只凭自述宣布整个工作流已完成。

长任务应逐片推进，保留已完成证据、未解决问题和接续入口。Anthropic 的长运行演示指出，模型会试图一次做太多，也会在看到部分功能后过早宣布完成；增量工作与实际端到端验证用于应对这些问题。[6] 演示偏向 Web 应用，其作者也没有断言多 Agent 必然优于单 Agent。

### 独立使用者 Agent：第一次接触工具的助手

使用者拿到用户任务、公开文档、待发布制品、指定权限和预算，在新的上下文中自行发现、调用、恢复与汇报。它不读取作者会话、源码、隐藏答案或评测器，也不直接改后端绕过接口。

如果只有作者自己会用，接口就还没有通过使用验收。另一方面，不能为了制造难度而隐藏正常用户会获得的公开文档或技能说明；应测试真实部署的发现路径。

### 可信验证器：检查环境事实与禁止变化

验证器优先采用确定性断言，读取获准的权威状态、审计记录和制品内容。使用者不必拥有数据库权限；独立验证程序可以在受控环境中只读检查。

它既检查目标是否达到，也检查没有发生什么：是否重复执行、是否修改其他任务、是否越过审批、是否泄露秘密、是否产生额外收费或通知。开放式诊断质量才交给模型评审，并以领域专家判断校准。[2]

“可信”指验证器、输入快照和证据渠道受到保护，不代表它不会写错。作者不能修改验收程序、伪造测试日志或替换后端来刷通过；验证器本身也需要参考解、失败样例和人工抽查。

### 公开规范，隐藏变体

开发集向作者开放；留出集隐藏具体数据、故障位置和边界组合，但不隐藏业务规则。Anthropic 明确指出：任务没规定脚本路径，评测却假设固定路径，是任务或评分器的问题。[2]

隐藏测试用于减少迎合，不是增加秘密要求。测试泄露或长期反复调优后，应补充新的盲测变体；已确认的失败可以转为公开回归案例。

## 六、CLI 契约：让 Agent 容易判断下一步

下面的契约是本文综合建议。对结构化资源操作使用完整契约；对简单文本转换、原始文件和无副作用命令按需裁剪。Vercel 与传统 CLI 指南都强调结果、诊断、交互和兼容性的边界。[11][12]

### 1. 渐进发现与语义例子

```bash
tool --help
tool jobs rerun --help
tool schema jobs.rerun --format json
```

帮助应在未登录、离线和配置损坏时仍能读取，且不触发业务工作。复杂命令的 Schema 给出输入、输出、约束、权限、副作用、状态和错误，尽量由真实定义生成。

Schema 解决结构有效性，却不能表达所有使用语义。何时需要某个可选字段、两个参数能否同时使用，需要简洁真实的例子。Anthropic advanced tool use 把按需发现、代码调用和使用示例分别用于不同瓶颈，不建议为每个任务堆齐所有机制。[7]

### 2. 输出是契约，而不是屏幕内容

| 输出种类 | 合适形式 |
|---|---|
| 有限结构化结果 | 一个完整 JSON 文档 |
| 日志、事件或增量结果 | 声明记录含义的 NDJSON |
| 归档、图片、下载文件或透传文本 | 约定媒体类型的原始字节 |

stdout 只承载约定结果，stderr 承载诊断。机器模式禁用动画、颜色码和成功闲聊，不返回被截断的非法 JSON。机器错误若写 stderr，就明确规定错误 JSON 与警告如何区分，不让纯文本混入后仍要求调用者解析。

成熟 CLI 应保留既有脚本合同，提供显式格式选项；不要仅因为 stdout 被管道连接就悄悄改变数据类型。TTY 检测主要帮助呈现与交互，不能承担权限判断。

### 3. 非交互、认证与 stdin

缺参数、缺认证或缺审批时返回明确错误，不能挂起、偷偷开浏览器或默认同意。首次建立认证与自动化复用授权是不同阶段；部署环境按需采用短期凭据、工作负载身份或凭据代理。

`--json` 选择格式，非交互模式禁止提示，`--yes` 表达某种确认，三者不是同一件事。[11] Google Cloud 的资料还提醒，关闭提示可能使用默认值，因此必须核实具体行为。[14]

支持文件输入与 `-` 读取 stdin，并声明编码、大小和批量语义。stdin 用作 payload 后，不能同时读密码或确认。能够直接启动进程时优先传 argv 数组，不把不可信文本拼成 Shell 程序。

### 4. 筛选、分页与上下文成本

优先服务端筛选和字段投影，再分页、聚合，最后把必要结果交给模型。GitHub CLI 的 `--json` 字段选择是具体参考，但只适用于文档明确支持的命令。[13]

必须区分 API 页大小、总返回上限、是否遍历所有页，以及终端分页器。AWS 文档明确展示 `--page-size` 并不是总输出限制。[15] 游标绑定筛选、排序和上下文；没有快照一致性时，不承诺翻页期间绝不遗漏或重复。

返回下一页游标和完整性信息，不能用“没有更多显示”冒充“没有更多数据”。客户端 `jq` 可以减少进入模型的文本，但不一定减少服务端查询、网络传输或敏感数据获取。

### 5. 错误必须指导安全恢复

退出码表达粗分类，结构化错误说明稳定错误码、参数位置、是否已有副作用、能否重试、前置恢复动作及请求标识。错误分类和退出码由工具文档定义，不宣称存在所有 CLI 通用的枚举；`diff` 等既有特殊语义应保留。

Google Cloud 明确不建议依赖 stderr 的自然语言措辞，也说明非零退出时可能已产生部分结果。[14] 因而 Agent 不能把所有失败都当作无副作用、可立即重试。

### 6. 超时、幂等与并发

区分单次请求超时、整个命令时限和等待远端完成的时限。异步任务需要可查询状态；停止本地等待不等于取消远端任务，发出取消请求也不等于取消已完成。

写操作按需提供服务端幂等键、请求内容匹配、保留期、revision／ETag 和条件更新。Stripe 的具体幂等语义说明，重试保证依赖服务端契约，不只是一个客户端选项；不同 API 版本的失败恢复也不同。[18]

服务端可能已执行但响应丢失时，先核对操作结果，不要换一个幂等键重做。本地锁不能解决多主机对同一远端资源的并发写；幂等也不替代乐观锁或业务一致性。

### 7. dry-run、计划与批准

必须说明 dry-run 是本地参数检查、远端读取预测，还是产生可执行计划。Terraform 提供保存计划与后续执行的参考，同时提醒状态漂移；apply 失败还可能留下部分变更，而不自动回滚。[16][17]

Stripe pay 的文档要求先确认精确收款人、金额、币种和资金来源，再使用确认选项；这提供了具体交互参考，但文档要求本身不证明存在不可绕过的人工审批。[19]

高风险操作的审批应绑定精确目标、计划摘要、调用主体、权限、有效期和相关资源版本。这里更强的外部审批绑定是本文建议：Terraform 会把传入保存计划视为批准；对于能自行生成计划的 Agent，持有计划不证明用户同意。[17]

### 8. 大输出、兼容和审计

大文件保存为受控制品，返回摘要、制品标识、大小、类型、校验和、归属执行环境、保留期和访问方式。本地路径不是跨主机资源；只说“已写文件”不能证明用户能获取。

分别管理 CLI、输出 Schema、协议和后端版本，兼容性包括默认值、排序、枚举、空值、分页和错误，不只是字段名。审计关联用户授权、任务、CLI 进程、远端请求和最终资源，避免默认记录全部敏感参数。

调用者标签是可观测元数据，不是可信身份；权限应来自实际认证主体。MCP 的工具 annotations 也不能被无条件当作安全证明。[27]

## 七、一个完整但有边界的示例

以下命令、资源 ID 和字段均为自拟设计，不对应现有产品，也未在真实服务运行。

### 发现、读取与计划

```bash
tool schema jobs.rerun --format json

tool jobs list --status failed   --from 2026-11-16T00:00:00+08:00   --until 2026-11-17T00:00:00+08:00   --context staging --limit 20   --fields id,report_name,status,revision --format json --no-input

tool jobs inspect job_123 --context staging --format json

tool jobs rerun job_123 --context staging   --if-match 7 --plan --format json --no-input
```

时间区间是示意任务在已知时区下对“昨天”的展开。计划只描述将要重跑的精确任务，不产生重跑副作用。

列表可返回：

```json
{
  "schema": "tool.jobs.list/v1",
  "status": "succeeded",
  "context": {"environment": "staging", "project_id": "project_123"},
  "data": [
    {"id": "job_123", "report_name": "daily-report", "status": "failed", "revision": "7"}
  ],
  "page": {"next_cursor": null, "has_more": false},
  "request_id": "request_123"
}
```

`has_more: false` 只说明该次分页已结束，不额外承诺数据库快照隔离。资源 ID 和 revision 用于下一步，不应为了省 token 而丢掉必要操作依据。

### 批准后执行

```bash
tool plans apply plan_123   --approval-ref approval_123   --idempotency-key operation_123   --format json --no-input
```

`approval_123` 是审批记录引用，不是“字符串存在就放行”的凭证。执行端应验证它与主体、计划、目标、版本及有效期的绑定。若执行变成异步任务，返回 `accepted` 和任务标识，不说报表已经完成。

### 请求发出但结果未知

stderr 的错误合同可为：

```json
{
  "schema": "tool.error/v1",
  "status": "unknown",
  "error": {
    "code": "OUTCOME_UNKNOWN",
    "message": "请求已发送，但尚未确认执行结果。",
    "retryable": false,
    "recovery": {
      "action": "inspect_operation",
      "operation_id": "operation_123"
    }
  },
  "request_id": "request_456"
}
```

这里的 `retryable: false` 表示当前不能盲目重放，应先按操作标识核对，不表示永久无法恢复。结构化地报告未知，比误报失败后诱导重复写入更可靠。

## 八、安全边界：把风险分开，而不是堆一个万能保护词

不同问题需要不同保护：

| 风险 | 主要保护 | 不能替代它的做法 |
|---|---|---|
| 用户目标不清 | 澄清、精确目标、已确认领域规则 | 模糊匹配后自动执行 |
| 未授权写入 | 最小权限、可信审批、执行端策略 | Agent 自己补 `--yes` |
| 不可信内容诱导操作 | 数据与指令隔离、能力限制、出口控制 | 只提醒模型小心或只做文本清洗 |
| Shell／路径／URL 注入 | 按字段验证、正确编码、argv 调用、路径边界 | 禁掉所有自由文本特殊字符 |
| 秘密泄露 | 凭据代理、受控输入、脱敏、最小可见性 | 把环境变量当天然保险箱 |
| 重复写和覆盖 | 幂等、条件更新、权威状态协调 | 无限重试或仅加本地锁 |
| 评测作弊或误判 | 保护评分器、干净试验、参考解、人工校准 | 让作者自行修改通过条件 |

Simon Willison 的分析强调私有数据、不可信内容和外部通信能力的危险组合。[24] Anthropic 与 OpenAI 的安全资料则把文件系统／网络限制和审批策略分开。[25][26] 沙箱限制能做什么，批准决定何时可以做，两者都不保证模型永远理解正确。

秘密不放 argv、普通日志或调试输出。环境变量也有继承和日志泄露风险；根据部署环境使用凭据代理、受控文件描述符或权限受限文件。外部文本即使出现在工具错误和轨迹中，也不能变成授权。评审 Agent 读取这些材料时同样要防注入。

不必给本地文本转换工具增加审批服务器；但付款、删除、公开发布和生产变更不能仅依赖一段技能说明。这是按后果设计，而不是按“是否由 AI 调用”统一加锁。

## 九、验证真实结果：目标、禁止变化、约束与汇报

可信验证器应回答四个问题：

1. **目标状态是否成立？** 指定任务是否完成，文件内容是否正确？
2. **禁止变化是否发生？** 是否重跑其他任务、重复创建、越环境或泄密？
3. **过程约束是否遵守？** 是否取得必要批准，是否超预算或绕权限？
4. **最终汇报是否忠于证据？** 是否把运行中说成完成，把查询失败说成没有结果？

只看最终状态可能遗漏“先越权再恢复”的行为，所以还需要受保护审计；只看调用日志又可能无法证明真实资源已经改变。因此，状态证据和过程证据相互补充。[2][9][10]

若执行和检查都从同一个错误本地缓存读取，两者一致也不构成独立证明。优先权威远端查询、独立审计和制品检查；缺少独立证据时说明验证强度。

对最终一致性设置有界等待与清晰终态；在预算内仍不能确认，就保留 `unknown`，不靠无限轮询制造确定性。一般不要规定唯一正确命令序列，但审批、安全和预算等必要过程约束必须检查。

### 三级环境，三级结论

- **本地隔离模拟**：适合状态机、契约、故障注入，不能证明真实认证和限流。
- **真实服务测试账户**：验证实际权限、分页、异步回调、网络失败和一致性。
- **明确授权的有限生产验收**：限定目标、数量、费用、时间、停止与回滚条件。

模拟通过不等于真实服务通过；真实测试账户通过不等于获准操作生产用户。测试后的外部清理同样属于操作，需要处在授权范围内。没有条件验证的层级应标为未验证。

## 十、Trace 与失败分类：每次修复都要有因果假设

轨迹记录用户任务与授权、制品和配置版本、执行环境、脱敏调用、标准流、退出状态、请求和作业标识、状态断言、耗时与费用。不需要强求模型披露隐藏思维；可观察操作、返回值和简短决策说明已能支持大量归因。

OpenAI 的 trace grading 用于定位工具选择、交接和规则遵守问题；重复数据集用于稳定比较。[9][10] 这些方法不替代最终状态验证，也不要求绑定某个特定评测平台。

| 失败类型 | 首先检查或修改的层 |
|---|---|
| 用户目标被误解 | 任务卡、歧义处理和领域规则 |
| 缺少必要操作 | 补最小能力，不扩成全能工具 |
| 找不到正确命令 | 命名、帮助和渐进发现 |
| 参数反复写错 | 输入结构、Schema 与示例 |
| 结果无法理解 | 字段、状态、错误与恢复契约 |
| 认证或目标环境错误 | 身份、作用域和部署配置 |
| 超时后重复执行 | 幂等及结果核对 |
| 并发覆盖 | 版本条件与权威协调 |
| 完成但汇报错误 | 验证步骤和证据映射 |
| 正确实现被判失败 | 任务歧义、评分器或环境污染 |

不要把所有失败归结为模型不够聪明，也不要每次都加提示词。针对失败提出一个可检验假设，只改必要层，固定其他条件比较。修复经过重复验证后进入回归集，同时在未参与调优的留出任务上检查泛化。[1][2][8]

## 十一、评测怎样公平，指标怎样不骗人

至少保留现有工具基线，再比较改善契约后的 CLI、加入必要领域能力后的方案，以及适用的 SDK／MCP／Code Mode 路径。模型、任务初始状态、权限、审批政策、数据、预算与故障条件尽量一致，分别测冷启动和熟悉后的表现。

每轮从干净环境开始，避免缓存、历史资源或上轮日志泄露答案。多次尝试、随机化执行顺序，并报告不确定性；不把基础设施故障悄悄归给模型，也不把失败试验随意剔除。[2]

### 建议记录的指标

| 指标 | 判断意义 |
|---|---|
| 安全完成率 | 达到目标且没有越权副作用的尝试比例 |
| 恢复成功率 | 遇到预设失败后仍正确恢复的比例 |
| 越权尝试与实际越权 | 分别暴露模型行为与执行边界问题 |
| 合法任务误拒 | 避免只靠阻止一切获得漂亮安全分 |
| 模型轮次、工具调用、错误和重试 | 找出发现、接口和恢复成本 |
| 输入／输出／缓存 token | 比较模型上下文开销 |
| 端到端与尾部耗时 | 观察用户等待及异常长任务 |
| 总费用与每个安全成功任务成本 | 包含模型、服务 API、运行环境与可归属成本 |
| 汇报真实性 | 最终结论与环境证据是否一致 |

拒绝未授权删除应是正确结果，不应按任务未执行判失败。评测既要有应执行案例，也要有应停止、澄清或拒绝案例。中间完成度可以用于诊断，但不能抵消关键安全约束失败。

多次尝试中挑一次成功，只能说明有成功路径，不能代表一次实际执行的可靠性；对有副作用的任务，失败尝试还可能已经改变环境。报告总体指标时同时给出任务类别、样本、运行条件和限制，不把零次观察到攻击成功写成安全证明。

### 必测的失败与安全场景

- 服务端执行完成但响应丢失；两个进程或主机重复提交。
- 读取后版本改变、计划过期、批量部分成功、游标失效。
- 凭据过期、权限撤销、限流、任务仍在运行时本地超时。
- SIGINT、磁盘写满、大输出、乱码、下游提前关闭管道。
- 名称含 Shell 元字符、路径穿越、恶意 URL 和提示注入。
- debug／错误／审计泄密，评分器被恶意轨迹诱导。
- 新旧 CLI／Schema／后端组合，以及制品处于另一执行环境。

本报告只提出测试方案，没有运行并得出测量值。

## 十二、实施路线：每个阶段留下可检查产物

| 阶段 | 主要工作 | 产物与放行条件 |
|---|---|---|
| 任务定义 | 提炼获准使用的真实工作流，确认价值和约束 | 人类确认的任务卡与不变量 |
| 验收定义 | 正常、歧义、失败、安全案例；验证任务可解 | 开发集、留出集、参考解与状态断言 |
| 能力建模 | 定义资源、主体、状态转换和副作用 | 最小能力图、权限表和错误恢复语义 |
| 接口原型 | 帮助、Schema、少量例子与有界输出 | 新使用者能够发现和调用的原型 |
| 隔离实现 | 作者逐片构建，做单元和契约测试 | 固定版本制品及开发证据 |
| 黑盒验收 | 新会话使用发布制品处理任务 | 轨迹、真实状态断言、耗时与费用 |
| 证据修复 | 分类根因、最小修改、回归与留出比较 | 改善证据与未解决风险 |
| 真实服务验收 | 在授权测试账户验证真实集成 | 环境能力矩阵，不把未测项写成通过 |
| 受控发布 | 确认范围、监控、停止和恢复方案 | 有依据的发布决定与后续反馈 |

可以从一条只读工作流和简单脚本式验证器开始。无需先购买评测平台，也不需要一次构建完整命令树。稳定重复的步骤应尽量固化为确定性代码，而不是每轮重新交给 Agent 猜。

人类保留用户目标、领域规则、风险容忍度、隐私和费用边界、不可逆动作批准、验收规范变更及安全例外的决定。Agent 可以给出建议和证据，但不能为了优化分数自行放宽这些条件。

## 十三、可复用 Prompt 模板

以下是未来经授权实施时的模板，不是本报告已经执行过的开发任务。

### 设计／作者 Agent

```text
你为真实用户工作流设计最小工具能力，不以命令数量为目标。

输入：
- 用户原话和任务卡：{任务}
- 已确认领域规则：{规则}
- 授权环境与动作：{范围}
- 成功条件、不变量、预算：{验收}
- 现有能力和开发测试：{材料}

先交付：
1. 目标结果、歧义、必须由人判断的事项。
2. 现有工具能否解决；为什么需要或不需要新能力。
3. 一个最小纵向切片及输入、状态、副作用、错误与恢复契约。
4. 正常、失败、安全场景及独立验证方法。

只在获得实施授权后于指定隔离环境实现。
每轮修一个已归因问题，保持已通过能力。
不得修改受保护验收器、削弱约束、获取隐藏答案或接触未授权系统。
不得把退出码、stdout 或自己的声明当作最终成功证据。
输出固定版本制品、变更、验证证据、未验证项及剩余风险。
```

### 独立使用者 Agent

```text
你是第一次接触工具的使用者，不是作者。
只获得用户任务与授权、发布制品、公开帮助／Schema、指定环境和预算。

经公开入口发现能力并处理任务；不查源码、作者会话、隐藏评测，
不修改工具或测试，不走后端捷径。
缺少关键目标、权限或必要批准时，停止并说明，不猜测、不扩大范围。
超时后先判断结果是否未知，避免盲目重放写操作。
记录脱敏调用、返回、错误、耗时和可核对标识。
通过公开检查能力核对结果，权威最终断言由独立验证器执行。

输出 completed／blocked／failed／unknown：
- 已验证事实和证据引用；
- 未完成项及原因；
- 是否发生或尝试越界；
- 接口障碍与最小改进建议。
不能为了完成任务绕过安全边界，也不能只因输出 success 宣布完成。
```

可信验证器主要应由受保护代码、状态断言和审计检查组成。模型评分用于必要的开放式判断，而不是用一句“请判断是否成功”替代所有验收。

## 十四、结论与仍需验证的问题

Agent 参与设计的价值，不只是更快写出 CLI，而是让工具在开发阶段就接受独立使用：是否找得到能力，能否理解错误，失败后是否安全恢复，最终能否拿出用户问题已解决的证据。

本报告建议把质量单位从“命令实现了没有”换成“工作流是否安全完成”。作者不能自己改考卷，使用者不能自行扩大授权，验证器也必须接受正确性检查。对于简单工具保留 Unix 的可组合性；对于复杂写操作，把协调、审批和恢复放到能够真正执行约束的层。

仍需用实际任务比较：职责隔离增加的成本是否值得，任务级组合能力和细粒度命令各适合什么模型，模拟环境与真实服务的差距有多大，以及长任务多次恢复后的稳定性。这些没有脱离场景的统一答案。

**最优解应是一条不断产生可验证结果、并用失败改进自身的工程闭环，而不是一套看起来很“Agent 原生”的选项清单。**

3. **Ryan Lopopolo／OpenAI，Harness engineering**。支持环境可读性、隔离实例、知识入口及反馈；是具体产品经验，不外推生产率估计。<https://openai.com/index/harness-engineering/>
4. **Erik S.、Barry Zhang／Anthropic，Building effective agents**。支持简单可组合方案、ACI 与防错设计；历史文章的产品生态不能直接当作当前选型清单。<https://www.anthropic.com/engineering/building-effective-agents>
5. **OpenAI，A practical guide to building agents**。PDF 相关章节支持任务选择、工具设计、评测基线和高风险人工介入；通用指南不是用户授权。<https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf>
6. **Justin Young／Anthropic，Effective harnesses for long-running agents**。支持增量开发、持久化交接与端到端测试；Web 应用演示不证明本文整个职责隔离方案普适最优。<https://www.anthropic.com/research/effective-harnesses-for-long-running-agents>
7. **Bin Wu／Anthropic，Introducing advanced tool use**。支持按需发现、程序化调用和语义例子；引用机制，不推荐照抄公告中的 beta 参数。<https://www.anthropic.com/research/advanced-tool-use>
8. **OpenAI，Evaluation best practices**。支持任务专属、持续评测与人工校准；引用方法，不将方案绑定到其过渡中的平台功能。<https://developers.openai.com/api/docs/guides/evaluation-best-practices>
9. **OpenAI，Evaluate agent workflows**。支持从轨迹调试进入重复数据集评测；不能替代环境事实检查。<https://developers.openai.com/api/docs/guides/agent-evals>
10. **OpenAI，Trace grading**。支持为轨迹分配结构化标签、定位回归；轨迹评分不是任务真实结果的全部证据。<https://developers.openai.com/api/docs/guides/trace-grading>
11. **Vercel，CLI Design Guidelines**。支持能力优先、精确目标、交互／格式／确认分离、真实状态；页面说明这是目标设计，不能假定已发布命令全部实现。<https://vercel.com/design/cli>
12. **Aanand Prasad、Ben Firshman、Carl Tashian、Eva Parish，Command Line Interface Guidelines**。支持标准流、组合、stdin、超时、兼容与秘密处理；人类优先指南不是 Agent 对照实验。<https://clig.dev/>
13. **GitHub CLI 团队，gh formatting**。支持部分命令的 JSON 字段选择和 jq；不扩大到全部命令。<https://cli.github.com/manual/gh_help_formatting>
14. **Google Cloud，Scripting gcloud CLI commands**。支持显式格式、过滤、退出状态和部分失败；该页还提示不支持多个 gcloud 命令并行执行，不能把单个产品行为当通用并发能力。<https://cloud.google.com/sdk/docs/scripting-gcloud>
15. **AWS，Using the pagination options in the AWS CLI**。支持页大小、总量、游标和分页器区别；服务排序差异可能影响遍历。<https://docs.aws.amazon.com/cli/latest/userguide/cli-usage-pagination.html>
16. **HashiCorp，terraform plan**。支持计划预览、保存与漂移限制；预览不保证未来状态不变。<https://developer.hashicorp.com/terraform/cli/commands/plan>
17. **HashiCorp，terraform apply**。支持非交互、批准、锁和部分失败；传入保存计划即视为批准，部分失败不自动回滚。<https://developer.hashicorp.com/terraform/cli/commands/apply>
18. **Stripe，Idempotent requests**。支持服务端幂等键、参数匹配与保留期；不同 API 版本恢复语义不同，不等于普遍 exactly-once。<https://docs.stripe.com/api/idempotent_requests>
19. **Stripe，stripe pay**。支持机器预览、dry-run 和精确付款信息确认；能力有资格限制，文档要求不证明存在不可绕过的人工审批。<https://docs.stripe.com/cli/pay>
20. **Adam Jones、Conor Kelly／Anthropic，Code execution with MCP**。支持按需加载与上下文外处理中间结果；安全运行环境有额外成本。<https://www.anthropic.com/research/code-execution-with-mcp>
21. **Matt Carey／Cloudflare，Code Mode: give agents an entire API in 1,000 tokens**。支持 search／execute、沙箱与受限授权；标题和统计涉及其工具定义场景，不当作完整任务收益。<https://blog.cloudflare.com/code-mode-mcp/>
22. **Mario Zechner，What if you don't need MCP at all?**【个人实践】支持 CLI／代码组合与按需说明；作者承认两种方式都可能高效，对 MCP 的批评不能泛化到所有后续实现。<https://mariozechner.at/posts/2025-11-02-what-if-you-dont-need-mcp/>
23. **Armin Ronacher，What is Codemode**【个人实践】支持 harness 与执行环境边界；持久化、二进制等仍有开放问题。<https://lucumr.pocoo.org/2026/10/6/codemode.md>
24. **Simon Willison，The lethal trifecta for AI agents**【安全分析】支持私有数据、不可信内容与对外通信的组合威胁；不是 CLI／MCP 性能排名。<https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/>
25. **David Dworken、Oliver Weller-Davies／Anthropic，Claude Code sandboxing**。支持文件系统与网络隔离、受控凭据代理；厂商安全措辞不构成绝对保证。<https://www.anthropic.com/research/claude-code-sandboxing>
26. **OpenAI，Agent approvals & security**。支持沙箱技术能力与审批策略分离、执行环境分别验证；是具体产品运行时资料。<https://learn.chatgpt.com/docs/agent-approvals-security>
27. **MCP 项目，Tools，2025-06-18 规范快照**。支持发现、输入输出 Schema、结构化内容和 annotations 信任边界；引用明确日期的规范，不声称为最新版。<https://modelcontextprotocol.io/specification/2025-06-18/server/tools>
28. **Justin Poehnelt，You Need to Rewrite Your CLI for AI Agents**【个人实践】支持原始 JSON、Schema、字段控制与输入加固；重写主张和防护方式仍需按场景验证。<https://justin.poehnelt.com/posts/rewrite-your-cli-for-ai-agents/>
