# Token Pooling 感知训练：压缩检索向量时，怎样保住真正有用的匹配

多向量检索为文档中的不同部分保留不同向量，查询可以分别找到与每个语义片段最匹配的位置。表达能力随之增加，索引也会变大。Token Pooling 把相近的文档向量合并；Pooling-aware training 则进一步让模型在训练时就面对这种压缩，学习怎样把重要信息放进压缩后仍然可用的表示里。[1]

核心思想不是“压缩没有代价”，而是：**既然部署时一定要压缩，就让训练目标也对压缩后的检索结果负责。**

## 1. 多向量检索为什么需要很多空间

在 ColBERT 一类后期交互方法中，查询和文档各有一组 Token 向量。原文使用 MaxSim：

\[
S(Q,D)=\sum_{q\in Q}\max_{d\in D}q^\top d
\]

- \(Q\)：查询向量集合。
- \(D\)：某篇文档的向量集合。
- \(q^\top d\)：一个查询向量与文档向量的内积。
- 每个查询向量先找到最匹配的文档位置，再把这些匹配得分相加。

因此，一个同时询问“笔记本电脑”和“长续航”的查询，可以在文档不同位置找到证据，而不必要求整篇文档压进一个向量后仍保留全部细节。[1]

只考虑量化残差的存储量，可以写成：

\[
B=N\cdot m\cdot d\cdot b/8
\]

其中 \(N\) 是文档数，\(m\) 是每篇平均向量数，\(d\) 是每个向量的维数，\(b\) 是每个坐标的位数，\(B\) 的单位是字节。

原文以 200 个向量、128 维、每维 4 bit 为例：每篇需要 12,800 字节，即十进制 12.8 KB；一百万篇为 12.8 GB。若减少到每篇 50 个向量，残差部分变成 3.2 GB。[1] 本次重算与原文一致，但这**不是完整索引体积**，没有包括检索结构、元数据和其他编码开销。

由公式也能看出，三种压缩方式处理不同维度：量化减少 \(b\)，Token Pooling 减少 \(m\)，Matryoshka 等维度压缩减少 \(d\)。它们可以结合，但质量损失仍需联合评估。

## 2. 相近向量怎样合并，预算又怎样指定

原文的 `HierarchicalTokenPooling` 使用 Ward 层次聚类。从每个向量单独成组开始，每一步选择让组内平方距离之和增加最少的合并，得到一棵由细到粗的聚类层次。最终用组内均值代表该组，再归一化，用于 MaxSim。[1]

默认情况下，压缩作用于文档向量，不压缩查询向量；首个 Token 受到保护，不参与普通合并。

三个预算参数并不等价：

| 控制方式 | 保证或目标 | 适合观察什么 |
| --- | --- | --- |
| `max_tokens=16` | 每篇最多 16 个，包含受保护 Token | 单篇容量上限 |
| `pool_factor=4` | 每篇保留约四分之一 | 按文档长度分配容量 |
| `distance_threshold` | 使用共同的 Ward 合并距离阈值 | 按向量几何结构分配容量 |

固定上限对长短文档一视同仁；比例压缩让长文档保留更多向量；距离阈值则允许包含更多不同语义的文档保留更多组。

自适应模式可以用代表性文档标定阈值，以某个**平均向量数**为目标。平均 16 不等于每篇最多 16；换到另一种语料，平均数也可能改变。[1] 如果系统有严格的单文档内存限制，不能只用平均值作为容量保证。

## 3. 一个实际计算过的反例：均值可能改变排名

下面的二维向量是自拟例子，专门展示过强压缩如何损失局部匹配，不模拟完整 Ward 聚类或默认首 Token 保护。

- 查询：\(q=(1,0)\)。
- 文档 A：\((1,0)\)、\((0,1)\)。
- 文档 B：\((0.8,0.6)\)。

未压缩时，A 中有一个向量与查询完全一致，所以 MaxSim 得分为 1；B 得分为 0.8，A 排在前面。

若强制把 A 的两个向量合成一个均值，再归一化，得到约 \((0.7071,0.7071)\)。A 的得分降为 0.7071，反而低于 B 的 0.8。

本次运行 Python 验证了这一排名翻转。它说明一个基本事实：**合并后的向量可以很好地代表一组内容的平均方向，却不再保留其中最关键的局部峰值。** MaxSim 恰恰依赖这样的最佳匹配，所以几何上合理的聚类不一定对检索任务无损。

这不意味着真实文档应该避免所有合并，而是说明单靠后处理看不见任务的重要性，需要训练目标提供反馈。

## 4. 把压缩部署方式放进损失函数

原文示例对同一批编码结果计算两种检索损失：

\[
\mathcal L=\tfrac12\mathcal L_{\mathrm{unpooled}}
+\tfrac12\mathcal L_{\mathrm{pooled}}
\]

第一项评价完整文档表示；第二项评价按 factor 4 压缩后的文档表示。两项更新同一个编码器。[1]

这样，模型不仅要让正确文档在完整表示下得分更高，也要让压缩后的表示保留这个优势。它可以改变向量的排列方式，使容易合并的部分更紧凑，让对检索重要的差异更能承受合并。

聚类分组是离散决策，不能按普通连续函数直接求导。原文实现使用 straight-through estimator，把池化向量的梯度传回成员向量，不对聚类归属的选择本身求导。[1] 因而，这是一种梯度近似，不是“层次聚类变成了处处可微”。

实现中，`MultiVectorTokenPoolingLoss` 包装已有的多向量检索损失；`None` 对应完整表示，pooler 对应压缩表示，权重控制两项贡献。不同压缩版本复用已经算出的 Token 向量，所以增加一个 pooler 会增加聚类和打分工作，而不必为该版本再跑一次编码器。[1]

这也提示一个部署原则：训练时包含将来实际使用的压缩方式，比训练完成后临时换成完全不同的表示更直接。但是否需要多个 pooler、怎样分配权重，仍是实际任务上的实验问题。

## 5. 97.8% 的“保留率”，分母是什么

作者从相同 ModernBERT-base 初始化出两个模型，使用相同的 120,000 个 MS MARCO 三元组、一个 epoch、种子及优化设置，主要改变损失函数。随后在 NanoBEIR@13 上报告平均 nDCG@10。[1]

摘取最关键的两行：

| 推理表示 | 平均文档向量数 | 普通训练 | 池化感知训练 |
| --- | ---: | ---: | ---: |
| 不压缩 | 193.22 | 51.84 | 52.39 |
| `pool_factor=4` | 48.68 | 49.03 | 51.23 |

表中的检索分数采用原文的百分数刻度。49.03 到 51.23 是 **2.20 个点**的提高，不是自动等于“检索能力提升 2.20%”。

原文的分数保留率，是压缩分数除以**该模型自己的未压缩分数**：

- 普通训练：\(49.03/51.84\approx94.58\%\)。
- 池化感知训练：\(51.23/52.39\approx97.79\%\)。

本次重算确认了四舍五入后的 94.6% 和 97.8%，以及约 74.81% 的向量数减少。不能将 97.8% 理解成每一篇文档、每一种查询都保留同样质量，也不能把它当成完整索引的空间缩减率。

实验还比较了固定上限和自适应阈值。自适应阈值是分别针对每个编码器、每个评测语料标定，以匹配特定平均向量预算。[1] 这个校准条件属于结果的一部分，不能省略后直接套到新语料。

## 6. 实际采用时，应该比较哪些成本

这篇文章说明了一种可行的训练方式，但不意味着“一开 pooler，整个搜索系统就快四倍”。

首先，文档池化发生在编码器前向之后，主要减少保留与检索的文档向量，不直接证明编码器本身少做了四分之三的工作。其次，聚类也有成本，尤其在建索引或训练时；原文提供 GPU 内核加速选项，但具体收益依赖硬件和设置。[1]

面向实际系统，可以分开记录：

- 文档编码与池化耗时。
- 完整索引占用，而不只是向量残差量。
- 查询延迟与峰值内存。
- 平均检索质量及长文档、稀有实体、多条件查询等子集表现。

若重要条件只出现一次，它可能比重复描述更容易在平均化后丢失。应优先检查这些局部证据密集的场景，而不是只看整体平均分。
