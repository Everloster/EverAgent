# Meta Muse：从产品承诺到代理边界——官方能力、市场信号与人类兜底

> **修订说明**：旧版把一篇微信公众号 APK 静态分析中的包名、权限、端点、MCP 协议和端云架构写进了产品结论，但没有实际 APK、反编译工件或独立第二来源。本版删除这些不可复核细节，只保留 Meta 官方材料、Reuters、CNBC 和可公开定位的模型页面能支持的内容。核验时点：2026-10-20。

## 一句话结论

Muse 的真正新意不只是“会聊天”，而是把**长期目标、云端浏览器、账号连接、支付和持续记忆**组合成可代人行动的产品。它也暴露了个人 Agent 最难的问题：用户必须知道**谁在行动、用了什么数据、何时需要批准、失败后如何追责**。Reuters 披露的真人电话试验说明，模型能力、产品能力和人工兜底不能混写成同一种“AI 能力”。

## 1. 已确认的产品能力

Meta 于 2026-09-08 在美国发布 Muse，入口包括 iOS、Android、`muse.ai` 和 WhatsApp，官方称之后会进入 AI 眼镜。官方描述的工作方式包括：

- 接受任务或长期目标，生成计划并在应用关闭后继续推进；
- 打开云端浏览器、填写表单、预订行程、整理邮箱和代表用户谈判；
- 在发送邮件、购买等敏感动作前请求批准；
- 通过 Stripe Link 的一次性卡号付款，避免向商家暴露真实卡号；
- 记住用户曾经表达的偏好，并据此主动提出建议；用户可以要求它忘记具体记忆。

这些都是**Meta 的产品口径**。它们证明了产品设计目标，不等于每类任务都已经达到稳定、无人值守的成功率。

## 2. 安全设计：解决了什么，仍留下什么

### 2.1 Meta 公布的四层控制

1. **Muse Secure VM**：每位用户使用专属云端虚拟机，浏览器、连接数据和凭据在其中运行。
2. **Sentinel Agent**：与主 Agent 在系统层隔离，主 Agent 的出网动作要经过 Sentinel 审核，必要时向用户请求许可。
3. **凭据盲区**：连接服务的密码和支付信息进入安全存储；官方称 Muse 可以调用，但看不到明文。
4. **权限与审计**：用户逐个连接应用，并区分读取和代发等权限；产品提供行为审计记录，也允许随时断开连接。

Meta 还承诺，Muse 对话和 VM 数据不进入广告系统；用户可以选择不将交互用于训练。官方当时把 Confidential VM 写成“later this year”的后续能力，因此不能当作发布时已经兑现的保护。

### 2.2 这些控制没有自动消除的风险

- **目标误解**：权限正确、凭据安全，仍可能执行了用户不想要的任务。
- **长链错误**：网页内容、商家回复和第三方工具都可能改变后续计划，单次授权无法覆盖整条链。
- **代理身份不透明**：收件人或商家需要知道对方是模型、人工坐席，还是两者的组合。
- **责任分散**：模型、Sentinel、连接器、云端浏览器和人工兜底分别可能出错；审计记录必须能还原每一步的实际执行者。

因此，“隔离得好”只能证明系统减少了部分泄露和越权面，不能证明任务结果可靠。

## 3. 真人接线员事件：一次重要的边界测试

Reuters 于 2026-09-22 报道，Meta 测试了名为 **human concierge** 的机制：部分通过 Muse 发起的电话由真人承包商在后台处理。报道引用内部帖子称，一些员工担心用户会在不知情时向呼叫中心承包商透露敏感信息。Meta 回应说这是公开发布前的测试，只有在准备好并提供适当披露后才会推出。

这件事不能推出“Muse 全靠人工”，但能推出三个更稳健的结论：

1. 当时的电话能力包含人工兜底，不能作为纯模型能力的证据。
2. **披露本身是安全机制**：用户是否愿意把信息交给模型，与是否愿意交给真人承包商，是两个不同的授权决定。
3. 端到端评估必须记录真实执行链，而不能只看最终任务是否完成。

对个人 Agent 来说，HITL 不只是“人在关键点批准 AI”，也可能是“人替 AI 完成它做不到的步骤”。两者在隐私、成本和产品承诺上完全不同。

## 4. 模型能力与产品能力要分开看

Muse 使用 Muse Spark 系列模型。Meta 的 Muse Spark 1.3 页面称其面向 agentic workflow、工具调用、长上下文、代码和多模态任务，并列出知识工作、电脑操作、网页研究、业务自动化和软件工程等基准。

这些数字属于**厂商自报的模型评测**，不能直接回答以下产品问题：

- Muse 在真实账号、真实网页和真实支付流程中的完成率是多少；
- 任务失败后能否正确停下，而不是继续扩大错误；
- Sentinel 拦截了多少危险动作，又误拦了多少正常动作；
- 长期记忆是否会把过时偏好带入新的高风险任务；
- 人工兜底参与了多少任务，用户是否清楚知情。

因此，模型榜单只能说明底座的部分能力。Muse 作为产品还需要一套涵盖**规划、工具、权限、记忆、人工介入和恢复**的端到端评估。

## 5. 市场信号：启动强，留存尚未知

CNBC 援引 Sensor Tower 称，截至 2026-09-21，Muse 上线后累计下载量超过 **250 万**，其中约 150 万来自 iOS、110 万来自 Android；在相同 13 天窗口里，它超过 Claude 和 Grok，但仍低于 ChatGPT 的 310 万。Sensor Tower 同时提醒，各产品的 iOS/Android 上线节奏不同，横向比较有口径偏差。

下载量能说明 Meta 的分发能力和首发关注度，不能说明：

- 用户是否持续使用；
- 复杂任务的成功率；
- 订阅转化和单位任务成本；
- 用户是否愿意长期授予邮箱、日历、支付和记忆权限。

个人 Agent 的长期竞争力更可能取决于“每周有多少任务被可靠完成”，而不是安装峰值。

## 6. 更合适的评估框架

| 层级 | 要测什么 | 典型指标 |
|---|---|---|
| 模型 | 推理、视觉、工具选择 | benchmark 成绩、首次调用正确率 |
| Harness | 计划、重试、上下文和停止 | 无效循环率、错误扩大率、恢复率 |
| 权限 | 最小授权与高风险动作 | 越权率、误拦率、批准覆盖率 |
| 记忆 | 写入、更新、遗忘和冲突 | 错误记忆率、过期记忆调用率、删除可验证性 |
| 执行 | 真实网页、连接器和支付 | 端到端完成率、人工接管率、平均成本 |
| 透明度 | 用户是否知道谁做了什么 | 执行者披露率、审计可还原率 |

最关键的失败指标不是“答错一道题”，而是**在不确定时仍继续行动**。对发信、支付、改预约和打电话等任务，正确停下往往比勉强完成更重要。

## 7. 对用户的实际建议

- 从只读连接开始，只在明确需要时开放发送、购买或修改权限。
- 把邮件、健康、支付等高敏感域分开授权，不做一次性全量开放。
- 在电话功能有清楚披露前，不向代理转交不希望真人承包商听到的信息。
- 定期检查审计记录和长期记忆，删除过时偏好与一次性敏感信息。
- 对重要任务保留可逆步骤，例如先生成草稿、暂存购物车、预留取消窗口。

## 8. 本次修订撤回的旧结论

旧版提到的 `com.facebook.aura`、Aura/Hatch/Node 代号、约 60 项 Android 权限、MCP Server、具体域名端点、Noise/Vesta 协议、437 个 skill 类和多设备令牌等，均来自单一二手静态分析，仓库中没有 APK、哈希、反编译输出或第二来源。本报告不再把它们写成 Muse 的事实。

如果未来取得合法公开的 APK 样本，应记录版本、SHA-256、获取渠道和复现命令，再逐条恢复经独立验证的发现。

## Limitations

- Meta 官方材料属于产品方自述；Secure VM、Sentinel 和训练退出机制未在本次研究中做黑盒或源码验证。
- Reuters 报道确认的是电话功能测试，不代表 Muse 的全部任务都有人类参与。
- CNBC 下载量来自第三方估算，且没有留存、活跃和付费数据。
- 本次没有登录 Muse 做真实账号任务，因此不评价当前交互质量和任务成功率。

## 思考与追问

1. Muse 的审计记录能否明确区分模型、自动化脚本和真人承包商？
2. 用户删除一条记忆后，相关向量、摘要、日志和备份是否都能被验证删除？
3. Sentinel 的评估集是否覆盖网页提示注入、跨工具数据外泄和长期任务中的权限漂移？
4. 当人工兜底提高成功率时，产品应如何同时披露隐私成本和“纯 AI 完成率”？
