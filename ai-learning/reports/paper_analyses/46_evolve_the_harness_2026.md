# 不要训模型，进化 Harness：LAB 实验的收益与边界

冻结模型权重，改进它周围的执行系统，能让 Agent 做得更好吗？Joel Niklaus 的法律任务实验给出了一个具体答案：DeepSeek-V4-Pro 在 100 个留出任务上的**评分条目通过率从 63.4% 升至 80.1%，整题全部通过率从 0% 升至 5.0%**。交付文件处理是其中一类重要改进。[S1][S2][S4]

这说明这套系统有可修复的工程损失。它没有证明模型不重要，也没有证明代码普遍优于提示词。尤其不能把 80.1% 理解成“八成法律任务已经能独立完成”。

> **2026-10-30 修订说明**：重新读取 Niklaus 文章六章及成本图表数据，固定到 HF Space 版本 `0b5b8d1`。纠正指标混用、迁移版本和候选数量，撤回“代码一劳永逸”“token 惩罚是代码胜出的根因”等外推。2026-07-19 补入的成本来源保留，进一步注明与 Sonnet 的成绩对照并非在同一留出集上完成。旧稿中的 Karpathy 实验次数、Star 数、任职信息及其他二手数字，本轮没有重新取得直接证据，撤去“已核验”判定，不再用于支持结论。

## 1. 进化的到底是哪一层

Harness 是模型周围的执行系统：决定读哪些资料、提供哪些工具、如何执行工具调用、怎样保存产物，以及什么时候结束任务。[S1]

| 层 | 内容 | 本实验是否修改 |
| --- | --- | --- |
| 模型权重 | 训练得到的参数 | 执行模型保持冻结 |
| Harness | 提示词、工具包装、文件处理、检查和编排 | 自动搜索修改的对象 |
| 单次运行状态 | 消息、工作区文件、工具结果 | 随任务执行变化；不是权重训练 |

例如，模型已经写出法律分析，却把文件放进了临时目录。评判器只读取 `output/` 顶层下指定文件名的产物，这份分析就可能没有被评分。`deliverable_landing_gate` 在运行后把交付物放到正确位置，修的是交付过程。[S2][S4]

这类纯文件处理可以不新增模型调用。但不能据此说整个 Harness“零 token、零成本”：工具定义和结果会占用上下文，某些检查还会触发重写或多次采样。文件位置正确也不代表法律内容正确。

## 2. 实验如何设计

### 2.1 任务、角色与数据切分

| 项目 | 原文设置 |
| --- | --- |
| 基准 | Harvey Legal Agent Benchmark（LAB）；给定合同、邮件、表格等资料，要求交付备忘录、修改稿等文件 |
| 执行模型 | `deepseek-ai/DeepSeek-V4-Pro`，经 HF Inference Providers 调用，权重不更新 |
| 提议者 | Claude Opus 4.8，读取历史轨迹并修改 Harness |
| 评判者 | `claude-sonnet-4-6`，逐条按 rubric 评分 |
| 开发集 | 从 1,251 个公开任务中选 24 个，每个法律实务类别一个；候选评估每题运行 3 次 |
| 测试集 | 另选 100 个留出任务，禁止提议者读取，用于最终报告 |

来源：[S1][S2][S3]。这是 Niklaus 自建的切分，**不是 Harvey 官方未公开的 train/test 切分**。测试集尽量匹配总体分布，并强制纳入若干极端案例，例如超长输入、多交付物任务。作者因此称结果偏保守；这种构造不能在统计意义上证明它是整个基准成绩的下界。[S2]

两个指标需要一直分开读：

- **Pooled criterion pass rate**：所有评分条目中通过的比例。条目多的任务对总体分数影响更大；它不等于逐任务通过率的简单平均。
- **All-pass rate**：所有条目全部通过的任务比例。它更接近“完整交付是否达标”，但在小样本上稀疏、容易波动。

法律内容由模型裁判评分，并非独立法律专家验收。实验中的“通过”首先指满足这套 benchmark 的评分条件。

### 2.2 搜索循环与晋级条件

```text
复制当前最佳 Harness → 加入一个机制 → 在少量开发任务上试验
→ 提交假说、改动和观察记录
→ 外层脚本在 24 个开发任务上各跑 3 次
→ 与当前最佳版本比较；达到晋级门槛才保留
```

新版本继承此前已采纳的机制，所以后面的候选不是彼此独立的单项试验。提议者由 `SKILL.md` 约束；外层 `meta_harness.py` 负责运行与判定。原文要求用旧轨迹的确定性重放，或至少覆盖 5 个修复任务、5 个回归任务的对照，避免把单题一次波动当改进。[S3]

原文给出的混合目标为：

```text
score = pooled_criterion_rate
      + 0.5 × all_pass_rate
      - 0.005 × tokens_per_million
```

前两项分别是评分条目通过比例和整题全过比例，后者权重为 0.5；最后一项惩罚 token 消耗，以百万 token 为单位。按比例口径，0.005 对应 **0.5 个百分点**，不能把百分数展示值直接代入而保持其余单位不变。原文把 `min_delta=1` 解释为晋级需高出 **1 个百分点**。[S3]

三次运行是成本与噪声的折中。附录根据三个单次结果估计，均值噪声约从 1.4 个百分点降至 0.8 个百分点，再选择 1 点门槛。这是作者的经验性选择，不是对反复搜索后误晋级概率的严格控制。[S6]

**目标含成本惩罚，只能说明搜索同时考虑成本。** 要证明它导致代码候选胜出，需要在相近搜索预算下移除或调整惩罚项，并比较结果。原文没有报告这项消融。

## 3. 收益来自哪里

### 3.1 整体结果

| 数据集与指标 | 原版 LAB Harness | 最终进化版本 | 变化 |
| --- | --- | --- | --- |
| 开发集：pooled | 63.1% | 83.3% | +20.2 个百分点 |
| 开发集：all-pass | 0% | 4.2% | +4.2 个百分点 |
| 留出测试集：pooled | 63.4% | 80.1% | +16.7 个百分点 |
| 留出测试集：all-pass | 0% | 5.0% | +5.0 个百分点 |

来源：[S2][S4][S5]。原文没有给出这里所有差异的置信区间。开发集反复参与选择、测试集分布也不同，不能仅凭两者增益差 3.5 点，就断言“过拟合”或“完全正常”。留出结果提供了泛化证据，但外推仍受任务规模与评分方式限制。

### 3.2 四类机制

| 机制 | 修复的问题 | 证据与限制 |
| --- | --- | --- |
| 交付文件处理 | 文件名、目录、分块写入覆盖造成产物缺失 | `deliverable_landing_gate` 使当时开发集 pooled 从 72.8% 升至 79.2%；这是继承已有机制后的增量 |
| 案件一致性检查 | 读了干扰案件，生成针对另一件纠纷的答复 | 检测后要求重写，最终版本还含小规模 best-of-N 投票；不能归为纯文件操作成本 |
| 执行健壮性 | 损坏的工具调用、重复循环 | 有跨模型受益案例，仍依赖接口及故障类型 |
| 提示词 playbook | 分析、起草、修订的工作方法 | 两个提示词 playbook 较早进入最佳版本，后续纯提示词候选未超过代码较多的版本 |

来源：[S3][S4]。原文还展示了从写入历史重组被覆盖长文的例子：恢复的是模型已经产生的内容，而非凭后处理补出新的法律论证。这解释了为什么某些低分任务能因工程修复出现大幅变化。

原文说“得分最高的六个 **Harness 候选中五个属于代码类**”，旧稿将它写成“最强六处改动中五处是代码”，把候选排名误当成了独立贡献排序。更关键的是，候选景观包含 **4 个纯提示词、14 个纯代码、1 个混合候选**，搜索量并不均衡。原文也明确表示，这不能证明提示词已耗尽潜力。[S4]

### 3.3 同模型、不同 Harness 的差异

| Harness | 留出集 pooled |
| --- | --- |
| Pi | 45.4% |
| Goose | 23.2% |
| mini-swe-agent | 3.5% |
| 原版 LAB | 63.4% |
| 最终进化版本 | 80.1% |

作者使用相同模型、裁判和任务比较这些包装，通用 Harness 沿用原版 LAB 合同，没有加入搜索发现的机制。预期交付文件类型的产出比例分别为 Pi 75/100、Goose 26/100、mini-swe-agent 7/100；超时也计入失败。[S2]

这组结果说明，**任务适配和执行行为能大幅影响同一模型的得分**。3.5% 与 80.1% 的比值不能解释为“智能提高二十多倍”；此表也没有同时比较多种模型升级方案，因而不能证明换 Harness 的收益普遍大于换模型。

## 4. 跨模型迁移测到了什么

迁移实验使用的是中途版本 **`deliverable_landing_gate`**，不是达到 80.1% 的最终版本。作者将这套中途 Harness 不作修改地用于相同留出集：[S4]

| 执行模型 | 相对该模型基线的 pooled 变化 |
| --- | --- |
| DeepSeek-V4-Flash | +14.4 个百分点 |
| Nemotron-3 Ultra | +0.4 个百分点 |

作者解释 Nemotron 的低净增益时，指出两个相抵的效果：工具调用 JSON 修复清除了崩溃，DeepSeek 定制的提示词却伤害了部分原本能完成的任务。[S4]

由此可保留的结论是：**这套 Harness 的净收益依赖执行模型；某些健壮性修复具有迁移价值，定制指导可能产生负迁移。** 原文自身把它概括为“代码能迁移、提示词不能”，但本文不将其提升为全称规律：这里只测试了有限模型和一个组合版本，没有覆盖所有组件、模型与任务的拆分对照。

[推测：工程含义] 换模型时，应检查提示词是否仍有帮助，也检查工具协议、文件约定和重试语义是否仍适用。确定性代码只保证写明的检查条件，仍需要维护；领域方法也可能跨模型有效，不能一概丢弃。

## 5. “成本只有 1/7”究竟怎么算

2026-07-19 的补证方向是对的：出处在交互图表的 JSON 数据中。本轮重新读取固定版本文件，得到：[S7]

| 图表对象 | all-pass | 按固定轨迹估算的 agent 成本 |
| --- | --- | --- |
| 最终 Harness + DeepSeek V4 Pro | 5.0% | $77.3 |
| Sonnet 4.6（图中引用的外部成绩） | 5.4% | $546.9 |

`546.9 / 77.3 ≈ 7.08`，但这是**同一 token 工作量按不同刊例价计算的比值**。输入轨迹来自 DeepSeek V4 Pro 基线的 100 个测试任务：174,799,637 个输入 token、1,502,524 个输出 token。数据注明 `agent_rollout_only`，排除共同的 Sonnet judge 费用、各模型用词与分词差异、缓存和长上下文附加费。[S7]

因此：

1. $77.3 也不是最终进化版本自己的实测账单，所有模型共用基线 token 轨迹。
2. 这不是“同一个 DeepSeek 改完 Harness 后便宜七倍”，而是与 Sonnet 刊例价的估算比较。
3. 5.0% 与 5.4% 的近似点值不能证明能力等效。Sonnet 成绩来自外部 LAB 报告，Niklaus 使用自建切分，未在此给出相同留出集上的受控对打。[S2][S7]
4. 应与正文所报成本分开：作者称一次 100 题测试实际约 $120–160（agent 约 $90–100，加 judge 约 $30–60），而多次开发评估及提议者运行还构成搜索成本。[S2]

成本图是有用的价差示意，不能直接作为部署预算或等效替代结论。这里也不把 2026 年 7 月的价格当作当前报价。

## 6. 搜索系统本身，也可能把结果测错

附录记录了几个比“自动调参”更值得复用的细节：[S6]

- **目标函数改变后使用了旧分数。** 一次候选在质量与 token 上都更差，却因与旧权重算出的分数比较而晋级。修复是用当前权重重算在任版本，不能混用历史派生值。
- **服务故障伪装成模型能力不足。** Nemotron 曾因首轮服务错误没有重试而大量失败；作者修正适配器，并在最终报告前重跑临时服务故障。与此同时，通用 Harness 自身的超时保留在失败统计里。[S2][S6]
- **长会话失败会丢掉实验。** 提议者需要恢复中断、处理认证失效、清理孤儿进程，并审计是否访问测试集。

这些记录表明，评分结果取决于可靠的测量过程。重试哪些错误、保留哪些失败、使用哪版目标函数，都应明确；“用了自动循环”本身不保证实验可信。

原文最后停在开发集约 83% pooled 的局部平台。税务案例的定量深度和引用精度仍持续失分。作者提出扩大开发集、校准更便宜的裁判、保留多个候选分支，以及继续探索提示词和工具等方向。[S4][S5] 这只是本次搜索触及的局部边界，不是模型能力的已知天花板。

## 7. 与 Karpathy、Meta-Harness 的关系

Niklaus 明确说实验建立在 **Meta-Harness** 上，并把 Karpathy autoresearch 列为相邻思路：由 Agent 修改工件，再按实验指标决定保留或丢弃。前者在这里修改法律 Agent 的 Harness；后者在该文章的类比中运行训练实验。共同点是搜索循环，优化对象不同。[S3]

旧稿标题中的“700 次 Loop”“76% 与模型无关”混入了另一条传播链。本轮没有重做那条新闻链的核验，也不推测“76%”具体怎样产生。Niklaus 本文支持的主数字是**留出集 +16.7 个百分点 pooled，以及 +5.0 个百分点 all-pass**。

[Meta-Harness 论文](https://arxiv.org/abs/2603.28052)仍是延伸阅读；本报告核对的是 Niklaus 的实现说明与结果，没有独立复现论文或 LAB 实验。GEPA、AlphaEvolve、ShinkaEvolve 等只作为原文列举的相关方向，不据此画成已证实的直接继承谱系。

## 8. 对实际项目的启示与未验证部分

[推测：工程建议] 应先辨认失败在哪里：没有取到资料、工具执行失败、产物未交付，还是内容推理本身不足。文件处理问题值得用代码检查；领域方法遗漏可能需要提示词或示例；知识与推理不足则可能需要工具、数据或更强模型。本文没有做这些路线的统一投入产出比较。

若要检验“代码与提示词谁更有效”，应分别对照组件，控制搜索预算，并把优化目标是否含 token 惩罚作为独立变量。若要检验迁移，则在目标模型上重新比较原版与候选版本，同时记录质量、耗时、token、重试和裁判成本。不要把“复现代码胜过提示词”预先写成实验目标。

本仓已有的[Agent Harness 概念页](../../wiki/concepts/agent_harness.md)、[三大设计流派](../knowledge_reports/Agent_Harness_三大设计流派解析.md)和[自进化技术路径](../knowledge_reports/Agent_自进化技术路径深度解析.md)可帮助定位这项实验。本文是受限任务上的实证案例，不能单独决定所有项目的架构。

## 思考与追问

1. **可以确认什么？** 在冻结 DeepSeek-V4-Pro 的 LAB 设置里，自动搜索 Harness 带来了留出集收益；交付与执行修复是可观察的贡献来源，提示词也曾进入最佳版本。
2. **还不能确认什么？** 代码候选相对提示词的普遍优势、token 惩罚的因果作用、整套最终 Harness 的广泛迁移，以及与 Sonnet 的能力等效，都缺少对应对照。
3. **最值得继续查什么？** 扩大未参与选择的任务后收益是否保持；哪些组件在哪些模型上有效；独立裁判或人工复核是否支持相同排序。复核报告能纠正解释，不能代替重新运行这些实验。
