# 写作与报告指南

本页是公共写作约定的主要入口，统一表达、读者反馈、元数据和按需复核。领域指南补充选材、机制和证据要求，引用本页即可。普通问答直接回答；有长期价值再保存笔记、实验或报告。

## 从当前需求开始

- 已有明确问题和交付物就直接推进，优先更新已有主题；不例行创建计划、证据模板或Reviewer任务。
- 需要旧资料时按主题取最小上下文；已知位置直接读取，不先扫描全部报告、wiki、Skill或画像文件。
- 研究方法按需看[METHODOLOGY.md](../METHODOLOGY.md)。使用用户选择的模型，记录生成/复核信息时只写真实值，未知不补造。
- 查资料、Token Plan、转写和文件传输按需使用`eacli --help`，不把session、同伴发现或套餐诊断作为写作开工前置。

## 内容怎么写

围绕问题组织内容，先说明发现和适用范围。关键事实就地引用原文、代码或真实结果，数字保留单位、时间与比较口径；作者观点、事实和个人推断分开。

### 开篇的概述与取景框

报告在正文标题后固定保留两部分：先“概述”，再“取景框 f(x)”。概述从总结、提炼和金句视角说明材料讲了什么、主要发现是什么、哪些值得记住；取景框说明作者让读者从什么角度看问题，以及用这个角度会怎样改变判断。两部分各有作用，正文再按材料自然展开。

```markdown
## 概述

概括材料的主线与主要发现，保留理解它所需的背景。

**提炼句：** 本报告对核心见解的凝练表达。

## 取景框 f(x)

**x｜问题：** 本文要回答的具体问题。

**f｜取景框：** 作者或本报告采用的核心区分、观察角度或解释框架。

**f(x)｜判断变化：** 把这个视角放回问题后，哪些信号、标准或行动会改变，何时适用。
```

概述不重复列一次 x、f、f(x)，也不塞入完整目录。提炼句可以由报告作者凝练，不能加引号或署名伪装成嘉宾原话；引用原话时须核对原文并就地标来源与位置，没有可靠引文就使用明确的作者提炼。

x 是问题而非话题名；f 是取景框，不应退化成工具清单或执行步骤；f(x) 应能从这个框架与证据推出。若概述已经回答“做了什么”，取景框就解释“为什么这样看会得出不同判断”。不要求把材料解释成数学函数，也不能换一篇文章仍是普遍正确的建议。

论文保留研究设计与外推边界，访谈区分嘉宾观点与报告推断，系统报告区分实现、测量与计划。日报等汇总型报告说明选材问题、筛选依据与主要发现，不把多条新闻拼成未经证明的单一因果结论。两部分用于正式报告，普通问答、清单条目、转写及来源附件不套用；既有报告仅在用户要求修订时调整。

### 正文的推进与回读

需要深度时保留机制、关键案例、反例和局限。章节、总结和追问按材料选择，不凑固定数量。解释应写清对象怎样变化、谁接收什么、根据什么作出下一步；一串术语省略了这些关系时，拆句并补足过程，允许改写后更长。

沿主问题检查各节的作用：它解决了哪个疑问，提供什么依据，怎样支持下一步判断。结论需要中间条件时补出条件；机制难以理解时，用能说明对象变化的例子或小图，再回到实际实现。删除与本篇研究无关的项目联想、职业八卦和重复总结；应用讨论应直接帮助理解材料或使用其判断框架。

让影响结论的条件留在结论附近，例如样本范围、指标口径、版本差异和作者尚未证实的原因。来源与适用范围简短说明即可；转写工具、下载与传输、哈希检查、运行日志和提交状态留在原有元数据、审计或任务记录中，不塞进报告正文。教学例子标明“自拟”“示意”，待做实验标明“设想”，不反复追加整套免责声明。保存代码与必要数据以便读者复算，但不把执行记录当成分析内容。

回读时合并重复铺垫与收尾，删除没有信息的强调；已经清楚的句子可以不改。否定、条件、归因和确定程度不随润色改变。副词、被动句、三项列举和标点按作用判断；不靠禁词表、字数下降或模型自评分判断文风。

完成后从原始材料反查是否漏掉关键例子、分歧或会改变结论的限制，再从正文检查 x、f、f(x) 是否相互支持。比较改写效果时，使用相同的阅读问题看读者能否找到方法、依据与适用条件；编辑检查与用户阅读评价分别记录。结构正确、检查通过或提要齐全都不能单独证明报告有用。

中文译解对照原文，说明全文翻译、摘译或概括的范围，直接解释内容；代码、参数、单位、版本、链接与引文按原意保留。需要校准语气时，按任务取用[当前阅读偏好与编辑样例](WRITING_EXAMPLES.md)，不把整份历史日志默认塞进写作上下文。

## 阅读反馈

收到具体阅读反馈时，在对应领域的既有日志中记录用户原话、所指文章或段落，以及实际改动。原因分析标为编辑判断；用户只认可整篇时，不推断其逐句认可，也不将某种写法推广为所有文章的固定要求。

需要了解阅读效果时可以轻量问一次；已有反馈就据此修改，不重复索要表态，也不把反馈等待设为每篇交付前置。用户同意实施修改，与认可修改后的阅读效果分别记录。

有可复用价值时，将原句、改写和具体原因补入样例，注明用户已评价的范围。链接、数字和渲染检查继续用于发现确定的问题；不新增“AI 味”评分、检测阈值或文风提交门槛。

## 草稿与完成状态

草稿、计划和实验笔记都可以提交，明确标注即可。`completed`表示完成本次写作目标，不自动表示通过独立复核或全部实机验收。

- `planned`：尚未开始的计划。
- `in_progress`：草稿或进行中的研究；正文开头也标明“草稿/未验证”，便于不显示frontmatter的阅读器识别。
- `completed`：当前问题已回答，局限和未验证项已经说明。
- `archived` / `superseded`：保留旧版本，不作为新的任务或当前事实。

不要求先取得82/88/92分，不要求每篇生成evidence/review文件，也不以索引更新、模型等级或独立Reviewer作为提交条件。

## 元数据

需要进入报告索引时，可使用下面的小型frontmatter；普通笔记不必为提交填写大表。

```yaml
---
title: "标题"
domain: "ai-learning"
report_type: "knowledge_report"
status: "in_progress"
updated_on: "YYYY-MM-DD"
semantic_tags: ["topic"]
---
```

领域与文件位置一致；`updated_on`是实际修改日期，不表示全部来源当天复验。tags和关联概念按实际需要填写。
`quality_schema`、`quality_tier`、`report_depth`等旧扩展不是普通新文档的必填项；需要旧严格审查工具时再显式采用其合同，不自动套用。
历史别名、已有字段、证据文件和评分保留，不能为通过新流程重写旧报告或重打分。

## 什么时候复核

普通笔记自行核对即可。重要研究或关键决策按用途确定复核范围；用户明确要求独立复核时才安排对应会话，不自动接管或创建其他Agent。

资料与可选审查工具统一由预先安装的eacli >=11.0.0提供，公开仓不提供对应源码运行入口。`scripts/edocs.sh report|full <args>`等仅供主动选用，可能执行旧版严格合同，不代表所有新报告都必须采用。历史用法见[可选严格审查与历史记录](REPORT_QUALITY_GATE.md)。
如果修改了已有报告，旧review/分数不自动证明新正文；保留原件，明确本次改动和实际复核范围，不伪造继承通过。

## 提交、索引与按需测试

`scripts/ecommit.sh`是已安装eacli的commit简写：Author来自已暂存的公开身份policy，Committer是当前真实模型或明确有效声明，新增公开内容扫描仍在eacli内存中执行并绑定实际暂存tree、提交后复验；不运行报告评分、独立Review、索引审计或Go/Python整套回归。具体约定见[提交与公开安全](PROTOCOL_COMMON.md)。
明显凭据与未获授权的原始全文不能公开。疑似私人路径、IP等只给提示，仍由作者确认适合公开；这个轻量检查不是完整隐私审计，也不证明图片或二进制安全。

索引需要更新时，主动运行`scripts/edocs.sh index --write`（`eacli docs index --repo-root ROOT --write`）。它不是提交前置，不复写报告原文；不要为迁移入口自动重生成报告或索引正文。薄脚本固定canonical ROOT、逐项转发参数，并按显式`EACLI_BIN`、`$HOME/.local/bin/eacli`、PATH检查plain版本；缺失、不可执行、非法或旧版本明确失败，不回退普通Git或寻找私仓，不自动build/install。
本仓不再要求GitHub CI。代码测试按实际改动主动选用，纯Markdown无需Go/Python全套测试；测试失败如实报告与修复，不与源码提交资格混在一起。

## 保留什么

原始来源、历史evidence/review、不可变策略版本和实验记录保留。当前目录或规则变短不改变历史结论的来源与时间；旧流程原文见[归档](archive/report-process-20261110/)。
